# 좌석 선점 락 방식 비교 (동시성 §17.1)

담당 B 강동균 · 핵심 수치 "락 방식별 TPS" · 측정일 2026-11-16

## 무엇을 비교하나

| 비교군 | 방식 |
|---|---|
| **A 비관적 락** | 운행 좌석 행을 미리 만들어 두고 `SELECT … FOR UPDATE` 로 줄을 세운 뒤 상태 변경 |
| **B 낙관적 락** | 락 없이 읽고 `version` 조건부 UPDATE. 0행이면 다시 읽어 재시도 (한도 20회) |
| **C 현재 설계** | Redis `hold.lua` 1차 + DB PK 최종 (§2). 1차에서 지면 **DB에 가지 않는다** |

## 돌리는 법

```bash
# Oracle (스키마 + 시드가 들어간 컨테이너) 와 Redis 가 떠 있어야 한다
docker start jejari-verify jejari-redis

pip install oracledb redis
sqlplus -S jejari/jejari@localhost:1521/FREEPDB1 @bench/schema.sql   # 실험 테이블
python bench/lock_compare.py                                         # 기본 5회
ROUNDS=10 python bench/lock_compare.py                               # 더 돌리기
```

## 측정 방법

- 세 전략이 **같은 `picks`**(요청별 좌석 배정)를 쓴다. 전략마다 다시 뽑으면 좌석 분포가
  달라져 성공 건수부터 어긋난다. 처음에 이 실수를 해서 성공 수가 318/327/315로 갈렸다.
- 전략마다 **워밍업 1회를 버리고 5회 측정해 중앙값**을 쓴다. 1회 측정은 같은 조건에서
  TPS가 2~4배 흔들려서 믿을 수 없었다 (B 시나리오3이 227 → 905).
- 재는 것은 **락 방식**이다. 세 방식에 똑같이 붙는 비용(FK·JPA·HTTP)은 넣지 않았다.

## 결과

### 시나리오 1 · 같은 좌석 1개에 100명 (극한 경쟁)

| 전략 | 성공 | TPS | 평균ms | p95 | p99 | **DB 왕복** |
|---|---|---|---|---|---|---|
| A 비관적 | 1 | 255 | 146.9 | 227.6 | 286.7 | 201 |
| B 낙관적 | 1 | 1,457 | 11.4 | 15.8 | 16.3 | 210 |
| **C 현재** | 1 | **2,732** | **3.2** | **6.6** | **8.2** | **2** |

C가 A의 **10.7배**, B의 1.9배. DB 왕복은 **2회 vs 201회(100배)** — 패배자 99명이
DB에 아예 가지 않기 때문이다 (§2.1-4).

### 시나리오 2 · 인기 운행 좌석 20개에 300명

| 전략 | 성공 | TPS | 평균ms | p95 | p99 | DB 왕복 |
|---|---|---|---|---|---|---|
| A 비관적 | 20 | 707 | 58.7 | 106.1 | 125.0 | 620 |
| B 낙관적 | 20 | 1,825 | 15.8 | **37.7** | **43.5** | 626 |
| **C 현재** | 20 | **2,083** | **10.5** | 56.6 | 74.3 | **40** |

C가 A의 2.9배. 다만 **꼬리 지연(p95·p99)은 B가 더 좋다.** C는 패배자가 Redis 왕복
한 번으로 아주 빨리 끝나 평균을 끌어내리는 대신, 승자들의 DB INSERT가 몰려 꼬리가 길어진다.

### 시나리오 3 · 좌석 500개에 500명 (경쟁 적음) ← 예상과 달랐던 구간

| 전략 | 성공 | TPS | 평균ms | p95 | p99 | DB 왕복 |
|---|---|---|---|---|---|---|
| A 비관적 | 312 | 787 | 66.3 | 170.7 | 180.7 | 1,312 |
| **B 낙관적** | 312 | **1,256** | **35.5** | **74.4** | **99.5** | 1,321 |
| C 현재 | 312 | 756 | 65.7 | 150.1 | 180.8 | **624** |

**경쟁이 적으면 C의 이점이 사라지고 B가 가장 빠르다.** 좌석이 겹치지 않으면 Redis 왕복이
순수 오버헤드가 되기 때문이다. C는 DB 왕복만 절반(624 vs 1,321)으로 줄였다.

### 중복 예약

**세 시나리오 × 세 전략 전부 0건.** 세 방식 모두 정확성은 만족한다. 차이는 비용이다.

## 읽는 법 — 이 실험이 말하는 것

1. **C의 가치는 TPS가 아니라 DB 보호다.** 경쟁이 심할수록 DB 왕복이 100배 차이 난다
   (201 → 2). 명절 예매처럼 인기 열차 한 편에 수만 명이 몰릴 때 DB가 버티느냐의 문제다.
2. **경쟁이 없으면 C는 B보다 느리다.** Redis 한 번이 그냥 더해지는 비용이 된다.
   그래서 좌석이 널널한 평시 운행까지 Redis를 태울 이유는 없다 — 다만 운영 중에
   "지금 경쟁이 심한가"를 알기 어려워서 1차 구현은 C로 통일한다.
3. **A는 쓸 이유가 없다.** 모든 구간에서 가장 느리고 변동이 가장 크다
   (TPS 98~930). 시나리오 3에서 락 대기가 p99 **2,646ms** 까지 튀었다.

## 이 수치의 한계 (발표 때 같이 말할 것)

- **로컬 단일 머신**이다. 앱·Oracle·Redis가 한 PC에서 돌아 네트워크 지연이 없다.
- **Python 스레드**로 부하를 준다. GIL 때문에 클라이언트 쪽 병목이 섞인다.
  뼈대가 올라오면 k6로 HTTP 레벨에서 다시 재야 한다 (조영준 E 담당).
- **커넥션 풀 64 고정.** 풀 크기가 A안 결과에 크게 영향을 준다.
- A와 C의 **회차 간 편차가 크다** (A 98~930, C 113~1,223). 중앙값을 써도 아직 거칠다.
  ROUNDS를 늘리거나 조용한 상태에서 다시 재는 게 좋다.
- 실제 §2.2 트랜잭션은 여기서 잰 것보다 무겁다 (reservation·reservation_seat·
  purchase_counter·history·saga·outbox 까지 한 트랜잭션). 세 방식에 공통으로 붙는 비용이라
  비교에는 영향이 없지만 절대 수치는 더 낮아진다.

## 실험 테이블

`bench/schema.sql` 이 만든다. 실제 스키마를 건드리지 않는다.

| 테이블 | 쓰는 곳 |
|---|---|
| `exp_seat` | A·B안. 좌석 행을 미리 만들어 둔다 (`AVAILABLE` → `HOLD`, `version`) |
| `exp_seat_inv` | C안. `seat_inventory` 와 같은 모양이고 **PK 충돌이 최종 판정** |

`seat_inventory` 를 그대로 쓰지 않은 이유: 실제 테이블은 `status` 가 `HOLD`/`SOLD` 뿐이라
"비어 있는 좌석 행"을 표현할 수 없고(A·B안이 요구), FK가 걸려 있어 `reservation` 행을
먼저 만들어야 한다. 비교하려는 건 락 방식이라 그 비용은 뺐다.
