## 1. `train_run.status`의 `DEPARTED`로 누가 바꾸나 (길동현)

- [x] **A안으로 결정 (2026-11-18)** — 스케줄러가 맡는다. 구현 완료, ERD v23.
      → [팀에-알림-20261118.md](팀에-알림-20261118.md) 1번

**지금 상태**: `DEPARTED`로 바꾸는 코드가 **하나도 없습니다.** 운행은 영원히 `CLOSED`에 머뭅니다.

```
SCHEDULED --(sale_open_at 지남)--> ON_SALE --(sale_close_at 지남)--> CLOSED --(???)--> DEPARTED
                       SaleOpenScheduler 가 여기까지만 함                    주체 없음
```

**왜 지금까지 괜찮았나**: `DEPARTED`를 **읽는 코드도 없기** 때문입니다. 찾아보니

- 취소 수수료(`CancelFeeCalculator`)는 상태가 아니라 **출발 시각**(`train_stop.departure_time`)으로 판단합니다
- `SaleOpenScheduler`는 "이미 `DEPARTED`면 건드리지 않는다"는 조건에만 씁니다
- 가상 데이터 생성기가 과거 운행을 `DEPARTED`로 만들어 넣는 것이 유일하게 쓰는 곳입니다

즉 **아무도 안 쓰는 상태값**입니다. ERD CHECK 제약에만 살아 있습니다.

**제가 안 하고 물어보는 이유**: 처음엔 "승차권(TKT) 담당이 바꿀 것"으로 미뤄 뒀는데,
**기능설계서에 TKT 기능이 아예 없습니다.** 넘길 담당이 없으니 결정이 필요합니다.

**제안 (A를 권합니다)**

| 안 | 내용 | 득실 |
|---|---|---|
| **A** | `SaleOpenScheduler`에 한 줄 추가 — 막차 출발 시각이 지난 `CLOSED` 운행을 `DEPARTED`로 | 상태 흐름이 끝까지 이어짐. 10초마다 도는 스케줄러라 비용 거의 없음. **일 1시간이면 됨** |
| B | 상태값에서 `DEPARTED`를 뺀다 | 안 쓰는 값이 사라져 깔끔. 다만 ERD 패치 + DDL CHECK 변경이고, 나중에 "출발한 운행"을 구분할 일이 생기면 되돌려야 함 |
| C | 그대로 둔다 | 할 일 없음. 발표에서 "이 상태는 아무도 안 바꿉니다"를 설명해야 함 |

A로 하면 §8.3 재판매 여부 집계 배치(출발 뒤 실행)가 나중에 붙을 때 기준이 생깁니다.

## 2. ADM-03 분당 수치에 **만료 건수**를 넣을지 (길동현·강다인)

- [x] **A안으로 결정 (2026-11-18)** — `HOLD → EXPIRED` 합산으로 넣는다. 구현 완료.
      → [팀에-알림-20261118.md](팀에-알림-20261118.md) 2번

**지금 상태**: 분당 수치는 **예약 · 결제 · 취소** 셋입니다.
그런데 여기서 "취소"는 `cancellation` 행 기준이라 **결제 기한 초과 만료가 빠집니다.**
만료는 돈이 오가지 않아 `cancellation` 행을 만들지 않기 때문입니다 (ERD `cancel_type` 설명).

**왜 문제인가**: 명절 예매에서 **가장 많이 일어나는 이탈이 "좌석은 잡았는데 결제를 안 한 것"**
입니다. 지금 화면으로는 그게 안 보입니다. 예약 100건·결제 40건이면 나머지 60건이
취소인지 만료인지 구분이 안 됩니다.

이게 제 핵심 수치(**기한 초과 좌석 반환율 100%**)와 직접 이어지는 지표라, 발표 때
화면으로 보여줄 수 있으면 좋겠습니다.

**제안**: 분당 수치에 `expires`를 추가합니다.
- 집계: `reservation_history`에서 `to_status = 'EXPIRED'` 행을 분 단위로
- 화면: 분당 그래프에 선 하나 추가 (A-04)
- 비용: `ReservationStatsReader`에 쿼리 하나, 반나절

**다만 한 가지 걸립니다 — `EXPIRED`로 끝나는 경로가 셋입니다** (동시성 §7.1).

| 경로 | from → to | 뜻 |
|---|---|---|
| §6.1 HOLD 만료 | HOLD → EXPIRED | **결제 기한 초과** ← 보고 싶은 것 |
| §3 재선점 | HOLD → EXPIRED | 만료된 좌석을 남이 이어받음 |
| §5.2 결제 실패 | PAYMENT_PENDING → EXPIRED | 카드 거절 |

`from_status`로 결제 실패는 갈라낼 수 있지만, **기한 초과와 재선점은 둘 다 `HOLD → EXPIRED`라
구분되지 않습니다.** 구분하려면 `outbox_event` payload의 `reason`(`TIMEOUT`·`PREEMPTED`)을
봐야 하는데, 그건 발행되면 24시간 뒤 지워집니다(`outbox.retention_hours`).

그래서 셋 중 하나를 골라야 합니다.

| 안 | 내용 |
|---|---|
| **A** | `HOLD → EXPIRED` 를 한 칸으로 (기한 초과 + 재선점 합산). 쿼리 한 줄, **재선점은 원래 기한이 지난 좌석이라 "결제로 안 이어진 것"에 넣어도 말이 됨** |
| B | 셋을 따로 보려고 `reservation_history`에 `reason` 컬럼을 넣는다 (ERD 패치 + §7.1 수정) |
| C | 넣지 않는다 |

**A를 권합니다.** 보고 싶은 것이 "선점은 됐는데 결제로 안 이어진 비율"이라, 재선점도 결국
같은 이탈입니다. B는 ERD와 절차 문서까지 바꿔야 해서 지금 들일 비용은 아닌 것 같습니다.

**강다인 님께**: 취소 쪽 지표라 겹칠 수 있어 같이 봐 주세요. `cancellation` 기준 "취소"와
`reservation_history` 기준 "만료"를 따로 세는 것이 맞는지, 아니면 하나로 묶을지.

기능설계서 11장 미정 15번에 "기획서 표를 고칠지, 조회 화면만 남길지"로 올라와 있고
담당이 **B·길동현**입니다.

**왜 지금 묻나**: 만들고 나니 세 문서가 전부 어긋난 상태입니다. 발표 자료를 쓸 때
"P2인데 왜 만들었나" 또는 "필수인데 왜 P2로 적혀 있나"를 설명해야 합니다.

**제안**: **ADM-01·02를 P1으로 올리고** 1.1의 "1차는 적재 스크립트" 문구를
"적재 스크립트로 시작해 2주차에 등록 API·화면까지 구현"으로 고칩니다.
기획서(필수)와 실제 구현이 맞으니 기능설계서만 맞추면 됩니다.

기능설계서는 팀장 문서라 제가 고치지 않았습니다. **괜찮으시면 제가 고치겠습니다.**
