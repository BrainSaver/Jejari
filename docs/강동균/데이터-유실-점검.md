# 데이터 유실 점검 — 어디서 흘릴 수 있고, 어떻게 막았나

> 2026-11-20 점검. 실패를 일부러 일으켜(Kafka 정지·MongoDB 정지·DB 제약으로 저장 실패·깨진 메시지) 확인했다.
> 절차 원천: `docs/concurrency.md` §11(outbox)·§12(inbox)·§12.1(격리 보관함)

## 1. 큰 그림 — 흘리지 않는 방법들

| 방식 | 뜻 | 우리 시스템 |
|---|---|---|
| **Outbox** | 업무 변경과 같은 트랜잭션에 이벤트를 쓰고, 나중에 보낸다 | 예약·결제 이벤트 (`outbox_event`) |
| **재시도** | 실패하면 몇 번 다시 | 소비자 5초 무한 재시도 · 알림 3번 · 행동 로그 보내기 3번 |
| **격리 보관함 (DLQ)** | 끝내 처리 못 한 메시지를 따로 보관 → 원인을 고친 뒤 다시 처리 | `<토픽>.DLT` + `tools/dlq.sh` (**이번에 추가**) |
| **Inbox (멱등)** | 같은 메시지가 두 번 와도 한 번만 처리 | `processed_event` · `event_id` 유니크 인덱스 |
| **대사(reconciliation)** | 주기적으로 어긋난 것을 찾아 고친다 | 결제 결과 모름 재조회 · 늦은 승인 환불 · 선점 만료 스캐너 · `check_booking.sh` |
| 로컬 버퍼(spool) | 보내는 쪽이 디스크에 쌓았다 나중에 보냄 | 쓰지 않음 (행동 로그는 메모리 큐 + 재시도로 충분, 아래 실측) |

## 2. 경로별 점검표

| 데이터 경로 | 인프라 장애 (Kafka·DB 정지) | 깨진 메시지·끝내 실패 | 보이나 |
|---|---|---|---|
| 예약·결제 → outbox → Kafka | outbox에 쌓였다 복구 후 발행 (실측: Kafka 40초 정지 → 600건 쌓임 → 20초 안에 0, 유실 0) | 재시도 소진 → 그 샤드만 순서대로 멈춤 (관리자가 고침) | A-10 |
| → `seat-release` (좌석 정리·취소표 제안) | 5초 무한 재시도 | **고치기 전: 로그만 남기고 버림** → 격리 보관 | A-10 |
| → `notification` (알림) | 3번 재시도 | **고치기 전: 3번 실패하면 버림** → 격리 보관 | A-10 |
| → `risk-signal` (위험 점수 재계산 표시) | 5초 무한 재시도 | **고치기 전: 버림** → 격리 보관 | A-10 |
| 행동 로그 보내기 (앱 → Kafka) | **고치기 전: 실패하면 버림 (Kafka 40초 정지에 약 0.4%)** → 큐 뒤에 다시 넣어 3번 재시도 → 같은 시험에서 **0건** | 큐가 가득 차면 버림 (5만 건, 세어서 보임) | A-10 |
| 행동 로그 적재 (Kafka → MongoDB) | 5초 무한 재시도 (실측: MongoDB 60초 정지 → 밀림 896건 → 복구 후 따라잡음) | **고치기 전: 버림** → 격리 보관 | A-10 |
| 녹화(replay) 보내기·적재 | 적재는 무한 재시도 | 적재의 깨진 메시지 → 격리 보관 | 로그 |
| 결제 결과 모름 (PG 시간 초과) | `next_check_at` 재조회 (PaymentRecheckScanner) | 늦은 승인은 자동 환불 (LateApprovalRefund) | `check_booking.sh` |
| 결제 안 한 선점 | 만료 스캐너가 풀어 줌 | — | `check_booking.sh` 5 |

## 3. 이번에 고친 것

1. **격리 보관함 (DLQ)** — `event/dlq/DeadLetters`. 위 표의 "버림" 다섯 곳이 이제 원본 그대로 `<토픽>.DLT`에 옮겨진다 (이유·출처·오류 헤더, 30일 보관). 앱이 뜰 때 토픽을 만든다
2. **다시 넣기 도구** — `tools/dlq.sh list | show | replay`. 다시 넣으면 **그 소비 그룹만** 처리하고 다른 그룹은 건너뛴다. 두 번 넣어도 결과가 같다 (실측: 알림 3건 → 두 번 다시 넣어도 3건)
3. **행동 로그 보내기 재시도** — 실패하면 큐 뒤에 다시 넣어 최대 3번. 큐가 80% 넘게 차면 새 로그를 위해 포기 (지표 `jejari_behavior_retried_total`)
4. **A-10** — 데이터 놓침·밀림에 "격리 보관 (최근 1시간)" 칸, 최근 5분에 1건이라도 있으면 주의
5. `seat-release`의 잘못된 주석 ("실패하면 재시작 때 다시 온다") — 묶음 소비(AckMode.BATCH)라 묶음이 끝나면 오프셋이 커밋되어 다시 오지 않았다. 고침

## 4. 실측 (로컬, 2026-11-20)

| 일부러 낸 실패 | 결과 |
|---|---|
| 예약 토픽에 깨진 JSON 1건 | `seat-release`·`notification`·`risk-signal` 셋이 각자 격리 보관 (3건), 원본·출처(`jejari.reservation-4@524`) 그대로 |
| 행동 토픽에 깨진 메시지 1건 | `behavior-sink`가 격리 보관 |
| 알림 테이블에 임시 제약(모든 INSERT 거부) 후 예매 3건 | 확정 이벤트가 3번 실패 → 격리 보관(`retries_exhausted`). 제약을 지우고 `dlq.sh replay reservation notification` → **알림 3건 = 예약 3건**, 두 번 넣어도 3건 |
| 예매 200건 중 Kafka 40초 정지 | 예매·결제 200/200, 이벤트·알림 빠짐 0, **행동 로그 빠짐 0** (재시도 18번, 실패 0 — 고치기 전 같은 시험에서 4건 빠짐) |

## 5. 운영에서 할 일

- A-10 "격리 보관"이 0이 아니면: `tools/dlq.sh list` → 이유를 보고 원인을 고친 뒤 → `tools/dlq.sh replay <토픽> <그룹>` → `loadtest/tools/check_booking.sh <운행>`으로 확인
- 형식 오류(`malformed`)는 코드를 고친 뒤 `replay … malformed`로 따로. 고치기 전에 넣으면 또 보관함으로 온다
- 보관함은 30일 뒤 지워진다. 그 전에 처리
