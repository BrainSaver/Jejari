## 1. `train_run.status`가 이제 `DEPARTED`까지 갑니다 (ERD v23)

**전**: `DEPARTED`로 바꾸는 코드가 없어서 운행이 영원히 `CLOSED`에 머물렀습니다.
값은 ERD CHECK 제약에만 있고 **읽는 코드도 없었습니다.**

**후**: 판매 오픈 스케줄러가 바꿉니다.

```
SCHEDULED --(sale_open_at)--> ON_SALE --(sale_close_at)--> CLOSED --(열차가 떠남)--> DEPARTED
```

- 기준은 **기점 출발 시각** (`MIN(train_stop.departure_time)`)
- **`DEPARTED`가 아닌 모든 상태에서 바로 갑니다.** 시드의 `sale_close_at`이 운행일 다음 날이라
  열차가 떠난 뒤에도 한동안 `ON_SALE`로 남기 때문입니다. 출발은 판매 일정과 무관한 사실이라
  다른 전이보다 세게 봤습니다
- 정차 정보가 없는 운행은 출발 시각을 몰라 그대로 둡니다

### 영향받는 분

| 누구 | 무엇 |
|---|---|
| **전원** | 운행을 상태로 거르는 코드가 있으면 `DEPARTED`도 생각해 주세요. 지금까지는 안 나오던 값입니다 |
| **김성원(A)** | `OnSaleRunProvider`는 `status = 'ON_SALE'`만 보므로 **영향 없습니다.** 떠난 운행이 자동으로 빠지니 오히려 정확해집니다 |
| **강다인(D)** | 취소 수수료는 상태가 아니라 출발 시각으로 판단하므로 **영향 없습니다** (확인했습니다) |
| **길동현(C)** | §8.3 재판매 여부 집계 배치를 나중에 붙일 때 "출발한 운행"의 기준으로 쓸 수 있습니다 |

### 각자 DB에 적용

스키마 자체는 안 바뀌었습니다 (컬럼·제약 그대로, **설명만** 바뀜). **다시 적용할 것 없습니다.**

## 2. ADM-03 실시간 현황에 "만료"가 생겼습니다

**전**: 분당 수치가 예약·결제·**취소** 셋이었습니다. 그런데 "취소"는 `cancellation` 행 기준이라
**결제 기한 초과 만료가 빠져 있었습니다** (만료는 돈이 오가지 않아 `cancellation`을 안 만듭니다).

예약 100건·결제 40건이면 나머지 60건이 취소인지 만료인지 알 수 없었습니다.

**후**: 네 번째 수치 `expires`가 생겼습니다.

### API 응답이 바뀝니다 (필드 추가)

```jsonc
// GET /api/v1/admin/dashboard/runs/{runId}
"rates": { "reservations": 12, "payments": 5, "cancels": 1, "expires": 6 }
//                                                           ^^^^^^^^^^ 추가

// GET /api/v1/admin/dashboard/runs/{runId}/minutes
"minutes": [ { "minute": "...", "reservations": 3, "payments": 1, "cancels": 0, "expires": 2 } ]
//                                                                             ^^^^^^^^^^ 추가
```

**필드가 늘어난 것뿐이라 기존 화면·클라이언트는 그대로 돕니다.**

### 무엇을 세나

`reservation_history`의 **`HOLD → EXPIRED`** 를 셉니다. 동시성 §7.1에서 `EXPIRED`로 끝나는
길이 셋인데, 이렇게 갈랐습니다.

| 경로 | from → to | 만료로 세나 |
|---|---|---|
| §6.1 기한 초과 (TIMEOUT) | HOLD → EXPIRED | **O** |
| §3 재선점 (PREEMPTED) | HOLD → EXPIRED | **O** |
| §5.2 결제 실패 (PAY_FAILED) | PAYMENT_PENDING → EXPIRED | **X** |

- **결제 실패를 뺀 이유**: 카드 거절은 결제를 시도한 것이라 "결제로 안 이어짐"과 뜻이 다릅니다
- **기한 초과와 재선점을 합친 이유**: 둘 다 `HOLD → EXPIRED`라 `from_status`로 구분되지 않습니다.
  가르려면 outbox payload의 `reason`이 필요한데 발행 뒤 24시간이면 지워집니다
  (`outbox.retention_hours`). 재선점도 결국 기한이 지난 선점이라 합쳐 세는 쪽이 뜻에 맞습니다

### 강다인 님께

취소 쪽 지표와 겹칠 수 있어 한 번 봐 주세요. 지금은 이렇게 나눠 셉니다.

- **취소** = `cancellation` 행 (사용자·운영 취소, 돈이 오감)
- **만료** = `reservation_history`의 `HOLD → EXPIRED` (돈이 안 오감)

하나로 묶는 편이 낫다고 보시면 바꾸겠습니다.

## 2-1. 열차 번호와 시각표·운임이 실제 공공데이터로 바뀌었습니다

정차 시각과 운임은 공공데이터가 아니라 제 계산식이었습니다
(거리÷2.7km/분 + 정차 2분, 2,800원 + 125원/km). 국토교통부 (TAGO) 열차정보 **오픈 API**로
실제 값을 받아 바꿨습니다.

| | 전 | 후 |
|---|---|---|
| 열차 번호 | `101` · `102` (제가 지은 값) | **`00103`** · **`00026`** (실제 KTX 편명) |
| 서울~부산 | 09:00 → 11:52 · 55,000원 | **09:28 → 12:35** · **54,400원** |
| 서울~광명 | 5,600원 | **7,500원** |

### 영향받는 분

| 누구 | 무엇 |
|---|---|
| **전원** | **열차 번호를 코드나 테스트에 박아 쓴 곳이 있으면 바꿔야 합니다** (`'101'` → `'00103'`). `train_id` 1·2는 그대로입니다 |
| **전원** | 시각·운임을 기대값으로 쓴 테스트가 있으면 영향. 제 테스트는 전부 통과했습니다 |
| 강다인(D) | 취소 수수료는 출발 시각 기준이라 **구간이 달라졌습니다** (서울~부산 2:52 → 3:07) |

`db/seed/data/tago-train-info.json`에 받은 원본을 그대로 뒀습니다.
다시 받으려면 `node tools/fetch-train-api.js` (서비스키는 `.env`의 `DATA_GO_KR_KEY`).

### 기획서도 고쳤습니다

데이터 활용 1번이 "파일데이터 4종 + 오픈 API 1종"이 됐습니다. 발표에서
**"시각표와 운임까지 실제 공공데이터"** 라고 말할 수 있습니다.

## 2-2. 각자 DB에 `db/patch/v24.sql`을 적용해 주세요 (중요)

오늘 통합 테스트를 돌리다 `RiskScoreBatchInfraTest` 2개가 깨졌습니다. 원인은 **제 Oracle
볼륨이 ERD v24 이전**이라 `case_marker.rule_code` CHECK에 `REGULAR_INTERVAL`이 없던 것이었습니다.

**DDL은 볼륨을 처음 만들 때만 돕니다.** 이미 띄워 둔 DB는 테이블이 다 있어 겉으로는
멀쩡해 보이는데, CHECK·시퀀스가 없어 엉뚱한 곳에서 깨집니다. 테스트 메시지
(`expected: 1 but was: 0`)만 봐서는 스키마 문제인 줄 모릅니다.

```bash
PW=$(grep '^ORACLE_APP_PASSWORD=' .env | cut -d= -f2)
docker compose exec -T -e NLS_LANG=AMERICAN_AMERICA.AL32UTF8 oracle   bash -lc "sqlplus -S -L jejari/$PW@localhost:1521/FREEPDB1" < db/patch/v24.sql
```

다시 실행해도 안전합니다. 적용 뒤 제 쪽은 단위·통합 전부 통과했습니다.

## 2-3. 조영준 님께 — 서버 다시 만들지 않아도 됩니다 (제가 만든 문제입니다)

공지 주의사항 2번 **"시드 운행 9001·9002는 넣은 날 + 3일에 출발하고, 출발하면 DEPARTED라
예매가 막혀요"** 는 **위 1번(제 DEPARTED 전이)이 만든 문제**입니다. 죄송합니다.
`DEPARTED`는 그때까지 아무도 안 쓰는 값이라, 시드가 "출발 3일 뒤"로 되어 있어도 아무 일이
없었습니다. 제가 스케줄러에 맡기자 그 3일이 시한이 되었습니다.

**고쳤습니다. 데이터 초기화 없이 시드 두 개만 다시 돌리면 됩니다.**

```bash
git pull   # main
docker compose exec -T oracle bash -lc '
cd /seed
for f in 04_regular_run.sql 05_train_stop_fare.sql; do
  sqlplus -s "${APP_USER}/${APP_USER_PASSWORD}@//localhost:1521/FREEPDB1" <<SQL
WHENEVER SQLERROR EXIT SQL.SQLCODE ROLLBACK
SET DEFINE OFF
SET SQLBLANKLINES ON
ALTER SESSION SET TIME_ZONE = '"'"'Asia/Seoul'"'"';
@${f}
EXIT
SQL
  echo "seed: ${f} ok"
done'
```

`04`가 운행일을, `05`가 정차 시각을 다시 계산해 덮어씁니다. **지우는 것이 없습니다** —
회원·예약은 그대로 있고, 예약은 `run_id`로 매달려 있어 열차와 함께 앞으로 밀립니다.
앱을 멈출 필요도 없습니다 (스케줄러가 다음 주기에 상태를 맞춥니다).

### 무엇이 바뀌었나

| | 전 | 후 |
|---|---|---|
| 9001·9002 출발 | 넣은 날 **+3일** | 넣은 날 **+45일** (발표 + 28일) |
| 묵었을 때 되살리기 | **DB 재생성** (회원·예약 삭제) | 시드 `04` → `05` 재실행 |
| 시드 검증 | 23항목 | **24항목** (24번이 묵은 운행을 잡습니다) |

`+45일`로 고른 이유: 오픈은 코레일 규칙대로 출발 2개월 전이라, 운행일이 너무 멀면
오픈이 아직 안 와서 `SCHEDULED`가 됩니다. `+45일`이면 오픈이 15일 전으로 지나 있어
`ON_SALE`이고, 출발은 45일 뒤입니다.

원래 `WHEN MATCHED`가 `status`만 갱신해서 **다시 돌려도 날짜가 안 바뀌는 것**이
초기화를 강요한 진짜 원인이었습니다. 이제 날짜까지 갱신합니다.

### 덤으로 고쳐진 것

9003(오픈 스케줄러 시연용, "오픈이 내일 07:00")도 하루가 지나면 그냥 `ON_SALE`이 되어
있었습니다. 아무것도 막지 않아 아무도 몰랐는데, 재실행하면 `SCHEDULED`로 되살아납니다.

자세한 추적은 [트러블슈팅](troubleshooting/20261118-시연-운행이-출발해-예매가-막힘.md)에 있습니다.

### 03의 명절 운행은 그대로 뒀습니다

명절 운행(1001~2004)은 "넣은 날 +30~33일"이라 지금 서버에서 **12-17~12-20 출발**입니다.
발표(12-05) 뒤이니 손대지 않았습니다. 다만 03은 `INSERT`만 해서 재실행으로 날짜가 밀리지
않습니다. 명절 날짜를 다시 잡아야 하면 말씀해 주세요 — 04처럼 바꾸겠습니다.

### INF-03 제목 건

사이트 로드맵 "Oracle Cloud A1 VM" → "Google Cloud VM"은 팀장 문서라 제가 안 고쳤습니다.
길동현 님께 전달된 것으로 알고 있습니다.

## 2-4. 열차 조회가 늘 비어 있던 것 — 운행을 예매 가능 기간 전체에 깔았습니다

검색 화면을 열면 기본 날짜가 **오늘**인데, **"조건에 맞는 열차가 없어요."** 만 나왔습니다.

원인은 둘을 같이 봐야 보입니다. 검색은 운행일이 **정확히 일치**해야 찾는데
(`TrainQueryService`의 `WHERE r.run_date = ?`), 시드가 **2개월 61일 중 6일**에만 운행을
두고 있었습니다 (명절 12-17~20, 9001·9002, 9003). 오늘은 그 6일에 없으니 무조건 빈 결과입니다.

**고쳤습니다.** 코레일 규칙대로 지금 예매할 수 있는 **모든 날**에 열차 2편씩 깔고,
**하루가 지나면 두 달 뒤의 새 날짜가 저절로 들어오게** 했습니다.

| | 전 | 후 |
|---|---|---|
| 운행이 있는 날 (앞으로 61일 중) | **6일** | **61일 전부** |
| 오늘 날짜로 조회 | 빈 결과 | 열차 2편 (`00103`·`00026`) |
| 하루 지나면 | 창이 하루 짧아짐 | 끝 날짜가 하루 따라옴 (새 `RunHorizonScheduler`) |
| 2개월 뒤 날짜 | 없음 | `SCHEDULED`로 있고 **07:00에 열림** |

시드만으로는 안 됩니다. 시드는 **돌린 순간**의 창을 만들 뿐이라 다음 날부터는 아무도
이어 주지 않습니다. 그래서 `RunHorizonScheduler`를 넣었습니다 — 10분마다 지평
(`ADD_MONTHS(오늘, 2) + 1일`)까지 빠진 날짜를 채웁니다. 시드와 **같은 번호 규칙·같은 날짜 규칙**을
써서 시드가 깐 행과 이어집니다. 중간에 구멍이 나도 같은 문장이 메우므로 묵은 DB도 스스로 복구됩니다.

> **기본값은 꺼져 있습니다** (`jejari.train.run-horizon-enabled=true`로 켬). 이유는 바로 아래.
> 시드가 깔아 둔 창(2개월)은 켜지 않아도 그대로 쓸 수 있습니다 — 꺼 두면 날이 갈수록 짧아지는 것만 남습니다.

아직 안 열린 날짜까지 `SCHEDULED`로 넣는 이유: 그 행이 있어야 화면이 "오전 7시 오픈"을
보여 줄 수 있고, **매일 07:00에 `SCHEDULED → ON_SALE` 전이가 실제로 일어납니다.**
열린 뒤에 행을 만들면 그 전이를 볼 수 없습니다.

- 번호는 `700000 + (운행일 - 2026-01-01) * 10 + train_id`입니다. **날짜에서 번호가 나와서**
  시드를 다시 돌려도 같은 날짜가 같은 행을 씁니다
- `9001`·`9002`(2027-01-02)와 `9003`(오픈 예정)은 **그대로**입니다. 테스트가 쓰는 번호라 안 건드렸습니다
- 명절 운행 8건도 그대로입니다. 같은 열차·같은 날에 운행이 있으면 건너뜁니다
- `seat_inventory`는 선점할 때 생기니 좌석 행은 안 늘어납니다

자세한 건 [트러블슈팅](troubleshooting/20261118-열차-조회가-늘-비어-있음.md)에 있습니다.

### 길동현 님께 — 제 것과 겹칩니다. 정리해야 합니다

작업하다 [`실제-ktx-시간표-적재`](../길동현/features/실제-ktx-시간표-적재.md)를 뒤늦게 봤습니다.
**비슷한 일을 하는 것이 둘이 됐습니다.** 먼저 쓰신 쪽을 못 보고 만든 제 잘못입니다.

| | 길동현 `tools/load-tago-schedule.js` | 강동균 시드 04 + `RunHorizonScheduler` |
|---|---|---|
| 열차 | **실제 KTX 전 편성** (`train` 10000+열차번호) | 시드 2편 (`train_id` 1·2) |
| 날짜 | 오늘 앞뒤 **7일** | 오늘 ~ **2개월 +1일** |
| 운행 번호 | `400000 + 연중일 × 1000 + 열차번호` | `700000 + (운행일 - 2026-01-01) × 10 + train_id` |
| 돌리는 방법 | **손으로** (`node` → `sqlplus`) | 시드 + **앱이 10분마다 자동** |
| 쓰는 곳 | 실제 시간표로 화면 보기 (개발용) | 기준 데이터 · 테스트 · 공용 서버 |

번호 대역이 달라 **지금도 같이 돌아갑니다** (열차 ID도 달라 유니크 제약에 안 걸립니다).
그래도 "운행 데이터를 어디서 만드나"가 둘인 건 발표에서 설명하기 어렵습니다. 제 생각엔
**실제 편성 전부는 동현 님 스크립트, 자동 연장은 제 스케줄러**로 갈라 두고, 나중에
동현 님 스크립트가 넣은 열차까지 제 스케줄러가 이어 주게 하면 하나로 모입니다
(`jejari.train.horizon-trains`에 열차 ID를 더하면 됩니다). 어떻게 할지 정해 주세요.

### 조영준 님께 — 서버에 이미 있는 해결책과 겹칩니다 + 틱이 꽉 찼습니다 (중요)

`deploy/tago-refresh.sh`와 `jejari-tago.timer`(매일 04:30)를 뒤늦게 봤습니다.
**서버는 이미 이 문제를 풀어 두셨습니다** — 그 스크립트 주석의 *"시드 운행은 '넣은 날 + 3일'
하루뿐이라 오늘·내일로 검색하면 열차가 없다 (11-18 팀원 제보)"* 가 제가 오늘 고친 것과 같은 건입니다.
Pushgateway 지표와 Grafana 경보까지 붙여 두신 것도 확인했습니다.

그래서 **제 스케줄러는 기본값을 꺼서 올렸습니다.** 켜면 서버가 위험합니다.

| | 운행 | 1초 틱의 Redis 왕복 | 걸리는 시간 |
|---|---|---|---|
| 시드만 (어제까지) | 11 | 44회 | ~10ms |
| **지금 서버** (TAGO 7일) | ~900 | 3,600회 | **~830ms** |
| + 제 스케줄러 | ~1,020 | 4,080회 | **~940ms** |

**지금 서버가 이미 1초 틱의 830ms를 쓰고 있습니다.** 왕복 0.23ms는 로컬 측정값이라
서버에서 더 느리면 지금도 넘칠 수 있습니다. 넘치면 `QueueAdmitScheduler`가 밀려
**대기열 입장이 늦어집니다** — 핵심 기능입니다. 서버에서 한 번 재 보시면 좋겠습니다
(`jejari_tago_runs` 지표에 운행 수가 있으니 거기에 ×4×왕복을 곱하면 됩니다).

제 쪽에서 할 수 있는 건 꺼 두는 것뿐이고, 그렇게 했습니다. 근본은 아래 성원 님 몫입니다.

### 성능 측정 전에 (이미 동현 님이 적어 두신 내용입니다)

`QueueAdmitScheduler`는 **판매 중 운행마다 1초에 한 번** `admit()`을 부르고, `admit()`은
**대기열이 비어 있어도 Redis 왕복을 4번** 합니다 (`SET throughput` · `ZCARD` · `TIME` ·
`ZREMRANGEBYSCORE`). 운행 수에 그대로 비례합니다.

이건 동현 님이 위 문서 "주의할 점"에 먼저 적어 두셨습니다 — *"운행이 많아지면(15일 ≈ 900개
ON_SALE) 대기열 입장 스케줄러가 매초 운행 수만큼 돈다. 부하 테스트 때는 이 점을 감안할 것."*
제가 처음 찾은 것처럼 적었는데 아닙니다. 숫자만 보태겠습니다.

측정값은 로컬 `redis-cli --latency` 평균 **0.23ms**(289회 표본)입니다.

**김성원 님 — 이게 지금 가장 급한 것 같습니다.** 대기열이 **빈 운행까지 매초 훑습니다.**
운행이 900건인 지금도 틱의 83%를 유휴 작업에 쓰고 있고, 늘어나면 바로 넘칩니다.
`admit()` 안에서 `ZCARD`가 0이면 끝내는 게 아니라, **애초에 대기열 키가 있는 운행만**
돌면 (예: `SCAN`/인덱스 집합 하나) 비용이 운행 수와 무관해집니다.
성원 님 영역이라 손대지 않았습니다. 제가 도울 게 있으면 말씀해 주세요.

### 정리하다 같이 고친 것

`SaleOpenSchedulerInfraTest`의 정리 범위가 `run_id >= 9101 AND < 1000000`이라
**시드의 날짜별 운행(700000~)과 합성 데이터(880000~)까지 지웠습니다.**
테스트 대역(`< 10000`)만 지우게 좁혔습니다.
