CSV에서 SQL을 생성한다

node tools/load-public-data.js            # 검사 (CI가 매 push마다 실행)
node tools/load-public-data.js --write    # SQL 값 블록 재생성

시드 SQL의 -- @generated:… ~ -- @end:… 사이가 CSV에서 생성되는 구역입니다. 거리 원본이 역×역 매트릭스인 것도, 공공 순번(서울 2·광명 4·대전 8·동대구 11·부산 19)을 우리 노선 안 1~5로 다시 매기는 것도 코드가 합니다.

왜 만들었나 — 처음엔 CSV를 눈으로 보고 SQL에 손으로 옮겼습니다. 그러다 역코드를 두 번 틀렸습니다 (4자리로 추측 → 3자리로 정정 → 진짜는 7자리). 값이 CSV에서 왔다는 것을 사람이 아니라 기계가 보증해야 합니다. 기능설계서 1.1이 ADM-01 등록 화면 대신 약속한 "적재 스크립트"가 이것입니다.

대조하면서 고친 것

  • 역코드는 7자리였습니다 (서울 3900023). 추측한 4자리·3자리 둘 다 틀렸습니다.
  • 거리가 재래선 값이었습니다. KTX는 경부고속선을 타므로 서울~부산은 441.7km가 아니라 417.4km입니다. 거리에서 운임이 나오므로 운임 40행이 전부 바뀌었습니다.
  • 좌석수가 달랐습니다. 추측한 일반 56·특실 36석 대신 원본의 55·30석. 좌석 1,080 → 1,050석. 55석이 열 문자 4개로 안 나누어떨어져서(13열 ABCD + 14열 ABC) 검증 10번을 CEIL(n/k) + FLOOR(n/k) 공식으로 바꿨습니다.
  • 노선명 경부선은 맞았습니다. 거리만 고속선 기준입니다.

자동 적재와 검증

docker compose up -d로 Oracle을 처음 띄우면 DDL 다음으로 시드가 자동 실행됩니다.

설계에서 신경 쓴 지점

  • hold.lua는 전부 검사 → 전부 쓰기. 일부만 잡힌 반쪽 예약이 안 생깁니다. GET 여러 번 후 SET 하면 그 틈에 다른 요청이 끼어들어 같은 좌석이 두 번 팔립니다.
  • limit_decr.lua는 표시 키를 선점한 쪽만 깎습니다. 커밋 후 보상이 빠른 경로와 outbox 보장 경로로 두 번 옵니다(§14.3). 두 번 깎이면 한도가 DB보다 작아져 정상 사용자가 막힙니다.
  • extend·rehold·limit_decr은 없는 키를 만들지 않습니다. extend가 없는 키를 만들면 이미 만료돼 남에게 넘어간 좌석을 되살립니다.
조영준(E)에게 — Redis maxmemory-policy가 반드시 noeviction이어야 합니다(§14.5). 기본값이면 메모리가 찰 때 seat:hold 키가 조용히 사라져 같은 좌석이 두 번 팔립니다. 현재 compose에 반영돼 있고, RedisConfigVerifier가 기동 시 검사합니다.

§17.1 · 좌석 선점 락 방식 비교 실측 완료

좌석을 선점하는 세 방법을 같은 조건·같은 입력으로 재서 무엇을 왜 고를지 정했습니다. 워밍업 1회를 버리고 5회 측정한 중앙값입니다.

A 비관적   SELECT ... FOR UPDATE  →  줄 서서 하나씩  →  UPDATE
B 낙관적   SELECT version         →  UPDATE ... WHERE version=?  →  0행이면 다시
C 현재     Redis hold.lua         →  지면 끝(DB 안 감)  →  이긴 사람만 INSERT(PK가 최종)

중복 예약은 세 방식 × 세 시나리오 전부 0건. 정확성은 셋 다 만족해서 변별력이 없었고, 차이는 전부 비용이었습니다.

C를 고른 이유는 TPS가 아니라 DB 왕복 — 극한 경쟁에서 201회 → 2회로 100배 줄어듭니다. 패배자 99명이 Redis에서 걸러져 DB에 아예 안 갑니다(§2.1-4). 명절 예매는 인기 열차 한 편에 수만 명이 몰리는 상황이라 "DB가 버티느냐"가 먼저입니다.

예상과 달랐던 것 — 그대로 남깁니다

  • 경쟁이 적으면 C가 B보다 느립니다 (756 vs 1,256 TPS). 좌석이 안 겹치면 Redis 왕복이 순수 오버헤드가 됩니다. "Redis를 끼우면 항상 빠르다"가 틀렸습니다.
  • 꼬리 지연은 B가 낫습니다 (시나리오 2에서 p99 43.5ms vs 74.3ms). C는 패배자가 빨리 끝나 평균을 끌어내리는 대신 승자들의 INSERT가 몰려 꼬리가 길어집니다.
  • 그래도 1차는 C로 통일합니다. 운영 중에 경쟁 정도를 미리 알 수 없고, 코드가 두 갈래가 되면 버그 자리가 늘어납니다. 대신 SeatHoldStrategy로 바꿔 끼울 수 있게 설계했습니다.
  • A는 쓸 이유가 없습니다. 전 구간 최하위에 변동이 가장 크고(TPS 98~930), 경쟁이 적은 시나리오 3에서 오히려 락 대기가 p99 2,646ms까지 튀었습니다.

측정 중에 고친 것

  • 공정성 버그 — 전략마다 좌석 배정을 다시 뽑아 분포가 달랐습니다 (성공 수가 318/327/315로 갈림). 같은 입력을 쓰도록 고쳤습니다.
  • 1회 측정은 못 믿습니다 — 같은 조건에서 TPS가 2~4배 흔들렸습니다 (B 시나리오3이 227 → 905). 워밍업 1회를 버리고 5회 중앙값으로 바꿨습니다.

둘 다 고치기 전 수치를 그대로 보고했으면 틀린 결론을 낼 뻔했습니다.

이 수치의 한계 (발표 때 같이 말할 것) — 로컬 단일 머신이라 네트워크 지연이 없고, Python 스레드(GIL) 때문에 클라이언트 병목이 섞여 있습니다. 커넥션 풀 64 고정이고, A·C는 회차 간 편차가 큽니다(A 98~930, C 113~1,223 TPS). 실제 §2.2 트랜잭션은 더 무겁습니다. 뼈대가 올라왔으니 k6로 HTTP 레벨에서 다시 재야 합니다(조영준 E).

v11에서 한 것 — 1일 매수 제한(PER_DAY) 추가

코레일 개인 구입 제한은 열차당 10석 · 하루 20석인데, 매수 제한 scope가 PER_RESERVATION/PER_RUN/PER_HOLIDAY뿐이라 하루 한도를 담을 자리가 없었습니다. 1인 매수 제한이 제 핵심 수치라 그대로 두면 검증할 기준이 없습니다.

행사 정책이 상시보다 우선합니다 (§10.6). 상시 1회 9매는 공시로 확인하지 못해 미정 사항 17번에 올렸습니다.

PER_DAY는 구매일 기준

purchase_counter.scope_ref_id에 구매일 YYYYMMDD를 넣습니다 (운행일이 아닙니다). 이 규칙은 "하루에 몰아 사는 것"을 막는 장치라 세는 단위가 타는 날이 아니라 사는 날이고, 이 프로젝트 목표인 암표·매크로 억제와도 맞습니다.

감수한 단점 — 감소할 때 "지금 날짜"를 쓰면 버그입니다. 자정을 넘겨 만료·취소되는 예약이 다음 날 카운터를 깎습니다. 그 예약의 created_at 날짜를 쓰도록 §10.2에 명시하고 테스트 T37로 박아 뒀습니다. 운행일 해석도 가능해 미정 사항 16번에 올렸습니다.

  • 기능설계서 — RSV-02 한도, LIMIT_PER_DAY 에러 코드, TRN-02·ADM-02 오픈 규칙, 미정 사항 16·17
  • 기획서 — 데이터 활용에 실제로 쓴 데이터셋 4건과 적용 값
강다인(D)에게 — 취소표 제안 §9.5의 대기자 한도 검사에 PER_DAY가 추가됐습니다. PER_RUN·PER_HOLIDAY만 보고 구현하면 1일 한도를 넘겨 제안됩니다. 그리고 cancel_fee_policy 예시 5건이 전부 지난 행사에 묶여 있어 지금은 취소 수수료가 계산되지 않습니다 — 상시 정책 세트가 필요합니다.

예매 오픈은 값이 아니라 규칙

코레일은 일반 승차권을 출발일 2개월 전 오전 7시에 엽니다. 그래서 오픈 시각을 손으로 적지 않고 ADD_MONTHS(run_date, -2) + 07:00으로 계산하고, status도 그 값과 지금 시각을 비교해 정합니다. 검증 22·23번이 규칙 위반을 잡습니다. 명절 특별예매는 일괄 오픈이라 행사 오픈 시각을 그대로 씁니다.
