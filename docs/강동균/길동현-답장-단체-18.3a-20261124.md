# 길동현 님께 · §18.3a 의견 반영

> 작성 2026-11-24 · 강동균 · `docs/concurrency.md` §18.3·18.3a·18.3b·18.8 · 브랜치 `DongGyun`

보내 주신 네 가지는 다 맞아서 반영했습니다. 두 곳은 조금 보탰고, 한 곳은 정해 주셔야 합니다.

## 반영한 것

1. **오픈 직후 18.3a 미루기** (18.3a-0, 새 절 18.3b)
   - 운행이 `ON_SALE`이고 대기열이 빈 뒤에만 일반 좌석을 가져갑니다.
   - 보탠 것 ①: "대기열이 빈 것" = 줄 선 사람(`queue:{runId}`) **과** 입장해서 좌석을 고르는 사람(`queue:active:{runId}`)이 둘 다 0. 줄만 보면, 입장한 사람이 좌석을 고르는 사이에 단체가 먼저 가져갑니다.
   - 보탠 것 ②: 미룬 신청을 다시 처리할 곳이 없어서 18.3b를 만들었습니다.
     - 스캐너가 `REQUESTED`를 신청 순서대로 다시 시도합니다.
     - 할당석만으로 되는 신청은 오픈 직후라도 바로 승인합니다. 할당석은 개인과 겨루지 않기 때문입니다.
     - 할당석 반납 시각까지 승인되지 못하면 `REJECTED`로 끝냅니다. 인기 운행은 대기열이 오래 안 빕니다.
   - 할당석 몫만 먼저 배정하지 않습니다. 예약이 두 건으로 쪼개지기 때문에, 모자라면 승인 전체를 미룹니다.
2. **테스트 G5c**: 대기자에게 제안 중인 좌석(`REOFFER:R`)은 18.3a가 못 가져갑니다.
   - 보탠 것: 제안 중인 좌석은 DB 행이 이미 지워져 있습니다. 그래서 DB만 보고 고르면 빈 좌석으로 골라 놓고 Redis에서 계속 실패합니다. 고를 때 Redis 키도 보고 빼도록 18.3a-1에 적었습니다.
   - `hold.lua`의 인계 값은 항상 `''`라는 것도 명시했습니다.
   - 덤으로 G5d(오픈 직후 미룸), G5e(할당석만으로 되면 바로 승인)도 표에 넣었습니다.
3. **두 스크립트 비원자 문제**: 말씀하신 문구를 넣었습니다(아래 "정해 주세요" 참고).
4. **§3 재선점 빼기**: 뺐습니다.
   - 일반 좌석은 **DB 행도 없고 Redis 키도 없는 좌석만** 고릅니다.
   - 그 사이 누가 먼저 잡아 PK 충돌이 나면, 전체를 롤백하고 다시 고릅니다(3회).
   - 만료된 HOLD 좌석은 스캐너가 풀어 줍니다.

## 정해 주세요: `group_claim.lua`를 하나로 할지

- **(제 권장) 스크립트 하나**: 할당석 키는 `GROUP`인지, 일반 좌석 키는 비었는지를 한 스크립트에서 전부 검사한 뒤 전부 씁니다. `hold.lua`처럼 "전부 아니면 전무"라 반쯤 잡힌 상태가 아예 없습니다. `group_claim.lua`는 아직 새로 만드는 스크립트라 지금 정하면 비용이 거의 없습니다.
- **스크립트 둘**: 동현 님 문구대로 "할당석 키는 그대로 두고 일반 좌석만 다시 고른다, 최종 실패 시 18.3-5로 둘 다 되돌린다"로 갑니다.

§18.3a-2에 두 방법을 다 적어 두었습니다. 정해 주시면 나머지 하나를 지우겠습니다.

## 영향

- 좌석 쪽 코드(`SeatHoldTx` 등)는 바뀌는 게 없습니다. 18.3a·18.3b는 단체 승인 코드(동현 님) 몫입니다.
- 18.3b 스캐너를 어디에 둘지(단체 쪽 새 스캐너 또는 제 `GroupQuotaScheduler`에 붙이기)도 편한 쪽으로 정해 주세요. 제 쪽에 붙이면 할당석 만들기·반납과 같은 1분 주기로 돕니다.
