## 왜 이렇게 했나

### Redis 보상을 트랜잭션보다 **먼저**

좌석 키를 `REOFFER:R`로 바꾸는 것이 일반 사용자를 막는 장치다. 트랜잭션 안에서 하면
커밋될 때까지 좌석이 열려 있어 일반 사용자가 먼저 채 간다. `reoffer.lua`가 두 번 돌려도
같게 만들어져 있어 밖에서 먼저 해도 안전하다.

### 취소표 행동 로그를 넣자고 한 이유

`SuspiciousCaseOpener`를 보니 규칙마다 조건이 다르다.

```java
case SAME_SEAT_RETRY -> ... Filters.eq("event_type", SEAT_HOLD) ...   // 종류를 특정
case FAST_CLICK      -> ... Filters.lt("interval_ms", ...) ...        // 종류를 안 가림
```

**`FAST_CLICK`·`REGULAR_INTERVAL`은 `event_type`을 가리지 않는다.** 취소표 요청이 남기만 하면
규칙을 하나도 안 고쳐도 신호에 들어온다. 반대로 지금까지는 봇이 `POST /waitlists`를 아무리
두드려도 두 규칙에 **안 보였다.**

게다가 §9.3이 패널티 180000(1점 = 3분)을 고른 이유를 "봇은 매진 직후 바로 신청하므로"라고
적어 뒀는데, **정작 그 행동이 로그에 안 남고 있었다.** 설계와 데이터가 어긋나 있었다.

빠진 구간은 그 구간만 안 보이는 게 아니라 `interval_ms`가 실제보다 길어 보여
**다른 이벤트의 신호까지 왜곡한다.** 사람처럼 보이게 만드는 쪽으로.

값만 늘리고 규칙은 건드리지 않았다. 행동 분석은 강다인 씨 것이다.

### 배포는 VM 1대에 compose 그대로

- GCP엔 **관리형 Oracle이 없다** (Cloud SQL은 MySQL·PG·SQL Server). 어차피 컨테이너면
  나머지만 쪼갤 이유가 없다
- **Cloud Run은 비용이 아니라 구조상 안 된다.** 상주 스케줄러 9개·Kafka 컨슈머 3개가
  돌아야 하는데 요청이 없으면 인스턴스가 0으로 줄어 선점 만료가 멈춘다
- 무료 등급 `e2-micro`는 RAM 1GB인데 **Oracle 컨테이너 하나가 2.59GB**다 (`docker stats` 실측)

## 막힌 점과 해결

### 통합 테스트가 매번 다르게 깨지던 것 → 원인 잡음

따로 문서로 썼다:
[앱이 떠 있으면 통합테스트가 조용히 깨짐](../troubleshooting/20261117-앱이-떠-있으면-통합테스트가-조용히-깨짐.md)

한 줄로: 내가 k6 벤치용으로 띄워 둔 `bootRun` 앱이 같은 Oracle·Redis·Kafka를 보면서
테스트의 HOLD를 먼저 만료시키고 outbox를 먼저 가져갔다. `NoRunningApp`(JUnit 확장)을
통합 테스트 전부에 붙여 **시작하자마자 알려 주고 멈추게** 했다.

### 취소표가 겹쳤다

시작 전에 모든 브랜치를 확인했을 때 취소표 코드가 하나도 없어서 WL-01·02까지 만들었는데,
**작업하는 동안 강다인 씨가 같은 것을 올렸다**(`0c092c0`). 같은 경로·같은 패키지·같은 접근이었다.

원래 담당이 D이고 구현도 나은 데가 있어(회원 행 잠금으로 따닥 방지, 점수·패널티를 응답에
노출하지 않음 — 봇이 기준을 역산하지 못하게) **내 것을 버리고 그쪽을 썼다.** 내 테스트는
`WaitlistOfferInfraTest`로 분리해 WL-03만 덮게 했다.

### 내 소비자가 내 테스트를 깨뜨렸다

병합 뒤 `WaitlistOfferInfraTest`가 "제안 0건"으로 깨졌다. 내가 만든 `SeatReleaseConsumer`가
테스트 컨텍스트에서도 돌면서, 내가 `offerTx.offer()`를 부르기 전에 Kafka로 이벤트를 받아
대기자에게 먼저 제안해 버린 것이다. 전에 통과한 건 타이밍 운이었다.
`jejari.waitlist.offer-enabled=false`로 껐다 — 그래서 만들어 둔 속성이다.

### 테스트 회원의 `ci_hash`가 아무 문자열이면 안 된다

취소표 신청이 전부 `IllegalStateException`으로 떨어졌다. `OracleMemberIdentityPort`가
`^[0-9a-f]{64}$`를 검사한다. 해시가 오염되면 위험 점수가 틀리니 막는 것이고 맞는 동작이다.
내 좌석 모듈은 `ci_hash`를 DB에서 그대로 읽어 써서 이 제약을 모르고 있었다. `%064x`로 고쳤다.

### 배포 문서에서 내가 틀린 것 셋

다시 검증하다 찾았다.

1. **"`gcloud compute ssh`가 IAP로 처리한다" — 틀렸다.** IAP는 `--tunnel-through-iap`와
   `35.235.240.0/20` 방화벽이 따로 필요하다. 그냥 되는 이유는 기본 VPC의
   `default-allow-ssh`(tcp:22, `0.0.0.0/0`) 때문이고, 즉 **22번이 전 세계에 열려 있다**
2. "컨테이너 7개 전부 Up" — 서비스는 8개고 `kafka-init`은 `Exited 0`이 정상이다.
   그러다 조영준 씨가 추가한 `redis-exporter`가 내 스택에 안 떠 있던 것도 발견했다
3. RAM을 추정으로 적었던 것을 `docker stats` 실측으로 바꿨다 (인프라 4.3GB, 전체 6.5GB)

## 배운 점

- **실패 수가 매번 다르면 내 코드가 아니라 환경을 의심한다.** 나는 "병합으로 들어온 변경"을
  먼저 의심했고 `origin/main` 단독 재현을 보고 "팀 누군가의 회귀"라고 결론 냈는데 둘 다 틀렸다.
  두 경우 다 내가 앱을 띄워 둔 상태였다
- **"무엇이 문제인가"보다 "어디까지 정상인가"를 먼저 가른다.** 스캐너 앞뒤를 가르는 검사 한 줄이
  범위를 절반으로 줄였고, 그다음 `reason: TIMEOUT`이 범인을 지목했다
- **배경에서 도는 것이 테스트보다 먼저 일하면 안 된다**는 같은 함정을 하루에 두 번 밟았다
  (떠 있는 앱, 그리고 내가 만든 소비자). 속성으로 끌 수 있게 만들어 둔 게 두 번째를 살렸다
- **착수 전에 한마디 남기는 게 코드를 아낀다.** 브랜치를 다 확인하고 시작했는데도 겹쳤다
- 남이 쓴 검증(`ci_hash` 형식, 시간대 점검)이 내 테스트를 막으면 대개 **그쪽이 맞다.**
  우회하지 말고 맞춰야 한다
