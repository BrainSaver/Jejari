## 어떻게 했나

```
보완할-일 다시 읽기 → "빈 운행" 항목이 이미 고쳐진 걸 코드로 확인(QueueAdmitScheduler가 queue:runs만) → 스케줄러 둘 켜기
→ 할당석이 현황 선점에 섞이는 것 확인 → BLOCKED 따로 세기 → 대회 운행이 할당석 대상인지 확인 (70일 뒤라 대상, 사용법에 적음)
→ 카드 상한이 왜 꺼졌나: 같은 카드번호를 쓰는 곳 목록(기능 문서 표) → 하나씩 사람별 번호로
→ 조영준 님 11-27 일지 "시연 카드 4111이 45점" → k6 시나리오 11·15의 4111+번호도 시험마다 같은 카드를 다시 쓰는 걸 발견 → 49 + 태그로
```

## 왜 이렇게 했나

- **할당석은 회원 배치도에서는 그대로 "선택 불가"**: 회원에게 "단체용이라 못 삼"과 "남이 잡고 있음"을 나눠 보여 줄 이유가 없다.
  관리자 숫자만 바꿨다. 원천은 DB 행 — 반납 순간 Redis `GROUP` 키가 먼저 지워져도 행이 있는 동안은 할당석으로 센다
- **테스트에서는 두 스케줄러를 끔**: 켜 두면 테스트 운행 좌석 5%가 BLOCKED가 되거나 운행이 늘어 좌석·건수를 세는 테스트가 흔들린다.
  각 스케줄러의 통합 테스트는 스케줄러를 직접 만들어 부른다
- **카드 상한은 공용 서버에서만 켜고 로컬·테스트 기본값(0)은 둠**: 통합 테스트 여러 개가 테스트 회원마다 같은 카드로 결제해서
  기본값을 3으로 바꾸면 그 테스트가 상한에 걸린다. 상한 자체는 `CardLinkLimitInfraTest`가 정책을 켜고 따로 본다
- **시험 카드 번호를 "사람"뿐 아니라 "시험"마다 다르게**: 카드 해시는 번호 전체의 HMAC이라 번호가 같으면 한 장이다.
  `4111 + 사람 번호`는 한 시험 안에서는 사람마다 달라도, 다음 시험의 새 계정이 같은 번호를 다시 쓴다 → 그 카드의 위험 점수가 시험마다
  쌓이고(시연 카드 45점이 그 모양) 상한을 켜면 3번째 시험부터 막힌다. 앞자리를 `49`로 해서 결제 화면 번호(`4111…`)와도 안 겹친다
- **같은 회원은 늘 같은 시험 카드**: 결제 화면 번호를 매번 무작위로 하면 회원 한 명에 카드가 수십 장 붙어 "카드 여러 장 쓰는 회원"처럼 보인다.
  회원 ID로 만들면 한 명 = 한 장
- **색은 안 바꾸고 무늬로**: 팔레트는 팀장 영역이고 다른 화면도 같은 토큰을 쓴다. 색만으로 구분하지 않는 게 원래 권장 방식이다

## 결제 화면 자동 재시도

오전 PG 시험에서 만든 동시 상한(`PgBulkhead`)이 넘치면 503 `PAYMENT_BUSY` + `Retry-After` 3초를 준다. 화면은 지금까지 안내 문구만 띄워서
사람이 직접 다시 눌러야 했다. 이제 **알려 준 초만큼 기다렸다 같은 멱등 키로 자동으로 다시 보낸다.**

| 정한 것 | 이유 |
|---|---|
| 같은 멱등 키 | 서버가 결제 행을 만들기 전에 거절하고 멱등 키를 지우므로, 같은 키로 다시 보내면 처음 요청처럼 처리된다. 두 번 결제될 일이 없고 좌석도 HOLD 그대로 |
| `Retry-After` ±20% | 바로 다시 보내면 그 재시도가 또 부하가 된다(오전 시험 503 1,451번). 같은 순간 거절당한 사람이 같은 순간 몰리지 않게 흔든다 — 로그인 대기실과 같은 방식 |
| 최대 10번, 결제 기한이 10초 넘게 남을 때만 | 기한 직전까지 기다리다 PG 처리 중에 기한이 지나면 더 나쁘다. 멈추면 "좌석은 그대로니 잠시 후 다시"를 띄운다 |
| 남은 초를 버튼에도 | 모바일에서는 안내 띠가 화면 위로 밀려 안 보였다 (390px 스크린샷으로 확인) |
| 화면을 떠나면 멈춤 | 다른 화면에서 결제가 몰래 이어지지 않게 |

확인: 간격 계산은 `payBusy.js`로 빼서 단위 테스트 5개. 화면은 Playwright로 API 응답을 가짜로 꾸며(503 두 번 → 승인) 돌려 보니
1초 간격으로 3번 보내고 멱등 키는 1개, 결과 화면으로 넘어감. 기한이 12초 남은 경우는 한 번 기다린 뒤 멈추고 안내 문구가 뜸.
~~실제 앱·PG 상한으로는 아직 안 돌려 봤다~~ → 저녁에 실제 앱으로 돌려 **버그 하나를 찾아 고침** (아래 "실제 앱으로 자동 재시도 확인").

## 길동현 님께 결제 코드 알림

결제(PAY)는 동현 님 담당인데 11-24부터 내가 결제 코드를 네 번 고쳤다. 11-24 카드 명의 상한 때 "알려 드려야 함"이라고만 적고 미뤄 둔 것까지 한 번에 묶었다.

| 정한 것 | 이유 |
|---|---|
| "기본값은 전부 예전 그대로"를 맨 앞에 | 받는 사람이 가장 먼저 알고 싶은 건 "내 흐름이 바뀌었나"다. 켜지 않으면 안 바뀐다는 걸 먼저 말하고, 예외(결제 화면 2가지)를 따로 적었다 |
| 변경마다 파일·기본값·커밋·테스트 | 코드 리뷰를 하려면 어디를 볼지가 먼저 필요하다 |
| 확인 부탁은 4개로 좁힘 | `PaymentService` 1-2 단계 위치, "결과 모름"으로 돌리는 경우가 기능설계서와 맞는지, 오류 코드 표 2줄(팀장 문서), 실제 PG를 붙일 때 바꿀 경로 |
| 긴 문서 + 메신저용 짧은 글 | 메신저에는 요약과 링크만, 근거는 문서에 |

보낸 뒤 답을 받으면 보완할-일의 "길동현 님께 알리기"를 체크한다.

## 실제 앱으로 자동 재시도 확인 (저녁)

작업 환경 Docker 위에서 앱을 `JEJARI_PG_MODE=http JEJARI_PG_MAX_CONCURRENT=1`로 띄우고, 가짜 PG는 승인 한 건 2.5초.
회원 A가 결제해 PG 자리 1칸을 잡은 동안 회원 B가 화면(`npx vite`, 390px)에서 [결제하기].

- **처음: 멈춤.** 서버는 503 + `Retry-After: 3`을 제대로 줬는데 화면이 "결제하는 중…"에서 멈추고 다시 보내지 않았다
- 원인: 내가 넣은 "화면을 떠나면 재시도 멈춤" 표시(`alive`)를 cleanup에서만 끄고 효과 본문에서 켜지 않았다. 개발 모드(StrictMode)가
  붙였다 떼고 다시 붙이면서 false로 남았다. 오전 가짜 응답 시험은 배포 빌드라 못 잡았다
  → [트러블슈팅](../troubleshooting/20261127-결제-화면-자동-재시도가-개발-모드에서-멈춤.md)
- 고친 뒤: B 요청 **503(+0.37초) → 3초 대기 → 201(+5.9초)**, 안내 띠·버튼 "몰려서 3초 뒤 자동으로 다시 (1/10)", 결과 화면 "표가 확정됐어요", 예약 CONFIRMED
- 공용 서버는 배포 빌드라 영향 없음 (StrictMode 두 번 붙이기는 개발 빌드에만)
- 배운 점: 화면 시험은 개발 서버와 배포 빌드 둘 다로. 가짜 응답만으로는 "서버가 뭘 주는가"만 맞출 뿐 화면 생명주기는 못 본다

## 결제 거절 반복 신호 — 추천안 (강다인 님께 드릴 것)

**하려는 것**: 훔친 카드 목록을 우리 결제로 "살아 있나" 시험하는 모양(카드 대입)을 위험 점수에 넣는다. 지금은 결제 실패가 위험 입력에서 아예 빠져 있다.

| 항목 | 추천 | 이유 |
|---|---|---|
| 규칙 | `DECLINED_CARDS`, **점수만** (케이스 아님) | 케이스 규칙은 `case_marker.rule_code` CHECK에 값을 넣는 ERD 패치가 필요하고, 사람 오탐을 아직 못 쟀다 |
| 대상 | **명의(CI)** | 계정을 바꿔 가며 시도해도 명의로 모인다. 카드 쪽(한 카드에 여러 명의)은 카드 명의 상한이 이미 맡는다 |
| 세는 것 | 최근 1시간 **서로 다른 카드**의 거절 수 | 같은 카드 거절 반복은 사람(한도 초과·잔액 부족 뒤 재시도). 카드를 바꿔 가며 거절이 나는 게 대입이다 |
| 뺄 것 | ~~`fail_reason = 'PG_NOT_RECEIVED'`~~ → **`PG_`로 시작하는 사유 모두** (강다인 님 수정) | 카드가 아니라 PG 문제다. 결제 단계 차단·카드 명의 상한 거절은 결제 행을 만들지 않아 원래 안 세진다 |
| 기준 | 3장 이상 → 30점 (경고 등급) | 사람은 오타·한도로 1~2장. 30점 단독으로는 차단(80)이 안 되고 다른 신호와 합쳐야 막힌다 → 오탐 비용이 작다 |
| 데이터 | `payment`(FAILED·`fail_reason`·`method_id`) + `reservation.member_id` | 새 컬럼 없음. 정책 키 2개(`risk.rule.declined_cards_min`, `…_points`)만 app_policy에 (ERD v41 `samples+`) |
| 구현량 | `RiskInputReader` 쿼리 1개 + `RiskRule` 1줄 + 점수 계산 | 기존 "구매·취소" 읽기와 같은 모양 |
| 검증 | 연습 봇에 "거절 카드 3장 → 승인 1장" 패턴 추가, 2차 대회 사람 데이터에서 사람당 거절 카드 수 분포 확인 | 잡히는지와 사람 오탐을 같이 본다 |

**알아 둘 점**: 우리 결제는 거절되면 좌석이 풀린다 (Saga 보상). 그래서 대입을 하려면 매번 다시 선점해야 하고, 선점 속도 제한·매수 한도가
이미 속도를 늦춘다. 이 신호는 "막는 첫 관문"이 아니라 **그 사이를 뚫은 대입을 점수로 남기는 것**이다. 3차 대회 전에 넣으면 3차에서 평가할 수 있다.

## 막힌 점과 해결

| 막힌 것 | 원인 | 해결 |
|---|---|---|
| 할당석을 켜면 대회 좌석 수가 흔들릴 수 있음 | 대회 운행은 70일 뒤라 대상. 만들고 몇 초 뒤 판매를 여는데 1분 틱이 그 사이에 걸리면 5% | 사용법·기능 문서에 적고, 같게 맞춰야 하면 `.env`에서 끄기 |
| 결제 화면이 로그인 확인 전에 그려지면 회원 ID가 없음 | 첫 렌더에서는 `member`가 아직 없음 | 회원이 정해지면 그 회원 번호로 다시 채움 (`useEffect`) |
| 카드 상한 기본값을 올리면 통합 테스트가 깨짐 | 테스트들이 같은 카드로 결제 | 기본값은 0, 공용 서버 정책만 3 |

## 배운 점

- "꺼 둔 이유"는 꺼 둔 곳에만 적으면 이유가 사라진 뒤에도 꺼진 채로 남는다. 이유가 다른 사람 작업이면 그 작업이 끝났는지 코드로 다시 본다
- 시험 데이터의 식별값(카드·전화번호)은 "한 시험 안에서 겹치지 않음"만으로는 모자라다. 운영 DB에 쌓이는 값이면 **시험끼리도** 안 겹쳐야 한다
