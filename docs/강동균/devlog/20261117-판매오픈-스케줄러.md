## 왜 했나

판매 중 여부의 원천은 `train_run.status`다. 대기열 진입과 좌석 선점이 둘 다 이 값을 본다.
**그런데 이 값을 바꾸는 주체가 없었다.**

시드는 넣는 순간의 시각으로 status를 한 번 정할 뿐이다. 그래서 `ON_SALE`인 운행은 시드가 일부러
만들어 둔 `9001`·`9002` 두 개뿐이었고, 명절 운행 8건과 `9003`은 **오픈 시각(내일 07:00)이 와도
열리지 않는다.** `CLOSED`는 상태 코드 목록에 있는데 쓰는 곳이 아예 없었다.

시드 주석도 이걸 기다리고 있었다 — "판매 오픈 시각이 되면 ADM-02 스케줄러가 ON_SALE로 바꿉니다".

## 어떻게 했나

조건부 UPDATE 두 개가 전부다. **마감을 먼저, 오픈을 나중에** 훑는다.

```
CLOSE: status IN ('SCHEDULED','ON_SALE') AND sale_close_at <= SYSTIMESTAMP   → CLOSED
OPEN:  status = 'SCHEDULED' AND sale_open_at <= SYSTIMESTAMP
       AND (sale_close_at IS NULL OR sale_close_at > SYSTIMESTAMP)           → ON_SALE
```

순서를 거꾸로 하면 오픈·마감이 **모두 지난** 운행을 `ON_SALE`로 한 번 올렸다가 곧바로 내린다.
그 찰나에 선점 요청이 들어오면 이미 지난 열차를 판다. 마감을 먼저 훑으면 `ON_SALE`을 거치지 않는다.

주기는 app_policy `sale.open_interval_sec`(10초). `HoldExpiryScanner`와 같은 방식으로 1초마다
깨어나 정책 주기가 지났을 때만 돈다 — 정책을 바꾸면 재기동 없이 반영된다.

## 생각이 바뀐 곳

### 시각 비교를 앱 시계로 하려 했다

`HoldExpiryScanner`·선점이 전부 `Clock`을 주입받아 쓰고 있어서 처음엔 그대로 따라갔다.
그런데 §0.2가 앱 시계를 쓰라고 한 건 **"한 요청 안에서 값이 흔들리면 안 된다"** 는 문제였다
(결제 마감 하나를 네 곳에 같은 값으로 넣는 것).

판매 오픈은 **"여러 대가 같은 기준으로 봐야 한다"** 는 반대 문제다. 앱이 세 대면 각자의 시계로
비교해서 같은 운행의 오픈 시점이 대마다 몇 초씩 달라진다. 그래서 비교를 전부 Oracle
`SYSTIMESTAMP`로 돌렸다. 같은 "시각을 다룬다"인데 규칙이 반대인 자리가 있다는 걸 알았다.

### 정책 리더가 패키지 순환을 만들 뻔했다

판매 오픈은 `train_run`을 건드리니 `train` 패키지가 맞는데, 정책 읽기(`SeatPolicy`)는 `seat`에
있었다. 그런데 `seat`는 이미 `train`을 참조한다 (`SeatMapService` → `TrainLayoutReader`,
`SeatReleaseService` → `TrainRunReader`). 그대로 쓰면 두 패키지가 서로를 참조한다.

`SeatPolicy`는 이름만 seat지 실은 `app_policy` 범용 리더라 `common.config.AppPolicy`로 옮겼다.
7개 파일의 이름만 바뀌고 동작은 그대로다. ADM-03도 정책을 읽을 테니 미리 치워 둔 셈이다.

## 막힌 점과 해결

- **기존 통합 테스트를 깨뜨릴 뻔했다.** 테스트 운행을 `9001`로 쓰려다, 스케줄러가 마감된 운행을
  닫는다는 걸 떠올렸다. 시드 날짜는 적재일 기준 상대값이라(`9001` 마감 = 적재일 + 4일) **볼륨을
  만든 지 5일이 지나면 `9001`이 CLOSED가 된다.** 다른 통합 테스트는 `9001`이 판매 중인 것에 기댄다.
  - 테스트 운행을 `9101~` 대역에 직접 넣고 끝나면 지우도록 바꿨다.
  - 기존 통합 테스트 4개에 `jejari.train.sale-open-scheduler-enabled=false`를 넣었다.
  - 다만 **묵은 볼륨 문제 자체는 스케줄러가 만든 게 아니다.** `TrainRunReader.onSaleRunIds()`와
    `RunInfo.onSale()`이 이미 `sale_close_at > SYSTIMESTAMP`를 함께 보고 있어서, 묵은 볼륨에서는
    스케줄러가 없어도 `9001`로 선점이 안 된다. 스케줄러는 `status`를 그 읽기 조건과 맞춘 것뿐이다.
    기능 문서에 "볼륨을 다시 만들라"를 적어 뒀다.
- `uq_train_run_train_id_run_date` 때문에 테스트 운행의 운행일이 시드와 겹치면 안 된다.
  열차 번호를 번갈아 쓰고 운행일을 +400일 이후로 밀었다.
