## 어떻게 했나

```
[만료] 스캐너 → 건마다 트랜잭션       ┐
[취소] /cancel                        ├→ SeatReleaseTx: 조건부 UPDATE(1행일 때만) → HOLD 행 삭제
[결제 실패] Saga 트랜잭션 안에서 호출 ┘                 → 카운터 감소 → Saga 보상 완료 → 이력 → outbox
                                        커밋 후: 좌석 키 REOFFER:R, limit_decr.lua (예약당 한 번)
```

- 스캐너 조회식은 인덱스 `ix_resv_hold_due`와 같은 `CASE WHEN status = 'HOLD' THEN pay_deadline_at END` 식이라 HOLD 행만 본다.
- 주기·건수·대기자 보류 시간은 `app_policy`(`scanner.hold_interval_sec`, `scanner.batch_size`, `waitlist.reoffer_hold_sec`)에서 읽어 재기동 없이 바꿀 수 있다.

## 왜 이렇게 했나

- **해제를 한 곳으로**: 만료·취소·결제 실패가 하는 일이 상태 값만 다르고 같다(§7.1 표). 세 군데 따로 만들면 카운터 감소나 이벤트 하나를 빠뜨리는 곳이 생긴다.
- **락 대신 "상태가 X일 때만 UPDATE"**: 취소와 만료가 동시에 오거나 앱 여러 대의 스캐너가 같은 예약을 잡아도 DB가 한쪽만 1행으로 만든다. 0행이면 아무것도 안 하니 카운터가 두 번 줄지 않는다.
- **결제 실패는 호출한 쪽 트랜잭션 안에서**: 결제 실패 기록과 좌석 해제가 같이 커밋·롤백돼야 한다. Redis 정리는 `afterCommit`에 걸어 롤백되면 하지 않는다.
- 감수한 단점: 커밋 직후 앱이 죽으면 Redis 정리가 빠진다. 같은 트랜잭션에 남긴 이벤트를 `seat-release` 소비자가 다시 처리해야 하는데, 그 소비자는 아직 없다 (C·D 파트).

## 막힌 점과 해결

- 세션 환경이 재시작돼 Docker·Redis가 내려가 있었다 → dockerd, Oracle(v16 DDL로 새로), Mongo, Redis(AOF)를 다시 띄움. 코드 문제는 없었다.
- 확정 예약 취소(CNL-02, 강다인)와 같은 `/cancel` 경로를 쓰기로 돼 있어 어디까지 내가 할지 애매했다 → 지금은 HOLD만 처리하고 CONFIRMED는 409 `RESERVATION_NOT_HOLD`. 그쪽 서비스가 생기면 컨트롤러에서 상태별로 나눠 부르기로 기능 문서에 적어 둠.

## 배운 점

- 동시성 테스트는 "둘 다 성공하지 않는다"만 보면 부족하다. **카운터가 한 번만 줄었는지**까지 봐야 한다. `CHECK(seat_count >= 0)`이 마지막 방어라 두 번 줄면 예외로 드러난다.
- 롤백 테스트(`setRollbackOnly`)로 "커밋 후에만 Redis를 건드린다"를 직접 확인할 수 있다.
