## 어떻게 했나

```
ERD 편집기 HTML (단일 원본)
  SEED(v1) → SEED_V2 → V3_OPS … V8_OPS   ← 배포된 패치는 고치지 않고 새 패치만 끝에 추가
  → check-erd.js (FAIL 0 확인 + Oracle DDL 생성)   → erd-md.js (종합 ERD 문서)
팀원이 편집기에서 고친 것 → JSON 내보내기 → erd-diff.js → 다음 패치
```

- v3 점검은 기획서 3장(기능)·4장(핵심 과제)·11장(성과 목표)의 항목마다 담당 테이블과 검증 방법을 짝지은 **추적표**로 했다. 테이블이 없는 기능, 기능이 없는 테이블이 거기서 드러났다
- FK 없는 ID 컬럼 14개를 하나씩 보고 7개는 FK로 이었다. 나머지 7개는 일부러 FK를 걸지 않고 이유를 적었다 (PG·Kafka 외부 값, 다형 참조, 키 번호)
- 패치 op는 **두 번 적용해도 결과가 같게** 만들었다. 팀원 브라우저에 저장된 스키마가 제각각이어도 새로 연 사람과 같아지게 하려고

## 왜 이렇게 했나

- **HTML 하나 + 패치**: 팀원 5명이 브라우저에서 각자 고치면 서로 덮어쓴다. 원본을 하나로 두고 바뀐 것만 패치로 쌓으면 누가 언제 무엇을 바꿨는지가 남는다
- **절차를 비고에서 빼서 `concurrency.md`로 (v7)**: 트랜잭션 순서·SQL·Redis 명령이 테이블 비고 수십 곳에 흩어져 서로 어긋나기 시작했다. 스키마(HTML)와 절차(문서), 원천을 두 개로 나누고 검사 스크립트가 § 번호를 확인한다
- **인덱스를 늘리지 않고 줄임 (v6, 54 → 42)**: 예약·좌석·outbox는 쓰기가 몰리는 테이블이라 인덱스 하나가 모든 INSERT 비용이다. 행을 지우지 않는 참조 테이블(역·노선·차종)의 FK 인덱스를 빼고, 배치용 재집계는 오프피크 풀스캔으로

## 막힌 점과 해결

- 검토가 거듭될수록 비고의 SQL이 문서와 어긋남 → v7에서 절차 분리 + 검사 스크립트
- DB 집계만으로는 같은 사람의 동시 요청이 매수 한도를 넘는 걸 못 막음 → v5 `purchase_counter` 조건부 UPDATE를 최종 판정으로, Redis는 1차
- 결제 중에 선점이 만료되는 경우 → v6에서 결제 시작 때 마감을 한 번 연장하고, 연장한 값을 모든 복사본(좌석·saga·Redis TTL)에 같이

## 배운 점

- 스키마는 "테이블을 그리는 것"보다 **검토를 받아 고치는 과정**이 훨씬 길다. 네 차례 검토에서 P0(그대로 두면 버그)만 15건이 넘었다
- 원본이 둘 이상이면 반드시 어긋난다. 원본을 정하고, 나머지는 원본에서 생성하거나 번호로만 가리킨다
