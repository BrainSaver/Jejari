## 어떻게 했나

```
jejari-integrity.timer (매시 41분)
  → deploy/integrity-check.sh → check_booking.sh all 120 (읽기 전용 COUNT 쿼리 10여 개, 약 4초)
  → Pushgateway(127.0.0.1:9091)  jejari_integrity_fail{check=…}, read_ok, last_run
  → Grafana 경보 → Discord
```

- 창을 2시간으로 잡아 매시간 실행이 겹친다 (한 번 놓쳐도 다음에 잡힘)
- 못 읽은 항목은 아예 빼서 **"값 없음"이 0(정상)으로 보이지 않게**. 못 읽으면 `read_ok=0`으로 따로 경보
- 확인: 로컬에서 서버 구성(Prometheus·Pushgateway·Grafana)으로 예약 하나를 일부러 깨뜨림 → "결제했는데 표 없음 1·판매 좌석 어긋남 1"로 critical → 되돌리니 풀림

## 왜 이렇게 했나

- 앱 안 스케줄러가 아니라 **앱 밖 타이머**: 앱이 멈추거나 잘못돼도 점검은 돈다. 점검 대상이 점검을 하면 같이 망가진다
- 구글 클라우드 API·외부 트래픽을 쓰지 않는다. 같은 VM 안 DB에 COUNT만 → 비용은 CPU 몇 초 (`Nice=10`)
- 점검 기록이 없으면 "정상"으로 보게(`noDataState: OK`) 해서, 설치 전에 Grafana가 먼저 규칙을 읽어도 잘못 울리지 않게

## 막힌 점과 해결

- **격리 보관 경보가 안 울림**: 카운터가 1에서 처음 생기면 `increase()`가 첫 1건을 못 본다 → 앱이 뜰 때 0으로 미리 만들어 둠
- 경보 제목의 콜론 때문에 YAML이 깨짐 → 따옴표. 0건인 항목까지 경보에 나열됨 → `> 0` 조건. 값이 소수 여러 자리 → `printf "%.0f"`
- **자동 배포가 BLOCKED로 멈춤**: 경보 규칙·systemd 유닛·sudoers는 서버에서 사람이 적용해야 하는 파일이라, 승인 전까지 **다른 팀원 커밋도 자동 배포가 안 됐다**. 그 전 DLQ 커밋(`docker/kafka/create-topics.sh`)도 같은 이유로 막혔을 수 있었음 → A-08 승인으로 풀고, 서버 작업은 담당 계정(`dita_810`) 경로로 유닛을 직접 설치
- 다른 계정으로 접속하면 홈 폴더가 달라 `~/jejari-app`이 없다. `setup-server.sh`는 실행한 사용자로 유닛을 덮어쓰므로 **다른 계정으로 돌리면 자동 배포가 깨질 수 있다**

## 배운 점

- 경보는 "울려야 할 때 울리는지"를 **일부러 고장을 내서** 봐야 한다. 규칙이 로드됐다는 것만으로는 모른다 (DLQ 경보가 그랬다)
- 서버 담당자만 적용할 수 있는 파일을 바꿀 때는 **커밋 전에** 팀에 알린다. 배포가 멈추면 내 커밋만이 아니라 모두의 배포가 멈춘다
