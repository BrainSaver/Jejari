## 왜 했나

`bench/README.md`에 내가 직접 적어 둔 한계가 있었다.

> Python 스레드로 부하를 준다. GIL 때문에 클라이언트 쪽 병목이 섞인다.
> 뼈대가 올라오면 k6로 HTTP 레벨에서 다시 재야 한다.

뼈대가 올라왔고 좌석 선점 API도 내가 만들었으니 더 미룰 이유가 없었다.

## 생각이 바뀐 곳

### "락 비교를 다시 잰다"를 처음엔 잘못 이해했다

`SeatHoldStrategy`를 프로덕션 `SeatHoldService`에 넣고 설정으로 세 방식을 바꿔 끼우는 것을
먼저 설계했다. 그게 "진짜 HTTP 수준 비교"라고 생각했다.

**그런데 A·B안으로 돌리면 Redis `seat:hold` 키가 비어 버린다.** 그 키는 좌석 배치도(RSV-01)·
해제(RSV-03)·결제 확정(PAY-02)의 원천이다. 측정하려고 운영 경로를 반쯤 거짓으로 만드는 셈이다.

다시 `bench/README.md`를 읽어 보니 재측정이 필요한 이유가 **"부하 생성기가 Python이라서"** 였다.
재는 대상(실험 테이블·락 방식)은 바꿀 이유가 없었다. 그래서 측정용 입구만 따로 만들고
프로덕션 경로는 손대지 않았다. 이렇게 하니 기존 수치와 사과 대 사과로도 비교된다.

**"다시 재라"는 말의 범위를 문서에 적힌 이유에서 다시 읽어야 했다.**

### TPS를 k6의 `iterations.rate`로 쓰면 안 됐다

k6가 주는 비율은 `setup()`까지 포함한 전체 시간으로 나눈다. 시나리오 1의 경쟁 구간은 ~110ms인데
setup(reset)이 수십 ms라 TPS가 반 토막으로 나왔다. 요청 시각의 최솟값·최댓값을 Trend로 모아
그 창으로 나누게 바꿨다 — Python이 ThreadPool 구간만 쟀던 것과 같은 창이다.

(처음엔 Trend의 `count`로 요청 수를 세려 했는데 **Trend에는 count가 없다**. Counter·Rate에만
있다. 결과 카운터 세 개를 더해 쓴다.)

## 결과 — 결론은 그대로, 근거는 더 분명해졌다

| 시나리오 1 (같은 좌석·100명) | TPS | DB 왕복 |
|---|---|---|
| A 비관적 | 167 (py 255) | 101 (py 201) |
| **B 낙관적** | **2,128** (py 1,457) | 119 (py 210) |
| C 현재 | 1,724 (py 2,732) | **1** (py 2) |

**시나리오 1에서 C가 B에 TPS로 졌다.** Python에서는 C가 1.9배 앞섰는데 뒤집혔다. HTTP + Spring
왕복이 요청마다 10~15ms 붙으면서 C가 아끼던 "Redis 왕복 한 번"의 비중이 작아졌기 때문이다.

그런데 **DB 왕복은 119 → 1이다.** 패배자 99명이 DB에 아예 가지 않는다. 명절 예매에서 중요한 건
"이 서버가 초당 몇 건 처리하나"가 아니라 **"Oracle이 버티나"** 다. 앱은 늘릴 수 있고 DB는 못 늘린다.

그래서 1차 구현은 C로 그대로 간다. 다만 **"C가 항상 가장 빠르다"는 말은 이제 안 한다.**
경쟁이 적으면 B가 빠르고(시나리오 3: B 286 vs C 242), 극한 경쟁에서도 TPS만 보면 B가 앞선다.
면접에서 이걸 먼저 말하는 게 더 설득력 있다고 생각한다.

### A 비관적 락은 더 나빠졌다 — 그리고 기다리는 곳이 바뀌었다

TPS가 시나리오와 거의 무관하게 붙어 버렸다 (167 / 148 / 156). Python에서는 경쟁이 줄면
A도 빨라졌는데(255 → 787) HTTP에서는 안 그렇다.

락 대기 p99는 오히려 작다 (28.7 / 10.6 / 7.5ms). 그런데 전체 응답은 245~365ms다.
**기다리는 곳이 DB 락이 아니라 커넥션 풀로 옮겨 간 것이다.** 락을 쥔 채 커밋까지 가는 구간에
HTTP 왕복이 더해져 락 보유 시간이 길어지고, 풀의 커넥션이 그만큼 오래 묶인다.
전에 겪은 "커넥션 풀 중첩 조회 멈춤" 트러블슈팅과 같은 종류의 문제다.

## 막힌 점과 해결

- **ORA-00955를 못 걸러냈다.** 실험 테이블을 "없으면 만든다"로 처리하려고 ORA-00955(이름이
  이미 쓰임)를 예외 메시지에서 찾았는데 안 잡혔다. Spring의 `BadSqlGrammarException.getMessage()`는
  `StatementCallback; bad SQL grammar [CREATE TABLE …]`까지만이고 **ORA 코드는 원인 체인에 있다.**
  `user_tables`를 먼저 보고, 동시 생성 대비로 `getMostSpecificCause()`를 검사하게 고쳤다.
- k6 설치: `winget install Grafana.k6`는 패키지를 못 찾는다. ID가 **`GrafanaLabs.k6`** 다 (v2.4.0).
- 러너의 `reset`에서 `flushdb`를 쓰려다 말았다. 대기열·정책 캐시까지 날려 다른 사람 작업을
  망친다. 그 시나리오의 좌석 키만 지운다.
