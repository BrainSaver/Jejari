## 어떻게 했나

```
연습 (10:49, 20명) → 도구 문제 셋 고침 → A-1 · A-2 (11:20, 200명씩, 서로 다른 새 계정)
```

- 시각은 매시 20분 시작 — 매시 17분 모델 점수 갱신, 41분 정합성 점검과 겹치지 않게
- 서버 쪽 값은 조영준 님이 vmstat(5초) · Grafana · Caddy 로그 · `check_booking.sh`로 같은 구간을 읽음. 서버 시계는 UTC라 KST − 9시간
- 행동 로그 유실 판정은 `jejari_behavior_sent_total` = `jejari_behavior_stored_total` (+ dropped·failed 0). MongoDB `estimatedDocumentCount`는 대충 세는 값이라 보조로만

## 왜 이렇게 했나

- **A-1·A-2를 서로 다른 새 계정으로**: 연습에서 같은 계정으로 두 번 하니 A-1 뒤 1분마다 도는 위험 점수가 계정을 봇처럼 봐서(95) A-2 결제 10/20이 결제 단계 차단(기준 80)에 걸렸다. 11-19 개선 전 측정에는 이 차단이 없었으니, 같은 조건 비교는 점수가 없는 계정으로
- **사람마다 다른 테스트 카드**: 카드 하나를 수백 명이 쓰면 그 카드가 위험 점수의 "결제 수단" 신호가 된다. 처음엔 카드 명의 상한(v37)을 의심했는데 조영준 님 로그로 보니 그 설정은 0(꺼짐)이었다 — 원인은 위 점수 차단
- **k6 버전은 11-19와 같은 1.1.0** (Docker): PC에 설치된 k6는 v2.4라 `K6_DOCKER=1`을 만듦. B는 기준값이 없어 다시 잴 때 설치된 k6로 (Docker 네트워크를 빼려고)
- **400명 이상은 서버 한계가 아니라고 판단한 근거**: 실패가 전부 로그인할 때 새 TCP 연결이 안 열린 것(Docker: connection refused 2,206건, 설치된 k6: 연결 시간 초과 877건), 서버 5xx·Caddy 오류 0, Caddy가 받은 로그인은 전부 200, Docker 유무와 상관없이 같은 곳(400명)에서 시작, 400명 단계 처리량이 800명보다 낮음
- **서버 안 k6는 보수적인 값**: k6가 서버 CPU 4개를 같이 쓴다. 그래도 PC 네트워크 제한을 피하는 유일한 방법이었고, 발표에서는 "보수적"이라고 같이 말한다
- **빅데이터 쪽은 "최대 속도"가 아니라 "몰릴 때 유실 0·밀림 회복"을 보여 줌**: 사용자 800명이 만드는 로그는 최고 259건/초로 파이프라인 한계(로컬 실측 초당 2만~2.8만 건)의 1%. 최대 속도를 공용 서버에서 재려면 MongoDB를 멈춰야 해서(팀원이 쓰는 서버) 로컬 값을 쓴다

## 배운 점

- 부하 도구가 막힌 건지 서버가 막힌 건지는 **서버에 도착한 요청 수**(Caddy 로그)로 가린다. k6의 "실패"에는 연결조차 안 된 것도 들어간다
- 보안 장치가 있는 시스템을 같은 계정으로 반복해서 재면, 두 번째부터는 성능이 아니라 그 장치를 잰다. 측정 계정도 "처음 보는 사용자"여야 한다
- 숫자 하나(5,000·2,000 같은 기본값)를 확인하지 않아 한 번 다시 돌렸다. 해제 화면에서 켠 값을 눈으로 확인하는 단계를 체크리스트에 넣을 것
- 서버 쪽 담당자가 같은 구간의 서버 값을 읽어 주면 원인을 몇 분 안에 가린다. 시각(KST·UTC)을 같이 적는 게 중요했다
