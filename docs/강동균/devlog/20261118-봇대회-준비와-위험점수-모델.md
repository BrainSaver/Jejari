## 왜 이렇게 했나

- **봇 대회**: 지금 탐지율 100%는 규칙을 아는 우리가 만든 봇으로 잰 값이다. 출제자가 푼 시험이라, 규칙을 모르는 사람의 봇이 필요했다
- **로컬 대회**: 공용 서버 비용을 아끼려고 (팀 결정). 대신 모두 한 IP라는 제약이 생겼다 (아래)
- **딥러닝이 아니라 부스팅**: 표 모양 특징 30여 개·수천 건에서는 결정 나무 계열이 처음 보는 수법에 더 버텼다.
  신경망은 마우스 궤적 같은 순서 데이터가 생기면 다시 본다
- **Isolation Forest를 안전망으로**: 부스팅은 "본 적 있는 봇과 닮았나", Isolation Forest는 "사람과 얼마나 다른가"를 봐서
  약점이 다르다 (속도형 29 → 89%)
- **공격 방향 제비뽑기**: 공격자가 모두 Claude로 만들면 봇끼리 닮는다. 방향은 실제 암표상 도구 유형일 뿐이라 블라인드는 안 깨진다

## 막힌 점과 해결

**실제로 돌려 보고서야 안 것들** (생성 데이터만 봤으면 몰랐다)

| 문제 | 원인 | 해결 |
|---|---|---|
| 브라우저 사용자의 기기 정보가 비어 있음 | 화면이 `X-Device-Id`를 안 보냄 (내 빠뜨림) | 처음 열 때 무작위 ID를 만들어 저장·전송 |
| 로그인한 사람의 검색이 행동 로그에 "비회원"으로 | 새로 연 페이지의 첫 요청이 토큰 재발급보다 먼저 나감 | 첫 요청 전에 리프레시를 기다림 |
| 판매 오픈 시각이 9시간 앞당겨 저장 | `setup.sh`가 UTC 컨테이너의 `date`를 그대로 보냄. `TZ=Asia/Seoul`도 Git Bash에선 무시될 수 있음 | UTC + 9시간을 직접 계산 |
| botc가 4석 중 3석에서 멈춤 | 빈 좌석 목록의 n번째를 미리 정해 누르는데, 누를 때마다 목록이 줄어 순번이 밀림 | 누르기 전에 좌석 요소를 고정 |
| 가입이 5명의에서 막힘 | IP당 1시간에 본인인증·가입 10번 (`rate:signup`) | 봇은 명의를 미리 만들기, 대회 날은 `day.sh`가 제한을 잠깐 올림 |

**모델이 배운 가짜 신호** (리허설에서 사람이 100점으로 오탐돼서 찾음)

| 특징 | 왜 가짜인가 | 처리 |
|---|---|---|
| 가입 기간 | 대회에서는 사람·봇 모두 그날 가입 | 모델에서 뺌 |
| 같은 IP 계정 수 · 시간차 | 로컬 대회는 모두 한 PC(한 IP) | 뺌 (`ML_USE_IP=1`로 되살림) |
| 오픈 뒤 첫 선점 | 오픈 시각 대신 "그 운행의 첫 이벤트"를 써서, 같이 넣은 데이터에 따라 기준이 바뀜 | DB의 `sale_open_at`을 꺼내 기준으로 |
| 두 점수의 큰 값 | 각각 95백분위로 자르면 오탐이 8.8% | 합친 점수로 문턱 |

**블라인드 봇을 대리 에이전트로 만들려다 실패**: 규칙을 모르는 새 에이전트에게 맡겼는데 탐지를 피하는 봇 코드를 쓰다
안전 필터에 막혔다. 우회하지 않았다. 대신 그 에이전트가 블라인드 공격자가 읽는 파일에서 규칙 이름이 새는 곳을 찾아 줬다
(내 `client.js` 주석은 지움, `ReservationController.java` 주석은 남음)

블라인드 봇이 검색을 한 번 넣으면 사라진다. 발표 숫자는 대회 날 블라인드 봇과 진짜 사람으로.

## 배운 점

- **섞어서 시험하면 거짓 자신감이 생긴다.** 같은 수법이 학습에도 있으면 100%, 계열 하나만 빼도 74%. 이 차이가 "생성 데이터로 시험하지 않는다"의 근거다
- **모델은 데이터를 모으는 방식의 차이까지 배운다.** 기기 헤더를 고치기 전 데이터는 "기기 없음 = 봇"으로, 로컬 대회는
  "한 IP = 봇"으로 잡혔다. 모델을 바꾸기 전에 데이터가 실제와 같은 모양인지부터 본다
- **실제로 돌려야 보이는 버그가 있다.** 위 표의 다섯 개 중 넷이 화면·스크립트를 실제로 돌려서 나왔다
- **같은 AI가 만들면 닮는다.** 블라인드는 "누가 코드를 쳤나"가 아니라 "지시하는 사람이 뭘 아나"가 가른다
