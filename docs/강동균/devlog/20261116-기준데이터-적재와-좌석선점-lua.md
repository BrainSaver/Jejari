## 어떻게 했나

### 기준 데이터

```
공공데이터 CSV 4건 → tools/load-public-data.js → db/seed/01~05.sql → Oracle → 99_verify.sql 23항목
```

- 시드 SQL의 `-- @generated:…` ~ `-- @end:…` 사이만 스크립트가 만든다. `MERGE` 문과 주석은 손으로 쓴 것이라 건드리지 않는다.
- `docker/oracle/init/02-seed.sh`가 DDL 다음으로 01~05를 실행한다. 전부 `MERGE`라 여러 번 돌려도 결과가 같다.
- CI가 매 push마다 `node tools/load-public-data.js`(검사 모드)를 돌려 시드와 원본이 어긋나면 빌드를 깬다.

### Lua 8개

`hold` · `release` · `extend` · `rehold` · `sold` · `reoffer` · `limit_incr` · `limit_decr`.
핵심은 `hold.lua`가 **전부 검사한 뒤 전부 쓰거나, 아무것도 안 쓰는** 것이다.

## 왜 이렇게 했나

- **적재 스크립트를 따로 만든 이유** — 처음엔 CSV를 눈으로 보고 SQL에 손으로 옮겼다.
  그러다 역코드를 **두 번 틀렸다**(4자리로 추측 → 3자리로 정정 → 진짜는 7자리).
  값이 CSV에서 왔다는 것을 사람이 아니라 기계가 보증해야 한다.
  기능설계서 1.1이 ADM-01 등록 화면 대신 약속한 "적재 스크립트"가 이것이다.
- **`PER_DAY`를 구매일 기준으로** — 이 규칙은 "하루에 몰아 사는 것"을 막는 장치라 세는 단위가
  타는 날이 아니라 사는 날이다. 프로젝트 목표인 암표·매크로 억제와도 맞는다.
- **Lua를 쓴 이유** — "전부 비었나 확인 → 전부 쓰기"를 쪼개면 그 사이에 다른 요청이 끼어든다.
  Redis는 Lua를 한 덩어리로 실행하므로 끼어들 틈이 없다. `WATCH`/`MULTI`로도 되지만 경쟁이 심하면 재시도가 폭증한다.
- **`limit_decr.lua`가 표시 키를 선점한 쪽만 깎는 이유** — 커밋 후 보상이 빠른 경로(앱)와
  보장 경로(outbox 소비)로 **두 번 온다**(§14.3). 두 번 깎이면 한도가 DB보다 작아져 정상 사용자가 막힌다.

## 막힌 점과 해결

- **추측한 값이 네 개 다 틀렸다.** 역코드 7자리, 거리는 재래선이 아니라 고속선(441.7 → **417.4km**),
  좌석수 일반 55·특실 30(추측은 56·36). 거리에서 운임이 나오므로 운임 40행이 전부 바뀌었다.
  → 공공데이터 원본을 받고 나서야 맞췄다. **구조는 추측해도 값은 추측하면 안 된다.**
- **55석이 열 문자 4개로 나누어떨어지지 않는다.** 13열 `ABCD` + 14열 `ABC`가 된다.
  하드코딩된 "창측 1/2" 검증이 깨져서 `CEIL(n/k) + FLOOR(n/k)` 공식으로 바꿨다.
  검증 8번도 `car_type.seat_count`와 비교하도록 일반화해서, 차량유형이 바뀌어도 검증이 따라간다.
- **`ORA-00903`으로 시드가 깨졌다.** 마커를 넣다가 `MERGE` 문 한가운데 빈 줄이 생겼는데,
  **SQL\*Plus는 `SQLBLANKLINES OFF`가 기본이라 문장 중간 빈 줄에서 입력을 끊는다.**
  빈 줄을 없애고 `02-seed.sh`에 `SET SQLBLANKLINES ON`을 넣어 재발을 막았다. 전체 시드도 훑어 확인.
- **매수 제한이 아예 안 걸리는 상태였다.** DDL 예시의 정책 3건이 모두 지난 행사(`valid_to` 2026-09-27)에
  묶여 있었다. §10.6은 유효 기간 안인 정책만 보므로 "정책 없음 = 제한 없음"이 된다.
  내 핵심 수치(1인 매수 제한)가 검증 불가였던 것 → 시연 기간을 덮는 행사·상시 정책을 시드에 넣었다.
  (같은 문제가 `cancel_fee_policy`에도 있어 강다인 님께 알렸고, 나중에 v21로 반영했다.)

## 배운 점

- **1회 측정은 못 믿는다.** 락 비교에서 같은 조건인데 TPS가 2~4배 흔들렸다(B 시나리오3이 227 → 905).
  워밍업 1회를 버리고 5회 중앙값으로 바꿨다.
- **공정 비교는 입력을 공유해야 한다.** 처음엔 전략마다 좌석 배정을 다시 뽑아서 성공 수가
  318/327/315로 갈렸다. 같은 `picks`를 쓰도록 고쳤다. 둘 다 고치기 전 수치를 그대로
  보고했으면 틀린 결론을 낼 뻔했다.
- **"Redis를 끼우면 항상 빠르다"가 틀렸다.** 경쟁이 적으면 Redis 왕복이 순수 오버헤드가 된다.
