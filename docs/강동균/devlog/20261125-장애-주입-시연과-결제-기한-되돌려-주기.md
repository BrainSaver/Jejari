## 어떻게 했나

- 시연: `k6(14_fault_demo.js, CSV 출력) → 60초 뒤 docker compose kill → 45초 뒤 start → healthy 대기 → 40초 뒤 check_booking.sh → (FAIL이면 60초 뒤 한 번 더) → fault_report.py → 시연 예약 정리`
- 결제 기한 되돌려 주기:
  ```
  Redis ping 실패 → downSince 기록 (스캐너 멈춤)
  ping 성공 → dt = min(장애 길이, 결제 기한) → pay_deadline_at > 장애 시작인 HOLD 예약마다
     한 트랜잭션: reservation(+dt, version+1, updated_at) · seat_inventory · saga_instance · waitlist(OFFERED)
     커밋 뒤: rehold.lua로 좌석 키 PXAT = 새 기한 + 유예
  ```
  같은 예약을 두 번 늘리지 않게 늘린 예약 번호를 기억함
- T23은 실행하는 테스트가 아니라 **소스 검사**: 예약·정책의 네이티브 UPDATE가 모두 `version + 1`·`updated_at`을 갖는지 (`NativeUpdateRuleTest`)

## 왜 이렇게 했나

- **문서보다 장애 주입을 믿기로**: "검색은 Redis를 안 써서 정상"이라고 적혀 있었지만 실제로 죽여 보니 917건이 503이었다. 이 시연이 없었으면 발표 때 틀린 말을 했을 것
- **기한을 늘려 주는 건 Redis가 아니라 DB 기준으로**: 장애 동안 Redis 좌석 키가 사라졌을 수도 있다. 원천인 `reservation.pay_deadline_at`을 먼저 옮기고, 복사본(좌석·Saga·대기자·Redis 키)을 따라 옮김 (CLAUDE.md "마감 시각은 같은 값을 복사하고 바꿀 때도 함께")
- **최대 결제 기한 한 번만**: 장애가 몇 시간이면 그만큼 다 주면 좌석이 오래 묶인다. 한 번 기회를 다시 주는 정도로 제한 (§6.3 한계에 적음)
- **공용 서버에서는 시연하지 않음**: 컨테이너를 죽이므로 팀원이 같이 쓰는 서버에서는 위험. PC 결과를 쓴다
