# 2026-11-27 · PG가 느리거나 멈출 때 — 가짜 PG 서버·HTTP 연결·동시 상한, 로컬 측정

> 작성: 강동균 · 결제 코드 담당 길동현 님 대신 진행 · 관련: [결과 문서](../features/PG-지연-시험.md)

## 한 일

- **문제 확인**: 지금까지 잰 결제 시간은 앱 안의 가짜 PG가 0초 만에 답한다고 가정한 값이었다 (`MockPgClient`). 실제 PG는 한 건에 0.5~2초이고 몰리면 더 느려진다
- **방법 고르기**: ① 앱 안에서 멈추기 ② **별도 가짜 PG 서버 + HTTP** ③ 실제 PG 테스트 모드 ④ WireMock 같은 도구 중 ②.
  ③은 테스트 서버 요청 한도가 낮아 우리 대신 그쪽을 재게 되고 장애를 고를 수 없다. ①은 연결·응답 시간 초과를 못 본다. ④는 "몰리면 느려짐"을 못 만든다
- **만든 것**: 가짜 PG 서버(`loadtest/mock-pg/server.js`, Node, 외부 패키지 없음, compose `pg` 프로필), `HttpPgClient`(연결·응답 한도, 실패는 결과 모름),
  `PgBulkhead`(PG 동시 승인 상한, 거절은 503 `PAYMENT_BUSY` + `Retry-After`), 시나리오 15(`./run.sh pgslow`), 단위 테스트 8개
- **측정** (내 PC, 구매자 300명/30초 + 조회만 50명, PG는 승인하지만 응답을 30초 안 줌):

  | | 스레드 최고 | 조회 p99 | 조회 최대 |
  |---|---|---|---|
  | ① PG 0초 (기준) | — | 1.6초 | 2.5초 |
  | ② 장애 · 응답 한도 30초 | **200/200** | **14.7초** | 16.3초 |
  | ③′ 장애 · 30초 + 상한 40 + Retry-After | 112 | 0.89초 | 1.9초 |
  | ④ 장애 · **응답 한도 3초 (앱 기본값)** | **68** | **0.56초** | 1.3초 |

- **정합성**: 네 회차 모두 돈만 빠진 결제·확정인데 승인 없음·예약당 승인 2건·같은 좌석 2번 확정 **0건**. ②의 결과 모름 300건은 스캐너가 약 1분 만에 전부 확정

## 어떻게 했나

```
가짜 PG 서버 → 앱 HTTP 모드로 20명 시험 (VU 번호 버그) → 0초 PG로 400명/5초 (PC DB가 먼저 참)
→ 150명/10초 기준 OK → PG 5초로 30명: 스레드는 묶이고 커넥션은 안 묶임 확인
→ 150명 장애: 147개라 안 넘침 → 300명/30초로 ①②③④ → ③에서 재시도 폭주·ERROR 로그 발견 → Retry-After·로그 고치고 ③′
```

## 왜 이렇게 했나

- **조회만 하는 사람을 같이 돌림**: 결제가 느린 것 자체는 당연하다. 문제는 결제가 스레드를 다 잡아 **결제와 상관없는 사람까지 멈추는 것**이라 그 사람의 응답 시간을 지표로 했다
- **"느린 PG"가 아니라 "응답 없는 PG"로 보임**: 이 PC는 결제가 초당 15건쯤에서 DB 커넥션이 먼저 찬다. 2~4초 PG로는 스레드가 45개 정도밖에 안 묶여서 차이가 안 난다. 같은 원리(스레드 수 = 초당 결제 × 한 건 시간)를 시간 쪽을 늘려 보였다
- **상한은 결제 행을 만들기 전에**: 거절된 결제가 DB에 흔적을 남기면 결과 모름·정리 경로를 타야 한다. 앞에서 막으면 예약이 HOLD 그대로라 같은 멱등 키로 다시 내면 처음처럼 된다
- **상한 기본은 끔**: 응답 한도 3초만으로 버텼다(④). 상한은 한도를 길게 잡아야 하는 PG를 붙일 때의 두 번째 방어

## 막힌 점과 해결

| 막힌 것 | 원인 | 해결 |
|---|---|---|
| 구매자 일부가 로그인 401 | 시나리오 두 개가 VU 번호를 나눠 써서, 구매자 번호가 만든 계정 범위를 넘음 | `exec.scenario.iterationInTest`로 구매자 번호 |
| 운행 9002 배치도 400인데 조용히 실패 | 9002는 부산→서울(반대 방향). 시나리오에 사전 점검이 없었음 | 사전 점검(대기열·배치도·빈 좌석 수) 추가 |
| 0초 PG로도 400명/5초에 503 | 이 PC의 DB 커넥션 20개가 먼저 참 (PG 문제 아님) | 부하를 초당 10명으로 낮추고 사람 수를 늘림 |
| 측정 스크립트를 같은 셸 뒤에서 돌리니 k6 출력이 사라짐 | 같은 셸에서 백그라운드로 돌린 것과 엉킴 | 측정은 별도 백그라운드 작업으로 |
| 상한 40에도 스레드 190개 | 거절당한 구매자가 1~2초마다 재시도(503 1,451번)하고, 503마다 ERROR 로그와 스택트레이스 | `Retry-After` 3초, 예상된 503은 ERROR 로그를 남기지 않음 → 112개 |
| "응답 없음"이 PG 처리 칸을 30초 차지 | 가짜 PG가 응답을 붙잡는 동안 칸을 안 돌려줌 → PG 처리 능력이 무너지는 다른 장애가 됨 | 처리는 끝내고 칸을 돌려준 뒤 응답만 늦춤 |
| 모든 node 프로세스 끄기가 막힘 | 다른 node 프로그램까지 꺼질 수 있음 (맞는 차단) | 포트로 PID를 찾아 그 프로세스만 |

## 배운 점

- 외부 호출이 있는 시스템에서 가장 먼저 볼 숫자는 **응답 한도**다. "기다리는 스레드 = 초당 요청 × 한 건 시간"이라 한도가 곧 최악의 스레드 수를 정한다
- 거절을 빨리 하는 것만으로는 반쪽이다. **언제 다시 오라고 알려 주지 않으면** 거절당한 사람이 재시도로 다시 몰려온다
- "예상된 거절"을 ERROR로 남기면 몰릴 때 로그가 그 자체로 부하가 된다
- PC 한 대 측정은 DB가 먼저 차서 원하는 병목을 못 만들 때가 있다. 그럴 땐 조건을 바꿔 같은 원리를 보이되, 그렇게 바꿨다고 같이 적는다
