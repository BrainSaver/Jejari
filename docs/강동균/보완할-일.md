## 팀과 정할 것

- [ ] **DEPARTED 전이**: `train_run.status`의 `DEPARTED`로 바꾸는 주체가 없다. 판매 오픈 스케줄러가 출발 시각에
  바꿀지, 승차권(TKT) 담당이 바꿀지 정한다. 정하면 `SaleOpenScheduler`에 한 줄 추가하거나 그쪽으로 넘긴다
- [ ] **ADM-03 분당 수치에 만료 건수 넣을지**: 지금 분당 수치는 예약·결제·취소. 결제 기한 초과 만료(RSV-03)를 넣으면
  "선점은 됐는데 결제로 안 이어진 비율"이 보인다. 넣으면 `ReservationStatsReader`에 EXPIRED 집계 추가
- [ ] **기능설계서 미정 사항 15번**: 기획서는 관리자 "열차·노선·좌석 등록"이 필수인데 ADM-01은 P2였다.
  이번에 API를 만들었으니 "1차는 적재 스크립트" 문구를 고칠지 팀장(길동현)과 정한다

## ADM-01·02 관리자 API (2026-11-17 구현) 뒤에 남은 것

- [x] **A-03 화면** (2026-11-17): `frontend/src/admin/Runs.jsx`
- [x] **A-02 화면** (2026-11-17): `frontend/src/admin/Master.jsx`
- [ ] **A-03 다듬기**: 행사 매수 제한 수정 칸, 판매 마감 시각 수정 칸(지금은 오픈 시각만), 운행이 많을 때 페이지 나누기(지금 최대 1000건)
- [ ] **새 노선의 운임**: 화면에서 노선을 만들어도 `fare` 행은 생기지 않는다. 시드 05의 운임 공식(2,800원 + 125원/km,
  특실 ×1.4)으로 노선 등록 때 함께 만들지, 운임 관리 화면을 따로 둘지 정한다. 지금은 새 노선 운행을 검색하면 운임이 비어 나온다
- [ ] **명절 행사 매수 제한 수정**: 행사를 만들 때 전용 정책(1회 4·열차당 4·1일 20·명절 8)이 생기지만, 값을 고치는 API는 없다
- [ ] **`sale_event.status`(PLANNED/OPEN/CLOSED)**: 읽는 곳이 없고 화면에서 손으로만 바꾼다. 운행 상태에서 계산할지 정한다
- [ ] **편성 캐시 여러 대**: 열차 편성을 바꾸면 그 요청을 받은 앱 한 대의 `TrainLayoutReader` 캐시만 비운다.
  운행이 없는 열차만 편성을 바꿀 수 있어 지금은 문제없지만, 앱을 여러 대 띄우면 Redis pub/sub 등으로 알려야 한다
- [ ] **정차 시각 직접 입력**: 운행 일괄 생성은 시드 공식(2.7km/분 + 정차 2분)으로만 시각을 만든다. 역마다 시각을 고치는 기능은 없다
- [ ] **시드 재실행 충돌 가능성**: 시드 04는 열차 1·2의 "오늘 + 3일" 운행을 넣는다. 화면에서 같은 열차·같은 날 운행을
  먼저 만들어 두면 시드 재실행이 `uq_train_run_train_id_run_date`에 걸린다. 시드 열차(1·2)에는 화면으로 운행을 만들지 않는 걸 권장
