# 락 방식 비교 — k6 HTTP 수준 재측정 (§17.1)

> 담당: 강동균 · 측정일 2026-11-17 · 코드: `bench/k6/lock-compare.js`, `bench/web/`, `src/main/java/com/jejari/bench/`
> 이전 측정(2026-11-16, Python): `bench/README.md`
>
> **발표에 쓸 수치는 아래 "재측정 2 — CPU 분리 + 10회차"입니다.** 바로 아래 결과(3회차)의 2·3번 해석은
> 재측정 2에서 뒤집혔습니다.

## 왜 다시 쟀나

`bench/README.md`의 "이 수치의 한계"에 이렇게 적어 뒀다.

> **Python 스레드**로 부하를 준다. GIL 때문에 클라이언트 쪽 병목이 섞인다.
> 뼈대가 올라오면 k6로 HTTP 레벨에서 다시 재야 한다.

고쳐야 할 것은 **부하 생성기**다. 그래서 **재는 대상은 그대로 두고**(실험 테이블 `exp_seat`·
`exp_seat_inv`, 같은 세 전략, 같은 세 시나리오) 부하만 Python 스레드 → k6로 바꿨다.
그래야 두 측정이 사과 대 사과로 비교된다.

### 프로덕션 선점 경로는 건드리지 않았다

`SeatHoldService`에 전략 스위치를 넣는 방법도 생각했지만 안 했다. A·B안에서는 Redis
`seat:hold` 키가 비는데, 그 키가 좌석 배치도·해제·결제 확정의 원천이다. 측정을 위해
운영 경로를 반쯤 거짓으로 만들 수는 없다. 대신 측정용 입구(`com.jejari.bench`)를 따로 뒀고
**개발 모드에서만 존재한다**(`jejari.dev-mode=true`).

## 구조

```
브라우저 ──(SSE)── bench/web/server.js ──(프로세스)── k6 ──(HTTP)── 앱(개발모드)
   ▲  버튼                │ 회차 반복·중앙값             │              │
   └─ 표가 차오름          └ 끝나고 DB로 중복 교차검증 ───┘              └─ exp_seat / exp_seat_inv
```

| 조각 | 하는 일 |
|---|---|
| `com.jejari.bench.LockBenchService` | 세 전략을 "한 요청 = 한 선점 시도"로 노출. `dbCalls`·`retries`·`lockWaitMs`를 응답에 담아 돌려준다 |
| `DevLockBenchController` | `POST /dev/bench/reset` · `POST /dev/bench/hold` · `GET /dev/bench/verify` |
| `bench/k6/lock-compare.js` | 한 번 실행 = 한 전략 × 한 시나리오 × 1회차. 결과를 `BENCH_RESULT {json}` 한 줄로 낸다 |
| `bench/web/server.js` | 사전 점검 → k6 실행 → 중앙값 계산 → 중복 교차검증 → SSE로 밀어 넣기 |

### 측정 공정성을 위해 한 것

- **세 전략이 같은 좌석 배정을 받는다.** 시드(기본 42)로 돌리는 LCG가 요청 i의 좌석을 정한다.
  전략마다 다시 뽑으면 성공 건수부터 어긋난다 (Python 측정에서 실제로 한 번 틀렸다).
  실측에서 세 전략의 성공 수가 **1 / 20 / 319로 정확히 같다** — 배정이 같았다는 증거다.
- **워밍업 1회를 버리고 N회(기본 3) 중앙값**을 쓴다.
- **TPS는 경쟁 구간만으로 계산한다.** k6의 `iterations.rate`는 `setup()`까지 포함한 전체
  시간으로 나누는데, 시나리오 1의 경쟁은 ~110ms라 왜곡이 너무 크다. 그래서 요청 시각의
  최솟값·최댓값을 Trend로 모아 그 창으로 나눈다 (Python이 ThreadPool 구간만 쟀던 것과 같은 창).
- **중복 예약은 앱 응답이 아니라 DB가 증명한다.** k6가 끝난 뒤 러너가 `verify`를 불러
  `GROUP BY HAVING COUNT(*) > 1`로 센다.

## HTTP로 재서 달라진 것

### 1. C안의 근거가 TPS에서 **DB 왕복**으로 더 확실히 옮겨 갔다

시나리오 1에서 **C가 B에 TPS로 졌다** (1,724 vs 2,128). Python에서는 C가 1.9배 앞섰다.
이유는 분명하다 — HTTP + Spring 왕복이 요청마다 10~15ms씩 더 붙으면서, C가 아끼던
"Redis 왕복 한 번" 차이가 전체에서 차지하는 비중이 작아졌다.

그런데 **DB 왕복은 119 → 1이다.** 패배자 99명이 DB에 아예 가지 않는다(§2.1-4).
명절 예매에서 중요한 것은 "이 서버가 초당 몇 건 처리하나"가 아니라 **"Oracle이 버티나"** 다.
앱은 늘릴 수 있고 DB는 못 늘린다. 이 수치가 C를 고른 이유이고, HTTP로 재니 더 분명해졌다.

### 2. ~~A 비관적 락은 더 나빠졌고, **TPS가 시나리오와 거의 무관하다** (167 / 148 / 156)~~

> **재측정 2에서 뒤집힘.** CPU를 나누고 예열하니 A도 893 / 2,120 / 1,553으로 시나리오를 따라 움직인다.
> "~150 TPS로 붙는다"는 A의 성질이 아니라 **CPU 경합 + 덜 데워진 JVM** 탓이었다.

Python에서는 경쟁이 줄면 A도 빨라졌다 (255 → 787). HTTP에서는 어느 시나리오든 ~150 TPS로
붙어 버린다. 락을 쥔 채 커밋까지 가는 구간에 HTTP 왕복 시간이 더해지면서, **락 보유 시간이
길어져 뒤에 선 요청이 전부 그만큼 더 기다린다.** 락 대기 p99는 오히려 작게 보이는데
(28.7 / 10.6 / 7.5ms) 전체 응답은 245~365ms다 — 기다리는 곳이 DB 락이 아니라 **커넥션 풀**로
옮겨 간 것이다. A를 쓸 이유가 없다는 결론은 더 강해졌다.

### 3. ~~경쟁이 적으면 B가 가장 빠르다 — 이건 그대로다~~

> **재측정 2에서 뒤집힘.** 시나리오 3도 C 2,598 · B 2,128이지만 회차 편차 안이라(p≈0.15) "어느 쪽이
> 빠르다"고 말할 수 없다. 아래 2·3번처럼 TPS 한 번의 차이를 해석하면 안 된다는 것이 재측정 2의 교훈이다.

시나리오 3에서 B 286 > C 242. Python과 같은 방향이다. 좌석이 겹치지 않으면 Redis 왕복이
순수 오버헤드가 된다. C는 그래도 DB 왕복을 825 → 319로 줄인다.

### 4. 꼬리 지연은 시나리오 2에서 C가 B를 **앞질렀다**

Python에서는 B가 나았다 (43.5 vs 74.3). HTTP에서는 C 104.5 vs B 130.0으로 뒤집혔다.
B의 재시도(평균 6회)와 패배자의 DB 왕복이 HTTP 지연과 겹쳐 꼬리를 늘린 것으로 보인다.
단 회차 편차가 커서(C 1,818~2,727) 이 뒤집힘은 한 번 더 재서 확인할 값이다.

### 결론은 바뀌지 않는다

1차 구현은 **C(Redis 1차 + DB PK)** 로 간다. 근거는 TPS가 아니라 DB 왕복이고, 그 근거는
HTTP 수준에서 더 커졌다. 다만 **"C가 항상 가장 빠르다"는 말은 이제 하지 않는다** — 경쟁이
적으면 B가 빠르고, 극한 경쟁에서도 TPS만 보면 B가 앞선다.

## 재측정 2 — CPU 분리 + 10회차 (2026-11-17 오후)

### 바꾼 조건

|---|---|---|
| 머신 | 팀원 PC 한 대 | 클라우드 컨테이너 4코어 한 대 |
| CPU | 앱·DB·k6가 같이 씀 | **앱 CPU 0-1 · Oracle·Redis·Mongo·Kafka CPU 2 · k6 CPU 3** (`taskset`, `docker update --cpuset-cpus`) |
| 회차 | 워밍업 1 + 3회 | 워밍업 1 + **10회** |
| 예열 | 칸마다 1회 | 앱 기동 뒤 전체를 한 번 돌린 다음(=1차 패스 버림) 다시 10회 |
| 편차 | 최소~최대 | 최소~최대 + **변동계수**(표준편차 ÷ 평균) + 회차별 값 전부 저장 |

### 차이가 진짜인가 (순위합 검정, 10회 대 10회)

중앙값만 보면 순서가 매번 바뀔 수 있어서, 두 전략의 회차 값 10개씩을 Mann-Whitney 순위합 검정으로
비교했다. p가 0.05보다 작으면 "우연으로 보기 어렵다".

| 비교 | 시나리오 1 | 시나리오 2 | 시나리오 3 |
|---|---|---|---|
| B·C가 A보다 TPS 높음 | 둘 다 p<0.001 | B p=0.01 · C p=0.001 | B p=0.04 · C p=0.02 |
| C vs B — TPS | p=0.57 (차이 없음) | p=0.21 (차이 없음) | p=0.15 (차이 없음) |
| C vs B — p99 | p=0.88 (차이 없음) | **C가 낮음 p=0.005** | C가 낮은 쪽 p=0.08 |

### 그래서 바뀐 것

1. **A(비관적 락)는 확실히 진다.** 세 시나리오 모두 B·C보다 TPS가 낮고, 시나리오 1에서는 p99가 4배다.
   다만 1차의 "~150 TPS로 붙는다"는 CPU 경합과 덜 데워진 JVM 탓이었다
2. **B와 C의 TPS는 구별되지 않는다.** 1차에서 "시나리오 1은 B가 이기고, 시나리오 3은 B가 빠르다"고
   적었지만 10회를 재 보니 전부 편차 안이다. **"C가 더 빠르다"도, "B가 더 빠르다"도 말하지 않는다**
3. **C의 근거는 그대로, 더 단단해졌다.** 차이가 확실한 것은 두 가지다
   - **DB 왕복**: 1 / 20 / 319 vs B 108 / 333 / 829 — 회차마다 같은 값(결정적)이다. 패배자가 Oracle에 가지 않는다
   - **경쟁이 있을 때 꼬리 지연**: 시나리오 2 p99 40ms vs B 55ms (p=0.005)

### 편차가 왜 아직 큰가 (변동 15~33%)

CPU를 나눴는데도 편차가 크게 줄지 않았다. **원인은 k6 경합보다 측정 창 길이**다. TPS를 경쟁 구간
(첫 요청~마지막 요청)으로 나누는데, 그 창이 시나리오 1에서 약 50ms, 시나리오 3에서도 약 200ms다.
요청 하나가 10ms만 늦어도 TPS가 20% 흔들린다. 클라우드 VM의 이웃 소음도 섞인다.

- 발표에서 TPS는 **중앙값 + 범위**로 말하고, 순위는 DB 왕복과 p99로 말한다
- 편차를 더 줄이려면 사용자 수를 10배(시나리오 1: 1,000명)로 늘려 창을 길게 만들어야 한다.
  다만 그러면 "100명이 1석"이라는 시나리오 자체가 바뀌어 Python 측정과 비교가 끊긴다

### 러너에 넣은 것

- 칸마다 TPS·평균·p99의 **최소·최대·변동계수·회차별 값**을 결과 JSON(`spread`)에 저장
- **전체 예열**(`warmupAll`, 기본 켬): 측정 전에 모든 칸을 한 번씩 돌리고 버린다.
  첫 패스에서 시나리오 1 A안이 회차마다 355 → 568로 오르는 것을 보고 넣었다
- `BENCH_LAYOUT` 환경 변수로 CPU 배치 같은 측정 환경을 결과 파일에 남긴다
- 회차 상한 10 → 15, 화면 기본 회차 3 → 10

CPU를 나눠 재현하는 법 (Linux, 4코어 기준):

```bash
docker update --cpuset-cpus 2 jejari-oracle-1 jejari-redis-1 jejari-mongo-1 jejari-kafka-1
set -a && . ./.env && set +a
LC_ALL=C.UTF-8 TZ=Asia/Seoul taskset -c 0,1 java -jar build/libs/jejari-0.0.1-SNAPSHOT.jar \
  --jejari.dev-mode=true --jejari.queue.dev-on-sale-runs=9001
printf '#!/bin/sh\nexec taskset -c 3 k6 "$@"\n' > /tmp/k6-pinned && chmod +x /tmp/k6-pinned
K6_BIN=/tmp/k6-pinned BENCH_LAYOUT="앱 0-1 · DB 2 · k6 3" node bench/web/server.js
```

Windows에서는 PC 두 대(앱·DB 한 대, k6 한 대)로 나누고 러너에 `BASE_URL=http://<앱 PC>:8080`을 주면 된다.

시나리오·전략·회차를 고를 수 있고, 표가 칸마다 차오르면서 Python 측정값이 작은 글씨로 함께
나온다. 결과는 `bench/results/lock-compare-<시각>.json`에 저장된다 (gitignore).
위 표의 기준 측정은 `bench/reference/lock-compare-2026-11-17.json`에 커밋해 뒀다.

k6만 직접 돌리려면:

```bash
k6 run -e STRATEGY=REDIS -e SEAT_FROM=5001 -e SEAT_COUNT=1 -e USERS=100 -e VUS=50 \
       bench/k6/lock-compare.js
```

## 이 수치의 한계 (발표 때 같이 말할 것)

- **앱·Oracle·Redis·k6가 모두 한 PC**다. k6가 CPU를 나눠 쓰므로 절대 수치는 낮게 나온다.
  특히 시나리오 3(500 VU 요청)에서 세 전략 모두 Python보다 3~5배 낮은 것은 여기서 온다.
- **커넥션 풀 기본값**을 그대로 썼다. A안 결과는 풀 크기에 크게 좌우된다.
- **회차 편차가 아직 크다** (변동 15~33%). CPU를 나누고 10회로 늘려도 크게 줄지 않았다 —
  측정 창이 50~200ms로 짧은 탓이다 (위 "재측정 2" 참고). 그래서 B·C의 TPS 차이는 해석하지 않는다.
- **실제 §2.2 트랜잭션은 이것보다 무겁다** (reservation·reservation_seat·purchase_counter·
  history·saga·outbox까지 한 트랜잭션). 세 방식에 공통으로 붙는 비용이라 비교에는 영향이
  없지만 절대 수치는 더 낮아진다. **실제 API 전 구간 수치는 이 실험이 아니라
  `SeatHoldInfraTest`와 `loadtest/` 시나리오 2에서 봐야 한다.**
- 좌석 배정 난수가 Python(`random.Random(42)`)과 **다른 생성기**라 시나리오 3의 성공 수가
  319(Python 312)로 조금 다르다. 한 번의 k6 측정 안에서는 세 전략이 같은 배정을 받으므로
  전략 간 비교에는 영향이 없다.
