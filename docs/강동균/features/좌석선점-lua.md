# 좌석 선점 Redis 스크립트 (RSV-02 1차 판정)

작성자: 강동균 · 코드 위치: `redis/lua/*.lua` (설명은 `redis/README.md`)

## 한 줄 요약

같은 좌석을 동시에 고른 사람 중 **딱 한 명만** 통과시키고 나머지는 **DB를 건드리지도 않고**
돌려보내는 Redis 스크립트 8개입니다.

## 어떻게 동작하나

```
요청 → 입장 토큰 확인 → 멱등 키로 예약 ID 확보
     → limit_incr.lua  (매수 한도 1차)
     → hold.lua        (좌석 경쟁)  ← 여기서 지면 DB 쓰기 0건
     → 이긴 사람만 DB 트랜잭션 (§2.2)
     → 실패하면 release.lua + limit_decr.lua 로 원복
```

- `hold.lua`는 예약할 좌석 키를 **전부 검사한 뒤 전부 쓰거나, 아무것도 안 씁니다.**
  일부만 잡힌 반쪽 예약이 생기지 않습니다.
- Lua를 쓰는 이유: "전부 비었나 확인 → 전부 쓰기"를 쪼개면 그 사이에 다른 요청이 끼어듭니다.
  Redis는 Lua를 한 덩어리로 실행하므로 끼어들 틈이 없습니다.

## 왜 이렇게 했나

- **Redis 1차 + DB 최종** (§0.1). 패배자는 DB에 아예 안 갑니다. 인기 열차에 1,000명이
  몰려도 DB에는 1건만 들어갑니다. 이게 락 방식 비교(§17.1)에서 현재 설계(C안)가
  비관적 락(A안)보다 유리한 지점입니다.
- **`limit_incr`이 걸린 키 번호를 돌려줍니다.** 열차당·1일·명절 중 어디서 걸렸는지 알아야
  `LIMIT_PER_RUN`·`LIMIT_PER_DAY`·`LIMIT_PER_HOLIDAY`를 구분해 응답합니다.
  문서(§14.2)엔 "0 반환"이라 돼 있던 걸 `{0, i}`로 바꾸고 `concurrency.md`도 같이 고쳤습니다.
- **`limit_decr`은 표시 키(`limit:dec:{R}`)를 선점한 쪽만 깎습니다.** 커밋 후 보상이
  빠른 경로(앱)와 보장 경로(outbox)로 **두 번 옵니다**(§14.3). 두 번 깎이면 한도가 DB보다
  작아져서 정상 사용자가 막힙니다.
- **`extend`·`rehold`·`limit_decr`은 없는 키를 만들지 않습니다.** 특히 `extend`가 없는 키를
  만들면 이미 만료돼 남에게 넘어간 좌석을 되살리게 됩니다.

## 주의할 점

- **Redis `maxmemory-policy`가 `noeviction`이어야 합니다** (§14.5). 기본값(`allkeys-lru`)이면
  메모리가 찰 때 `seat:hold` 키가 조용히 사라져 **같은 좌석이 두 번 팔립니다.**
  조영준(E)의 Docker Compose에 이 설정이 꼭 들어가야 합니다.
- 만료는 전부 **앱 시계로 계산한 `PXAT`(epoch ms)** 입니다. Redis 서버 시계를 쓰지 않습니다
  (§0.7). `reservation.pay_deadline_at`과 같은 값이어야 합니다 (§0.2).
- `limit_incr`의 키 순서는 **열차당 → 1일 → 명절**로 고정입니다. 순서를 바꾸면 에러 코드가
  뒤바뀝니다.
- 키 이름의 `{}`는 자리표시자입니다. 실제 키엔 중괄호가 없습니다 (§14.4의 클러스터 해시
  태그와 다름).
