# 카드 한 장에 붙는 명의 상한 (도용 카드)

> 작성: 강동균 · 2026-11-23 · 절차: [concurrency.md §4.3](../../concurrency.md) · ERD v37 (`card_lock`)
> 결제(PAY-01)는 **길동현 님 담당**이라, 결제 시작 흐름은 바꾸지 않고 검사 하나만 덧붙였습니다.

## 한 줄 요약

같은 카드를 **서로 다른 사람(명의) 여럿이** 쓰려 하면 정해 둔 수(`payment.max_ci_per_card`)부터 결제 시작을 거절합니다.
**지금은 꺼져 있습니다(0).** 켜기 전에 할 일이 있습니다 (맨 아래).

## 왜

카드가 도용됐는지는 카드사·PG가 판단합니다. 우리가 볼 수 있는 건 **한 카드가 여러 사람에게 쓰이는 모양**입니다.
훔친 카드 한 장을 명의 여러 개로 돌려 쓰면 매수 제한(명의별)을 피해 표를 더 살 수 있습니다.
전에는 같은 카드에 명의가 몇 개 붙든 막지 않았고, 위험 점수(`LINKED_ACCOUNTS`)만 조금 올렸습니다.

## 핵심 원리

**1. 계정이 아니라 명의로 셉니다.** `member.ci_hash`는 유일하지 않아 한 사람이 계정을 여러 개 가질 수 있습니다.
본인 카드를 본인 계정 여러 개에 쓰는 건 정상이라, 같은 명의의 다른 계정은 한 명으로 셉니다.

**2. "센 다음 넣기"는 동시 요청에 뚫립니다.** 새로 훔친 카드로 계정 10개가 **동시에** 결제를 시작하면
모두 "0명"으로 세고 전부 통과합니다. 도용 카드를 쓰는 쪽이 바로 이렇게 할 사람들입니다.
아직 `payment_method` 행이 하나도 없는 카드라 `FOR UPDATE`로 잠글 행도 없습니다.

그래서 카드 해시마다 한 행짜리 **`card_lock`** 을 두고, 그 행을 잠근 **뒤에** 셉니다.

```
MERGE card_lock (없으면 만듦) → SELECT … FOR UPDATE (같은 카드는 여기서 줄 섬) → 원천 테이블에서 셈 → 넣거나 거절
```

매수 제한의 `purchase_counter`가 판정을 한 행에 모으는 것과 같은 생각입니다. 잠금은 결제 시작 트랜잭션 맨 나중에
한 행만 잡아서 데드락이 생기지 않습니다 (concurrency.md §0.4-8).

**3. 개수는 따로 세지 않습니다.** 합성 데이터 생성기나 테스트처럼 이 경로를 거치지 않고 `payment_method`에 넣는 곳이
있어서, 개수를 `card_lock`에 따로 두면 어긋납니다. 잠근 뒤 매번 원천에서 셉니다.

**4. 거절돼도 좌석은 그대로입니다.** 결제 시작 트랜잭션 전체가 되돌아가 예약은 HOLD로 남고,
다른 카드로 바로 다시 결제할 수 있습니다 (위험 차단 `PAYMENT_RISK_BLOCKED`는 좌석을 푸는 것과 다릅니다).

## 확인한 것 (`CardLinkLimitInfraTest`)

| 시험 | 기대 |
|---|---|
| 끄면(0) 명의 5개가 같은 카드 | 전부 통과 |
| 켜면(3) 명의 4번째 | `PAYMENT_CARD_LINK_LIMIT`(422), 예약은 HOLD, 다른 카드로 다시 결제 성공 |
| 같은 명의의 계정 3개 + 다른 명의 2개 | 전부 통과 (명의는 3개) |
| 상한이 찬 뒤 이미 붙은 명의의 새 계정 | 통과 |
| **처음 보는 카드로 명의 10개 동시 결제 시작** | **정확히 3개만 성공, 7개 거절** |

## 켜기 전에 할 일 — 같은 가상 카드번호를 쓰는 곳

카드 해시는 **번호 전체의 HMAC**이라 번호가 같으면 한 장의 카드입니다. 모의 PG는 **끝자리로만** 결과를 정하니
(0 거절 · 8 늦은 승인 · 9 결과 모름 · 나머지 승인), 앞부분을 사람마다 다르게 바꾸면 동작은 그대로입니다.

| 곳 | 지금 | 켜면 | 담당 |
|---|---|---|---|
| 결제 화면 버튼 `frontend/src/user/Pay.jsx` | "바로 승인" = `4111111111111111` 고정 | 시연·대회에서 **4번째 사람부터 막힘** | 화면 |
| k6 시나리오 11 `loadtest/scenarios/11_user_journey.js` | 가상 사용자 전원 같은 카드 | **성능 측정이 깨짐** | 김성원·조영준 |
| 대회 사람 안내 · 진행 화면 | 예시 `4111 2222 3333 4441` | 예시를 따라 친 사람끼리 막힘 → **사람 오탐** | 강동균 |
| botb `loadtest/contest/botb/bot.cjs` | 6개 명의가 같은 카드 | 4번째부터 막힘 | 길동현 (블라인드 봇이라 다른 사람이 못 고침) |
| botc · k6 시나리오 12 | 명의마다 다른 번호 | 영향 없음 | — |

botb가 막히는 건 사실 **이 기능이 잡아야 할 모양 그대로**입니다(한 카드로 명의 여럿). 다만 2차 대회의 "보강 전후" 비교에
들어가는 변화라, 켜는 시점은 강다인 님(수비)과 맞춰야 합니다.

켜는 방법: 관리자 화면 정책에서 `payment.max_ci_per_card`를 `3`으로. 1초 안에 반영됩니다.
기존 DB는 먼저 `db/patch/v37.sql`을 적용하세요 (끈 상태에서는 패치 전에도 결제는 그대로 됩니다).
