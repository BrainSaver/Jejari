# 행동 로그 적재 용량 — 얼마나 받을 수 있고, 밀리면 어떻게 따라잡나

> 작성: 강동균 · 2026-11-20 · 관련: RISK-01 (행동 로그), `behavior/sink/BehaviorSink`·`SinkPacer`
> 같이 보기: [데이터-유실-점검](데이터-유실-점검.md) · [트러블슈팅: 밀린 행동 로그를 따라잡느라 예매가 느려짐](../troubleshooting/20261120-밀린-행동-로그를-따라잡느라-예매가-느려짐.md)

## 한 줄 요약

행동 로그 적재(Kafka → MongoDB)는 **초당 약 2만~3만 건**까지 받는다. 평소 유입(예매 150명 몰림에 초당 최고 약 100건)의
수백 배라 **평소엔 병목이 아니다.** 문제는 장애 뒤 **밀린 것을 한꺼번에 따라잡을 때**다. 그때 CPU를 다 써서 예매가 약 3배
느려졌다 → 적재 속도 상한 **초당 2,000**으로 따라잡는 속도만 낮췄다.

## 흐름

```
요청 → BehaviorPublisher(메모리 큐 → 실패하면 디스크 버퍼) → Kafka jejari.behavior (파티션 12)
     → BehaviorSink 소비자 3개 → [속도 상한 2,000/초] → CI 찾기·기기 연결(Oracle) → MongoDB behavior_log
```

## 1. 최대 적재 속도 (밀린 30만 건을 다 넣는 속도, 10%→90% 구간)

앱을 멈춘 채 Kafka에 30만 건을 미리 넣고 → 앱을 띄워 1초마다 저장 건수(`jejari_behavior_stored_total`)를 읽음.
회원 5,000명(시험용 `@loadtest.example.com`, 끝나고 지움), 이벤트 종류는 실제 비율과 비슷하게.

| 설정 | 초당 저장 | Oracle 커넥션 최대 |
|---|---|---|
| 지금 (소비자 3 · 묶음 1,000) | **28,274** (다시 재면 19,029) | 2~3 |
| 비로그인 이벤트 (Oracle 안 감) | 39,375 | 1 |
| 소비자 6 | 24,528 | 4 |
| 소비자 12 | 27,797 | **12** |
| 묶음 3,000 | 29,141 | 3 |

- **소비자를 늘려도 빨라지지 않는다.** 4코어에서 MongoDB·CPU가 먼저 찬다. 대신 Oracle 커넥션을 소비자 수만큼 쥔다 → 3개 유지
- 다시 쟀을 때 느려진 것은 컬렉션이 커지면서다 (아래 3)

## 2. 밀린 것을 따라잡는 동안 예매는? (핵심)

**MongoDB가 멈춘 사이 50만 건이 밀림 → 예매 150명이 10초 안에 몰리는 중에 MongoDB 복구** (판매 오픈 중 장애 복구와 같은 상황).
같은 앱·같은 열차의 빈 운행으로 "예매만" 기준선과 번갈아 쟀다.

| 상한 | 좌석 선점 p95 (예매만 → 따라잡는 중) | 결제 p95 | 좌석 배치도 p95 | 50만 건 따라잡는 시간 |
|---|---|---|---|---|
| 없음 (2회) | 217~222 → **631~633ms** (최대 1.53초) | 140~164 → 424~563ms | 91~128 → 394~505ms | 약 20초 (최고 초당 3만) |
| 5,000 (2회) | 143~226 → 385~420ms | 110~123 → 289~332ms | 81~113 → 183~217ms | 약 100초 |
| **2,000** | 264 → **339ms** (약 1.3배) | 152 → 287ms | 145 → 182ms | 약 4분 |

- **DB 커넥션 대기는 모든 경우 0.** 느려진 원인은 커넥션 풀이 아니라 **CPU 100%** (예매 + 따라잡기가 같은 4코어)
- 서버도 4코어 VM 하나에 앱·Oracle·MongoDB·Kafka가 같이 있어 같은 일이 생긴다
- 평소 유입은 예매 150명 몰림에 **초당 최고 약 100건**(1인 약 4건) → 800명이면 약 530건. 상한 2,000은 그 약 4배라 평소엔 기다리지 않는다
- 밀림 경보(10만 건 · 5분)도 안 울린다: 50만 건 밀림 + 유입 530/초여도 (50만 - 10만) ÷ (2,000 - 530) ≈ 4.5분

## 3. 디스크와 인덱스

| 항목 | 값 (233만 건일 때) |
|---|---|
| 문서 평균 크기 | 578바이트 (압축 전) |
| 디스크 (데이터 + 인덱스) | 667MB + 472MB → **1건에 약 490바이트** |
| 가장 큰 인덱스 | `ux_event_id` 236MB (인덱스 전체의 **50%**) |

- 보관 180일 기준 디스크 = 하루 건수 × 180 × 490바이트. 예: 하루 100만 건이면 약 88GB → 서버 디스크 크기와 같이 봐야 한다
- `event_id`는 무작위 UUID라 인덱스 아무 데나 끼어 들어간다 → 컬렉션이 커질수록 쓰기가 느려진다 (다시 잰 값이 느렸던 이유로 추정).
  시간순 UUID(v7)로 바꾸면 끝에만 붙어 덜 느려진다 — 다음 후보

## 4. 설정

| 설정 | 기본 | 뜻 |
|---|---|---|
| `jejari.behavior.sink-max-per-sec` | 2000 | 적재 속도 상한 (0 = 끔). 바꾸면 앱 재시작 |
| `jejari.behavior.sink-concurrency` | 3 | 소비자 스레드 수 (늘려도 빨라지지 않음) |
| `behavior.batch_size` (app_policy) | 1000 | 한 번에 받는 건수 |

## 5. 다시 재는 법

1. 시험 회원 5,000명 넣기 (`member` 900001~905000, 이메일 `tput*@loadtest.example.com`)
2. 앱을 멈추고 Kafka에 N건 넣기 (`kafka-console-producer.sh --property parse.key=true`, 키 `m:<회원>`)
3. 앱을 띄워 `/actuator/prometheus`의 `jejari_behavior_stored_total`을 1초마다 → 10%→90% 구간 속도
4. 따라잡기 시험: `docker pause jejari-mongo-1` → N건 넣기 → 20초 쉼 → `./run.sh journey -e USERS=150 -e SPREAD_SEC=10 -e RUN_ID=<빈 운행>` 시작 3초 뒤 `docker unpause`
5. 끝나면 시험 회원·`member_device`·시험 문서를 지운다

## 한계

- 로컬 4코어 컨테이너 하나 (서버와 구성은 같지만 CPU 성능은 다름). 서버에서 다시 재야 정확하다
- 예매 기준선이 회차마다 흔들린다 (143~264ms). 그래서 매번 "예매만"을 바로 옆에서 같이 쟀다
- 상한 2,000은 1회 측정. 서버 실측 뒤 조정
