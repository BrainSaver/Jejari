한눈에 수치 무엇이 달라졌나 직접 돌려보기 한계

한 줄 결론

C(Redis 1차 + DB PK)로 간다. 이유는 속도가 아니라 DB 보호다.
같은 좌석에 100명이 몰릴 때 C는 DB를 1번 두드린다. A는 101번, B는 119번이다.

같은 좌석 1개에 100명 — DB 왕복 횟수

A 비관적101회
B 낙관적119회
C 현재1회

진 요청 99명이 Redis에서 걸러져 DB에 아예 가지 않는다 (concurrency.md §2.1-4).

같은 구간 — 초당 처리(TPS)

A 비관적167
B 낙관적2,128
C 현재1,724
TPS만 보면 C가 B에 진다. 이전 Python 측정에서는 C가 1.9배 앞섰는데 HTTP로 재니 뒤집혔다. 요청마다 HTTP·Spring 왕복이 10~15ms 붙으면서 C가 아끼던 "Redis 왕복 한 번"의 비중이 작아졌기 때문이다.
그래도 결론은 그대로다 — 앱은 늘릴 수 있고 Oracle은 못 늘린다. 명절 예매에서 먼저 터지는 쪽은 DB다.

정확성은 셋 다 같다

3 시나리오 × 3 전략 9칸 전부 중복 예약 0건, HTTP 오류 0건. 세 전략의 성공 수가 1 / 20 / 319로 정확히 같다 — 좌석 배정이 공정했다는 증거다. 차이는 정확성이 아니라 비용이다.

왜 다시 쟀나

bench/README.md의 "이 수치의 한계"에 이렇게 적어 뒀었다.

Python 스레드로 부하를 준다. GIL 때문에 클라이언트 쪽 병목이 섞인다. 뼈대가 올라오면 k6로 HTTP 레벨에서 다시 재야 한다.

고쳐야 할 것은 부하 생성기다. 그래서 재는 대상(실험 테이블 exp_seat·exp_seat_inv, 같은 세 전략, 같은 세 시나리오)은 그대로 두고 부하만 Python 스레드 → k6로 바꿨다. 그래야 두 측정이 사과 대 사과로 비교된다.

프로덕션 선점 경로는 건드리지 않았다

SeatHoldService에 전략 스위치를 넣는 방법도 생각했지만 안 했다. A·B안에서는 Redis seat:hold 키가 비는데, 그 키가 좌석 배치도·해제·결제 확정의 원천이다. 측정을 위해 운영 경로를 반쯤 거짓으로 만들 수는 없다. 대신 측정용 입구(com.jejari.bench)를 따로 뒀고 개발 모드에서만 존재한다.

HTTP로 재서 달라진 것

1. C의 근거가 TPS에서 DB 왕복으로 옮겨 갔다

시나리오 1에서 C가 B에 TPS로 졌다(1,724 vs 2,128). 그런데 DB 왕복은 119 → 1이다. 명절 예매에서 중요한 것은 "이 서버가 초당 몇 건 처리하나"가 아니라 "Oracle이 버티나"다.

2. A 비관적 락은 더 나빠졌고, 기다리는 곳이 바뀌었다

TPS가 시나리오와 거의 무관하게 붙어 버린다 — 167 / 148 / 156. Python에서는 경쟁이 줄면 A도 빨라졌는데(255 → 787) HTTP에서는 그렇지 않다.

락 대기 p99는 오히려 작다(28.7 / 10.6 / 7.5ms). 그런데 전체 응답은 245~365ms다. 기다리는 곳이 DB 락이 아니라 커넥션 풀로 옮겨 간 것이다. 락을 쥔 채 커밋까지 가는 구간에 HTTP 왕복이 더해져 락 보유 시간이 길어지고, 풀의 커넥션이 그만큼 오래 묶인다.

3. 경쟁이 적으면 B가 가장 빠르다 — 이건 그대로다

시나리오 3에서 B 286 > C 242. 그래도 C는 DB 왕복을 825 → 319로 줄인다.

결론은 바뀌지 않는다

1차 구현은 C로 간다. 다만 "C가 항상 가장 빠르다"는 말은 이제 하지 않는다 — 경쟁이 적으면 B가 빠르고, 극한 경쟁에서도 TPS만 보면 B가 앞선다.

직접 돌려보기

버튼을 누르면 실제 k6가 돈다. 이 페이지처럼 숫자가 박혀 있는 게 아니라, 그 자리에서 다시 잰다.

이 러너는 내 PC에서만 돌린다. 서버에 올리지 않는다 — 벤치 API는 개발 모드에서만 열리고 인증이 없어서, 공인 IP에 노출하면 누구나 실험 테이블을 건드릴 수 있다. 수치도 "앱·DB·k6가 한 PC"를 전제로 한 값이라 서버에 올리면 비교가 깨진다.

이 수치의 한계 (발표 때 같이 말할 것)

  • 앱·Oracle·Redis·k6가 모두 한 PC다. k6가 CPU를 나눠 쓰므로 절대 수치는 낮게 나온다. 특히 시나리오 3에서 세 전략 모두 Python보다 3~5배 낮은 것은 여기서 온다.
  • 커넥션 풀 기본값을 그대로 썼다. A안 결과는 풀 크기에 크게 좌우된다.
  • 회차 편차가 아직 크다 (C 시나리오 1: 893~1,754 TPS). 회차를 늘리거나 조용한 상태에서 다시 재는 것이 좋다. 시나리오 2의 p99 뒤집힘은 한 번 더 재서 확인할 값이다.
  • 실제 §2.2 트랜잭션은 이것보다 무겁다 (reservation·reservation_seat·purchase_counter· history·saga·outbox까지 한 트랜잭션). 세 방식에 공통으로 붙는 비용이라 비교에는 영향이 없지만 절대 수치는 더 낮아진다. 실제 API 전 구간 수치는 SeatHoldInfraTest와 loadtest/ 시나리오 2에서 봐야 한다.
  • 좌석 배정 난수가 Python(random.Random(42))과 다른 생성기라 시나리오 3의 성공 수가 319(Python 312)로 조금 다르다. 한 번의 k6 측정 안에서는 세 전략이 같은 배정을 받으므로 전략 간 비교에는 영향이 없다.

측정 공정성을 위해 한 것

  • 세 전략이 같은 좌석 배정을 받는다. 시드(기본 42)로 돌리는 난수가 요청 i의 좌석을 정한다. 전략마다 다시 뽑으면 성공 건수부터 어긋난다 (Python 측정에서 실제로 한 번 틀렸다).
  • 워밍업 1회를 버리고 3회 중앙값을 쓴다.
  • TPS는 경쟁 구간만으로 계산한다. k6의 iterations.rate는 setup()까지 포함한 전체 시간으로 나누는데, 시나리오 1의 경쟁은 ~110ms라 왜곡이 너무 크다. 요청 시각의 최솟값·최댓값을 모아 그 창으로 나눈다.
  • 중복 예약은 앱 응답이 아니라 DB가 증명한다. k6가 끝난 뒤 러너가 직접 GROUP BY … HAVING COUNT(*) > 1로 센다.
