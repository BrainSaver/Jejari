# Redis 단일 장애점 — 멈추는 것과 지켜지는 것

> 작성: 강동균 · 2026-11-25 · 원천: [`docs/concurrency.md`](../../concurrency.md) §2.1·§10.4·§10.7·§14.3·§14.4·§14.5
> 계기: 외부 평가 ⑤ "Redis가 단일 노드라 SPOF. 재시작 복구(T14)는 있지만 장애 조치 이야기는 없다"

## 한 줄 요약

**Redis는 "가용성"의 단일 장애점이지 "정합성"의 단일 장애점이 아닙니다.** Redis가 죽으면 예매가 멈추지만(503),
잘못 팔리지는 않습니다. 좌석은 DB의 PK, 매수 한도는 DB 카운터(`purchase_counter`), 커밋 뒤 정리는 outbox가 최종이라
Redis가 가진 값을 잃어도 되살릴 수 있게 설계했습니다. 그래서 장애 조치(복제·Sentinel)는 **덜 멈추게 하는 일**이지
"틀리지 않게 하는 일"이 아닙니다.

## 1. Redis가 통째로 죽으면 (코드로 확인)

연결이 끊기면 요청은 **2초 안에 503 `SERVICE_UNAVAILABLE`** 을 받습니다 (`spring.data.redis.timeout: 2s`, `RedisExceptionHandler`).
기본값(60초)이면 요청 스레드가 묶여 Redis와 상관없는 API까지 멈췄을 것입니다.

| 기능 | Redis를 쓰는 곳 | 죽으면 | 데이터 |
|---|---|---|---|
| 역·운행 검색, 운임 | 남은 좌석 수만 Redis 좌석 키로 셈 | **정상** — Redis가 안 되면 DB `seat_inventory`로 셈 | 11-25 시연에서 처음엔 503이었던 것을 고침 ([시연](장애-주입-시연.md)) |
| 대기열 진입·입장 | 대기열 자체가 Redis (`queue:*`) | 503 | 줄 선 순서는 Redis에만 있음 |
| 좌석 배치도 | 입장 토큰 확인 + 1초 캐시 (`seatmap:*`) | 503 | — |
| 좌석 선점 | 1차 판정 `hold.lua`·`limit_incr.lua`, 멱등 키 | **DB에 가기 전에** 503 | DB는 건드리지 않음 → 어긋남 없음 |
| 결제 시작 | 멱등 키 `idem:pay:*` (첫 단계) | DB·PG에 가기 전에 503 | 돈이 나가지 않음 |
| 결제 단계 차단 (위험 점수) | 점수 캐시 | **모르면 통과** (§7.5) | 장애 한 번에 모든 결제가 막히지 않게 |
| 대기열 위험 점수 | 점수 캐시 | 모르면 100점 (뒤로) | 대기열은 이미 Redis가 죽어 503 |
| 로그인 | 시도 제한·잠금 카운터 | 503 (제한을 못 세면 막는 쪽) | 무차별 대입을 열어 주지 않음 |
| 결제 기한 만료 스캐너 | DB로 판정, 끝나고 Redis 정리 | **DB 만료는 계속됨**, Redis 정리는 실패 로그 | 정리는 outbox 보장 경로가 5초마다 다시 (§14.3) |
| 행동 로그·outbox 발행 | 안 씀 (Kafka·Oracle) | 정상 | — |

**주의할 점 하나**: 이미 좌석을 잡은 사람도 결제를 시작하지 못하는데, 만료 스캐너(DB)는 계속 돕니다.
장애가 결제 기한(`reservation.pay_deadline_min` 10분)보다 길면 **그 사람들의 선점이 만료**됩니다.
잘못된 판매는 아니지만 사용자에게는 손해라, **11-25부터 자동으로 막습니다** (concurrency.md §6.3, `RedisOutageGuard`): Redis가 죽어 있는 동안 HOLD 만료를 멈추고, 복구되면 장애 시간만큼(최대 결제 기한 한 번 = 10분) 기한을 늘립니다 (T47).

## 2. Redis가 다시 살아나면

| 잃은 것 | 되살리는 방법 | 확인 |
|---|---|---|
| (AOF `everysec`) 마지막 최대 1초 | 아래와 같음 | — |
| 매수 한도 `limit:*` | 다음 요청이 DB 카운터 값으로 **SET NX 복원** 뒤 더함. 동시에 여러 요청이 와도 한 번만 채움 (§10.4) | **T14** |
| 한도가 DB보다 크게 남음 (보상 유실) | 거절할 때 DB와 비교해 자가 복구 (§10.7) | T33 |
| 좌석 키 `seat:hold:*` | 키가 없으면 `hold.lua`는 통과하지만 **DB에 살아 있는 HOLD 행이 거절** (§2.2-1, DB가 최종) | **T14** |
| 커밋 뒤 정리(좌석 키 → REOFFER, 한도 감소) | outbox `seat-release` 소비자가 같은 스크립트를 다시 돌림. 두 번 돌려도 결과가 같음 (§14.3) | **T26** |
| 위험 점수 캐시 `risk:*` | `RiskCacheResync`가 Oracle `risk_score`로 다시 채움 | — |
| 대기열 순서 `queue:*` | **되살릴 원본이 없음** — 줄 선 사람은 다시 서야 함 | — |

대기열은 일부러 Redis에만 둡니다. 명절 오픈 순간 초당 수천 건의 진입을 DB에 쓰면 DB가 먼저 무너지기 때문입니다.
잃어도 "다시 줄 서기"로 끝나고 돈·좌석은 어긋나지 않는 데이터라서 이 트레이드오프를 골랐습니다.

## 3. 왜 단일 노드인가

- **정합성을 Redis에 걸지 않았기 때문**에, 복제의 이득이 "덜 멈춤"뿐입니다. 3주 프로젝트·CPU 4개 서버 한 대에서는 그 비용(노드·감시·장애 조치 시험)을 정합성 쪽에 썼습니다
- Lua 스크립트가 여러 키를 한 번에 다룹니다. 클러스터에서는 같은 슬롯이어야 해서 키 모양을 바꿔야 합니다 (§14.4에 바꿀 모양을 미리 적어 둠)
- `noeviction`: 메모리가 차도 좌석·멱등 키가 조용히 밀려나지 않고 **쓰기 오류로 드러나게** 했습니다 (§14.5)

## 4. 실제 운영이라면 — 장애 조치 계획

| 단계 | 방법 | 효과 | 남는 위험 |
|---|---|---|---|
| 1 | 복제본 1 + **Sentinel 3** (자동 승격) | 수십 초 안에 다시 받음 | 비동기 복제라 승격 순간 마지막 쓰기를 잃을 수 있음 → **위 2절과 같은 경로로 복구** (T14·T26이 그 근거) |
| 2 | ~~장애 시간만큼 결제 기한 자동 연장~~ (11-25 함, §6.3) | 1절의 "선점 만료" 손해를 없앰 | 최대 결제 기한 한 번으로 제한 · 앱 1대 기준 |
| 3 | 클러스터 (§14.4 해시 태그) | 쓰기 처리량을 나눔 | 키 이름 변경·Lua 분리. 지금 규모에는 필요 없음 |

**발표에서 말할 것**: "Redis가 죽으면 예매는 멈추지만 잘못 팔리지는 않습니다. 좌석은 DB가, 한도는 DB 카운터가,
커밋 뒤 정리는 outbox가 최종이라 Redis 값을 잃어도 되살립니다 — T14·T26이 그 시험입니다.
복제와 Sentinel은 덜 멈추게 하는 다음 단계입니다."
