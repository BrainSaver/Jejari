# 실시간 예매 현황 (ADM-03)

> 담당: 강동균 · 코드: `src/main/java/com/jejari/admin/`
> 관련: 기능설계서 ADM-03 / 화면 A-04 · `GET /api/v1/admin/dashboard/runs/{runId}`

## 한 줄 요약

운행 하나의 "지금"을 숫자 하나로 모아 준다. 10초 폴링 화면이 그대로 그린다.

```
GET /api/v1/admin/dashboard/runs/9001       (관리자 토큰 필요)

{
  "runId": 9001, "status": "ON_SALE",
  "asOf": "2026-11-17T10:30:12", "windowSec": 60,
  "seats":    { "total": 1050, "sold": 12, "held": 3, "remaining": 1035 },
  "rates":    { "reservations": 4, "payments": 2, "cancels": 1 },
  "queue":    { "waiting": 120, "active": 20, "admitPerSec": 5 },
  "payments": { "unknown": 0 }
}
```

`GET /api/v1/admin/dashboard/runs` 는 판매 중 운행 ID 목록 — 화면이 "어느 운행을 볼까"를 고를 때 쓴다.

`GET /api/v1/admin/dashboard/runs/{runId}/minutes?minutes=30` 은 분 경계로 자른 분당 이력이다
(2026-11-17 추가, 아래 "분당 이력" 절).

```
{ "runId": 9001, "asOf": "2026-11-17T10:31:00",
  "minutes": [ { "minute": "2026-11-17T10:02:00", "reservations": 3, "payments": 1, "cancels": 0 },
               …,
               { "minute": "2026-11-17T10:31:00", "reservations": 1, "payments": 0, "cancels": 0 } ] }
```

## 숫자가 어디서 오는가

| 묶음 | 원천 | 비용 |
|---|---|---|
| `seats` | **Redis** `seatmap:{runId}` 캐시 (`SeatMapService` 재사용) | 왕복 1회. 캐시가 살아 있으면 Oracle 0회 |
| `rates` | Oracle `reservation` · `payment` · `cancellation` | 쿼리 3회, 전부 인덱스 범위 |
| `queue` | **Redis** `queue:*` (A 김성원 모듈 키를 읽기만) | 파이프라인 1회 |
| `payments.unknown` | Oracle `payment` (§6.2와 같은 식) | 쿼리 1회, 함수 인덱스 |

## 왜 이렇게 했나

### 좌석은 다시 세지 않고 좌석 모듈에 묻는다

`seat_inventory`를 직접 COUNT하고 싶었지만 **그건 틀린 숫자다.** 좌석 선점은 진 요청이 DB에
아예 쓰지 않는 구조라(§17.1 C안), 실시간 선점 상태는 DB가 아니라 Redis `seat:hold` 키에 있다.
`SeatMapService`가 이미 그 둘을 합쳐 보고 있어서 그대로 불렀다.

덤으로 `seatmap:{runId}` 캐시(1초)가 걸려 있어 **10초 폴링이 Oracle을 두드리지 않는다.**
대신 최대 `seatmap.cache_ms`만큼 늦다 — 현황 화면에서 1초 지연은 문제가 아니다.

### 분당 건수는 캐시하지 않는다

현황 화면이 보는 이유가 "지금 몇 건 들어오는가"라서, 캐시된 값을 보여 주면 폴링하는 의미가 없다.
그래서 이 셋만 매번 Oracle에 간다.

**새 인덱스는 만들지 않았다.** CLAUDE.md가 쓰기 폭주 테이블(`reservation` 등)에 인덱스를 더할 땐
쓰는 쿼리를 같이 적으라고 해서 먼저 기존 인덱스로 되는지 봤다.

- `ix_reservation_run_id` — 운행 하나의 예약만 읽는다. 한 운행의 예약 행은 좌석 수에 묶여
  많아도 수천 건이라, 그 안에서 `created_at`을 걸러도 가볍다
- `uq_payment_phs12n`(`reservation_id` 선행) · `ix_cancellation_reservation_id` —
  결제·취소에는 `run_id`가 없어 예약을 거쳐 조인한다
- `ix_pay_recheck` — 결과 모름 건수. §6.2의 조회식과 **같은 CASE 식**이라야 인덱스를 탄다

### 세는 기준을 좁혔다

- **결제는 `APPROVED`만** 센다. `REQUESTED`는 아직 팔린 게 아니다
- **취소는 `cancellation` 행 기준**이라 "사용자·운영 취소"다. 만료는 돈이 오가지 않아
  `cancellation` 행을 만들지 않으므로(ERD `cancel_type` 설명) 이 숫자에 안 들어온다.
  만료 건수가 따로 필요하면 `reservation.status = 'EXPIRED'`를 세는 항목을 추가해야 한다
- **`payments.unknown`은 운행별이 아니라 전체**다. §6.2의 "결과 모름"은 PG 대사 문제라
  운행과 상관이 없고, 같은 화면 A-04가 ADM-09(결과 모름 처리)도 맡는다

### 대기열은 읽기만 한다

`QueueKeys`(공개 클래스)가 계약이다. 김성원 씨 코드를 건드리지 않고 키 세 개를 파이프라인
한 번에 읽는다.

- `queue:{runId}` ZSET 크기 = 줄 서 있는 사람
- `queue:active:{runId}` ZSET 크기 = 입장해 있는 사람
- `queue:throughput:{runId}` = 초당 입장 수 (입장 스케줄러가 덮어씀)

**Redis가 죽어도 화면 전체가 죽지 않게** 대기열만 0으로 돌려준다. 좌석·예약 숫자는 Oracle에서
오니 그쪽만이라도 보이는 것이 낫다. (좌석은 Redis가 원천이라 그쪽은 그대로 실패한다.)

## 분당 이력 (2026-11-17)

처음엔 화면이 10초마다 받은 "최근 60초 건수"를 브라우저에 쌓아 그래프를 그렸다. 그러면 두 가지가 아쉬웠다.

- **화면을 연 뒤부터만 보인다.** 새로고침하면 그래프가 비고, 판매 오픈 직후 몰린 흐름을 나중에 열어선 못 본다
- **막대끼리 겹친다.** 10초 간격으로 잰 60초 창이라 한 건이 막대 6개에 들어간다

그래서 서버가 **분 경계**(10:31:00 ~ 10:31:59 = 한 칸)로 잘라 지난 N분을 한 번에 준다.

- **새 저장소를 두지 않았다.** 예약·결제·취소 행에 이미 시각(`created_at`·`approved_at`·`canceled_at`)이
  있으니 `GROUP BY TRUNC(시각, 'MI')`로 센다. 시계열 DB나 집계 테이블은 필요 없다
- **같은 인덱스를 쓴다.** 운행 하나의 행만 읽는 건 "최근 60초"와 같고 창만 최대 60분으로 길다.
  한 운행의 예약은 좌석 수에 묶여 많아도 수천 건이라 가볍다
- **빈 분은 0으로 채워** 칸 수가 늘 같다 (그래프 x축이 흔들리지 않게)
- **마지막 칸은 진행 중인 분**이라 폴링할 때마다 자란다. 화면은 흐리게 그려 "아직 덜 찼다"를 보인다
- 범위 밖 `minutes`(0, 500 등)는 오류 대신 1~60으로 자른다
- 이력 요청만 실패하면 숫자 카드는 그대로 두고 그래프 자리에 안내 문구를 띄운다

긴 기간(몇 시간~며칠)의 추이는 여전히 Grafana(ADM-10, 조영준)가 맞다. 여기는 "판매 오픈 뒤 30분"처럼
운영자가 지금 화면에서 바로 볼 짧은 흐름만 맡는다.

## 권한 — VIEWER

`SecurityConfig`가 `/api/v1/admin/**`에 `hasRole("ADMIN")`을 걸고, 그 위에 설계서가 정한
**VIEWER** 등급을 컨트롤러에 붙였다.

```java
@PreAuthorize("hasAuthority('ADMIN_VIEWER')")
```

`AdminRole`은 아래로 갈수록 위 권한을 포함하므로 REVIEWER·SUPERVISOR도 통과한다. 현황 조회는
읽기 전용이고 개인정보가 없어(운행·좌석·건수뿐) 가장 낮은 등급에 두는 것이 맞다. 마스킹이 필요한
ADM-04·05(강다인)와는 성격이 다르다.

> 관리자 등급은 2026-11-17 AUTH-05(관리자 로그인)로 들어왔다. 그 전에는 `hasRole("ADMIN")`
> 하나로만 막혀 있었다.

**`adm` 클레임이 없는 ADMIN 토큰은 403이 아니라 401이다.** `JwtPrincipalConverter`가 세부 권한
없는 관리자 토큰을 위조·손상으로 보고 토큰 자체를 거절한다 (권한 부족이 아니라 인증 실패).

## 행동 로그를 남기지 않는다

내 다른 API 4곳에는 `BehaviorLog.mark`를 넣었지만 여기는 넣지 않았다. 그 로그는 **이용자**
행동을 모으는 것이고(D 강다인), 10초마다 들어오는 관리자 폴링을 섞으면 분석 대상이 관리자
조회로 덮인다.


`AdminDashboardInfraTest` 19개 (분당 이력 4개는 2026-11-17 추가).

| 확인한 것 | 기대 |
|---|---|
| 로그인 없이 | 401 |
| 회원 토큰 | 403 `ADMIN_FORBIDDEN` |
| 등급(`adm`) 없는 관리자 토큰 | 401 (위조로 봄) |
| REVIEWER · SUPERVISOR 토큰 | 200 (VIEWER가 최소 등급) |
| 없는 운행 | 404 `NOT_FOUND` |

| `SOLD:` 키가 있는 좌석 | `sold` 1 |

| `REQUESTED` 결제 | `rates.payments` 0 (승인만 센다) |
| `APPROVED` 결제 + 취소 | 각각 1 |
| `next_check_at`이 미래인 `REQUESTED` | `unknown` 그대로 |
| `next_check_at`이 과거인 `REQUESTED` | `unknown` +1 |
| 대기열 2명·입장 1명·속도 5 | 그대로 보임 |
| 판매 중 운행 목록 | 9001 포함 |
| 분당 이력 기본값 | 30칸, 마지막 칸 = `asOf`, 빈 분은 0 |
| 3분 전 예약 · 10분 전 예약 · 지금 예약+결제 (`minutes=5`) | 3분 전 칸 1, 지금 칸 1, 10분 전은 빠짐 |
| `minutes=500` · `minutes=0` | 60칸 · 1칸 |
| 없는 운행의 이력 | 404 |

> 시드 DDL의 예시 행(예약 301)이 운행 9001 좌석 하나를 `SOLD`로 넣는다. 그래서 좌석 테스트는 시작할 때
> 이미 팔린 좌석 수(`soldBefore`)를 읽어 기준으로 삼는다 (새 볼륨이면 1, 다른 테스트가 지웠으면 0).
