0한 장 요약

처음 보는 사람에게 1분 안에 설명한다면

제자리는 명절 열차표를 봇·매크로 없이 공정하게 파는 예매 시스템입니다. 판매가 열리는 순간 수만 명이 몰리는 상황을 가정하고, 세 가지 문제를 풉니다.

① 공정 — 봇을 막는다

대기열로 줄을 세우고, 사람의 행동 로그(클릭 간격·순서)로 봇 같은 계정을 찾아 순번을 뒤로 미루거나 관리자에게 알린다.

② 정확 — 돈과 좌석이 어긋나지 않는다

같은 좌석을 두 명이 사지 않고, 돈만 빠져나가는 일이 없다. Redis로 빠르게 거르고 Oracle이 최종 판정한다.

③ 버티기 — 몰려도 안 무너진다

로그인 폭주·예매 몰림·장애 중에도 핵심 기능이 살아 있고, 데이터를 잃지 않는다. 숫자로 재서 확인한다.

한 문장으로: "Redis로 빠르게, Oracle로 정확하게, Kafka로 나중에 할 일은 나중에, MongoDB에 행동을 쌓아 봇을 찾는다."

배치 vs 스트림

스트림 (흘러오는 대로)

Kafka 소비자가 이벤트가 오면 바로 처리 — 알림, 좌석 정리, 행동 로그 적재.

배치 (모아서 한 번에)

위험 점수 1분마다, 모델 점수 매시간, 재학습 매주 일요일, 정합성 점검 매시간.

둘을 섞은 이유: 적재는 빨라야 놓치지 않고, 점수 계산은 여러 이벤트를 모아 봐야 의미가 있다 (클릭 하나로는 봇인지 모름).

4Kafka란 무엇인가

"메시지 큐"보다 "모두가 읽을 수 있는, 지워지지 않는 일지"에 가깝다

비유: 공용 업무 일지

예매 서버가 "예약 R123 확정됨"이라고 일지 맨 끝에 한 줄 적는다. 알림 담당, 좌석 정리 담당, 위험 점수 담당은 각자 자기 책갈피(오프셋)를 갖고 그 일지를 읽어 내려간다. 한 사람이 읽었다고 줄이 지워지지 않아서, 담당이 늦거나 잠깐 쉬어도 돌아와서 이어 읽는다. 일지는 7일 동안 보관된다.

왜 Kafka인가 — 다른 방법과 비교

방법장점단점판단
예매 코드에서 알림·좌석 정리를 직접 호출간단알림이 느리거나 죽으면 예매도 느려지거나 실패✗
RabbitMQ작업 큐에 좋음, 라우팅 풍부읽으면 지워져 다시 읽기 어렵다. 여러 소비자가 같은 이벤트를 각자 읽으려면 큐를 여러 개△
Redis Streams이미 쓰는 Redis메모리라 대량·장기 보관에 부담, Redis가 예매 핵심이라 부하를 섞고 싶지 않음△
Kafka디스크 보관·다시 읽기·그룹별 책갈피·파티션 순서·대량 처리운영할 것이 하나 더 (브로커)✓

전달 보장 — "정확히 한 번"을 어떻게 흉내 내나

  • Kafka 기본은 최소 한 번(at-least-once): 처리 후 오프셋 커밋 전에 죽으면 같은 메시지가 다시 온다.
  • 그래서 소비자를 멱등하게 만든다: 두 번 처리해도 결과가 같게. 예약 이벤트는 processed_event(consumer_group, event_id) PK로, 행동 로그는 event_id 유니크 인덱스로 중복을 걸러 낸다.
  • 최소 한 번 + 멱등 = 사실상 정확히 한 번 (effectively once).
  • 보내는 쪽은 멱등 프로듀서(enable.idempotence=true, acks=all): 재전송해도 브로커에 두 번 적히지 않는다.

함정 (실제로 겪음): 묶음 리스너에서 예외를 catch로 삼키면 묶음이 "성공"으로 끝나 오프셋이 커밋되고, 실패한 메시지는 다시 오지 않는다. 주석에는 "재시작 때 다시 온다"고 적혀 있었지만 사실이 아니었다 → 격리 보관함(DLQ)으로 고침.

6Outbox · Inbox · DLQ — Kafka를 "안전하게" 쓰는 패턴

DB와 Kafka에 동시에 쓰면 생기는 문제

문제: 이중 쓰기 (dual write)

예약을 DB에 저장하고 Kafka에 "확정됨"을 보내는 두 동작은 하나로 묶을 수 없다. DB 커밋 후 Kafka 전송 전에 서버가 죽으면 예약은 있는데 알림·좌석 정리는 영원히 안 된다. 반대 순서면 없는 예약의 알림이 간다.

해결 1: Transactional Outbox

한 트랜잭션reservation 저장 + outbox_event에 이벤트 행 INSERT
→
릴레이 (0.2초마다)PENDING인 샤드만 찾아 seq 순서로 발행
→
Kafka멱등 프로듀서, acks=all
→
PUBLISHED 표시성공한 행만
  • 이벤트가 예약과 같은 트랜잭션에 들어가므로 둘 다 있거나 둘 다 없다.
  • 샤드 16개: shard_no = ORA_HASH(partition_key, 15). 같은 예약은 같은 샤드 → 샤드 안에서 seq 순서대로 발행 → 순서 보장. 샤드 하나가 막혀도 나머지 15개는 계속.
  • 맨 앞 행이 FAILED면 그 샤드는 멈춘다 (뒤 이벤트가 앞지르지 않게). 관리자가 고치면 재개.
  • 잠금은 맨 앞 N개 rowid만 (FOR UPDATE WAIT, SKIP LOCKED는 순서가 깨져 안 씀).
  • 함수 기반 인덱스 ix_outbox_pending: PENDING·FAILED 행만 인덱스에 들어가서, 발행 끝난 행이 수만 건 쌓여도 가볍다.
11-20 개선: 보낼 것이 없어도 0.2초마다 샤드 16개에 트랜잭션을 열어, 아무도 안 쓸 때 DB 커넥션을 초당 76번 빌리고 있었다(전체의 93%). "보낼 것이 있는 샤드"를 인덱스로 먼저 찾게 바꿔 초당 81.5 → 10.5번. 발행 지연은 그대로였다. 조건을 IS NOT NULL로 쓰면 테이블 전체를 읽어서 >= 0으로 바꿨다 (실행 계획으로 확인).

해결 2: Inbox (멱등 소비자)

-- 한 트랜잭션에서
INSERT INTO processed_event (consumer_group, event_id, processed_at) ...;  -- 이미 있으면 ORA-00001 → 건너뜀
-- 업무 처리
COMMIT;  -- 그다음 Kafka 오프셋 커밋

processed_event는 8일 보관 — Kafka 보관(7일)보다 길어야 재전달 중복을 막는다.

해결 3: DLQ (격리 보관함)

계속 실패하는 메시지 하나 때문에 파티션 전체가 멈추면 안 되고, 그렇다고 버리면 안 된다 → <토픽>.DLT에 원본 그대로 + 헤더(그룹·이유·오류·시각)로 옮긴다. 원인을 고친 뒤 tools/dlq.sh replay로 원래 토픽에 다시 넣는다 (헤더 dlt-replay-for로 그 그룹만 처리).

7좌석 동시성 — 같은 좌석을 두 명이 사지 않게

프로젝트의 심장

2단 판정

요청 100명같은 좌석
→
Redis hold.lua모든 구간 키를 한꺼번에 SET. 하나라도 남의 것이면 전부 실패
→
승자 1명만 DBreservation → seat_inventory(PK) → purchase_counter 한 트랜잭션
  • Lua가 원자적이라 "검사 → 쓰기" 사이에 다른 요청이 끼지 못한다. "전부 아니면 전무"라 반쪽 예약이 없다.
  • 패배자 99명은 Redis에서 끝나 DB에 아예 안 간다.
  • DB가 거절하면(PK 충돌 등) 롤백 후 Redis 키를 되돌린다(보상). 커밋 뒤 정리는 outbox로 보장.
  • Redis 키 만료 시각 = 결제 마감 시각 (PXAT). 원천은 reservation.pay_deadline_at 하나, 나머지는 복사본.

락 방식 비교 — 왜 이 방식인가 (§17.1)

방식1석 100명 TPS (k6, 10회 중앙값)DB 왕복중복 예약
A 비관적 락 SELECT FOR UPDATE8931010
B 낙관적 락 version2,2481080
C Redis 1차 + DB PK 최종2,04410
예상과 달랐던 점: 처음엔 "C가 가장 빠르다"고 생각했지만, CPU를 나누고 10회 반복해 다시 재니 B와 C는 편차 안이라 승부가 없었다. C를 고른 진짜 이유는 TPS가 아니라 DB 왕복 101 → 1. 명절엔 인기 열차 한 편에 수만 명이 몰리므로 DB가 버티는 게 먼저다. "C가 가장 빠르다"가 아니라 "C만 DB를 지킨다".

멱등 키 — 버튼을 두 번 눌러도 예약은 하나

  1. 화면이 버튼마다 UUID Idempotency-Key를 만들고, 재시도엔 같은 키를 쓴다.
  2. Redis SET idem:{회원}:{키} 새예약ID NX — 처음이면 진행, 이미 있으면 기존 예약 상태를 돌려줌 (아직 처리 중이면 202).
  3. DB 최종 방어: UNIQUE(member_id, idempotency_key).

매수 제한 — 1인 열차당 10석, 하루 20석

  • Redis limit:* Lua가 1차, Oracle purchase_counter의 조건부 UPDATE(seat_count + n <= max)가 최종.
  • "하루"는 사는 날 기준 (하루에 몰아 사는 것을 막는 규칙이라). 자정을 넘겨 취소돼도 그 예약의 날짜 카운터를 깎는다.

8대기열 — 공정하게 줄 세우기

Redis 정렬 집합(ZSET) + Lua

  • 진입: enter.lua가 중복 확인과 ZADD queue:{운행}을 한 번에. 같은 사람(CI)이 다른 계정으로 또 서는 것도 막는다.
  • 시각은 앱이 아니라 Redis TIME으로 읽는다. 앱 서버가 여러 대여도 시계 차이로 순번이 뒤집히지 않게.
  • 입장: 스케줄러가 1초마다 앞에서부터 처리량만큼 입장 토큰 발급 → 좌석 선점 API는 토큰을 검증.
  • 위험 패널티: 위험 점수 1점 = 3분 뒤로 (80점이면 4시간). 차단이 아니라 뒤로 미루기 — 오탐이어도 표를 살 수는 있다.
왜 Redis인가: 수만 명이 1초에 몰리는 쓰기·순위 조회를 DB에 하면 DB가 먼저 무너진다. 줄은 잃어도 다시 설 수 있지만(원본 아님), 돈·좌석은 잃으면 안 되므로 Oracle.

9결제 · 만료 · 취소

외부(PG)가 끼면 "결과를 모른다"가 생긴다

결제 시작 = 마감 연장

HOLD → PAYMENT_PENDING 전이가 1행일 때만 마감을 한 번 늘린다 (PG 타임아웃 + 여유). 결제 중에 좌석이 풀리지 않게.

Saga

결제는 여러 단계(시작·PG·확정)라 한 트랜잭션으로 못 묶는다. 단계마다 상태를 남기고 실패하면 되돌리는 보상 단계를 실행.

만료 스캐너

1초마다 마감 지난 HOLD를 찾아 좌석 반환. 함수 기반 인덱스로 HOLD 행만 본다.

늦은 승인 환불

만료된 뒤 PG가 "승인"이라 답하면 좌석 대신 자동 환불. 돈만 빠지는 일이 없게.

결과 모름 재확인

PG 응답이 끊기면 결과를 모르는 동안 만료시키지 않고 주기적으로 다시 묻는다.

취소표 제안

취소된 좌석을 대기자에게 먼저 제안 (REOFFER 인계 값). 위험 점수가 높으면 뒤로.

블라인드 봇 대회 — 왜 했나

규칙을 아는 우리가 만든 봇으로 잰 100%는 출제자가 푼 시험이다. 그래서 규칙을 모르는 팀원이 봇을 만들고(공격자는 탐지 코드를 못 봄), 학습은 생성 데이터로만, 시험은 손대지 않은 대회 데이터로만 했다.

학습 순환

  1. 실데이터로 "사람 기준" 다시 맞추기 (recalibrate.py)
  2. 관리자 판정을 정답으로 모으기 + 무작위 점검 표본 (의심과 무관하게 뽑은 계정 — 자기 확신 고리 끊기)
  3. 매주 일요일 새벽 재학습 + 자동 시험(관문) → 통과하면 꺼진 후보로 등록, 켜는 건 관리자 (A-09)
정직하게: 사람 기록이 부족해 실제 사람 오탐은 아직 못 쟀다. 봇만 있는 데이터의 100%는 "모두 봇이라 하는 모델"과 구별되지 않는다. 그래서 모델은 보조 의견에 머문다.

16스스로 점검 — 면접 예상 질문

먼저 답해 보고 펼쳐 보기

Kafka의 파티션과 키는 왜 중요한가?

Kafka는 파티션 안에서만 순서를 보장한다. 같은 예약의 이벤트(생성→확정→취소)는 순서가 중요해서 키를 reservation_id로 해 같은 파티션에 넣는다. 다른 예약은 다른 파티션에서 병렬로 처리된다 — 순서와 병렬을 같이 얻는다.

DB에 저장하고 Kafka로 보내는데, 중간에 서버가 죽으면?

이중 쓰기 문제. Outbox 패턴으로 이벤트를 예약과 같은 트랜잭션에서 outbox_event 테이블에 쓰고, 릴레이가 따로 Kafka로 보낸다. 둘 다 있거나 둘 다 없다. 릴레이가 보내고 표시하기 전에 죽으면 다시 보내는데, 소비 쪽 Inbox(processed_event)가 중복을 거른다.

Kafka는 "정확히 한 번"을 보장하나?

기본은 최소 한 번. 오프셋 커밋 전에 죽으면 다시 온다. 그래서 소비자를 멱등하게(processed_event PK, event_id 유니크) 만들어 사실상 한 번으로 만든다. 보내는 쪽은 멱등 프로듀서.

같은 좌석을 두 명이 동시에 누르면?

Redis Lua가 모든 구간 키를 원자적으로 한꺼번에 잡아 한 명만 통과시키고, 승자만 DB로 간다. DB의 PK가 최종 방어. 패배자는 DB에 가지 않아 DB 왕복이 101회에서 1회로 줄었다.

왜 행동 로그는 Oracle이 아니라 MongoDB인가?

양이 많고(요청마다), 모양이 이벤트마다 다르며(meta), 돈과 무관해 트랜잭션이 덜 중요하다. 예매 원본 DB(Oracle)에 부하를 섞지 않고, TTL로 180일 뒤 자동 삭제가 쉽다.

소비자가 처리하지 못한 메시지는 어떻게 하나?

재시도 후에도 안 되면 DLQ(<토픽>.DLT)에 원본 그대로 보관하고 다음 메시지로 넘어간다 (파티션이 막히지 않게). 원인을 고친 뒤 dlq.sh로 그 그룹에만 다시 넣는다. 깨진 메시지는 다시 넣어도 실패하므로 기본 제외.

로그인이 몰리면 왜 다른 기능까지 멈췄나?

Argon2id는 일부러 느리고 서버는 동시에 4개만 돌린다. 요청 스레드가 해시를 기다리며 다 묶여 대기열·조회까지 멈췄다. 해시만 별도 작업자 4개 + 대기 200칸에 가두고 넘치면 429 + Retry-After (벌크헤드) → 800명에서 5xx 0%.

빅데이터 쪽 병목은 어디였나?

적재 자체는 초당 2만 건 이상이라 평소엔 병목이 아니었다. 장애 뒤 밀린 것을 최대 속도로 따라잡을 때 CPU를 다 써서 예매가 3배 느려졌다. 커넥션 풀을 의심했지만 대기 0이라 아니었고, 따라잡는 속도에 상한을 걸어 1.3배로 줄였다.

모델이 봇이라고 하면 바로 막나?

아니다. 사람 오탐을 아직 충분히 재지 못했고, 틀리면 진짜 사람이 표를 못 산다. 관리자에게 보조 의견(근거·닮은 유형)만 보이고, 규칙 엔진 점수도 차단이 아니라 대기열 뒤로 미루기다.

측정하면서 틀린 적은?

커넥션 풀 비교에서 막 띄운 앱과 데운 앱을 섞어 개선 폭을 두 배로 부풀렸다. 같은 조건으로 다시 재서 25~30%로 고쳐 적었다. A-09 쿼리가 전체를 읽을 거라는 추정도 explain으로 재 보니 틀렸다 — 코드가 아니라 실행 계획으로 판단한다.
