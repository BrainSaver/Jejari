# 판매 오픈 스케줄러 (ADM-02)

> 담당: 강동균 · 코드: `src/main/java/com/jejari/train/SaleOpenScheduler.java`
> 관련: 기능설계서 ADM-02, ERD v18, `TrainRunReader`

## 한 줄 요약

`train_run.status`를 시각에 맞춰 옮긴다. 오픈 시각이 지나면 `ON_SALE`, 마감 시각이 지나면 `CLOSED`.

```
SCHEDULED --(sale_open_at 지남)--> ON_SALE --(sale_close_at 지남)--> CLOSED
```

## 왜 필요했나

판매 중 여부의 **원천은 `train_run.status`** 다. 대기열 진입(`JdbcOnSaleRunProvider`)과 좌석 선점
(`SeatHoldService`)이 둘 다 이 값을 본다.

그런데 이 값을 바꾸는 주체가 아무도 없었다.

- 시드(`db/seed/04_regular_run.sql`)는 **넣는 순간의 시각으로 status를 한 번 정할 뿐**이다.
  그 뒤로 오픈 시각이 지나도 `SCHEDULED`로 남는다.
- 그래서 지금 `ON_SALE`인 운행은 시드가 일부러 만들어 둔 `9001`·`9002` 두 개뿐이었다.
  명절 운행 8건(1001~2004)과 `9003`은 오픈이 내일 07:00인데, **내일이 와도 열리지 않는다.**
- `CLOSED`는 상태 코드 목록(`SCHEDULED / ON_SALE / CLOSED / DEPARTED`)에 있는데 **쓰는 곳이 없었다.**

시드의 주석도 이 스케줄러를 기다리고 있었다 — "status는 SCHEDULED. 판매 오픈 시각이 되면
ADM-02 스케줄러가 ON_SALE로 바꿉니다" (`03_sale_event_run.sql`).

## 어떻게 했나

### 마감을 먼저, 오픈을 나중에

```java
int closed = jdbc.update(CLOSE);   // SCHEDULED·ON_SALE 중 마감 지난 것 → CLOSED
int opened = jdbc.update(OPEN);    // SCHEDULED 중 오픈 지났고 마감 안 지난 것 → ON_SALE
```

순서를 거꾸로 하면, 오픈·마감이 **모두 지난** 운행(지난 날짜 운행)을 `ON_SALE`로 한 번 올렸다가
곧바로 `CLOSED`로 내린다. 그 사이 찰나에 선점 요청이 들어오면 이미 지난 열차를 팔 수 있다.
마감을 먼저 훑으면 그런 운행은 `ON_SALE`을 거치지 않고 바로 `CLOSED`가 된다.

### 조건부 UPDATE 두 개가 전부다

목록을 읽어 와서 건마다 처리하지 않는다. 운행 수는 좌석·예약과 달리 많지 않고(지금 11건),
"바꿀 것만 바꾸는" 조건이 그대로 WHERE가 된다. 왕복 2회로 끝난다.

현재 status를 WHERE에 넣은 조건부 UPDATE라(§0.3) **앱이 여러 대여도 안전하다.** 같은 운행을
두 대가 동시에 잡으면 한쪽만 영향 행 1을 받고 다른 쪽은 0을 받는다 (멀티인스턴스 코딩 규칙 3번).
`train_run`에는 `version` 컬럼이 없어 `updated_at = SYSTIMESTAMP`만 올린다.

### 시각 비교는 전부 Oracle `SYSTIMESTAMP`

앱 시계(`Clock`)를 쓰지 않았다. 앱이 여러 대일 때 각자의 시계로 비교하면 같은 운행의 오픈
시점이 대마다 달라진다. 비교 기준은 DB 한 곳이어야 한다.

> 선점의 결제 마감(`pay_deadline_at`)은 반대로 **앱 시계로 한 번 계산해 네 곳에 같은 값**을
> 넣는다(§0.2). 그건 "한 요청 안에서 값이 흔들리면 안 되는" 문제이고, 이건 "여러 대가 같은
> 기준으로 봐야 하는" 문제다.

### 주기

app_policy `sale.open_interval_sec` = **10초** (ERD v18). 1초마다 깨어나 정책 주기가 지났을 때만
돈다 — `HoldExpiryScanner`와 같은 방식이라 정책을 바꾸면 재기동 없이 반영된다.

10초면 오픈 시각보다 최대 10초 늦게 열린다. 명절 예매는 07:00:00에 수만 명이 몰리므로 더 짧게
하고 싶을 수 있지만, 그건 **스케줄러를 조이는 게 아니라 대기열이 받아내는 문제**다. 대기열은
오픈 전에도 줄을 세울 수 있다.

끄는 법: `jejari.train.sale-open-scheduler-enabled=false` (통합 테스트에서 이렇게 끈다).

## 범위에서 뺀 것

**`DEPARTED` 전이는 넣지 않았다.** 출발 시각이 `train_run`이 아니라 `train_stop`의
`MIN(departure_time)`에 있어 조인이 필요하고, 무엇보다 **`DEPARTED`를 읽는 코드가 아직 없다.**
`CLOSED`면 판매가 막히므로 지금 수치에 영향이 없다. 승차권 사용 처리(TKT)를 맡는 사람이
정의할 때 같이 넣는 것이 맞다.

## 알아 둘 것 — 시드 날짜가 묵으면

시드는 **실행한 날 기준 상대 날짜**다 (`9001`의 운행일 = 적재일 + 3일, 마감 = 운행일 + 1일).
그래서 Oracle 볼륨을 만든 지 **5일이 지나면 `9001`의 마감 시각이 과거**가 된다.

이때 스케줄러는 `9001`을 `CLOSED`로 바꾼다. 통합 테스트는 `9001`이 판매 중인 것에 기대므로 깨진다.

**이건 스케줄러가 만든 문제가 아니다.** `TrainRunReader.onSaleRunIds()`와 `RunInfo.onSale()`이
이미 `sale_close_at > SYSTIMESTAMP`를 함께 보고 있어서, 묵은 볼륨에서는 스케줄러가 없어도
`9001`로는 선점이 안 된다. 스케줄러는 `status`를 그 읽기 조건과 **일치시킨 것**뿐이다.

고치는 법 — 시드를 다시 넣어 날짜를 재기준한다:

```bash
docker compose rm -sf oracle && docker volume rm jejari_oracle-data && docker compose up -d oracle
```

## 검증

```bash
docker compose up -d
LC_ALL=C.UTF-8 TZ=Asia/Seoul ./gradlew infraTest --tests 'com.jejari.train.SaleOpenSchedulerInfraTest'
```

`SaleOpenSchedulerInfraTest` 9개. 테스트 운행은 `9101~` 대역에 직접 넣고 끝나면 지우므로
시드 운행(`9001`~)을 건드리지 않는다.

| 확인한 것 | 기대 |
|---|---|
| 오픈 시각 지난 `SCHEDULED` | → `ON_SALE` |
| 오픈 시각 안 된 운행 | 그대로 `SCHEDULED` |
| 마감 시각 지난 `ON_SALE` | → `CLOSED` |
| 오픈·마감 모두 지난 운행 | `ON_SALE`을 **거치지 않고** `CLOSED` |
| 마감 시각 없는 운행 | 오픈만 되고 다시 훑어도 안 닫힘 |
| 이미 `CLOSED`·`DEPARTED` | 건드리지 않음 |
| 두 번 훑기 | 두 번째는 영향 행 0 (여러 대 안전) |
| 전이한 운행 | `updated_at` 갱신됨 |
| 오픈 뒤 대기열 목록 | `onSaleRunIds()`에 들어오고 `9001`도 그대로 판매 중 |

## 다른 파트와의 연결

| 상대 | 영향 |
|---|---|
| A 김성원 (대기열) | `JdbcOnSaleRunProvider`가 보는 운행이 시각에 맞춰 늘고 줄어든다. `9003`은 내일 07:00에 자동으로 열린다 |
| E 조영준 (부하 테스트) | 오픈 순간 트래픽 시나리오를 실제로 재현할 수 있다 — `sale_open_at`을 몇 초 뒤로 넣으면 그 시각에 열린다 |
