## 0. 먼저 — 오전 시험의 서버 값 (결과 문서 빈칸, 5~10분)

[결과 문서](공용서버-부하시험-결과.md)에서 서버 쪽 값만 비어 있다. 빅데이터 시험 전에 읽어 두면 vmstat 파일 하나로 끝난다.
**서버 시계는 UTC** — vmstat 파일(`~/perf-vmstat-0205.txt`, 11:05 KST 시작)은 **KST − 9시간**으로 본다.

## 1. 왜 하나 (1분 요약)

- 오전 시험에서 공용 서버는 **동시 300명 · 초당 327건 · p95 0.22초 · 오류 0**으로 버텼다
- 400명부터는 **내 PC의 네트워크가 새 연결을 막아서**(한 기기 동시 연결 약 300~400개 제한으로 보임) 더 올리지 못했다. 실패한 요청은 서버에 도착하지도 않았다 (조영준 님 확인: 서버 5xx 0, Caddy 오류 0)
- 보고 싶은 것은 **빅데이터 처리** — 사용자 요청마다 생기는 행동 로그가 `앱 → Kafka(jejari.behavior 토픽) → behavior-sink 소비자 → MongoDB behavior_log`로 **놓치지 않고, 밀리지 않고** 쌓이는지
- 그래서 **서버 안에서 k6를 돌려** 네트워크 제한 없이 400 → 800명까지 올리고, 그동안 행동 로그 파이프라인을 잰다

## 2. 무엇을 재나

| 볼 것 | 어디서 | 합격 |
|---|---|---|
| 동시 사용자별 초당 요청 · p95 · 5xx | k6 결과 표 (마지막에 출력) | 버틴 단계 = p95 < 1초 · 5xx < 1% |
| **행동 로그 초당 적재량** | Grafana: `sum(rate(jejari_behavior_stored_total{job="jejari-app"}[1m]))` | 들어오는 만큼 쌓임 (아래 둘과 같이 봄) |
| **보낸 수 = 쌓인 수** (유실) | Grafana: `sum(increase(jejari_behavior_sent_total[20m]))` vs `sum(increase(jejari_behavior_stored_total[20m]))` · 버림 `jejari_behavior_dropped_total` · 실패 `jejari_behavior_failed_total` | **버림 0 · 실패 0**, 보낸 수 ≈ 쌓인 수 |
| **밀림** | Grafana: `max(jejari_kafka_consumer_lag{group="behavior-sink"})` | 몰려도 끝나고 **몇 초~수십 초 안에 0** |
| MongoDB 실제 건수 | 아래 3-2·3-5 명령 (시험 전후) | 늘어난 건수 ≈ 쌓인 수 |
| 서버 CPU | vmstat (`100 − id`) · Grafana | 기록만 (k6도 같은 CPU를 써서 보수적인 값) |
| 예매 정합성 | `check_booking.sh all 30` | 10항목 OK |

## 3. 순서 (약 20분, **매시 20분에 시작** — 매시 17분 모델 점수 갱신·41분 정합성 점검을 피함)

서버 터미널에서 `cd ~/Jejari`. 시작 전에 팀 채널에 "○○:20~○○:40 공용 서버 시험" 공지, 자동 배포 타이머는 꺼 둔 채로. vmstat은 오전 것이 14:05 KST까지 기록하니, 그 뒤에 하면 `vmstat -t 5 | tee ~/perf-vmstat-$(date +%H%M).txt`로 새로 켠다.

### 3-1. 코드 받기 (서버는 이미 main이라 보통 바뀌는 것 없음)

```bash
cd ~/Jejari && git log -1 --oneline
```

### 3-2. 시작 전 MongoDB 행동 로그 건수 (시각도 같이 적음)

```bash
date '+%F %T' | tee ~/bigdata-start.txt
docker compose exec -T mongo bash -c 'mongosh --quiet -u "$MONGO_APP_USER" -p "$MONGO_APP_PASSWORD" --authenticationDatabase jejari jejari --eval "print(\"behavior_log 전체: \" + db.behavior_log.estimatedDocumentCount())"'
```

### 3-3. 작게 한 번 (1~2분, 서버 안에서 k6가 도는지)

```bash
docker run --rm --network host -v "$PWD/loadtest:/lt" -w /lt -e BASE_URL=http://127.0.0.1:8080 grafana/k6:1.1.0 run scenarios/13_capacity.js \
  -e STEPS=10 -e STEP_SEC=30 -e RUN_ID=731045 -e RUN_TAG=s$(date +%H%M)
```

- 마지막에 `용량 시험 결과` 표가 나오면 준비 끝
- `사전 점검 실패(대기열)` → 운행 731045가 판매 중이 아님 (내일 14:28 KTX — 오늘은 판매 중이어야 정상)
- 서버 안(`127.0.0.1:8080`)에서는 앱이 `X-Forwarded-For`를 믿어서(`deploy/jejari@.service`의 신뢰 프록시) **사람마다 다른 IP**로 보인다 → 가입·로그인 한도 해제가 없어도 된다. Caddy를 거치지 않고 앱으로 바로 간다

### 3-4. 본 시험 (약 12분 — 계정 800개 만들기 약 5분 + 단계 4개 × 90초)

서버 창을 하나 더 열어 vmstat이 켜져 있는지 보고(오전 것이 3시간 동안 기록 중이면 그대로), Grafana에서 2절의 그래프를 띄워 둔다.

```bash
docker run --rm --network host -v "$PWD/loadtest:/lt" -w /lt -e BASE_URL=http://127.0.0.1:8080 grafana/k6:1.1.0 run scenarios/13_capacity.js \
  -e STEPS=300,400,600,800 -e STEP_SEC=90 -e RUN_ID=731045 -e RUN_TAG=b$(date +%H%M) 2>&1 | tee ~/bigdata-k6.txt
```

- 어느 단계든 5xx 20% 또는 p95 5초를 넘으면 20초 지켜본 뒤 **스스로 멈춘다** (안전장치). 손으로 멈추려면 `Ctrl+C`
- 시험 동안 볼 것: A-10 상태 띠·흐름도(어느 노드가 먼저 노래·빨개지나), Grafana 행동 로그 적재량·밀림·CPU
- 끝나면 **밀림이 0이 될 때까지** 기다린다 (보통 몇 초~수십 초). 그 시간도 적는다

### 3-5. 끝난 뒤 MongoDB 건수

```bash
date '+%F %T' | tee ~/bigdata-end.txt
docker compose exec -T mongo bash -c 'mongosh --quiet -u "$MONGO_APP_USER" -p "$MONGO_APP_PASSWORD" --authenticationDatabase jejari jejari --eval "print(\"behavior_log 전체: \" + db.behavior_log.estimatedDocumentCount())"'
```

### 3-6. Grafana에서 숫자 읽기 (시간 범위 = 3-2 시작 ~ 3-5 끝)

Explore(Prometheus)에 그대로 붙여 넣는다. `[20m]`은 시험 길이에 맞게.

```
sum(increase(jejari_behavior_sent_total{job="jejari-app"}[20m]))
sum(increase(jejari_behavior_stored_total{job="jejari-app"}[20m]))
sum(increase(jejari_behavior_dropped_total{job="jejari-app"}[20m]))
sum(increase(jejari_behavior_failed_total{job="jejari-app"}[20m]))
max_over_time(sum(rate(jejari_behavior_stored_total{job="jejari-app"}[1m]))[20m:15s])
max_over_time(max(jejari_kafka_consumer_lag{job="jejari-app",group="behavior-sink"})[20m:15s])
max_over_time(process_cpu_usage{job="jejari-app"}[20m])
```

### 3-7. 정합성 · 되돌리기

```bash
bash loadtest/tools/check_booking.sh all 30
```

- [ ] vmstat 끄기 — **0절·4절 값을 다 옮긴 뒤에** (`~/perf-vmstat-*.txt` 지우기)

## 5. 이 시험이 보여 주는 것 · 못 보여 주는 것 (발표에서 같이 말할 것)

| 보여 주는 것 | 못 보여 주는 것 |
|---|---|
| 동시 800명이 몰리는 동안 행동 로그가 **버림·실패 0**으로 쌓이는지, 밀림이 얼마나 빨리 0이 되는지 | 행동 로그 파이프라인의 **최대 적재 속도** — 사용자 800명이 만드는 로그는 초당 수백 건이라 파이프라인 한계(로컬 실측 초당 2만~3만 건)에 한참 못 미침 |
| 서버(CPU 4개)가 버티는 동시 사용자 수 (네트워크 제한 없이) | 실제 명절 규모(수만 명) · 여러 지역에서 오는 부하 |
| | k6가 서버 CPU를 같이 써서 **실제보다 낮게(보수적으로)** 나옴 |

- 최대 적재 속도는 로컬 실측을 그대로 쓴다: 초당 **2만~2.8만 건**, 장애 뒤 밀린 50만 건 따라잡기 ([행동 로그 적재 용량](행동-로그-적재-용량.md)). 공용 서버에서 같은 "밀린 것 따라잡기"를 하려면 MongoDB를 잠깐 멈춰야 해서(로그인 기록 등도 같이 멈춤) 팀원이 쓰는 서버에서는 하지 않는다
- 발표 문장 예: "공용 서버 한 대에서 동시 ___명이 몰리는 동안 행동 로그 ___건을 버림 0으로 쌓았고, 밀림은 끝나고 ___초 안에 0이 됐습니다. 파이프라인 자체는 초당 2만 건 이상을 받습니다(로컬 실측)."

## 6. 문제가 생기면

| 증상 | 할 일 |
|---|---|
| `사전 점검 실패(계정 … 가입): 429` | 앱이 `X-Forwarded-For`를 안 믿음 → `systemctl cat jejari@8080`에서 신뢰 프록시(`127.0.0.1`) 설정 확인. 급하면 관리자 화면 한도 해제의 IP를 `127.0.0.1`로 |
| 앱 health 실패 1분 이상 · Discord critical 경보 | `Ctrl+C`로 바로 멈추고 원인부터 (재시작 절차는 `deploy/README.md`) |
| 정합성 FAIL | 성능 숫자보다 먼저. 그 항목 이름과 건수를 강동균에게 |
| 밀림이 몇 분 넘게 안 줄어듦 | 기록하고 기다림 (소비자 적재 속도 상한 초당 2,000 — [행동 로그 적재 용량](행동-로그-적재-용량.md)) — 결과에 그대로 씀 |
