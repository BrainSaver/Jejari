# 데이터 유실 점검 — 어디서 흘릴 수 있고, 어떻게 막았나

> 2026-11-20 점검. 실패를 일부러 일으켜(Kafka 정지·MongoDB 정지·DB 제약으로 저장 실패·깨진 메시지) 확인했다.
> 절차 원천: `docs/concurrency.md` §11(outbox)·§12(inbox)·§12.1(격리 보관함)

## 1. 큰 그림 — 흘리지 않는 방법들

| 방식 | 뜻 | 우리 시스템 |
|---|---|---|
| **Outbox** | 업무 변경과 같은 트랜잭션에 이벤트를 쓰고, 나중에 보낸다 | 예약·결제 이벤트 (`outbox_event`) |
| **재시도** | 실패하면 몇 번 다시 | 소비자 5초 무한 재시도 · 알림 3번 · 행동 로그 보내기 3번 |
| **격리 보관함 (DLQ)** | 끝내 처리 못 한 메시지를 따로 보관 → 원인을 고친 뒤 다시 처리 | `<토픽>.DLT` + `tools/dlq.sh` (**이번에 추가**) |
| **Inbox (멱등)** | 같은 메시지가 두 번 와도 한 번만 처리 | `processed_event` · `event_id` 유니크 인덱스 |
| **대사(reconciliation)** | 주기적으로 어긋난 것을 찾아 고친다 | 결제 결과 모름 재조회 · 늦은 승인 환불 · 선점 만료 스캐너 · `check_booking.sh` |
| 로컬 버퍼(spool) | 보내는 쪽이 디스크에 쌓았다 나중에 보냄 | 쓰지 않음 (행동 로그는 메모리 큐 + 재시도로 충분, 아래 실측) |

## 1-1. 왜 DLQ가 없었나

| 이유 | 근거 |
|---|---|
| **설계가 "보내는 쪽"의 유실만 다뤘다** — 예약 이벤트가 Kafka로 꼭 나가게(outbox §11)에 집중하고, "받는 쪽"이 실패했을 때는 정하지 않았다 | concurrency.md §12 소비 그룹 표가 `seat-release`만 적고 나머지는 "알림·로그 등 각자 → 각 기능 문서"로 넘김 |
| **그래서 소비자마다 실패 처리가 제각각** — 같은 실패에 3번 하고 버림 / 무한 재시도 / 로그만 | `notification` FixedBackOff(1초, 3) · `seat-release`·`risk-signal`·적재 FixedBackOff(5초, 무한) · `seat-release`는 처리 실패를 catch해 로그만 |
| **DLQ라는 말이 설계서·명세 어디에도 없다** | 기능설계서·DB설계서·concurrency.md·docs/spec에 0건. 저장소 전체 이력에서 처음 나온 것이 이번 커밋 |
| (추정) "멈추지 않기"를 먼저 생각했다 — 메시지 하나가 뒤를 막지 않게 건너뛰었는데, "건너뛴 것을 어디에 둘까"가 빠졌다 | 소비자 주석이 모두 "컨슈머를 멈추지 않는다"를 이유로 듦 |
| (추정) 장애를 일부러 내는 시험이 없어 버려지는 것이 안 보였다 — 버림은 WARN 로그 한 줄이고 지표가 없었다 | 통합 테스트는 정상 경로·멱등 위주. 이번에 Kafka 정지·DB 제약·깨진 메시지로 처음 드러남 |
| (추정) 돈·좌석의 정답은 Oracle에 있으니 나머지(알림·위험 신호·로그)는 "부가"라고 봤다 | 하지만 알림·취소표 제안이 빠지면 사용자가 바로 겪는다 |

## 1-2. 신뢰성 방식 비교 — 우리 프로젝트에 있는 것·없는 것

| 방식 | 막는 것 | 장점 | 단점·비용 | 우리 프로젝트 | 판단 |
|---|---|---|---|---|---|
| **Outbox** | 업무는 됐는데 이벤트가 안 나감 | DB 트랜잭션과 같이 원자적 | 테이블·릴레이 필요 | ✅ 예약·결제 (§11) | 충분 |
| **Inbox / 멱등 키** | 같은 메시지를 두 번 처리 | 재전달·다시 넣기가 안전해짐 | 보관 기간 관리 | ✅ `processed_event` · `event_id` 유니크 · `Idempotency-Key` | 충분 |
| **즉시 재시도 (blocking)** | 잠깐의 장애 | 간단 | 길어지면 그 파티션 전체가 멈춤 | ✅ 있음 (그룹마다 3번 / 무한으로 제각각) | 무한은 장애엔 맞고 깨진 메시지엔 위험 → DLQ로 보완 |
| **지연 재시도 토픽 (non-blocking)** | 재시도가 뒤 메시지를 막음 | 실패한 것만 따로 몇 분 뒤 다시 | 토픽·소비자 늘어남, 순서가 깨질 수 있음 | ❌ 없음 | 지금은 필요 낮음 (DLQ + 수동 다시 넣기로 충분, 예약 순서 보장이 더 중요) |
| **DLQ (격리 보관)** | 끝내 실패한 메시지가 사라짐 | 원본 보존, 원인 해결 후 재처리 | 보는 도구·운영 절차 필요 | ✅ **이번에 추가** (§12.1, `tools/dlq.sh`) | — |
| **대사 배치 (reconciliation)** | 어긋난 상태가 오래 남음 | 원인과 상관없이 결과를 맞춤 | 주기만큼 늦게 고쳐짐 | ✅ 결제 재조회 · 늦은 승인 환불 · 환불 재시도(CNL-03, 설계상 `refund` 소비 그룹 대신) · 선점 만료 스캐너 | 충분 |
| **정합성 점검 자동 실행** | 대사 배치가 못 잡는 어긋남을 사람이 모름 | 매일 아침 "0건" 확인 | 쿼리 비용 (가벼움) | ⚠️ `check_booking.sh`는 **손으로만** 돌림 | **추천**: 서버 타이머로 매시간, FAIL이면 경보 |
| **유실·밀림 경보** | 화면을 안 보면 모름 | 바로 알림 (Discord) | 경보 피로 | ⚠️ A-10에 **보이기만** 함. Grafana 경보는 배포·앱 응답·KTX 시간표만 | **추천**: 격리 보관·outbox 밀림·소비 밀림을 Discord 경보에 |
| **보내는 쪽 로컬 버퍼 (spool)** | 브로커가 오래 죽으면 메모리 큐가 넘침 | 디스크라 큼 | 파일 관리·재시작 시 복구 | ❌ 없음 (행동 로그는 메모리 큐 5만 + 재시도 3번) | 필요 낮음 (Kafka 40초 정지에 0건, 몇 분 넘으면 버림이 지표로 보임) |
| **Kafka 복제 (replication ≥ 3)** | 브로커·디스크 고장 시 Kafka 안의 메시지 유실 | 무중단 | 브로커 3대 | ❌ 1대 (replication 1) | 학교 서버 1대라 현실적으로 불가. 예약 이벤트의 원본은 Oracle outbox |
| **백업** | 서버 디스크 고장 | 통째로 되돌림 | 하루 단위면 그날 데이터는 잃음 | ✅ GCP 디스크 스냅샷 매일 03시·7일 (deploy/README.md) | 하루 단위로 충분. 시연 전 수동 스냅샷 |
| **서킷 브레이커** | 외부(PG)가 느릴 때 스레드가 다 묶임 | 빨리 실패 | 설정·튜닝 | ❌ 없음 | 지금은 모의 PG라 필요 낮음 (실 PG를 붙이면 필요) |
| **메시지 스키마 버전** | 형식이 바뀌면 소비자가 못 읽음 | 옛·새 형식 공존 | 버전 관리 | ❌ 없음 (JSON 봉투) | DLQ가 깨진 메시지를 보관하므로 형식 실수는 되살릴 수 있게 됨 |
| **Kafka 트랜잭션 (exactly-once)** | 중복·유실 없이 정확히 한 번 | 이론상 가장 강함 | 복잡·느림, DB까지는 못 묶음 | ❌ 안 씀 | outbox + inbox가 같은 효과 (실무에서 더 흔한 조합) |



| 데이터 경로 | 인프라 장애 (Kafka·DB 정지) | 깨진 메시지·끝내 실패 | 보이나 |
|---|---|---|---|
| 예약·결제 → outbox → Kafka | outbox에 쌓였다 복구 후 발행 (실측: Kafka 40초 정지 → 600건 쌓임 → 20초 안에 0, 유실 0) | 재시도 소진 → 그 샤드만 순서대로 멈춤 (관리자가 고침) | A-10 |
| → `seat-release` (좌석 정리·취소표 제안) | 5초 무한 재시도 | **고치기 전: 로그만 남기고 버림** → 격리 보관 | A-10 |
| → `notification` (알림) | 3번 재시도 | **고치기 전: 3번 실패하면 버림** → 격리 보관 | A-10 |
| → `risk-signal` (위험 점수 재계산 표시) | 5초 무한 재시도 | **고치기 전: 버림** → 격리 보관 | A-10 |
| 행동 로그 보내기 (앱 → Kafka) | **고치기 전: 실패하면 버림 (Kafka 40초 정지에 약 0.4%)** → 큐 뒤에 다시 넣어 3번 재시도 → 같은 시험에서 **0건** | 큐가 가득 차면 버림 (5만 건, 세어서 보임) | A-10 |
| 행동 로그 적재 (Kafka → MongoDB) | 5초 무한 재시도 (실측: MongoDB 60초 정지 → 밀림 896건 → 복구 후 따라잡음) | **고치기 전: 버림** → 격리 보관 | A-10 |
| 녹화(replay) 보내기·적재 | 적재는 무한 재시도 | 적재의 깨진 메시지 → 격리 보관 | 로그 |
| 결제 결과 모름 (PG 시간 초과) | `next_check_at` 재조회 (PaymentRecheckScanner) | 늦은 승인은 자동 환불 (LateApprovalRefund) | `check_booking.sh` |
| 결제 안 한 선점 | 만료 스캐너가 풀어 줌 | — | `check_booking.sh` 5 |

## 3. 이번에 고친 것

1. **격리 보관함 (DLQ)** — `event/dlq/DeadLetters`. 위 표의 "버림" 다섯 곳이 이제 원본 그대로 `<토픽>.DLT`에 옮겨진다 (이유·출처·오류 헤더, 30일 보관). 앱이 뜰 때 토픽을 만든다
2. **다시 넣기 도구** — `tools/dlq.sh list | show | replay`. 다시 넣으면 **그 소비 그룹만** 처리하고 다른 그룹은 건너뛴다. 두 번 넣어도 결과가 같다 (실측: 알림 3건 → 두 번 다시 넣어도 3건)
3. **행동 로그 보내기 재시도** — 실패하면 큐 뒤에 다시 넣어 최대 3번. 큐가 80% 넘게 차면 새 로그를 위해 포기 (지표 `jejari_behavior_retried_total`)
4. **A-10** — 데이터 놓침·밀림에 "격리 보관 (최근 1시간)" 칸, 최근 5분에 1건이라도 있으면 주의
5. `seat-release`의 잘못된 주석 ("실패하면 재시작 때 다시 온다") — 묶음 소비(AckMode.BATCH)라 묶음이 끝나면 오프셋이 커밋되어 다시 오지 않았다. 고침

## 5. 운영에서 할 일

- A-10 "격리 보관"이 0이 아니면: `tools/dlq.sh list` → 이유를 보고 원인을 고친 뒤 → `tools/dlq.sh replay <토픽> <그룹>` → `loadtest/tools/check_booking.sh <운행>`으로 확인
- 형식 오류(`malformed`)는 코드를 고친 뒤 `replay … malformed`로 따로. 고치기 전에 넣으면 또 보관함으로 온다
