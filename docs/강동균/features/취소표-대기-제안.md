# 취소표 대기·제안 (WL-01·02·03)

> 담당: 강동균 · 코드: `src/main/java/com/jejari/waitlist/`
> 관련: 기능설계서 4.7, concurrency.md §9 · §14.3 · 담당 표에는 D·C로 적혀 있음 (아래 "왜 내가 만들었나")

## 왜 내가 만들었나

기능설계서의 담당은 D·C지만 **아무 브랜치에도 코드가 없었고**, §9가 기대는 소비 그룹
`seat-release`가 비어 있었습니다. 그 소비자는 취소표 제안만 하는 게 아니라 **제 좌석 모듈의
Redis 보상 보장 경로(§14.3)** 이기도 합니다 — 해제한 쪽이 커밋 직후 하는 "빠른 경로"가 앱이
죽어 유실될 때 다시 돌려 주는 자리입니다. 그래서 제가 입구를 만들었습니다.

**남은 것은 담당 그대로입니다**: WL-04 알림 발송(채널)은 C, WL-05 수락(= PAY-01)은 이미 C가
만들어 둔 결제입니다. 여기서는 `notification` 행만 같은 트랜잭션에 남깁니다.

## 한 줄 요약

| 기능 | 하는 일 |
|---|---|
| **WL-01** `POST /api/v1/waitlists` | 매진된 등급을 기다리겠다고 신청. 순서는 신청 시각이 아니라 **위험 패널티를 더한 시각** |
| **WL-02** `GET`·`DELETE /api/v1/waitlists` | 내 대기 목록(순번 포함)·대기 취소 |
| **WL-03** `seat-release` 소비자 | 좌석이 풀리면 **대기 순서대로 시스템이 대신 선점**하고 알림 행을 남김 |

## 핵심 — 순서를 신청 시각으로 하면 안 된다

대기열(QUE-01)에서 위험 점수로 뒤로 밀린 사용자가 취소표에서 정상 사용자와 같은 순서로
가져가면 **위험 점수 후순위가 통째로 우회됩니다.** 취소표는 대기열 입장 토큰 없이 신청하기 때문에
더 그렇습니다.

```
priority_at = 신청 시각 + (위험 점수 × waitlist.penalty_ms_per_point)
```

- 점수 계산은 대기열과 **같은 규칙**이라 김성원 씨의 `RiskPenaltyService`를 그대로 씁니다
- **1점당 미루는 시간만 다릅니다.** 대기열은 `risk.penalty_ms_per_point`(1점 = 1초)인데,
  대기열은 몇 분 안에 줄이 빠지지만 취소표는 몇 시간~며칠이라 같은 단위면 80점이 80초라
  순서가 사실상 안 바뀝니다. `waitlist.penalty_ms_per_point` = **180000 (1점 = 3분, 80점 = 4시간)**
- **신청할 때 한 번** 계산해 저장하고, 그 뒤 점수가 바뀌어도 다시 계산하지 않습니다 (§9.3-3)
- 패널티 때문에 신청을 막지는 않습니다. 앞에 대기자가 없으면 패널티가 있어도 바로 제안받습니다

**`RESTRICTED`는 신청 자체를 막습니다** (§9.3-0). 최대 패널티(100점 = 5시간)로 미뤄도 결국
가져가기 때문입니다. `BANNED`는 로그인에서 막혀 여기까지 오지 않습니다.

## WL-03 제안 — 이벤트 하나 = 트랜잭션 하나

```
RESERVATION_CANCELED · RESERVATION_EXPIRED (Kafka)
        │
        ├─ 1. Redis 보상 (트랜잭션 밖, 멱등)          ← §14.3 보장 경로
        │     좌석 키 → REOFFER:R  ·  한도 감소
        │     (이래야 일반 사용자의 hold.lua가 막힌다)
        │
        └─ 2~8. 트랜잭션 T 하나
              processed_event 도장 (§12 중복 소비 차단)
              대기자 조회  FOR UPDATE SKIP LOCKED  ORDER BY priority_at, waitlist_id
              대기자마다:
                 구간·등급·매수 안 맞으면 → 다음 사람 (상태 그대로)
                 매수 한도에 걸리면      → SKIPPED + 알림, 다음 사람
                 맞으면 → 그 사람 명의로 §2 선점 (REOFFER 인계)
                          waitlist OFFERED + notification INSERT
              COMMIT
```

### 왜 Redis 보상이 트랜잭션보다 먼저인가

좌석 키를 `REOFFER:R`로 바꾸는 것이 **일반 사용자를 막는 장치**입니다. 트랜잭션 안에서 하면
커밋될 때까지 좌석이 열려 있어 일반 사용자가 먼저 채 갑니다. 그래서 T 밖에서 먼저 하고,
`reoffer.lua`가 두 번 돌려도 같도록 만들어져 있어 안전합니다.

### `SKIP LOCKED`를 쓰는 이유

앱이 여러 대면 같은 운행의 빈 좌석 이벤트를 여러 대가 동시에 받습니다. 다른 인스턴스가 잡은
대기자 행은 건너뛰어야 **한 대기자에게 한 번만** 제안됩니다 (§9.1-4).

### 제안 예약이 일반 예약과 다른 점

| | 일반 (§2) | 취소표 제안 (§9.1-6) |
|---|---|---|
| 입장 토큰 | 필요 | 보지 않음 |
| `source` | `NORMAL` | `WAITLIST` |
| `idempotency_key` | 요청이 준 값 | `wl:{waitlistId}` |
| 이력 `actor_type` | `USER` | `SYSTEM` |
| `hold.lua` 인계 값 | `''` | `REOFFER:{이전예약}` |
| 1회 매수 한도 | 선점 때 검사 | **신청 때 이미 봤으므로 다시 안 봄** |
| 매수 카운터 | 증가 | **증가** (제안도 샀다고 센다) |

`SeatHoldService.offerInCurrentTx(...)`로 열어 뒀습니다. `SeatPaymentService`·`SeatReleaseService`의
`*InCurrentTx`와 같은 방식이라 **호출한 쪽 트랜잭션에서** 돕니다.

## 겪은 것

### `ci_hash`는 아무 문자열이나 되지 않는다

테스트 회원의 `ci_hash`를 `wl-ci-{id}`로 만들었더니 신청이 전부 `IllegalStateException`으로
떨어졌습니다. `OracleMemberIdentityPort`가 `^[0-9a-f]{64}$`를 검사합니다 — 해시가 오염되면
위험 점수가 틀리므로 막는 것이고, 맞는 동작입니다. 제 좌석 모듈은 `ci_hash`를 DB에서 그대로
읽어 쓰기 때문에 이 제약을 모르고 있었습니다. 테스트를 `%064x`로 고쳤습니다.

### 알림 ID 시퀀스가 없었다

`notification`에 ID 시퀀스가 없어서 제안과 같은 트랜잭션에 알림을 넣을 수 없었습니다.
ERD **v20**으로 `notification_seq`를 추가했습니다.

### 매진을 만들 수 없어 테스트를 나눴다

운행 9001은 1,050석이라 통합 테스트에서 매진을 만들 수 없습니다. 그래서 신청은 정책 검사
순서로 확인하고(매진 검사 앞의 RESTRICTED·매수 한도·구간), 제안 흐름은 대기 행을 직접 넣어
확인합니다.

## 아직 안 한 것 · 다른 파트와의 연결

| 상대 | 내용 |
|---|---|
| C 길동현 | **WL-04 알림 발송.** 저는 `notification` 행만 남깁니다 (`WAITLIST_OFFER` / `WAITLIST_SKIPPED`, 채널 PUSH). 보내는 것은 `notification` 소비 그룹이 할 일입니다 |
| C 길동현 | **WL-05 수락 = 결제.** 제안 예약을 PAY-01로 결제하면 수락입니다. §4-5대로 **결제 시작 때 `waitlist.offer_deadline_at`도 같이 연장**해야 합니다 — 지금은 연장되지 않습니다 |
| C 길동현 | 기한이 지나면 §6→§7이 예약을 만료시키는데, 그때 **`waitlist`를 `EXPIRED`로 바꾸는 것**이 아직 없습니다 (§9.2). 제 `SeatReleaseTx`가 할지 결제 쪽이 할지 정해야 합니다 |
| D 강다인 | **행동 로그.** `BehaviorType`에 취소표 값이 없어 로그를 남기지 않았습니다. `WAITLIST_APPLY`·`WAITLIST_CANCEL`이 필요하면 알려 주세요 (컨트롤러에 두 줄) |
| D 강다인 | WL-01·02는 원래 D 담당입니다. 화면(U-10)과 응답 모양이 맞는지 봐 주세요 |
| A 김성원 | `RiskPenaltyService`를 그대로 가져다 씁니다 (점수 규칙은 대기열과 동일, 1점당 시간만 다름) |
