# 발표 5분 스크립트 — 강동균 (초안)

> 작성: 2026-11-26 · 화면: [산출물](산출물.html) (절 이름을 괄호로 적음) · 발표 2026-12-05
> 읽는 속도 기준 1분에 약 250~300자. 굵은 글씨가 꼭 말할 숫자. **직접 소리 내 읽어 보고 내 말투로 고칠 것**

## 0:00 ~ 0:30 — 맡은 것 (진행 현황)

> "저는 **좌석 선점 동시성**, 열차 도메인, 그리고 ERD를 맡았습니다. 명절 예매에서 가장 무서운 건 느린 것보다
> **같은 좌석이 두 번 팔리는 것**이라, '틀리지 않게' 만든 다음 '빠르게', 마지막으로 '봇을 막게' 순서로 일했습니다."

- 화면: 진행 현황 표만 잠깐. 숫자는 뒤에서

## 0:30 ~ 1:20 — 같은 좌석에 100명 (RSV-02)

> "같은 좌석에 **100명이 동시에** 누르면 **딱 1명만** 통과하고, 나머지 99명은 **DB에 가기 전에** Redis에서 돌려보냅니다.
> 최종 판정은 DB의 기본키라서, Redis가 틀리거나 죽어도 **두 번 팔리지는 않습니다.**
> 이걸 실제 Oracle·Redis로 돌리는 통합 테스트로 확인했고, 시나리오 47개를 테스트와 하나하나 맞춰 뒀습니다."

- 화면: T1 애니메이션(점 100개 → 1개)
- 숫자: **1 / 100**, 중복 예약 **0건**

## 1:20 ~ 2:00 — 왜 이 방식인가 (§17.1 락 비교)

> "락 방식 세 가지를 같은 조건에서 10번씩 쟀습니다. 처리량은 B와 C가 **통계적으로 차이가 없었습니다.**
> 그래서 'C가 더 빠르다'는 말은 하지 않습니다. C를 고른 이유는 **DB 왕복이 108번에서 1번**으로 줄기 때문입니다.
> 명절에 DB가 먼저 무너지니까, DB를 덜 부르는 쪽을 골랐습니다."

- 화면: 처리량 막대(범위 선) + DB 왕복 막대
- 숫자: DB 왕복 **108 → 1**, TPS 차이 없음(p 0.57)
- 한 줄 덧붙이기(시간 되면): "처음 잰 숫자는 측정 도구 문제로 뒤집혔고, CPU를 나눠 다시 재서 지금 숫자가 됐습니다"

## 2:00 ~ 3:00 — localhost가 아니라 공용 서버에서 (공용 서버 측정)

> "외부 평가에서 '숫자가 다 localhost 한 대'라는 지적을 받아서, **실제 공용 서버**(CPU 4개짜리 VM 한 대에 앱·DB·Kafka 전부)에서 다시 쟀습니다.
> 개선 전과 같은 조건(200명이 20초에 몰림)에서 좌석 선점은 **0.55초에서 0.32초**, 결제는 **0.47초에서 0.27초**로 빨라졌습니다.
> 동시 사용자는 **600명, 초당 554건을 오류 0으로** 처리했고, 800명이 몰려도 **느려질 뿐 서버 오류는 0**이었습니다.
> 그동안 쌓인 행동 로그 **6만 5천 건 중 버려진 건 0건**, 밀린 것은 끝나고 **5초 안에** 다 처리됐습니다."

- 화면: 공용 서버 측정 절의 지표 4개 → 동시 사용자 표
- **먼저 말할 한계**: "제 PC 네트워크가 400명에서 막혀서, 그 위는 서버 안에서 쟀습니다. 그래서 실제 한계는 이보다 위입니다."

## 3:00 ~ 4:10 — 봇을 어떻게 막았나 (봇 대회·모델)

> "규칙을 만든 사람이 만든 봇으로만 시험하면 탐지율이 아니라 **제 생각**을 재게 됩니다.
> 그래서 규칙을 모르는 팀원이 봇을 만들고, 진짜 사람이 같이 사는 **봇 대회**를 두 번 열었습니다.
> 1차에는 규칙이 블라인드 봇을 **0/12**로 하나도 못 잡았고, 보강한 뒤 2차에는 **6/6**을 잡으면서 진짜 사람 27계정은 **한 명도 막지 않았습니다.**
> 규칙이 못 잡는 봇을 위해 모델도 붙였습니다. 모델 하나로는 '총무'나 '가족 구매' 같은 정상 사용자를 서로 맞바꾸며 틀려서,
> **주 판정 뒤에 그룹별로 '이건 평범한 사람'이라고 변호하는 작은 모델**을 두었습니다. 같은 시험 2만 명에서 사람 오탐 **6.3%에서 3.8%**, 봇 탐지 **92.6%에서 98.4%**입니다.
> 다만 모델이 틀리면 진짜 사람이 표를 못 사니까, 모델 점수는 **관리자에게 보여 주는 의견**으로만 씁니다."

- 화면: 봇 대회 지표(0/12 → 6/6, 0/27) → 모델 r10 표
- 정직하게: "0/27은 '오탐 0%'가 아니라 '12.5%보다 낮을 가능성이 높다'입니다. 가족 몫 대량 구매는 기록상 봇과 같아 관리자 검토로 보냅니다."

## 4:10 ~ 4:50 — 장애가 나도 틀리지 않게 (유실·정합성)

> "부하가 걸린 상태에서 Redis를 **강제로 죽여 봤습니다.** 대기열·선점은 **2초 안에 '잠시 후 다시'**로 거절되고, 열차 조회는 계속 됩니다.
> 다시 살리면 약 20초 뒤 정상으로 돌아오고, 돈만 빠진 결제나 어긋난 좌석은 **0건**입니다. 장애가 결제 기한보다 길면 그만큼 기한을 되돌려 줍니다.
> 이 시연을 하다가 '조회도 같이 멈춘다'는 문제를 찾아서 고쳤습니다 — 문서에는 '정상'이라고 적혀 있었는데, 실제로 죽여 보니 달랐습니다."

- 화면: Redis 장애 표 (+ 캡처: A-10 상태 띠 빨강 → 초록)
- 숫자: 운행 조회 503 **917 → 0건**, 정합성 **10/10**

## 4:50 ~ 5:00 — 마무리

> "정리하면, **두 번 팔리지 않게** 만들고, 그걸 **실제 서버 숫자와 장애 시연으로** 확인했고, 봇은 **모르는 사람이 만든 봇과 진짜 사람**으로 쟀습니다. 감사합니다."

## 예상 질문 (짧게 답할 것)

| 질문 | 답 |
|---|---|
| 앱을 2대로 늘리면 더 버티나? | 지금 서버는 CPU 4개에 DB까지 같이 있어서 2대가 오히려 느렸습니다(11-19). "앱은 늘리고 DB는 버틴다"는 서버를 나눠야 보여 줄 수 있고, 이번에는 못 했습니다 |
| 수만 명이면? | 이번 숫자는 VM 한 대 기준입니다. 한계가 CPU였고, 대기열이 오픈 순간 진입을 받아 주는 구조라 서버를 늘리면 비례해 늘어날 것으로 보지만 재 보지는 않았습니다 |
| Redis가 단일 장애점 아닌가? | 가용성은 맞습니다. 그래서 죽으면 멈춥니다. 하지만 정합성은 DB에 걸어서 틀리지는 않습니다. 복제·Sentinel은 다음 단계입니다 |
| 모델을 왜 차단에 안 쓰나? | 실제 사람 표본이 33계정뿐이라 오탐 구간이 넓습니다. 틀리면 사람이 표를 못 사니 관리자 의견으로만 씁니다 |
| 봇이 사람처럼 천천히 오면? | 바닥은 본인인증 기준 매수 제한입니다. 아무리 사람 같아도 명의 수 × 4석이 끝입니다 |
