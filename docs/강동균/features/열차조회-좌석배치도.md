# TRN-01~03 열차 조회 · RSV-01 좌석 배치도

작성자: 강동균 · 코드 `com.jejari.train`(`TrainQueryService`, `TrainController`), `com.jejari.seat`(`SeatMapService`, `SeatMapController`)

## 한 줄 요약

로그인 없이 역·운행·운임을 검색하고, 대기열을 통과한 회원은 호차별 좌석 배치와 상태(빈 좌석·선점·판매)를 본다. 상태는 1초짜리 Redis 캐시에서 읽어 DB를 거의 건드리지 않는다.

## API

| 기능 | 경로 | 인증 | 행동 로그 |
|---|---|---|---|
| TRN-01 역 목록 | `GET /api/v1/stations` | 없음 | - |
| TRN-02 운행 검색 | `GET /api/v1/runs?from=&to=&date=2026-11-19` | 없음 | `VIEW_TRAIN` (fromStationId, toStationId, travelDate, resultCount) |
| TRN-03 운행 상세·운임 | `GET /api/v1/runs/{runId}?from=&to=` | 없음 | - |
| RSV-01 좌석 배치도 | `GET /api/v1/runs/{runId}/seats?from=&to=&grade=` | 로그인 + 입장 토큰 | `VIEW_SEAT` (grade, availableCount) |

검색 결과: 열차 번호, 출발·도착 시각, 소요 분, 판매 상태·예매 가능 여부, 등급별 운임, 등급별 남은 좌석 수(판매 중일 때만).

## 어떻게 동작하나

```
배치도·남은 좌석 → seatmap:{runId} 해시가 있으면 그대로
                    없으면: 좌석 키 seat:hold:* 를 MGET + DB의 SOLD 행 → 상태 계산 → 해시에 1초 저장
상태: 키 값 R 또는 REOFFER:R → HELD,  SOLD:R 또는 DB SOLD → SOLD,  키 없음 → EMPTY
```

- 열차 편성·좌석 목록은 바뀌지 않는 기준 데이터라 열차별로 앱 메모리에 한 번만 읽는다.
- 내가 선점·취소하면 그 운행 캐시를 지워 내 화면엔 바로 반영된다. 남의 화면은 1초 안에 따라온다.

## 왜 이렇게 했나

- **DB의 HOLD 행이 아니라 Redis 좌석 키를 본다**: 좌석 경쟁에서 진 요청은 DB에 쓰지 않으므로 실시간 상태의 원천은 Redis 키다. 판매(SOLD)만 DB와 함께 본다(키가 없어져도 판매는 남게).
- **짧은 캐시(1초, app_policy `seatmap.cache_ms`)**: 예매 오픈 때 배치도 새로고침이 가장 많다. 매번 좌석 525개를 MGET하면 Redis가 바빠진다. 1초 늦게 보여도 **최종 판정은 선점 때**라 같은 좌석이 두 번 팔리지 않는다.
- **취소된 좌석(REOFFER)은 선점된 것으로 보여 줌**: 대기자에게 먼저 가는 좌석이라 일반 사용자는 잡을 수 없다.
- **검색은 비회원 허용**: 기능설계서 2장. SecurityConfig에서 GET `/stations`, `/runs`, `/runs/{runId}`만 열었다. 배치도는 그대로 로그인 + 입장 토큰.

## 주의할 점

- 캐시가 만료되는 순간 요청이 몰리면 여러 요청이 동시에 다시 만든다(같은 값이라 결과는 맞음). 부하 테스트에서 문제가 되면 한 대만 만들게 바꾼다.
- 개발용 대용품 `DevSeatsController`를 지웠다 (김성원 요청 3번). 개발 모드 부하 테스트(k6/queue)의 배치도 호출도 이제 실제 API를 탄다 — Oracle이 떠 있어야 한다.
