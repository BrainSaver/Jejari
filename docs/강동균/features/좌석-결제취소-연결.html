요약 흐름 재생 사용법 반환값·Redis 주의할 점 검증

한 줄 요약

결제(PAY-01·02)와 확정 취소(CNL-02)는 자기 트랜잭션 안에서 메서드 한 줄만 부르면 됩니다. 그러면 좌석 재고와 매수 카운터가 같은 트랜잭션에서 바뀌고, 커밋된 뒤에 Redis 좌석 키가 맞춰집니다.

메서드 한눈에

메서드부르는 때DB에서 하는 일 (같은 트랜잭션)커밋 뒤 Redis돌려주는 값
extendHoldInCurrentTxreservation을 PAYMENT_PENDING으로 바꾸고 새 마감 d를 읽은 뒤seat_inventory.hold_expires_at = d (HOLD 행 K개)extend.lua 값이 R인 키만 d까지 연장true / false
confirmSeatsInCurrentTxreservation 행을 FOR UPDATE로 잠근 뒤, payment·reservation 갱신 전HOLD → SOLD, hold_expires_at = NULL (K개)sold.lua 키를 SOLD:R로 덮어씀, 만료 = 운행 출발true / false
returnSoldSeatsInCurrentTxreservation을 CONFIRMED → CANCELED로 바꾼 뒤(1행)SOLD 행 삭제, purchase_counter 감소reoffer.lua → REOFFER:R 60초, limit_decr.lua 한도 감소ReturnedSeats / null
releaseInCurrentTx (기존)결제 실패 §5.2: payment FAILED 기록과 같은 트랜잭션PAYMENT_PENDING → EXPIRED, HOLD 행 삭제, 카운터 감소, saga·이력·outboxREOFFER:R, 한도 감소true / false

K = 예약의 좌석 구간 행 수 = seat_count × 구간 수. 지금은 구간 재고 OFF라 K = 매수입니다 (§2.4).

원칙 하나: 예약 행 락을 먼저 잡은 뒤에 부른다 (§0.4-1). reservation UPDATE나 SELECT … FOR UPDATE가 앞에 있으면 같은 예약을 다루는 트랜잭션이 줄을 서서, 좌석·카운터가 엇갈리지 않습니다.

흐름 재생

예약 R=1201(좌석 5A·5B, 2매)의 값이 단계마다 어떻게 바뀌는지 보여 줍니다. 단계를 누르면 그 단계로 이동합니다. 좌석을 잃은 경우를 켜면 롤백 흐름을 볼 수 있습니다.

    사용법

    길동현 · §4 결제 시작 (PAY-01)

    @Transactional
public void startPayment(long memberId, long r, String idemKey) {
    LocalDateTime cand = LocalDateTime.now(clock).plusSeconds(pgTimeoutSec + graceSec);   // 앱 시계 (§0.7)
    int n = jdbc.update("""
        UPDATE reservation SET status = 'PAYMENT_PENDING',
               pay_deadline_at = GREATEST(pay_deadline_at, ?), updated_at = SYSTIMESTAMP, version = version + 1
         WHERE reservation_id = ? AND member_id = ? AND status = 'HOLD' AND pay_deadline_at > SYSTIMESTAMP""",
        cand, r, memberId);
    if (n != 1) throw new BusinessException(...);                    // 이미 결제 중·만료·남의 예약
    LocalDateTime d = jdbc.queryForObject(
        "SELECT pay_deadline_at FROM reservation WHERE reservation_id = ?", LocalDateTime.class, r);

    if (!seatPay.extendHoldInCurrentTx(r, d)) {                      // ← 좌석 단계
        throw new BusinessException(...);                            // 좌석을 잃음 → 예외로 롤백
    }
    // saga PAYING · waitlist 제안 기한 · payment REQUESTED(next_check_at = d) · 이력 · outbox PAYMENT_STARTED
}   // 커밋되면 Redis 좌석 키도 d까지 연장 (자동)

    길동현 · §5.1 결제 승인 (PAY-02)

    @Transactional
public Result approve(long r, long paymentId, String pgTxId) {
    jdbc.queryForObject("SELECT status FROM reservation WHERE reservation_id = ? FOR UPDATE", String.class, r);
    // payment 상태 갈래(REQUESTED / APPROVED / FAILED …)는 §5.1-3 표대로

    if (!seatPay.confirmSeatsInCurrentTx(r)) {                       // ← 좌석 단계
        throw new SeatLostException(r);                              // 롤백 → 바깥에서 "확정 실패" 경로 (§5.1)
    }
    // payment APPROVED · reservation CONFIRMED · saga CONFIRMED/DONE · 이력 · outbox RESERVATION_CONFIRMED
}   // 커밋되면 Redis 좌석 키 = SOLD:R, 만료 = 운행 출발 (자동)

// 확정 실패: 별도 트랜잭션에서 reservation 잠금 → payment REQUESTED → APPROVED → 늦은 승인 환불(§7.3).
// 예약이 아직 PAYMENT_PENDING이면 같은 트랜잭션에서 release.releaseInCurrentTx(r, ReleaseReason.PAY_FAILED)

    강다인 · §8 확정 예약 취소 (CNL-02)

    @Transactional
public CancelResult cancelConfirmed(long memberId, long r) {
    int n = jdbc.update("""
        UPDATE reservation SET status = 'CANCELED', canceled_at = SYSTIMESTAMP, updated_at = SYSTIMESTAMP,
               version = version + 1
         WHERE reservation_id = ? AND member_id = ? AND status = 'CONFIRMED'""", r, memberId);
    if (n != 1) { /* 이미 취소됨이면 같은 결과, 아니면 404·409 */ }

    ReturnedSeats seats = release.returnSoldSeatsInCurrentTx(r);     // ← 좌석 단계 (SOLD 행 삭제 + 카운터 감소)

    long fee = feePolicy.feeFor(...);                                 // cancel_fee_policy
    // cancellation INSERT (refund_status = 'REQUESTED', resold_yn = 'N') · 이력
    Map<String, Object> payload = new LinkedHashMap<>(seats.eventPayload());
    payload.put("reason", ...);  payload.put("cancelFee", fee);  payload.put("refundAmount", paid - fee);
    outbox.recordReservation(r, EventType.RESERVATION_CANCELED, payload);
}   // 커밋되면 좌석 키 = REOFFER:R (60초 대기자 먼저), 한도 감소 (자동)

    반환값과 예외

    결과뜻부르는 쪽이 할 일
    trueK개 행을 모두 바꿨습니다. 커밋 뒤 Redis 작업이 예약됐습니다나머지 단계를 이어서 하고 커밋
    false바뀐 행 수가 K와 다릅니다. 그 사이 좌석을 잃었거나 예약이 이미 풀렸습니다. Redis 작업은 걸지 않습니다반드시 롤백. §4는 결제 시작 거절, §5.1은 "확정 실패" 경로
    ReturnedSeatsSOLD 행을 지우고 카운터를 줄였습니다cancellation·이력·outbox를 이어서 하고 커밋
    null지울 SOLD 행이 없습니다 (이미 돌려줌). 카운터는 그대로입니다이미 처리된 취소로 보고 같은 결과를 돌려줌

    왜 이렇게 했나

    결정이유다른 선택지
    호출하는 쪽 트랜잭션 안에서 실행결제 기록과 좌석 확정이 같이 커밋되거나 같이 롤백돼야 "돈은 냈는데 좌석은 HOLD" 같은 반쪽 상태가 없습니다좌석 쪽이 따로 커밋 → 둘 중 하나만 성공하는 틈이 생김
    Redis는 afterCommit에서만롤백됐는데 Redis만 SOLD가 되면 그 좌석은 출발까지 아무도 못 삽니다트랜잭션 안에서 Redis 갱신 → 롤백 때 되돌릴 방법이 없음
    예외 대신 boolean좌석을 잃었을 때 결제 쪽 대응이 경우마다 다릅니다 (§4 거절 / §5.1 늦은 승인 환불)좌석 쪽 예외 → 결제 쪽이 잡아서 다시 분기해야 함
    확정 취소는 좌석 부분만수수료·환불·cancellation은 CNL 규칙입니다. 좌석·카운터·Redis는 해제(§7)와 같은 코드라 한 번만 줄고, 이벤트 모양도 같습니다취소 전체를 좌석 쪽이 맡음 → 수수료 규칙이 두 파트에 흩어짐

    검증

    SeatPaymentInfraTest 11개를 실제 Oracle·Redis로 돌렸습니다. 결제·취소 쪽 트랜잭션은 테스트가 SQL 몇 줄로 흉내 냅니다.

    구분확인결과
    결제 시작좌석 마감과 Redis TTL이 새 마감(10분 → 20분)으로 바뀜통과
    좌석 하나를 잃으면 false, 롤백하면 예약 HOLD·TTL 그대로통과
    TTL로 사라진 Redis 키는 되살리지 않음통과
    승인K행 SOLD, hold_expires_at NULL, Redis SOLD:R 출발까지, 다른 사람 선점은 SEAT_ALREADY_TAKEN통과
    Redis 키가 사라졌어도 SOLD:R로 다시 씀통과
    좌석을 잃으면 false, 롤백하면 좌석·Redis 그대로통과
    확정 취소SOLD 행 0, 카운터·Redis 한도 0, 좌석 키 REOFFER:R(60초), 일반 사용자 선점 거절 (T30 앞부분)통과
    두 번 불러도 카운터는 한 번만 감소통과
    예약이 CANCELED가 아니면 거부통과
    롤백하면 좌석·카운터·Redis 그대로통과
    공통트랜잭션 밖 호출은 세 메서드 모두 거부통과
