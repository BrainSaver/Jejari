# 구글 클라우드 배포 — 방법 정리

> 조사·정리: 강동균 · 2026-11-17
>
> **배포 담당은 조영준 씨(E, 인프라)입니다.** 개발일지에 "VM 사양·방화벽·비밀값 전달 방법 정리"를
> 다음 할 일로 적어 두신 걸 보고, 제가 먼저 조사해 둔 것을 넘깁니다. 고치거나 버리셔도 됩니다.
> 쓰시게 되면 `docs/조영준/` 또는 팀 문서로 옮기는 게 맞습니다.
>
> 관련: `개발일지/2026-11-16-용량-산정.md`(RAM·디스크 실측), 기획서 "웹으로 배포한다"

## 한 줄 결론

**VM 1대에 지금 `compose.yaml`을 그대로 올린다.** 관리형 서비스로 쪼개지 않는다.

이유 세 가지:

1. **GCP에는 관리형 Oracle이 없다.** Cloud SQL은 MySQL·PostgreSQL·SQL Server뿐이다.
   Oracle은 어차피 컨테이너로 우리가 띄워야 한다 — 그러면 나머지만 관리형으로 쪼갤 이유가 없다.
2. **무료 등급으로는 안 된다.** Always Free e2-micro는 **RAM 1GB**인데
   **Oracle 컨테이너 하나가 2.59GB**다 (실측). 전체는 놀 때 6.5GB, 부하 때 10GB로 본다. 그래서 어느 쪽을 고르든 **$300 체험 크레딧(90일)** 을 쓰게 된다.
3. **3주짜리 프로젝트다.** 관리형으로 쪼개면 Redis만 월 $36, Kafka는 CPU 시간당 과금이라
   크레딧이 금방 빠진다. 쪼개서 얻는 가용성은 우리가 쓸 일이 없다.

## 1. 무엇을 올려야 하나

`compose.yaml`에 서비스가 8개 있다. 그중 `kafka-init`은 토픽만 만들고 끝나므로
**7개가 계속 떠 있고**, 거기에 앱이 붙는다.

| 서비스 | 이미지 | RAM (`docker stats` 실측, 2026-11-17) |
|---|---|---|
| Oracle | `gvenzl/oracle-free:23-slim-faststart` | **2.59GB** |
| Kafka | `apache/kafka:4.1.0` | **1.10GB** |
| MongoDB | `mongo:8.0` | 311MB (데이터가 쌓이면 캐시가 늡니다) |
| Grafana | `grafana/grafana:11.6.0` | 182MB |
| Prometheus | `prom/prometheus:v3.5.0` | 91MB |
| Redis | `redis:7.4-alpine` | 16MB (키가 쌓이면 `REDIS_MAXMEMORY`까지) |
| redis-exporter | `oliver006/redis_exporter` | 6MB |
| (kafka-init) | `apache/kafka:4.1.0` | 토픽만 만들고 종료 |
| **인프라 합** | | **약 4.3GB** |
| 앱 (Spring Boot) | 직접 빌드 | ~1GB |
| OS | — | ~1GB |
| **전체** | | **약 6.5GB** (여유 포함 **8~10GB**로 잡는다) |

> 위 수치는 **놀고 있는 상태**다. 부하가 걸리면 MongoDB WiredTiger 캐시와 Redis가 늘고,
> Oracle SGA도 커진다. 개발일지 `2026-11-16-용량-산정.md`가 **약 10GB**로 잡은 것은
> 그걸 감안한 값이고, VM 사양은 그쪽을 따른다.

→ **16GB 머신이면 넉넉하고 12GB면 빠듯하게 된다.**

디스크는 50GB로 시작한다. `behavior_log` 1억 건이 약 50GB인데(용량 산정 문서),
3주 시연에서 거기까지 갈 일이 없고 `expire_at` TTL로 자동으로 지워진다.

## 2. 선택지 비교

| | **A. VM 1대 + compose** | B. 관리형으로 쪼개기 | C. Cloud Run |
|---|---|---|---|
| Oracle | 컨테이너 | **불가** (관리형 없음) → 결국 VM | **불가** |
| MongoDB | 컨테이너 | Atlas (마켓플레이스) | Atlas |
| Redis | 컨테이너 | Memorystore **월 $36~** | Memorystore |
| Kafka | 컨테이너 | Managed Kafka (CPU 시간당 $0.09~) | Managed Kafka |
| 앱 | jar 또는 컨테이너 | Cloud Run / VM | Cloud Run |
| 한 달 비용 | **$98~130** | $200+ | $150+ |
| 수고 | compose 그대로 | 서비스마다 연결·보안 설정 | 상동 + 앱 수정 |
| 우리에게 | **이것** | 과하다 | **스케줄러 때문에 안 된다** |

**C(Cloud Run)가 안 되는 이유**는 비용이 아니다. 우리 앱에는 **상주 스케줄러가 9개**
(`HoldExpiryScanner`, `OutboxRelayScheduler`, `SaleOpenScheduler`, `QueueAdmitScheduler`,
`PaymentRecheckScanner`, `RiskScoreBatch`, `RiskCacheResync`, `RiskJobRunner`, `EventCleanup`)
있고 **Kafka 컨슈머가 3개**(`seat-release`, `risk-signal`, `behavior-sink`) 붙어 있다. Cloud Run은 요청이 없으면 인스턴스를
0으로 줄이므로 **선점 만료가 안 되고 이벤트가 안 나간다.** 최소 인스턴스를 1로 고정하면
돌긴 하지만 그 순간 VM보다 비싸진다.

## 3. 절차

### 0. 사전 준비

```bash
# gcloud CLI 설치 후
gcloud auth login
gcloud projects create jejari-demo --name="제자리"
gcloud config set project jejari-demo
gcloud billing projects link jejari-demo --billing-account=<결제계정ID>
gcloud services enable compute.googleapis.com
```

> **결제 계정 연결이 필요하다.** $300 체험 크레딧을 쓰려면 카드 등록이 있어야 하고,
> 크레딧이 남아 있는 동안에는 과금되지 않는다. **체험이 끝나도 자동 과금으로 넘어가지 않는다**
> (직접 업그레이드해야 한다).

### 1. VM 만들기

```bash
gcloud compute instances create jejari \
  --zone=asia-northeast3-a \
  --machine-type=e2-standard-4 \
  --image-family=ubuntu-2404-lts-amd64 --image-project=ubuntu-os-cloud \
  --boot-disk-size=50GB --boot-disk-type=pd-balanced \
  --tags=jejari-web
```

| 항목 | 고른 값 | 이유 |
|---|---|---|
| 리전 | `asia-northeast3`(서울) | 시연 때 지연이 낮다. 미국(`us-central1`)이 월 $30쯤 싸다 |
| 머신 | `e2-standard-4` (4 vCPU / 16GB) | 10GB 필요 + 여유. 월 **$130**(서울) / **$98**(아이오와) |
| 이미지 | Ubuntu 24.04 **amd64** | 팀이 x86으로 정한 이유와 같다 — 로컬과 같은 이미지를 그대로 쓴다 (조영준 씨 개발일지). Oracle 이미지는 arm64도 있지만(`docker manifest inspect`로 확인) ARM(T2A)은 리전이 제한적이다 |
| 디스크 | 50GB pd-balanced | 용량 산정 문서 기준 |

**아끼려면**: `--machine-type=e2-custom-4-12288` (4 vCPU / 12GB)로 월 $20쯤 줄어든다.
MongoDB 캐시를 줄여야 한다(`--wiredTigerCacheSizeGB 2`).

### 2. 방화벽 — **8080만 연다**

```bash
gcloud compute firewall-rules create jejari-web \
  --allow=tcp:8080 --target-tags=jejari-web \
  --source-ranges=0.0.0.0/0 --description="제자리 앱 API"
```

> **DB 포트(1521·27017·6379·9092)는 절대 열지 않는다.**
> `compose.yaml`이 이미 `127.0.0.1:` 로 묶어 둬서 기본적으로 밖에서 안 보인다
> (`ports: ["127.0.0.1:1521:1521"]`). **이 바인딩을 풀지 마라.** 앱은 같은 VM 안에 있으므로
> `localhost`로 붙는다.
>
> DB에 직접 붙어야 하면 포트를 여는 대신 **SSH 터널**을 쓴다:
> ```bash
> gcloud compute ssh jejari --zone=asia-northeast3-a -- -L 1521:localhost:1521
> ```
> 그러면 내 PC의 `localhost:1521`이 서버 Oracle이 된다. 1521을 인터넷에 여는 것과 달리
> SSH로 인증된 사람만 들어온다.

#### SSH 22번은 **이미 열려 있다** — 좁히는 것을 권한다

`gcloud compute ssh`는 IAP를 자동으로 쓰지 않는다. 기본 VPC에 구글이 만들어 두는
**`default-allow-ssh`(tcp:22, `0.0.0.0/0`)** 때문에 되는 것이다. 즉 **22번이 전 세계에 열려 있다.**

세 가지 중 하나를 고른다.

| 방법 | 수고 | 안전함 |
|---|---|---|
| 그대로 둔다 | 0 | 낮음. 키 인증이라 뚫리진 않지만 로그가 스캔으로 도배된다 |
| **팀원 IP만 허용** | 5분 | 중간. 집·학교 IP가 바뀌면 다시 고쳐야 한다 |
| **IAP 터널만 허용** | 15분 | 높음. 구글 계정 권한이 있는 사람만 |

팀원 IP만 허용:

```bash
gcloud compute firewall-rules update default-allow-ssh   --source-ranges=<팀원1 IP>/32,<팀원2 IP>/32   # 내 IP: curl ifconfig.me
```

IAP만 허용 (더 권함. IP가 바뀌어도 그대로 된다):

```bash
gcloud services enable iap.googleapis.com
gcloud compute firewall-rules create allow-ssh-from-iap   --allow=tcp:22 --source-ranges=35.235.240.0/20 --target-tags=jejari-web
gcloud compute firewall-rules delete default-allow-ssh      # 전 세계 22번을 닫는다

# 접속할 때마다 --tunnel-through-iap 를 붙인다
gcloud compute ssh jejari --zone=asia-northeast3-a --tunnel-through-iap
```

> 팀원에게 `roles/iap.tunnelResourceAccessor` 권한을 줘야 한다.
> 이걸 안 주고 `default-allow-ssh`를 지우면 **아무도 못 들어간다.** 지우기 전에 다른 창에서
> IAP 접속이 되는지 먼저 확인한다.

### 4. 코드와 비밀값 올리기

```bash
git clone https://github.com/BrainSaver/Jejari.git && cd Jejari
```

**`.env`는 gitignore라 레포에 없다.** 따로 올려야 한다.

```bash
# 내 PC에서
gcloud compute scp .env jejari:~/Jejari/.env --zone=asia-northeast3-a
# 서버에서
chmod 600 ~/Jejari/.env
```

꼭 지킬 것:

- **`JEJARI_HMAC_KEY`는 팀 공용 값이다.** 서버에서 새로 만들면 `ci_hash`가 달라져
  매수 제한·위험 점수가 로컬과 안 맞는다
- **`compose.override.yml`은 올리지 마라.** 내 PC의 MongoDB 포트 충돌(27018)을 피하려고 만든
  파일이라 서버에서는 틀린 설정이다 (gitignore라 clone하면 안 따라온다)
- **운영 값을 바꿀 것**: `JWT_REFRESH_COOKIE_SECURE=true`, 비밀번호를 로컬과 다르게

> 제대로 하려면 Secret Manager를 쓴다(`gcloud secrets create`). 3주 프로젝트에서는
> `chmod 600`한 `.env`로 충분하다고 본다. 어느 쪽이든 **git에는 올라가면 안 된다.**

### 5. 인프라 기동

```bash
cd ~/Jejari
docker compose up -d
docker compose logs oracle | grep "jejari seed loaded"    # 스키마·시드까지 들어갔는지
```

Oracle은 첫 기동에 **약 5분** 걸린다 (내 로컬 컨테이너 로그 실측: 기동 → `jejari seed loaded`까지 4분 40초).
스키마 44개 + 시퀀스 14개 + 시드가 들어간다. 그동안 앱을 띄우면 접속 실패로 죽으니 기다린다.

스키마가 바뀌면 볼륨을 새로 만들거나 `db/patch/`의 델타를 돌린다.

### 6. 앱 띄우기

```bash
cd ~/Jejari
set -a && . <(grep -E "^JEJARI_|^JWT_" .env) && set +a
LC_ALL=C.UTF-8 TZ=Asia/Seoul ./gradlew bootJar
```

`systemd`로 상주시킨다 (`/etc/systemd/system/jejari.service`):

```ini
[Unit]
Description=제자리
After=docker.service
Requires=docker.service

[Service]
User=ubuntu
WorkingDirectory=/home/ubuntu/Jejari
EnvironmentFile=/home/ubuntu/Jejari/.env
Environment=TZ=Asia/Seoul
Environment=LANG=C.UTF-8
ExecStart=/usr/bin/java -jar build/libs/jejari-0.0.1-SNAPSHOT.jar
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now jejari
journalctl -u jejari -f
```

> **`TZ=Asia/Seoul`이 없으면 앱이 아예 안 뜬다.** 기동 점검(`TimeZoneVerifier`, §0.7)이
> JVM 시간대가 UTC면 거부한다. 일부러 그렇게 만들어 둔 것이다 — 시간대가 어긋나면
> 결제 기한·매수 한도(구매일 기준)가 조용히 틀어지기 때문이다.
>
> `LANG=C.UTF-8`이 없으면 빌드가 한글 파일 이름에서 깨진다.

## 4. 이 프로젝트에서 특히 걸릴 것

### 시드 날짜가 "적재한 날" 기준 상대값이다

`9001`의 운행일 = 적재일 + 3일, 판매 마감 = 운행일 + 1일. **서버를 5일 넘게 켜 두면
`9001`이 판매 중이 아니게 되고 시연이 막힌다.** 판매 오픈 스케줄러가 `status`를 `CLOSED`로
맞추는데, 그건 읽기 조건과 일치시킨 것이고 원인은 묵은 시드다.

시연 전날 다시 넣는 것이 안전하다:

```bash
docker compose rm -sf oracle && docker volume rm jejari_oracle-data && docker compose up -d oracle
```

### Oracle Free 12GB 상한

에디션 자체의 하드 제한이다. 예약 약 2,400만 행. 데모엔 충분하지만
**수천만 건짜리 부하 테스트를 공용 서버에 때려넣으면 닿는다.**
부하 테스트는 로컬에서 한다 (용량 산정 문서의 결론과 같다).

### 공용 서버에 앱이 떠 있어도 내 로컬 테스트에는 영향 없다

단, **로컬 테스트가 공용 DB를 보게 설정하면 안 된다.** 앱의 스케줄러가 테스트가 만든
HOLD를 먼저 만료시키고 outbox를 먼저 가져간다
(`troubleshooting/20261117-앱이-떠-있으면-통합테스트가-조용히-깨짐.md`).

### 방화벽은 두 군데가 아니다 (Oracle Cloud와 다름)

Oracle Cloud는 Security List와 VM 안의 iptables 둘 다 열어야 했는데,
**GCP는 VPC 방화벽 규칙 하나면 된다.** Ubuntu 이미지에 ufw가 꺼져 있다.

## 5. 돈이 새지 않게

```bash
# 예산 알림 (크레딧 소진 전에 알려 준다)
gcloud billing budgets create --billing-account=<ID> \
  --display-name="제자리" --budget-amount=100USD \
  --threshold-rule=percent=0.5 --threshold-rule=percent=0.9
```

- **안 쓸 땐 중지한다** (`gcloud compute instances stop jejari`). 중지하면 vCPU·RAM 요금이
  멈추고 디스크(50GB, 월 $5쯤)만 남는다. **삭제하면 데이터도 사라진다.**
- **고정 IP를 예약했다면 안 쓸 때도 돈이 나간다.** VM에 붙어 있는 임시 IP는 중지 중엔 공짜다.
- 3주 쓰고 끄면 **$100 안쪽**이다 ($300 크레딧 안).

| 항목 | 월 (서울) | 월 (아이오와) |
|---|---|---|
| e2-standard-4 | $130 | $98 |
| 디스크 50GB | $5 | $5 |
| 외부 IP | $3 | $3 |
| **합** | **약 $138** | **약 $106** |

## 7. 다음에 할 수 있는 것 (지금은 안 해도 됨)

- **HTTPS·도메인** — 지금은 `http://IP:8080`이다. 쿠키에 `Secure`를 켜려면 HTTPS가 필요하다.
  Caddy를 앞에 두면 Let's Encrypt 인증서가 자동이다
- **CI에서 자동 배포** — `.github/workflows/ci.yml`에 빌드가 이미 있다. jar를 서버로 보내고
  `systemctl restart jejari`까지 붙이면 된다
- **Grafana 공개** — 지금 3000은 `127.0.0.1`에 묶여 있다. 보려면 SSH 터널을 쓰거나
  Caddy 뒤에 인증을 걸고 연다

## 8. 담당자가 할 일 (체크리스트)

**전체 2~3시간**입니다. Oracle 기동 5분과 gradle 빌드를 빼면 대부분 기다리는 시간입니다.
각 단계 끝에 **확인**이 있습니다. 거기서 멈추면 다음으로 넘어가지 말고 그 자리에서 해결하세요.

### 먼저 팀과 정할 것 (혼자 정하지 말 것)

| 정할 것 | 선택지 | 추천 |
|---|---|---|
| 리전 | 서울 $138/월 · 아이오와 $106/월 | **서울** (시연 지연) |
| 결제 계정 | 누구 카드로 $300 크레딧을 받나 | — |
| SSH 범위 | 전 세계(기본) · 팀원 IP · IAP | **IAP** (3-2절) |
| 공용 DB 비밀번호 | 로컬과 같게 / 다르게 | **다르게** |
| 끄는 규칙 | 상시 / 안 쓸 때 중지 | **밤에 중지**하면 비용 절반 |

`JEJARI_HMAC_KEY`만은 **팀 공용 값 그대로** 써야 합니다 (바꾸면 `ci_hash`가 달라져
매수 제한·위험 점수가 로컬과 안 맞음).

---

### 1단계 — 계정·프로젝트 (20분)

- [ ] gcloud CLI 설치, `gcloud auth login`
- [ ] 프로젝트 생성 + **결제 계정 연결** ($300 크레딧)
- [ ] `gcloud services enable compute.googleapis.com`
- [ ] **예산 알림부터 건다** (5절). 나중으로 미루면 까먹는다

**확인** `gcloud config list` 에 project가 찍히고, 콘솔 결제 화면에 크레딧 잔액이 보인다.

### 2단계 — VM (10분)

- [ ] `e2-standard-4` / Ubuntu 24.04 amd64 / 50GB / 태그 `jejari-web` (3-1절)
- [ ] 외부 IP 확인해서 팀에 공유

**확인** `gcloud compute ssh jejari --zone=asia-northeast3-a` 로 들어가진다.

### 3단계 — 방화벽 (15분) ★ 여기가 제일 위험

- [ ] 8080만 연다
- [ ] **DB 포트(1521·27017·6379·9092)는 열지 않는다** — 열지 "않는" 게 아니라, 애초에
      `compose.yaml`이 `127.0.0.1`에 묶어 둬서 밖에서 안 보인다. **그 바인딩을 풀지 마라**
- [ ] SSH 22번을 좁힌다 (IAP 권장). **지우기 전에 다른 창에서 IAP 접속이 되는지 먼저 확인**

**확인** 내 PC에서

```bash
curl -m 5 http://<IP>:8080/actuator/health   # 아직 앱이 없으니 연결 거부 (정상)
nc -zv <IP> 1521                             # 반드시 "실패"여야 한다 ★
```

`nc`가 성공하면 Oracle이 인터넷에 노출된 것이다. **즉시 멈추고 바인딩을 확인한다.**

### 4단계 — 서버 준비 (15분)

- [ ] `docker.io` + `docker-compose-v2` + `openjdk-21-jdk-headless` + `git` 설치
- [ ] `usermod -aG docker` 후 **재접속** (안 하면 권한 오류)
- [ ] `git clone`

**확인** `docker compose version` 과 `java -version`(21) 이 나온다.

### 5단계 — 비밀값 (10분) ★ 두 번째로 위험

- [ ] `.env`를 `scp`로 올리고 `chmod 600`
- [ ] 운영 값으로 바꾼다: `JWT_REFRESH_COOKIE_SECURE`, DB 비밀번호
- [ ] **`JEJARI_HMAC_KEY`는 그대로**
- [ ] `compose.override.yml`이 서버에 없는지 확인 (`ls` — 있으면 지운다)

**확인**

```bash
ls -l ~/Jejari/.env            # -rw------- 여야 한다
git -C ~/Jejari status         # .env가 안 보여야 한다 (gitignore)
```

### 6단계 — 인프라 (20분, 대부분 대기)

- [ ] `docker compose up -d`
- [ ] **Oracle이 healthy가 될 때까지 기다린다** (약 5분). 그 전에 앱을 띄우면 접속 실패로 죽는다

```bash
# healthy가 되면 바로 빠져나온다
until [ "$(docker inspect -f '{{.State.Health.Status}}' jejari-oracle-1)" = healthy ]; do sleep 10; done
```

> healthcheck가 **앱 계정으로 FREEPDB1에 실제 접속**하는 것까지 본다 (조영준 씨 개선).
> 그래서 healthy = 바로 쓸 수 있다는 뜻이다. 예전처럼 "healthy인데 PDB가 아직 안 열림"이 없다.

**확인**

```bash
docker compose logs oracle | grep "jejari seed loaded"     # 이 줄이 나와야 한다
docker compose ps                                          # 아래 7개가 Up
# oracle · mongo · redis · redis-exporter · kafka · prometheus · grafana
# (kafka-init은 토픽만 만들고 끝나므로 Exited 0이 정상이다)
PW=$(grep '^ORACLE_APP_PASSWORD=' .env | cut -d= -f2)
docker compose exec -T -e NLS_LANG=AMERICAN_AMERICA.AL32UTF8 oracle   bash -lc "cd /seed && sqlplus -S -L jejari/$PW@localhost:1521/FREEPDB1 @99_verify.sql"
```

시드 검증 **23항목이 전부 OK**여야 한다. 하나라도 틀리면 볼륨을 지우고 다시 한다.

### 7단계 — 앱 (30분, 대부분 빌드)

- [ ] `LC_ALL=C.UTF-8 TZ=Asia/Seoul ./gradlew bootJar`
- [ ] systemd 등록 (3-6절). **`Environment=TZ=Asia/Seoul` 빠뜨리지 말 것**

**확인**

```bash
journalctl -u jejari -n 50 | grep "시간대 점검 통과"      # 이 줄이 나와야 정상
curl localhost:8080/actuator/health                        # {"status":"UP"}
```

`시간대 점검 통과`가 안 보이고 `IllegalStateException`이 뜨면 `TZ`를 빠뜨린 것이다.

### 8단계 — 밖에서 확인 (10분)

```bash
IP=<외부 IP>
curl http://$IP:8080/actuator/health
curl "http://$IP:8080/api/v1/stations"
curl "http://$IP:8080/api/v1/runs?from=3900023&to=3900114&date=$(date -d '+3 days' +%F)"
```

- [ ] 세 번째 응답에 **`"bookable": true`인 운행 9001**이 보인다 ← 시연 가능 상태
- [ ] `nc -zv $IP 1521` 이 **여전히 실패**한다

### 9단계 — 팀에 알리기

- [ ] 외부 IP, 8080만 열려 있다는 것, SSH 접속 방법
- [ ] **"로컬 통합 테스트를 이 서버 DB로 돌리지 마세요"** — 서버 앱의 스케줄러가 테스트의
      HOLD를 먼저 만료시키고 outbox를 가져간다 (4절)
- [ ] **시연 전날 Oracle 볼륨을 다시 만들 것** (4절, 시드 날짜가 상대값)
- [ ] 밤에 끄는 규칙을 쓰기로 했다면 그 시각

---

### 막혔을 때

| 증상 | 원인 | 할 일 |
|---|---|---|
| 앱이 바로 죽고 `IllegalStateException` | `TZ` 없음 | systemd에 `Environment=TZ=Asia/Seoul` |
| 빌드가 `bad filename …$회피.class` | 로케일 | `LC_ALL=C.UTF-8` |
| 앱이 `PiiCipher` 빈 없다고 함 | `.env` 키 누락 | `JEJARI_ENC_KEYS`·`JEJARI_PEPPER_KEYS` 확인 |
| 통합 테스트가 무더기로 깨짐 | Oracle 볼륨이 묵음 | `SELECT COUNT(*) FROM user_sequences` → 14여야 함 |
| `9001`로 예매가 안 됨 | 시드 날짜가 지남 | 볼륨 재생성 (4절) |
| `docker` 권한 오류 | 그룹 적용 전 | 재접속 |
| 갑자기 아무도 SSH 못 함 | `default-allow-ssh`를 성급히 지움 | 콘솔 → VM → **직렬 콘솔**로 들어가 규칙 복구 |

### 요약 — 순서만

```
1. gcloud 설치 · 프로젝트 · 결제 연결 · 예산 알림
2. e2-standard-4 / Ubuntu 24.04 amd64 / 50GB (서울), 태그 jejari-web
3. 방화벽 8080만 · SSH 좁히기     ← nc -zv IP 1521 이 실패해야 한다
4. docker.io + compose-v2 + JDK21 설치, 재접속
5. git clone + .env scp (chmod 600)
6. docker compose up -d → 5분 대기 → "jejari seed loaded" + 검증 23항목
7. ./gradlew bootJar → systemd (TZ=Asia/Seoul 필수) → "시간대 점검 통과"
8. 밖에서 curl → 9001이 bookable:true
9. 팀에 IP·주의사항 공유, 안 쓸 땐 instances stop
```
