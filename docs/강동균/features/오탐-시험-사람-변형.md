봇을 잘 잡는 것만큼 **사람을 안 잡는 것**이 중요합니다. 지금까지 합성 사람은 한 가지 모습(천천히 둘러보는 사람)뿐이라 오탐 근거가 약했습니다.
그래서 **진짜 사람이 하는데 규칙에 걸리기 쉬운 행동**을 10가지로 나눠 돌렸습니다. 여전히 스크립트라 "이 행동이면 오탐이 나는가"만 보고, 오탐률은 2차 대회 사람으로 잽니다.

### 고칠 것 1 — 한 기기의 가족이 다계정으로 잡힘 (강다인 님)

- MULTI_ACCOUNT_SYNC는 "같은 기기에서 서로 다른 계정이 60초 안에 선점"이면 케이스입니다. botshareddev(기기 공유 봇)를 잡는 규칙인데, **가족이 한 컴퓨터로 차례로 사는 경우**도 똑같이 걸립니다
- 명절에는 자녀가 부모님 계정으로 차례로 예매해 드리는 일이 흔해서 실제 오탐 위험이 큽니다
- 가르는 기준 제안: **로그인 세션이 동시에 열려 있었나**
  - 가족: 한 사람이 끝나고(로그아웃 또는 세션 끝) 다음 사람이 로그인 → 세션이 겹치지 않음
  - 봇: 계정 여러 개를 한꺼번에 열어 둠 → 같은 순간 열린 세션이 여러 개
- 또는 **기기(DEVICE) 대상만** 창을 60초 → 10초로 줄이고, 화면 녹화가 사람답지 않을 때만 케이스로 (CI·결제 수단 대상은 그대로)
- 고친 뒤 `PROFILES=humanfamily,botshareddev`로 둘 다 다시 재기 (가족은 0, 봇은 그대로 잡혀야 함)

### 고칠 것 2 — 같은 IP 뒤 5명이 넘으면 가입이 막힘 (회원 담당)

- `auth.signup_rate_per_hour` = 10인데, **본인인증과 가입이 둘 다** 한 번씩 세서(`SignupService.checkSignupRate`가 두 곳에서 불림) 실제로는 **IP당 시간당 5명**입니다
- 회사·학교·PC방처럼 한 IP 뒤 사람이 많으면, 판매 오픈 전 가입이 몰릴 때 6번째 사람부터 1시간 동안 가입을 못 합니다 (탐지가 아니라 서비스 거절)
- 제안: 가입 완료만 세거나(본인인증은 별도 한도), 한도를 30 정도로. 가입 매크로는 본인인증(CI) 한 명당 계정 하나라서 IP 한도가 없어도 명의 수 이상으로 늘릴 수 없습니다

## 2. 가장 잘 숨는 봇 3종 (3단계 추가)

| 봇 | 녹화 | 결과 | 의미 |
|---|---|---|---|
| botrecjump | 클릭 자리에 점 하나 찍고 클릭 (순간이동) | 통과 (5점) | 순간이동 3~5번 < 문턱 8 — [마우스 제안](마우스-궤적-보강-제안.md) 5절 "이동 단위로 세기"와 같은 문제 |
| botrecmobile | 휴대폰인 척 (터치 클릭만) | 통과 | **humanmobile과 녹화가 같음** — 녹화만으로는 못 가름 |
| botrecreal | 사람과 같은 녹화 + 2단계 피하기 전부 | 통과 | 규칙으로 잡을 수 있는 상한을 넘은 봇 |

- **botrecmobile·botrecreal은 행동 규칙으로 못 잡는 게 정상**입니다. 사람과 똑같이 행동하면 행동으로는 구별할 근거가 없습니다
- 이런 봇의 피해는 **행동이 아닌 구조**가 막습니다: 명의(CI)당 4매 매수 제한, 명의당 대기열 1자리(QUEUE_DUPLICATED), 좌석 조회·선점 속도 제한, 결제 기한 지난 좌석 대기자 우선(A안). 봇 운영자가 늘릴 수 있는 것은 **실제 명의 수**뿐이라 피해가 명의 수 × 4매로 묶입니다
- 그래서 남은 방어 순서: ① 오탐 먼저 줄이기(위 1·2) ② 이동 단위 세기(botrecjump) ③ 점수가 애매한 계정에만 확인 단계(CAPTCHA 등) ④ 2차 사람 데이터로 모델
