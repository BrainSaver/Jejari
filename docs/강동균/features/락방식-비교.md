# 좌석 선점 락 방식 비교와 SeatHoldStrategy (§17.1)

작성자: 강동균 · 코드 위치: `bench/lock_compare.py`, `bench/schema.sql` (상세는 `bench/README.md`)

## 한 줄 요약

좌석을 선점하는 세 가지 방법(비관적 락 · 낙관적 락 · Redis 1차)을 **같은 조건에서 실제로
재서** 무엇을 왜 고를지 정하고, 나중에 설정으로 바꿔 끼울 수 있게 인터페이스로 나눕니다.

## 어떻게 동작하나

```
A 비관적   SELECT ... FOR UPDATE  →  줄 서서 하나씩  →  UPDATE
B 낙관적   SELECT version         →  UPDATE ... WHERE version=?  →  0행이면 다시
C 현재     Redis hold.lua         →  지면 끝(DB 안 감)  →  이긴 사람만 INSERT(PK가 최종)
```

좌석 1,080석이 들어간 로컬 Oracle에 워밍업 1회 + 5회 측정 중앙값으로 쟀습니다.

## 결과 (요약)

| 시나리오 | A 비관적 | B 낙관적 | C 현재 | C의 DB 왕복 |
|---|---|---|---|---|
| 같은 좌석 1개에 100명 | 255 TPS | 1,457 | **2,732** | **2회** (A는 201회) |
| 좌석 20개에 300명 | 707 | 1,825 | **2,083** | **40회** (A는 620회) |
| 좌석 500개에 500명 | 787 | **1,256** | 756 | 624회 |

**중복 예약은 세 방식 × 세 시나리오 전부 0건.** 정확성은 다 만족하고, 차이는 비용입니다.

## 왜 이렇게 했나 — 그리고 예상과 달랐던 것

- **C를 고른 이유는 TPS가 아니라 DB 보호입니다.** 극한 경쟁에서 DB 왕복이 **201회 → 2회**로
  100배 줄어듭니다. 패배자 99명이 Redis에서 걸러져 DB에 아예 안 가기 때문입니다(§2.1-4).
  명절 예매처럼 인기 열차 한 편에 수만 명이 몰릴 때 DB가 버티느냐의 문제라 이게 핵심입니다.
- **경쟁이 적으면 C가 B보다 느립니다** (756 vs 1,256 TPS). 좌석이 안 겹치면 Redis 왕복이
  그냥 더해지는 비용이 됩니다. 이건 예상과 달랐고, "Redis를 끼우면 항상 빠르다"는 말이
  틀렸다는 뜻입니다. 그래도 1차는 C로 통일합니다 — 운영 중에 "지금 경쟁이 심한가"를
  미리 알 수 없고, 코드가 두 갈래가 되면 버그가 생길 자리가 늘어납니다.
- **꼬리 지연은 B가 낫습니다** (시나리오 2에서 p99 43.5ms vs 74.3ms). C는 패배자가 아주
  빨리 끝나 평균을 끌어내리는 대신 승자들의 INSERT가 몰려 꼬리가 길어집니다.
- **A는 쓸 이유가 없습니다.** 전 구간에서 가장 느리고 변동이 가장 큽니다(TPS 98~930).
  경쟁이 적은 시나리오 3에서 오히려 락 대기가 p99 **2,646ms** 까지 튀었습니다.

## SeatHoldStrategy — 바꿔 끼울 수 있게

세 방식을 인터페이스 하나 뒤에 두고 설정으로 고릅니다. 비교 실험을 재현할 수 있어야 하고,
C에 문제가 생기면 되돌릴 수 있어야 하기 때문입니다.

```java
public interface SeatHoldStrategy {
    /** 좌석을 선점한다. 실패하면 이유를 담아 돌려준다. DB 트랜잭션은 호출한 쪽이 연다. */
    SeatHoldResult hold(SeatHoldCommand cmd);

    /** 선점을 되돌린다 (§2.3 보상). 여러 번 호출해도 결과가 같아야 한다. */
    void release(long reservationId, List<SeatKey> seats);

    String name();   // "PESSIMISTIC" | "OPTIMISTIC" | "REDIS"
}
```

- `RedisSeatHoldStrategy` — 본 구현. `hold.lua` + DB PK (§2)
- `PessimisticSeatHoldStrategy` · `OptimisticSeatHoldStrategy` — **실험 전용**

설정 `jejari.seat.hold-strategy` 로 고르고 기본값은 `REDIS` 입니다. 실험용 두 개는
운행 좌석 행을 미리 만들어야 해서 운영 경로에서는 쓰지 않습니다.

## 주의할 점

- **이 수치는 로컬 단일 머신·Python 스레드 기준입니다.** 앱·Oracle·Redis가 한 PC에 있어
  네트워크 지연이 없고 GIL 때문에 클라이언트 병목이 섞여 있습니다. 뼈대가 올라오면
  k6로 HTTP 레벨에서 다시 재야 합니다 (조영준 E).
- 실제 §2.2 트랜잭션은 여기서 잰 것보다 무겁습니다 (reservation·reservation_seat·
  purchase_counter·history·saga·outbox 까지 한 트랜잭션). 세 방식에 공통으로 붙으므로
  비교에는 영향이 없지만 절대 수치는 더 낮아집니다.
- A·C는 회차 간 편차가 큽니다 (A 98~930, C 113~1,223 TPS). 발표용 수치로 쓸 때는
  `ROUNDS` 를 늘려 다시 재는 게 좋습니다.
- 실험 테이블(`exp_seat`, `exp_seat_inv`)은 `bench/schema.sql` 이 만듭니다.
  실제 스키마는 건드리지 않습니다.
