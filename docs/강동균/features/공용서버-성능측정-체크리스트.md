> 개선 전 기준: [조영준 · 성능측정-공용서버](../../조영준/features/성능측정-공용서버.md) (11-19)

## 무엇을 재나

11-19에 조영준 님이 앱 1대·해시 4로 잰 값을 **개선 전**으로 둡니다. 그 뒤 서버에 들어간 개선은 세 가지입니다.

| 개선 | 커밋 | 기대 |
|---|---|---|
| 커넥션 풀 10 → 20, 연결 대기 30 → 5초 | `b99c043` | 선점·결제의 커넥션 대기 감소 |
| 로그인 대기실 (해시 4개 자리에서 줄 서기, 가득 차면 429 + Retry-After) | `f7c3872` | 로그인이 몰려도 다른 API가 안 멈춤, 503 대신 재시도 |
| outbox 릴레이가 보낼 것이 있는 샤드만 처리 | `822ce67` | 유휴 DB 호출 초당 81.5 → 10.5번 (바탕 부하 감소) |

**조건은 11-19와 같게** 둡니다: 200명이 20초 안에 흩어져 도착하고 한 명이 예매를 한 번 합니다. 서울 → 부산 구간에서, 빈 운행을 측정마다 하나씩 씁니다.
k6는 내 PC에서 돌려 서버 CPU를 쓰지 않게 하고, Docker의 `grafana/k6:1.1.0`을 씁니다.

달라진 점이 하나 있습니다. 계정을 **미리 만들어 두고 다시 씁니다**(`ACCOUNTS=existing`). 공용 서버에서는 모든 요청이 내 IP 하나로 들어와,
가입 제한(시간당 최대 100회, 계정 하나에 본인인증·가입 2회)으로는 한 시간에 계정 50개밖에 못 만듭니다.
같은 계정으로 하루 여러 번 재도 됩니다 (회원당 하루 20장 제한, 측정 한 번에 1장).

| 키 | 지금 값 (적기) | 측정 동안 | 왜 |
|---|---|---|---|
| `auth.login_rate_per_min` | ____ (기본 20) | **600** (최대) | 200명의 로그인이 전부 내 IP 하나에서 나감 |

## 2. 계정 준비 (처음 한 번만, 내 PC)

저장소 루트의 Git Bash에서 실행합니다. 주소는 팀 채널에 있습니다.

```bash
export BASE_URL=https://<서버 주소>
```

```bash
loadtest/tools/server_perf.sh accounts
```

- 계정 50개마다 가입 제한(429)에 걸려 멈추고 "계정 N/200개까지 준비됨"을 알려 줍니다. 그러면 **서버에서** 가입 제한 카운터를 비웁니다
  (IP별 시간당 카운터라 지워도 다른 기능에는 영향이 없습니다):
  ```bash
  docker compose exec -T redis sh -c 'redis-cli --scan --pattern "rate:signup:*" | xargs -r redis-cli DEL'
  ```
  그다음 같은 명령을 다시 돌리면 이미 있는 계정은 건너뛰고 이어서 만듭니다. 200개를 만들려면 3번 비우면 됩니다
- 끝나면 `계정 준비 끝: 200개`가 나옵니다. 오후에 다른 사람이 잴 때도 **같은 `RUN_TAG`(기본 `perf1`)이면 이 계정을 그대로 씁니다**
- 계정 준비가 끝나면 `auth.signup_rate_per_hour`는 원래 값으로 되돌려도 됩니다

## 3. 측정 (한 번에 3~4분)

1. 빈 운행 고르기 (내 PC)
   ```bash
   loadtest/tools/server_perf.sh find
   ```
   남은 좌석이 많은 순으로 나옵니다. 200석 넘게 남은 운행을 고르고, 측정마다 다른 운행을 씁니다.
   좌석 경쟁 조건을 같게 하려면 같은 열차(좌석 수가 같은 것)끼리 비교합니다
2. **서버 창 하나 더 열어** CPU 기록 켜기 (측정이 끝나면 `Ctrl+C`)
   ```bash
   vmstat -t 5 | tee ~/perf-vmstat-$(date +%H%M).txt
   ```
3. 측정 (내 PC)
   ```bash
   loadtest/tools/server_perf.sh run <운행 번호>
   ```
   끝나면 표가 나옵니다 (원본은 `loadtest/results/perf_<운행>_<시각>.json`). 종료 코드 99는 기준(p95 1초 등)을 못 넘었다는 뜻일 뿐이고, 결과는 유효합니다.
   **시작·끝 시각을 적어 둡니다** (4단계에서 Grafana 범위로 씀)
4. 같은 조건으로 **최소 2번**, 운행을 바꿔 잽니다. 11-19도 순서 효과를 보려고 다시 쟀습니다

## 4. 서버 쪽 값 읽기

| 항목 | 어디서 | 읽는 법 |
|---|---|---|
| VM CPU 최대 | 3단계의 `vmstat` 파일 | `100 - id` 열의 최댓값 |
| 부하 평균 | 서버 `uptime` (측정 직후) | 1분 값 |
| DB 커넥션 대기 최대 | Grafana `https://<서버 주소>/grafana/` → "제자리 · 앱 개요" → 커넥션 패널, 시간 범위 = 측정 시작~끝 | `pending` 최댓값 |
| GC 일시정지 합 | Grafana Explore (Prometheus) | `sum(increase(jvm_gc_pause_seconds_sum{job="jejari-app"}[5m]))` (끝 시각 기준) |
| 앱 CPU 최대 | Grafana Explore | `max_over_time(process_cpu_usage{job="jejari-app"}[5m])` |

**정합성 점검** (서버, 읽기만 함): 측정한 운행에서 결제·표·좌석·이벤트가 어긋난 곳이 없는지 봅니다.
```bash
bash loadtest/tools/check_booking.sh <운행 번호> 30
```
FAIL이 있으면 성능 수치보다 이게 먼저입니다.
