# 용량 시험 — 우리 서버는 몇 명까지 버티나

> 시나리오: `loadtest/scenarios/13_capacity.js` (`./run.sh capacity`)
> 같이 볼 화면: 관리자 **A-10 트래픽 관제** (상태 띠·흐름도·데이터 놓침·밀림)

## 1. 무엇을 재나

동시 사용자를 단계별로 늘린다 (기본 10 → 25 → 50 → 100 → 200명, 단계마다 90초). 한 사람은 실제 회원(JWT 로그인)이고 아래를 반복한다.

```
열차 조회 → 대기열 진입·입장 대기 → 좌석 배치도 → 대기열 나가기 → 3초 쉬기 (사람처럼 ±50%)
```

명절에 몰리는 요청 대부분이 이것(조회·대기열 폴링·배치도)이라 기본은 좌석 선점을 하지 않는다. `-e BOOK=hold`면 선점 후 바로 취소까지 한다 (같은 계정이 반복하므로 매수 제한·취소 남용 규칙에 걸릴 수 있음).

끝나면 단계별 표와 **"버틴 최대 단계"** (p95 < 1초 이고 5xx < 1% 인 가장 높은 단계 — A-10의 "주의" 문턱과 같음)를 출력하고 `capacity-result.json`에 남긴다.

**안전장치**: 어느 단계든 5xx가 20%를 넘거나 p95가 5초를 넘으면 20초 지켜본 뒤 스스로 멈춘다. 그 단계가 한계라 더 올릴 이유가 없고, 공용 서버를 오래 쓰러뜨리지 않으려고.

| 옵션 (`-e 이름=값`) | 기본 | 뜻 |
|---|---|---|
| `STEPS` | `10,25,50,100,200` | 단계별 동시 사용자 (최대 2000) |
| `STEP_SEC` | 90 | 단계마다 시간 |
| `THINK_SEC` | 3 | 한 바퀴 뒤 쉬는 시간 |
| `LOGIN_SPREAD_SEC` | 30 | 단계가 오를 때 새로 온 사람들의 첫 로그인을 이 시간 안에 흩뜨림. **0이면 전원이 같은 순간에 로그인 (로그인 폭주 시험)** |
| `BOOK` | `no` | `hold`면 좌석 선점 후 바로 취소 |
| `RUN_ID` · `FROM` · `TO` | 9001 · 서울 · 부산 | 판매 중인 운행과 정차역 |
| `P95_MS` · `ERR_PCT` | 1000 · 1 | "버틴다"의 기준 |

## 2. 로컬에서 먼저 잰 결과 (2026-11-20)

환경: 4코어 컨테이너 하나에 앱·Oracle·Kafka·MongoDB·Redis·Prometheus·**k6까지 같이** — 서버 숫자가 아니라 "방법이 맞나, 어디가 먼저 무너지나"를 보는 용도.

| 실행 | 결과 |
|---|---|
| 10 → 25 → 50 → 100명 (로그인 흩뜨림 30초) | 모두 버팀. 초당 20 → 50 → 98 → 196건, p95 11~29ms. 사람 1명 ≈ 초당 2건 |
| 200 → 400 → 800명 (로그인 흩뜨림 30초) | **400명까지 버팀** (초당 531건, p95 471ms). 800명에서 넘음 (p95 5.2초, 5xx 6.5%) → 안전장치로 멈춤 |
| 200 → 400명 (**로그인 폭주**, 흩뜨림 0, 해시 32개) | **200 → 400명으로 오르는 순간 무너짐**: 초당 344건 → **5건**, 5xx 38%, p95 6초 |

### 발견: 로그인 폭주가 이 시스템의 한계를 정한다

- 넘은 단계의 5xx는 **전부 로그인**(`POST /api/v1/auth/login` → 503 `SERVICE_UNAVAILABLE`, 928건)이었다. 대기열·배치도·조회는 5xx가 없었다
- 비밀번호 확인은 Argon2id(m=19MiB, t=2 — 일부러 느림)이고 동시에 32개까지만 계산한다 (`auth.max_concurrent_hash`). 자리를 못 받은 로그인은 **최대 3초 기다리며 Tomcat 요청 스레드를 붙잡는다**
- 200명이 한꺼번에 로그인하면: CPU 100%, GC 멈춤 8.8초/10분, Tomcat 스레드 200개 전부 사용, DB 커넥션 대기 38 → **로그인과 상관없는 대기열 폴링까지 멈춘다** (초당 5건)
- 정책값만으로는 안 고쳐진다 (로컬에서 확인, 커밋하지 않음):

  | 바꾼 것 | 200명 폭주 결과 |
  |---|---|
  | 그대로 (동시 32, 대기 3초) | 200명은 버팀, 400명에서 무너짐 |
  | 동시 해시 4개 (`auth.max_concurrent_hash=4`) | **더 나빠짐** — 200명에서 무너짐 (기다리는 로그인이 늘어 스레드가 더 빨리 참) |
  | 대기 0.2초 (코드 임시 변경) | 200명에서 무너짐 (CPU·GC가 여전히 포화) |

- 다만 4코어에 k6까지 같이 돈 결과라, **서버에서 같은 시험을 해서 확정**해야 한다 (아래 3장)

### 고친 것: 로그인 대기실 (GCP 서버 조건 — 해시 4개 고정으로 재현)

GCP 서버는 Argon2 동시 계산을 **4개로 고정**해 쓴다. 지금은 서버 시험이 어려워, 로컬에서 같은 조건(`auth.max_concurrent_hash=4`)을 만들어 재현하고 고쳤다.

- 원인: 해시 자리(4개)를 기다리는 로그인이 **Tomcat 요청 스레드를 붙잡은 채** 최대 3초 기다림 → 스레드 200개가 차면 로그인과 상관없는 API까지 멈춤. 자리 수를 줄이면 오히려 더 빨리 무너진다
- 해결 (`member/login/LoginGate`):
  - 로그인은 **전용 일꾼 4명(= 해시 자리)**이 처리하고, 요청 스레드는 줄에 넣자마자 풀려난다 (서블릿 비동기)
  - 줄(기본 200칸, `jejari.auth.login-queue-capacity`)이 가득 차거나 8초 넘게 기다리면 해시를 계산하지 않고 **429 `AUTH_LOGIN_BUSY` + `Retry-After`(예상 대기 초)**
  - 로그인 화면은 그 초만큼 **카운트다운하며 자동으로 다시 보낸다** (사용자는 다시 누르지 않음)
  - A-10 자원에 "로그인 대기실" 막대, 몰리면 상태 띠에 "알림"

| 해시 4개 · 전원 동시 로그인 | 고치기 전 | **고친 뒤** |
|---|---|---|
| 200명 | **무너짐** — 초당 10건, 5xx 24% | 초당 366건, p95 16ms, 5xx 0% |
| 400명 | (못 감) | 초당 591건, p95 140ms, 5xx 0% |
| 800명 | (못 감) | 초당 740건, p95 322ms, 5xx 0%, 바퀴 실패 2.2% |
| 로그인 자체 | 503으로 실패 | 평균 6.5초(200명) · 15초(400명) · 39초(800명) 걸려도 **성공** |
| Tomcat 스레드 최대 | 200 (전부) | 20 |

p95는 로그인을 뺀 요청(대기열·좌석·조회)의 값이다. 로그인은 몰리면 대기실에서 기다리는 것이 정상 동작이라 "로그인(초)"로 따로 잰다.

### 남은 것 (서버에서 확인 · 팀 결정)

- **로그인 처리 속도**: 로컬(4코어를 k6·DB와 나눠 씀)에서는 해시 4개로 **초당 약 5건**. GCP 서버의 실제 값은 MongoDB `login_attempt.verify_ms`(로그인마다 비밀번호 확인에 걸린 ms)로 바로 알 수 있다. 서버에서:

  ```bash
  docker compose exec -T mongo bash -c 'mongosh --quiet -u "$MONGO_APP_USER" -p "$MONGO_APP_PASSWORD" --authenticationDatabase jejari jejari --eval "db.login_attempt.aggregate([{\$match:{verify_ms:{\$ne:null}}},{\$group:{_id:null,n:{\$sum:1},avg:{\$avg:\"\$verify_ms\"},max:{\$max:\"\$verify_ms\"}}}]).forEach(printjson)"'
  ```

  초당 처리량 ≈ 4 ÷ (평균 ms ÷ 1000). 예: 평균 200ms면 초당 20건 → "오픈 직전 1분에 몇 명이 로그인할까"와 비교
- **오픈 전 미리 로그인** 안내 (로그인 유지·리프레시 토큰은 해시를 안 함) — 오픈 순간의 로그인 수 자체를 줄이는 가장 싼 방법
- 현실에서 "같은 1초에 800명 로그인"은 드물다. 이 시험은 **한도를 넘었을 때 나머지 서비스가 같이 죽지 않는지**를 보는 최악의 경우다. 실제로 몰리는 것은 오픈 순간의 대기열 진입이고, 그것은 대기열이 받는다

## 3. 공용 서버에서 돌리는 순서

> **k6를 서버 안에서 `127.0.0.1:8080`으로 돌린다.**
> 내 PC에서 돌리면 모든 요청이 같은 IP라 가입이 IP당 시간당 최대 100번(`auth.signup_rate_per_hour` 상한)이라 계정을 못 만든다.
> 서버 앱은 `127.0.0.1`을 신뢰 프록시로 두므로(`deploy/jejari@.service`) 서버 안에서는 사람마다 다른 IP(X-Forwarded-For)를 쓸 수 있고, 한도를 올릴 필요가 없다.
> k6도 서버 CPU를 같이 쓰므로 결과는 실제보다 약간 낮게(보수적으로) 나온다.

### 0) 미리 (하루 전)

- 팀 단톡에 **시간 공지** (15~20분, 아무도 서버를 안 쓰는 시간). 시험 중에는 서버가 느려지거나 잠깐 응답하지 않을 수 있다
- 운행: 기본값(운행 9001, 서울 3900023 → 부산 3900114)은 시드의 상시 판매 운행이라 보통 그대로 된다. 안 되면 2)의 사전 점검이 이유를 알려 주고, 그때 판매 중인 운행 번호·정차역 코드를 `-e RUN_ID= -e FROM= -e TO=`로 넣는다
