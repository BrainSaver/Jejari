# [frontend] 이용자 화면이 기기 ID(X-Device-Id)를 보내지 않아 기기 기준 위험 신호가 비어 있었음

| 항목 | 내용 |
|---|---|
| 작성자 | 강동균 |
| 날짜 | 2026-11-18 |
| 상태 | 해결 |
| 관련 커밋 | `fccfa0e` fix(frontend): 이용자 요청에 기기 ID(X-Device-Id)를 붙임 |

## 1. 문제

- **현상**: 브라우저로 예매한 계정은 행동 로그(MongoDB `behavior_log`)의 `device_hash`가 전부 `null`이었다.
  봇 대회 리허설에서 botc(브라우저 봇)를 평가하자 6명의 모두 "기기 정보 없음"으로 나왔다
- **재현 조건**: 화면(React)으로 로그인 → 대기열 → 좌석 → 결제. k6 시나리오는 스스로 헤더를 붙여서 이 문제가 안 보였다
- **영향**: 같은 기기를 여러 계정이 쓰는 다계정 신호가 **브라우저 사용자에게는 아예 걸리지 않았다.**
  위험 점수 설계(ERD `member_device`, `risk_score`의 DEVICE 대상)는 기기 단위로 묶게 되어 있는데, 지금까지의 탐지율 측정은
  전부 헤더를 직접 붙인 k6 봇으로 잰 것이라 이 빈틈이 숫자에 드러나지 않았다

## 2. 원인

- 가설: 서버가 헤더를 버린다 → `BehaviorInterceptor`를 보니 `X-Device-Id`를 형식 검사(영문·숫자·`_-` 8~128자) 뒤 해시해서 남긴다. 서버는 정상
- 확인: `frontend/src/api/client.js`의 `send()`가 만드는 헤더에 `X-Device-Id`가 없다
- **최종 원인**: 화면을 만들 때(2026-11-17) 기기 ID 헤더를 빠뜨렸다. k6 시나리오에서는 `setDevice()`로 붙이고 있어 아무도 몰랐다

```
리허설 c1 (botc 6명의, 고치기 전)  device_missing = 1 × 6
```

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 서버가 User-Agent·IP로 기기를 추정 | 화면 수정 없음 | 같은 회사·같은 브라우저 버전이면 다 같은 기기로 묶임 (오탐) | |
| 화면이 처음 열릴 때 무작위 ID를 만들어 `localStorage`에 저장, 이용자 요청마다 헤더로 | 설계 의도 그대로. 한 브라우저 = 한 기기 | 클라이언트 값이라 봇은 바꾸거나 뺄 수 있음 | ✓ |

- 선택한 이유: 설계가 원래 "클라이언트가 보낸 기기 ID"를 쓰게 되어 있고, 빠진 건 화면이었다. 헤더를 바꾸는 봇은 못 막지만
  "같은 브라우저를 여러 계정이 쓰는" 흔한 경우는 잡는다. 저장소가 막힌 브라우저(사생활 보호 창)는 탭마다 새 ID로 대신한다
- **관리자 요청에는 붙이지 않는다** — 관리자 조회가 이용자 행동 분석에 섞이지 않게
- 바뀐 코드: `frontend/src/api/client.js` `device()`, `send()`

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 브라우저 예매의 행동 로그 중 `device_hash`가 있는 비율 | 0% (botc 6명의 전부 없음) | 100% (대기열·좌석 조회·선점·결제 4종 모두 있음) |

- 측정 환경: 로컬 Docker Compose (클라우드 컨테이너 4코어), 운행 1000005
- 측정 방법: `loadtest/contest/botc/bot.js`로 예매 → `tools/ml/export_live.sh <태그> <폴더>` → `features.py`의 `device_missing`,
  또는 Mongo에서 `event_type`별로 `device_hash` 유무 집계

## 5. 정리

- 면접용 한 줄 요약: "부하 테스트 봇은 기기 ID 헤더를 직접 붙여서 탐지율이 100%로 나왔지만, 실제 화면은 헤더를 안 보내 브라우저
  사용자의 기기 신호가 0%였다. 봇 대회 리허설에서 실제 브라우저로 돌려 보고 발견해, 화면이 기기 ID를 만들어 보내게 고쳤다."
- 다음에 비슷한 상황이면: **측정용 클라이언트(k6)와 실제 클라이언트(화면)가 같은 요청을 보내는지** 먼저 맞춰 본다.
  측정 도구가 실제보다 친절하면 숫자가 실제보다 좋게 나온다
