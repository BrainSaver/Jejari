# [deploy] 새 모델 버전을 등록하면 매시간 점수가 "특징 없음"으로 멈출 뻔함

| 항목 | 내용 |

| 작성자 | 강동균 |
| 날짜 | 2026-11-25 |
| 상태 | 해결 (공용 서버 배포 대기) |
| 관련 커밋·이슈 | `591f387` (main `562b9cd`) |

## 1. 문제

- 현상: 6차 모델 r10을 공용 서버에 버전 `ens-2026.11-03`으로 올리기 전에 서버 스크립트를 읽어 보니, 등록하는 순간 매시간 점수 갱신(`deploy/model-refresh.sh`)이 이 버전에서 `score.py`가 **"features.csv에 모델이 쓰는 특징이 없음"**으로 멈추게 되어 있었다
- 재현 조건: `features.py`를 `ML_STAGE=1`만 켜고 만든 `features.csv`로 r6~r12(운행별 속도 `ML_RUNS`, 한 번에 잡은 좌석 `ML_HOLD`, 기기 연결 시간차 `ML_LINK`를 쓰는 모델)를 매기면 바로 난다
- 영향: 스크립트는 버전 하나라도 실패하면 `fail`로 끝난다 → **꺼진 후보 하나 때문에 사용 중인 버전의 점수까지 그 시간에 안 들어간다**. 관리자 케이스 화면(A-06)의 모델 보조 의견이 통째로 멈춤

## 2. 원인

- 가설 1: 모델 파일(pickle)이 서버 라이브러리 버전과 안 맞음 → 아님. r10과 지금 모델 모두 scikit-learn 1.9.1로 저장됐고, 서버 이미지(`deploy/ml/Dockerfile`)도 1.9.1로 고정
- 가설 2: 서버가 만드는 특징 칸이 모델이 쓰는 칸보다 적음 → **맞음**

```
deploy/model-refresh.sh:  ml "ML_STAGE=1 python -I tools/ml/features.py $OUT"
model-real-r10 features: [..., 'open_to_hold_med_log', 'max_seats_per_hold', 'seats_per_resv']   ← ML_RUNS·ML_HOLD 칸
score.py: missing = [c for c in model["features"] if c not in rows[0]] → sys.exit(...)
```

- 최종 원인: 특징 칸은 환경 변수로 켜는데, 4~6차에서 새 칸(`ML_RUNS`·`ML_HOLD`·`ML_LINK`)을 학습 쪽(`train_real.py`)에만 켜고 서버 점수 스크립트에는 넣지 않았다. 그리고 실패 처리가 "버전 하나 실패 = 전체 실패"였다

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 모델마다 필요한 환경 변수를 `model_run.params`에 적고 버전별로 특징을 따로 만듦 | 정확 | 특징 계산을 버전 수만큼 반복 (매시간 CPU) | |
| **특징은 한 번, 선택 칸을 전부 켜서 만듦** (모델은 자기가 쓰는 칸만 이름으로 꺼냄) | 한 번 계산, 옛 모델 점수 그대로 | 안 쓰는 칸 계산 비용 약간 | ✓ |
| + **꺼진 후보가 실패하면 그 버전만 건너뜀** (사용 중인 버전 실패만 전체 실패) | 후보 하나가 운영 의견을 막지 않음 | 후보 실패를 경고로만 봄 → 로그 확인 필요 | ✓ |

- 선택한 이유: `score.py`가 칸을 **이름으로** 꺼내므로(`model["features"]` 순서대로) 칸이 늘어도 옛 모델이 읽는 값은 같다. 새 칸은 기존 칸 계산을 바꾸지 않고 끝에 붙인다 (`features.py`의 `RUNS`·`HOLD`·`LINK`)
- 바뀐 코드 위치: `deploy/model-refresh.sh` (특징 `ML_STAGE=1 ML_RUNS=1 ML_HOLD=1 ML_LINK=1`, 꺼진 후보 실패 → `경고 … 건너뜀`) · 등록 SQL `deploy/ml/register-ens-2026.11-03.sql`

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| r10 등록 뒤 점수 갱신 | 매시간 실패 (예상) | `모델 점수 갱신: 1개 계정 · ens-2026.11-03` (11-25 조영준 님 서버 확인) |
| 후보 하나가 실패할 때 사용 중 버전 점수 | 그 시간 0건 | 그대로 적재 |

- 측정 환경: 공용 서버 (조영준 님 실행), 로컬은 r10 `model.pkl`의 특징 목록과 서버 스크립트 비교
- 측정 방법: `sudo systemctl start jejari-model` → `journalctl -u jejari-model -n 20`

## 5. 정리

- 면접용 한 줄 요약: "새 모델을 서버에 올리기 전에 운영 스크립트를 따라가 보다가, 서버가 새 특징을 만들지 않아 점수가 멈추고 후보 하나가 운영 중인 버전까지 막는 구조를 찾아, 특징은 한 번에 모두 만들고 후보 실패는 그 버전만 건너뛰게 고쳤다."
- 다음에 비슷한 상황이면: 학습 쪽에 새 입력을 켰으면 **운영에서 그 입력을 만드는 곳**을 같이 찾는다. 여러 개를 도는 배치는 "하나 실패 = 전부 실패"인지 먼저 본다
