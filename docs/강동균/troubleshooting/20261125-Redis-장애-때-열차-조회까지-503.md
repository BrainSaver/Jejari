# [seat] Redis가 죽으면 열차 조회(운행 상세·검색)까지 503

| 항목 | 내용 |
|---|---|
| 작성자 | 강동균 |
| 날짜 | 2026-11-25 |
| 상태 | 해결 |
| 관련 커밋·이슈 | `798dec8` (main `ac5591c`) |

## 1. 문제

- 현상: 장애 주입 시연에서 Redis를 죽였더니 **운행 상세 930건 중 917건이 503**. 열차를 고르는 화면부터 막혀 대기열까지 가지도 못함
- 재현 조건: 앱 + `docker compose up -d` → `loadtest/tools/fault_demo.sh redis` (정상 사용자 30명이 예매를 반복하는 중에 Redis SIGKILL)
- 영향: 문서([Redis 단일 장애점](../features/Redis-단일-장애점.md) 1절)에는 "검색은 Redis를 안 써서 정상"이라고 적혀 있었는데 실제와 달랐음. Redis 장애 = 서비스 전체 장애처럼 보임

## 2. 원인

- 가설: 검색은 Oracle만 쓴다 → 틀림. `TrainQueryService.detail`·`search`가 등급별 **남은 좌석 수**를 `SeatMapService.remainingByGrade`로 구하는데, 이것이 Redis 좌석 키(`seat:hold:*`)와 1초 캐시(`seatmap:*`)를 읽음
- 최종 원인: 남은 좌석 수 하나 때문에 Redis 연결 오류가 조회 API 전체를 503으로 만들었다

```
장애 동안 기능별 (고치기 전)
| 역 목록   | Oracle | 930 | 930 | 0   |
| 운행 상세 | Oracle | 930 | 12  | 917 |   ← 남은 좌석 수를 Redis로 셈
```

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| Redis가 안 되면 남은 좌석을 null(모름)로 | 단순 | 화면에 숫자가 빠짐, 프론트 수정 필요 | |
| Redis가 안 되면 DB `seat_inventory`로 셈 | 응답 모양 그대로, 숫자도 거의 같음 | 유예 중인 키·대기자 보류는 빠져 조금 많게 보일 수 있음 | ✓ |

- 선택한 이유: DB에도 이긴 선점(HOLD)·판매(SOLD)·단체 할당(BLOCKED) 행이 있어 숫자가 거의 같다. 좌석은 선점 때 다시 판정하므로 숫자가 조금 달라도 잘못 팔리지 않는다 (concurrency.md §2). 연결과 상관없는 Redis 오류(스크립트 오류 등)는 숨기지 않고 그대로 던진다
- 바뀐 코드 위치: `src/main/java/com/jejari/seat/SeatMapService.java` (`remainingByGrade` → `fromDb`), 판별은 `RedisExceptionHandler.isUnavailable`(public으로) · 시험 `SeatMapServiceTest`

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| Redis 장애 동안 운행 상세 503 | 917 / 930 | **0 / 865** |
| 장애 동안 실패율 (전체 요청) | 48.4% | 49.3% (대기열·선점 503만 남음 — 그건 정상 동작) |

- 측정 환경: 내 PC (4코어), 앱 1대 + Docker Compose, 정상 사용자 30명
- 측정 방법: `loadtest/tools/fault_demo.sh redis` → `loadtest/results/fault_redis_*/report.md`의 "장애 동안 기능별" 표

## 5. 정리

- 면접용 한 줄 요약: "Redis 장애 시연에서 '남은 좌석 수' 때문에 Redis와 상관없는 열차 조회까지 503이 나는 것을 찾았고, Redis가 안 될 때만 DB로 세게 바꿔 장애 중 조회 실패를 917건에서 0건으로 줄였다."
- 다음에 비슷한 상황이면: "이 API는 X를 안 쓴다"는 문서는 장애를 실제로 주입해 확인한다. 부가 정보(숫자·캐시) 하나가 핵심 API 전체를 묶지 않게, 부가 정보에는 대체 경로를 둔다
