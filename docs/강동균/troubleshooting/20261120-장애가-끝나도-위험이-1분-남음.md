## 1. 문제

- 현상: Redis를 40초 끊었다 다시 켠 뒤, 앱은 2초 만에 회복했는데(마지막 Redis 오류 로그 03:02:18) A-10 상태 띠와 KPI는 **30초 뒤에도 "위험 · 5xx 43%"였고 숫자가 오히려 올라가고 있었다.** 같은 화면의 흐름도는 이미 오류 0%.
- 재현 조건: 부하 중 짧은 장애(수십 초) 후 회복. 기간 "30분" 기준
- 영향: 운영자가 "아직 장애 중"으로 보고 불필요한 조치(재시작·롤백)를 할 수 있다. 같은 화면 안에서 흐름도와 KPI가 서로 다른 말을 한다

## 2. 원인

- 가설 1: 앱이 Redis에 다시 붙지 못했다 → 아님. Prometheus에 직접 `rate(...{status=~"5.."}[15s])`를 물으니 0이었고, 앱 로그의 마지막 Redis 오류는 재시작 2초 뒤
- 가설 2: 화면 값이 오래된 창으로 계산된다 → **맞음**

KPI·상태 판정이 **그래프의 마지막 점**을 썼다. 그래프는 점 간격(30분 기간이면 15초)에 맞춰 `rate(...[60s])`(창 = max(60초, 간격))로 계산하므로, 마지막 점은 "지난 1분 평균"이다. 회복 30초 뒤에도 그 1분 안에는 장애 30초가 들어 있고, 장애 중 k6 요청이 5초 시간 초과로 쌓였다가 한꺼번에 실패 처리되면서 비율이 잠깐 더 올라가 보였다.

```
# 그래프 마지막 점 (회복 30초 뒤)
sum(rate(..._count{status=~"5.."}[60s])) / sum(rate(..._count[60s]))  → 0.43
# 같은 시각 최근 15초
sum(rate(..._count{status=~"5.."}[15s]))                                → 0
```

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 그래프 창을 줄이기 (`[15s]`) | 쿼리 하나로 끝 | 6시간·24시간 기간에서 점 사이 값을 놓침 (창 < 간격) | |
| "지금" 값·상태만 따로 `[30s]` 순간 쿼리 | 그래프는 정확, 지금 값은 빠름. 흐름도와 같은 창이라 서로 맞음 | 쿼리 4개 추가 (Prometheus에 가벼움) | ✓ |
| 창을 더 줄이기 (`[10s]`) | 더 빠름 | 수집 5초라 점이 2개뿐 → 값이 튐, 상태가 깜빡임 | |

- 선택한 이유: 그래프는 "흐름", KPI·상태는 "지금"이라 목적이 다르다. 30초는 수집 6번이라 튀지 않으면서 회복을 30~45초 안에 보인다
- 바뀐 코드: `src/main/java/com/jejari/admin/traffic/TrafficService.java` — `nowStatus`·`now50/95/99` 순간 쿼리와 `mix()`. 테스트 `TrafficServiceTest.장애가_끝나면_30초_안에_정상으로_돌아온다`

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| Redis 회복 30초 뒤 상태 띠 5xx | 43% (올라가는 중) | 12% (내려가는 중) |
| 정상으로 돌아올 때까지 | 약 60~75초 | 약 30~45초 |
| 흐름도와 KPI의 창 | 30초 / 60초 (서로 다름) | 30초 / 30초 |

- 측정 환경: 로컬 docker compose + 앱 1대, Prometheus 수집 5초
- 측정 방법: [흐름도 이름표 문서](20261120-흐름도-이름표가-첫-값에-멈춤.md)와 같은 k6 부하 + `docker compose stop redis` 40초. 회복 뒤 30초에 A-10 상태 띠 읽기
