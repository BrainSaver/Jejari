# [train] 시연 운행이 3일 뒤 출발해, 지나면 DEPARTED로 예매가 막힘

| 항목 | 내용 |
|---|---|

| 날짜 | 2026-11-18 |
| 상태 | 해결 |
| 관련 커밋·이슈 | 원인 `b82f219`(DEPARTED 전이) · 수정은 이 커밋 |

## 1. 문제

- 현상: 공용 서버에서 **11/21(금) 09:00부터 운행 9001 예매 불가**. 로컬도 같다
  (볼륨을 만든 날 + 3일 09:28에 출발).
- 재현 조건: 시드를 넣고 3일이 지나기만 하면 된다. 특별한 요청도, 동시성도 필요 없다.
- 영향: 좌석 선점(RSV-02)·결제·취소·대기열 테스트가 **전부** 쓰는 운행이 9001이다.
  막히면 기능 테스트를 아예 못 돌린다. 지금까지는 **DB를 다시 만드는 것**이 유일한 방법이었고,
  그때마다 회원·예약이 지워졌다 (조영준 님이 서버 공지에 "그 전에 제가 다시 만들게요
  (데이터 초기화)"라고 적어 둔 것이 이것이다).

## 2. 원인

두 가지가 겹쳤다. 하나만으로는 문제가 되지 않았다.

**(1) 시드의 운행일이 "넣은 날 + 3일"이었다** — `db/seed/04_regular_run.sql`

```sql
-- 지금 판매 중: 출발 3일 뒤 → 오픈은 약 두 달 전이라 이미 지났음
SELECT 9001 AS run_id, 1 AS train_id, TRUNC(SYSDATE) + 3 AS run_date FROM dual
```

`+3`을 고른 이유는 **예매 오픈**이었다. 코레일 규칙대로 오픈은 출발 2개월 전이라,
운행일이 가까워야 오픈이 과거가 되어 `ON_SALE`이 된다. 출발이 언제인지는 생각하지 않았다.

**(2) 내가 그날 아침 DEPARTED 전이를 붙였다** — `SaleOpenScheduler`

`DEPARTED`는 그때까지 아무도 쓰지 않는 죽은 상태값이었다. 스케줄러가 맡게 하면서,
기점 출발 시각이 지난 운행을 전부 `DEPARTED`로 바꾸게 했다. 그 순간부터 (1)의 `+3`이
"3일 뒤면 시연이 멈춘다"는 뜻이 되었다. **값을 쓰는 사람이 생기자 데이터의 가정이 깨졌다.**

로컬에서 확인한 모습 — 고치기 전:

```
    RUN_ID RUN_DATE     OPEN_AT            STATUS
      9001 2026-11-20   2026-09-20 07:00   ON_SALE     ← 모레 09:28 출발
      9002 2026-11-20   2026-09-20 07:00   ON_SALE
      9003 2027-01-18   2026-11-18 07:00   ON_SALE     ← SCHEDULED여야 하는데 이미 열려 버렸다
```

9003도 같은 병이다. "오픈이 내일 07:00"이라 오픈 스케줄러 시연용이었는데, 하루가 지나
그냥 `ON_SALE`이 되어 있었다. 이쪽은 아무것도 막지 않아서 아무도 몰랐다.

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| A. 운행일을 멀리 둔다 (+45일) | 한 줄. 규칙(오픈 2개월 전)을 그대로 지킨다 | 기간이 길어지면 또 묵는다 | ✓ |
| B. DEPARTED 전이를 되돌린다 | 즉시 해결 | 기능을 버린다. 실제로는 출발한 열차를 팔면 안 된다 | |
| C. 시연용으로 DEPARTED를 끈다 (플래그) | 시연이 안 멈춘다 | 끄고 쓰는 기능은 검증되지 않는다 | |
| D. 스케줄러가 묵은 운행을 자동으로 밀어 준다 | 영원히 안 묵는다 | 운영 코드가 시연을 위해 데이터를 고친다. 선 넘는다 | |

A를 고르되, **A만으로는 부족**했다. 이미 묵어 버린 DB(= 공용 서버)를 살릴 수 없기 때문이다.

### 핵심: 시드를 다시 돌리면 날짜가 갱신되게 했다

원래 `WHEN MATCHED`가 `status`만 갱신했다. 그래서 04를 다시 돌려도 **운행일은 그대로**였고,
이미 출발한 운행은 되살릴 수 없어 DB를 지우는 수밖에 없었다.

```sql
WHEN MATCHED THEN
  -- 날짜까지 덮어씁니다. 예약은 run_id로 매달려 있어 열차와 함께 밀립니다.
  UPDATE SET t.run_date = s.run_date, t.sale_open_at = s.sale_open_at,
             t.sale_close_at = s.sale_close_at, t.status = s.status,
             t.updated_at = SYSTIMESTAMP
```

05가 정차 시각을 `run_date`에서 다시 만들므로(이미 `WHEN MATCHED`로 갱신한다),
**04 → 05만 다시 돌리면 창이 앞으로 밀린다. 지우는 것이 없다.**

### 다시 안 당하게: 시드 검증에 항목을 하나 더

이 함정은 "어느 날 갑자기 테스트가 깨진다"는 모습으로만 드러난다. 원인이 *시각*이라
실패 메시지를 봐도 알 수 없다 (11-17 시퀀스 누락, 11-18 v24 CHECK 누락도 같은 종류였다).
그래서 사람이 눈치채기 전에 시드 검증이 먼저 말하게 했다 — `99_verify.sql` 24번:

```sql
SELECT '24. 평시 운행이 7일 넘게 남음', CASE WHEN COUNT(*) = 0 THEN 1 ELSE 0 END,
       '곧 출발/출발함 ' || COUNT(*) || '건 → 04·05 다시 돌리세요'
  FROM train_run WHERE sale_event_id IS NULL AND run_date < TRUNC(SYSDATE) + 7
```

- 바뀐 코드 위치: `db/seed/04_regular_run.sql`, `db/seed/99_verify.sql`

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 시연이 멈추기까지 | **3일** | **45일** (발표 2026-12-05 + 28일) |
| 되살리는 방법 | DB 재생성 (회원·예약 전부 삭제) | 시드 04 → 05 재실행 (삭제 없음) |
| 묵었을 때 알아차리는 방법 | 테스트가 깨진 뒤 원인 추적 | 시드 검증 24번이 FAIL |
| 시드 검증 | 23항목 | **24항목 전부 OK** |

적용 후:

```
      9001 2027-01-02   2026-11-02 07:00   ON_SALE      ← 45일 뒤 출발
      9002 2027-01-02   2026-11-02 07:00   ON_SALE
      9003 2027-01-19   2026-11-19 07:00   SCHEDULED    ← 오픈 스케줄러 시연이 되살아났다
```

- 측정 환경: 로컬 Docker Compose (Oracle Free 23c), 시드 11건 운행
- 측정 방법: `04` → `05` → `99_verify.sql` 재실행 후 `train_run` 조회.
  영향 테스트 65개(스케줄러·좌석결제·취소·좌석배치도·예매흐름·관리자) 통과

## 5. 정리

- 면접용 한 줄 요약: "죽어 있던 `DEPARTED` 상태를 스케줄러에 맡겼더니, 시드의 '출발 3일 뒤'라는
  가정이 깨져 3일마다 시연이 멈췄다. 운행일을 45일로 늘리고 시드 MERGE가 날짜까지 갱신하게 바꿔
  DB를 지우지 않고 되살릴 수 있게 했으며, 같은 일이 조용히 반복되지 않도록 시드 검증에 감지 항목을 넣었다."
- 다음에 비슷한 상황이면: **죽은 상태값에 소유자를 만들 때, 그 값에 기대지 않고 만들어진
  기존 데이터를 먼저 찾는다.** 기능은 멀쩡했고 깨진 건 데이터의 가정이었다.
  그리고 **상대 날짜로 만든 시드는 반드시 "얼마나 버티나"를 따져 본다.**
