# [behavior] Kafka가 멈춘 채 앱이 재시작(배포)되면 행동 로그 70%가 사라짐

| 항목 | 내용 |
|---|---|
| 작성자 | 강동균 |
| 날짜 | 2026-11-20 |
| 상태 | 해결 |
| 관련 커밋·이슈 | 행동 로그 디스크 버퍼 커밋 (`SpillBuffer`, `BehaviorPublisher`) |

## 1. 문제

- 현상: 초당 1,500건 검색 중 Kafka를 멈추고 10초 뒤 앱을 종료(SIGTERM, 배포 재시작과 같음) → 응답한 요청 **42,743건 중 29,919건(70%)의 행동 로그가 MongoDB에 없음**. 어떤 지표에도 안 잡힘 (버림 1건)
- 종료에 **47초** 걸림 → 서버라면 `TimeoutStopSec=40`에서 강제 종료(SIGKILL)
- 재현: `docker pause jejari-kafka-1` → `kill -TERM <앱>` → 다시 띄운 뒤 `behavior_log`에서 그 검색 태그 개수 세기 (k6 `constant-arrival-rate` 1,500/초, 400 응답 수 = 로그 수)
- Kafka가 정상일 때 같은 재시작은 유실 0 (24,820 = 24,820) — 그래서 지금까지 안 보였다
- 영향: 봇 탐지 재료가 판매 오픈처럼 몰리는 순간에 통째로 빈다. 자동 배포가 몇 분마다 앱을 재시작하므로 Kafka가 잠깐 느린 때와 겹치면 언제든 생긴다

## 2. 원인

세 가지가 겹쳤다.

```java
// ① 종료 때 큐를 5초만 기다리고 남은 것은 버림 (큐는 최대 5만 건)
sender.shutdown();
sender.awaitTermination(5, TimeUnit.SECONDS);

// ② Kafka가 멈추면(응답 없음) 메시지마다 max.block.ms=2초씩 붙잡힘 → 초당 0.5건만 빠짐 → 큐가 계속 쌓임
props.put(ProducerConfig.MAX_BLOCK_MS_CONFIG, 2000);
```

- ③ 종료 단계 대기 기본 30초: Kafka 소비자 단계가 Kafka를 기다리며 30초를 다 쓰고, 그동안 웹은 요청을 계속 받아 큐에 더 쌓음 → 47초
- 11-20 오전 점검표에서 "보내는 쪽 디스크 버퍼는 필요 낮음"으로 판단했다. Kafka 40초 **정지(stop)** 시험에서 0건이었기 때문인데, stop은 연결이 바로 거절돼 빨리 실패하고, **멈춤(pause, 응답 없음)** 과 **재시작**이 겹치는 경우는 재지 않았다

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 종료 대기만 늘리기 | 간단 | Kafka가 멈춰 있으면 아무리 기다려도 안 빠짐, 서버 강제 종료 40초에 걸림 | |
| 메모리 큐 키우기 | 간단 | 재시작하면 어차피 사라짐 | |
| **디스크 버퍼 + 회로 차단** | 재시작·긴 장애에도 남음, 회복하면 자동으로 다시 보냄 | 파일 관리 코드, 중복 전송(적재 쪽 event_id로 걸러짐) | ✓ |

- `SpillBuffer`: 못 보낸 로그를 `~/.jejari/behavior-spill/<포트>/spill-*.jsonl`에 한 줄씩(줄마다 flush, 권한 600, 상한 512MB)
- **회로 차단**: 전송이 한 번 실패하면 5초 동안 Kafka를 부르지 않고 바로 디스크로 → 메시지마다 2초씩 붙잡히지 않음
- 5초마다 회로가 닫혔고 큐가 한가하면 오래된 파일부터 다시 큐에 넣고, 다 넣으면 지움
- 종료: 큐를 최대 8초 비우고(Kafka가 멈춰 있으면 기다리지 않음) 남은 것은 디스크로, 프로듀서는 2초 안에 닫아 못 보낸 묶음도 실패 콜백으로 디스크로
- `spring.lifecycle.timeout-per-shutdown-phase: 30s → 10s` — 최악 합계 33초 < 40초
- 버림(`dropped`)·실패(`failed`)는 이제 **디스크에도 못 적은 진짜 유실**만 센다 → 기존 Discord 경보(`jejari-behavior-loss`)를 그대로 써서 경보 규칙 파일을 바꾸지 않음 (자동 배포가 멈추지 않게)
- 새 지표: `jejari_behavior_spilled_total`·`replayed_total`·`spill_bytes`

## 4. 수치

| 시험 (초당 1,500 검색) | 개선 전 | 개선 후 |
|---|---|---|
| Kafka 멈춘 채 재시작 | 42,743건 중 **29,919건 유실 (70%)**, 종료 47초 | 43,534건 중 **0건**, 종료 **19초** |
| Kafka 정상 재시작 | 0건 (24,820) | 0건 (29,014), 종료 2초 |
| Kafka 45초 멈춤 (재시작 없음) | — (메시지마다 2초 → 큐 5만 넘칠 상황) | 87,906건 중 **0건**, 버림·실패 0 |
| 단위·통합 테스트 | — | 단위 516 전부 통과, 행동 로그 통합 7 통과 |

- 측정 환경: 로컬 docker compose (Oracle·MongoDB·Kafka·Redis) + 앱 1대(jar) + k6, 4코어 컨테이너 하나
- 측정 방법: 검색 태그를 시험마다 바꿔(`from=<태그>`) k6의 400 응답 수와 `behavior_log`의 `meta.fromStationId=<태그>` 개수를 비교. 디스크로 30,018건 → 다음 기동 때 파일 4개에서 6,691 + 14,275 + 8,287 + 765 = 30,018건 다시 보냄

## 5. 정리

- 면접용 한 줄 요약: "Kafka가 멈춘 채 배포가 겹치면 메모리 큐에 있던 행동 로그 70%가 조용히 사라졌다. 디스크 버퍼와 회로 차단을 넣고 종료 시간을 서버 강제 종료 한도 안으로 줄여, 같은 시험에서 유실을 0으로 만들었다."
- 다음에 비슷한 상황이면:
  - 장애 시험은 **멈춤(stop)과 응답 없음(pause)을 둘 다** 한다. 클라이언트가 실패하는 속도가 완전히 다르다
  - 메모리에 쌓는 구조는 **재시작**을 꼭 같이 시험한다. 배포가 잦으면 재시작이 가장 흔한 "장애"다
  - 종료 순서·시간을 서버의 강제 종료 한도와 같이 계산한다
  - "필요 낮음"으로 미룬 항목도 근거가 된 시험이 무엇을 빠뜨렸는지 다시 본다
