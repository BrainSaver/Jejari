# [seat] Redis가 잠깐 죽으면 좌석 정리 이벤트가 다시 시도 없이 바로 격리 보관됨

| 항목 | 내용 |
|---|---|
| 작성자 | 강동균 |
| 날짜 | 2026-11-27 |
| 상태 | 해결 (로컬 장애 주입으로 확인) |
| 관련 커밋·이슈 | 이 문서와 같은 커밋 (`SeatReleaseConsumer.transientInfra`) |

## 1. 문제

- 현상: 발표 캡처용으로 장애 주입(`loadtest/tools/fault_demo.sh redis`, 20명, Redis 45초 정지)을 돌렸더니, 복구 뒤에도 A-10 상태 띠가
  초록으로 안 돌아오고 "격리 보관 47건"(주의)이 5분 동안 남았다. `jejari_dead_letter_total{group="seat-release",reason="handler_failed"}` = 47
- 재현 조건: Redis가 죽어 있는 동안 결제 전 취소·선점 만료가 생기면 된다 (10명으로 다시 해도 3건)
- 영향: `seat-release`는 커밋 뒤 Redis 정리의 **보장 경로**다 (concurrency.md §14.3). 여기서 빠지면
  - 그 좌석의 Redis 키가 만료(마감 + 유예, 약 10분)까지 남아 **빈 좌석인데 아무도 못 산다**
  - 그 좌석의 **취소표 제안(§9)이 사라진다** — 대기자에게 갈 표가 그냥 일반 판매로
  - 매수 한도 키가 안 줄어 다음 선점이 한도에 걸릴 수 있다 (거절 때 DB 대조로 스스로 고쳐지긴 함, §10.7)
  - 사람이 `tools/dlq.sh replay`로 다시 넣을 때까지 그대로

## 2. 원인

- 처음 가설: 컨테이너 재시도(5초 간격 무제한, `DefaultErrorHandler(FixedBackOff)`)가 45초를 못 버텼다 → 아니었다. 재시도까지 가지도 않았다
- `SeatReleaseConsumer.consume()`이 `handle()`의 **모든 예외를 잡아 곧바로 격리 보관**하고 다음 메시지로 넘어갔다.
  예외가 컨테이너로 안 올라가니 컨테이너의 재시도 설정이 한 번도 쓰이지 않았다. 11-20 격리 보관함을 넣을 때
  "한 건 실패가 나머지를 막지 않게"만 생각하고, 잠깐의 연결 장애와 다시 해도 같은 실패를 나누지 않았다
- 최종 원인: 일시적 장애(Redis 연결 끊김)도 영구 실패처럼 다뤘다

```
dlt-group:seat-release,dlt-reason:handler_failed,dlt-error:RedisSystemException: Redis exception
Caused by: io.lettuce.core.RedisException: Connection disconnected
값 {"eventType":"RESERVATION_CANCELED", ... "reason":"USER_BEFORE_PAY"}   ← 장애 중 결제 전 취소
```

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 그대로 두고 운영자가 `dlq.sh replay` | 코드 그대로 | 장애마다 사람 손, 그동안 좌석·취소표가 멈춤 | |
| 모든 예외를 컨테이너로 올려 재시도 | 간단 | 다시 해도 같은 실패(버그·Lua 오류)가 파티션을 영원히 막음 | |
| **연결 장애만 다시 시도, 나머지는 지금처럼 격리 보관** | 장애가 끝나면 저절로 처리, 버그는 막지 않음 | 장애 동안 그 파티션이 기다림 (Redis가 없으면 어차피 처리 불가) | ✓ |

- 연결 장애 판단(`transientInfra`): 원인 사슬에 Lettuce `RedisException`(명령 오류 `RedisCommandExecutionException`은 제외) ·
  `RedisConnectionFailureException` · `RedisConnectionException` · `RedisCommandTimeoutException` · Spring `TransientDataAccessException` ·
  `DataAccessResourceFailureException`(DB 커넥션 못 얻음 포함) · `ConnectException`
- 그러면 `BatchListenerFailedException(인덱스)`를 던진다 → 컨테이너가 그 메시지 **앞까지만 커밋**하고 5초마다 그 메시지부터 다시 준다.
  처리는 inbox로 멱등이라 다시 돌려도 결과가 같다
- 바뀐 코드: `src/main/java/com/jejari/waitlist/offer/SeatReleaseConsumer.java`, 테스트 `SeatReleaseTransientTest` (3개)

## 4. 수치

같은 조건(10명, Redis 50초에 죽이고 45초 뒤 살림, 운행 1000004):

| 지표 | 고치기 전 | 고친 뒤 |
|---|---|---|
| seat-release 격리 보관 | 3건 (20명일 때 47건) | **0건** |
| 장애 동안 | 바로 보관함으로 | 같은 메시지를 약 5초마다 13번 다시 → Redis 복구 뒤 처리 |
| 정합성 점검 10항목 | 통과 | 통과 |
| A-10 상태 띠 | 복구 뒤 5분 동안 주의 | 복구 뒤 초록 |

## 5. 배운 점

- 격리 보관함은 "다시 해도 안 되는 것"을 치우는 곳이다. 잠깐의 장애까지 넣으면 장애가 끝나도 일이 멈춘다
- 장애 주입은 "그 순간 버티나"만이 아니라 **끝난 뒤 저절로 돌아오나**까지 봐야 한다. 이번엔 정합성 점검은 통과했는데 관제 화면이 알려 줬다
- 남은 것: 같은 "모든 예외 → 바로 보관" 모양이 다른 소비자에도 있는지 (notification·risk-signal·behavior-sink) 확인
