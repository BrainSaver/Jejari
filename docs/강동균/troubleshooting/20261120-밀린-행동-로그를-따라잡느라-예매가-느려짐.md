# [behavior] MongoDB 장애 뒤 밀린 행동 로그를 따라잡느라 예매가 3배 느려짐

| 항목 | 내용 |
|---|---|
| 작성자 | 강동균 |
| 날짜 | 2026-11-20 |
| 상태 | 해결 (상한값은 서버 실측 뒤 조정) |
| 관련 커밋·이슈 | 행동 로그 적재 속도 상한 커밋 (`SinkPacer`) |

## 1. 문제

- 현상: MongoDB가 멈춘 사이 행동 로그 50만 건이 Kafka에 밀렸다가, 예매 150명이 몰리는 중에 MongoDB가 돌아오자
  좌석 선점 p95가 **217~222ms → 631~633ms**(최대 1.53초), 결제 p95 140~164 → 424~563ms로 느려짐
- 재현: `docker pause jejari-mongo-1` → 행동 로그 50만 건을 Kafka에 → `./run.sh journey -e USERS=150 -e SPREAD_SEC=10` 시작 3초 뒤 `docker unpause`
- 영향: 판매 오픈 중 MongoDB·Kafka가 잠깐 멈췄다 돌아오거나, 디스크 버퍼를 다시 보낼 때 예매가 느려진다. 행동 로그(부가 기능)가 예매(핵심 기능)를 늦춘다

## 2. 원인

- 처음 가설은 "적재가 Oracle 커넥션을 쥐어 예매가 커넥션을 못 얻는다"였다. 적재가 묶음마다 Oracle을 쓰기 때문(CI 찾기, 기기 연결 MERGE)
- 재 보니 **커넥션 대기는 모든 경우 0**. 커넥션은 최대 19/20까지 썼지만 기다린 요청은 없었다
- 진짜 원인은 **CPU**: 적재는 초당 최대 약 3만 건까지 되고, 밀린 것이 있으면 그 속도를 다 낸다. 4코어에 앱·Oracle·MongoDB·Kafka가 같이 있어
  CPU가 100%가 되고 예매 요청이 CPU를 기다린다 (서버 VM도 같은 구성)

```java
// 밀린 것이 있으면 poll → insertMany → poll …을 쉬지 않고 반복. 속도를 정하는 것이 없었다
@KafkaListener(id = "behavior-sink", ...)
public void consume(List<ConsumerRecord<String, String>> records) { ... insert(docs); ... }
```

- 첫 시험(Kafka에 50만 건을 넣으면서 동시에 예매)은 **넣는 쪽 부하가 섞여** 상한을 걸어도 안 좋아진 것처럼 보였다.
  실제로는 밀림이 "장애 뒤 복구"로 생기므로, MongoDB를 멈춰 먼저 쌓아 두고 예매 중에 풀어 주는 방식으로 다시 쟀다

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 소비자 수 줄이기 (3 → 1) | 간단 | 평소에도 느려지고, 1개도 CPU를 꽤 씀 | |
| 적재 전용 커넥션 풀 | 커넥션 경쟁 제거 | 원인(CPU)이 아님 — 대기 0 | |
| **적재 속도 상한 (초당 2,000)** | 평소엔 영향 없음, 따라잡기만 천천히 | 밀림을 다 따라잡는 데 더 오래 (50만 건 약 4분) | ✓ |

- `SinkPacer`: 소비자 스레드 전체가 나눠 쓰는 시간표. 다음 묶음이 시작할 수 있는 시각을 앞으로 미루고 그만큼 잔다. 한가했던 시간은 1초까지만 모아 둔다
- 상한 2,000의 근거: 평소 유입은 예매 150명 몰림에 초당 최고 약 100건(1인 약 4건) → 800명이면 약 530건. 그 약 4배라 평소엔 기다리지 않는다
- 밀림 경보(10만 건 · 5분)가 울리지 않는 범위: (50만 - 10만) ÷ (2,000 - 530) ≈ 4.5분
- 설정 `jejari.behavior.sink-max-per-sec` (application.yml 기본값 없음 → 코드 기본 2000). app_policy로 두면 관리자가 바로 바꿀 수 있지만 ERD 패치가 필요해 (자동 배포가 멈춤) 이번엔 설정값으로

## 4. 수치

| 상한 | 좌석 선점 p95 (예매만 → 따라잡는 중) | 결제 p95 | 따라잡는 시간 (50만 건) |
|---|---|---|---|
| 없음 (2회) | 217~222 → 631~633ms (약 2.9배) | 140~164 → 424~563ms | 약 20초 |
| 5,000 (2회) | 143~226 → 385~420ms | 110~123 → 289~332ms | 약 100초 |
| **2,000** | 264 → **339ms (약 1.3배)** | 152 → 287ms | 약 4분 |

- 측정 환경: 로컬 4코어 컨테이너 하나에 앱(jar)·Oracle Free·MongoDB·Kafka·Redis·k6
- 측정 방법: 회차마다 같은 열차의 빈 운행(100026~100046)을 써서 "예매만" 기준선과 "따라잡는 중"을 번갈아 잼. 예매 성공률은 모두 100%
- 단위 520 · 행동 로그 통합 7 통과

## 5. 정리

- 면접용 한 줄 요약: "장애 뒤 밀린 행동 로그를 최대 속도로 따라잡느라 CPU가 100%가 되어 예매가 3배 느려졌다. 커넥션 풀을 의심했지만 대기 0으로 아니었고, 적재 속도 상한을 평소 유입의 약 4배로 걸어 따라잡는 동안의 지연을 1.3배로 줄였다."
- 다음에 비슷한 상황이면:
  - 가설(커넥션 풀)부터 고치지 말고 **대기 지표를 먼저 본다**. 이번엔 대기 0이라 엉뚱한 곳을 고칠 뻔했다
  - 부하 시험은 **실제 상황의 순서**대로 재현한다 (장애로 쌓임 → 복구 중 풀림). "넣으면서 동시에"는 넣는 쪽 부하가 섞인다
  - 부가 기능(로그·통계)은 핵심 기능(예매)과 같은 CPU를 쓰면 **속도 상한**을 둔다. 따라잡기는 늦어도 되지만 예매는 늦으면 안 된다
