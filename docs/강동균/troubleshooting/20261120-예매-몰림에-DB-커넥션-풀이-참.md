# [db] 예매가 몰리면 DB 커넥션 풀(10개)이 차서 선점·결제가 줄을 섬

| 항목 | 내용 |
|---|---|
| 작성자 | 강동균 |
| 날짜 | 2026-11-20 |
| 상태 | 해결 |
| 관련 커밋·이슈 | `b99c043` perf(db): 커넥션 풀 10 → 20, 연결 대기 30초 → 5초 |

## 1. 문제

- 현상: 300명이 10초 안에 예매(로그인 → 대기열 → 좌석 선점 → 결제)하면 Hikari 커넥션 10개가 모두 쓰이고 요청이 줄을 섰다. 좌석 선점 p95 1.7~2.8초
- 재현 조건: `cd loadtest && ./run.sh journey -e USERS=300 -e SPREAD_SEC=10`, 기본 풀(`maximum-pool-size` 미설정 = 10)
- 영향: 명절 오픈 직후처럼 한꺼번에 몰릴 때 선점·결제가 느려짐. 데이터는 어긋나지 않음 (정합성 점검 전부 OK)

## 2. 원인

- 5초마다 Prometheus를 찍어 보니 몰린 순간 `hikaricp_connections_active` 10/10, `pending` 9~39
- 풀 크기를 정하지 않아 Spring Boot 기본값 10이었다
- **처음 측정은 틀렸다**: 풀 10은 "막 띄운 앱"에서, 풀 30은 "데운 앱"에서 재서 2.8초 → 1.36초(절반)로 보였다. 같은 조건(DB·Redis 새로, 1.5분 데우기)으로 다시 재니 개선 폭은 25~30%였다. 막 띄운 앱은 JIT·커넥션 생성 때문에 첫 몰림에서 훨씬 느리다

```
같은 조건 (데운 앱, 300명 10초 몰림)
풀 10: hold p95 1.73s (max 2.94s), pay p95 1.00s, seat_map p95 1.07s, pending max 9
풀 20: hold p95 1.26s (max 1.70s), pay p95 0.85s, seat_map p95 0.73s, pending max 0
풀 30 (참고): 실제 사용 최대 18
```

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 그대로 10 | — | 몰림에 줄 섬 | |
| 30 이상 | 여유 | Oracle Free는 CPU 2개라 DB 안에서 줄만 섬. 실제 사용 최대 18 | |
| **20 + 연결 대기 5초** | 몰림에 대기 0, Oracle processes 200 안 (앱 2대여도 40) | 테스트처럼 컨텍스트가 많으면 연결 수가 커짐 → 테스트는 따로 | ✓ |

- `application.yml`: `maximum-pool-size: 20`, `connection-timeout: 5000` (풀이 차면 30초씩 요청 스레드를 쥐지 않게 — 로그인 폭주 때와 같은 원리)
- **곁가지로 생긴 문제**: Hikari는 기본으로 쉬는 연결도 최대치만큼 유지한다(`minimum-idle` = `maximum-pool-size`). 통합 테스트는 Spring 컨텍스트를 20여 개 띄워 두므로 20 × 20여 개 > Oracle processes 200 → 통합 테스트 43개가 연결을 못 얻음 (`ORA-17800`). `build.gradle`에서 테스트만 풀 10·쉬는 연결 2로
- 서버 Oracle 한도는 같은 이미지(`gvenzl/oracle-free:23-slim-faststart`)로 확인: processes 200, sessions 322, CPU 2, 평소 내부 세션 약 79

## 4. 수치

| 지표 | 개선 전 (풀 10) | 개선 후 (풀 20) |
|---|---|---|
| 좌석 선점 p95 / 최대 | 1.73초 / 2.94초 | 1.26초 / 1.70초 |
| 좌석 배치도 p95 | 1.07초 | 0.73초 |
| 커넥션 대기 최대 | 9 | 0 |
| 예매 성공 · 정합성 | 300/300 · OK | 300/300 · OK |
| 통합 테스트 | — | 474/475 (남은 1건은 날짜 경계, 무관) |

- 측정 환경: 로컬 4코어 컨테이너 하나에 앱·Oracle Free·Kafka·MongoDB·Redis·k6
- 측정 방법: 매번 Oracle·Redis를 새로 만들고 → 용량 시험으로 1.5분 데우기 → `./run.sh journey -e USERS=300 -e SPREAD_SEC=10` → `loadtest/tools/check_booking.sh` (`docs/강동균/용량-시험-안내.md` "예매 쪽 데이터 처리")

## 5. 정리

- 면접용 한 줄 요약: "예매 몰림에서 커넥션 풀 10이 다 차 요청이 줄을 섰다. Oracle 한도(processes 200, CPU 2)와 실제 최대 사용량(18)을 재서 20으로 맞추고 대기 시간을 5초로 줄여, 같은 조건에서 커넥션 대기를 0으로, 선점 p95를 25~30% 줄였다."
- 다음에 비슷한 상황이면:
  - 비교 실험은 **조건을 같게** (막 띄운 앱 vs 데운 앱을 섞으면 개선 폭이 두 배로 부풀려진다)
  - 풀은 크게가 아니라 **실제 최대 사용량 + 약간**. DB CPU가 적으면 더 키워도 DB 안에서 줄만 선다
  - 풀 설정을 바꾸면 **테스트 쪽 연결 총량**도 본다 (컨텍스트 수 × 풀)
  - 배포 직후 첫 몰림이 가장 약하다 → 판매 오픈 직전에는 배포하지 않기
