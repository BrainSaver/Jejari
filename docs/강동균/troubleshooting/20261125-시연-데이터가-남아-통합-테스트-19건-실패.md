# [loadtest] 장애 시연이 남긴 예약 때문에 통합 테스트 19건 실패

| 항목 | 내용 |
|---|---|
| 작성자 | 강동균 |
| 날짜 | 2026-11-25 |
| 상태 | 해결 |
| 관련 커밋·이슈 | `986fe97` (시연 스크립트가 스스로 정리) |

## 1. 문제

- 현상: 오전에 전체 통과(556개)하던 `./gradlew infraTest`가 장애 시연 뒤 **19건 실패**. 모두 같은 메시지 `BusinessException: 다른 사람이 먼저 선택한 좌석입니다.`
- 재현 조건: `loadtest/tools/fault_demo.sh redis`(또는 kafka)를 돌린 뒤 같은 PC에서 `SeatReleaseInfraTest`·`WaitlistOfferInfraTest`
- 영향: 코드에는 문제가 없는데 테스트가 깨져 "방금 고친 코드가 망가뜨렸나"를 헷갈리게 함

## 2. 원인

- 가설 1: 새로 쓴 테스트끼리 좌석이 겹침 → 아님 (테스트마다 시작 전에 자기 데이터를 지움)
- 가설 2: 다른 데이터가 운행 9001 좌석을 차지 → 맞음

```sql
SELECT COUNT(*) FROM seat_inventory WHERE run_id = 9001;                 -- 270
-- 그중 오늘 만든 @loadtest.example.com 회원의 예약 좌석                   -- 270 (전부)
```

- 최종 원인: 시연(k6 시나리오 14)은 회원마다 3장까지 결제한 표를 남긴다 (30명 × 3번 시연 = 270석). 통합 테스트도 운행 9001의 정해진 좌석을 쓰는데, 시연이 무작위로 산 좌석과 겹쳤다. 테스트는 자기가 만든 회원(ID 대역)의 데이터만 지우므로 시연 데이터는 남아 있었다

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 테스트가 시작할 때 운행 9001을 통째로 비움 | 확실 | 팀원이 로컬에서 만든 데이터까지 지움 | |
| 시연을 다른 운행으로 | 겹치지 않음 | 시드의 상시 판매 운행이 9001·9002뿐이고 9002도 테스트가 씀 | |
| **시연이 끝나면 자기가 만든 예약만 지움** (회원 이메일 `lt{태그}x…`로 찾음) | 시연 결과(보고서)는 남고 DB는 원래대로 | 남겨서 보고 싶으면 `KEEP=1` | ✓ |

- 이번에 남은 데이터: 오늘 만든 시연 회원의 운행 9001 예약 4,327건(결제 270석)과 딸린 행(결제·이력·Saga·좌석·outbox·알림·카운터), 앱 Redis의 9001 좌석 키를 지움
- 바뀐 코드 위치: `loadtest/tools/fault_demo.sh` 끝의 "정리" 단계

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 시연 뒤 운행 9001 좌석 행 | 270 | 0 |
| 통합 테스트 | 19건 실패 | 전체 564개 통과 |

- 측정 방법: 위 SQL, `./gradlew test infraTest`

## 5. 정리

- 면접용 한 줄 요약: "부하 시연과 통합 테스트가 같은 운행 좌석을 쓰면서 시연 데이터가 테스트를 깨뜨렸고, 시연이 자기 데이터를 스스로 지우게 해 같은 PC에서 둘을 번갈아 돌려도 깨지지 않게 했다."
- 다음에 비슷한 상황이면: 데이터를 만드는 도구(부하·시연)는 만든 것을 찾을 표식(태그)을 남기고 끝날 때 지운다. 테스트가 깨지면 먼저 "내 코드"보다 "공유하는 데이터"를 의심한다
