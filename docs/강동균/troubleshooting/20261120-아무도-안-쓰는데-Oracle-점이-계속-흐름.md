# [event] 아무도 안 쓰는데 트래픽 관제(A-10)에 웹 서버 → Oracle 점이 계속 흐름

| 항목 | 내용 |
|---|---|
| 작성자 | 강동균 |
| 날짜 | 2026-11-20 |
| 상태 | 해결 |
| 관련 커밋·이슈 | outbox 릴레이가 보낼 샤드만 보도록 한 커밋 (`OutboxRelay.shardsWithWork`) |

## 1. 문제

- 현상: A-10 흐름도를 켜 두고 아무것도 안 하는데 웹 서버 → Oracle로 점이 무수히 흐름
- 재현: 앱만 띄우고 1분 동안 `hikaricp_connections_usage_seconds_count` 증가량을 봄 → **초당 81.5번** 커넥션을 빌림
- 영향: 화면이 "사람이 몰린 것처럼" 보여 진짜 몰림과 구분이 안 된다. 서버 Oracle(CPU 2개)도 아무도 안 쓸 때 쓸데없이 일한다

## 2. 원인

Oracle에서 1분 동안 실행된 SQL을 셌다 (`v$sql`의 executions 증가량).

| SQL | 초당 | 누가 |
|---|---|---|
| outbox 샤드 맨 앞 행 잠금 조회 | **76.0** (전체의 93%) | outbox 릴레이 |
| app_policy 값 읽기 | 3.8 | 정책 캐시 |
| 그 밖 (알림 발송·만료 스캐너·판매 오픈·결제 재확인) | 각 0.1~1 | 정기 작업 |

```java
// 0.2초마다, 보낼 것이 없어도 샤드 16개에 트랜잭션을 하나씩 연다 → 16 × 약 5회/초
for (int shard = 0; shard <= OutboxRecorder.MAX_SHARD; shard++) {
    total += relayShard(shard).published();   // tx.execute → 커넥션 빌림 → SELECT … FOR UPDATE
}
```

- 처음 잰 값은 초당 298번이었다. 그중 대부분은 내가 앞서 돌린 부하 시험이 남긴 위험 점수 재계산 대상 8.7만 개(`risk:dirty`)를 배치가 처리하던 것 — 그걸 비우고 다시 잼
- 흐름도의 Oracle 선은 "커넥션을 빌린 횟수"라 사용자 요청이 아닌 정기 작업도 점으로 보인다

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 릴레이 주기 늘리기 (0.2 → 1초) | 간단 | 예약 이벤트(알림·좌석 정리)가 늦어짐 | |
| 화면에서 정기 작업을 빼고 그리기 | 화면은 깔끔 | Oracle이 하는 일은 그대로 | |
| **보낼 것이 있는 샤드만 처리** | 지연 그대로, 쓸데없는 일만 없앰 | 회차마다 확인 쿼리 1번 | ✓ |

- 회차마다 먼저 `SELECT DISTINCT CASE WHEN status IN ('PENDING','FAILED') THEN shard_no END … >= 0` 한 번 → 나온 샤드만 처리. 확인이 실패하면 16개 모두
- **함정**: 조건을 `IS NOT NULL`로 쓰면 Oracle이 테이블 전체를 읽었다 (`TABLE ACCESS FULL`). 범위 조건 `>= 0`이라야 `INDEX RANGE SCAN IX_OUTBOX_PENDING` — 발행 끝난 행은 인덱스에 없어 쌓여도 가볍다
- 절차 원천 `docs/concurrency.md` §11.3에 같이 적음

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 아무도 안 쓸 때 커넥션 빌림 | 초당 81.5번 | **초당 10.5번** |
| 예약 이벤트 발행 지연 (60명 예매 2회, 데운 앱) | 평균 162~858ms, p95 384~4,021ms | 평균 116~128ms, p95 233~295ms (늦어지지 않음) |
| outbox·이벤트 통합 테스트 | — | 20/20 (순서·FAILED 샤드 정지 포함), 단위 520 |
| 예매 정합성 (30명 예매) | — | 10항목 OK |

- 측정 환경: 로컬 docker compose + 앱 1대(jar)
- 측정 방법: 앱을 띄우고 1분 쉰 뒤 1분 동안 `hikaricp_connections_usage_seconds_count` 증가량 ÷ 60. SQL별은 `v$sql.executions` 증가량. 발행 지연은 `outbox_event.published_at - created_at`

## 5. 정리

- 면접용 한 줄 요약: "사용자가 없는데도 관제 화면에 DB 트래픽이 흘러 SQL별 실행 횟수를 재 보니 93%가 outbox 릴레이가 빈 샤드 16개를 0.2초마다 도는 것이었다. 보낼 샤드만 인덱스로 먼저 찾게 바꿔 유휴 DB 호출을 초당 82 → 10번으로 줄이고 발행 지연은 그대로 유지했다."
- 다음에 비슷한 상황이면:
  - "트래픽"이 어디서 오는지 **DB 쪽 실행 횟수(`v$sql`)로** 센다. 앱 지표만 보면 누가 부르는지 모른다
  - 앞선 시험이 남긴 상태(재계산 대기열 등)가 측정을 오염시키지 않았는지 먼저 본다
  - 함수 기반 인덱스는 `IS NOT NULL`보다 범위 조건에 더 잘 탄다 — 실행 계획으로 확인
