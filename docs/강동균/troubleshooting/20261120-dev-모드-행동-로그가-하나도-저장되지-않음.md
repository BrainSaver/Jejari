# [behavior] dev 모드 부하 시험의 행동 로그가 하나도 저장되지 않음 (오류도 밀림도 없이)

| 항목 | 내용 |
|---|---|
| 작성자 | 강동균 |
| 날짜 | 2026-11-20 |
| 상태 | 해결 |
| 관련 커밋·이슈 | `8e058a2` A-10 데이터 놓침·밀림 (발견), `eef5877` dev 모드 세션 ID를 UUID로 (해결) |

## 1. 문제

- 현상: dev 모드(`--jejari.dev-mode=true`, `X-Member-Id` 헤더)로 k6 부하를 주면 행동 로그가 Kafka까지는 초당 20건씩 가는데 **MongoDB `behavior_log`에는 0건**. 앱 로그에 `행동 로그 형식 오류 N건을 건너뜀`이 5,699번 찍혀 있었지만 ERROR가 아닌 WARN이라 아무도 몰랐다
- 이상한 점: Kafka 소비 밀림(lag)은 계속 0. MongoDB를 60초 꺼도 밀림이 늘지 않았다 → "원래 아무것도 저장하지 않고 있었다"
- 재현 조건: dev 모드로 앱을 띄우고 행동 로그가 남는 API(대기열 줄 서기 등)를 호출
- 영향
  - dev 모드로 만든 부하 시험 데이터는 봇 탐지·모델 학습에 쓸 수 없었다 (행동 로그 0건)
  - 재생 기록(replay)은 모든 dev 회원이 세션 하나로 섞였다 (세션 ID가 재생 세션 문서의 `_id`)
  - **더 큰 문제**: 운영에서 화면 배포 실수 등으로 형식이 깨져도 똑같이 조용히 사라진다. 오류도 밀림도 없어 관제 화면이 "정상"이었다

## 2. 원인

- 가설 1: MongoDB 쓰기가 실패하는데 오프셋을 커밋한다 → 아님. 적재기(`BehaviorSink`)는 MongoDB 오류면 커밋하지 않고 5초 뒤 다시 시도한다 (코드·실측 모두 확인)
- 가설 2: 메시지가 형식 검사에서 걸린다 → **맞음**. Kafka에서 직접 꺼낸 메시지:

```json
{"eventId":"a35a6102-…","eventType":"QUEUE_ENTER","memberId":1120089,"sessionId":"dev-session", …}
```

적재기의 형식 검사(`BehaviorDocuments.parse`)는 `sessionId`가 UUID가 아니면 메시지를 버린다. dev 모드 필터(`DevMemberHeaderFilter`)는 모든 회원의 세션 ID를 고정 문자열 `"dev-session"`으로 만들고 있었다.
형식 오류는 다시 시도해도 고쳐지지 않으므로 적재기가 **건너뛰고 오프셋을 커밋**한다 (깨진 메시지 하나 때문에 전체가 멈추지 않게 하는 올바른 설계). 그래서 밀림에도 안 잡히고 오류도 아니다.

```
Kafka 받음 20/초 · MongoDB 저장 0/초 · 소비 밀림 0 · 형식 오류 건너뜀 1,402건/5분
```

## 3. 해결

### 3-1. 세션 ID

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 형식 검사를 느슨하게 (UUID 아니어도 받기) | 한 곳만 고침 | 운영 데이터 검사가 약해짐. 이상한 값이 분석에 섞임 | |
| 요청마다 무작위 UUID | 간단 | 같은 회원이 요청마다 다른 세션 → 클릭 간격·재생이 끊김 | |
| **회원 번호로 정해지는 UUID (v3)** | 같은 회원은 늘 같은 세션 (한 번 로그인해 계속 쓰는 것과 같음). 실제 로그인 세션(무작위 v4)과 겹치지 않음 | 없음 | ✓ |

- 바뀐 코드: `src/main/java/com/jejari/queue/dev/DevMemberHeaderFilter.java` — `sessionOf(memberId)` = `UUID.nameUUIDFromBytes("jejari-dev-session:" + memberId)`
- 테스트: `DevSecurityConfigTest.세션_ID는_회원마다_고정된_UUID`

### 3-2. 다시는 조용히 사라지지 않게 (관제)

형식 오류로 건너뛴 건수와 MongoDB 저장 건수를 지표로 내보내 A-10 트래픽 관제 "데이터 놓침 · 밀림"에 띄운다 (`jejari_behavior_skipped_total`·`_stored_total`).
최근 5분에 1건이라도 건너뛰면 **주의**, 건너뛴 것이 저장한 것보다 많으면 **위험** (형식이 통째로 깨진 것). 받는 양에 비해 저장이 10% 미만이면 "적재 멈춤".

### 3-3. 보안 점검 (같이 확인한 것)

| 항목 | 판단 |
|---|---|
| 세션 ID를 회원 번호로 예측할 수 있다 | 문제 없음. 세션 ID는 로그아웃·재생 표본 고르기·로그 묶기에만 쓰이고 **증명 수단이 아님**. 예전 `"dev-session"`은 모두가 같은 값이라 더 예측 가능했다 |
| 실제 로그인 세션과 겹칠 수 있나 | 아님. 실제 세션은 무작위 v4, dev는 이름 기반 v3라 UUID의 버전 자리가 다르다 |
| **dev 모드 자체가 서버에서 켜질 수 있다** | 원래부터 있던 더 큰 위험: dev 모드에서는 `X-Member-Id` 헤더 하나로 **아무 회원**이 될 수 있다. 서버 .env 한 줄 실수로 켜질 수 있었고 막는 장치가 없었다 → `DevSecurityConfig`가 `JEJARI_DOMAIN`(서버 .env에만 있음)을 보면 **기동을 멈추게** 함. 테스트 `DevSecurityConfigGuardTest` |

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| dev 모드 행동 로그 MongoDB 저장 | 0 / 초 (받음 20 / 초) | 20 / 초 |
| 형식 오류로 건너뜀 (5분) | 1,402건 (화면에 안 보임) | 0건 (생기면 화면에 위험) |
| 재생 세션 | 모든 dev 회원이 1개 | 회원마다 1개 |

- 측정 환경: 로컬 docker compose (Oracle·Redis·MongoDB·Kafka·Prometheus) + 앱 1대 dev 모드
- 측정 방법: k6 `대기열 줄 서기 20/초 · 상태 조회 150/초 · 좌석 60/초` 8분, A-10 화면과 `kafka-console-consumer.sh`·`kafka-consumer-groups.sh --describe --group behavior-sink`로 대조. 개선 후 값은 같은 방식(회원 번호 UUID)을 임시로 넣어 잰 것

## 5. 정리

- 면접용 한 줄 요약: "관제 지표를 만들다가, 형식 검사에서 건너뛴 메시지는 오프셋이 커밋돼 오류도 밀림도 남기지 않는다는 걸 발견했다. dev 모드의 고정 세션 ID 때문에 부하 시험 행동 로그가 100% 버려지고 있었고, 회원별 UUID로 고친 뒤 건너뜀 건수를 지표로 만들어 같은 유실이 화면에 바로 뜨게 했다."
- 다음에 비슷한 상황이면:
  - "건너뛰고 계속"하는 코드는 **건너뛴 건수를 지표로** 남긴다. 로그 WARN만으로는 아무도 안 본다
  - 밀림이 0이라는 것은 "다 처리했다"이지 "다 저장했다"가 아니다. **받은 양과 저장한 양을 나란히** 본다
  - 개발 전용 우회(헤더 로그인 등)는 운영에서 켜지면 기동을 멈추게 해 둔다
