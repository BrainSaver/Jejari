# [event] 소비자가 처리하지 못한 메시지가 로그 한 줄만 남기고 사라짐

| 항목 | 내용 |
|---|---|
| 작성자 | 강동균 |
| 날짜 | 2026-11-20 |
| 상태 | 해결 |
| 관련 커밋·이슈 | 격리 보관함(DLQ)·행동 로그 재시도 커밋 |

## 1. 문제

- 현상: 예약 이벤트·행동 로그를 읽는 소비자들이 **깨진 메시지나 계속 실패하는 메시지를 건너뛰면서 로그 한 줄만** 남겼다. 무엇을 놓쳤는지 셀 수도, 다시 처리할 수도 없었다 (Kafka 보관 7일이 지나면 원본도 사라짐)
- 특히
  - `notification`: 3번 실패하면 버림 → **예매 완료 알림이 조용히 빠짐**
  - `seat-release`: 처리 중 실패를 로그만 남기고 넘어감. 주석에는 "재전달은 재시작 때 일어난다"고 적혀 있었지만 **사실이 아니었다** → 그 좌석의 취소표 제안이 사라짐
  - 행동 로그 보내기: Kafka 전송 실패를 그대로 버림 → Kafka 40초 정지에 약 0.4% 유실 (봇 탐지 재료)
- 재현: 알림 테이블에 모든 INSERT를 거부하는 임시 제약을 걸고 예매 → 확정 알림 이벤트가 3번 실패 후 사라짐
- 영향: 사용자는 알림·취소표 제안을 못 받고, 운영자는 그런 일이 있었는지조차 모른다

## 2. 원인

- 소비자는 "메시지 하나 때문에 뒤의 메시지가 모두 멈추면 안 된다"는 이유로 건너뛰게 짜여 있었다 — 이 판단은 맞다. 문제는 **건너뛴 메시지를 둘 곳이 없었다**는 것
- `seat-release`의 "재시작 때 다시 온다"가 틀린 이유:

```java
f.setBatchListener(true);
f.getContainerProperties().setAckMode(AckMode.BATCH);   // 묶음이 끝나면 오프셋 커밋
...
} catch (RuntimeException e) {
    log.warn("seat-release: 예약 {} 처리 실패 (다음 전달 때 다시)", ...);   // 예외를 삼킴 → 묶음 정상 종료 → 커밋 → 다시 오지 않음
}
```

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 실패하면 다시 던져 멈추기 | 유실 없음 | 깨진 메시지 하나가 그 파티션 전체를 영원히 막음 | |
| DB에 실패 테이블 | SQL로 보기 쉬움 | ERD 변경·스키마 이전 필요, 행동 로그처럼 많으면 DB 부담 | |
| **Kafka 격리 보관함 (`<토픽>.DLT`)** | 원본 그대로, 순서용 키 유지, 스키마 변경 없음, 30일 보관 | 보는 도구가 따로 필요 → `tools/dlq.sh` | ✓ |

- `event/dlq/DeadLetters` — 원본 키·값 + 헤더(그룹·이유·출처·오류·시각)로 옮김. 옮기기에 실패하면 예외를 던져 커밋하지 않음 (보관함마저 안 되면 버리지 않고 멈춤)
- 다섯 곳에 연결: `notification`(재시도 소진·형식 오류), `seat-release`(처리 실패·형식 오류), `risk-signal`·`behavior-sink`·`replay-sink`(형식 오류)
- `tools/dlq.sh replay` — 원래 토픽에 헤더 `dlt-replay-for=<그룹>`을 붙여 다시 넣고, 다른 그룹은 `DeadLetters.notForMe`로 건너뜀. 소비자가 멱등이라 두 번 넣어도 같음
- 행동 로그 보내기 — 실패하면 큐 뒤에 다시 넣어 3번까지 (큐가 80% 넘게 차면 포기)
- 절차는 `docs/concurrency.md` §12.1, 전체 점검표는 `docs/강동균/features/데이터-유실-점검.md`

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 알림 저장이 3번 실패한 확정 이벤트 | 사라짐 (로그 1줄) | 격리 보관 → 원인 해결 후 다시 넣어 **알림 3건 = 예약 3건** (두 번 넣어도 3건) |
| 깨진 메시지 | 사라짐 | 소비 그룹마다 원본·출처와 함께 보관, A-10에 건수 |
| Kafka 40초 정지 중 예매 200건의 행동 로그 | 4건 유실 (약 0.4%) | **0건** (재시도 18번) |
| 통합 테스트 | — | 474/475 (남은 1건은 날짜 경계 문제로 무관) |

- 측정 환경: 로컬 docker compose + 앱 1대
- 측정 방법: 깨진 메시지는 `kafka-console-producer.sh`로 직접 넣음. 저장 실패는 `ALTER TABLE notification ADD CONSTRAINT tmp_block_all CHECK (1 = 0) ENABLE NOVALIDATE` 후 `./run.sh journey -e USERS=3`. Kafka 정지는 `docker compose stop kafka` 40초

## 5. 정리

- 면접용 한 줄 요약: "소비자가 막힘을 피하려고 실패 메시지를 로그만 남기고 건너뛰어 알림·취소표 제안이 조용히 사라지고 있었다. 격리 보관함(DLQ)과 그룹별 다시 넣기 도구를 붙이고 실패를 일부러 일으켜 검증해, 놓친 메시지를 0건으로 만들고 되살릴 수 있게 했다."
- 다음에 비슷한 상황이면:
  - "건너뛴다"는 코드를 보면 **어디에 두는지**를 같이 본다. 둘 곳이 없으면 그건 건너뛰기가 아니라 버리기
  - "다시 온다"는 주석은 오프셋 커밋 방식(AckMode)으로 확인한다
  - 유실 시험은 장애를 **일부러** 낸다 (Kafka 정지·DB 제약·깨진 메시지). 정상 부하만으로는 안 보인다
