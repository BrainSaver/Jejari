# [waitlist] 취소·만료된 좌석에 대기자가 없어도 60초 동안 아무도 못 삼

| 항목 | 내용 |

| 날짜 | 2026-11-25 |
| 상태 | 해결 (통합 테스트 2개 통과, 11-25) |
| 관련 커밋·이슈 | 이 문서와 같은 커밋, concurrency.md §9.1, §16 T43 |

## 1. 문제

- 현상: 결제 전 취소·확정 취소·결제 기한 만료로 풀린 좌석의 Redis 키가 `REOFFER:R`(대기자 몫)로 바뀐 뒤,
  **맞는 대기자가 없어도** `waitlist.reoffer_hold_sec`(기본 60초)가 지나야 일반 사용자가 그 좌석을 잡을 수 있었다
- 재현: 대기자가 없는 운행에서 좌석을 잡았다가 취소 → 바로 다른 사람이 같은 좌석을 선점 → `SEAT_ALREADY_TAKEN`
- 영향: 명절 오픈처럼 취소·만료가 많은 순간, 풀린 좌석마다 1분씩 팔리지 않음 (잘못 팔리는 것은 아님)
- 어떻게 찾았나: 외부 평가 뒤 T1~T46 추적표를 만들다 T43("만료 처리 뒤 REOFFER:R가 release.lua로 풀려 일반 선점 가능")을 검증하는 테스트도, 그 일을 하는 코드도 없다는 것을 발견

## 2. 원인

- 설계(concurrency.md §9.1-8)는 "더 이상 맞는 대기자가 없으면 남은 `REOFFER:R` 키를 `release.lua`로 지운다"인데,
  `SeatReleaseConsumer.handle`은 1단계(Redis 보상)와 제안 트랜잭션만 하고 이 단계를 빠뜨렸다
- TTL(60초)이 안전망이라 좌석이 영원히 막히지는 않아 지금까지 눈에 띄지 않았다

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| `reoffer_hold_sec`를 줄이기 | 코드 변경 없음 | 대기자가 있을 때 제안할 시간도 줄어듦 | |
| 제안 트랜잭션 **안에서**(커밋 전) 풀기 (문서 원래 순서) | 문서 그대로 | 제안이 롤백되면 이미 푼 키와 엇갈림 | |
| 제안 트랜잭션 **커밋 뒤** compare-and-delete로 풀기 | 대기자에게 넘어간 좌석(값 R')은 건드릴 수 없음, 같은 이벤트가 다시 와도 같음 | 커밋과 풀기 사이에 앱이 죽으면 TTL(60초)까지 막힘 — 예전과 같은 정도 | ✅ |

- `SeatReleaseService.releaseUnofferedReoffer(R, runId, seatIds)`: 값이 `REOFFER:R`인 키만 지움, 지운 수를 돌려줌
- `SeatReleaseConsumer.handle`: 제안 트랜잭션 뒤 호출
- concurrency.md §9.1: 8 COMMIT → 9 커밋 뒤 풀기로 순서를 코드와 맞춤

## 5. 배운 점

- TTL 같은 안전망이 있으면 빠진 단계가 "가끔 조금 느림"으로만 보여 오래 숨는다. 절차 문서의 단계마다 테스트가 있는지 추적표로 보는 것이 이런 걸 찾는다
