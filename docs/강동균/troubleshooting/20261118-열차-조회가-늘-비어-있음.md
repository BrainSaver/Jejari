# [train] 어느 날짜로 조회해도 "조건에 맞는 열차가 없어요"

| 항목 | 내용 |
|---|---|
| 작성자 | 강동균 |
| 날짜 | 2026-11-18 |
| 상태 | 해결 |
| 관련 커밋·이슈 | `4dc1477` 뒤에 발견 (그 커밋이 증상을 더 키웠다) |

## 1. 문제

- 현상: U-03 운행 검색에서 **"조건에 맞는 열차가 없어요."** 가 뜬다.
  화면을 열면 기본 날짜가 **오늘**인데, 오늘은 늘 비어 있다.
- 재현 조건: 그냥 화면을 열고 출발·도착역만 고르면 된다.
- 영향: 예매 흐름의 **첫 화면**이다. 여기서 막히면 뒤가 전부 안 보인다.
  시연·발표에서 날짜를 정확히 찍어 줘야만 열차가 나온다.

## 2. 원인

둘을 같이 봐야 보인다.

**(1) 검색은 운행일이 정확히 일치해야 찾는다** — `TrainQueryService.java:51`

```sql
WHERE r.run_date = ? AND a.stop_order < b.stop_order
```

범위도, 가까운 날 대체도 없다. 그 날짜에 `train_run` 행이 없으면 빈 결과다.

**(2) 시드는 날짜 몇 개에만 운행을 넣었다** — `db/seed/03·04`

고치기 전 운행이 있던 날은 이게 전부였다.

| 운행일 | 며칠 뒤 | 무엇 |
|---|---|---|
| 12-17 ~ 12-20 | 29~32 | 명절 8건 (03) |
| 2027-01-02 | 45 | 9001·9002 (04) |
| 2027-01-19 | 62 | 9003 (04) |

**2개월 예매 기간 61일 중 운행이 있는 날이 6일이었다.** 화면 기본값(오늘)은 그 6일에
들어 있지 않으니 열면 무조건 빈 결과다.

같은 날 오전에 내가 9001·9002를 `+3일` → `+45일`로 옮겼는데(`4dc1477`),
그게 **가장 가까운 운행을 2일 뒤에서 45일 뒤로 밀어** 증상을 더 눈에 띄게 만들었다.
그 커밋은 다른 문제(출발하면 예매가 막히는 것)를 고친 것이라 되돌릴 일은 아니다.

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| A. 예매 가능한 **모든 날**에 운행을 깔고, **스케줄러가 하루씩 이어 준다** | 아무 날이나 조회해도 나온다. 코레일 "2개월 전부터" 규칙과 그대로 맞고, 날이 지나도 창이 줄지 않는다 | ON_SALE 운행이 11 → 124건. 대기열 1초 스케줄러가 도는 운행이 그만큼 늘어난다 (아래 4장) | ✓ |
| B. 14일만 깐다 | 스케줄러 부담이 적다 | "2개월 전 예매"가 핵심 기능인데 2개월 뒤를 조회하면 비어 있다 | |
| C. 화면 기본 날짜를 가장 가까운 운행일로 | 데이터를 안 건드린다 | 다른 날짜는 그대로 빈 결과. 근본 원인이 남는다 | |
| D. 검색을 "그 날짜 이후 가장 가까운 운행"으로 | 데이터가 희소해도 뭔가 나온다 | 사용자가 고른 날짜를 무시한다. 실제 예매 사이트도 이러지 않는다 | |

A를 골랐다. 기획서에 "출발일 기준 2개월 전부터 예매"가 적혀 있는데 2개월 뒤를 조회하면
비어 있는 건 앞뒤가 안 맞는다.

### 시드만 고치면 반쪽이다 — 창이 하루씩 짧아진다

처음엔 시드만 고쳤다. 그런데 시드는 **돌린 순간**의 창을 만들 뿐이다. 하루가 지나면 코레일
규칙상 두 달 뒤의 새 날짜가 하나 열려야 하는데, 아무도 넣어 주지 않는다. 끝 날짜는 그대로고
오늘만 앞으로 가니 **창이 매일 하루씩 짧아진다.** 60일쯤 뒤엔 처음 문제로 돌아간다.

그래서 `RunHorizonScheduler`를 만들었다. 10분마다 지평(`ADD_MONTHS(오늘, 2) + 1일`)까지
빠진 날짜를 채운다. 읽기 전용으로 모사해 본 결과:

```
가정한오늘     지평         새로 넣을 날짜
2026-11-18   2027-01-19   (없음 — 꽉 차 있다)
2026-11-19   2027-01-20   01-20
2026-11-20   2027-01-21   01-20 01-21
2026-11-21   2027-01-22   01-20 01-21 01-22
```

**아직 안 열린 날짜까지 넣는다.** 지평의 마지막 날은 오픈이 내일 07:00이라 `SCHEDULED`로
들어간다. 그 행이 있어야 화면이 "오전 7시 오픈"을 보여 줄 수 있고, 07:00에
`SaleOpenScheduler`가 `ON_SALE`로 넘기는 것이 **매일 실제로 일어난다.** 열린 뒤에 행을
만들면 그 전이를 볼 수 없다 — 전에는 운행 `9003` 하나로 그걸 흉내 냈고, 하루가 지나면
그마저 그냥 `ON_SALE`이 되어 있었다.

**정차 시각은 그 열차의 기존 운행에서 베낀다.** 시각표의 원천은 공공 API이고 시드가 넣은
값이다. 스케줄러에서 다시 계산하면 원천이 둘이 된다. 날짜만 바꿔 같은 시각을 쓰되,
시·분을 떼어 쓰는 대신 **기준 운행일로부터의 간격**을 옮긴다 (자정을 넘겨 도착하는 열차의
날짜 차이를 잃지 않으려고).

**어느 열차를 이어 줄지는 설정으로 뒀다** (`jejari.train.horizon-trains`, 기본 `1,2`).
모든 열차를 자동으로 이어 주면 관리자가 화면에서 지운 운행이 되살아난다. 실제 서비스라면
운행 계획(다이어) 테이블을 읽어야 하는데 우리 스키마에 없다.

### 날짜 범위를 세지 않고 오픈 시각으로 걸러 낸다

```sql
CROSS JOIN (SELECT LEVEL - 1 AS n FROM dual CONNECT BY LEVEL <= 63) d
...
WHERE r.sale_open_at <= SYSTIMESTAMP
```

`ADD_MONTHS`로 보는 2개월은 달 길이에 따라 **59~62일**이다 (2월+3월 59일, 7월+8월 62일).
"60일"처럼 숫자를 박으면 달에 따라 끝자락이 아직 안 열렸는데 운행을 넣게 된다.
넉넉히 63일을 만들고 **오픈이 지난 것만** 남기면, 남는 범위가 곧 규칙과 같아진다.

### 번호 산식을 쓰려다 버렸다 (같은 날 오후에 되돌림)

처음엔 `700000 + (운행일 - 2026-01-01) * 10 + train_id`로 **날짜에서 번호를 뽑았다.**
적재일 기준으로 매기면 다시 돌릴 때 같은 날짜가 다른 번호를 받아
`uq_train_run_train_id_run_date`에 걸리기 때문이었다.

그런데 길동현 님 `tools/load-tago-schedule.js`가 이미
`400000 + 연중일 * 1000 + 열차번호`를 쓰고 있었다. 그쪽 대역은 **401000~766999**이고,
내 `700000~707999`가 그 안에 통째로 들어간다. **겹칠 수 있는 번호가 880개다.**

실제로 깨지는지 세어 봤더니 **0개**였다. 내 번호와 만나려면 열차번호 211 이상이 필요한데
실제 경부선 KTX는 **1~128**뿐이다. 즉 지금 멀쩡한 이유가 **설계가 아니라 우연**이다.
KTX-산천(4xx번대)이나 다른 노선이 들어오면 바로 겹친다.

그래서 **산식을 버렸다.** `train_run_seq`(ERD v27)가 번호를 주고, 같은 날짜가 있는지는
번호가 아니라 **진짜 자연키 `(train_id, run_date)`** 로 본다. 이미 `UNIQUE`가 걸려 있어
제약도 새로 만들 게 없다. 실제 Oracle에서 전제를 먼저 확인했다 —
MERGE의 INSERT 절에서 시퀀스를 쓸 수 있고, 두 번 돌려도 `0 rows merged`다.

`MAXVALUE 399999`를 둔 이유: 다 썼을 때 **조용히 남의 대역으로 넘어가지 않고** `ORA-08004`로
멈추게 하려는 것이다. 하루 ~110편이면 2,700일분이다.

| 대역 | 쓰는 곳 |
|---|---|
| 1001~2004 | 명절 운행 (시드 03) |
| 9001~9003 | 평시 시연 운행 (시드 04, 번호 고정 — 테스트·bench·문서가 씀) |
| 9101~9999 | 판매 오픈 스케줄러 테스트 |
| **100000~399999** | **날짜별 평시 운행 (`train_run_seq`)** |
| 401000~766999 | 실제 KTX 시간표 적재 (길동현) |
| 880000~889999 | 합성 데이터 |
| 1000000~ | 관리자 화면에서 만든 운행 |

**배운 것: 번호에 뜻을 담으면 두 사람이 각자 산식을 만들고, 대역은 언젠가 겹친다.**
유일성은 자연키가 보장하게 두고 번호는 시퀀스에 맡기면 맞출 것이 없다.

이걸 정리하다 **스케줄러 테스트의 정리 범위가 너무 넓은 것**을 찾았다.

```java
// 전: 시드의 날짜별 운행과 합성 데이터까지 지운다
jdbc.update("DELETE FROM train_run WHERE run_id >= ? AND run_id < 1000000", BASE);
// 후: 테스트 대역만
jdbc.update("DELETE FROM train_run WHERE run_id >= ? AND run_id < 10000", BASE);
```

### 고정 건수로 보던 검증을 구조 검사로

운행 수가 날마다 달라지니 `11. 운행 11건`·`13. 정차 55건` 같은 기대값이 못 쓰게 됐다.
숫자를 올리는 대신 뜻으로 바꿨다 — 애초에 이게 나은 검사다.

| 번호 | 전 | 후 |
|---|---|---|
| 11 | 운행 11건 (명절 8 + 평시 3) | **명절 운행 8건** (평시는 날마다 늘어남) |
| 13 | 정차 55건 (운행 11 × 역 5) | **운행마다 정차 5건** |
| 24 | 평시 운행이 7일 넘게 남음 | **내일부터 50일 매일 판매 중** |

24번은 아침에 넣은 "묵음 감지"를 겸한다. 묵은 DB에서는 50일이 전부 비어 FAIL이 된다.

### 대신 늘어난 비용 — 대기열 1초 스케줄러

`QueueAdmitScheduler`는 **판매 중 운행마다 1초에 한 번** `admit()`을 부른다.
`admit()`은 대기열이 비어 있어도 Redis 왕복을 4번 한다
(SET throughput · ZCARD · TIME · ZREMRANGEBYSCORE).

| | 전 (11건) | 후 (124건) |
|---|---|---|
| 1초 틱의 Redis 왕복 | 44회 | **496회** |
| 걸리는 시간 (왕복 0.23ms 기준) | ~10ms | **~113ms** |

- 측정 환경: 로컬 Docker Compose, `redis-cli --latency` 평균 **0.23ms** (289회 표본)
- 1초 틱 안에 들어오지만 전부 **유휴 작업**이다. 운행 수에 비례한다
- **이건 내가 찾은 게 아니다.** 길동현 님이 [`실제-ktx-시간표-적재`](../../길동현/features/실제-ktx-시간표-적재.md)
  "주의할 점"에 먼저 적어 두셨다 — *"운행이 많아지면(15일 ≈ 900개 ON_SALE) 대기열 입장
  스케줄러가 매초 운행 수만큼 돈다."* 내 몫은 숫자를 붙인 것뿐이다.
  공용 서버 성능 측정 전에 팀에 알렸다 ([팀에-알림 2-4](../팀에-알림-20261118.md))

### 겹치는 작업을 뒤늦게 발견했다

길동현 님의 위 스크립트가 **실제 KTX 전 편성의 시간표를 앞뒤 7일치** 넣는다. 내 쪽과
"운행 데이터를 만든다"는 점이 겹친다. 번호 대역이 겹칠 수 있던 것은 위처럼 시퀀스로 고쳤고,
열차 ID가 달라(`10000+열차번호` vs `1·2`) 지금도 같이 돌아간다. 다만 만드는 곳이 둘인 건
설명하기 어렵다.

**먼저 있는 걸 못 찾고 만든 내 잘못이다.** 다른 사람 영역의 `docs/{이름}/features/`를
먼저 훑어야 했다. 어떻게 합칠지는 팀에 물어 두었다.

## 5. 정리

- 면접용 한 줄 요약: "검색이 운행일 정확히 일치인데 시드가 2개월 중 6일에만 운행을 둬서
  첫 화면이 늘 비어 있었다. 예매 가능한 모든 날에 운행을 깔아 메우고, 날짜 범위를 숫자로
  박는 대신 오픈 시각으로 걸러 달 길이(59~62일)에 안 흔들리게 했다."
- 다음에 비슷한 상황이면: **시드 데이터는 "값이 맞는가"만 보지 말고 "화면이 그걸 찾을 수
  있는가"를 본다.** 23항목 검증이 전부 OK인데 첫 화면은 비어 있었다. 검증은 데이터를 봤고
  화면은 쿼리를 통해 봤기 때문이다. 그래서 24번은 "화면이 보게 될 것"으로 적었다.
