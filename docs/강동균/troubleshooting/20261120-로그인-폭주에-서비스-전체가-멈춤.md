# [member] 로그인이 한꺼번에 몰리면 로그인과 상관없는 API까지 멈춤 (해시 4개 서버)

| 날짜 | 2026-11-20 |

| 관련 커밋·이슈 | 용량 시험 `045f04c`(발견), 로그인 대기실 커밋(해결) |

## 1. 문제

- 현상: 용량 시험(`loadtest/scenarios/13_capacity.js`)에서 동시 사용자가 늘며 새 사람들이 한꺼번에 로그인하자, **로그인뿐 아니라 대기열 폴링·좌석 배치도·열차 조회까지** 멈췄다. 초당 344건 → 5건, 5xx 38%, p95 6초
- 재현 조건: GCP 서버와 같이 Argon2 동시 계산 **4개**(`auth.max_concurrent_hash=4`), 동시 200명이 같은 순간 로그인 (`-e LOGIN_SPREAD_SEC=0`)
- 영향: 명절 오픈 직전 로그인이 몰리면 이미 로그인해 줄 서 있던 사람들의 대기열 화면까지 멈춘다 — 대기열을 만든 이유가 사라짐

## 2. 원인

- 가설 1: CPU가 모자라다 → 일부. 해시는 일부러 무겁다(Argon2id m=19MiB, t=2)
- 가설 2: 해시 자리를 기다리는 로그인이 요청 스레드를 붙잡는다 → **맞음**

`PasswordHasher`는 해시 자리(세마포어)를 **최대 3초 기다린다**. 그동안 그 요청의 Tomcat 스레드가 묶인다. 자리는 4개뿐이라 200명이 몰리면 196명이 기다리고, 스레드 200개가 다 차면 다른 API 요청이 들어갈 스레드가 없다.

```
Tomcat busy threads 200/200 · DB 커넥션 대기 38 · 로그인 503 (PasswordHasher.withSlot) 928건
대기열·좌석·조회 5xx 0건 — 실패는 전부 로그인인데, 느려진 것은 전부
```

확인 실험 (로컬, 같은 폭주):

| 바꾼 것 | 결과 | 뜻 |
|---|---|---|
| 해시 32개 | 200명 버팀, 400명 무너짐 | |
| 해시 4개 | **200명에서 무너짐** (더 나쁨) | 자리가 적을수록 기다리는 스레드가 늘어 더 빨리 참 → 원인은 "기다리며 스레드를 쥠" |

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 해시 자리 늘리기 | 설정만 | 메모리(1개 19MiB)·CPU 한계. 서버는 4개 고정 | |
| 기다리지 않고 바로 503 | 스레드가 안 묶임 | 몰리면 거의 다 실패, 사용자가 계속 다시 누름 | |
| **로그인 대기실 (벌크헤드)**: 전용 일꾼 4명 + 줄, 요청 스레드는 바로 풀어 줌, 줄이 차면 429 + Retry-After, 화면이 자동 재시도 | 로그인이 몰려도 다른 API는 멀쩡. 로그인은 늦어도 성공 | 몰릴 때 로그인이 수십 초 걸릴 수 있음 | ✓ |

- 바뀐 코드
  - `member/login/LoginGate.java` — 일꾼 수 = 해시 자리, 줄 200칸(`jejari.auth.login-queue-capacity`), 8초 넘게 기다리면 해시 없이 돌려보냄, 지표 `jejari_login_queue_size`·`jejari_login_busy_total`
  - `member/web/MemberAuthController.login` — `CompletableFuture`를 돌려줘 서블릿 비동기로 (요청 스레드를 즉시 반납)
  - `common/error/RetryAfterException` + `GlobalExceptionHandler` — `Retry-After` 헤더, 오류 코드 `AUTH_LOGIN_BUSY`(429)
  - `frontend/src/api/client.js`·`user/Login.jsx` — 429 + Retry-After면 카운트다운("N초 뒤 자동으로 다시 시도해요") 후 자동 재전송
  - A-10 트래픽 관제: 자원에 "로그인 대기실" 막대, 몰리면 "알림"
- 테스트: `LoginGateTest` (요청 스레드 즉시 반환·가득 차면 429·오래 기다린 요청은 해시 안 함·traceId 전달), 로그인을 MockMvc로 부르는 통합 테스트 4개는 `asyncDispatch`로

## 4. 수치

| 지표 (해시 4개, 전원 동시 로그인) | 개선 전 | 개선 후 |
|---|---|---|
| 동시 200명: 초당 요청 / 로그인 뺀 p95 / 5xx | 10건 / 수 초 / 24% | 366건 / 16ms / 0% |
| 동시 800명 | (200명에서 무너짐) | 740건 / 322ms / 0% |
| Tomcat 스레드 최대 | 200 | 20 |
| 로그인 | 503 실패 | 평균 6.5초(200명)~39초(800명) 걸려도 성공 |

- 측정 환경: 로컬 4코어 컨테이너 하나에 앱·Oracle·Kafka·MongoDB·Redis·Prometheus·k6 (서버보다 불리)
- 측정 방법: `cd loadtest && ./run.sh capacity -e STEPS=200,400,800 -e STEP_SEC=60 -e THINK_SEC=2 -e LOGIN_SPREAD_SEC=0`, 해시 4개는 Redis `policy:cache`의 `auth.max_concurrent_hash=4` 후 앱 재시작

## 5. 정리

- 면접용 한 줄 요약: "Argon2 해시 자리를 기다리는 로그인이 요청 스레드를 붙잡아, 로그인 폭주가 대기열까지 멈추게 했다. 로그인을 전용 일꾼과 대기실로 분리하고(벌크헤드) 넘치면 Retry-After로 돌려보내 화면이 자동 재시도하게 해, 같은 폭주에서 다른 API의 5xx를 24%에서 0%로, 버티는 동시 사용자를 200명 미만에서 800명으로 늘렸다."
- 다음에 비슷한 상황이면:
  - 느린 작업을 **세마포어로 기다리게** 하면 기다리는 동안 요청 스레드가 묶인다. 막는 대신 **줄을 따로** 두고 요청 스레드는 풀어 준다
  - 자원을 줄이는 것(해시 자리 32 → 4)이 늘 안전한 쪽은 아니다. 기다리는 쪽이 무엇을 쥐고 있는지 본다
  - 시험의 판정 기준을 "모든 요청 p95"로 하면, 설계상 기다리는 요청(로그인 대기실)이 섞여 엉뚱한 결론이 난다 → 시나리오를 로그인과 나머지로 나눠 잼
