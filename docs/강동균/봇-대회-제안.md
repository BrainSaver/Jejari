# 봇 대회 제안 — 서로 모르는 봇 4개로 탐지를 시험하고 보강하기

> 작성 2026-11-18 · 강동균 · **진행 확정 (2026-11-18)** — 결정 사항은 맨 아래 "결정"
> 위험 점수 담당: 강다인 · 팀장: 길동현
> 관련: RISK-02·04, ADM-05·06·11, 기능설계서 10장 "탐지율 90% 이상 / 오탐률 5% 이하", 기획서 6장 데이터 신뢰성

## 한 줄 요약

위험 점수 규칙을 모르는 팀원 네 명이 **각자 매크로 봇을 하나씩** 만들고, 집계자 한 명의 로컬 서버에서 한꺼번에 돌려 표를 노립니다.
처음 보는 봇을 얼마나 잡는지 재고, 뚫린 수법으로 규칙을 보강한 뒤 **같은 봇으로 다시 재서 개선 전후 수치**를 냅니다.

## 왜 하나

지금 탐지율 100%(90/90, 24/24)는 **우리가 규칙을 알고 만든 봇**으로 잰 값입니다.

- 봇은 "규칙 문턱을 확실히 넘게" 만들었고(조영준 문서에도 그렇게 적혀 있음), 사람 데이터도 우리가 정한 모양입니다.
  그래서 시험 문제를 출제자가 직접 푼 셈입니다.
- 실제로 문턱 근처를 재 보니 계단 모양이었습니다: 연타 20번 0% · 21번 100%, 일정 간격 매크로는 0%.
- 딥러닝이나 Isolation Forest를 붙여도 같은 데이터로 학습·시험하면 **우리 규칙을 다시 외운 모델**이 나옵니다.
  데이터를 더 많이 만들어도 이 편향은 그대로 커질 뿐입니다.

**해결책은 봇을 만드는 사람과 막는 사람을 나누는 것입니다.** 보안에서 말하는 레드팀입니다.
네 명이 만들면 공격 방식도 네 가지라, 한 사람이 만든 봇보다 다양합니다.

## 누가

| 역할 | 사람 | 하는 일 |
|---|---|---|
| 수비 | 강다인 | 규칙·점수 그대로 두고 대회를 맞음. 끝난 뒤 뚫린 수법을 보고 보강 |
| 공격 | 김성원 · 길동현 · 강동균 · 조영준 | 봇 하나씩 |
| 진행·집계 | 강동균 | 일정·결과표·평가 스크립트 실행 (조영준 님 `eval_risk.sh` 사용) |

### 공격자마다 아는 정도가 다릅니다 — 숨기지 않고 두 부류로 나눠 셉니다

| 부류 | 사람 | 이유 |
|---|---|---|
| **블라인드** (규칙을 모름) | 김성원 · 길동현 | 위험 점수 코드를 본 적이 없음 |
| **규칙을 아는 공격자** | 조영준 · 강동균 | 조영준: 경계 측정으로 문턱을 앎. 강동균: 규칙 이름과 일부 문턱을 문서에서 봄 |

두 부류는 결과를 **따로** 냅니다. 블라인드 결과는 "처음 보는 공격을 잡나", 규칙을 아는 쪽 결과는
"규칙을 알고 피하려는 공격자를 잡나"(현실의 숙련된 매크로 업자)에 대한 답입니다. 둘 다 발표에 쓸 수 있습니다.

## 대회 규칙

### 목표 (모두 같음)

> **명절 행사 운행에서 표를 최대한 많이 확보하라.** 방법은 자유.

- 매수 제한(1회 4 · 열차당 4 · 1일 20 · 명절 8, 본인인증 CI 기준)은 그대로 켭니다. 제한을 피하는 것도 공격의 일부입니다
- 다계정, 시간 분산, 사람 흉내(무작위 지연), 취소 후 재구매 등 무엇이든 됩니다

### 하지 말 것

1. **규칙 코드와 정책 값을 보지 않습니다** (블라인드 두 분). `com.jejari.risk` 패키지, `app_policy`의 `risk.*` 값,
   강다인 님 기능 문서의 규칙 표, 조영준 님 경계 측정 결과. **문턱이 주석에 적힌 파일도**:
   `loadtest/scenarios/12_bot_detection.js`, `loadtest/tools/eval_risk.sh`, `docs/조영준/features/부하테스트-봇-탐지.md`
2. **다른 공격자의 봇 코드(`loadtest/contest/bot*/`)와 학습용 생성기(`tools/ml/generate.py`)를 대회 전에 보지 않습니다** (모두). 수법이 서로 닮으면 다양성이 사라집니다
3. **서버를 망가뜨리지 않습니다.** 공용 서버는 같이 쓰는 곳이라 봇 하나당 **동시 사용자 50 · 초당 요청 100 이하**(제안값).
   과부하로 다른 사람 예매를 막는 건 이 대회의 공격이 아닙니다
4. **테스트 계정만 씁니다.** 가입 정보는 전부 가짜, 실제 개인정보 금지
5. **서버 코드를 고치지 않습니다.** 봇은 바깥에서 HTTP나 브라우저로만 들어옵니다

### 꼭 지킬 것

1. **봇 하나당 명의(본인인증)는 최대 6개.** 모의 본인인증은 가짜 명의를 끝없이 만들 수 있어서, 상한이 없으면
   매수 제한(명의당 열차 4매)이 의미가 없어집니다. 6개 = "명의를 빌린 사람 6명"에 해당합니다.
   **가입은 대회 전날까지** 해 둡니다 — 가입은 IP당 1시간에 명의 5개까지라(`rate:signup`), 대회 날 네 명이 한 PC에서
   몰아서 만들면 막힙니다

2. **라벨은 이메일에만 넣습니다** (서버는 라벨을 볼 길이 없어야 공정).
   지금 형식 그대로: `lt{태그}.{종류}.g{묶음}.{번호}@loadtest.example.com`
   - 종류는 영문 소문자만: `bota` · `botb` · `botc` · `botd` (누가 무엇인지는 대회가 끝날 때까지 집계자만 앎)
   - 다계정이면 같은 사람 계정끼리 같은 `g{묶음}`
3. **4개 중 최소 하나는 브라우저 봇**(Playwright 등)으로 만듭니다. k6는 요청만 보내서 마우스 궤적이 안 남습니다.
   궤적이 있어야 나중에 마우스 모델과 CCTV 재생(ADM-11)이 의미 있습니다
4. **봇 코드와 한 줄 설명을 제출합니다** (`loadtest/contest/{종류}/`). 수법 설명은 대회가 끝난 뒤에 공개합니다
5. **각자 하루 안에** 만듭니다. 기능 마무리 일정이 밀리지 않게

## 준비하다 발견한 것 — 고침 (2026-11-18)

**이용자 화면(프론트엔드)이 기기 ID 헤더(`X-Device-Id`)를 보내지 않습니다.** 서버는 이 헤더로 기기를 구분하는데
(`BehaviorInterceptor`), 화면이 보내지 않아 **브라우저로 들어오는 사람·봇은 기기 정보가 비어 있습니다.**
지금 기기 기준 규칙(같은 기기 다계정 `MULTI_ACCOUNT_SYNC` 등)은 k6 봇처럼 **스스로 헤더를 붙여 준 경우에만** 걸립니다.

- 화면을 만든 사람(강동균)의 빠뜨림입니다. 고치는 방법: 화면이 처음 열릴 때 무작위 기기 ID를 만들어 브라우저에
  저장하고 모든 요청에 붙임 (반나절 이하)
- 다만 헤더는 클라이언트 값이라 봇은 언제든 바꾸거나 뺄 수 있습니다. 고쳐도 "같은 브라우저를 쓰는 봇"만 잡힙니다
- ~~고치고 대회를 할지, 지금 상태로 할지~~ → **고치고 대회합니다.** 화면이 처음 열릴 때 무작위 기기 ID를 만들어
  브라우저에 저장하고 이용자 요청마다 붙입니다 (`frontend/src/api/client.js`, 관리자 요청에는 안 붙임).
  로컬에서 브라우저 봇으로 돌려 행동 로그의 모든 이벤트에 기기 정보가 남는 것을 확인했습니다

  **고친 이유**: ① 설계가 원래 기기 단위로 묶게 되어 있고(ERD `member_device`, `risk_score`의 DEVICE) 빠진 건 화면의
  빠뜨림이지 규칙의 선택이 아니다 — "수비 고정"은 규칙을 고정하는 것이지 버그를 남겨 두는 것이 아니다
  ② 고치지 않으면 대회는 "기기 규칙이 꺼진 상태"를 재게 되어, 뚫린 봇이 나와도 규칙이 약한 건지 버그인지 가를 수 없다
  ③ 사람도 같은 헤더를 보내야 가족 기기 공유 같은 오탐을 제대로 잰다.
  한계는 그대로 적습니다: 봇은 브라우저마다 새 ID를 만들거나 헤더를 빼면 피해 갑니다

## 사람 데이터도 같이 모읍니다 (오탐률용)

봇 4개로는 **탐지율**만 잴 수 있습니다. **오탐률**(사람을 봇으로 잘못 잡는 비율)은 진짜 사람이 필요합니다.

- 대회 날 집계자 PC의 로컬 서버에 같은 와이파이로 팀원·지인이 접속해 직접 예매합니다 (비용 0). 목표 10~20명.
  모자라면 공용 서버를 사람 데이터 모을 때만 30분 켭니다
- 로컬 접속 전에 확인: 앱이 다른 기기에서 열리는지(방화벽), HTTP에서 로그인 쿠키가 동작하는지(`JWT_REFRESH_COOKIE_SECURE=false`)
- 라벨: `lt{태그}.human.g0.{번호}@loadtest.example.com`
- 실제 이름·전화번호를 넣지 않고 가짜 정보로 가입하도록 안내합니다 (모의 본인인증)
- 마우스 궤적·클릭 간격은 사람 기준선이 됩니다. 이게 지금 우리에게 가장 없는 데이터입니다

## 학습용 데이터는 만들어 쓰고, 시험용 데이터는 손대지 않습니다

모델(Isolation Forest·딥러닝)을 붙인다면 데이터가 많이 필요합니다. 봇을 실제로 돌려 쌓는 것만으로는 양이 부족하므로
**학습용 데이터는 생성기로 대량으로 만듭니다.** 다만 생성한 데이터로는 **시험하지 않습니다.**

| 용도 | 데이터 출처 | 이유 |
|---|---|---|
| **학습** (양 늘리기) | 생성기로 만든 데이터 — 수법 수십 가지, 수천~수만 명 | 빠르고 싸다. 수법을 다양하게 넣어 모델이 한 가지 모양만 외우지 않게 |
| **시험** (발표 숫자) | 블라인드 봇 + 진짜 사람 | 만든 사람의 생각이 들어가지 않은 데이터여야 "처음 보는 공격을 X% 잡는다"를 정직하게 말할 수 있다 |
| **CCTV 재생 시연** | 실제로 실행한 봇 | 영상은 실제 흐름(대기열 대기, 남과 부딪힌 409, 응답 지연)이 있어야 보여 줄 수 있다 |

**생성 데이터만으로 시험하면 안 되는 이유**
- 생성기를 만든 사람이 "봇은 이렇게, 사람은 이렇게"를 정하는 순간, 모델은 진짜 봇이 아니라 그 생각을 배운다.
  같은 생성기로 시험하면 점수는 잘 나오지만 실제 매크로가 다르게 움직이면 못 잡는다
- 생성기를 만드는 사람이 규칙을 알면(강동균·Claude 포함) 그 데이터는 "규칙을 아는 공격자"의 데이터가 된다
- 실제 시스템을 지나야 생기는 것이 빠진다. 이번 준비 중에도 **실제로 돌려 보고서야** 두 가지를 알았다:
  화면이 기기 ID를 보내지 않는다는 것, 가입이 IP당 시간당 명의 5개로 막힌다는 것

**지킬 것**
1. 생성 데이터와 대회 데이터는 태그로 나눠 **절대 섞지 않습니다.** 생성 데이터는 `synthetic_label.generation_params`의
   `source`를 `generator`로, 대회 데이터는 `loadtest/contest`로 둡니다 (`eval_contest.sh`가 이미 그렇게 씀)
2. 생성기에 넣는 수법 목록은 대회가 끝날 때까지 공격자에게 보여 주지 않습니다 (대회 봇이 생성 데이터를 닮으면 시험이 쉬워짐)
3. 형식(어느 테이블·컬렉션에, 어떤 라벨로, 몇 명)은 **강다인 님과 먼저 맞춥니다.** 가상 데이터 생성기(`com.jejari.synthetic`,
   DATA-02)가 이미 있어 그걸 넓히는 것이 맞고, 위험 점수 모델도 강다인 님 담당입니다
4. 모델 비교(위 "평가 2")는 **생성 데이터로 학습 → 대회 데이터로 시험** 순서로만 합니다

## 평가

### 1. 대회 점수표 (봇마다)

| 항목 | 뜻 |
|---|---|
| 확보한 좌석 수 | 공격이 얼마나 성공했나 |
| 탐지 여부 | 봇 계정 중 하나라도 의심 케이스가 열렸나 (지금 `eval_risk.sh`와 같은 기준: 회원 단위) |
| 탐지까지 걸린 시간 | 첫 요청부터 케이스가 열릴 때까지 |
| **어느 층에서 막혔나** | 매수 제한 / 규칙 점수 / 대기열 순번 / 관리자 판정 / 뚫림 |

마지막 줄이 핵심입니다. 막는 장치는 한 층이 아니라 겹겹이라, **어느 층이 일했는지**가 보강할 곳을 알려 줍니다.

```
매수 제한(CI 기준) → 규칙 점수 → 대기열 순번 조정 → 관리자 판정(CCTV 재생)
  한 사람 8매 상한     케이스 열림     위험 사용자는 뒤로      사람이 최종 판단
```

### 2. 모델 비교 — 돌려 가며 하나씩 빼기 (선택, 강다인 님 판단)

규칙 외에 Isolation Forest(ERD `risk_score.iforest_score` 자리 있음)나 작은 딥러닝 모델을 붙여 본다면,
**4개를 전부 학습에 넣으면 시험할 봇이 없어집니다.** 그래서 돌려 가며 하나씩 뺍니다.

| 회차 | 학습 | 시험 |
|---|---|---|
| 1 | botb · botc · botd | bota |
| 2 | bota · botc · botd | botb |
| 3 | bota · botb · botd | botc |
| 4 | bota · botb · botc | botd |

- 4회 평균 = **처음 보는 봇을 잡는 실력** (발표에 쓸 숫자)
- 실제로 쓸 모델은 4개 전부로 학습
- 규칙 · Isolation Forest · 딥러닝 셋을 같은 표로 비교. 사람 데이터로 오탐률도 같이
- 모델 점수는 **관리자에게 보여 주는 보조 의견**으로만 씁니다. 순번 조정·제한은 지금처럼 규칙 점수와 사람 판정으로

### 3. 보강 후 재대회 — 개선 전후 수치

강다인 님이 뚫린 수법으로 규칙을 보강한 뒤 **같은 봇 4개를 그대로 다시** 돌립니다.
"보강 전 X개 중 Y개 탐지 → 보강 후 Z개" — 기획서 성과 목표의 **개선 전후 수치**가 탐지 쪽에서도 생깁니다.
(봇 코드는 고치지 않습니다. 봇이 적응하면 비교가 안 됩니다)
