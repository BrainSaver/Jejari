## 1. CI 전부 실패 — GitHub 계정 결제 잠김

- 11-23 09:14부터 모든 CI 실행(ERD check, Gradle build)이 2~3초 만에 실패한다.
- check-run 주석에 남은 원인은 `The job was not started because your account is locked due to a billing issue.`이다. 코드 문제가 아니라 작업이 아예 시작되지 않는다.
- 자동 배포는 CI가 성공한 커밋만 배포하므로, 이 상태에서는 새 커밋을 배포하지 않는다 (WAITING_CI).

## 2. 자동 배포가 3일 전 커밋을 고른 버그

**현상:** 09:21 `BLOCKED 27f50db`. 막힌 파일 목록에 db/patch v0~v32와 시드가 보였다.

**원인:**

```
main:      ... ─ 822ce67 (배포된 것) ───────────┐
                                               ├─ a75dc75 (merge, main 최신)
SeongWon:  ... ─ 27f50db (11-20 00:50) ────────┘
                 ↑ 첫 번째 부모
```

- 김성원 님 브랜치에서 `main을 SeongWon에 합친` merge가 그대로 main에 올라갔다 (fast-forward). 그래서 main의 첫 번째 부모 줄이 SeongWon 쪽 옛 커밋으로 이어졌다.
- `auto-deploy.sh`는 `git rev-list --first-parent 배포된것..main`으로 최신부터 CI 성공 커밋을 찾는다. a75dc75는 CI가 실패해 건너뛰었고, 27f50db(11-20 CI 통과)를 골랐다.
- 27f50db는 822ce67의 후손이 아니다. 배포하면 3일치가 되돌아간다 (파일 420개, 5만 줄 삭제).

**왜 막혔나:** 되돌림 범위에 db 파일이 있어 BLOCKED가 걸렸을 뿐이다.
- 앱 코드만 되돌리는 경우였다면 승인 없이 자동으로 배포됐을 것이다.
- A-08에서 승인하면 되돌림 배포가 된다.

**CI가 정상이어도 생긴다:** CI가 도는 3~5분 동안은 최신 커밋이 "진행 중"이라 건너뛰기 때문이다.

**해결 (CI가 풀린 뒤):** 후보 커밋마다 `git merge-base --is-ancestor "$CUR" "$sha"`로 배포된 커밋의 후손인지 확인하고, 아니면 건너뛴다.

## 3. 수동 배포

- 서버에서 `sudo -iu dita_810; cd ~/Jejari; bash deploy/deploy.sh`로 main 최신 32d72d0을 배포했다. 앱은 active이고 health 확인은 200이다.
- `deployed-sha`가 바뀌어 27f50db BLOCKED가 풀렸다. Grafana "자동 배포 멈춤" 경보가 RESOLVED로 디스코드에 왔다.
- 직후 올라온 930c7ce는 CI 실패로 WAITING_CI다. 정상 동작이다.
- 윈도우 PowerShell은 실행 정책 때문에 `gcloud.ps1`을 막는다. `gcloud.cmd`를 쓰거나 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`로 푼다.

**운영 방식 (CI가 풀릴 때까지):** 팀원이 요청하면 조영준이 로컬 테스트 → 서버 `deploy.sh` → `systemctl start jejari-autodeploy` 순서로 수동 배포한다. "CI 대기 1시간" 경보는 원인을 알고 있으니 무시한다.

## 9. 수동 배포 뒤 ERD v33 DB 패치가 빠져 오류 130건

**현상**
- 14:08(KST)에 6617d81까지 수동 배포됐다. 김성원 님 비회원 예매 코드(e96590f)가 같이 올라갔다.
- 그런데 DB에는 v33(`member.member_type`·`guest_expires_at`)이 없었다.
- 그 결과 14:08~14:21에 `ORA-00904: "MEMBER_TYPE": invalid identifier`가 130건 났다.
  - 게스트 정리 조회가 114건, 게스트 예매가 16건이다.
  - 취소표 대기 등록과 내 정보 변경도 같은 검사(`GuestGuard`)를 타서 실패했을 것이다.
  - health는 200이라 겉으로는 정상처럼 보였다.

**원인: "재배포하면 DB도 자동 적용"은 사실이 아니다**
- `deploy.sh`는 DB 패치를 넣지 않는다.
- 패치는 자동 배포가 **BLOCKED**로 멈췄을 때 A-08 [적용]으로만 들어간다.
- 지금은 CI가 잠겨 자동 배포가 CI 확인(WAITING_CI)에서 먼저 멈춘다. 그래서 BLOCKED도, A-08 패치 화면도 나오지 않는다.
- 즉 수동 배포에서는 DB 패치를 사람이 따로 챙겨야 한다.

**조치 (사용자 승인 후)**
- `db/patch/v33.sql`을 앱 계정으로 적용했다.
  - 컬럼 2개(NULL 허용), `ck_member_r1`, `guest.enabled=N` 외 설정 2개가 들어갔다.
  - `~/jejari-app/db-patches.applied`에 기록했다.
  - 적용 뒤 ORA-00904는 0건, health 200.
- 강동균 님 요청으로 MongoDB `behavior_log`의 `ix_run_ts`를 삭제했다 (색인 7 → 6).
  - 전제 커밋 c52aca6은 배포돼 있었다.
  - 정합성 점검을 바로 한 번 돌렸고 10개 항목 모두 OK였다.

## 10. deploy.sh가 빠진 DB 패치를 잡게

- **배포 전 확인:** 지난 배포(`deployed-sha`) 이후 새로 생기거나 바뀐 `db/patch/vNN.sql` 중 `db-patches.applied`에 기록이 없는 것이 있으면, 빌드 전에 멈추고 목록과 다음 명령을 보여 준다.
  - A-08 [적용]도 같은 파일에 기록하므로 승인 경로는 그대로 통과한다.
- **`APPLY_PATCHES=1`:** 버전 순서(`sort -V`)대로 앱 계정으로 넣고 기록한다.
  - 출력에 `ORA-`·`SP2-`·`PLS-`가 있으면 중단한다. 이때 앱은 그대로다.
- **`SKIP_PATCH_CHECK=1`:** 이미 손으로 넣었을 때 쓴다.
- **배포 뒤 알림:** 바뀐 설정 중 사람이 할 일(경보 규칙 → `restart grafana` 등)을 보여 주기만 한다. 오늘 Grafana 재시작을 빠뜨린 것 때문에 넣었다.
  - 스크립트는 `exit 0`으로 끝난다. auto-deploy.sh가 종료 코드로 성공을 판단하기 때문이다.
- **시험:** 임시 git 저장소에서 7가지를 확인했다.
  1. 미적용 2개 → 멈춤
  2. 일부만 기록 → 나머지만 표시
  3. APPLY → 적용·기록
  4. 다시 실행 → 통과
  5. SKIP → 통과
  6. ORA 오류 → 중단
  7. 경보 파일 변경 → restart grafana 알림

## 11. 봇 대회 보강 7번 — 결제 단계 차단

팀 회의에서 보강 7개가 정해졌고, 그중 7번 "결제 단계 차단"을 맡았다.
- 위험 점수가 케이스 기준(80) 이상이면 결제를 막는다.
- 사용자와 정한 것:
  - 막으면 좌석을 **바로 해제**한다.
  - 점수를 **모르면 통과**시킨다.
  - 설계대로 진행한다.
- 위치: `PaymentService.start()`에서 멱등 키를 처음 잡은 직후, PG를 부르기 전이다. 같은 키로 다시 온 요청은 막지 않는다.
- 새로 만든 것:
  - `PaymentRiskGuard`
  - `RiskPenaltyService.knownScore()`
  - `ReleaseReason.RISK_BLOCKED`(actor SYSTEM)와 `SeatReleaseService.releaseForRiskBlock()`
  - `PAYMENT_RISK_BLOCKED`(403)와 Pay.jsx 안내
  - 지표 `jejari_payment_risk_check_total`
  - 스위치 `jejari.payment.risk-block`
- 절차 원천 `docs/concurrency.md`에 §7.5를 추가했다. §7.1 표에 한 줄 더했다.
- 시험: 새 단위 테스트 13개, 전체 536개 통과. 프론트는 로컬에 node_modules가 없어 빌드하지 못했다. 서버 deploy.sh가 빌드하고, 실패하면 멈춘다.
