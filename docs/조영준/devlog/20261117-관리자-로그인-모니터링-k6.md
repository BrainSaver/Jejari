## 어떻게 했나

- `AdminLoginService`가 강다인 님의 `PasswordHasher`·`AuthLimiter`·`AuthPolicy`·`LoginAttemptLog`를 그대로 사용
- 토큰 발급은 기존 `AuthTokenService.issue(ADMIN, adminId, …)`. `AdminRoleLookup`으로 현재 권한을 읽어 `adm`에 넣음
- 다른 팀원 파일은 추가만: `LoginAttemptLog.recordAdmin()`(강다인), `Purpose.ADMIN_LOGIN`·정규화 규칙·테스트 예시값(김성원), 테스트 도우미에서 관리자 토큰에 권한 넣기(김성원·내 테스트)
- 대시보드는 JSON 파일(`docker/grafana/dashboards/`)로 커밋 → Grafana가 기동 때 자동 등록. 검증은 대시보드의 쿼리 37개를 Prometheus API로 직접 실행해 값·오류 확인
- k6는 로컬 설치 없이 Docker(`grafana/k6:1.1.0`)로 실행. 기존 Mock 시나리오가 쓰는 `[가정]` 경로는 두고 실제 예약·결제 경로를 `config.js`에 추가, 실제 흐름 함수는 `lib/journey.js`로 분리(항상 JWT)

## 왜 이렇게 했나

- **pepper 고정**: admin_user에 `pepper_key_id`가 없음. 관리자는 몇 명뿐이라 ERD 변경 대신 현재 pepper로만 검증
- **첫 계정을 기동 때**: 해시가 각자의 pepper에 묶여 시드 SQL로 공유 불가
- **권한은 토큰에만 먼저**: 관리자 API가 아직 없어 `ADMIN` 하나로 막고, 나중에 `@PreAuthorize`만 붙이면 됨
- **adm 없는 관리자 토큰은 위조로 봄**: 관리자 토큰을 만드는 곳은 로그인 하나뿐이라 adm이 빠졌다면 정상 토큰이 아님
- **대시보드를 k6보다 먼저**: 개선 전후를 같은 패널·같은 쿼리로 비교하려면 측정 기준이 먼저 있어야 함. 평균 대신 p95·p99 (일부만 몹시 느린 모양을 평균이 숨김)
- **Redis 서버 메모리를 따로**: 좌석 키가 사라지면 이중 판매. 한도에 얼마나 가까운지가 핵심 지표
- **k6는 기존 loadtest에 합류**: 실행 앱·결과 비교·사전 점검이 이미 있어 두 벌을 만들지 않음. 좌석은 무작위로 골라 정상 사용자끼리 불필요한 경합을 줄임 (경합은 시나리오 2 담당)

## 막힌 점과 해결

- DATA-02 생성기가 내 DB에서 `ORA-00001 PK_PAYMENT`로 실패 → 앱은 `payment_id = reservation_id`, 생성기는 `payment_seq` 사용. 로컬에서 고쳐 재현만 확인하고 강다인 님께 전달 (내 파일 아님)
- 평가 스크립트가 아무 출력 없이 끝남 → sqlplus 출력의 탭 때문에 회원 ID 추출이 비고 `set -e`로 조용히 종료. 탭 제거 + 비었을 때 안내
- 계정 64명 평가에서 `SP2-0027 Input is too long` → 기기 목록을 한 줄로 붙여 sqlplus 한 줄 4999자 제한을 넘음. 한 줄에 하나씩
- `@EnableMethodSecurity`만 켜면 권한 거부 예외가 공통 처리기의 "예상 못한 오류"로 빠져 **500**이 됨 → `AccessDeniedException`을 403(관리자 경로는 ADMIN_FORBIDDEN)으로 처리하는 핸들러 추가, 테스트로 확인
- 관리자 토큰 형식이 바뀌어 기존 테스트 2개(권한 없는 관리자 토큰 사용) 실패 → 테스트 도우미가 관리자일 때 VIEWER를 넣도록 수정 (테스트 의도는 그대로)
- `Purpose`에 종류를 추가하자 `Pseudonymizer`·테스트의 `switch` 식이 컴파일 오류 → 각각 규칙·예시값 추가 (enum 끝에 추가만, 기존 해시 영향 없음)
- 로컬 Oracle이 v16 → 볼륨 재생성으로 v17
- 대시보드 쿼리 37개 중 1개(좌석 반환)가 빈 값 → 오류가 아니라 카운터가 첫 반환 때 생기는 방식. 예약 흐름을 돌리면 나타남
- Grafana 로그에 plugins·alerting 폴더 없음 오류 → 빈 폴더 추가로 정리 (동작 영향 없음)
- k6 첫 실행에서 성공 0% → 결제 API가 새 결제에 **201**을 돌려주는데 200만 성공으로 봤음. DB에는 결제 10건 모두 APPROVED였음 (내 체크가 틀림). 201·200 둘 다 받도록 수정 후 50명 100%
- k6와 서버 측정이 맞는지 확인: 좌석 선점 p95가 k6 141ms, Prometheus 138ms로 일치
