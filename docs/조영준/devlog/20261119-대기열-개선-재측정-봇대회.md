## 왜 이렇게 했나

- 사용자가 없는 상태부터 잰 이유: 아무것도 안 할 때 CPU를 73% 쓰는 서버로 부하 테스트를 하면 "개선 전" 수치가 앱 성능이 아니라 이 낭비를 재게 됨. 바탕 부하를 먼저 걷어 내야 PERF-01 숫자를 믿을 수 있음

- **PERF-01 앱 1대 vs 2대 (공용 서버, 사용자 200명 전체 흐름)**: 2대 → 1대 → 2대 순으로, 같은 열차의 빈 운행을 따로 써서 잼. **1대가 더 빠름**(예매 p95 8.0초 vs 14.6~18.0초, 로그인 p95 2.4초 vs 5.9~7.0초). 세 번 모두 VM CPU 100%. 원인: CPU 4개를 DB·Kafka·앱이 함께 쓰는데 앱마다 Argon2 해시 32개를 동시에 돌려 2대면 64개가 다툼 + JVM 두 개의 GC → [성능측정-공용서버](../features/성능측정-공용서버.md)
- 측정 동안만 IP당 가입·로그인 제한을 올렸다가 되돌림. 처음에 10000을 넣었더니 **관리자 정책 API는 저장했지만 앱은 범위 밖이라 기본값을 씀** → ADM-08 버그로 기록
- 서버 `jejari@` 유닛이 "파일이 바뀌어 다시 읽어야 함" 상태였음 (어제 같은 내용으로 다시 설치하며 시각만 바뀜). 실행 명령이 같은 것을 확인하고 `daemon-reload`

## 추가: ADM-08 범위 검사

- 측정 중 발견한 "정책 API가 범위 밖 값을 저장" 문제를 고침. 공용 인터페이스 `PolicyBounds`(common/policy)를 두고, 값을 읽는 모듈이 **읽을 때 쓰는 범위 상수를 그대로** 알려 주게 함(`AuthPolicy`, `BehaviorPolicy`). 관리자 API는 저장 전에 범위 밖·소수면 400. 모듈의 읽기 동작은 그대로
- 왜 모듈이 범위를 알려 주나: 범위를 관리자 쪽에 따로 적으면 두 곳이 어긋날 수 있음. 읽는 쪽 상수가 원본이어야 "저장은 됐는데 무시됨"이 다시 안 생김
- 남은 것: 대기열·결제 기한(AppPolicy)·위험 점수는 아직 범위가 없음 → 각 담당과 정하면 `PolicyBounds`만 구현
