# [deploy] 시드 05를 다시 돌리자 공용 서버의 실제 KTX 시간표가 전부 09:28로 바뀜

| 항목 | 내용 |
|---|---|
| 작성자 | 조영준 |
| 날짜 | 2026-11-18 |
| 상태 | 서버는 복구 · 근본 원인(시드 05 범위)은 팀원 수정 대기 |
| 관련 커밋·이슈 | 서버 데이터 재생성 + `4e3c84f` 배포, 실제 시간표 재반영 |

> 파일 이름: `docs/조영준/troubleshooting/20261118-시드05가-실제시간표-덮어씀.md`

## 1. 문제

- 현상: 공용 서버에서 오늘 날짜로 검색하면 열차가 하나도 안 뜸. 내일 이후는 뜨지만 53편이 **전부 09:28 출발 · 12:35 도착 · 모든 역 정차**
- 재현 조건: 실제 KTX 시간표(`deploy/tago-refresh.sh`)를 넣은 **뒤에** 시드 `05_train_stop_fare.sql`을 다시 실행
- 영향: 오늘 실제 운행 106편이 출발 스케줄러에 의해 전부 `DEPARTED`(09:28이 지났으니) → 화면은 떠난 열차를 빼므로 0건. 정차역도 사실과 다르게 표시

## 2. 원인

- 가설: 화면 필터 문제 → API 응답을 보니 출발 시각이 전부 같음 → DB를 읽기만 해서 확인

| 확인 (실제 시간표 운행, run_id 400000~) | 정상 | 실제 |
|---|---|---|
| 날짜별 기점 출발 시각 종류 | 수십 가지 | **2가지** (하행 09:28, 상행 09:37) |
| 한 편당 정차역 수 | 2~5역 | **1,604편 전부 5역** |
| 정차 행 마지막 변경 | 시간표 넣은 15:41 | **15:44:06** (시드 05 실행 시각, 8,020행 동시) |

```sql
-- db/seed/05_train_stop_fare.sql: 경부선(route_id = 1) 열차의 "모든 운행"에 시드 시각표 하나를 MERGE
FROM train_run run JOIN train tr ON tr.train_id = run.train_id JOIN sched sc ON sc.direction = tr.direction
WHERE tr.route_id = 1
-- tools/load-tago-schedule.js: 실제 KTX 열차 143편도 route_id = 1로 넣음 → 05가 자기 것으로 보고 덮어씀
```

- 최종 원인: **시드 05의 대상(경부선 전체 운행)과 실제 시간표 도구의 데이터(경부선 열차)가 겹침.** 강동균 님 커밋 안내("04 → 05만 다시 돌리면 날짜가 밀린다")대로 내가 서버에서 05를 다시 돌린 순서가 문제를 드러냄
- 같은 문제는 로컬에서 시간표 도구를 돌린 뒤 05를 다시 돌린 팀원 PC에서도 생김

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 실제 시간표 운행의 정차 행만 지우고 시간표 다시 넣기 | 회원·예약 유지 | 팀원이 시드를 고치는 중이라 또 바뀔 수 있음 | |
| **서버 데이터 재생성 + main 배포 + 실제 시간표 다시 넣기** | 빈 DB에서는 05가 시간표보다 **먼저** 한 번만 돎 → 덮어쓰기 없음. 새 시드(두 달치 매일 운행)까지 한 번에 | 회원·예약·행동 로그 삭제 (테스트 데이터) | ✓ (영준 님 결정) |
| 근본: 05에서 실제 시간표 운행 빼기 (`run.run_id < 400000` 등) 또는 실제 시간표를 다른 노선으로 | 다시 안 생김 | 시드·도구 담당 수정 | 팀원 수정 중 |

- 내 운영 규칙: **서버에서 시드 05를 다시 돌렸으면 바로 이어서 `sudo systemctl start jejari-tago`** (근본 수정 전까지). `deploy/README.md` 운영자 안내에 적음

## 4. 수치

| 서울→부산 | 덮어쓴 뒤 | 복구 뒤 |
|---|---|---|
| 오늘 예매 가능 | 0 (106편 전부 DEPARTED) | 21 (지금 이후 출발편) |
| 내일 출발 시각 종류 | 1가지 (09:28) | 53가지 (05:13 ~) |
| 앞으로 7일 판매 중 실제 운행 | (시각이 틀림) | 932건 |

- 측정 환경: 공용 서버(GCP e2-standard-4), 앱 2대. 확인은 API(`/api/v1/runs`)와 DB 읽기 쿼리

## 5. 정리

- 면접용 한 줄 요약: "시드 스크립트가 같은 노선의 모든 운행을 덮어쓰는 바람에 실제 시간표를 넣은 뒤 시드를 다시 돌리자 모든 열차가 같은 시각이 됐고, DB 수정 시각으로 원인을 특정해 데이터를 재생성하고 실제 시간표를 다시 넣어 복구했다."
- 다음에 비슷한 상황이면: 두 데이터 원천(시드·외부 적재)이 **같은 행을 대상으로 삼는지** 먼저 본다. 적재 순서가 결과를 바꾸면 둘 중 하나의 범위를 좁혀야 한다
