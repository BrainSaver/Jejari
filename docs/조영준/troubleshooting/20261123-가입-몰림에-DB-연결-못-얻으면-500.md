# [common] 가입이 몰려 DB 연결을 못 얻으면 500, 다시 시도해도 "본인인증 실패"

| 항목 | 내용 |
|---|---|
| 작성자 | 조영준 (제보: 강다인) |
| 날짜 | 2026-11-23 |
| 상태 | 해결 (서버 반영은 다음 수동 배포 때) |
| 관련 커밋·이슈 | 이 문서와 같은 커밋 |

## 1. 문제

- **현상:** 연습 봇과 합성 사람 가입을 한꺼번에 돌리자 가입 일부가 **500**으로 끝났다. 오류는 `CannotGetJdbcConnectionException`이었다 (강다인 님 제보).
- **재현 조건:** 커넥션 풀(20)이 모두 사용 중인 상태가 연결 대기 시간(5초)보다 오래 이어질 때.
- **영향:**
  1. 서버 코드가 틀린 게 아니라 **바쁜 것**인데 500이 나간다. 클라이언트는 다시 시도해도 되는지 알 수 없고, Grafana·로그에는 "서버 오류"로 섞인다.
  2. 더 큰 문제가 있었다. 가입은 본인인증 토큰을 **DB 저장 전에 소비(GETDEL)** 한다. 그래서 저장이 실패하면 토큰이 이미 없어 **다시 시도해도 "본인인증 실패"** 가 나고, 본인인증부터 다시 해야 했다.

## 2. 원인

- **처음 가설:** 가입이 Argon2 해싱(수백 ms) 동안 DB 연결을 잡고 있어서 풀이 빨리 바닥난다.
  - `SignupService`를 확인해 보니 아니었다. 해싱은 트랜잭션 **밖**에서 하고, `open-in-view`도 꺼져 있다. 연결은 INSERT 트랜잭션 동안만 잡는다.
- **최종 원인:**
  - 풀 바닥 자체는 그 순간 전체 부하 때문이다 (연습 봇·합성 사람 동시 실행). 공용 서버 Oracle 여유는 processes 106/200이고 풀 20이 적정하다 (같은 날 실측).
  - 오류 처리 쪽에 원인이 두 가지 있었다.
    - `GlobalExceptionHandler`에 연결 획득 실패 처리가 없어 `Exception` → 500으로 떨어졌다. Redis 장애는 이미 `RedisExceptionHandler`가 503으로 바꾸고 있었다.
    - 저장 실패 때 소비한 토큰을 되돌리는 코드가 없었다.

```
Hikari: SQLTransientConnectionException "Connection is not available, request timed out after 5000ms"
  ← CannotGetJdbcConnectionException (JdbcTemplate) / CannotCreateTransactionException (트랜잭션 시작)
  → GlobalExceptionHandler.handleUnexpected → 500 INTERNAL_ERROR
```

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 풀을 더 키움 | 바쁨이 덜 생김 | Oracle CPU 2개라 처리량은 그대로, 대기만 DB 쪽으로 옮겨감 (풀 20 근거 실측과 어긋남) | |
| 연결 획득 실패만 **503 + Retry-After 2** | "잠시 뒤 다시"가 맞는 신호. 다른 DB 오류는 그대로 500 | 처리기 하나 추가 | ✓ |
| + 저장 실패 시 토큰 되돌리기 | 503 뒤 재시도가 실제로 성공 | 회원 모듈 수정 | ✓ |

- **바뀐 코드:**
  - `common/error/DatabaseBusyExceptionHandler.java` (새 파일)
    - 원인 사슬에 `CannotGetJdbcConnectionException`이나 `SQLTransientConnectionException`이 있으면 503, 아니면 지금처럼 500이다. 원인 없는 `CannotCreateTransactionException`도 503으로 본다.
    - JdbcTemplate·트랜잭션 시작·JPA 경로를 모두 잡는다.
    - 경고는 10초에 한 번만 남긴다.
  - `member/verify/VerificationTokens.restore()`
    - 원래 인증 시각을 그대로 써서 유효 시간이 늘지 않는다.
    - `SET NX`라 이미 있으면 덮어쓰지 않는다.
  - `member/signup/SignupService`: 중복(409)이 아닌 저장 실패이면 토큰을 되돌린 뒤 예외를 그대로 던진다. 트랜잭션이 롤백돼 회원이 없으므로 안전하다.

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 풀 바닥 시 응답 | 500 `INTERNAL_ERROR` | 503 `SERVICE_UNAVAILABLE` + `Retry-After: 2` |
| 그 뒤 같은 토큰으로 다시 가입 | 실패 (본인인증부터 다시) | 성공 |
| 제약 위반 등 다른 DB 오류 | 500 | 500 (그대로) |

- **측정 방법:** 단위 테스트 11개를 추가했다.
  - `DatabaseBusyExceptionHandlerTest` 8개: Hikari 예외 모양 3경로, 다른 DB 오류는 500, 요청 경로에서 처리기 순서 확인
  - `VerificationTokensRestoreTest` 3개
- 전체 단위 테스트 579개가 통과했다. 실제 부하 재현은 서버 반영 뒤 강다인 님 연습 하네스로 다시 본다.

## 5. 정리

- **면접용 한 줄 요약:** "가입 몰림에 DB 연결을 못 얻으면 500이 나가고 본인인증 토큰까지 사라지던 것을, 연결 획득 실패만 골라 503+Retry-After로 바꾸고 저장 실패 시 토큰을 되돌려 '잠시 뒤 다시'가 실제로 되게 했다."
- **다음에 비슷한 상황이면:**
  - 503으로 바꿀 때 "다시 시도하면 정말 되는가"까지 본다. 앞 단계에서 1회용 자원(토큰·멱등 키)을 써 버리지 않았는지 확인한다.
