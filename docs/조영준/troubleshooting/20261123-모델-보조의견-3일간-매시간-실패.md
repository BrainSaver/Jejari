# [deploy] 위험 점수 모델 보조 의견이 3일 동안 매시간 "꺼내기 실패"

| 항목 | 내용 |
|---|---|
| 작성자 | 조영준 |
| 날짜 | 2026-11-23 |
| 상태 | 해결 (서버 반영은 다음 수동 배포 때) |
| 관련 커밋·이슈 | 47e7a14(모델 타이머 도입), 이 문서와 같은 커밋 |

## 1. 문제

- **현상:** `jejari-model.service`(매시간 17분)가 2초 만에 `꺼내기 실패:`로 끝난다. 오류 내용은 비어 있다.
- **기간:** 마지막 성공은 11-20 15:17, 첫 실패는 11-20 16:19 (KST). 그 뒤 11-23 오전까지 매시간 실패했다.
- **재현 조건:** 최근 1일 동안 행동 로그(behavior_log)가 0건일 때. 주말이라 사이트를 쓴 사람이 없었다.
- **영향:** 모델 점수(model_score)가 갱신되지 않았다. 보조 의견이라 대기열·이용 제한에는 영향이 없다.
  - 모델 실패에 대한 Grafana 경보가 없어서 3일 동안 아무도 몰랐다.
  - jejari-model CPU 제한을 정하려고 실행 시간을 보다가 발견했다.

## 2. 원인

- **처음 가설:** DB 연결이나 컨테이너 문제.
- **확인 방법:** 서버에서 `bash -x tools/ml/export_live.sh --recent 1 <임시폴더>`로 재현했다 (읽기만). 회원은 꺼냈고, 행동 로그 조회 직후 종료 코드 1로 끝났다.

```
+ docker compose exec -T mongo ... db.behavior_log.find({ ts: { $gte: ... 1일 전 } ... })
+ tr -d '\r'
+ grep '^{'
exit=1        ← events.jsonl 0바이트
```

- **최종 원인:** `grep`은 맞는 줄이 0개면 종료 코드 1을 돌려준다. 스크립트가 `set -euo pipefail`이라 파이프 전체가 실패로 처리돼 말없이 끝났다.
  - 호출하는 `model-refresh.sh`에는 "행동 로그 0건이면 정상 종료"하는 분기가 이미 있었다. 그런데 그 분기까지 가지 못하고 "꺼내기 실패"로 처리됐다.
  - 회원 조회의 `grep -E '^[0-9]+\|'`도 같은 구조라, 회원 0건일 때 "계정이 없습니다" 안내까지 가지 못했다.

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| `pipefail` 끄기 | 한 줄 | 앞쪽 `docker compose exec`·`mongosh` 실패까지 숨김 | |
| `grep ... \|\| true`로 0건만 허용 | 0건만 정상, 앞 명령 실패는 그대로 잡힘 | 줄마다 붙여야 함 | ✓ |

- **바뀐 코드:** `tools/ml/export_live.sh`의 회원·행동 로그 `grep` 두 곳 → `{ grep … || true; }`
- **같이 한 것:** 모델 컨테이너 CPU 제한
  - `deploy/model-refresh.sh` `docker run --cpus 1` (매시간 점수)
  - `deploy/model-retrain.sh` `--cpus 2` (일요일 새벽 재학습)
  - 바꾸려면 `ML_CPUS`
  - 작업이 컨테이너 안에서 돌기 때문에 systemd 유닛의 `CPUQuota`·`Nice`는 닿지 않는다. 그래서 유닛이 아니라 `docker run`에서 제한했다.

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 행동 로그 0건일 때 결과 | 실패 (exit 1, "꺼내기 실패:") | 정상 종료 ("최근 1일 행동 로그 없음") |
| 모델 컨테이너 CPU 상한 | 없음 (4개 모두 사용 가능) | 점수 1개, 재학습 2개 |

- **측정 방법:** 로컬에서 `set -euo pipefail` 아래 0건·1건 입력으로 바뀐 파이프를 실행했다.
- **서버 확인:** `docker run --cpus 1 jejari-ml`이 도는지 확인했다.
- **서버 반영:** 다음 수동 배포 뒤 `journalctl -u jejari-model -n 5`로 확인한다.

## 5. 정리

- **면접용 한 줄 요약:** "`pipefail` 아래에서 `grep` 0건이 실패로 처리돼 데이터가 없는 날마다 모델 갱신이 실패했고, 0건만 허용하도록 고쳐 '데이터 없음'과 '진짜 실패'를 구분했다."
- **다음에 비슷한 상황이면:**
  - `set -o pipefail` 스크립트에서 `grep`을 필터로 쓰면 0건을 생각한다.
  - 주기 작업을 만들면 실패 경보도 같이 만든다.
  - 컨테이너 작업의 자원 제한은 `docker run`에서 건다.
