## 3. 설계 결정

### 결정 1. Spring Boot 4.0.9 + 단일 모듈

- 상황: 3주 프로젝트, 5명이 같은 앱에 기능을 붙임
- 고려한 대안: Boot 3.5 / 멀티 모듈
- 선택과 이유: 3.5는 무료 지원이 끝나 4.0.9. 모듈은 하나로 두고 도메인 패키지로 나눠 빌드·설정을 단순하게 (순수 계산 라이브러리 `risk`만 별도 모듈)
- 감수한 단점: Boot 4 자료가 적음 (Jackson 3 패키지, starter 이름 변경 등을 직접 확인)
- 관련 코드·커밋: `build.gradle`, `2fadb6c`

### 결정 2. 리프레시 토큰 회전은 "행 유지, 해시만 교체"

- 상황: 설계 문서의 `revoke_reason = ROTATED`는 회전마다 새 행을 만드는 구조로 보였지만, `auth_session.session_id`는 CCTV 녹화·행동 로그의 연결 키
- 고려한 대안: 회전마다 새 행 (session_id가 15분마다 바뀌어 행동 로그가 쪼개짐)
- 선택과 이유: 로그인 1번 = 행 1개, 회전은 같은 행의 해시만 조건부 UPDATE. 옛 토큰이 다시 오면 해시 불일치 → 탈취로 보고 `SUSPICIOUS` 폐기. **ERD 변경 없이** 다른 팀원 기능에 영향 없음
- 감수한 단점: `ROTATED` 값은 쓰지 않음. 두 탭이 동시에 재발급하면 세션이 폐기될 수 있음 (프론트가 재발급을 하나씩)
- 관련 코드·커밋: `auth/session/AuthTokenService`, `AuthSessionRepository#rotate`, `b1c5fdf`

### 결정 3. 요청마다 DB를 보지 않는 JWT (15분)

- 상황: 명절 예매 트래픽에서 인증이 병목이 되면 안 됨
- 고려한 대안: 매 요청 세션 조회, Redis 차단 목록
- 선택과 이유: 서명·만료만 확인 → DB 왕복 0. payload는 `sub·role·sid`만 (JWT는 암호화가 아니라 개인정보 금지)
- 감수한 단점: 로그아웃·정지 후에도 최대 15분 유효. 즉시 차단이 필요해지면 Redis 차단 목록 추가
- 관련 코드·커밋: `auth/jwt/*`, `docs/조영준/features/JWT-인증.md`

### 결정 4. 설정 실수는 "경고" 대신 "기동 실패"

- 상황: 시간대 하나가 어긋나면 결제 마감이 9시간 틀어지고(§0.7), Redis 기본 정책이면 좌석 키가 조용히 사라져 이중 판매(§14.5). 둘 다 평소엔 티가 안 남
- 고려한 대안: compose 설정만 믿기, 로그 경고
- 선택과 이유: 앱이 기동 때 직접 확인하고 틀리면 멈춤. compose 없이 띄운 서버에서도 막힘
- 감수한 단점: CONFIG가 막힌 관리형 Redis에선 끄는 설정이 필요 (`jejari.redis.verify-config=false`)
- 관련 코드·커밋: `common/config/TimeZoneVerifier`, `RedisConfigVerifier`, `453d464`

### 결정 5. 개발은 각자 로컬 DB, 공용 서버는 2주차 초

- 상황: 처음부터 공용 DB로 같이 개발할지 검토
- 고려한 대안: 공용 DB 하나로 개발
- 선택과 이유: 공유할 것은 데이터가 아니라 코드·DDL·시드. 공용 DB면 스키마 재생성이 5명을 멈추고, 좌석 동시성 테스트 데이터가 섞이며, Oracle Free(CPU 2·RAM 2GB)를 나눠 씀. 접속 정보가 전부 `.env`라 나중에 옮겨도 코드 수정 없음
- 감수한 단점: 앱 여러 대에서만 드러나는 문제는 공용 서버 전까지 못 봄 → [멀티 인스턴스 대비 코딩 규칙](features/멀티인스턴스-코딩-규칙.md)으로 미리 예방, 고칠 시간 1주를 남기려 2주차 초로
- 이후 변경 (2026-11-17): 공용 서버는 Oracle Cloud A1(ARM) 대신 **Google Cloud**로 팀 결정. x86 VM이라 로컬과 같은 이미지(Oracle Free 등)를 그대로 쓸 수 있어 ARM 호환 확인이 필요 없어짐
- 관련 코드·커밋: `da02891`

### 결정 6. 관리자 로그인은 회원 로그인 부품을 재사용하고, ERD는 늘리지 않음

- 상황: AUTH-05. admin_user에는 회원(member_credential)과 달리 `pepper_key_id`·실패 횟수 컬럼이 없고, 시퀀스도 없음
- 고려한 대안: ERD에 컬럼 추가 요청(v18 대기) / 관리자 전용 잠금·기록을 따로 구현 / 시드 SQL로 첫 계정
- 선택과 이유: 잠금·시도 제한은 Redis라 컬럼이 필요 없음 → 강다인 님 `AuthLimiter`·`PasswordHasher`·`LoginAttemptLog`를 그대로 사용. pepper는 현재 값으로 고정(관리자는 몇 명뿐). 첫 계정은 해시가 각자 pepper에 묶여 있어 시드로 공유 불가 → `.env` 값으로 기동 때 1회 생성. 세부 권한은 토큰(`adm`)에만 먼저 담고 관리자 API가 생길 때 `@PreAuthorize`
- 감수한 단점: pepper를 바꾸면 관리자 비밀번호 재설정 필요. 비활성화는 최대 15분(다음 재발급) 뒤 반영
- 관련 코드·커밋: `auth/admin/*`, [관리자-로그인](features/관리자-로그인.md)

### 결정 7. 공용 서버는 VM 1대 + Caddy(HTTPS) + 앱 2대

- 상황: INF-03. 클라우드는 Google Cloud로 팀 결정. 강동균 님이 "VM 1대에 compose 그대로, 8080 공개, 앱 1대"로 조사해 넘겨줌
- 고려한 대안: 조사안 그대로(`http://IP:8080`) / 관리형 서비스로 쪼개기(GCP에 관리형 Oracle 없음, 비용 큼) / Cloud Run(상주 스케줄러·Kafka 컨슈머가 멈춤)
- 선택과 이유: VM 1대는 조사안을 따름. 다만 리프레시 쿠키가 Secure라 http에서는 브라우저 재발급이 전부 실패하고, 8080을 열면 내부 지표가 공개됨 → Caddy로 HTTPS(`외부IP.sslip.io`, 도메인 구매 없음), 80·443만 열기. 멀티 인스턴스 규칙을 실제로 확인하려고 앱 2대, 배포는 한 대씩
- 감수한 단점: 구성 요소 하나(Caddy) 추가. VM을 껐다 켜면 외부 IP가 바뀔 수 있어 주소가 바뀜 (고정 IP는 유료)
- 관련 코드·커밋: `deploy/`, `1526769`, [공용서버-배포](features/공용서버-배포.md)

## 7. 예상 질문

- Q. JWT를 쓰면 로그아웃한 토큰은 어떻게 막나요?
  - A. 액세스 토큰은 15분으로 짧게 두고 요청마다 DB를 보지 않는 대신, 리프레시 토큰을 DB에서 폐기해 재발급을 막습니다. 즉시 차단이 필요하면 Redis 차단 목록을 추가하는 트레이드오프입니다.
- Q. 리프레시 토큰 탈취는 어떻게 감지하나요?
  - A. 재발급할 때마다 토큰을 바꾸고 DB에는 해시만 둡니다. 이미 바뀐 옛 토큰이 다시 오면 누군가 복사해 간 것이므로 세션을 폐기합니다. 판정은 조건부 UPDATE 한 문장이라 동시 요청에도 한쪽만 성공합니다.
- Q. Redis `noeviction`이 왜 중요한가요?
  - A. 기본 정책이면 메모리가 찰 때 좌석 선점 키가 조용히 지워져 같은 좌석이 두 번 팔릴 수 있습니다. noeviction이면 쓰기 오류로 드러납니다. 실제로 한도를 낮춰 좌석 키가 남는 것을 확인했고, 앱이 기동할 때 이 설정을 검사합니다.
- Q. 시간대를 왜 세 곳에서 맞추나요?
  - A. Oracle `SYSTIMESTAMP`는 DB 서버 OS 시간대, TIMESTAMP 비교는 세션 시간대, 앱은 JVM 시간대를 따릅니다. 하나라도 UTC면 마감 시각이 9시간 어긋나서, 세 곳을 모두 고정하고 기동 때 확인합니다.
