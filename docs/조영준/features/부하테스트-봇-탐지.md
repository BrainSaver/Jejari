# 부하 테스트: 봇 탐지 평가 (DATA-03 봇 쪽, k6 시나리오 12)

작성자: 조영준 · 코드 위치: `loadtest/scenarios/12_bot_detection.js`, `loadtest/tools/eval_risk.sh`, `loadtest/lib/journey.js`(기기 ID·운행 검색 추가)

> 강다인 님의 위험 점수 엔진(RISK-02)·의심 케이스(RISK-04)가 **실제 트래픽에서** 봇을 잡고 사람은 놔두는지 재는 시나리오입니다. 기능설계서 목표: 탐지율 90% 이상, 오탐률 5% 이하.

## 한 줄 요약

정상 사용자 40명과 봇 24명을 실제 앱에 같이 흘려보내고, 1분 배치가 돈 뒤 **정답 라벨(`synthetic_label`)과 서버가 연 의심 케이스를 비교**해 탐지율·오탐률을 낸다.

## 어떻게 동작하나

```
k6 setup: 계정 65개 가입 (이메일에 종류 표시) + 도우미가 좌석 1개를 사 둠 (retry 봇의 과녁)
k6 본편:  정상 40 · fast 5 · retry 5 · multi 3묶음×3 · cancel 5 가 각자 30초 안에 도착해 행동
   ↓ 앱: 행동 로그(Kafka → Mongo) · 예약 이벤트 → risk:dirty → 1분 배치 → risk_score · suspicious_case
eval_risk.sh: 배치 대기 → 이메일에서 정답 읽어 synthetic_label MERGE → 회원별 "연결된 대상에 케이스가 있나" → 표
```

| 종류 | 정답 라벨 | 행동 | 걸려야 하는 규칙 |
|---|---|---|---|
| normal | NORMAL | 사람 속도, 20%는 한 번 취소 | 없음 |
| fast | MACRO | 운행 검색 20~60ms 간격 50번 | FAST_CLICK |
| retry | MACRO | 팔린 좌석을 0.3~0.6초 간격 8번 | SAME_SEAT_RETRY |
| multi | RESELLER | 한 기기로 3계정이 몇 초 안에 선점 | MULTI_ACCOUNT_SYNC |
| cancel | CANCEL_ABUSER | 결제 1~3초 뒤 취소 × 3 | CANCEL_AFTER_PAY |

## 경계 측정 (2026-11-18, 로컬, `BOUNDARY=1`)

봇 강도를 여러 단계로 섞어 한 번에 돌렸다 (강도마다 3명, 정상 20명). 강도는 이메일의 `g{강도}`에 남고 `eval_risk.sh`가 강도별로 센다. 봇 행동 완수 100% (연타 480·409 78·취소 18, 계획과 정확히 같음).

| 봇 | 강도 → 탐지 | 문턱 (규칙) |
|---|---|---|
| fast 연타 수 | 10·15·19·**20 → 0%** · **21**·25·50 → 100% | 200ms 미만 간격 20회. 연타 N번이면 서버가 세는 간격은 N−1 (Mongo로 확인: 20번 → 19회, 21번 → 20회) |
| retry 같은 좌석 시도 | 3·**4 → 0%** · **5**·6·8 → 100% | 같은 좌석 실패 5회 |
| cancel 결제 직후 취소 | **1 → 0%** · **2**·3 → 100% | 30분 안 취소 2건 |
| multi 한 기기 계정 수 | **2**·3 → 100% (45점·55점) | 2계정 |
| steady 일정 간격 (300·500·1000ms) | **모두 0%** (20점) | REGULAR_INTERVAL은 걸림(변동계수 0.001~0.003 ≤ 0.05), 하지만 보조 규칙 15점이라 케이스가 안 열림 |
| normal | 0% (5점: 신규 계정만) | - |

**알게 된 것**
- **경계가 규칙 정의와 정확히 같다.** 문턱 한 칸 아래는 0%, 문턱부터 100%. 실제 HTTP → Kafka → Mongo → 배치 경로에서 세는 방식이 어긋나지 않음 (간격 개수 N−1만 주의)
- **문턱 바로 아래 봇은 점수도 0이다** (신규 계정 5점만). 규칙이 문턱 아래에서 점수를 전혀 주지 않는 계단 모양이라, 하루 연타 19번·좌석마다 4번씩 바꿔 가며 시도·취소 1건으로 조절하는 봇은 **흔적이 남아도 점수에 안 나타남**
- **일정 간격 매크로는 잡히지 않는다.** 200ms보다 느리게, 기계처럼 일정하게 새로고침하는 매크로(예: 취소표 새로고침)는 REGULAR_INTERVAL 15점뿐이라 케이스·대기열 순서에 거의 영향이 없음
- → 둘 다 **규칙 설계(강다인 님 RISK-02)의 판단 사항**이라 측정 결과로 공유하고, 바꿀지는 함께 정함. 후보: REGULAR_INTERVAL을 마커 규칙으로 / 문턱 아래 구간에도 작은 점수 / 같은 기기·CI의 "좌석별 시도" 합계로 SAME_SEAT_RETRY 보완
- 이번 탐지율 56.5%는 문턱 아래 봇을 일부러 섞은 값이라 목표(90%)와 비교하지 않는다. 목표 비교는 기본 실행(봇이 실제 매크로 수준)으로

```bash
./run.sh 12 -e BOUNDARY=1                     # 또는 FAST_LEVELS=10,19,21 RETRY_LEVELS=4,5 ... 직접
./tools/eval_risk.sh <tag>                    # "봇 강도별 탐지" 표
```

## 재측정 (2026-11-18 저녁, 규칙 보강 뒤)

위 경계 측정을 보고 강다인 님이 규칙 두 개를 고쳤다 (`bd18e4e`, ERD v24): ① **같은 좌석 재시도를 여러 좌석 합산** (좌석마다 두 번째 실패부터 더함, 한 좌석 최댓값과 합 중 큰 값) ② **REGULAR_INTERVAL을 마커 규칙으로** (케이스를 엶). ①을 재려고 **`rotate` 봇**(사 둔 좌석 3개를 돌아가며 좌석마다 문턱 아래로 시도)을 추가했다. 빈 로컬 DB, 강도마다 3명, 정상 20명, 봇 행동 완수 98/98.

| 봇 | 이전 | 이번 |
|---|---|---|
| steady 300·500·1000ms | 전부 0% (15점) | **전부 100%** (REGULAR_INTERVAL 케이스) |
| rotate 좌석 3개 × 좌석마다 2·3·4번 | (이전 규칙이면 한 좌석 최대 4 < 5라 0%) | 2번 0% · **3번·4번 100%** (합 = 3 × (n−1) = 6·9 ≥ 5) |
| retry · fast · cancel · multi | 4/5 · 20/21 · 1/2 · 2 경계 | 그대로 |
| normal | 오탐 0% | **오탐 0%** |

**남는 빈틈 (규칙 설계 판단)**: 좌석마다 **한 번씩만** 시도하면 첫 실패를 세지 않아 좌석을 아무리 많이 돌아도 0점. 사람도 "이미 잡힌 좌석" 한 번은 흔해서 일부러 뺀 것이라, 막으려면 "짧은 시간에 서로 다른 좌석 실패 N개" 같은 별도 신호가 필요하다.

```bash
./run.sh 12 -e BOUNDARY=1      # rotate 포함 (ROTATE_LEVELS=2,3,4, ROTATE_SEATS=3)
```

## 왜 이렇게 했나

- **봇 하나에 규칙 하나**: 여러 규칙을 같이 건드리면 탐지돼도 어느 규칙 덕인지, 놓쳐도 어느 규칙이 약한지 모름
- **라벨은 이메일에, 서버로는 안 보냄**: 앱 코드가 라벨을 볼 길이 없어야 평가가 공정. 평가 스크립트만 Oracle에서 읽어 `synthetic_label`(ERD의 정답 테이블)에 넣음
- **카드·기기를 사람마다 다르게**: 시나리오 11처럼 모두 같은 카드를 쓰면 결제 수단 하나에 50계정이 묶여 그 카드의 취소 봇 점수가 전원에게 번짐 → 현실과 다른 오탐
- **회원 기준으로 셈**: 케이스는 CI·결제 수단·기기 단위로 열리지만 목표는 "사람"의 탐지율. 회원에 연결된 대상 중 하나라도 케이스가 있으면 탐지
- **비밀값은 컨테이너 안에서만**: 평가 스크립트가 DB 비밀번호를 명령줄·화면에 올리지 않음

## 주의할 점

- **`member_device`를 채우는 곳이 아직 없습니다** (실행 후 0행). 그래서 기기 점수의 연결 계정 수가 0이고, 관리자 화면에서 기기 케이스의 회원이 안 보입니다. 평가는 Mongo `behavior_log`의 (회원, 기기) 쌍으로 대신 연결합니다 → 강다인 님께 공유
- 정상 사용자 점수 5점은 `NEW_ACCOUNT`(가입 7일 미만) 가산입니다. 문제 아님
- 반복 실행하면 좌석이 줄어듭니다. 실행 태그가 달라 계정은 겹치지 않습니다
- 평가는 배치 뒤에 (스크립트가 `risk:dirty`가 빌 때까지 기다림)
