# 관리자 로그인 (AUTH-05, A-01)

작성자: 조영준 · 코드 위치: `com.jejari.auth.admin` (`AdminLoginService`, `AdminAuthController`, `AdminAccountRepository`, `AdminBootstrap`), `auth/AdminRole`

## 한 줄 요약

관리자는 `POST /api/v1/admin/auth/login`으로 회원과 같은 방식·같은 보호 장치로 로그인하고, 토큰에 세부 권한(VIEWER·REVIEWER·SUPERVISOR)이 함께 담긴다.

## 어떻게 동작하나

```
POST /api/v1/admin/auth/login {loginId, password}
  → IP당 분당 시도 제한 → ID별 연속 실패 잠금(5회/15분) → Argon2id 검증(없는 ID도 같은 시간)
  → 비활성이면 AUTH_BANNED → 성공: 액세스 토큰(adm 클레임) + 리프레시 쿠키
재발급·로그아웃: 회원과 같은 /api/v1/auth/refresh, /api/v1/auth/logout
```

- 회원 로그인(강다인)의 부품을 그대로 씁니다: `PasswordHasher`, `AuthLimiter`(Redis 잠금), `AuthPolicy`(5회·15분 등 app_policy 값), `LoginAttemptLog`
- 시도는 모두 MongoDB `login_attempt`에 `actor_type = ADMIN`, `admin_id`로 남습니다 (관리자 계정 무차별 대입 탐지)
- 토큰: `{"role":"ADMIN","adm":"SUPERVISOR",...}` → 권한 `ROLE_ADMIN` + `ADMIN_VIEWER`·`ADMIN_REVIEWER`·`ADMIN_SUPERVISOR` (상위 권한은 하위를 모두 가짐)

## 관리자 API 만들 때 (다른 팀원용)

```java
@GetMapping("/api/v1/admin/cases/{id}/timeline")           // /api/v1/admin/** 는 이미 ADMIN만 통과
@PreAuthorize("hasAuthority('ADMIN_VIEWER')")              // 세부 권한 (기능설계서 7장 표의 VIEWER/REVIEWER/SUPERVISOR)
Timeline timeline(@PathVariable long id, @AuthenticationPrincipal AuthPrincipal me) {
    long adminId = me.adminId();                            // 회원 토큰이면 403
    AdminRole role = me.adminRole();
}
```

권한이 모자라면 `403 ADMIN_FORBIDDEN` (공통 실패 형식, traceId 포함).

## 첫 관리자 계정

`.env`에 `JEJARI_ADMIN_BOOTSTRAP_ID`·`JEJARI_ADMIN_BOOTSTRAP_PASSWORD`를 넣고 앱을 띄우면, **admin_user가 비어 있을 때만** SUPERVISOR 1명(admin_id = 1)이 만들어집니다. 이미 있으면 아무것도 하지 않습니다. 만든 뒤에는 비밀번호를 `.env`에서 지워도 됩니다.

## 왜 이렇게 했나

- **회원 로그인 부품 재사용**: 잠금·시도 제한·더미 해시·시도 기록을 두 벌 만들면 한쪽만 고쳐지는 일이 생깁니다.
- **pepper는 현재 값으로 고정**: admin_user에 `pepper_key_id` 컬럼이 없습니다. 관리자는 몇 명뿐이라 ERD를 늘리지 않고, pepper를 바꾸면 관리자 비밀번호만 다시 설정합니다 (2026-11-17 결정).
- **첫 계정을 기동 때 만드는 이유**: 비밀번호 해시가 각자의 pepper에 묶여 있어 시드 SQL로 같은 해시를 나눠 줄 수 없습니다.
- **세부 권한은 토큰에만 먼저**: 1차는 `ADMIN` 하나로 막고, 관리자 API가 생길 때 `@PreAuthorize`만 붙이면 됩니다 (토큰 형식은 그대로).
- **재발급 때마다 DB 권한을 다시 읽음**: 관리자를 비활성화하면 다음 재발급(최대 15분 뒤)에 세션이 닫힙니다(`revoke_reason = ADMIN`). 권한을 바꿔도 다음 재발급부터 반영됩니다.

## 확인한 것 (2026-11-17, 실제 Oracle·Redis·Mongo)

| 시나리오 | 결과 |
|---|---|
| 기동 시 첫 관리자 생성 | admin_id=1 SUPERVISOR |
| `" Admin "`로 로그인 (공백·대문자) | 200, 토큰에 `adm: SUPERVISOR` |
| 관리자 토큰으로 회원 API(대기열) | 403 ACCESS_DENIED |
| 틀린 비밀번호 5회 → 6회째, 맞는 비밀번호 | AUTH_LOCKED, AUTH_LOCKED |
| 비활성화 후 재발급 / 로그인 | AUTH_REFRESH_INVALID(세션 ADMIN 폐기) / AUTH_BANNED |
| login_attempt | actor_type=ADMIN, admin_id로 10건 |

## 공용 서버에서 확인 (2026-11-18, HTTPS · 앱 2대)

- 첫 관리자 계정이 서버 `.env`로 자동 생성됨 (`admin`, SUPERVISOR)
- 로그인 → 관리자 API → 토큰 없음 401 · 회원 API 403 → 쿠키 재발급 → 로그아웃 → 재발급 401 모두 기대대로. HTTPS라 Secure 쿠키가 실제로 오감
- **화면 A-01**: 강동균 님이 대신 만든 `frontend/src/admin/AdminLogin.jsx`를 검토 — 요청 필드(`loginId`·`password`), 토큰은 메모리에만, 새로고침 때 `/api/v1/auth/refresh` 쿠키 재발급이 이 API와 맞음. 화면 디자인(시안 대비)은 브라우저로 한 번 더 볼 것

## 주의할 점

- 관리자 로그인은 회원과 **같은 IP 시도 제한 카운터**(`rate:login:{ipHash}`)를 씁니다. k6로 로그인 부하를 걸 때 같이 소진됩니다.
- 관리자 세부 권한 표(어떤 API가 어떤 권한인지)는 기능설계서 7장을 따릅니다.
- TOTP(2단계 인증)는 P3, `mfa_secret_enc` 컬럼만 있습니다.
