# 모니터링 대시보드 (INF-04 · ADM-10)

작성자: 조영준 · 코드 위치: `docker/grafana/dashboards/jejari-overview.json`, `docker/prometheus/prometheus.yml`, `compose.yaml`(redis-exporter), `application.yml`(`management.metrics`)

## 한 줄 요약

`docker compose up -d` 후 http://localhost:3000 → Jejari 폴더 → **제자리 · 앱 개요**. 부하를 걸었을 때 "어디서 느려지는지"를 위에서 아래로 좁혀 보는 대시보드다.

## 어떻게 동작하나

```
앱(/actuator/prometheus) ─┐
redis-exporter(:9121) ────┼─→ Prometheus(5초마다 수집) ─→ Grafana(대시보드 파일 자동 등록)
```

- 앱: Spring Boot Actuator + Micrometer. 응답 시간 p95·p99를 계산하려고 HTTP·Redis·커넥션 획득 시간에 **히스토그램 버킷**을 켬
- Redis 서버: 앱 메트릭은 "명령이 얼마나 걸렸나"만 보여서, 메모리 사용량·한도·밀려난 키는 redis-exporter로 따로 수집
- 대시보드는 JSON 파일이라 저장소에 커밋되고, 모두 같은 화면을 봅니다

## 보는 순서 (병목 찾기)

| 줄 | 보는 것 | 이렇게 보이면 |
|---|---|---|
| 한눈에 보기 | 초당 요청, p95, 5xx 비율, Heap·DB 커넥션·Redis 메모리 사용률 | 빨간 칸부터 아래 줄에서 원인 찾기 |
| HTTP 요청 | API별 초당 요청·p95, 상태 코드 | 특정 API만 느린가? 409·429는 정상 거절일 수 있음 |
| 스레드 · DB 커넥션 | Tomcat 사용 중/최대, Hikari 사용 중/대기/최대, 커넥션 얻는 시간 | Tomcat이 최대에 붙음 → 요청이 스레드를 기다림. Hikari 대기 > 0 → DB 커넥션 부족 또는 느린 쿼리 |
| Redis | 명령별 p95·초당 호출(EVALSHA = Lua), 서버 메모리, 밀려난 키 | Lua p95가 오르면 Redis가 병목. 밀려난 키는 **항상 0**이어야 함 (noeviction) |
| Kafka · 업무 | 발행·소비 속도, 좌석 반환(사유별) | 발행 평균 시간이 오르면 Outbox 릴레이가 밀림 |
| JVM | Heap, GC 멈춤, CPU, 스레드 | GC 멈춤이 오르면 응답 시간도 같이 튐. CPU의 "머신"은 k6를 같은 PC에서 돌리면 같이 오름 |

## 왜 이렇게 했나

- **k6보다 먼저**: 개선 전후 TPS·응답 시간을 비교하려면 측정 기준(같은 패널·같은 쿼리)이 먼저 있어야 합니다.
- **평균 대신 p95·p99**: 명절 예매는 "대부분 빠르고 일부가 몹시 느린" 모양이라 평균은 문제를 숨깁니다. 히스토그램 버킷이 있어야 Prometheus에서 계산할 수 있습니다.
- **수집 5초**: 부하 테스트 중 짧은 튐을 보려고. 보관은 15일.
- **Redis 서버 지표를 따로**: 좌석 키가 사라지면 이중 판매라, 메모리가 한도(maxmemory)에 얼마나 가까운지가 핵심 지표입니다 (concurrency.md §14.5).

## 확인한 것 (2026-11-17)

- 수집 대상 3개(앱·Redis·Prometheus) UP
- 트래픽을 흘린 뒤 대시보드 쿼리 37개를 Prometheus에서 직접 실행 → 36개 값 있음, 오류 0. 빈 1개(좌석 반환)는 카운터가 첫 반환 때 생기는 방식이라 예약 흐름을 돌리면 나타남
- Grafana에 파일로 등록됨, Grafana를 통한 조회도 정상

## 주의할 점

- 앱은 호스트(IDE)에서 돌고 Prometheus는 컨테이너라 `host.docker.internal:8080`을 수집합니다. 앱을 여러 대·다른 포트로 띄우면 `docker/prometheus/prometheus.yml`의 `targets`에 추가합니다 (instance 이름으로 구분).
- 대시보드를 Grafana 화면에서 고쳤다면 **Export → JSON**으로 `docker/grafana/dashboards/`에 덮어써 커밋해야 다른 팀원에게도 반영됩니다.
- 히스토그램 버킷은 시계열 수를 늘립니다. 메트릭을 새로 켤 때는 `minimum/maximum-expected-value`로 범위를 좁힙니다.
- 아직 없는 것: Oracle 서버 지표(세션·대기 이벤트), Kafka 소비 지연(lag). 병목 분석(PERF-01) 때 필요하면 exporter를 추가합니다.
