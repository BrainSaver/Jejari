# 성능 측정: 공용 서버 앱 1대 vs 2대 (PERF-01)

작성자: 조영준 · 도구: k6 시나리오 11(`loadtest/scenarios/11_user_journey.js`), 서버 Prometheus

> 공용 서버(GCP e2-standard-4, vCPU 4·메모리 15GB 한 대)에서 **실제 사용자 흐름 전체**(로그인 → 조회 → 대기열 → 좌석 배치도 → 선점 → 결제)를 돌려, 앱을 2대로 늘리면 빨라지는지 쟀다.

## 한 줄 요약

**이 서버에서는 앱 2대가 1대보다 느리다.** 예매 전체 p95가 1대 8.0초, 2대 14.6~18.0초. CPU 4개를 DB·Kafka·앱이 함께 쓰고 있어 CPU가 이미 100%이고, 앱을 하나 더 띄우면 일을 나눠 갖는 게 아니라 **같은 CPU를 두고 다툰다**. 2대의 의미는 지금은 처리량이 아니라 **무중단 배포·장애 대비**다.

## 조건

- 사용자 200명이 20초 안에 흩어져 도착, 한 명이 예매 한 번 (계정은 측정 전에 만들어 둠)
- k6는 내 PC에서 인터넷을 거쳐 서버로 (서버 CPU를 k6가 쓰지 않게)
- 운행: 같은 열차(525석)의 빈 운행을 측정마다 따로 (2대 703341 · 1대 703351 · 2대 다시 703361). 좌석 경쟁 조건이 같음
- 2대를 먼저 재서 예열 효과가 의심돼 **1대 뒤에 2대를 한 번 더** 잼
- 측정 동안만 IP당 가입·로그인 제한을 허용 최댓값으로 올렸다가 되돌림 (모든 요청이 내 PC IP 하나에서 나가서). 바탕 부하는 대기열 개선 뒤라 CPU 24%

| 로그인 p95 | 7.0초 | **2.4초** | 5.9초 |

| 결제 p95 | 3.7초 | **1.1초** | 2.8초 |
| 대기열 진입 p95 | 3.6초 | **0.7초** | 1.9초 |
| 처리한 요청 | 초당 43 | 초당 42 | 초당 40 |
| VM CPU 최대 | 100% | 99% | 100% |

- 처리량이 세 번 다 초당 40 남짓인 건 도착 속도(200명/20초)가 정한 값. 서버 한계를 잰 것은 아님

## 왜 2대가 느린가

1. **CPU가 이미 꽉 참**: 세 번 모두 VM CPU 99~100%. 앱 하나가 더 떠도 CPU는 4개 그대로라 처리량이 늘 수 없음
2. **로그인(Argon2id)이 CPU를 가장 많이 씀**: 비밀번호 해시는 일부러 느리고 무거움. 앱마다 동시에 해시 32개까지 허용(`auth.max_concurrent_hash`)이라 2대면 64개가 CPU 4개를 두고 다툼 → 모든 요청이 같이 느려짐. 로그인 p95가 1대 2.4초 → 2대 5.9~7.0초
3. **JVM 두 개의 메모리 정리(GC)**: 앱마다 힙 1GB. Argon2가 해시마다 메모리를 크게 써서 GC가 잦아지고, 그동안 그 앱의 요청이 멈춤
4. **DB 커넥션 대기**: 앱마다 풀 10개. 느려진 요청이 커넥션을 오래 잡아 대기가 생김(최대 64). 원인이라기보다 CPU 부족의 결과

## 개선 1: 동시 해시 수 32 → 4 (2026-11-19 오전, 같은 조건)

정책값 `auth.max_concurrent_hash`만 4(CPU 수)로 바꾸고 앱을 재시작해 다시 잼 (2대 703371 · 1대 703381). 코드 변경 없음.

| 항목 | 2대 · 해시 32 | 2대 · **해시 4** | 1대 · 해시 32 | 1대 · **해시 4** |
|---|---|---|---|---|
| 예매 성공 | 200/200 | **178/200** (로그인 503 21건) | 200/200 | **200/200** |
| 예매 전체 p95 | 14.6~18.0초 | 10.0초 | 8.0초 | **4.9초** |
| 로그인 p95 | 5.9~7.0초 | 4.9초 | 2.4초 | 2.6초 |
| 좌석 선점 p95 | 4.6~6.3초 | 2.3초 | 1.9초 | **0.55초** |
| 결제 p95 | 2.8~3.7초 | 1.4초 | 1.1초 | **0.47초** |
| 좌석 배치도 p95 | 3.1~4.4초 | 1.5초 | 1.6초 | **0.37초** |
| DB 커넥션 대기 최대 | 21~64 | 1 | 16 | **0** |
| GC 일시정지 합 | 2.8~4.8초 | - | 2.3초 | **1.0초** |

- **로그인 뒤 단계가 3~4배 빨라짐**: 해시가 CPU를 덜 차지해 선점·결제·배치도가 CPU를 얻음. 메모리도 덜 써 GC가 절반
- **로그인 자체는 거의 그대로**: 해시는 줄을 서서 기다리는 시간이 생긴 대신 계산이 빨라짐
- **2대 + 해시 4에서 로그인 21건이 503**: 해시 자리를 3초 안에 못 얻으면 거절하는 설계(`PasswordHasher`, 서버 보호). 1대에선 0건 → 2대가 CPU를 다투며 해시 하나가 느려져 줄이 길어진 것
- **결론**: 이 서버에서 가장 좋은 조합은 **앱 1대 + 해시 4** (예매 p95 8.0 → 4.9초, 선점 p95 1.9초 → 0.55초). 다만 실제 운영 값을 바꾸는 건 두 가지를 정한 뒤:
  1. 앱 1대로 두면 무중단 배포가 안 됨 (배포 때 1~2분 멈춤)
  2. 해시 4에서 로그인이 몰리면 503이 날 수 있음 → 화면이 503을 "잠시 뒤 다시"로 안내하는지 (가입·로그인 담당 강다인 님)
- 측정 뒤 서버 값은 모두 원래대로 되돌림 (해시 32, 앱 2대)

## 결정: 앱 1대 + 해시 4 (2026-11-19 오후, 팀 결정)

무중단 배포를 지키는 대안 "앱 2대 + 앱마다 해시 2(합 4)"를 같은 조건으로 한 번 더 쟀다 (운행 100034, 12/6).

| 항목 | 1대 · 해시 4 | 2대 · 해시 2 | 2대 · 해시 4 |
|---|---|---|---|
| 예매 성공 | **200/200** | 155/200 (로그인 503 45건) | 178/200 (503 21건) |
| 예매 전체 p95 (성공한 사람) | **4.9초** | 8.0초 | 10.0초 |
| 좌석 선점 p95 | **0.55초** | 2.6초 | 2.3초 |
| 로그인 p95 | 2.6초 | 4.2초 | 4.9초 |

- 2대에서는 앱마다 해시 자리가 더 적어 줄이 길어지고, 3초 안에 자리를 못 얻은 로그인이 503으로 거절됨. CPU는 여전히 100%라 2대가 처리량을 늘리지 못함
- **결정: 앱 1대 + 해시 4.** 대가는 배포 때 재시작하는 40초~1분 느려짐(Caddy가 최대 45초 기다렸다 보냄, 502 대신). 시연 중에는 자동 배포를 끔
- 적용: `jejari@8081` 끔, `deploy.sh`는 켜 둔 앱만 재시작, Caddy·Prometheus에서 8081 제외, `auth.max_concurrent_hash` 4. 되돌리는 법은 `deploy/README.md` "앱 1대 ↔ 2대 전환"
- 2대는 버린 게 아니라 **멀티 인스턴스 검증용**으로 쓴 것: 대기열 입장 인원 2배 문제를 2대여서 찾았음. CPU를 따로 가진 VM이 있다면 다시 2대가 맞음

| 앱을 다른 VM에 | 2대의 효과를 제대로 보려면 CPU를 따로 가져야 함 | 비용이 들어 판단 필요 |

## 같이 발견한 것

- **관리자 정책 API가 허용 범위 밖의 값도 저장함**: 처음에 제한을 10000으로 올렸더니 API는 성공했지만 앱은 "범위(1~100) 밖이라 기본값을 씀" 경고를 남기고 기본값 10을 씀. 관리자는 바뀐 줄 아는데 실제로는 그대로 → ADM-08(내 담당)에서 저장 전에 범위를 검사해야 함
