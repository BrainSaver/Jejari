## 한 줄 요약

계획한 뼈대는 **강다인 님이 구현**했고, 2장 점검에서 나온 버그·노이즈·경계 유형·카드 공유(#1·2·3·5)도 **반영 후 재점검까지 끝났다** (5장). 이제 오탐률 0%는 정상 회원에게 사람다운 실수가 들어간 상태에서 나온 값이다. 남은 것은 **봇 쪽 경계(#4·6)**와 **아직 0회인 규칙 2개(LAST_MINUTE_CANCEL·REGULAR_INTERVAL)**이고, 조영준이 맡는다.

> 2장은 2026-11-17 첫 점검 기록이다 (그 뒤 고쳐짐). 최신 수치는 5장.

## 2. 점검 결과 (2026-11-17, 내 PC, 1,000명 재생성)

### 결과는 재현됨

| 종류 | 인원 | 탐지 | 점수 |
|---|---|---|---|
| normal | 910 | 0 | 평균 0.5, 최고 10 |
| fast · retry · cancel | 20씩 | 20씩 | 25 · 20 · 15 |
| multi | 30 | 30 | 50 |

### 버그 1건: 앱으로 결제한 적이 있는 DB에서 생성 실패

- 증상: `ORA-00001 PK_PAYMENT` — 회원 1,000명만 들어가고 예약 0건에서 멈춤
- 원인: 앱은 `payment_id = reservation_id`로 쓰는데(`PaymentStartTx`), 생성기는 `payment_seq`에서 번호를 받음 → 앱이 만든 결제 번호와 겹침. 통합 테스트는 결제가 없는 DB라 드러나지 않음
- 영향: 각자 PC(시나리오 11·12를 돌린 DB)와 **공용 서버**에서 실패
- 수정 제안 (한 줄): `VALUES (payment_seq.NEXTVAL, …)` → `VALUES (?, …)`에 `r`(예약 번호)을 넣기. 로컬에서 이렇게 고쳐 재현까지 확인했고, 강다인 님 파일이라 커밋은 하지 않음

### 시험되지 않는 규칙 5개

이 데이터로 점수를 낸 대상(CI·카드·기기)의 근거(`risk_score.reasons`)를 모두 셌다.

| 규칙 | 발동 | 왜 안 걸리나 |
|---|---|---|
| FAST_CLICK · SAME_SEAT_RETRY · CANCEL_AFTER_PAY | 40씩 | 봇 대상 (CI·기기 또는 CI·카드) |
| LINKED_ACCOUNTS | 33 | 다계정 기기 10 + 가족 공유 기기 23 (정상 최고 10점의 원인) |
| MULTI_ACCOUNT_SYNC | 10 | 다계정 묶음 |
| **BULK_PURCHASE** | 0 | 회원당 최대 3건·6매 (문턱 20매) |
| **HIGH_CANCEL_RATIO** | 0 | 구매 4건 이상일 때만 계산하는데 최대 3건 |
| **LAST_MINUTE_CANCEL** | 0 | 출발 전 분이 2,035~21,975분 (문턱 180분) |
| **REGULAR_INTERVAL** | 0 | 일정 간격 매크로 없음 (봇 간격은 무작위) |
| **NEW_ACCOUNT** | 0 | 일부러 피함 (의도) |

### 오탐률 0%가 설계상 당연함

- 정상 회원의 클릭 간격이 **800~6,000ms**라 200ms 미만이 한 번도 없음 → FAST_CLICK 오탐이 나올 수 없음. 실제 사람은 더블클릭·새로고침 연타가 가끔 있음
- 정상 회원에게 좌석 선점 실패(409)가 없음 → 인기 열차에서 사람끼리 부딪히는 상황이 빠짐
- 봇은 문턱을 확실히 넘게, 정상은 확실히 안 넘게 만들어져 있어 **경계를 재지 않음**

→ 지금 숫자는 "규칙이 실제 테이블·해시·배치를 거쳐 끝까지 동작한다"는 확인이다. 목표(탐지율 90%·오탐률 5%)를 **달성했다고 말하려면** 아래 3장이 필요하다.

## 4. 공용 서버에서 쓸 때

- 생성기는 앱 전체를 띄웠다 끄는 방식이라, **서버 앱(8080·8081)이 떠 있으면 포트가 겹치고 배치가 두 곳에서 돌 수 있음** → 앱을 잠시 멈추거나 `--server.port=0`으로 실행하는 방법을 정해야 함
- 1번 버그는 고쳐짐 (`31bca5b`)
