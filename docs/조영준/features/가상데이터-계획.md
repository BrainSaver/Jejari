# 가상 회원·예매 데이터 계획 (DATA-02)

작성자: 조영준 · 담당: E 조영준 · D 강다인 · 상태: **계획 초안 (강다인 님 확인 전)**

> 이 데이터가 있어야 봇 탐지 평가(DATA-03, [시나리오 12](부하테스트-봇-탐지.md))가 실제 상황을 반영합니다. DATA-03은 DATA-02 없이도 돌아가지만, 지금은 모든 계정이 방금 가입했고 과거 이력이 없어서 30일 기준 규칙을 시험하지 못합니다.

## 한 줄 요약

**"한 달 동안 서비스를 써 온 회원들"**을 만든다. 오래된 계정과 지난 30일의 구매·취소 이력 위에서 시나리오 12를 돌려야 탐지율·오탐률이 실제 상황에 가깝다.

## 1. 왜 필요한가

위험 점수 엔진(`RiskInputReader`)이 읽는 것과 지금 시나리오 12의 상태:

| 엔진이 읽는 것 | 기간 | 지금 |
|---|---|---|
| `reservation.confirmed_at`, `seat_count` (누적 구매) | 30일 | 오늘 산 1~3건뿐 |
| `cancellation`의 사용자 취소, 구매 후·출발 전 몇 분인지 | 30일 | 오늘 취소한 것뿐 |
| 같은 CI·카드·기기로 묶인 계정 수, 가장 오래된 계정의 가입 시각 | - | 전원 방금 가입 (`NEW_ACCOUNT` +5) |
| 행동 로그 (클릭 간격, 선점 실패) | 1일 | k6가 만듦 |

그래서 DATA-02는 **Oracle 쪽 과거 이력**을 만들고, 행동 로그는 지금처럼 k6(DATA-03)가 맡는다.

## 2. 만들 사람들 (기본 1,000명, 숫자는 바꿀 수 있음)

| 정답 라벨 | 유형 | 비율 | 30일 이력 | 노리는 것 |
|---|---|---|---|---|
| NORMAL | 일반 | 75% | 구매 0~2건, 취소는 드묾 | 기본 오탐 |
| NORMAL | **가족 다구매** | 8% | 한 번에 4매씩 여러 번 (누적 매수가 문턱 근처) | 봇처럼 보이는 정상 |
| NORMAL | **일정 변경이 잦은 사람** | 5% | 취소 2~3건, 대부분 구매 며칠 뒤 | 취소 규칙의 오탐 |
| NORMAL | **출장자** | 4% | 출발 직전 취소 1~2건 | `LAST_MINUTE_CANCEL` 오탐 |
| RESELLER | 다계정 되팔이 | 3% (묶음 3~5계정) | 차명 계정이 카드 하나를 같이 씀, 누적 40매 이상, 취소 비율 높음 | 결제 수단 연결, `BULK_PURCHASE` |
| CANCEL_ABUSER | 취소 남용 | 3% | 구매 30분 안 취소 5건 이상, 출발 직전 취소 | `CANCEL_AFTER_PAY` |
| MACRO | 매크로 | 2% | 이력은 평범 | 계정만 만들고 행동은 시나리오 12가 맡음 |

**원칙: 문턱에 맞춰 만들지 않는다.**
- 유형은 "그런 사람이 실제로 어떻게 행동하나"로 정한다. 데이터를 규칙에 맞춰 만들면 탐지율이 당연히 100%가 나와서 측정 의미가 없어진다.
- 정상 회원 중 일부(가족 다구매, 일정 변경, 출장자)는 일부러 경계 근처에 둔다. 오탐률 5% 목표는 이런 회원이 있어야 의미가 있다.
- 분포의 근거(코레일 통계, DATA-04 Kaggle 분석 등)는 `synthetic_label.generation_params`에 남긴다. 위 비율은 **[가정]**이며 근거를 찾으면 바꾼다.

## 3. 만드는 방법: 앱 안의 Java 생성기

`./gradlew syntheticData`처럼 앱의 부품을 그대로 쓰는 생성기를 만든다. 개발 모드에서만 실행되고 공용 서버의 운영 설정에서는 막는다.

**SQL 시드가 아닌 이유**

| 이유 | 설명 |
|---|---|
| 해시가 앱과 같아야 함 | CI는 `Pseudonymizer.mockCiHash`, 카드는 결제 수단 해시, 비밀번호는 `PasswordHasher.hash`. 다르게 만들면 엔진이 같은 사람·같은 카드로 묶지 못함 (강다인 님 문서 `회원가입-본인인증.md`의 요청) |
| pepper·암호화 키가 팀원마다 다름 | 각자 PC에서 돌리면 각자의 키로 맞게 만들어짐. 시드 SQL로는 공유할 수 없음 (관리자 첫 계정을 기동 때 만드는 것과 같은 이유) |
| 과거 날짜 | API로는 30일 전 구매를 만들 수 없어 DB에 직접 넣음 |

**생성기가 하는 일**

1. **회원:** `member`, `member_credential`, `payment_method`를 만들고 가입 시각을 1~400일 전으로 흩뜨린다. 비밀번호 해시는 한 번만 계산해 전원이 같이 쓴다 (Argon2를 1,000번 돌리면 몇 분 걸림, 가상 데이터라 문제없음).
2. **지난 운행:** 출발이 끝난 운행(`DEPARTED`)을 따로 만든다. 운행 번호 구간을 분리해 판매 중인 운행 9001·9002와 매수 제한에 영향을 주지 않는다.
3. **예매 이력:** 지난 30일 기준으로 예약(`reservation`, `reservation_seat`), 결제(`payment` 승인·환불), 취소(`cancellation`, 구매 후·출발 전 분 포함)를 넣는다.
4. **정답:** `synthetic_label`에 유형과 묶음 번호(`group_id`), 생성 파라미터를 넣는다.
5. **위험 점수 계산 요청:** 만든 CI와 카드를 `risk:dirty`에 넣어 1분 배치가 계산하게 한다 (배치는 새 신호가 생긴 대상만 계산함).
6. **재현과 정리:** 같은 `SEED`면 같은 데이터. 이메일 도메인(`@synthetic.example.com`)과 운행 번호 구간으로 한 번에 지우는 정리 스크립트를 같이 둔다.

**구현하면서 확인할 것**
- 지난 운행에 `seat_inventory`가 꼭 필요한지, 예약·결제·취소 테이블의 CHECK 제약(상태별 필수 컬럼)을 어떻게 맞출지
- 현재 테이블로 안 되면 ERD 변경을 강동균 님께 요청 (지금은 필요 없어 보임)

## 4. DATA-03와 합치기

- 시나리오 12에 `ACCOUNTS=synthetic` 옵션 추가: 새로 가입하는 대신 DATA-02 계정으로 로그인해서 행동한다
- `eval_risk.sh`는 그대로 쓰고, 정답을 이메일 대신 `synthetic_label`에서 읽도록만 바꾼다
- 결과는 두 가지로 나눠 본다
  - **과거 이력만으로 잡히는가:** k6 없이 배치만 돌린 뒤 RESELLER와 CANCEL_ABUSER 확인
  - **이력 위에 행동까지 얹었을 때:** 시나리오 12를 함께 돌림

## 5. 역할 나누기

| 조영준 (E) | 강다인 (D) |
|---|---|
| 생성기 틀, Oracle 적재, 지난 운행, 정리 스크립트, k6 연동, 평가 | 유형별 행동 분포 검토, 해시 함수 사용법 검토 |

규칙을 만든 사람이 데이터를 맞추면 데이터가 규칙 쪽으로 기울 수 있다. 그래서 강다인 님은 "이 사람이 현실적인가"를 위주로 본다.
