# 가상 회원·예매 데이터 (DATA-02) — 계획과 점검

> 구현 문서: [강다인 · 가상데이터-생성](../../강다인/features/가상데이터-생성.md) (`src/main/java/com/jejari/synthetic/`)

## 한 줄 요약

계획한 뼈대(오래된 계정, 지난 이력, 실제와 같은 해시, 태그 단위 생성·삭제)는 **강다인 님이 구현했고 결과도 재현된다** (1,000명, 탐지율 100%·오탐률 0%). 다만 **위험 규칙 10개 중 5개는 이 데이터로 한 번도 시험되지 않고**, 정상 회원에게 사람다운 실수가 없어 오탐률 0%가 설계상 당연한 값이다. 남은 일은 이 두 가지다.

## 1. 계획 대비 구현

| 계획 | 구현 | 비고 |
|---|---|---|
| 앱 안 Java 생성기 (해시를 앱과 같은 함수로, 각자 키로) | ✅ `--spring.profiles.active=synthetic` | `mockCiHash`·`PiiCipher`·카드·기기 HMAC |
| 오래된 계정 (`NEW_ACCOUNT` 가산 피함) | ✅ 정상 30~730일, 봇 8~67일 | |
| 지난 이력 (구매·결제·취소) | ✅ 최근 20일, 전용 "출발한 운행"(880001~) | 판매 중 운행 9001·9002 재고는 건드리지 않음 |
| 정답 라벨 (`synthetic_label`) | ✅ 시나리오 12와 같은 이메일 규칙 → `eval_risk.sh`가 기록 | 생성 파라미터(seed 등)는 라벨에 안 남음 |
| `risk:dirty` 표시 → 점수 계산 | ✅ 생성 직후 그 자리에서 배치까지 | 앱을 따로 켤 필요 없음 |
| 재현·정리 | ✅ `seed`, 태그 단위 `cleanup` | |
| 행동 로그 | ✅ 생성기가 직접 만듦 (계획은 k6가 맡기로 했음) | 로그인 없이 대량으로 가능 |
| `member_device` | ✅ 행동 로그 적재 때 기록 (같은 날 수정) | 시나리오 12에서 발견한 빈틈 |
| 경계 근처 정상 회원 (가족 다구매·일정 변경·출장자) | ❌ 가족 기기 공유만 | 2장 |
| 다계정이 카드 하나 공유 (결제 수단 연결) | ❌ 다계정은 기기만 공유, 카드는 각자 | 2장 |
| 로그인 가능한 계정 (이력 위에 k6 행동) | ❌ 비밀번호 없음 | 3장 |

## 2. 점검 결과 (2026-11-17, 내 PC, 1,000명 재생성)

### 결과는 재현됨

| 종류 | 인원 | 탐지 | 점수 |
|---|---|---|---|
| normal | 910 | 0 | 평균 0.5, 최고 10 |
| fast · retry · cancel | 20씩 | 20씩 | 25 · 20 · 15 |
| multi | 30 | 30 | 50 |

### 버그 1건: 앱으로 결제한 적이 있는 DB에서 생성 실패

- 증상: `ORA-00001 PK_PAYMENT` — 회원 1,000명만 들어가고 예약 0건에서 멈춤
- 원인: 앱은 `payment_id = reservation_id`로 쓰는데(`PaymentStartTx`), 생성기는 `payment_seq`에서 번호를 받음 → 앱이 만든 결제 번호와 겹침. 통합 테스트는 결제가 없는 DB라 드러나지 않음
- 영향: 각자 PC(시나리오 11·12를 돌린 DB)와 **공용 서버**에서 실패
- 수정 제안 (한 줄): `VALUES (payment_seq.NEXTVAL, …)` → `VALUES (?, …)`에 `r`(예약 번호)을 넣기. 로컬에서 이렇게 고쳐 재현까지 확인했고, 강다인 님 파일이라 커밋은 하지 않음

### 시험되지 않는 규칙 5개

이 데이터로 점수를 낸 대상(CI·카드·기기)의 근거(`risk_score.reasons`)를 모두 셌다.

| 규칙 | 발동 | 왜 안 걸리나 |
|---|---|---|
| FAST_CLICK · SAME_SEAT_RETRY · CANCEL_AFTER_PAY | 40씩 | 봇 대상 (CI·기기 또는 CI·카드) |
| LINKED_ACCOUNTS | 33 | 다계정 기기 10 + 가족 공유 기기 23 (정상 최고 10점의 원인) |
| MULTI_ACCOUNT_SYNC | 10 | 다계정 묶음 |
| **BULK_PURCHASE** | 0 | 회원당 최대 3건·6매 (문턱 20매) |
| **HIGH_CANCEL_RATIO** | 0 | 구매 4건 이상일 때만 계산하는데 최대 3건 |
| **LAST_MINUTE_CANCEL** | 0 | 출발 전 분이 2,035~21,975분 (문턱 180분) |
| **REGULAR_INTERVAL** | 0 | 일정 간격 매크로 없음 (봇 간격은 무작위) |
| **NEW_ACCOUNT** | 0 | 일부러 피함 (의도) |

### 오탐률 0%가 설계상 당연함

- 정상 회원의 클릭 간격이 **800~6,000ms**라 200ms 미만이 한 번도 없음 → FAST_CLICK 오탐이 나올 수 없음. 실제 사람은 더블클릭·새로고침 연타가 가끔 있음
- 정상 회원에게 좌석 선점 실패(409)가 없음 → 인기 열차에서 사람끼리 부딪히는 상황이 빠짐
- 봇은 문턱을 확실히 넘게, 정상은 확실히 안 넘게 만들어져 있어 **경계를 재지 않음**

→ 지금 숫자는 "규칙이 실제 테이블·해시·배치를 거쳐 끝까지 동작한다"는 확인이다. 목표(탐지율 90%·오탐률 5%)를 **달성했다고 말하려면** 아래 3장이 필요하다.

## 3. 남은 일

| # | 할 일 | 누가 | 효과 |
|---|---|---|---|
| 1 | 결제 번호 버그 수정 (`payment_id = reservation_id`) | 강다인 | 공용 서버·각자 DB에서 생성 가능 |
| 2 | 정상 회원에 사람다운 노이즈: 가끔 200ms 미만 클릭 몇 번, 인기 좌석 409 1~2번 | 강다인·조영준 | 오탐률이 의미 있는 숫자가 됨 |
| 3 | 경계 근처 정상 유형: 가족 다구매(누적 매수 많음), 일정 변경(취소 비율 높음, 구매 4건 이상), 출장자(출발 직전 취소) | 강다인·조영준 | 보조 규칙 3개(BULK·HIGH_CANCEL·LAST_MINUTE)가 시험됨 |
| 4 | 문턱 근처 봇: 연타 15~25회, 반복 4~6회, 취소 1~2건, 다계정 2개 | 조영준 (시나리오 12 옵션으로 이미 가능) | 탐지율이 어디서 떨어지는지 |
| 5 | 되팔이 다계정이 카드 하나 공유 | 강다인 | 결제 수단 연결(LINKED_ACCOUNTS·CANCEL_AFTER_PAY의 카드 쪽) 시험 |
| 6 | 일정 간격 매크로 (간격 변동 작음, 30건 이상) | 조영준 | REGULAR_INTERVAL 시험 |
| 7 | (선택) 로그인 가능한 계정 → 이력 위에 시나리오 12 행동 | 조영준 | "쌓인 이력 + 지금 행동"을 함께 봄 |

2·3·5는 **규칙을 보고 맞추지 않고** "그런 사람이 실제로 어떻게 행동하나"로 정한다. 데이터가 규칙 쪽으로 기울면 측정 의미가 없어진다. 비율·분포의 근거(코레일 통계, DATA-04 Kaggle 등)를 찾으면 `generation_params`에 남긴다.
