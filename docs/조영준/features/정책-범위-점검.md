# 운영 정책(app_policy) 50개 범위 점검

작성자: 조영준 · 2026-11-19 · 관련: [운영 설정(ADM-08)](운영-설정.md)

> 관리자 화면에서 바꿀 수 있는 정책 50개를 "누가 읽는지 · 이상한 값이면 어떻게 되는지"로 점검했다. 범위는 **제안값**이고 각 기능 담당이 확정한다. 확정되면 그 모듈이 `PolicyBounds`를 구현하면 관리자 API가 저장 전에 거절한다.

## 한 줄 요약

- 범위가 있는 키 **9개** (인증 7 · 행동 로그 2). 나머지 숫자 키는 **음수만 막고 0이나 아주 큰 값은 그대로 들어감**
- **0이 들어가면 기능이 멈추는 키가 여럿** (입장 속도, 선점 만료 스캐너 묶음 크기, 이벤트 발행 묶음 크기 등)
- **소수가 들어가면 멈추던 문제는 막음** (11-19, 지금 값이 정수인 키에는 정수만)
- **읽는 코드가 없는 키 9개**: 화면에서 바꿔도 아무 일도 안 일어남

## 리더별 동작

| 리더 (담당) | 읽는 곳 | 범위 검사 | 소수·문자 |
|---|---|---|---|
| `AuthPolicy` (강다인) | Redis | ✅ 범위 밖이면 기본값 + 관리자 API가 거절 | 기본값 |
| `BehaviorPolicy` (강다인) | Redis | ✅ 〃 | 기본값 |
| `PolicyProvider` 대기열 (김성원) | Redis | ❌ | **예외** → 입장 처리 실패 (11-19 관리자 API에서 막음) |
| `AppPolicy` 예약·대기·리플레이·스캐너 (강동균·강다인) | Redis → Oracle | ❌ | **예외** (〃) |
| `EventPolicy`·`PaymentPolicy`·`NotificationPolicy` (길동현) | Oracle | ❌ | 기본값 (조용히) |

### 서로 묶인 값 (범위만으로는 못 막음)

- `notification.pay_reminder_sec` < `reservation.pay_deadline_min` × 60 (알림이 기한보다 늦으면 의미 없음)
- `inbox.retention_days` > Kafka 보관 기간(7일)
- 이런 관계는 저장 전 검사에 "다른 키와 비교"가 필요 → 필요하면 ADM-08에 추가

## 읽는 코드가 없는 키 9개

화면에는 보이지만 바꿔도 동작이 안 바뀜. 코드에서 키 이름 문자열로 찾지 못한 것이라, 다른 방식(설정 파일·상수 조합)으로 읽는지 담당 확인 필요.

| 키 | 지금 | 추정 |
|---|---|---|
| `inventory.segment_mode` | OFF | 구간 판매 확장 예정 |
| `outbox.shard_count` | 16 | 코드에 16 고정 (바꾸면 위험: 샤드 재배치) |
| `relay.lease_sec` | 15 | 릴레이 1대 구조라 안 씀 |
| `queue_log.retention_days` · `evidence.retention_days` | 30 · 365 | Mongo TTL 색인이 원본일 수 있음 |
| `replay.hold_cache_sec` | 30 | - |
| `cancel.after_departure_limit_min` | 20 | - |
| `scanner.pay_recheck_interval_sec` | 10 | 결제 재확인은 `payment.pg_recheck_sec`를 씀 |
| `risk.batch_interval_sec` | 60 | `application.yml` `jejari.risk.batch-interval`(1m)이 실제 값 |

→ 제안: 안 쓰는 키는 화면에 "앱이 읽지 않음" 표시하거나 ERD에서 정리 (ERD는 강동균 님)

## 담당 답변과 확정 범위 (2026-11-19 오후)

| 담당 | 답 | 확정 |
|---|---|---|
| **팀장님** (이벤트·결제·알림) | 제안 범위 동의. 단 `idem.ttl_sec` **하한 600** (결제 마감 전에 중복 방지 키가 사라지지 않게). 묶음 조건 2개 추가: `payment.pg_unknown_max_min × 60 ≥ payment.pg_timeout_sec`, `payment.pg_recheck_sec × 3 ≤ payment.pg_unknown_max_min × 60` | ✅ **`PolicyBounds`는 팀장님이 직접 구현** |
| **김성원 님** (대기열) | `admit_per_sec` 1~2000(**2000은 k6로 확인 후 확정**), `pass_ttl_sec` 60~1800, `penalty_ms_per_point` 0~10000 동의. `entry_ttl_sec` 하한은 **1200 이상, 또는 `penalty_ms_per_point ÷ 10`보다 크게**. `member_penalty_rule`은 **`MAX`만**. 묶음 조건 2개(입장 속도 × 토큰 유효 시간, `entry_ttl_sec` > 최대 지연). `queue.pass_extend_sec`도 범위에 | ✅ (11-27 확정: 2000은 입력 실수를 막는 상한, "입장 속도 × 토큰 유효 시간" 묶음 조건은 넣지 않음) |
| **강다인 님** (대기·리플레이) | waitlist 범위 동의. 추가: `waitlist.penalty_ms_per_point` 0~3,600,000, `replay.retention_days` **7~180**(0이면 녹화가 바로 지워짐), `replay.max_path_points` 5~200, `replay.batch_sec` 1~60, `replay.max_events_per_session` 100~50,000, `replay.full_record_score` 0~100. `replay.full_record_ratio`(0~1)는 소수라 지금 `Range`로는 안 됨 | ✅ |
| 강동균 님 (AppPolicy 나머지·안 쓰는 키 9개) | 답 대기 | |

### 이 답으로 생긴 일 (ADM-08, 내 담당)

1. **묶음 조건(키 여러 개를 함께 보는 검사)** — 팀장님 2개 + 김성원 님 2개. 지금 `PolicyBounds`는 키 하나의 범위만 알려 줌 → "다른 키의 지금 값과 비교"하는 검사를 받을 수 있게 넓혀야 함 (예: `validate(바꿀 키, 새 값, 지금 값 전체)`)
2. **소수 범위** — `replay.full_record_ratio` 0~1. `Range`가 정수만이라 소수 범위를 추가
3. **문자열 허용값** — `risk.member_penalty_rule`은 `MAX`만
4. `queue.pass_extend_sec`는 코드 기본값만 있고 `app_policy`에 행이 없어 **관리자 화면에 안 보임** → 범위는 넣되, 화면에서 바꾸려면 ERD 행 추가가 필요 (강동균 님)
5. ~~`queue.admit_per_sec` 상한 2000은 k6로 확인한 뒤 확정~~ → **11-27 김성원 님 확정: 2000 그대로.** 서버가 버티는 값이 아니라 0·터무니없는 값을 막는 상한 (공용 서버 측정 11-26은 동시 600명·초당 554건). 운영 값은 200 유지
6. 대기열·AppPolicy의 `PolicyBounds` 구현은 담당이 맡는다고 하지 않아 내가 하거나 담당과 나눔 → 정할 것

### 반영 (2026-11-19 저녁, `PolicyBounds` 확장 + 대기열·AppPolicy 연결)

`PolicyBounds`가 네 가지를 알려 줄 수 있게 넓힘: **정수 범위**(`bounds`) · **소수 범위**(`decimalBounds`) · **문자열 허용값**(`allowedValues`) · **묶음 조건**(`rules`, 키 여러 개를 함께 봄). 같은 키를 두 모듈이 알려 주면 **겹치는 구간만** 받음 (예: `idem.ttl_sec`은 AppPolicy와 결제가 함께 읽음)

| 모듈 | 연결한 것 | 남은 것 |
|---|---|---|
| 대기열 `PolicyProvider` (김성원 님 답) | `admit_per_sec` 1~2000 · `pass_ttl_sec` 60~1800 · `pass_extend_sec` 60~1800(제안) · `entry_ttl_sec` 1200~86400 · `penalty_ms_per_point` 0~10000 · `member_penalty_rule` = MAX · 묶음: `entry_ttl_sec` > `penalty_ms_per_point ÷ 10` | ~~2000은 k6 확인 후~~ 2000 확정(11-27) · `pass_extend_sec` 범위 확인 · ~~"입장 속도 × 토큰 유효 시간"의 상한 값~~ 넣지 않기로(11-27) · `pass_extend_sec`는 app_policy 행이 없어 화면에 안 보임 (ERD) |
| `AppPolicy` 대기·리플레이 (강다인 님 답) | `waitlist.*` 4개 · `replay.*` 5개 정수 · `replay.full_record_ratio` 0~1 소수 | - |
| `AppPolicy` `idem.ttl_sec` (팀장님 답) | 600~86400 | - |
| `AppPolicy` 예약·스캐너·좌석 배치도·판매 오픈 (강동균 님) | - | 답 대기 |
| 이벤트·결제·알림 (팀장님) | - | 팀장님이 직접 구현 (묶음 조건 2개 포함, 아래 예) |

- 안전장치: **ERD 시드값이 모든 모듈의 범위·허용값·묶음 조건을 이미 만족하는지** 테스트가 확인 (`PolicyBoundsTest`). 범위가 지금 값을 막아 버리는 일이 없게
- 묶음 조건이 보는 키가 아직 app_policy에 없으면 그 조건은 건너뜀 (행이 생기면 그때부터)

결제 묶음 조건 구현 예 (팀장님용):

```java
@Override public List<Rule> rules() {
  return List.of(
    new Rule(Set.of(PG_UNKNOWN_MAX_MIN, PG_TIMEOUT_SEC),
      v -> v.num(PG_UNKNOWN_MAX_MIN).multiply(BigDecimal.valueOf(60)).compareTo(v.num(PG_TIMEOUT_SEC)) >= 0,
      "payment.pg_unknown_max_min × 60은 payment.pg_timeout_sec 이상이어야 합니다."),
    new Rule(Set.of(PG_RECHECK_SEC, PG_UNKNOWN_MAX_MIN),
      v -> v.num(PG_RECHECK_SEC).multiply(BigDecimal.valueOf(3)).compareTo(v.num(PG_UNKNOWN_MAX_MIN).multiply(BigDecimal.valueOf(60))) <= 0,
      "payment.pg_recheck_sec × 3은 payment.pg_unknown_max_min × 60 이하여야 합니다 (결과 모름 동안 세 번은 다시 확인)."));
}
```

### 김성원 님 답 (2026-11-27): 대기열에 남아 있던 두 가지

| 물은 것 | 답 | 이유 |
|---|---|---|
| "입장 속도 × 입장 토큰 유효 시간" 묶음 조건 | **넣지 않음** | 좌석 수가 운행마다 달라 고정 상한을 정할 수 없음. 실제 부하는 곱이 아니라 **입장 속도**가 정함 (사람들은 토큰 시간 300초를 다 쓰지 않고 좌석을 고르면 나감). 좌석 쪽은 좌석 조회·선점 속도 제한과 Lua 원자 선점으로 따로 막혀 있음 → 각 값의 범위(`admit_per_sec` 1~2000, `pass_ttl_sec` 60~1800)로 충분 |
| `queue.admit_per_sec` 상한 2000 | **2000 확정** | k6로 2000을 따로 재지는 않음. 2000은 "서버가 버틴다"는 값이 아니라 **입력 실수를 막는 상한**. 공용 서버 측정(11-26)은 동시 600명·초당 554건이므로 운영 값은 지금처럼 200 |

- `entry_ttl_sec` > `penalty_ms_per_point ÷ 10` 묶음 조건은 꼭 필요해 그대로 둠
- 코드 주석(`PolicyProvider.bounds()`의 "상한 2000은 k6 확인 후 확정")은 김성원 님이 이 뜻으로 고침 → 대기열 쪽 범위는 남은 질문 없음 (`pass_extend_sec` 범위·ERD 행은 별개)
