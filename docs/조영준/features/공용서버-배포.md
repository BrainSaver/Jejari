### 하다가 막힌 것

- **첫 화면 NOT_FOUND**: `deploy.sh`가 `bootJar`만 해서 화면(frontend) 없이 빌드됨 → Node 22 컨테이너로 화면 빌드, jar에 화면이 없으면 배포 중단 ([트러블슈팅](../troubleshooting/20261118-공용서버-화면-누락.md))
- **방화벽 생성 실패**: Windows에서 `gcloud.cmd`를 Git Bash로 부르면 `cmd`가 `--allow=tcp:80,tcp:443`의 **쉼표를 인자 구분자로 잘라** 오류. → SDK 내장 파이썬으로 `lib/gcloud.py`를 직접 실행 (`cmd`를 거치지 않음)
- **SSH 22번을 지우는 순서**: IAP 규칙을 먼저 만들고 IAP로 접속되는 것을 확인한 뒤 기본 규칙을 지움 (거꾸로 하면 아무도 못 들어감)

### 팀이 접속하는 법

- 서비스: 팀 채널의 `https://…sslip.io` 주소 (HTTPS만)
- 서버 SSH: GCP 프로젝트 권한(`roles/iap.tunnelResourceAccessor` + Compute 접근)을 받은 뒤 `gcloud compute ssh jejari --zone=asia-northeast3-a --tunnel-through-iap`
- Grafana: `https://…/grafana/`에서 아이디 `team`으로 로그인 (비밀번호는 담당자에게, 보기 전용). SSH는 필요 없음

## 왜 이렇게 했나 (강동균 님 조사와 다른 점)

| 조사 문서 | 여기 | 이유 |
|---|---|---|
| `http://IP:8080` 공개 | Caddy로 HTTPS, 80·443만 | 리프레시 쿠키가 Secure라 http에서는 브라우저가 저장·전송하지 않아 **재발급이 전부 실패**. 8080을 열면 `/actuator/prometheus`(내부 지표)도 공개됨 |
| 앱 1대 | 2대 | [멀티 인스턴스 규칙](멀티인스턴스-코딩-규칙.md)을 실제로 확인. 배포 때 한 대씩 재시작 |
| `User=ubuntu` | 실제 사용자 | GCP Ubuntu에는 `ubuntu` 계정이 없음 (`gcloud compute ssh`가 내 PC 사용자 이름으로 만듦) |
| 내 PC `.env` 복사 | 새로 생성 | 로컬 비밀번호·임시 키가 서버로 가지 않게 |

도메인은 사지 않고 `외부IP.sslip.io`를 쓴다 (IP를 이름으로 바꿔 주는 공개 DNS, Let's Encrypt 바로 가능).
