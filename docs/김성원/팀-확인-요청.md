# 대기열·HMAC 작업 팀 확인 요청

> 작성 김성원 · 2026-11-16 · 브랜치 `SeongWon` · 코드 `queue/`, `hmac/`, `k6/queue/` · 기능 문서 `docs/김성원/features/`

대기열(QUE-01~05)과 HMAC 모듈을 구현하면서 **다른 파트의 결정이나 작업이 필요한 것**을 사람별로 모았습니다. 각 항목은 "무엇을 / 왜 / 제안"이고, 답을 받으면 이 문서의 체크박스를 지웁니다. 모두 **제안**이며 합의된 것이 아닙니다.

현재 상태 요약: main의 새 구조(루트 Gradle 프로젝트, `com.jejari`, JWT 인증)에 맞춰 옮겼고, 인프라 없이 도는 테스트 39개(HMAC 19개 포함)와 Redis 통합 테스트 57개가 통과, 진입 처리량은 한 PC 기준 초당 약 3,000건(내 PC) ~ 4,700건(4코어 컨테이너)에서 정체. 회원·운행 연동·로그 적재는 아직 없어서 `queue/port/`의 인터페이스로 막아 두었습니다 (구현이 없어도 앱은 뜨고 대기열만 "준비 중"으로 동작).

---

## 전원에게 (공지)

- `git pull origin main`(내 브랜치에서) 뒤 **`.env`에 `JEJARI_HMAC_KEY=`가 새로 필요합니다.** `.env.example`을 다시 보고 같은 줄을 추가하세요. `.env`는 저장소에 올라가지 않아서 팀원마다 직접 만들어야 합니다. 값은 `openssl rand -base64 32`로 만들되, **팀 전원이 같은 값**을 써야 같은 사람의 해시(CI·전화번호·카드)가 같아집니다 (팀장이 정해 공용 비밀값으로 공유하는 것을 제안). 프로젝트 기간 동안 바꾸지 않습니다. 키가 없어도 앱은 뜹니다(가명처리 빈만 안 만들어짐).
- 테스트는 두 가지입니다: `./gradlew test`(인프라 불필요, CI) / `./gradlew infraTest`(`@Tag("infra")`, `docker compose up -d` 필요). 인프라가 필요한 테스트에는 `@Tag("infra")`를 붙여 주세요.
- 한글 테스트 이름이 들어 있어서, 로케일이 UTF-8이 아닌 리눅스 환경에서는 Gradle이 HTML 리포트를 만들다 실패할 수 있습니다 (`LC_ALL=C.UTF-8`). CI(ubuntu)는 영향 없음.

## 강동균 (열차 도메인 · ERD 반영 담당)

- [ ] **1. ERD의 `queue:member` 값 형식 갱신**
  - 무엇을: Redis 키 표의 `queue:member:{memberId}` 값을 `{runId}|{queue member}` → `{runId}|{queue member}|{ciHash}`로.
  - 왜: 입장·이탈 처리(Lua)가 그 회원의 `queue:ci:{ciHash}` 항목을 찾아 갱신해야 하는데, 스크립트 안에서는 회원 ID만으로 CI를 알 수 없습니다. 앞의 두 칸은 그대로라 기존 해석은 깨지지 않습니다.
  - 제안: 새 패치(V11 이후)의 `redis_keys` 비고 수정. CLAUDE.md 규칙상 ERD 패치는 동균 님만 합니다.
- [ ] **2. `app_policy` 시드에 `queue.entry_ttl_sec` 추가**
  - 무엇을: 키 `queue.entry_ttl_sec`, 값 `3600`, 타입 NUMBER, 설명 "대기 기록(queue:member)이 남는 최대 시간".
  - 왜: 줄에 선 뒤 이탈 없이 사라진 회원의 기록이 영원히 남지 않게 하는 상한입니다. 지금은 코드의 기본값 3600초를 씁니다 (TTL을 코드에 박지 않는다는 규칙 위반).
- [ ] **3. 좌석 API가 입장 토큰을 확인하는 방법**
  - `GET /api/v1/runs/{runId}/seats`는 제 인터셉터(`QueueSeatTokenInterceptor`, 로그인 검사 뒤)가 헤더 `X-Queue-Token`을 컨트롤러 앞에서 검사하므로 **추가 작업이 필요 없습니다.** 경로에 `{runId}`가 있어야 합니다. 개발 모드에는 같은 경로의 임시 컨트롤러 `DevSeatsController`가 있으니, **실제 좌석 배치도 API를 만들면 그 파일을 지워 주세요** (같은 경로가 둘이면 개발 모드 기동이 실패).
  - `POST /api/v1/reservations`는 운행 ID가 요청 본문에 있어 필터로 막을 수 없습니다. 컨트롤러에서 **`QueuePassService.verify(runId, memberId, token)`을 직접 호출**해 주세요 (예외: `QUEUE_TOKEN_REQUIRED` / `QUEUE_TOKEN_INVALID`, 모두 403). 토큰 없이 좌석 API 호출 차단율 100%는 이 호출이 빠지면 지켜지지 않습니다.
- [ ] **4. 판매 중 운행 정보 제공**
  - 무엇을: `OnSaleRunProvider`(`find(runId)`, `onSaleRunIds()`)를 `train_run.status = ON_SALE`과 `sale_close_at`으로 구현.
  - 왜: 대기열 진입은 판매 중인 운행에만 열고, 입장 스케줄러가 어느 운행을 처리할지 알아야 합니다. 지금은 개발용 대용품이 `--jejari.queue.dev-on-sale-runs=9001 (시드의 ON_SALE 운행 9001·9002와 맞춤)`로 대신합니다.

## 길동현 (팀장 · 기능설계서 · 이벤트)

- [ ] **5. 기능설계서 9장 에러 코드 추가** (`AUTH_REQUIRED`는 이미 있어 제외, 코드는 `QueueErrorCode`·`CommonErrorCode`에 구현됨)

  | 코드 | HTTP | 상황 |
  |---|---|---|
  | `QUEUE_NOT_FOUND` | 404 | 대기 중이 아닌데 번호표 조회 |
    | `SERVICE_UNAVAILABLE` | 503 | Redis 연결 끊김·응답 지연 (아래 8번). 공통 코드(`CommonErrorCode`)에 추가함 |
  | `QUEUE_TOKEN_REQUIRED`, `QUEUE_TOKEN_INVALID`, `QUEUE_DUPLICATED`, `RUN_NOT_ON_SALE` | 403·403·409·409 | 이미 설계서에 있음. `QueueErrorCode`로 구현 |

- [ ] **6. `queue_log` 적재 경로 (Kafka 토픽과 Mongo 적재 담당)**
  - 지금: 대기열이 `QueueLogSink`로 이벤트(`ENTERED`, `ADMITTED`, `LEFT`, `REJECTED_DUPLICATE`)를 넘기고, 기본 구현은 로그 출력뿐입니다.
  - 필요: DB설계서 6.1은 `queue_log`를 "행동 로그와 같은 경로"(Kafka → insertMany)로 적재한다고 되어 있습니다. 토픽 이름(`jejari.behavior`에 섞을지 별도 토픽일지), 메시지 키, Mongo 문서에서 한 번의 진입(ENTERED → ADMITTED/LEFT)을 한 문서로 합치는 방법을 정해야 합니다.
  - 순번 조정 정확도 검증의 근거 데이터라서 필요합니다 (`initial_rank` → `adjusted_rank`, `penalty_ms`). `session_id`는 로그인 세션이 붙은 뒤에 채웁니다.
- [ ] **7. 번호표 응답 필드를 API 문서에 반영**
  - 진입·조회 응답: `state`(WAITING/ADMITTED), `runId`, `ticketNo`, `rank`, `ahead`, `estimatedWaitSec`, `pollIntervalSec`, 입장 시 `passToken`, `passExpiresAt`(+09:00). 화면(U-04)은 `pollIntervalSec`(1~5초) 간격으로 폴링합니다.
- [ ] **8. Redis 장애 시 정책을 서비스 전체로 맞추기 (제안)**
  - 대기열은 Redis가 끊기면 요청을 붙잡지 않고 즉시 503으로 응답합니다 (개선 전에는 요청마다 스레드를 60초 점유해 앱 전체가 멈췄음, 응답 60초 → 6ms). 결제·Outbox·Kafka·DB 쪽도 외부 시스템이 죽었을 때 기본 대기 시간(수십 초)에 스레드가 묶이지 않는지 한 번 확인하면 좋습니다. 트러블슈팅: `docs/김성원/troubleshooting/20261116-Redis-끊김-60초-대기.md`.

## 강다인 (위험 점수 · 회원)

- [ ] **9. 위험 점수 캐시 형식 확인**
  - 대기열이 읽는 키: `risk:CI:{해시}`, `risk:PAYMENT:{해시}`, `risk:DEVICE:{해시}`. 값은 `final_score` **숫자 문자열**(`80`, `80.5`)이어야 합니다 (0~100, 자세한 형식은 17번). `risk:meta:synced_at`이 있을 때만 "키가 없음 = 0점"으로 읽습니다 (17번).
  - **신규 계정이 0점이 되는 문제**: 기획서는 "신규 계정은 기본 신뢰도를 낮게" 시작한다고 했는데, 캐시에 점수가 없으면 대기열은 0점을 줍니다. 계정을 새로 만들어 위험 점수를 피할 수 있으므로, 가입 시점에 기본 점수를 캐시에 채워 주거나, 캐시 미스 때 점수 계산 쪽을 호출하는 방식을 정해 주세요.
  - 여러 점수는 **최댓값**(`risk.member_penalty_rule = MAX`)을 쓰고, 패널티는 `점수 × risk.penalty_ms_per_point`(기본 1점 = 1초)입니다.
- [ ] **10. `MemberIdentityPort` 구현**
  - 필요한 값: 회원 상태(`ACTIVE`/`RESTRICTED`/`BANNED`), `ci_hash`, 결제 수단 해시 목록, 기기 해시 목록. `RESTRICTED`는 최대 패널티(100점 취급), `BANNED`는 `AUTH_BANNED`로 거절합니다 (기능설계서 2장 [가정]).
  - **진입 1건마다 호출됩니다.** DB를 읽는 구현이라면 처리량에 직접 영향이 있으므로, 캐시나 JWT에 담는 방법을 같이 생각해 주세요 (지금 수치는 메모리 조회 기준이라 실제로는 더 낮아질 수 있음).
- [ ] **11. 식별 해시는 `hmac` 모듈로 만들어 주세요**
  - `ci_hash`, `phone_hash`, `email_hash`, `method_hash`, `device_hash`, `ip_hash`를 각자 구현하면 값이 달라져 같은 CI·카드 묶음이 깨집니다. 사용법은 `docs/김성원/features/hmac-가명처리.md`. 모의 본인인증은 `mockCiHash(이름, 전화번호)`를 쓰면 표기가 달라도 같은 사람이 같은 CI가 됩니다.
- [ ] **12. 취소표 대기에도 위험 점수 패널티 적용 (기능설계서 미정 7번) — 김성원이 설계 문서를 고쳤으니 확인·구현 부탁**
  - 왜: 지금까지는 대기 순서를 `requested_at`으로만 정해서, 대기열에서 뒤로 밀린 매크로·암표 계정이 취소표 신청에서는 정상 사용자와 같은 순서로 취소표를 가져갈 수 있었습니다 (위험 점수 후순위 우회).
  - 바꾼 규칙 (`docs/concurrency.md` §9.3, 기능설계서 WL-01):
    - 순서 기준 = `priority_at` = 신청 시각 + 패널티. 신청 때 한 번 계산하고 이후 점수가 바뀌어도 유지 (대기열과 같음).
    - 점수는 대기열과 같은 규칙: `risk:{CI|PAYMENT|DEVICE}:{해시}` 최댓값, `RESTRICTED`는 100점, 없으면 0점.
    - 신청을 막지는 않고 뒤로 밀기만 함. 앞에 대기자가 없으면 바로 제안받음.
    - 제안 조회 쿼리: `ORDER BY priority_at, waitlist_id` (인덱스도 `priority_at`으로).
  - **확인 부탁: 패널티 단위.** 대기열의 1점 = 1초를 그대로 쓰면 취소표 대기(몇 시간~며칠)에서는 80점이 80초라 순서가 사실상 안 바뀝니다. 그래서 별도 정책 `waitlist.penalty_ms_per_point`를 두고 기본 60000(1점 = 1분, 80점 = 80분)으로 적었습니다. 이 값은 예시이고 다인 님·팀이 정해야 합니다.
  - **강다인 님**: 신청(WL-01) 때 위의 규칙으로 `priority_at`·`penalty_ms`를 계산해 저장하고, WL-03 조회 쿼리를 `priority_at` 기준으로. 점수 계산은 `queue`의 `RiskPenaltyService`(`score`, `penaltyMs`)와 같은 로직이니 그대로 가져가거나 공용으로 빼 주세요 (모듈 구조는 16번).
  - **강동균 님 (ERD 패치, 규칙상 제가 직접 못 고침)**: 새 패치에 아래를 반영해 주세요. 기존 행은 `priority_at = requested_at`, `penalty_ms = 0`으로 채웁니다.

    ```js
    // 초안 — check-erd.js로 확인 필요 (waitlist 예시 행에도 새 NN 컬럼 값 필요)
    ['add','waitlist','requested_at',[
      ['priority_at','TIMESTAMP','NN','시스템','대기 순서 기준 시각 = requested_at + penalty_ms','위험 점수가 높은 대기자는 뒤로 (concurrency.md §9.3). 대기 순서는 이 컬럼으로만 정렬'],
      ['penalty_ms','NUMBER(12)','NN','시스템','위험 점수로 미룬 시간(ms), 패널티 없으면 0','순서 조정 근거 기록 (운영 원칙: 점수 근거 기록)']
    ]],
    // 비고의 인덱스를 ix_waitlist_next ON waitlist (run_id, status, priority_at) 로 교체
    // app_policy 시드: waitlist.penalty_ms_per_point = 60000 (NUMBER), 설명 "위험 점수 1점당 취소표 대기 순서를 미루는 ms"
    ```
  - 테스트: `docs/concurrency.md` T38(위험 대기자가 늦게 신청한 정상 대기자보다 뒤), T39(패널티 시간이 지난 뒤 신청한 정상 대기자는 뒤), 지표는 `priority_at` 순서 위반 0건.
- [ ] **17. 위험 점수 Redis 캐시 읽기 규칙 — 대기열 쪽 변경은 구현 완료, Oracle 조회 포트 구현 부탁**
  - 대기열에 넣은 것 (코드 `queue/domain/RiskPenaltyService`, 테스트 `RiskPenaltyServiceTest` 9개). 다인 님의 Redis 동기화 규칙 7개 중 6·7번에 해당합니다.
    - **값 검증(7번)**: `0~100`의 십진수 문자열만 읽습니다 (`80`, `80.5`, 소수 6자리까지). `abc`, 빈 문자열, 음수, 101 이상, JSON, `NaN`, `1e2`, `80d`는 **100점으로 취급**하고 경고 로그를 남깁니다 (10초에 한 번). 값이 하나라도 오염되면 다른 값이 낮아도 100점입니다. 기존 코드는 이런 값에서 예외가 나 진입이 500이었습니다. 쓰는 쪽은 숫자 문자열만 `SET` 해 주세요.
    - **동기화 표시 키(6번)**: `risk:meta:synced_at`이 있을 때만 `risk:*` 캐시를 믿습니다 (같은 `MGET` 왕복에 함께 읽어 추가 비용 없음). 없으면 캐시가 비었을 수 있다고 보고 **Oracle `risk_score`에서 이 회원의 점수를 직접 조회**하고, 조회가 실패하면 100점입니다 (안전한 쪽). 값의 내용은 보지 않고 존재만 봅니다.
  - **다인 님이 해 주실 것**
    - `queue/port/RiskScoreFallbackPort`를 구현한 빈을 등록: `double maxScore(MemberIdentity member)`. 회원의 CI·결제 수단·기기 해시로 `risk_score`를 찾아 **최댓값**(없으면 0, 값은 0~100)을 돌려주고, DB 오류는 예외를 던지면 됩니다. 이 빈이 없으면 기본값이 "항상 실패 → 100점"이라, 표시 키가 없는 동안 모든 사용자가 최대 패널티를 받습니다 (개발 모드에는 Redis를 읽는 대용품이 붙어 영향 없음).
    - 배치는 `risk:*`를 모두 쓴 **다음에** `risk:meta:synced_at`을 `SET` (앱 시작 때와 10분마다 전체 재동기화, 점수 > 0인 것만).
  - **확인할 위험 두 가지**
    - Redis가 재시작되면 다음 재동기화 전까지(최대 10분) **모든 진입이 Oracle을 조회**합니다. 오픈 폭주 중이면 부하가 큽니다. 재시작 감지 즉시 재동기화하는 방법, 조회 동시 수 제한(제가 `RiskPenaltyService`에 넣을 수 있음)을 정해 주세요.
    - 표시 키가 있어도 배치가 죽어 오래 갱신이 안 되는 건 지금 알 수 없습니다. 표시 키 값에 시각을 넣어 주시면 "N분 넘게 갱신 없음 → 경고(또는 Oracle 조회)"를 대기열에 넣을 수 있습니다 (제안).

## 조영준 (인증 · 인프라)

- [x] **13. 로그인 인증 → 해결.** 대기열은 팀의 JWT 인증을 그대로 씁니다 (`@AuthenticationPrincipal AuthPrincipal`의 `memberId()`). 개발 모드(`jejari.dev-mode=true`)에서만 `X-Member-Id` 헤더로 로그인하는 별도 보안 필터 체인(`queue/dev/DevSecurityConfig`)이 있어 부하 테스트가 JWT 없이 돕니다. 운영에서는 이 설정이 통째로 빠집니다. **확인 부탁**: 이 체인은 `@Order(HIGHEST_PRECEDENCE)`로 `X-Member-Id` 헤더나 `/api/v1/dev/**` 요청만 먼저 받으므로, `SecurityConfig`를 바꿀 때 영향이 없는지 봐 주세요 (`DevSecurityConfigTest`가 확인).
- [ ] **14. 비밀값·Redis 설정**
  - `JEJARI_HMAC_KEY`: `.env.example`에 추가했고 `application.yml`의 `jejari.hmac.key`로 읽습니다 (위 공지). Base64 32바이트 이상, **프로젝트 기간 동안 바꾸면 안 됩니다.** 팀 공용 값을 정해 주세요.
  - **공통 영역에 제가 추가한 것(리뷰 부탁)**: `application.yml`에 `spring.data.redis.timeout/connect-timeout: 2s`와 `jejari.*` 항목, `common/config/RedisFailFastConfig`(끊기면 명령을 쌓지 않고 바로 실패, 기본은 60초 대기로 앱 전체가 멈춤), `common/error/RedisExceptionHandler`(Redis 문제는 503), `CommonErrorCode.SERVICE_UNAVAILABLE`, `build.gradle`의 `@Tag("infra")` 제외·`infraTest` 작업. 모두 기존 코드를 고치지 않고 덧붙인 것입니다.
  - Redis: 7.x 단일 노드, `maxmemory-policy noeviction`, AOF `everysec`. 대기열 스크립트가 `TIME`과 `ZPOPMIN`을 쓰므로 **5.0 이상**이 필요합니다. 클러스터로 바꾸면 스크립트가 쓰는 키의 해시 태그를 바꿔야 합니다.
- [ ] **15. 부하 테스트 구조 맞추기**
  - 대기열 전용 시나리오 4개를 `k6/queue/`에 두었습니다 (`flow`, `token-guard`, `penalty-order`, `entry-burst`, 사전 점검 포함). 공용 시나리오와 폴더·태그·임계값 이름을 맞출지, Grafana에 대기열 지표(대기 인원, 입장 속도)를 노출할지 의견 부탁합니다.
- [x] **16. 모듈 구조 → 해결.** main에 루트 단일 Gradle 프로젝트(`com.jejari`, 패키지는 도메인별)가 올라와서 `queue`와 `hmac`을 그 안으로 옮겼습니다 (`queue/`, `common/hmac/`). 기존 독립 Gradle 프로젝트는 삭제했습니다.
