# 대기열·HMAC 작업 팀 확인 요청

> 작성 김성원 · 2026-11-16 · 브랜치 `SeongWon` · 코드 `queue/`, `hmac/`, `k6/queue/` · 기능 문서 `docs/김성원/features/`

대기열(QUE-01~05)과 HMAC 모듈을 구현하면서 **다른 파트의 결정이나 작업이 필요한 것**을 사람별로 모았습니다. 각 항목은 "무엇을 / 왜 / 제안"이고, 답을 받으면 이 문서의 체크박스를 지웁니다. 모두 **제안**이며 합의된 것이 아닙니다.

현재 상태 요약: 대기열 테스트 46개(실제 Redis)·HMAC 단위 테스트 19개 통과, 진입 처리량은 한 PC 기준 초당 약 3,000건(내 PC) ~ 4,700건(4코어 컨테이너)에서 정체. 회원·운행·인증·로그 적재는 아직 개발용 대용품으로 막아 둔 상태입니다 (`queue/.../port/`).

## 강동균 (열차 도메인 · ERD 반영 담당)

- [ ] **1. ERD의 `queue:member` 값 형식 갱신**
  - 무엇을: Redis 키 표의 `queue:member:{memberId}` 값을 `{runId}|{queue member}` → `{runId}|{queue member}|{ciHash}`로.
  - 왜: 입장·이탈 처리(Lua)가 그 회원의 `queue:ci:{ciHash}` 항목을 찾아 갱신해야 하는데, 스크립트 안에서는 회원 ID만으로 CI를 알 수 없습니다. 앞의 두 칸은 그대로라 기존 해석은 깨지지 않습니다.
  - 제안: 새 패치(V11 이후)의 `redis_keys` 비고 수정. CLAUDE.md 규칙상 ERD 패치는 동균 님만 합니다.
- [ ] **2. `app_policy` 시드에 `queue.entry_ttl_sec` 추가**
  - 무엇을: 키 `queue.entry_ttl_sec`, 값 `3600`, 타입 NUMBER, 설명 "대기 기록(queue:member)이 남는 최대 시간".
  - 왜: 줄에 선 뒤 이탈 없이 사라진 회원의 기록이 영원히 남지 않게 하는 상한입니다. 지금은 코드의 기본값 3600초를 씁니다 (TTL을 코드에 박지 않는다는 규칙 위반).
- [ ] **3. 좌석 API가 입장 토큰을 확인하는 방법**
  - `GET /api/v1/runs/{runId}/seats`는 제 필터(`QueueTokenFilter`)가 헤더 `X-Queue-Token`을 컨트롤러 앞에서 검사하므로 **추가 작업이 필요 없습니다.**
  - `POST /api/v1/reservations`는 운행 ID가 요청 본문에 있어 필터로 막을 수 없습니다. 컨트롤러에서 **`QueuePassService.verify(runId, memberId, token)`을 직접 호출**해 주세요 (예외: `QUEUE_TOKEN_REQUIRED` / `QUEUE_TOKEN_INVALID`, 모두 403). 토큰 없이 좌석 API 호출 차단율 100%는 이 호출이 빠지면 지켜지지 않습니다.
- [ ] **4. 판매 중 운행 정보 제공**
  - 무엇을: `OnSaleRunProvider`(`find(runId)`, `onSaleRunIds()`)를 `train_run.status = ON_SALE`과 `sale_close_at`으로 구현.
  - 왜: 대기열 진입은 판매 중인 운행에만 열고, 입장 스케줄러가 어느 운행을 처리할지 알아야 합니다. 지금은 개발용 대용품이 `--jejari.queue.dev-on-sale-runs=1001`로 대신합니다.

## 길동현 (팀장 · 기능설계서 · 이벤트)

- [ ] **5. 기능설계서 9장 에러 코드 3개 추가**

  | 코드 | HTTP | 상황 |
  |---|---|---|
  | `QUEUE_NOT_FOUND` | 404 | 대기 중이 아닌데 번호표 조회 |
  | `AUTH_REQUIRED` | 401 | 로그인하지 않은 요청 (E의 JWT 코드와 맞추면 이 코드는 바꿀 수 있음) |
  | `SERVICE_UNAVAILABLE` | 503 | Redis 연결 끊김·응답 지연 (아래 8번) |

- [ ] **6. `queue_log` 적재 경로 (Kafka 토픽과 Mongo 적재 담당)**
  - 지금: 대기열이 `QueueLogSink`로 이벤트(`ENTERED`, `ADMITTED`, `LEFT`, `REJECTED_DUPLICATE`)를 넘기고, 기본 구현은 로그 출력뿐입니다.
  - 필요: DB설계서 6.1은 `queue_log`를 "행동 로그와 같은 경로"(Kafka → insertMany)로 적재한다고 되어 있습니다. 토픽 이름(`jejari.behavior`에 섞을지 별도 토픽일지), 메시지 키, Mongo 문서에서 한 번의 진입(ENTERED → ADMITTED/LEFT)을 한 문서로 합치는 방법을 정해야 합니다.
  - 순번 조정 정확도 검증의 근거 데이터라서 필요합니다 (`initial_rank` → `adjusted_rank`, `penalty_ms`). `session_id`는 로그인 세션이 붙은 뒤에 채웁니다.
- [ ] **7. 번호표 응답 필드를 API 문서에 반영**
  - 진입·조회 응답: `state`(WAITING/ADMITTED), `runId`, `ticketNo`, `rank`, `ahead`, `estimatedWaitSec`, `pollIntervalSec`, 입장 시 `passToken`, `passExpiresAt`(+09:00). 화면(U-04)은 `pollIntervalSec`(1~5초) 간격으로 폴링합니다.
- [ ] **8. Redis 장애 시 정책을 서비스 전체로 맞추기 (제안)**
  - 대기열은 Redis가 끊기면 요청을 붙잡지 않고 즉시 503으로 응답합니다 (개선 전에는 요청마다 스레드를 60초 점유해 앱 전체가 멈췄음, 응답 60초 → 6ms). 결제·Outbox·Kafka·DB 쪽도 외부 시스템이 죽었을 때 기본 대기 시간(수십 초)에 스레드가 묶이지 않는지 한 번 확인하면 좋습니다. 트러블슈팅: `docs/김성원/troubleshooting/20261116-Redis-끊김-60초-대기.md`.

## 강다인 (위험 점수 · 회원)

- [ ] **9. 위험 점수 캐시 형식 확인**
  - 대기열이 읽는 키: `risk:CI:{해시}`, `risk:PAYMENT:{해시}`, `risk:DEVICE:{해시}`. 값은 `final_score` 문자열(`80`, `80.00` 모두 가능). 키가 없으면 **0점으로 처리**합니다.
  - **신규 계정이 0점이 되는 문제**: 기획서는 "신규 계정은 기본 신뢰도를 낮게" 시작한다고 했는데, 캐시에 점수가 없으면 대기열은 0점을 줍니다. 계정을 새로 만들어 위험 점수를 피할 수 있으므로, 가입 시점에 기본 점수를 캐시에 채워 주거나, 캐시 미스 때 점수 계산 쪽을 호출하는 방식을 정해 주세요.
  - 여러 점수는 **최댓값**(`risk.member_penalty_rule = MAX`)을 쓰고, 패널티는 `점수 × risk.penalty_ms_per_point`(기본 1점 = 1초)입니다.
- [ ] **10. `MemberIdentityPort` 구현**
  - 필요한 값: 회원 상태(`ACTIVE`/`RESTRICTED`/`BANNED`), `ci_hash`, 결제 수단 해시 목록, 기기 해시 목록. `RESTRICTED`는 최대 패널티(100점 취급), `BANNED`는 `AUTH_BANNED`로 거절합니다 (기능설계서 2장 [가정]).
  - **진입 1건마다 호출됩니다.** DB를 읽는 구현이라면 처리량에 직접 영향이 있으므로, 캐시나 JWT에 담는 방법을 같이 생각해 주세요 (지금 수치는 메모리 조회 기준이라 실제로는 더 낮아질 수 있음).
- [ ] **11. 식별 해시는 `hmac` 모듈로 만들어 주세요**
  - `ci_hash`, `phone_hash`, `email_hash`, `method_hash`, `device_hash`, `ip_hash`를 각자 구현하면 값이 달라져 같은 CI·카드 묶음이 깨집니다. 사용법은 `docs/김성원/features/hmac-가명처리.md`. 모의 본인인증은 `mockCiHash(이름, 전화번호)`를 쓰면 표기가 달라도 같은 사람이 같은 CI가 됩니다.
- [ ] **12. 취소표 대기 순번에 위험 점수를 반영할지 (기능설계서 미정 7번)**
  - 지금 설계는 대기 순서를 `requested_at`으로만 정합니다. 그러면 대기열에서 뒤로 밀린 매크로·암표 계정이 취소표 신청에서는 정상 사용자와 같은 순서로 취소표를 가져갈 수 있어 위험 점수 후순위가 우회됩니다. 최소한 점수가 높은 대상은 신청을 제한하거나 순서에 패널티를 주는 방안을 검토해 주세요.

## 조영준 (인증 · 인프라)

- [ ] **13. `MemberAuthenticator`를 JWT 구현으로 교체**
  - 인터페이스 `OptionalLong memberId(HttpServletRequest)` 하나입니다. 지금은 개발 모드(`jejari.dev-mode=true`)에서만 `X-Member-Id` 헤더를 회원으로 믿는 대용품이 쓰이고, 운영에서는 구현이 없으면 앱이 뜨지 않게 해 두었습니다 (가짜 인증이 조용히 쓰이지 않도록). 입장 토큰 필터(`QueueTokenFilter`)가 인증 뒤에 실행되도록 필터 순서도 확인해 주세요.
- [ ] **14. 비밀값·Redis 설정**
  - `JEJARI_HMAC_KEY`: Base64 32바이트 이상 (`openssl rand -base64 32`). **프로젝트 기간 동안 바꾸면 안 됩니다** (바꾸면 저장된 해시와 이어지지 않음). 저장소·로그에 두지 않고 환경변수로만.
  - Redis: 7.x 단일 노드, `maxmemory-policy noeviction`, AOF `everysec`. 대기열 스크립트가 `TIME`과 `ZPOPMIN`을 쓰므로 **5.0 이상**이 필요합니다. 클러스터로 바꾸면 스크립트가 쓰는 키의 해시 태그를 바꿔야 합니다.
- [ ] **15. 부하 테스트 구조 맞추기**
  - 대기열 전용 시나리오 4개를 `k6/queue/`에 두었습니다 (`flow`, `token-guard`, `penalty-order`, `entry-burst`, 사전 점검 포함). 공용 시나리오와 폴더·태그·임계값 이름을 맞출지, Grafana에 대기열 지표(대기 인원, 입장 속도)를 노출할지 의견 부탁합니다.
- [ ] **16. 모듈 구조 (팀 전체 결정)**
  - 지금 `queue/`와 `hmac/`는 각각 독립 Gradle 프로젝트입니다. 최종 앱이 하나의 Spring Boot인지, 모듈을 합칠지(멀티 모듈) 정해야 합니다. 합칠 때 `hmac`은 Spring 비의존 라이브러리라 그대로 가져갈 수 있습니다. 그리고 Spring Boot 플러그인을 쓰지 않는 모듈은 `options.encoding = 'UTF-8'`을 직접 넣어야 한글이 안 깨집니다 (`hmac`에서 실제로 컴파일 실패를 확인).
