# [queue] 위험 점수가 높은 봇이 정상 사용자보다 먼저 입장함

> 파일 이름: `docs/김성원/troubleshooting/20261116-패널티-봇-선입장.md`

## 1. 문제

- 현상: 순번 조정 k6 시나리오(`penalty-order.js`)에서 위험 점수 80점인 봇 20명이 정상 사용자 100명보다 **먼저** 입장했다. 두 판정 지표가 모두 0%였다.

```
정상 사용자 입장까지: 최소 1.0s  평균 5.5s  최대 10.0s
봇(위험 점수)  입장까지: 최소 1.0s  평균 1.5s  최대 2.0s
판정: 일부 봇이 정상 사용자보다 먼저 입장 (패널티 미적용 또는 부족)
```

- 재현 조건: 봇 20명이 t=0에 줄을 서고, 3초 뒤 정상 사용자 100명이 줄을 선다. 입장 처리는 초당 10명으로 이미 돌고 있는 상태.
- 영향: "위험 사용자는 후순위"라는 핵심 기능이 동작하지 않는 것으로 보였다 (순번 조정 정확도 지표를 못 채움).

## 2. 원인

- 가설 1: 위험 점수가 읽히지 않는다 (Redis 키 이름 오류). → Redis에 점수가 들어 있고 앱 로그에 패널티가 찍혀 있어 아니었다.

```
$ redis-cli get risk:CI:dev-ci-3000000
80
ENTERED member=3000000 run=1001 ticket=14 risk=80.0 penaltyMs=80000 rank=1->14
```

- 가설 2: 점수는 적용되는데 입장 처리가 패널티와 상관없이 봇을 꺼낸다. → 맞았다. 입장 처리는 1초마다 **줄 맨 앞부터** N명을 꺼낸다. t=1~2초에는 줄에 봇밖에 없어서, 봇이 "맨 앞"이 되어 그대로 입장했다. 정상 사용자는 t=3초에야 들어왔다.
- 최종 원인: 패널티는 **다른 사람보다 뒤로** 보낼 뿐 줄에 혼자 있는 사람을 붙잡아 두지 않는다 (기획서의 "요청을 지연시키지 않고 순번만 조정"). 대기열 쪽 버그가 아니라, 시나리오가 "정상 사용자가 오기 전에 입장 처리가 이미 돌고 있다"는 전제를 깔고 있었다.
- 두 번째 원인(재발): 이후 정책 값을 앱에서 1초 캐시하도록 바꾸자(`2dc0269`) 같은 시나리오가 다시 0%가 됐다. 시나리오는 입장 정지(`queue.admit_per_sec = 0`)를 걸고 시작하는데, 앱이 직전 실행의 값(20)을 최대 1초 더 들고 있어 그 사이에 봇이 입장했다.

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| A. 입장 때 "score가 아직 미래인 항목은 꺼내지 않기" (패널티를 실제 대기 시간으로) | 줄이 비어도 패널티가 효과를 냄 | 혼자 있는 위험 사용자도 80초를 기다림. 오탐이면 정상 사용자가 피해. 기획서의 "요청을 지연시키지 않고 순번만 조정"과 다름 | |
| B. 시나리오를 현실에 맞춤: 입장을 멈춘 채 봇·정상 사용자를 모두 줄 세운 뒤 입장 시작 | 설계 의도를 그대로 검증. 오픈 직후 한꺼번에 몰리는 실제 상황과 같음 | 시나리오가 한 단계 복잡해짐 | ✓ |

- 선택한 이유: 설계 의도가 "붐빌 때 뒤로 밀린다"이므로 시나리오를 의도에 맞췄다. A는 팀 결정이 필요한 설계 변경이라 채택하지 않았다.
- 바뀐 코드 위치:
  - `k6/queue/run-penalty-order.sh`: 초기화 → 위험 점수 설정(입장 정지) → 줄 서기 → 입장 시작 순서로 실행
  - `k6/queue/penalty-order.js`: 봇을 먼저, 정상 사용자를 3초 뒤에 줄 세우고 두 방향으로 판정
  - 정책 캐시 반영 대기(`POLICY_WAIT`, 기본 2초)

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 봇이 모든 정상 사용자 뒤에 입장한 비율 | 0% | 100% |
| 정상 사용자 입장 시점에 봇이 대기 중이던 비율 | 0% | 100% |
| 입장까지 걸린 시간 (정상 / 봇) | 최대 10초 / 최소 1초 | 최대 13초 / 최소 17초 |

- 측정 환경: 클라우드 컨테이너 4코어, k6 v0.55, 앱·Redis 같은 머신, 개발용 대용품
- 측정 방법: `K6=$(which k6) ./run-penalty-order.sh` (봇 20명, 위험 점수 80, 정상 100명, 입장 10명/초). 반복 실행에서 모두 100%.

## 5. 정리

- 면접용 한 줄 요약: "위험 점수가 높은 봇이 먼저 입장해서 패널티가 안 먹는 줄 알았는데, 패널티는 '다른 사람보다 뒤'로 보낼 뿐 줄이 비면 바로 입장하는 설계라서 시나리오 전제가 틀렸던 것이었고, 줄이 찬 뒤 입장을 시작하도록 고쳐 봇 전원이 정상 사용자 뒤에 입장(0% → 100%)함을 확인했다."
- 다음에 비슷한 상황이면: 결과가 기대와 다르면 먼저 시스템이 정말 틀렸는지(로그·Redis 값으로 패널티가 적용됐는지) 확인한 뒤 테스트의 전제를 의심한다. 설정을 바꾸는 시나리오는 캐시 반영 시간을 기다린다.
- 팀에 남은 질문: 위험 사용자를 줄이 비어 있을 때도 붙잡아 둘지(선택지 A)는 정책 결정이다. 지금 설계는 붙잡지 않는다.
