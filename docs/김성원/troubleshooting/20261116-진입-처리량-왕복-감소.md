# [queue] 진입 처리량이 초당 약 2,000~2,900건에서 정체

> 파일 이름: `docs/김성원/troubleshooting/20261116-진입-처리량-왕복-감소.md`

## 1. 문제

- 현상: 진입 API에 걸리는 초당 요청 수(목표)를 올려도 실제 처리량이 일정 값에서 멈추고, 응답 시간이 급격히 늘었다. 요청 실패는 없었다.

```
내 PC (k6·앱·Redis 동시 실행)
목표(건/초)  실제(건/초)  실패율  p95(ms)
      2000        1992.1    0.0%     64.3
      4000        2009.0    0.0%    569.6   ← 목표를 2배로 올려도 처리량이 그대로
      8000        2058.8    0.0%    558.6
```

- 재현 조건: `k6 run -e RATES=500,1000,2000,4000,8000 -e STEP_SEC=20 entry-burst.js`
- 영향: 오픈 직후 접속이 몰리면 줄을 서는 데만 수백 ms가 걸린다. 처리량 목표를 잡을 근거가 없었다.

## 2. 원인

- 가설 1: 입장 대기 때문에 k6의 가상 사용자가 부족하다. → 기존 `flow.js`는 입장을 기다리며 VU를 붙잡아 실제로 부족했지만(`Insufficient VUs`), 입장을 기다리지 않는 `entry-burst.js`로 바꿔도 처리량이 같은 값에서 멈췄다. 한 단계의 p95(약 570ms)는 "동시 요청 1000 ÷ 처리량 2000/초 = 0.5초"로 계산한 값과 같아서, 요청이 서버 안에서 줄을 서는 상태로 판단했다.
- 가설 2: 진입 한 건이 하는 일이 많다. → 코드를 따라가며 Redis 왕복 횟수를 셌다.

| 단계 | 왕복 |
|---|---|
| 정책 조회 (패널티 규칙, 단가, 대기 기록 유지 시간) | 3 |
| 위험 점수 조회 (`multiGet`) | 1 |
| 진입 스크립트 | 1 |
| 진입 직후 번호표 재조회 (회원 키, 토큰, 순번, 입장 속도) | 4 |
| **합계** | **약 9** |

- 최종 원인: 진입 한 건당 Redis를 약 9번 왕복한다. 한 요청이 오래 걸리는 것은 아니지만 모든 요청이 같은 연결과 같은 Redis 한 대를 거치므로 왕복 수가 곧 처리량 상한이 된다.
- 확인하지 못한 것: 병목이 앱 CPU인지 Redis인지 k6인지는 도구로 직접 확인하지 못했다. "왕복이 많다"는 코드 근거와, 줄이자 처리량이 올랐다는 결과의 일치로 판단했다.

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| A. 앱 스레드·서버 대수 늘리기 | 코드 변경 없음 | 한 PC에서는 효과 불명확, Redis 왕복은 그대로 | |
| B. 왕복 줄이기 | 한 요청의 일이 줄어 어디서나 이득 | 정책이 최대 1초 늦게 반영됨, 스크립트가 길어짐 | ✓ |

- 선택한 이유: 원인으로 보이는 것이 왕복 수라서 거기를 직접 줄였다.
- 바꾼 것:
  1. 정책 값을 앱에서 1초 캐시 → 진입마다 3번 읽던 조회 제거 (`PolicyProvider`)
  2. 진입 스크립트가 순번·입장 속도를 함께 돌려줌 → 재조회 제거 (`enter.lua`)
  3. 번호표 조회를 스크립트 하나로 통합 (`status.lua`, 4번 → 1번). 조회 도중 입장 처리가 끼어들어도 결과가 어긋나지 않음
- 결과: 진입 왕복 9번 → 2번 (위험 점수 조회 1 + 진입 스크립트 1)
- 바뀐 코드 위치: `src/main/java/com/jejari/queue/domain/QueueService.java`, `PolicyProvider.java`, `src/main/resources/lua/queue/enter.lua`, `status.lua` (`2dc0269`)
- 부작용: 정책을 바꾸면 최대 1초 뒤 반영된다. 이 때문에 순번 조정 시나리오가 한 번 실패했다 (`20261116-패널티-봇-선입장.md` 참고).

## 4. 수치

클라우드 컨테이너 4코어, 같은 머신에서 k6·앱·Redis 실행, 각 2회 측정 (표는 범위).

| 목표(건/초) | 개선 전 실제 · p95 | 개선 후 실제 · p95 |
|---|---|---|
| 3000 | 2814~2858 · 194~237ms | 2977~2999 · 9~53ms |
| 4000 | 2800~2958 · 568~625ms | 3984~3999 · 32~62ms |
| 6000 | 2889~3048 · 585~612ms (정체) | 4651~5016 · 330~393ms (정체) |

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 처리량이 정체하는 지점 | 약 2,900건/초 | 약 4,700~5,000건/초 |

내 PC (Windows, k6·앱·Redis(Docker) 동시 실행, 코어 수는 기록하지 못함). 개선 전·후 각 1회.

| 목표(건/초) | 개선 전 실제 · p95 · 못 보낸 | 개선 후 실제 · p95 · 못 보낸 |
|---|---|---|
| 2000 | 1992 · 64ms · 160 | 2000 · 17ms · 0 |
| 3000 | (측정 안 함) | 2895 · 123ms · 1,048 |
| 4000 | 2009 · 570ms · 39,823 (정체) | 3008 · 554ms · 9,931 (정체) |
| 6000/8000 | 2059 · 559ms (8000, 정체) | 3020 · 597ms (6000, 정체) |

| 지표 (내 PC) | 개선 전 | 개선 후 |
|---|---|---|
| 처리량이 정체하는 지점 | 약 2,000건/초 | 약 3,000건/초 |

- **비교 조건이 완전히 같지는 않다.** 개선 전은 단계 20초·k6 최대 VU 1,000·목표 500~8,000, 개선 후는 단계 10초·최대 VU 1,500·목표 1,000~6,000이었다. 처리량 정체 지점은 비교할 수 있지만, 정체 구간의 p95(약 550~600ms)는 "VU 상한 ÷ 처리량"으로 정해져(1,500 ÷ 3,000 = 0.5초) VU 상한이 다르면 비교 대상이 아니다. 같은 조건으로 다시 재면 더 정확하다.
- 두 환경(내 PC 약 1.5배, 클라우드 약 1.6배)에서 개선 폭이 비슷한 것은 왕복 수 감소가 환경과 무관하게 효과가 있다는 근거다.
- 측정 환경: 4코어 컨테이너, Redis 7.0 로컬 프로세스, 앱은 `bootRun`, 회원·운행은 개발용 대용품(메모리 조회). 첫 실행은 JVM 예열 영향이 있어(개선 전 1회차 1000건/초 단계 p95 191ms) 2회차 값을 기준으로 보았다.
- 측정 방법: `./k6/queue/reset.sh` 후 `k6 run -e RATES=1000,2000,3000,4000,6000 -e STEP_SEC=10 -e GAP_SEC=3 -e MAX_VUS=1500 k6/queue/entry-burst.js`
- 개선 뒤에도 단위·통합 테스트 42개와 k6 흐름·차단율·순번 조정 시나리오가 그대로 통과했다.

## 5. 정리

- 면접용 한 줄 요약: "진입 처리량이 초당 약 2,900건에서 정체해서 코드를 따라가 보니 진입 한 건이 Redis를 9번 왕복하고 있었고, 정책 캐시와 스크립트 통합으로 2번으로 줄여 정체 지점을 약 4,700~5,000건/초로 올리고 4,000건/초 구간의 p95를 568~625ms에서 32~62ms로 낮췄다. 단, 병목 위치는 도구로 확인하지 못하고 코드 근거와 측정 결과로 판단했다."
- 다음에 비슷한 상황이면: 처리량이 정체하면 서버를 늘리기 전에 요청 하나가 외부 호출(Redis·DB)을 몇 번 하는지부터 센다. 병목은 추정하지 말고 CPU·Redis 지연(`redis-cli --latency`, `info commandstats`)으로 먼저 확인한다.
- 남은 일: ① 내 PC 개선 전·후를 같은 조건(단계 길이, 최대 VU)으로 다시 재고 CPU 코어 수 기록 ② 실제 회원 조회(DB)가 붙은 뒤 진입 처리량 재측정 ③ 병목을 도구로 확인해 이 문서의 "원인" 칸 보강.
