# [queue] Redis가 끊기면 요청마다 스레드를 60초 붙잡고 500을 돌려줌

> 파일 이름: `docs/김성원/troubleshooting/20261116-Redis-끊김-60초-대기.md`

## 1. 문제

- 현상: Redis가 꺼진 상태에서 진입 API를 부르면 응답이 **60초** 뒤에야 500으로 돌아왔다. 팀원 PC에서 Redis 없이 `entry-burst.js`를 돌렸을 때는 "실패율 100%, 지연이 1초→11초로 증가"하는 표만 나와서 성능 문제처럼 보였다.
- 재현 조건: 앱을 띄운 채 Redis를 종료하고 `curl -X POST -H "X-Member-Id: 1" localhost:8080/api/v1/runs/1001/queue`
- 영향: 요청마다 서버 스레드를 60초씩 붙잡는다. Redis가 잠깐만 끊겨도 스레드가 순식간에 다 묶여 **앱 전체가 멈추고**, 복구 뒤에도 대기가 풀릴 때까지 응답이 없다. 클라이언트는 원인을 알 수 없는 500만 받는다.

## 2. 원인

- 가설: Lettuce(Redis 클라이언트)가 연결이 끊긴 동안 명령을 버리지 않고 재연결을 기다리며 쌓아 둔다. → 맞았다. Lettuce의 기본 동작은 재연결 동안 명령을 큐에 쌓아 두고, 명령 응답 대기는 60초다.

```
$ time curl -m 70 -X POST -H "X-Member-Id: 2" localhost:8080/api/v1/runs/1001/queue
status=500 time=60.036467s
```

- 최종 원인: 끊김 상태에서 명령을 즉시 거절하는 설정이 없고(기본 60초 대기), 연결 오류를 별도로 처리하지 않아 일반 500으로 나갔다.

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| A. 타임아웃만 2초로 줄임 | 설정 한 줄 | 끊긴 동안에도 요청마다 2초씩 스레드를 붙잡음 | |
| B. 끊김 상태에서 명령을 즉시 거절 + 타임아웃 2초 | 끊긴 동안 거의 즉시 실패, 스레드 안 묶임. 재연결은 계속 시도해 복구 자동 | 일시적 끊김에도 그 순간 요청은 실패 (클라이언트 재시도 필요) | ✓ |

- 추가로 연결 문제는 500이 아니라 `503 SERVICE_UNAVAILABLE`(`{code, message, traceId}`)로 알린다. 연결과 무관한 Redis 오류(스크립트 오류 등)는 숨기지 않고 그대로 서버 오류로 남긴다.
- 입장 토큰 필터도 같은 처리: Redis를 못 읽으면 토큰을 확인할 수 없으므로 통과시키지 않고 503 (닫는 쪽으로 실패).
- 바뀐 코드 위치: `QueueConfig.lettuceFailFast`(`REJECT_COMMANDS`), `application.yml`(`timeout`, `connect-timeout` 2초), `ApiExceptionHandler`, `QueueTokenFilter`
- k6 시나리오에는 시작 전 사전 점검(`preflight`)을 넣어, 앱·Redis 문제를 "실패율 100% 표"가 아니라 원인과 함께 알려 주도록 했다.
- 놓쳤다가 고친 것: 처음에는 처리기가 예외를 못 잡아 여전히 500이 나왔다. 끊김 상태에서 Spring이 던지는 예외가 `RedisSystemException`이라서였고, 실제 로그로 확인해 맞췄다.

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| Redis 끊김 중 진입 응답 | 60.04초 → 500 | 0.006초 → 503 |
| Redis 끊김 중 좌석 API(토큰 확인) | (스레드 60초 점유) | 0.007초 → 503 |
| Redis 복구 후 | 대기가 풀릴 때까지 응답 없음 | 앱 재시작 없이 즉시 정상 (200, 0.011초) |

- 측정 환경: 클라우드 컨테이너 4코어, Redis 7.0 로컬 프로세스, 앱 `bootRun`
- 측정 방법: 앱 실행 → `redis-cli shutdown nosave` → 위 `curl` 반복 → Redis 재시작 → 같은 `curl` (단위 테스트 `ApiExceptionHandlerTest` 4개 포함)

## 5. 정리

- 면접용 한 줄 요약: "부하 테스트에서 전부 실패하는 표가 나와 원인을 찾다가, Redis가 끊기면 클라이언트 기본 설정 때문에 요청마다 스레드를 60초 붙잡아 앱 전체가 멈춘다는 걸 발견해, 끊긴 상태에서 명령을 즉시 거절하고 503으로 알리도록 바꿔 응답을 60초에서 6ms로 줄이고 복구는 자동이 되게 했다."
- 다음에 비슷한 상황이면: 외부 시스템(Redis·DB·PG)이 죽었을 때 어떻게 되는지 부하를 걸기 전에 먼저 한 번 꺼 보고, 기본 타임아웃(대부분 수십 초)을 확인한다. 장애는 "빨리 실패해서 퍼지지 않게" 하는 것이 먼저다.
- 남은 일: Oracle·Kafka·PG 쪽도 같은 점검이 필요하다 (각 담당 파트). 기능설계서 9장에 `SERVICE_UNAVAILABLE`(503) 추가 요청.
