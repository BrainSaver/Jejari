## 1. 문제

한글이 코드(주석·문자열)와 테스트 이름에 많이 들어 있어서, 시스템 기본 인코딩이 UTF-8이 아닌 환경에서 두 군데가 깨졌다.

- **컴파일**: 팀원이 "hmac/build.gradle에 UTF-8이 없어서 한글이 깨질 수 있다"고 지적했다. 기본 인코딩이 US-ASCII인 환경에서 컴파일하면 실패하거나, MS949 같은 환경이면 오류 없이 한글이 `?????`로 바뀐 채 컴파일될 수 있다.

```
PseudonymizerTest.java:19: error: unmappable character (0x82) for encoding US-ASCII
```

- **테스트 리포트**: 테스트는 통과했는데 Gradle이 HTML 리포트를 만들다 실패했다. 한글 테스트 이름이 파일 이름이 되기 때문이다 (팀의 기존 테스트에서도 똑같이 남).

```
Could not generate test report to '.../build/reports/tests/test'.
   > Malformed input or input contains unmappable characters: ./com.jejari.common.error.ErrorResponseTest/예상못한_오류는_500이고_내부_메시지를_숨긴다().html
```

## 2. 원인

- 컴파일: `java-library` 플러그인만 쓰던 `hmac/`는 컴파일 인코딩을 지정하지 않았다. JDK 18 이상은 기본이 UTF-8이라 대부분 괜찮지만, 구버전 JDK의 Windows(MS949)나 로케일이 C/POSIX인 리눅스에서는 깨진다. Spring Boot 플러그인은 자동으로 UTF-8을 지정해서 `queue/`는 원래 안전했다.
- 리포트: 파일 이름을 만들 때 OS의 파일 이름 인코딩(`sun.jnu.encoding`)을 쓰는데, 이 환경의 로케일이 ASCII였다. 코드 문제가 아니라 환경 문제다.

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 컴파일: `options.encoding = 'UTF-8'` 명시 | 환경과 무관하게 같은 결과 | 없음 | ✓ |
| 리포트: 테스트 이름을 영문으로 | 로케일과 무관 | 한글 테스트 이름이 팀 규칙이라 전부 바꿔야 함 | |
| 리포트: 실행 환경을 UTF-8 로케일로 (`LC_ALL=C.UTF-8`) | 코드 변경 없음 | 환경마다 설정 필요 | ✓ (우회) |

- 바뀐 것: `hmac/build.gradle`에 인코딩 명시 (이후 `hmac`이 루트 프로젝트로 합쳐져 Boot 플러그인이 같은 일을 함). 리포트 문제는 CI(ubuntu, 기본 UTF-8)에서는 일어나지 않는다고 보지만 직접 확인하지는 못했다.

## 4. 수치

기본 인코딩을 US-ASCII로 바꿔 같은 조건에서 비교했다.

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| hmac 컴파일 | 실패 (`unmappable character`) | 성공 |
| 테스트 리포트 (로케일 ASCII) | 실패 | 성공 (`LC_ALL=C.UTF-8`) |

- 측정 방법: `LC_ALL=C ./gradlew clean compileJava compileTestJava --no-daemon -Dorg.gradle.jvmargs=-Dfile.encoding=COMPAT`

## 5. 정리

- 면접용 한 줄 요약: "한글 소스가 많은데 인코딩을 지정하지 않은 모듈이 로케일에 따라 컴파일이 실패하거나 한글이 깨질 수 있다는 걸 기본 인코딩을 바꿔 재현하고, 컴파일 인코딩을 명시해 환경과 무관하게 같은 결과가 나오게 했다."
- 다음에 비슷한 상황이면: Spring Boot 플러그인을 쓰지 않는 모듈은 `options.encoding = 'UTF-8'`을 직접 넣는다. 리눅스에서 한글 테스트 이름의 리포트가 실패하면 `LC_ALL=C.UTF-8`을 확인한다.
