# [member] 정지된 회원이 같은 명의로 다시 가입하고, 남은 토큰으로 결제·탈퇴까지 할 수 있었음

| 항목 | 내용 |
|---|---|
| 작성자 | 김성원 |
| 날짜 | 2026-11-25 |
| 상태 | 해결 |
| 관련 커밋·이슈 | 이 문서와 같은 커밋 (보안 점검 2026-11-25 §2.1·§2.2) |

## 1. 문제

- 현상 1 (§2.1, High): 관리자가 정지(`BANNED`)한 회원이 **같은 이름·휴대폰으로 본인인증하고 다른 이메일로 가입하면 201**이 나와 새 `ACTIVE` 계정이 생겼다. 새 계정으로 로그인·대기열 진입이 모두 됐다.
- 현상 2 (§2.2, Medium): 정지 직전에 받은 액세스 토큰(최대 15분)으로 아래가 모두 성공했다.
  - 결제 시작 `201 APPROVED/CONFIRMED`
  - 정보 변경 `200`(연락처·비밀번호), 원문 보기 `200`
  - 탈퇴 `204` → 이메일이 `withdrawn-{id}@…`로 바뀌어 **같은 이메일로 다시 가입할 수 있는 상태**가 됨
- 재현 조건: 회원 가입·로그인 → (현상 2는 좌석 선점까지) → `UPDATE member SET status='BANNED'` (관리자 정지와 같은 효과) → 위 요청
- 영향: 위험 점수로 막은 매크로·암표 사용자가 정지를 그대로 피해 갈 수 있었다. 정지의 의미가 없어진다.

## 2. 원인

- 가설: 정지 처리(`CaseActionService.ban`)가 세션을 안 지운다 → 확인해 보니 `auth_session`은 폐기하고 있었다. 문제는 그 다음이었다.
- 액세스 토큰은 서버에 묻지 않고 서명·만료만 확인하는 방식(stateless JWT)이라, 세션을 지워도 이미 받은 토큰은 15분 동안 통과한다. 그래서 **기능마다 DB의 `member.status`를 봐야** 하는데, 보는 곳과 안 보는 곳이 섞여 있었다.

| 기능 | DB 상태 확인 | 정지 회원 |
|---|---|---|
| 대기열 진입 `QueueService.enter` | O | 403 |
| 좌석 선점 `SeatHoldService.memberCiHash` | O | 403 |
| 취소표 대기 `WaitlistService.apply` | O | 403 |
| 비회원 입장 `GuestService.checkAllowed` | O (CI 기준) | 403 |
| **회원 가입** `SignupService` | **X** (게스트 행만 찾음) | 201 |
| **결제 시작** `PaymentService.start` | **X** | 201 |
| **정보 변경·원문·탈퇴** `MyAccountService` | **X** (게스트 여부만) | 200/204 |

- 최종 원인: 정지 여부를 보는 공용 장치 없이 기능마다 따로 확인했고, 가입·결제·내 정보에서 빠졌다. 가입은 회원 ID가 없어 CI로 봐야 하는데, 그 확인이 비회원 입장에만 있었다.

```
SignupService.insert : SELECT member_id FROM member WHERE ci_hash = ? AND member_type = 'GUEST'   -- BANNED 행을 안 봄
GuestService         : SELECT member_type, status, withdrawn_at FROM member WHERE ci_hash = ?   -- BANNED면 403
```

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 모든 요청마다 필터에서 `member.status` 조회 | 빠지는 기능이 없다 | 대기열 폴링처럼 매우 잦은 요청마다 DB 조회가 붙는다 | |
| 액세스 토큰 수명을 짧게(1~2분) | 구멍이 줄어든다 | 없어지지는 않는다. 재발급이 잦아진다 | |
| 공용 검사기 `MemberStatusGuard`를 만들어 **돈·계정이 바뀌는 기능**에서만 확인 | 호출이 드문 기능이라 조회 1번은 부담이 없다. 확인 기준이 한 곳에 모인다 | 새 기능을 만들 때 붙이는 걸 잊을 수 있다 | ✓ |

- 선택한 이유: 정지 회원이 실제로 이득을 보는 기능(가입·결제·연락처 변경·탈퇴)만 막으면 되고, 이 기능들은 호출이 드물다. 대기열·좌석 선점은 원래 막혀 있었다.
- 바뀐 코드
  - `member/MemberStatusGuard.java` (새 파일): `forbidBanned(memberId)`, `forbidBannedCi(ciHash)` — `GuestGuard`와 같은 방식(JWT가 아니라 DB로 판단)
  - `member/signup/SignupService.java`: 토큰 확인 직후(토큰을 쓰기 전)와 저장 트랜잭션 안, 두 번 CI로 확인
  - `payment/PaymentService.java`: 멱등 키를 잡기 전에 확인. 막히면 선점 좌석을 바로 반환(`releaseForRiskBlock`, 위험 점수 차단과 같은 경로)
  - `member/me/MyAccountService.java`: 정보 변경·원문 보기·탈퇴
- **일부러 열어 둔 것** (팀 결정이 필요하면 다시 논의)
  - `GET /api/v1/me`: 화면이 "정지된 계정"을 안내하려면 상태를 읽을 수 있어야 한다.
  - 예약 취소: 막으면 정지 회원의 좌석이 묶이고 본인 돈도 환불되지 않는다. 취소를 허용하는 편이 좌석을 다른 사람에게 돌려준다.

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 정지 명의로 다른 이메일 재가입 | 201 (새 ACTIVE 계정) | 403 AUTH_BANNED, 회원 행 생성 0 |
| 정지 직후 토큰으로 결제 | 201 APPROVED | 403, 선점 예약은 즉시 CANCELED |
| 정지 직후 정보 변경 / 원문 / 탈퇴 | 200 / 200 / 204 | 403 / 403 / 403 |
| 정지 직후 내 정보 조회 | 200 | 200 + `status: BANNED` (의도) |

- 측정 환경: 로컬 Docker Compose 인프라 + `bootRun`(운영 모드 `jejari.dev-mode=false`), 실제 HTTP 요청
- 측정 방법: 회귀 테스트 `src/test/java/com/jejari/member/SecurityAuditInfraTest.java`
  ```bash
  set -a && . <(grep -E "^JEJARI_(ENC|PEPPER|HMAC)" .env) && set +a
  LC_ALL=C.UTF-8 TZ=Asia/Seoul ./gradlew infraTest --tests 'com.jejari.member.SecurityAuditInfraTest'
  ```

## 5. 정리

- 면접용 한 줄 요약: "무상태 JWT라 정지 후에도 토큰이 15분 살아 있었고 가입은 정지 명의를 보지 않아, 정지 회원이 재가입·결제·탈퇴로 정지를 피할 수 있었다. 공용 정지 검사기를 만들어 돈·계정이 바뀌는 기능에서 DB 상태를 확인하게 바꿔 우회 경로를 0으로 만들었다."
- 다음에 비슷한 상황이면: 결제·계정 변경처럼 되돌리기 어려운 기능을 새로 만들 때 `GuestGuard.forbidGuest`와 `MemberStatusGuard.forbidBanned`를 같이 붙인다. "토큰이 유효하다"와 "지금 이 사람이 해도 된다"는 다른 질문이다.
