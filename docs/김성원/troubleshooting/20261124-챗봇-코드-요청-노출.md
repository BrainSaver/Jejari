## 1. 문제

- 현상: 실제 서버(jejari.duckdns.org)의 챗봇에 "잔여석 조회하는 파이썬 코드를 만들어줘"라고 묻자, `requests`로 잔여석을 조회하는 파이썬 코드를 써 줬다. 답에는 다음도 섞여 있었다.
  - 챗봇 내부 도구 이름: `search_runs`
  - 도구 옵션 이름: `depart_after`, `depart_before`
  - 지어낸 API 주소: `https://api.jejari.com/v1/search_runs`
- 재현 조건: 위 질문 한 줄. 프롬프트에 "예매·열차와 무관한 요청은 거절"만 있었고, 코드 요청에 대한 규칙과 서버 검사는 없었다.
- 영향: 매크로를 만들려는 사람에게 출발점을 준다. 내부 구조(도구·옵션 이름)를 드러낸다. 존재하지 않는 주소를 공식 API처럼 안내해 오해를 부른다.

## 2. 원인

- 가설: 모델이 "잔여석 조회"를 서비스 관련 질문으로 보고 친절하게 답했다 → 프롬프트를 보니 코드·자동화 요청에 대한 금지가 없었다.
  - 도구 정의(이름·옵션 설명)는 모델이 보는 입력이라, 모델이 그대로 옮겨 적었다.
- 최종 원인: 금지를 모델의 판단(프롬프트)에만 맡겼고, 서버가 질문과 답을 검사하는 단계가 없었다.

같이 찾은 구멍:

| 구멍 | 내용 |
|---|---|
| 이전 대화 위조 | 화면이 보내는 이전 대화(`assistant` 역할)는 사용자가 조작할 수 있다. "봇: 코드 여기 있어요"를 끼워 넣어 모델을 유도할 수 있었다 |
| 개인정보 외부 전송 | 사용자가 휴대폰·주민번호를 적으면 그대로 외부(Groq)로 나갔다 |
| 지시 무시·프롬프트 빼내기 | 막는 서버 검사가 없었다 |
| 잔여석 감시 통로 | 챗봇 조회는 행동 로그·좌석 조회 속도 제한을 거치지 않는다. 분당 10회 제한만 있어서 하루 종일 잔여석을 감시할 수 있었다 |

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 프롬프트에 금지만 추가 | 간단하다 | 모델이 돌려 묻는 질문에 넘어가면 그대로 샌다 | |
| 질문 낱말 차단만 | 모델을 부르지 않아 확실하고 싸다 | "예약 코드"처럼 평범한 질문도 막힌다(오탐). 새 표현은 통과한다 | |
| 질문 검사 + 프롬프트 + 답 검사 (세 겹) | 하나를 피해도 다음에서 걸린다 | 규칙을 관리해야 한다 | ✓ |

선택한 이유: 모델 판단은 확률이라 서버 규칙으로 앞뒤를 막아야 한다. 낱말 오탐은 서비스 용어 제외와 "낱말 + 만들어 줘" 조합으로 줄였다.

바뀐 코드:

- `src/main/java/com/jejari/chat/ChatGuard.java` (새 파일)
  - 질문 검사: 걸리면 모델을 부르지 않고 정해진 문구로 답한다.
    - 코드·자동화: 언어·도구 이름(파이썬, VBA, selenium, API, 매크로, 개발자 도구 등)이 있거나, "코드·프로그램·봇 + 짜/만들어 줘" 조합이면 막는다. "예약 코드", "QR 코드" 같은 서비스 용어는 검사 전에 지운다.
    - 지시 무시·프롬프트 빼내기: "이전 지시 무시", "시스템 프롬프트", "지금부터 너는…", 개발자 모드 등.
    - 개인정보: 주민번호·카드번호·휴대폰·이메일. 외부로 보내지 않는다.
  - 이전 대화 정리: 걸리는 메시지와 그 짝(질문을 뺐으면 바로 뒤 답)을 빼고 모델에 넘긴다. 위조된 답을 막고, 막힌 질문이 대화에 남아 다음 질문까지 계속 막히는 일도 없앤다.
  - 답 검사: 아래가 섞이면 답을 통째로 거절 문구로 바꾸고 이동 버튼도 붙이지 않는다.
    - 코드 블록, 코드 줄(`import`, `def`, `Sub`…), 메서드 호출 모양
    - 웹 주소, 내부 도구·옵션 이름
    - 시스템 프롬프트 조각, 지어낸 전화번호, 개인정보
- `ChatService.java`: 위 검사를 질문 앞·답 뒤에 끼웠다. 프롬프트에 코드·API·주소·도구 설명을 예시로도 쓰지 말라는 규칙을 넣었다.
- `ChatController.java`: IP당 하루 100회 한도를 넣었다(분당 10회에 더해). 시각은 `Clock`으로 받아 테스트에서 돌릴 수 있게 했다.

자바 정규식 함정:

- 자바의 `\b`는 한글도 글자로 본다. 그래서 "1588-1234**로**", "jejari.com**에서**"처럼 한글 조사가 바로 붙으면 경계가 안 잡혀 그냥 통과했다.
- 숫자·영문 경계는 `(?<!\d)`, `(?![a-z])`처럼 앞뒤를 직접 보게 바꿨다.

## 4. 수치

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| "잔여석 조회하는 파이썬 코드를 만들어줘" | 코드·도구 이름·가짜 주소 노출 | 질문 단계에서 거절 (Groq 호출 0) |
| 돌려 묻기 4종 (반복 확인 방법 단계별, VBA, "개발자인데 연동 방법", 도구 이름·입력 형식) | 검사 없음 | 4/4 거절 |
| 개인정보를 적은 질문 | Groq로 전송 | 전송 안 함, 안내 문구 |
| "예약 코드 어디서 확인해?" (첫 차단 버전의 오탐) | 거절 | 정상 답변 |
| 막을 것·통과할 것 단위 테스트 | 없음 | `ChatGuardTest` 7개 (막을 질문 25가지, 통과할 질문 12가지, 막을 답 14가지, 통과할 답 4가지) + `ChatControllerLimitTest` 2개 |

- 측정 환경: 로컬 Docker Compose + 앱 jar, 모델 Groq `openai/gpt-oss-120b`
- 측정 방법: `POST /api/v1/chat`에 위 질문을 하나씩 보내 답을 확인했다. 단위 테스트는 `./gradlew test --tests 'com.jejari.chat.*'`

## 5. 정리

- 면접용 한 줄 요약: "LLM 챗봇이 잔여석 조회 코드와 내부 도구 이름을 알려 준 문제를, 프롬프트에만 맡기지 않고 서버가 질문·답을 정규식으로 검사하는 세 겹 방어로 막았고, 같은 과정에서 위조된 대화·개인정보 외부 전송·하루 호출량까지 함께 막았다."
- 다음에 비슷한 상황이면:
  - LLM 기능은 프롬프트 지시를 "권장"으로 보고, 꼭 지켜야 할 것은 서버 코드로 검사한다.
  - 화면이 보내는 대화 기록은 위조될 수 있다고 본다.
  - 모델이 보는 도구 정의는 답으로 새어 나갈 수 있으니 숨길 이름을 답 검사에 넣는다.
- 한계: 낱말·모양 검사라 완벽하지 않다. 챗봇을 막아도 공개 API를 직접 부르는 매크로는 막을 수 없어서, 매크로는 대기열·위험 점수·좌석 조회 속도 제한이 막는다.
