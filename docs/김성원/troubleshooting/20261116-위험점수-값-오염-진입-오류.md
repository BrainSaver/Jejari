> 파일 이름: `docs/김성원/troubleshooting/20261116-위험점수-값-오염-진입-오류.md`

## 1. 문제

- 현상: 대기열은 Redis `risk:{CI|PAYMENT|DEVICE}:{해시}` 값을 `Double.parseDouble`로 읽었다. 값이 숫자 문자열이 아니면 아래처럼 동작했다 (자바 코드를 직접 실행해 확인).

| 캐시 값 | 기존 동작 | 결과 |
|---|---|---|
| `abc`, 빈 문자열, `0x10` | `NumberFormatException` | 그 회원의 진입이 500 오류 |
| `NaN` | 계산이 `NaN`이 되고 패널티가 `0`으로 반올림 | **패널티가 조용히 사라짐** (위험 사용자가 정상 사용자처럼 통과) |
| `Infinity` | 패널티가 `Long.MAX_VALUE` | score 계산이 넘칠 수 있음 |
| `1000` | 패널티 1,000초 | 범위(0~100)를 벗어난 값이 그대로 반영 |
| `-5` | 0으로 처리 | 음수가 0점이 됨 |

- 재현 조건: 쓰는 쪽(다인 님의 배치)이 JSON이나 오염된 값을 `SET` 하거나, 누군가 Redis 값을 조작한 경우. 지금은 `risk:*`를 쓰는 쪽이 아직 없어 실제로 발생한 적은 없다.
- 영향: 오류는 해당 회원만 막히지만, `NaN`은 **위험 사용자의 패널티를 없애는 우회로**가 된다.

## 2. 원인

- 가설: 값 형식을 대기열이 검증하지 않고 `parseDouble`이 받아 주는 모든 문자열(`NaN`, `Infinity`, `1e2`, `80d`)을 숫자로 믿었다.
- 확인: 아래 값을 직접 `parseDouble` → `Math.max` → `Math.round(×1000)`에 넣어 표의 결과를 얻었다.
- 최종 원인: 입력 검증 없이 "쓰는 쪽이 항상 올바른 숫자를 쓴다"고 가정했다.

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| A. 잘못된 값은 무시(0점) | 진입이 막히지 않음 | 조작된 값이 곧 "패널티 없음"이 되는 우회로 | |
| B. 잘못된 값은 100점으로 처리 + 경고 | 오염돼도 통과가 아니라 막는 쪽으로 동작 | 쓰는 쪽 버그가 있으면 정상 사용자도 뒤로 밀림 (경고 로그로 발견) | ✓ |
| C. 오류로 진입 거절 | 가장 엄격 | 회원 한 명의 값 하나로 진입 불가 | |

- 선택한 이유: 위험 점수는 "모르면 막는 쪽"이 안전하다. 패널티는 진입을 거절하지 않고 순번만 미루므로 B가 피해가 작다.
- 규칙: `0~100`의 십진수 문자열(소수 6자리까지)만 인정. 정규식으로 먼저 형식을 거르고, 그다음 범위를 확인한다 (`parseDouble`에 맡기면 `NaN`·`1e2`가 통과함). 여러 값 중 하나라도 오염되면 100점. 경고 로그는 10초에 한 번만 남긴다 (폭주 중 로그 폭발 방지).
- 같이 넣은 것: `risk:meta:synced_at`(배치가 전체 동기화를 끝낼 때 갱신)이 없으면 캐시를 믿지 않고 Oracle에서 직접 조회, 조회 실패 시 100점. Redis 재시작 뒤 "빈 캐시 = 0점"으로 위험 사용자가 통과하는 구멍을 막는다.
- 바뀐 코드 위치: `src/main/java/com/jejari/queue/domain/RiskPenaltyService.java`, `port/RiskScoreFallbackPort.java`
- 부작용: Redis 재시작 뒤 다음 재동기화 전까지 모든 진입이 Oracle을 조회한다 (최대 10분). `팀-확인-요청.md` 17번에서 대응을 협의 중이다.

## 4. 수치

- `RiskPenaltyServiceTest` 9개 추가 (잘못된 값 15종 → 전부 100점, 정상 값 7종 → 그대로, 표시 키 유무별 Oracle 호출 여부). Redis 통합 테스트 48 → 57개 통과.
- 처리량 영향은 재지 않았다. 표시 키는 기존 `MGET`에 한 키를 더 얹은 것이라 왕복은 늘지 않는다 (재측정 예정).
- 측정 환경: Redis 7.0 로컬 프로세스. 측정 방법: `./gradlew infraTest`.

## 5. 정리

- 면접용 한 줄 요약: "위험 점수 캐시를 `parseDouble`로 믿고 읽다가 `NaN` 값이 들어오면 패널티가 조용히 0이 되는 우회로가 있는 것을 발견해서, 형식·범위 검증과 '오염되면 100점' 규칙, 동기화 표시 키 확인을 넣었다."
- 다음에 비슷한 상황이면: 다른 파트가 쓰는 값을 읽을 때는 "항상 올바르다"고 가정하지 말고, 검증 실패 시 안전한 쪽(통과가 아니라 제한)으로 동작하게 만든다. 숫자 파서(`parseDouble`)가 받아 주는 입력의 범위를 먼저 확인한다.
- 남은 일: Redis 재시작 시 Oracle 조회 부하 제한, 표시 키 오래됨 감지 (17번 협의 후).
