## 0. 먼저 읽기 — 30초·2분 소개

### 30초 소개 (자기소개 끝에 붙이기)

> 명절 열차를 공정하게 파는 예매 시스템 팀 프로젝트(5명, 3주)에서 **대기열과 식별정보 보호**를 맡았습니다. Redis Lua 스크립트로 번호표 발급과 순번 조정을 원자적으로 처리했고, 위험 점수가 높은 사용자는 요청을 늦추지 않고 **순번만 뒤로 보내도록** 설계했습니다. 부하 테스트로 병목을 찾아 진입 처리량을 약 1.5배 올렸고, 개인정보는 HMAC으로 가명처리했습니다. 이후에는 동시성 테스트, 비회원 예매, 좌석 조회 속도 제한, 딥러닝 봇 탐지 프로토타입까지 넓혔습니다.

### 2분 소개 (발표 도입)

1. **문제**: 명절 예매는 짧은 시간에 요청이 몰리고, 매크로가 좌석을 먼저 가져갑니다 (기획서 근거: 코레일 추석 웹서버 11대→60대 증설, 설 예매 비정상 접근 4만 2천 건 차단).
2. **내가 맡은 것**: 사용자가 좌석을 고르기 *전* 관문. 대기열(번호표·순번·입장 토큰)과, 위험한 사용자를 후순위로 미는 규칙, 식별정보 가명처리.
3. **핵심 선택 3가지**: ① 진입 판단을 Lua 스크립트 한 번으로 ② 패널티는 지연이 아니라 순번 조정 ③ 입장 토큰은 Redis에 두고 컨트롤러 앞단에서 검증.
4. **검증**: k6 부하 테스트로 처리량, 순번 조정 정확도, 토큰 없는 호출 차단율을 숫자로 확인.
5. **한계와 배운 점**: 딥러닝 봇 탐지는 합성 데이터에서만 잘 맞고 실제 로그에서는 실패했다 (→ 8장에서 솔직하게).

## 3. 대기열 — 가장 깊게 파일 것

### 3.1 한 장 그림

```
POST /runs/{id}/queue ──▶ queue:{runId}   (ZSET, score = 진입시각ms + 위험점수×1000ms)
                              │ 1초마다 맨 앞 N명 (queue.admit_per_sec)
                              ▼
                     queue:pass:{runId}:{memberId}  = 256비트 무작위 토큰, 300초
                              │
GET /runs/{id}/seats ◀── X-Queue-Token 검증 (QueueSeatTokenInterceptor, 컨트롤러 앞)
POST /reservations   ◀── QueuePassService.verify 를 컨트롤러가 직접 호출 (운행 ID가 본문에 있어서)
```

### 3.2 `enter.lua` — 진입 판단을 한 번에 🟢

한 번의 스크립트 안에서 순서대로 합니다.
1. `redis.call('TIME')`으로 **Redis 시각**을 읽는다 (앱 시계가 아님).
2. 이미 같은 운행에 줄 섰으면 → 기존 순번 그대로 (status 1).
3. 다른 운행에 대기 중이면 → 거절 (-1).
4. **같은 CI의 다른 회원**이 대기 중이면 → 거절 (-2). 만료된 멤버는 먼저 정리.
5. `ZCOUNT`로 "패널티가 없었다면 몇 번째였을지" 계산.
6. `INCR`로 번호표 발급, 멤버는 `000000000012:{회원ID}` 형식 (12자리 0 채움).
7. `ZADD score = now + 패널티ms`.
8. 활성 운행 목록(`queue:runs`)에 추가, 대기 기록·CI 기록 저장, 판매 마감 시각에 TTL.
9. `ZRANK`로 조정된 순번 반환.

**왜 Lua인가**: 여러 명령이면 동시 요청이 사이에 끼어든다 (새로고침 연타, 다계정 동시 진입). Redis는 스크립트 하나를 끝까지 실행한 뒤 다음을 처리하므로 **락 없이 원자성**이 생기고 왕복도 1번이다.
- 대안: ① 앱에서 분산 락 → 락 자체의 왕복·실패 처리가 늘어남 ② `MULTI/WATCH` → 충돌 시 재시도가 복잡 ③ Lua ✓.
- 확인한 것: 500명 동시 진입에서 번호표 중복 0, 같은 회원 50번 연타에서 줄에 1번, 같은 CI 20계정 동시 진입에서 1계정만 성공 (`QueueServiceTest`, 문서 기록).

**왜 Redis `TIME`인가**: 앱이 시각을 찍으면, 시각을 읽고 잠깐 멈춘 요청이 번호표는 늦은데 시각은 이른 값을 받아 **순번이 뒤집힐 수 있다**. 앱이 여러 대면 서버 시계 차이도 섞인다. 번호표 발급과 시각 읽기가 같은 스크립트 안이라 시각 순서 = 번호표 순서가 항상 보장된다.
- 감수한 단점: Redis 한 대의 시계가 기준. 클러스터로 가면 샤드마다 시계가 달라 보장이 약해지고, 스크립트가 쓰는 키를 같은 슬롯에 두어야 한다 (이 프로젝트는 단일 노드 전제).

**왜 멤버를 `번호표:회원` 12자리 0채움으로?** ZSET은 score가 같으면 멤버를 사전순으로 정렬한다. 0을 채워 두면 같은 score일 때 **번호표 순서**가 곧 정렬 순서가 된다. 회원 ID 크기는 순서에 영향을 주지 않는다.

### 3.3 `admit.lua` — 입장 처리 🟢

- `ZPOPMIN`으로 맨 앞 N명을 꺼내 토큰(`SET ... PX`) 발급, `queue:active`에 기록.
- **유령 방지**: 줄(ZSET)과 대기 기록(`queue:member`)은 서로 다른 키라 TTL이 따로 돈다. 대기 기록이 만료됐는데 줄에 남은 사람(유령)이 입장해 자리를 낭비하는 문제가 있었다. 꺼낸 멤버의 **대기 기록이 있고 번호표가 같을 때만** 입장시키고, 건너뛴 자리는 다음 사람으로 채운다.
- **앱이 여러 대여도 초당 입장 수가 정책값**: "이번 1초에 이미 입장시킨 수"를 Redis(`queue:adm:{runId}:{초}`)에 함께 세어 남은 만큼만 입장시킨다. 앱 두 대가 같은 초에 불러도 합쳐서 정책값을 넘지 않는다.
- **활성 운행만 처리**: 줄 선 사람이 있는 운행만 `queue:runs`(SET)에 둬서, 판매 중 운행이 1,000건이어도 사용자가 없으면 `SMEMBERS` 1번이면 끝난다. `reconcile.lua`가 앱 시작 시와 5분마다 빠진 운행을 다시 넣는다.

### 3.4 5분 연장 🟡

`extend.lua`가 **토큰 확인 → 연장 표시(`queue:passext`) → `PEXPIRE`** 를 한 번에 해서, 두 번 누르거나 여러 탭에서 동시에 눌러도 1회만 적용된다. 이미 썼으면 409 `QUEUE_EXTEND_USED`. 남은 시간에 `queue.pass_extend_sec`(기본 300초)을 더한다.

### 3.5 입장 토큰 검증 🟢/🟡

- 키가 `queue:pass:{운행}:{회원}` → **남의 토큰·다른 운행 토큰은 조회 단계에서 걸러진다.** 이탈하면 키만 지워도 즉시 무효.
- **왜 JWT가 아닌가**: JWT는 이미 발급한 토큰을 되돌릴 방법이 없다 (이탈·만료 즉시 무효 불가). Redis 키는 지우면 끝. 대신 좌석 요청마다 Redis를 한 번 읽는 비용.
- 검증 위치: 좌석 조회는 인터셉터에서, `POST /reservations`는 운행 ID가 본문에 있어 필터로 못 막으므로 컨트롤러가 `QueuePassService.verify`를 직접 호출.
- 측정: 차단해야 할 요청 500건(토큰 없음·가짜·남의 토큰·다른 운행·이탈 후) 중 **500건 차단**, 열려야 할 요청 300건 중 300건 통과.

## 4. 위험 사용자는 요청을 늦추지 않고 순번만 뒤로 — 설계 결정

- **상황**: 기획서 요구가 "요청을 지연시키지 않고, 위험 점수만큼 순번을 뒤로 조정해 서버 자원 낭비 없이 후순위로 처리".
- **대안**: ① 요청 처리를 `sleep`으로 지연 ② 위험 사용자용 별도 대기열 ③ 정렬 점수(score)에 패널티를 더해 **한 줄에서 정렬**.
- **선택(③)과 이유**: ①은 스레드·연결을 붙잡아 봇 트래픽이 서버 자원을 갉아먹는다. ②는 두 줄을 합쳐 공정하게 입장시키는 로직이 따로 필요. ③은 `ZADD` 한 번이면 끝나고 입장 처리는 맨 앞부터 꺼내기만 하면 된다.
- **수식**: `score = 진입 시각(ms) + 위험 점수 × risk.penalty_ms_per_point`(기본 1점 = 1초). 위험 점수는 CI·결제 수단·기기 해시 세 가지 중 **최댓값**.
- **감수한 단점 (면접에서 꼭 묻는다)**:
  - 줄이 비어 있으면 패널티가 의미 없다. 봇이 혼자 있으면 바로 입장한다. 그래서 정확한 표현은 **"붐빌 때 뒤로 밀린다"**.
  - 점수는 **진입하는 순간에만** 반영된다. 줄을 선 뒤 점수가 바뀌어도 이미 정해진 순번은 안 바뀐다.
  - 오탐이면 정상 사용자가 손해를 본다 → 그래서 차단이 아니라 순번 조정을 택했다 (되돌릴 수 있는 약한 대응).
- **측정**: 위험 점수 80인 봇 20명이 먼저 줄을 서도 정상 사용자 100명이 전원 입장한 뒤에 입장 **100%** (여러 번 반복). 조건: 입장을 멈춘 채 모두 줄 세운 뒤 입장 시작 (붐비는 오픈 직후 상황).
  - 이 조건은 트러블슈팅에서 나왔다 → 6장 1번.

## 5. 식별정보 가명처리 (HMAC) 🟢(문서)

- 전화번호·CI·카드번호·기기 지문·IP는 **원문을 저장하지 않고 HMAC-SHA256(64자 16진수)** 로만 다룬다. 같은 값은 항상 같은 해시라서 원문 없이 "같은 사람인가"를 비교할 수 있다 (대기열의 같은 CI 중복 방지, 위험 점수 묶음).
- **왜 SHA-256이 아니라 HMAC**: 전화번호는 경우의 수가 작아서 키 없는 해시는 전부 계산해 보면 원문이 나온다(레인보우 테이블식 대입). 비밀 키가 있어야 해시를 만들 수 있게 해서 DB가 유출돼도 원문 복원이 어렵다.
- **왜 종류 이름(`CI`, `PHONE`, `EMAIL`, `PAYMENT`, `DEVICE`, `IP`)을 함께 해시**: 같은 문자열이라도 종류가 다르면 해시가 달라서, 다른 테이블의 해시를 맞대어 사람을 잇지 못한다.
- **표기 차이는 같은 값으로**: `010-1234-5678` = `+82 10 1234 5678`, 이메일 대소문자·공백 무시, 카드번호 하이픈 무시. 안 맞추면 같은 사람이 다른 사람으로 센다.
- **이상한 입력은 조용히 버리지 않고 오류**: 전화번호에 글자가 섞였을 때 글자를 버리면 서로 다른 번호가 같은 해시가 된다. 오류 메시지에도 입력 원문을 넣지 않는다 (로그 유출 방지).
- **지켜야 할 것**: 키(`JEJARI_HMAC_KEY`)는 환경변수로만, **프로젝트 기간 동안 바꾸지 않는다** (바꾸면 지금까지의 해시와 안 이어져 매수 제한·위험 점수 묶음이 끊김). 정규화 규칙·`Purpose` 순서는 고정값 테스트가 막는다.
- **면접 한계 질문**: "키가 유출되면?" → 해시를 새로 만들 수 있게 되어 대입 공격이 가능해진다. 그래서 환경변수로 분리하고 저장소·로그에 안 둔다. 키 교체 절차(재해시 마이그레이션)는 이 프로젝트에서 설계하지 않았다.

## 6. 트러블슈팅 6선 (STAR로 말하기)

면접에서 "어려웠던 문제"를 물으면 이 중 두세 개를 **문제 → 가설 → 원인 → 선택지 → 결과 → 배운 점** 순서로 말하세요. 모두 `docs/김성원/troubleshooting/`에 문서가 있습니다.

### ① 위험 점수 80인 봇이 정상 사용자보다 먼저 입장함 (지표 0%)
- **가설 1**: 점수가 안 읽힌다 → Redis에 80이 있고 로그에 패널티 80,000ms가 찍혀 아니었다.
- **가설 2**: 입장 처리가 패널티와 무관하게 맨 앞을 꺼낸다 → 맞았다. 시나리오가 t=1~2초에 **줄에 봇밖에 없는** 상태였다. 패널티는 "다른 사람보다 뒤로" 보낼 뿐 혼자 있는 사람을 붙잡지 않는다.
- **선택지**: A. 패널티를 실제 대기 시간으로(혼자여도 80초 대기) B. 시나리오를 현실에 맞춤(입장을 멈추고 모두 줄 세운 뒤 시작). **B 선택.** A는 오탐 사용자가 손해를 보는 **설계 변경이라 팀 결정이 필요**해 채택하지 않았다.
- **재발**: 정책 값을 1초 캐시로 바꾸자(성능 개선) 같은 시나리오가 또 0%가 됐다 → 시나리오가 입장 정지(`admit_per_sec=0`)를 걸고 시작하는데 캐시 때문에 최대 1초 늦게 반영됐다.
- **배운 점**: 테스트가 틀린 건지 코드가 틀린 건지 구분하고, 설계 변경은 혼자 정하지 않는다. 성능 개선이 다른 가정을 깨뜨릴 수 있다.

### ② 진입 처리량이 초당 약 2,000~2,900건에서 정체
- **가설 1**: k6 가상 사용자 부족 → 입장을 기다리지 않는 `entry-burst.js`로 바꿔도 같아 아니었다.
- **가설 2**: 요청 하나가 하는 일이 많다 → 코드를 따라가며 **Redis 왕복 횟수를 세었다**: 정책 조회 3 + 위험 점수 1 + 진입 스크립트 1 + 번호표 재조회 4 = **약 9번**.
- **조치**: 정책 값 1초 캐시(3→0), 진입 스크립트가 순번·입장 속도를 함께 반환(재조회 제거), 번호표 조회를 스크립트 하나로 통합(4→1). **9번 → 2번.**
- **결과**: 내 PC 약 2,000 → 3,000건/초(p95 64→17ms @2,000), 클라우드 4코어 약 2,900 → 4,700~5,000건/초(p95 568~625 → 32~62ms @4,000). 실패 0건.
- **솔직한 한계**: k6·앱·Redis가 **한 대에서 같이** 돌았다. "이 환경에서 정체하는 지점"이지 서버 한계가 아니다. 병목이 앱·Redis·k6 중 어디인지는 도구로 직접 확인하지 못했고, "왕복이 많다는 코드 근거 + 줄이자 올랐다는 결과의 일치"로 판단했다. 부작용: 정책 변경이 최대 1초 늦게 반영.
- **배운 점**: 성능은 추측이 아니라 **세어서**(왕복 수) 개선한다. 측정 조건을 같이 말한다.

### ③ Redis가 끊기면 요청마다 스레드를 60초 붙잡고 500
- **원인**: Lettuce는 연결이 끊긴 동안 명령을 버리지 않고 재연결을 기다리며 쌓는다(기본 60초). 스레드가 순식간에 다 묶여 **앱 전체가 멈춘다**.
- **선택지**: A. 타임아웃만 2초 B. **끊김 상태에서 명령을 즉시 거절 + 타임아웃 2초** ✓ (재연결은 계속 시도해 자동 복구).
- 연결 문제는 500이 아니라 **503 `SERVICE_UNAVAILABLE`** 로. 입장 토큰 필터도 Redis를 못 읽으면 통과시키지 않고 503 (**닫는 쪽으로 실패, fail-closed**).
- **fail-open과 fail-closed를 구분해 말하기**: 토큰 검증은 보안이라 닫고(fail-closed), 속도 제한은 "정상 예매를 막으면 피해가 더 크다"여서 Redis가 안 되면 통과(fail-open)시키되 경고 로그·지표를 남긴다.

### ④ 대기 기록이 만료되면 줄에 남은 유령이 입장해 자리를 낭비
- **원인**: 줄(ZSET)과 대기 기록이 다른 키라 TTL이 따로 돌고, `admit.lua`가 꺼낸 멤버의 대기 기록 존재를 확인하지 않았다.
- **선택지**: 입장 때 번호표 일치 확인 ✓ / 만료 때 줄에서도 삭제(keyspace 이벤트) — 이벤트는 유실 가능하고 구성이 복잡해 기각.
- **이유**: 판단을 **입장 시점 Lua 안에서 원자적으로** 하므로 유실·경합이 없다.

### ⑤ 초기화 스크립트가 키 24만 개에서 10분 걸림
- **원인**: 200개씩 지우는데 묶음마다 `docker exec`를 새로 실행하고 명령마다 컨테이너 확인도 함 (호출 약 2,400번). 문서에는 Windows 소요 시간이 **추정**이라고 적혀 있으니 "10분"은 추정치로 말하세요.
- **해결**: 키 목록을 밖으로 가져오지 않고 **Redis 안에서 `SCAN` + `UNLINK`을 Lua로 한 번**. 호출이 키 수와 무관하게 1번. 병목은 호출 횟수였다.

### ⑥ 챗봇이 파이썬 코드와 내부 도구 이름을 알려줌 (보안)
- **원인**: 금지를 모델 판단(프롬프트)에만 맡겼고 서버 검사가 없었다. 같이 찾은 구멍: 이전 대화 위조(`assistant` 역할을 사용자가 조작), 개인정보 외부 전송, 프롬프트 빼내기, 챗봇이 좌석 속도 제한을 우회하는 감시 통로.
- **해결**: **질문 검사 + 프롬프트 + 답 검사 세 겹**(`ChatGuard`). 낱말 오탐("예약 코드")은 서비스 용어를 먼저 지우고 "코드+만들어 줘" 조합으로 줄였다. 위조 가능한 `system`·`tool` 역할은 받지 않는다. IP당 하루 100회 한도 추가.
- **배운 점**: LLM의 판단은 확률이므로 **서버 규칙으로 앞뒤를 막는다**. 자바 `\b`는 한글도 글자로 봐서 "…로", "…에서"가 붙으면 경계가 안 잡혀 통과했다 (정규식 함정).

## 7. 그 밖의 기능 — 한 줄씩 + 왜

### 7.1 좌석 조회·선점 속도 제한 🟡
- **물통 + 잠금 2단**: (회원, 운행)마다 처음 10번은 통과, 이후 초당 1번 충전. 물이 바닥난 채 60초 안에 20번 넘게 거절당하면 60초 쉬게 함. 사람은 거의 안 걸리고 한도에 붙어 두드리는 봇만 걸린다.
- **IP가 아닌 (회원, 운행)** 기준: 공유기·회사망의 정상 사용자가 같이 막히지 않게. **조회와 선점은 따로** 센다. **토큰이 맞는 요청만** 센다(남의 한도를 쓰거나 키를 만들 수 없게).
- **한계**: 속도를 늦출 뿐 구멍을 닫지는 못한다. **계정을 여러 개 쓰는 봇은 계정마다 따로 세므로 못 막는다.** 수치(10·1·20·60)는 추정값이라 로그를 보고 조정.

### 7.2 비회원(게스트) 예매 🟡
- 가입 없이 **본인인증만** 하면 예매. 서버에서는 비밀번호가 없는 회원(`member_type='GUEST'`)이라 대기열·선점·결제·매수 제한·위험 점수가 **그대로** 적용된다.
- **같은 CI는 행 하나를 재사용**: 예매마다 새로 만들면 위험 점수가 "같은 CI의 계정 수"를 세서 다계정으로 오탐한다.
- **`status`가 아니라 `member_type`**: `status`는 관리자 조치 칸이라 GUEST를 넣으면 이용 제한·정지 해제 흐름이 꼬인다.
- 조회: 예약 번호 + 휴대폰 HMAC 비교, 없는 번호·다른 휴대폰·회원 예약은 **모두 같은 404** (존재 여부를 알 수 없게). 기한이 지나면 이름·연락처는 지우고 **CI 해시는 남긴다** (매수 제한 유지).
- **기본은 꺼져 있고**(`guest.enabled=N`) DB 패치 v33을 먼저 적용해야 한다.

### 7.3 예매 안내 챗봇 🟡
- Groq `openai/gpt-oss-120b`에 **도구 호출(function calling)** 로 `search_runs` 등을 요청 → **서버가 실제 `TrainQueryService`를 실행**해 결과를 넘기고 모델이 글로 정리. 모델이 열차를 지어내지 못하게 도구 결과만 근거로 말하게 함. 도구는 최대 3바퀴.
- **조회만** 한다: 챗봇이 대기열·선점·결제를 대신하면 공정 흐름과 봇 탐지가 무의미해진다. 버튼은 화면 이동만.
- 개인정보는 모델에 보내지 않는다. 모델이 자주 내려가 404가 난 적이 있어 모델명은 환경변수.

### 7.4 동시성 테스트 (T6·T16) 🟢 코드 / 🔴 실행
- `concurrency.md §16`의 핵심 10개(T1·T2·T3·T5·T6·T10·T15·T16·T18·T21)가 어느 테스트에서 검증되는지 매핑(`docs/김성원/features/동시성-테스트-매핑.md`). 8개는 이미 있었고 **T6·T16을 추가**.
- **T6**: 결제를 시작해도 마감이 **줄지 않는다** (`GREATEST(기존 마감, 후보 마감)`). 줄면 결제 중인 좌석이 일찍 풀린다.
- **T16**: 앞 대기자가 매수 한도에 걸리면 **SKIPPED**로 두고 다음 대기자에게 같은 좌석을 제안.
- 대표 예: T1 같은 좌석 동시 100건 → 1건만 성공, T10 취소와 만료가 동시에 와도 한쪽만 처리되고 카운터는 한 번 감소, T21 같은 Kafka 메시지 2회 소비해도 업무 처리 1회(Inbox).
- 기록상 강동균 님이 11-25 PC에서 `WaitlistOffer 8/8`, `SeatHold 14/14` 통과를 기록했다 (커밋 메시지).
- **정직하게**: 내 환경에는 Oracle이 없어 T6·T16은 직접 실행해 보지 못하고 작성만 했다.

### 7.5 팀 작업 방식 (면접에서 협업 질문)
- **기능마다 짧은 기능 문서, 문제마다 트러블슈팅 문서** (템플릿 있음), 개발일지, 개인 기여 문서. 다른 팀원이 1~2분에 이해할 수 있게.
- **타 파트 의존은 "팀 확인 요청" 문서**로 번호를 붙여 묻고 결정을 남긴다 (예: 19번 "결제 기한이 지나 풀린 좌석을 대기자가 먼저 갖도록" → 강동균 님이 A안 확정 → 유예 10초 정책값 `reservation.hold_release_grace_sec`).
- 규칙: 새 브랜치를 만들지 않고 이름 브랜치에서 작업, 스키마는 ERD HTML이 단일 원본이고 **이미 배포된 패치 블록은 고치지 않는다**.

## 8. 딥러닝 봇 탐지 — 가장 조심해서 말할 것

### 8.1 한 일 🟢 (이 부분은 직접 구현·학습·평가)
- **입력**: 한 대상(회원·기기)의 이벤트 순서 (종류 8가지, 앞 이벤트와의 간격, 응답 상태 2xx/409/기타) + 기기 공유 신호(연결 계정 수, 60초 안 동시 선점 수) + **간격이 거의 같은 다른 세션 수**(여러 세션 묶기).
- **모델**: 1D-CNN → 양방향 GRU → 어텐션·최대 풀링 → 세션 요약 통계 12개(이벤트 종류별 사람 기준 속도로 정규화한 간격의 평균·분산·자기상관 등) → 점수. PyTorch.
- **출력**: 단계형 tier 0·1·2 (강한 단계 사람 오탐 1.5%, 약한 단계 5%로 보정). 서버 점수에는 아직 연결 안 함 (오프라인 도구).
- **평가 방식**: 학습에 안 쓴 시드로 다시 만든 데이터, 보정 전용 사람(문턱만 고름), 모델 시드 3~5개 반복, "처음 보는 공격 유형"을 빼고 학습하는 leave-one-family-out.
- 테스트 23개, 학습 모델 6개와 문턱 파일을 `tools/dl-defense/models/`에 저장.

### 8.2 결과를 말하는 법 — 정직이 핵심
- 가상 데이터에서는 **AUC 1.0, 탐지율 100%** 까지 나왔지만, 이건 **실력이 아니라 시뮬레이터의 난이도**다 (봇이 사람과 너무 잘 갈림).
- 공격 생성기 v3(17변형)에서는 오탐 2% 이하 조건에서 탐지율이 **약 88.5%에서 멈췄다**. 원인을 **상한 분석**으로 확인했다: 생성기의 기준값까지 아는 oracle 신경망도 오탐 2%에서 89% 안팎. adaptive·mimic_hard 두 유형은 사람 분포에서 직접 뽑아서 **세션 하나에는 구별할 정보가 거의 없다**.
- **강동균 님의 같은 기준 비교 (11-19)**: 내 모델은 **실제 리허설·대회 로그에서 일부 봇(botc)을 못 잡았고**, 사람을 봇으로 보는 오탐이 컸다. 팀이 쓰는 모델은 `tools/ml`이다. 결론: **"어느 모델이든 학습한 생성기와 같은 세계에서만 맞히고, 다른 세계로 가면 사람을 대부분 봇으로 본다."**
- 실제 로그에서 오탐이 컸던 구체적 이유 하나: **화면의 자동 검색(`meta.auto`)이 12~81ms 간격으로 찍히는데 내 변환 코드가 이를 "봇 속도"로 읽었다.** 이 버그는 **아직 안 고쳤다.**

### 8.3 이 경험에서 말할 수 있는 배운 점
1. **가상 데이터 점수는 모델 성능이 아니라 시뮬레이터의 난이도**다.
2. 데이터가 다르면(화면 클릭 단위 vs 서버 API 로그) 같은 구조의 모델도 결과가 뒤집힌다 → 학습 데이터를 **실제 로그와 같은 모양**으로 만들어야 한다.
3. **정보의 상한**을 먼저 재면 "더 학습할지, 방식을 바꿀지" 판단이 빨라진다 (상한이 89%인데 95%를 쫓는 일을 멈출 수 있었다).
4. 한 세션만 보는 모델은 같은 템플릿을 여러 계정이 나눠 쓰는 매크로를 못 본다 → 여러 세션 묶기(간격 중복 신호)로 해결, 단 독립 세션인 봇에는 효과 없음.
5. 목표를 맞추려고 **시험 데이터를 보고 문턱을 조정하지 않는다** (보정 전용 사람을 따로 둔다). 처음에 문턱을 검증 사람 수백 명으로 골랐더니 모델 시드마다 오탐이 2.17%까지 흔들려서 보정 사람 3,200명으로 바꿨다.

## 10. 예상 질문과 답변 방향

> 아래는 **답의 뼈대**입니다. 숫자·이름은 위 장에서 확인하고, 말투는 자기 것으로.

### 대기열·Redis
1. **Redis를 왜 썼나? DB로는 안 되나?** — 순번 정렬과 TTL이 핵심인데 ZSET이 정렬된 집합이라 `ZADD`·`ZRANK`·`ZPOPMIN`이 로그 시간이다. 대기열은 짧게 쓰고 버리는 데이터라 영속성이 필요 없고, 초당 수천 건의 쓰기를 DB에 주면 좌석·결제 쪽과 자원을 다툰다.
2. **Lua 스크립트가 왜 필요한가? Redis 트랜잭션은?** — "이미 줄 섰나 → 같은 CI 있나 → 번호표 → ZADD"가 사이에 끼어들면 안 된다. `MULTI/WATCH`는 충돌 시 재시도 로직이 필요하고, Lua는 한 번에 끝나고 왕복도 1번.
3. **Lua의 단점은?** — 스크립트가 실행되는 동안 Redis 전체가 쉰다(길면 안 됨), 바뀌면 동작 전체가 바뀌어 통합 테스트 필수, 클러스터에서는 키를 같은 슬롯에 둬야 한다.
4. **앱 서버가 여러 대면?** — 순번 시각을 Redis `TIME`으로 찍어 서버 시계 차이를 없앴고, 입장 속도는 Redis에 "이번 초 입장 수"를 같이 세어 앱 대수와 무관하게 정책값이 되게 했다.
5. **Redis가 죽으면?** — 즉시 실패(fail-fast)하고 503. 스레드를 안 묶는다. 입장 토큰은 닫는 쪽으로(통과 안 시킴). 단일 노드라 SPOF이고, 정합성의 최종 판정은 DB(`purchase_counter` 조건부 UPDATE)가 한다 (팀 결정).
6. **같은 사람이 다계정으로 여러 줄을 서면?** — 같은 CI는 한 줄만 (`queue:ci` + 진입 스크립트). 단 CI가 다른 여러 계정이 사람 속도로 움직이면 사람 여러 명과 같아서 이 방식으로는 못 막는다 (본인인증의 몫).
7. **번호표 순서가 어떻게 보장되나?** — 번호표 발급과 시각 읽기가 같은 Lua 안, 멤버를 12자리 0채움으로 해서 같은 score면 번호표 순.

### 설계·공정성
8. **위험 점수가 높으면 왜 막지 않고 뒤로 보내나?** — 점수는 오탐 가능. 차단은 되돌리기 어렵고 정상 사용자가 직접 피해. 순번 조정은 약한 대응이고, 지연(sleep)은 서버 자원을 붙잡는다.
9. **줄이 비어 있으면 패널티가 의미 없지 않나?** — 맞다. "붐빌 때 뒤로 밀린다"가 정확하다. 혼자여도 기다리게 하는 안(A)은 오탐 사용자 손해가 커서 팀 결정이 필요하다고 보고 채택하지 않았다.
10. **봇이 계정을 여러 개 쓰면?** — 속도 제한은 계정별이라 못 막는다. 매수 제한(CI 기준), 본인인증, 위험 점수의 몫이고 딥러닝의 기기 공유 신호가 보조.

### 보안
11. **HMAC을 왜 쓰나? 해시와 암호화 차이는?** — 해시는 단방향(비교용), 암호화는 복호화가 필요할 때(전화번호 원문이 필요한 알림 등은 AES-256-GCM, 이건 강다인 님 파트). HMAC은 키가 있는 해시라 전화번호처럼 경우의 수가 작은 값을 대입으로 못 푼다.
12. **개인정보를 로그에 안 남기려고 한 것은?** — 행동 로그 `meta`는 숫자·true/false만, HMAC 입력 오류 메시지에 원문 미포함, 챗봇은 도구 결과에 시간표·운임·잔여석만, 비밀 값은 환경변수.
13. **챗봇 프롬프트 인젝션은 어떻게?** — 프롬프트만 믿지 않고 서버가 질문·답을 검사 (세 겹). 6장 ⑥.

### 테스트·성능
14. **부하 테스트를 어떻게 설계했나?** — 시나리오 4종: 처리량(`entry-burst`), 순번 조정(`penalty-order`), 토큰 차단(`token-guard`), 진입 한계. 사전 점검(preflight)으로 앱·Redis 문제를 "실패율 100% 표"가 아니라 원인과 함께 알려 주게 함.
15. **병목을 어떻게 찾았나?** — 가설을 세우고 하나씩 지웠다 (VU 부족 → 아님, 한 요청의 일 → Redis 왕복 9번). 도구로 확인하지 못한 부분은 **코드 근거 + 개선 결과의 일치**로 판단했고 그렇게 문서에 적었다.
16. **동시성 테스트에서 가장 중요한 것은?** — "동시에 100번"이 아니라 **기대 결과가 무엇인가** (1건 성공, 나머지는 DB 쓰기 0건, 카운터 한 번 감소). T6·T16 같은 경계 조건을 명세(`concurrency.md §16`)에 맞춰 옮겼다.

### 딥러닝·데이터
17. **왜 딥러닝으로 했나? 규칙으로 충분하지 않나?** — 규칙(`risk/`)은 이미 있고 대체하지 않는다. 규칙은 임계값 하나를 비켜가는 봇에 약해서, 순서 정보를 보는 모델을 "옆에서 비교·보강"으로 시험했다.
18. **결과가 어땠나?** — 8.2 그대로: 가상 데이터는 높았지만 실제 로그에서 일부 봇을 못 잡고 오탐이 컸다. 이유 분석과 배운 점까지 말한다.
19. **오탐/탐지율을 어떻게 평가했나?** — 학습·보정·시험 시드를 분리, 문턱은 보정 전용 사람으로만, 모델 시드 여러 개, 처음 보는 유형 평가. 시험 데이터를 보고 문턱을 맞추지 않았다.
20. **더 잘할 방법은?** — 학습 데이터를 서버 API 로그 모양으로 (화면 클릭 단위가 아니라), 실제 사람 로그, 단계별 속도 특징. `meta.auto` 제외 같은 데이터 변환 정합성 먼저.

### 협업·태도
21. **가장 어려웠던 점?** — 6장 ①~② 중 하나를 STAR로. (추천: ① "테스트가 틀린 건지 코드가 틀린 건지" + 설계 변경은 팀 결정으로 넘긴 것)
22. **팀 의견이 달랐을 때/혼자 정하기 어려운 변경은?** — 위험 사용자 패널티를 "혼자여도 대기"로 바꾸면 오탐 사용자가 손해를 보는 **설계 변경이라 팀 결정이 필요**하다고 보고 코드를 바꾸지 않고 시나리오를 설계 의도에 맞췄다. 타 파트에 걸치는 결정은 "팀 확인 요청" 문서로 번호를 붙여 묻고, 절차가 바뀌면 `concurrency.md`를 먼저 고친 뒤 구현한다는 규칙을 지켰다.
23. **다시 한다면?** — 입장 처리 개선 전후 수치를 같은 조건으로 재측정, 대기열 부하 테스트를 서로 다른 머신에서, 딥러닝은 처음부터 서버 로그 모양으로 학습.
24. **AI 도구를 썼나?** — (11장 참고) 솔직하게: 썼다. 내가 정한 것(요구 해석, 설계 선택, 무엇을 측정할지, 결과 판단)과 AI가 한 것(코드 초안, 반복 작업)을 구분해서, **내가 설명할 수 있는 범위**를 말한다.

## 11. AI 도구 사용 질문과 정직한 준비

이 저장소의 `SeongWon` 브랜치에는 AI 코딩 도구(Claude Code)가 작성한 커밋이 많습니다. 면접에서 "직접 했나요?"를 물으면:

- **하지 말 것**: 설명 못 하는 코드를 "내가 짠 것"으로 말하기. 숫자를 기억에 의존해 부풀리기.
- **할 것**: ① 어떤 문제를 정의하고 어떤 선택을 했는지(예: 패널티는 지연이 아닌 순번 조정) ② 무엇을 측정해서 어떻게 판단했는지 ③ AI가 낸 결과를 어떻게 검증했는지(테스트, 재현, 상한 분석) ④ 실패한 것(딥러닝이 실제 로그에서 실패)을 숨기지 않기.
- 🟡로 표시한 영역(속도 제한, 비회원 예매, 챗봇, 결제 단계 차단)은 **면접 전에 코드를 직접 읽고 "요청이 들어와서 응답이 나갈 때까지"를 손으로 따라가 보세요.** 못 따라가면 그 부분은 "팀 코드를 이해해서 설명할 수 있는 수준"이라고 말하는 편이 안전합니다.

|---|---|
