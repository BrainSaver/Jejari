# 대기열·번호표·입장 토큰 (QUE-01~05)

> 담당 김성원 · 코드 `queue/` · 설계 기능설계서 4.3 · 키 목록 DB설계서 6.2

## 한눈에

회원이 줄을 서면 **Redis 정렬 집합(ZSET)** 에 들어가고, 1초마다 맨 앞 N명이 **입장 토큰**을 받습니다. 좌석 API는 이 토큰이 없으면 컨트롤러에 닿기 전에 403으로 막습니다.

```
POST /runs/{id}/queue ──▶ queue:{runId} (score = 진입시각ms + 위험점수×1000ms)
                              │ 1초마다 맨 앞 queue.admit_per_sec명
                              ▼
                     queue:pass:{runId}:{memberId}  (토큰, 300초)
                              │
GET /runs/{id}/seats ◀── X-Queue-Token 검증 (QueueTokenFilter)
```

## 핵심 원리 4가지

1. **위험 사용자는 요청을 늦추지 않고 순번만 뒤로 보냅니다.** score에 `점수 × risk.penalty_ms_per_point`를 더할 뿐이라 서버 자원은 똑같이 쓰고, 정렬 결과만 뒤로 갑니다 (80점이면 80초 뒤).
2. **판단은 Lua 한 번으로 끝냅니다.** "이미 줄 섰나 → 같은 CI의 다른 계정이 있나 → 번호 발급 → ZADD"를 스크립트 하나로 하므로, 새로고침 연타나 다계정 동시 진입에도 줄에는 한 번만 섭니다.
3. **진입·입장 시각은 앱이 아니라 Redis `TIME`으로 스크립트 안에서 읽습니다.** 앱 서버가 여러 대여도, 완전 동시에 와도 번호표(seq) 순서와 시각 순서가 같습니다. 정렬은 score(시각+패널티)이고, 같으면 12자리 seq가 먼저 비교되므로 회원 ID 크기는 순서에 영향이 없습니다. (Redis 5.0 이상)
4. **토큰은 (운행, 회원) 쌍마다 하나**이고 값은 256비트 무작위입니다. 남의 토큰·다른 운행의 토큰은 조회 단계에서 걸러지고, 이탈하거나 시간이 지나면 키가 지워져 재사용이 안 됩니다.

## 규칙 요약

| 상황 | 동작 |
|---|---|
| 같은 운행에 다시 진입 | 새 번호표 없이 기존 순번 그대로 (새로고침해도 안 밀림) |
| 다른 운행에 대기·입장 중 | `QUEUE_DUPLICATED` (회원당 1개) |
| 같은 CI의 다른 계정이 대기·입장 중 | `QUEUE_DUPLICATED` (`queue_log.left_reason = REJECTED_DUPLICATE`) |
| RESTRICTED 회원 | 최대 패널티 (100점 취급) |
| BANNED 회원 | `AUTH_BANNED` |
| 입장 뒤 토큰 만료 | 대기 기록도 같이 사라져 다시 줄 설 수 있음 |

패널티 점수는 회원의 CI·결제 수단·기기 해시로 `risk:{종류}:{해시}`를 읽어 **최댓값**을 씁니다 (캐시에 없으면 0점).

## 실행·테스트

```bash
# Redis가 localhost:6379에 있어야 합니다 (테스트는 15번 DB만 씀)
cd queue && ./gradlew test
# 개발용 실행: 가짜 회원·운행 켜기
./gradlew bootRun --args='--jejari.dev-mode=true --jejari.queue.dev-on-sale-runs=1001'
```

## 확인한 것 (테스트 46개, 실제 Redis)

- 500명 동시 진입: 번호표 중복 0, 순번 = 번호표 순서
- 같은 회원 50번 연타: 줄에 1번, 같은 CI 20계정 동시: 1계정만 성공
- 입장 처리와 진입이 동시에: 입장 200명 중복 0
- 토큰 없음·가짜·남의 것·다른 운행·이탈 후·만료 후: 좌석 API 전부 403

## 진입 성능 개선 (perf)

진입 한 건이 Redis를 약 9번 왕복하던 것을 2번으로 줄였습니다.

| 바꾼 것 | 효과 |
|---|---|
| 정책값(`app_policy`)을 앱에서 1초 캐시 | 진입마다 서너 번 읽던 HGET 제거. 정책 변경은 최대 1초 뒤 반영 |
| 진입 스크립트가 순번·입장 속도를 함께 돌려줌 | 진입 직후 순번·토큰·입장 속도를 다시 조회하던 3번 제거 |
| 번호표 조회를 스크립트 한 번(`status.lua`)으로 | 4번 → 1번. 조회 중 입장 처리가 끼어들어도 어긋나지 않음 (원자적) |

같은 PC(4코어, k6·앱·Redis 동시 실행)에서 `entry-burst.js`로 단계별 측정:

| 목표(건/초) | 개선 전 실제 · p95 | 개선 후 실제 · p95 |
|---|---|---|
| 3000 | 2814~2858 · 194~237ms | 2977~2999 · 9~53ms |
| 4000 | 2800~2958 · 568~625ms | 3984~3999 · 32~62ms |
| 6000 | 2889~3048 · 585~612ms (정체) | 4651~5016 · 330~393ms (정체) |

처리량이 정체하는 지점이 약 2900건/초에서 약 4700~5000건/초로 올랐습니다. 이 PC의 값이고, 운영에서는 회원 조회(DB)가 진입마다 추가되므로 더 낮아질 수 있습니다.

## Redis 장애 시 동작

| 상황 | 동작 |
|---|---|
| Redis 끊김 | 명령을 쌓아 두지 않고 즉시 실패 → `503 SERVICE_UNAVAILABLE` (진입 응답 0.006초, 개선 전 60초). 토큰 필터도 통과시키지 않고 503 |
| Redis 복구 | 앱 재시작 없이 자동 재연결 |
| 응답 지연 | 2초 넘으면 실패 (`timeout`, `connect-timeout`) |

## 개발 모드 전용 관리 API

부하 테스트 프로그램(`loadtest/`)이 Redis에 직접 접속하지 않고 시나리오를 준비하도록, `jejari.dev-mode=true`일 때만 열리는 API가 있습니다 (인증 없음, 운영에는 존재하지 않음).

| API | 하는 일 |
|---|---|
| `POST /api/v1/dev/reset` | 대기열·위험 점수·정책 캐시 키를 지움 |
| `PUT /api/v1/dev/risk/dev-members?from=&count=&score=` | 개발용 회원 N명에게 위험 점수 설정 |
| `PUT /api/v1/dev/policy/{key}` | 정책 값 설정 (앱은 최대 1초 뒤 반영) |
