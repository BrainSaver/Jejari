# 열차 조회 기준 데이터 캐시 (역 목록·운임)

작성자: 김성원 · 코드 위치: `src/main/java/com/jejari/train/TrainQueryService.java`

> 부하 시험으로 측정한 결과를 바탕으로 한 개선입니다. 수치는 이 PC 한 대(앱·DB·k6 동거) 기준이라 방향만 읽어 주세요.

## 한 줄 요약

거의 안 바뀌는 **역 목록(`/stations`)과 화면에 보이는 운임**을 30초 동안 메모리에 들고 있어서, 요청마다 DB를 치지 않게 했다.

## 어떻게 동작하나

```
GET /stations → 캐시가 30초 안이면 그대로 응답 → 아니면 DB 조회 후 다시 30초
운임(faresByGrade) → 열차·종류·구간·날짜를 키로 같은 방식
```

- `stations`: 읽기 전용 목록 한 덩어리를 `volatile`로 보관
- 운임: `ConcurrentHashMap`, 키가 5,000개를 넘으면 비운다 (끝없이 늘지 않게)
- 시간 비교는 `System.nanoTime()`

## 왜 이렇게 했나

- 500명 부하 시험에서 DB 연결을 기다리는 요청이 190개까지 섰다. 연결을 한 번 쥐는 시간은 평균 27ms로 짧은데 **횟수가 많았다** (요청당 2.36회).
- 풀을 20 → 40으로 키워도 처리량은 그대로(221 → 206 req/s)이고 연결 점유 시간만 2배가 됐다. DB 자체가 병목이라 풀을 키우는 건 답이 아니다 (`application.yml` 풀 설정 주석과 같은 결론).
- 그래서 횟수를 줄이는 쪽을 택했다. 결과는 **요청당 2.36 → 1.86회 (-21%)**. 처리량 수치는 이 PC가 CPU 100%라 실행마다 흔들려 비교하지 않았다.
- 다른 후보: Redis 캐시(과함), Spring Cache + Caffeine(의존성 추가). 단순한 메모리 캐시로 충분했다.

## 주의할 점

- 관리자가 역을 고치면 사용자 화면에는 **최대 30초 뒤** 반영된다.
- 좌석 선점이 금액을 확정할 때는 `FareReader`를 직접 읽는다. 이 캐시를 거치지 않으므로 결제 금액에는 영향이 없다.
- 앱이 여러 대면 각자 캐시를 갖는다 (30초 안에 서로 달라질 수 있음).
- 같이 바꾼 것: Tomcat 동시 연결 한도 `max-connections 20000`, `accept-count 2000` (`application.yml`). 문제와 결과는 `troubleshooting/20261123-tomcat-연결-한도-거절.md`.
