2. 순번이 정해지는 규칙

상황순서는 이렇게 정해집니다
일반 사용자점수 = 진입 시각(Redis 시계). 먼저 온 사람이 앞.
위험 점수 80점점수 = 진입 시각 + 80초. 요청은 늦추지 않고 순번만 80초 뒤로.
같은 밀리초에 진입번호표(seq 12자리)가 작은 쪽이 앞. 회원 ID 크기는 영향 없음.
점수가 여러 개 (CI·결제·기기)최댓값 하나만 사용. RESTRICTED 회원은 100점.
줄이 비어 있을 때위험 사용자도 앞에 아무도 없으므로 바로 입장 (패널티는 "붐빌 때 뒤로 밀림").

3. 직접 해 보기: 봇이 먼저 몰려와도 뒤로 밀릴까?

봇(위험 점수 높음)이 정상 사용자보다 먼저 줄을 서는 상황입니다. 입장은 오픈 후 지정한 초부터 1초마다 맨 앞 N명씩 진행됩니다. 진입 시각은 봇 0~2초, 정상 1~3초에 고르게 분포한다고 가정합니다.

4. 입장 토큰

상황결과
입장 처리됨(운행, 회원) 쌍마다 256비트 무작위 토큰 1개, 300초 유효
토큰 없음·가짜·남의 것·다른 운행·이탈 후·만료 후로 좌석 API 호출전부 403 (QueueSeatTokenInterceptor)
입장 뒤 토큰이 만료대기 기록도 같이 사라져 다시 줄을 설 수 있음
같은 CI의 다른 계정이 이미 대기·입장 중QUEUE_DUPLICATED (한 사람이 여러 계정으로 줄 서기 방지)

5. 위험 점수를 읽을 때의 안전장치

"모르면 막는 쪽으로" 동작합니다. 점수 캐시가 비거나 오염돼도 위험 사용자가 패널티 없이 통과하지 못하게 하려는 것입니다.

상황동작
risk:meta:synced_at 있음 + 점수 키 없음0점 (정상 사용자)
risk:meta:synced_at 없음 (Redis 재시작 등)캐시를 믿지 않고 Oracle risk_score를 직접 조회
위 조회 실패100점
값이 0~100 숫자 문자열이 아님 (abc, NaN, 101, JSON…)100점 + 경고 로그
Redis 재시작 직후에는 다음 재동기화 전까지(최대 10분) 모든 진입이 Oracle을 조회합니다. 부하 제한 방식은 팀 협의 중입니다 (팀-확인-요청.md 17번).

6. Redis 장애

Redis 연결이 끊기면 요청이 60초씩 매달리지 않고 즉시 503 SERVICE_UNAVAILABLE로 응답하고, 복구되면 자동으로 다시 동작합니다.
