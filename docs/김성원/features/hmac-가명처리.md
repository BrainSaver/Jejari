# 식별정보 가명처리 (HMAC)

> 담당 김성원 · 코드 `hmac/` · 근거 DB설계서 2장(식별 해시), 기획서 6장(묶음 기준)

## 한눈에

전화번호·CI·카드번호·기기 지문·IP 같은 식별정보는 원문을 저장하지 않고 **HMAC-SHA256 값(소문자 16진수 64자)** 으로만 다룹니다. 같은 값은 항상 같은 해시라서, 원문 없이도 "같은 CI의 여러 계정", "같은 카드를 쓰는 계정"을 묶을 수 있습니다.

```java
Pseudonymizer p = Pseudonymizer.fromEnv();      // 환경변수 JEJARI_HMAC_KEY
p.phone("+82 10-1234-5678");                    // 010-1234-5678과 같은 해시
p.mockCiHash("김성원", "010-1234-5678");         // 모의 본인인증의 CI 해시 (AUTH-02)
p.paymentMethod("4111-1111-1111-1111");
```

## 왜 이렇게 했나

1. **SHA-256이 아니라 HMAC**: 전화번호는 경우의 수가 작아서 키 없는 해시는 전부 계산해 보면 원문이 나옵니다. 비밀 키가 있어야 해시를 만들 수 있게 해서 DB가 유출돼도 원문을 못 맞추게 합니다.
2. **종류 이름을 함께 해시** (`CI`, `PHONE`, `EMAIL`, `PAYMENT`, `DEVICE`, `IP`): 같은 문자열이라도 종류가 다르면 해시가 달라, 서로 다른 테이블의 해시를 맞대어 사람을 잇지 못합니다.
3. **표기 차이는 같은 값으로**: `010-1234-5678`, `+82 10 1234 5678`은 같은 해시. 이메일은 대소문자·공백 무시, 카드번호는 하이픈·공백 무시. 안 맞추면 같은 사람이 다른 사람으로 갈립니다.
4. **이상한 입력은 거부**: 전화번호에 글자가 섞이면 조용히 버리지 않고 오류. 글자를 버리면 서로 다른 번호가 같은 해시가 됩니다. 오류 메시지에는 입력 원문을 넣지 않습니다.

## 지켜야 할 것

| 항목 | 규칙 |
|---|---|
| 키 | 환경변수 `JEJARI_HMAC_KEY`(Base64, 32바이트 이상). 저장소·로그에 두지 않음. `openssl rand -base64 32`로 만듦 |
| 키 변경 | **프로젝트 기간 동안 바꾸지 않음.** 바꾸면 지금까지의 해시와 이어지지 않아 위험 점수·매수 제한 묶음이 끊김 |
| 해시 형식 | `VARCHAR2(64)` / MongoDB String. `Purpose` 이름·순서와 정규화 규칙을 바꾸면 안 됨 (고정값 테스트가 막아 줌) |
| 새 종류 | `Purpose` 끝에 추가만 |

## 쓰는 곳

| 해시 | 컬럼 | 쓰는 파트 |
|---|---|---|
| `ci` | member.ci_hash, identity_verification.ci_hash, behavior_log.ci_hash, `queue:ci:*`, `risk:CI:*` | D(회원), A(대기열) |
| `phone` | member.phone_hash | D |
| `email` | login_attempt.email_hash | E |

## 확인한 것 (테스트 19개)

- RFC 4231 표준 시험값과 HMAC 결과가 같음
- Python으로 따로 계산한 고정값과 일치 (저장된 해시와의 호환이 깨지면 테스트가 실패)
- 표기만 다른 전화번호·이메일·카드번호는 같은 해시, 다른 값은 다른 해시, 종류가 다르면 다른 해시
- 짧은 키·잘못된 Base64 거부, 오류 메시지·`toString()`에 키와 원문이 나오지 않음
- 16개 스레드 2000번 동시 호출에서 결과 동일
