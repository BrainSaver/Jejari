## 어떻게 했나

- **연장**: `extend.lua`가 토큰 확인 → 연장 표시(`queue:passext`) → `PEXPIRE`를 한 번에 처리해 동시에 눌러도 1회만 적용. 남은 시간에 `queue.pass_extend_sec`(기본 300초)를 더하고, 입장자 목록과 회원·CI 대기 기록 만료도 함께 연장. 이미 썼으면 `QUEUE_EXTEND_USED`(409). 좌석 선택 화면에 "5분 더 쓰기 (1회만 가능)" 버튼
- **입장 처리**: 줄 선 사람·입장 중인 사람이 있는 운행만 `queue:runs`(SET)에 두고 스케줄러는 그 목록만 처리 (판매 중 운행이 1,000건이어도 사용자가 없으면 `SMEMBERS` 1번). `admit.lua` 한 번에 만료 정리·처리량 기록·입장·활성 운행 정리까지 (운행당 Redis 왕복 1번). 운행별 이번 1초 입장 수를 `queue:adm`에서 세어 앱 여러 대의 합이 상한을 넘지 않게 함. 처리량 기록은 값이 바뀔 때만, 정책값은 tick당 한 번만 읽음. `reconcile.lua`가 앱 시작과 5분마다 목록에서 빠진 운행을 다시 넣음 (`concurrency.md` §14.1에 키 추가, `QueueServiceTest`에 테스트 추가)
- **행동 로그**: 컨트롤러에서 `BehaviorLog.mark(BehaviorType.QUEUE_ENTER, runId, meta)` 한 줄. 요청에 표시만 하고 요청이 끝날 때 인터셉터가 응답 코드를 붙여 보냄. `meta`는 숫자·true/false만 (개인정보 없음)
- **딥러닝 탐지**: 행동 로그의 한 대상(회원·기기)의 이벤트 순서(종류·간격·응답 상태)와 기기 공유 신호를 보고 0~100으로 매김. 규칙 엔진(`risk/`)을 대신하지 않고 옆에서 비교·보강. 서버와는 연결하지 않음

## 왜 이렇게 했나

- **연장을 Lua 한 번에**: 두 번 누르거나 여러 탭에서 동시에 눌러도 1회만 되어야 한다. 여러 명령으로 나누면 사이에 끼어든다
- **입장 처리를 활성 운행만**: 판매 중 운행이 많아도 비용이 사용자가 있는 운행 수에만 비례하게 하려는 것. 앱 여러 대가 같은 운행을 동시에 처리해도 입장 속도가 대수만큼 늘지 않게, 상한을 Redis에서 센다 (이전에 "입장 스케줄러는 앱 1대 기준"이라 적었던 한계를 풀었다)
- **거절된 요청도 행동 로그에**: 봇은 실패를 빠르게 반복한다. 성공만 남기면 가장 중요한 신호가 사라진다 (다인 님의 설계 원칙)
- **딥러닝은 규칙 엔진 "옆에서"**: 가상 데이터로만 학습했고, 시뮬레이터가 만든 봇이 사람과 너무 잘 갈려서 나온 **가상 데이터 점수(탐지율 100%, AUC 1.0)는 실력이 아니다.** 실제 성능은 대회 로그 같은 실제 사람 데이터로만 알 수 있다 (프로토타입 README의 경고)
- 감수한 단점: 서버와 연결되지 않은 오프라인 도구라 당장 점수에 반영되지는 않음

## 막힌 점과 해결

- **좌석 배치도가 실제 API가 됨**: 정상 토큰의 배치도 호출이 Oracle을 읽어, 운행이 시드에 없으면 404가 대기열 문제처럼 보임 → 시작 전에 한 번 불러 원인(404 시드 없음, 500 Oracle, 503 연결)을 알려 줌. 차단(403) 판정은 인터셉터가 컨트롤러 앞에서 막아 영향 없음. 이전 `flow.js` 수치는 대용품 기준이라 같은 조건이 아님
- **탐지율의 한계**: 강동균 님의 비교 결론은 "어느 모델이든 학습한 생성기와 같은 세계에서만 맞히고, 다른 세계로 가면 사람을 봇으로 본다"이다. 비교 표에서 내 모델은 리허설 봇 9/12, 사람 오탐 0/12였다
- 11-19 대회는 사람 참가자가 결제 단계에서 막혀(집계자 PC의 Redis에 이전 리허설 기록이 남아 있었다고 문서에 적혀 있음) **사람 데이터 없이 봇 2개만** 돌았다. 그래서 사람 기준 판단은 아직 못 한다
