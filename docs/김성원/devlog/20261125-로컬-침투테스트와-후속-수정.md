# 2026-11-25 · 로컬 침투 테스트 보안 점검과 후속 수정

> 파일 이름: `docs/김성원/devlog/20261125-로컬-침투테스트와-후속-수정.md`
> 이 일지는 11-27에 **커밋 메시지와 보고서·트러블슈팅 문서를 보고** 정리했다.

## 한 일

- **로컬 침투 테스트** (`1db6f6b`): 로컬에서 운영 모드(`jejari.dev-mode=false`)로 서버를 띄우고 실제 HTTP 요청으로 공격. 요청받은 14개 항목 + 동시성·토큰·관리자 권한·대기자 흐름 약 70개 시나리오 → [보고서](../security/20261125-로컬-침투테스트-보안점검.md)
  - 예: 결제 본문에 `amount:1`을 넣어도 실제 청구 54,400원(서버가 계산), 남의 예약 ID로 조회·취소하면 404, 같은 좌석 동시 선점은 정확히 1명만 성공, SQL 주입은 전부 400
  - 끝나고 테스트 데이터를 FK 순서로 지우고 회원 수·고아 데이터·Redis 잔여를 확인해 점검 전 상태(회원 131명, 관리자 1명)로 되돌림
- **추가 점검에서 결함 4건 발견·수정** (`e732e1d`): 처음 보고서의 "취약점 0건"을 정정함 (`441d317`)
  - [High] 정지된 명의로 다시 가입 가능
  - [Medium] 정지 직후 남은 토큰(최대 15분)으로 결제·정보 변경·탈퇴 가능
  - [Medium] 비ASCII User-Agent로 로그인하면 500
  - [Low] 좌석 선점 `seats:[null]`이면 500
  - 덤으로 단체 관리자 API의 클래스 권한 표기를 다른 관리자 API와 통일
- 회귀 테스트 `SecurityAuditInfraTest`·`UserAgentsTest`, [기능 문서](../features/정지-회원-차단과-요청-입력-정리.md) (`e384587`)

## 어떻게 했나

- **`MemberStatusGuard`**: JWT가 아니라 DB의 `member.status`로 판단한다
  - `forbidBannedCi(ciHash)`: 가입할 때. 그 CI로 정지된 계정이 하나라도 있으면(탈퇴 계정 포함) 거절. 저장 트랜잭션 안에서 한 번 더 확인
  - `forbidBanned(memberId)`: 결제·정보 변경·원문 보기·탈퇴 앞에서. 결제에서 막히면 선점 좌석을 바로 돌려준다
- **`UserAgents`**: 제어 문자를 빼고 UTF-8 300바이트로 자른다 (글자 중간은 안 끊음). 회원·비회원·관리자 로그인이 모두 이걸 쓴다. Spring Security 방화벽이 헤더를 거절하면 500이 아니라 400
- 좌석 목록에 `null`이 있으면 검증 단계에서 400

## 왜 이렇게 했나

- **DB 상태로 확인**: 관리자가 정지하면 세션은 지워지지만 액세스 토큰은 15분 동안 살아 있다. 토큰만 보면 그 사이에 결제할 수 있다. 모든 요청이 아니라 **돈이나 개인정보가 걸린 요청만** DB를 한 번 더 읽어서 비용을 줄였다
- **조회(`GET /me`)는 열어 둠**: 정지된 사용자가 자기 상태를 볼 수는 있어야 한다
- **처음 보고서를 지우지 않고 정정**: 처음 점검은 정상 회원·관리자 입장의 공격만 다뤘다. 무엇을 시험하지 않았는지 남겨야 다음 점검에서 같은 곳을 놓치지 않는다

## 배운 점

- "전부 막았다"는 **시험한 범위 안에서만** 맞는 말이다. 계정 상태가 바뀌는 순간(정지·탈퇴)과 이상한 입력(비ASCII, null)은 정상 흐름 시험에서 잘 빠진다
- 500은 대부분 보안 문제가 아니라 입력 검증 누락이지만, 서버 내부 정보가 새거나 로그를 어지럽힐 수 있어 400으로 바꾸는 게 맞다
