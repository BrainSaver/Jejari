## 어떻게 했나

- 위험 점수: `점수 키들 + risk:meta:synced_at`을 같은 `MGET` 한 번으로 읽음(왕복 추가 없음) → 표시 키가 없으면 `RiskScoreFallbackPort` → 값은 정규식(`0~100`, 소수 6자리)으로 먼저 거른 뒤 파싱. 포트 구현은 다인 님이 `OracleRiskScoreFallback`으로 채움
- 시나리오 10: `동시 가입 경합(같은 이메일 N명 → 1명만 201) → 가입 처리량 → 로그인 처리량 → 5회 오류 잠금`. 인증 API가 IP당 시도를 제한해서 요청마다 다른 IP를 `X-Forwarded-For`로 보내고, 앱은 `--jejari.auth.trusted-proxies`(환경 변수 `JEJARI_AUTH_TRUSTED_PROXIES`)로 로컬 주소만 신뢰하게 띄움
- 시작 전에 가입 → 로그인을 한 번 끝까지 해 보고, 실패하면 원인(비밀값 누락 404, IP 제한 429, Oracle 500, Redis 503)과 할 일을 알려 줌
- 검증: mock 서버에서 정상/결함(`--bug dup-email`, `--bug no-lockout`) 모두 의도대로 통과·미달, 실제 앱 + Oracle은 내 PC에서 실행

## 왜 이렇게 했나

- **모르면 막는 쪽으로**: 캐시가 비거나 오염된 틈으로 위험 사용자가 패널티 없이 통과하면 안 된다. 코드를 읽다가 값이 `NaN`이면 패널티가 조용히 0이 되는 우회로를 발견해(`parseDouble`이 `NaN`·`1e2`·`80d`를 받음) 오류가 아니라 100점으로 처리하게 했다 (`troubleshooting/20261116-위험점수-값-오염-진입-오류.md`)
- **표시 키가 오래돼도 점수는 그대로 쓰고 경고만**: 오래됨이 캐시가 비었다는 증거는 아니라서 막으면 정상 사용자까지 영향을 받는다
- **시나리오 10은 합격 기준을 정확한 값으로**: 경합은 라운드마다 `count==1`, 429(`auth_rate_limited`)는 0이어야 함(설정 문제를 실패로 보이게). 503(해시 동시 처리 한도 초과)은 실패와 따로 센다 — 과부하 시작점을 알려 주기 때문
- **신뢰 프록시 옵션은 테스트용 앱에만**: 앱이 `X-Forwarded-For`를 아무에게나 믿으면 IP 제한이 우회된다. 로컬 주소 한정으로만 켬
- 감수한 단점: 시나리오 10을 돌리면 Oracle에 `@loadtest.example.com` 계정이 남음(비우려면 볼륨 재생성). mock 결과의 성능 수치는 의미 없음

## 막힌 점과 해결

- **로컬 Oracle 첫 기동에서 겪은 것 (코드 문제 아님)**: ① Redis 6379 포트가 이전에 띄운 컨테이너에 점유됨 → 컨테이너 삭제 ② `jejari-oracle-1` 이름 충돌 ③ 스키마 적재 중 컨테이너를 지워 초기화가 끊김 → 볼륨 재생성(이 이미지는 초기화 스크립트를 첫 기동 때 한 번만 실행) ④ `findstr "문구 전체"`는 단어 하나만 맞아도 출력해서 완료 확인을 잘못 읽음 → `findstr /c:"…"` ⑤ 스키마(DDL)에 시퀀스 2개가 더해져(v15) 오래된 볼륨은 재생성 필요 ⑥ `.env`에 새 키(`JEJARI_ENC_KEYS`, `JEJARI_PEPPER_KEYS`)가 없어 인증 API가 404 → 로컬 전용 키를 만들어 추가
- **시나리오 10 첫 실제 실행(내 PC, Oracle)**: 가입 201건 모두 성공(p95 564ms), 동시 가입 경합은 라운드마다 승자 1명(중복 거절 57건)으로 합격. 하지만 **로그인이 요청마다 약 30초**(p95 33초)였고 잠금 확인은 판정 불가였다. 로그인이 시도마다 MongoDB에 기록을 남기는데, Mongo에 못 닿으면 드라이버 기본 서버 선택 대기(30초)만큼 응답이 멈춘다는 것이 코드와 숫자로 본 가장 유력한 원인이었다. 이후 다인 님이 `5aaff8a`로 타임아웃 2초 + 비동기 기록으로 고쳤고(수정 전 30초 → 0.3초라고 커밋에 적음), 원인 추정과 일치한다. **수정 후 내 PC에서 같은 시나리오로 재확인은 아직 못 했다**
- 위험 점수 값 오염: `troubleshooting/20261116-위험점수-값-오염-진입-오류.md`

## 배운 점

- 부하 테스트를 "실제 의존성(Oracle, Mongo)을 거치는 경로"로 한 번 돌리니, 단위 테스트와 mock으로는 안 보이는 문제(로그 기록이 로그인 응답을 30초 붙잡음)가 바로 드러났다. 다른 사람 모듈의 약점도 이렇게 찾을 수 있다
- 로그 확인 명령은 "문구 전체 일치"인지 "단어 일치"인지부터 확인한다. 잘못 읽으면 끝나지 않은 초기화를 끝난 것으로 오해한다
- 팀원이 같은 값을 정한 것(180000, RESTRICTED 신청 불가)은 내 문서에서도 바로 고쳐야 한다. 어긋난 문서가 가장 위험하다
- 이 환경에는 Oracle이 없어서 실제 DB 경로는 내 PC에서만 확인할 수 있다. 확인하지 못한 것은 문서에 그렇게 적는다
