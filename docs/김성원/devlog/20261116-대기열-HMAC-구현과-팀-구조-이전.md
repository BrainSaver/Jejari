- main에 올라온 팀 구조(루트 Gradle 프로젝트, JWT 인증)에 맞춰 `queue`·`hmac`을 이전하고 main에 합침
- 팀 확인 요청 메모, 기능 문서, 기여 문서, 트러블슈팅 문서 정리

## 어떻게 했나

- 대기열: `진입 → Lua 한 번(중복 확인·번호표·줄 넣기) → 1초마다 맨 앞 N명에게 토큰 → 좌석 API 앞 인터셉터가 토큰 검증`
- 순번 = 진입 시각 + 위험 점수 × 1초 (Redis ZSET의 score). 시각은 앱이 아니라 Redis `TIME`으로 찍음
- 검증은 매번 같은 순서로: 동작 확인 → 부하 측정 → 원인 가설 → 고침 → 같은 조건으로 재측정
- 팀 구조 이전: 독립 Gradle 프로젝트 → `com.jejari.queue`, `com.jejari.common.hmac`. 인증은 팀의 `AuthPrincipal`, 오류는 `BusinessException`·`ErrorCode`, 개발 모드는 별도 보안 체인으로 분리

## 왜 이렇게 했나

- **패널티는 요청을 늦추지 않고 순번만 뒤로**: 지연시키면 봇이 서버 자원을 붙잡는다. 대신 줄이 비어 있으면 위험 사용자도 바로 입장한다 ("붐빌 때 뒤로 밀린다").
- **Lua 스크립트 한 번**: 여러 명령이면 동시 요청이 사이에 끼어든다 (새로고침 연타, 다계정 동시 진입).
- **HMAC(키 있는 해시)**: 전화번호는 경우의 수가 작아 키 없는 SHA-256은 전수 대입이 가능하다. 종류 이름을 함께 해시해 테이블 간 연결도 막음.
- **다른 파트 연동은 인터페이스(port)로**: 회원·운행 구현이 없어도 앱이 뜨고 대기열만 "준비 중"이 되게 해서, 팀 전체의 기동을 막지 않음.
- **감수한 단점**: 정책 변경이 최대 1초 늦게 반영됨, 입장 스케줄러는 앱 1대 기준, 병목 위치는 도구로 확인하지 못하고 추정.

## 배운 점

- 결과가 기대와 다르면 시스템이 틀렸다고 단정하기 전에, 먼저 테스트의 전제와 환경(포트, 로케일, 캐시 지연)을 의심한다.
- 성능 수치는 **측정 환경과 조건을 같이** 적어야 믿을 수 있다. 개선 전·후 조건이 다르면(단계 길이, 최대 VU) 일부 지표는 비교하면 안 된다.
- 공통 영역에 슬라이스 테스트가 자동으로 읽는 빈을 추가하면 남의 테스트가 깨질 수 있다. 합치기 전에 전체 테스트를 돌린다.
- 이 환경에서 직접 못 해 본 것(전체 앱 기동, 데스크톱 앱 화면, PowerShell 실행의 일부)은 문서에 "확인 못 함"으로 적어야 한다.
