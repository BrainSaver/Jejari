# [security] 로컬 침투 테스트 — 전체 보안 점검

| 항목 | 내용 |
|---|---|
| 작성자 | 김성원 |
| 날짜 | 2026-11-25 |
| 상태 | 완료 — **정정**: 이 점검 뒤 추가 점검에서 결함 4건이 더 나와 수정함 (아래 "추가 발견") |
| 방법 | 로컬 스택 기동 후 실제 HTTP 요청으로 공격, 끝나고 테스트 데이터 전량 삭제·검증 |
| 환경 | `docker compose` 인프라 + `bootRun`(운영 모드, `jejari.dev-mode=false`), `localhost:8080` |

> 코드 정적 분석이 아니라 **실제로 서버를 띄우고 요청을 보내** 확인한 결과입니다. 테스트 중
> 생성한 회원·예약·결제·대기·관리자 계정은 모두 FK 순서로 삭제했고, 최종적으로 회원 수·고아
> 데이터·Redis 잔여를 검증해 점검 전 상태(회원 131명, 관리자 1명)로 복구했습니다.

> **추가 발견 (같은 날 추가 점검, 모두 수정함)** — 이 문서의 시험은 정상 회원·관리자 입장의 공격만 다뤘고,
> 정지(`BANNED`) 같은 계정 상태 전환과 비ASCII 헤더는 시험하지 않아 아래를 놓쳤습니다.
> - [High] 정지 명의 재가입, [Medium] 정지 직후 토큰으로 결제·정보 변경·탈퇴 → [트러블슈팅](../troubleshooting/20261125-정지회원-재가입과-남은-토큰으로-결제.md)
> - [Medium] 비ASCII User-Agent 로그인 500 → [트러블슈팅](../troubleshooting/20261125-비ASCII-User-Agent-로그인-500.md)
> - [Low] 좌석 선점 `seats:[null]` 500 → [트러블슈팅](../troubleshooting/20261125-좌석-선점-null-원소-500.md)
>
> 아래 1~9장은 처음 점검 당시 기록 그대로입니다.

## 1. 요약

**약 70개 공격 시나리오 전부 방어.** 실제로 뚫린 취약점은 없습니다. 몇 건의 "FAIL"은 모두
테스트 스크립트 쪽 버그(응답 필드명·대상 선택 오류)였고, DB·재작성으로 안전을 재확인했습니다.

| 영역 | 결과 |
|---|---|
| 1차: 요청한 14개 항목 + 기본 공격 | 전부 방어 |
| 2차: 동시성·토큰·멱등·매수한도·리프레시·정보노출 | 전부 방어 |
| 3차: 대기자(취소표) 흐름 / 관리자 세부 권한 | 전부 방어 |

이 시스템의 일관된 원칙 — **클라이언트를 믿지 않음**(서버측 금액 계산, 토큰 기반 소유권, 입력
화이트리스트, 실패 시 막는 쪽) — 이 모든 공격면에서 지켜졌습니다.

## 2. 요청받은 14개 항목

| # | 공격 | 결과 | 막는 지점 |
|---|---|---|---|
| 1 | 주소 뒤 `/admin` | 토큰없이 401, 회원토큰 403 | `/api/v1/admin/**` = `hasRole("ADMIN")`, `/admin`은 751B 껍데기 HTML |
| 2 | URL ID 바꾸기(IDOR) | A토큰으로 B 예약 조회/취소/견적 전부 404 | 전 엔드포인트 `me.memberId()` 기반, 남의 것=없는 것 |
| 3 | 브라우저 API키 | 프론트 번들에 키 없음 | Groq 키 서버 보관(`GROQ_API_KEY`) |
| 4 | 가격 고치기 | 결제 본문 `amount:1` 주입 → **DB 실청구 54,400원** | 금액은 서버가 `reservation.total_amount`로 계산 |
| 5 | 수량 -1개 | 빈목록·음수ID 거부, 중복좌석 400, 25매 422 | 수량=좌석ID 목록 크기(음수 불가) + 매수한도 |
| 6 | 결제 성공 위조 | callback/webhook/notify/confirm/approve 전부 404 | 결제 콜백 엔드포인트 자체가 없음(서버가 PG 동기 호출) |
| 7 | 쿠폰 100번 | 비해당 | 쿠폰 기능 없음 |
| 8 | 가입 시 관리자 | role/isAdmin/authority 주입 가입 → 관리자API 403 | 가입에 role 필드 없음, 관리자는 별도 테이블 |
| 9 | 인증번호 전수조사 | 로그인 5회 실패 → 423 AUTH_LOCKED | 본인인증은 256비트 토큰(짧은 코드 없음) + 잠금 |
| 10 | AI "지시 무시" | 프롬프트유출 4종 + 위조 history 전부 차단 | `ChatGuard` 입력·과거대화·출력 3중 검사 |
| 11 | 닉네임 스크립트(XSS) | 이름에 `<script>` → 400, 응답에 원시태그 없음 | 닉네임 없음 + 이름 화이트리스트 + React 이스케이프 |
| 12 | 비사진 파일 업로드 | 비해당 | 업로드 엔드포인트 없음 |
| 13 | GitHub `.env` | 커밋 이력 없음 | `.gitignore`, actuator는 health/info/prometheus만 |
| 14 | DB 직접쿼리(SQLi) | `' OR 1=1`, `UNION SELECT password_hash` 전부 400 | 전부 `?` 바인딩, 덤프·DB오류 없음 |

## 3. 심화 공격 (동시성·인증 체계)

이 프로젝트의 핵심인 좌석 동시성과 인증 토큰을 집중 공격.

| 공격 | 결과 |
|---|---|
| **같은 좌석 동시 선점**(2명 병렬) | 정확히 1명만 201, 나머지 409 — 더블부킹 없음 |
| 입장토큰 탈취(타인 토큰 재사용) | 403 QUEUE_TOKEN_INVALID (Redis 키가 `(runId, memberId)`별) |
| 입장토큰 위조 / 없이 호출 | 403 — "토큰 없이 좌석 API 차단율 100%" 실증 |
| 멱등키 재사용 / 교차 | 같은 예약 반환(이중생성 없음), 회원별 네임스페이스 독립 |
| **여러 예약으로 매수한도 우회** | 누적 6매에서 LIMIT_PER_RUN 차단 — `purchase_counter`가 예약 경계 넘어 누적 |
| JWT 위조 (alg=none / 타키 서명 / payload 변조) | 전부 401 AUTH_TOKEN_INVALID |
| **리프레시 토큰** | HttpOnly·SameSite=Strict·경로한정 + 회전 + **재사용 탐지(옛 토큰 401)** + 로그아웃 무효화 |
| X-Forwarded-For 스푸핑으로 레이트리밋 우회 | 매 요청 IP 바꿔도 결국 429 (trusted-proxy 아니면 XFF 무시) |
| 숫자 경계값/음수/overflow/문자열 ID | 전부 4xx, **5xx 없음** |
| 좌석 10만개 대용량 페이로드 | 403 거부, 서버 생존(health UP) |
| 보호 엔드포인트 11개 토큰 없이 | 전부 401/403, 인증 누락 0 |
| 에러 응답 정보 노출 | 스택트레이스·내부경로·SQL 노출 없음 |
| 보안 헤더 | `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` |

## 4. 대기자(취소표 대기) 흐름

| 공격 | 결과 |
|---|---|
| 대기 신청(매진 아닌 운행) | 409 WAITLIST_NOT_SOLD_OUT — 남은 좌석 있으면 신청 거부(정상) |
| **WB가 WA의 대기 항목 취소(IDOR)** | 404 WAITLIST_NOT_FOUND, WA 항목 유지 |
| 본인 대기 취소 / 재취소 | 204 성공, 재취소도 멱등 204 |
| 대기 수량 음수·과다, 좌석등급 이상값 | 전부 400 |
| 없는 대기 ID 취소 | 404, 정보 유출 없음 |

`WaitlistService.cancel`이 `WHERE waitlist_id = ? AND member_id = ?`로 소유권을 강제. 비회원은
컨트롤러에서 `forbidGuest`로 차단.

## 5. 관리자 세부 권한 경계 (VIEWER / REVIEWER / SUPERVISOR)

테스트용 3역할 관리자 계정을 만들어 엔드포인트 × 역할 매트릭스를 검증. **18/18 완벽.**

| 엔드포인트 (필요 권한) | VIEWER | REVIEWER | SUPERVISOR |
|---|---|---|---|
| `GET /admin/dashboard` (VIEWER) | 통과 | 통과 | 통과 |
| `POST /admin/cases/{id}/actions` (REVIEWER) | **403** | 통과 | 통과 |
| `POST /admin/groups/{id}/approve` (REVIEWER) | **403** | 통과 | 통과 |
| `POST /admin/cases/{id}/unmask` (SUPERVISOR) | **403** | **403** | 통과 |
| `PUT /admin/policies/{key}` (SUPERVISOR) | **403** | **403** | 통과 |
| `POST /admin/reservations/{id}/cancel` (SUPERVISOR) | **403** | **403** | 통과 |

- 계층 포함 관계(SUPERVISOR ⊃ REVIEWER ⊃ VIEWER)가 정확히 동작.
- `@PreAuthorize`가 **비즈니스 로직 이전**에 평가됨 — 권한 없으면 403 ADMIN_FORBIDDEN, 권한
  있으면 그 다음 단계의 400/404로 진행(정보 노출 없이 깔끔히 분리).

## 7. 참고 — 운영 배포 시 확인(취약점 아님, 하드닝)

1. `jejari.auth.trusted-proxies` — 리버스 프록시를 쓰면 그 IP만 정확히 지정, 아니면 비워 두기
   (현재 비어 있어 XFF 스푸핑이 무력화됨 = 안전).
2. `JWT_REFRESH_COOKIE_SECURE=true` (HTTPS 환경).
3. `/actuator/prometheus` 내부망 한정 — 코드 주석대로 포트·네트워크로 실제 격리.
4. **HSTS 헤더** 없음(로컬 HTTP라 당연) — 운영 HTTPS 뒤에서 `Strict-Transport-Security` 추가 권장.
5. 실제 본인인증(PASS) 연동 시 공급자 쪽 인증번호 재전송·시도 제한 확인(현재 모의는 256비트 토큰이라 전수조사 불가).
6. 관리자 케이스 액션에 **없는 case_id + 잘못된 body**를 보내면 500(INTERNAL_ERROR) 응답 —
   정보 노출은 없으나 400/404로 다듬으면 더 깔끔(권한 경계와는 무관).

## 8. 테스트 데이터 정리 확인

테스트로 만든 회원·예약·결제·취소·위험케이스·대기행·관리자 계정을 전부 FK 순서로 삭제.

| 검증 항목 | 값 |
|---|---|
| 회원 수 | 131 (점검 전과 동일) |
| 관리자 수 | 1 (원본 SUPERVISOR만) |
| 테스트 잔여 회원 | 0 |
| 고아 credential·좌석 | 0 |
| 잔여 대기행 | 0 |
| Redis 좌석홀드(run 9001) | 0 (TTL 만료 확인) |

> 참고: 테스트 중 레이트리밋(가입·로그인)이 정상 작동해 재테스트가 막혔고, 그때마다 테스트가
> 유발한 Redis 카운터(`rate:signup:*`, `login:fail:*`)만 선택적으로 비웠습니다. 이는 보호장치가
> 실제로 동작한다는 방증이기도 합니다.

## 9. 재현 방법(요약)

1. `docker compose up -d` 로 인프라 기동(시드 자동 적재).
2. `set -a && . <(grep -E "^JEJARI_(ENC|PEPPER|HMAC)" .env) && set +a` 후
   `LC_ALL=C.UTF-8 TZ=Asia/Seoul ./gradlew bootRun`.
3. 테스트 회원 생성 → 대기열 입장 → 좌석 선점 → 결제/취소 흐름으로 예시 데이터 생성.
4. 항목별 공격 요청(Node `fetch` 하네스)으로 응답 코드·DB 상태 검증.
5. 생성 데이터 FK 순서 삭제 후 회원 수·고아·Redis 잔여 검증.

테스트 하네스를 정식 통합 테스트(`@Tag("infra")`)로 승격하는 것도 가능(회귀 방지). 필요 시 별도 작업.
