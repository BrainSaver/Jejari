> 면접에서 "본인이 한 일"을 바로 꺼내 쓸 수 있게, 작업할 때마다 조금씩 채웁니다.
> 마지막 갱신 2026-11-16. 수치는 측정한 환경을 함께 적었고, 팀 확인 전인 내용은 "제안"으로 표시했습니다.

## 1. 담당 범위

- 직책: 팀원 (A)
- 범위: 대기열·번호표·예상 대기 시간(Redis), 위험 점수를 받아 순번에 반영, 대기열 입장 토큰 발급·검증, 식별정보 가명처리(HMAC) 모듈
- 코드: `src/main/java/com/jejari/queue/`(대기열), `src/main/java/com/jejari/common/hmac/`(가명처리), `k6/queue/`(CLI 부하·검증 시나리오), `loadtest/`(창으로 조작하는 부하 테스트 프로그램). 팀 구조(루트 Gradle 프로젝트, `com.jejari`)에 맞춰 옮김

## 2. 핵심 수치

| 지표 | 목표 | 결과 | 측정 방법 |
|---|---|---|---|
| 동시 접속 처리량 | 측정 후 설정 | 진입 처리량이 정체하는 지점을 두 환경에서 쟀다. **내 PC**: 약 2,000건/초 → 약 3,000건/초 (2,000건/초 구간 p95 64ms → 17ms). **클라우드 4코어**: 약 2,900건/초 → 약 4,700~5,000건/초 (4,000건/초 구간 p95 568~625ms → 32~62ms). 두 환경 모두 약 1.5~1.6배, 요청 실패 0건 | `k6/queue/entry-burst.js`. 초당 진입 수를 1,000→6,000으로 올려 가며 단계당 10초. k6·앱·Redis를 한 대에서 같이 돌림. 내 PC는 개선 전·후 각 1회(조건이 완전히 같지는 않음, 아래 참고), 클라우드는 각 2회 |

| 입장 토큰 없이 좌석 API 호출 차단율 | 100% | 차단해야 할 요청 500건 중 **500건 차단**(토큰 없음·가짜·남의 토큰·다른 운행·이탈 후), 열려야 할 요청 300건 중 300건 통과 | `k6/queue/token-guard.js`, `QueueApiTest` |

> 아직 못 잰 것: 배포 환경 수치, 실제 회원 조회(DB)가 붙은 뒤의 진입 처리량, 병목이 앱·Redis·k6 중 어디인지(도구로 확인 못 함).
> 위 처리량은 "이 환경에서 정체하는 지점"이지 서버 한계가 아닙니다 (k6·앱·Redis가 한 대에서 같이 돌았음).
> 내 PC의 개선 전·후는 단계 길이(20초 → 10초)와 k6 최대 VU(1,000 → 1,500)가 달랐고 CPU 코어 수는 기록하지 못했습니다. 정체 지점(약 2,000 → 약 3,000)은 비교할 수 있지만, 정체 구간의 p95(약 560~600ms)는 VU 상한에 좌우되어 비교 대상이 아닙니다.

## 3. 설계 결정

### 결정 1. 위험 사용자는 요청을 늦추지 않고 순번만 뒤로 보낸다

- 상황: 기획서의 요구는 "요청을 지연시키지 않고, 위험 점수만큼 순번을 뒤로 조정해 서버 자원 낭비 없이 후순위로 처리"였다.
- 고려한 대안: ① 요청 처리를 `sleep`으로 지연 ② 위험 사용자용 별도 대기열 ③ 정렬 점수에 패널티를 더해 한 줄에서 정렬
- 선택과 이유: ③. 진입 시각(ms)에 `위험 점수 × 1000ms`를 더해 Redis ZSET의 score로 쓴다. ①은 스레드·연결을 붙잡아 봇 트래픽이 서버 자원을 갉아먹고, ②는 두 줄을 합쳐 공정하게 입장시키는 로직이 따로 필요하다. ③은 ZADD 한 번이면 끝나고 입장 처리는 맨 앞부터 꺼내기만 하면 된다.
- 감수한 단점: 줄이 비어 있으면 패널티가 의미가 없다 (봇이 혼자 있으면 바로 입장). 그래서 "붐빌 때 뒤로 밀린다"가 정확한 설명이다. 점수는 진입하는 순간에만 반영되어, 줄을 선 뒤 점수가 바뀌어도 이미 정해진 순번은 안 바뀐다.
- 관련 코드·커밋: `enter.lua`, `RiskPenaltyService` · `c70a1a1`

### 결정 2. 진입 판단을 Lua 스크립트 하나로 원자적으로

- 상황: "이미 줄 섰나 → 같은 CI의 다른 계정이 있나 → 번호표 발급 → 줄에 넣기"가 여러 명령이면 동시 요청이 사이에 끼어든다 (새로고침 연타, 다계정 동시 진입).
- 고려한 대안: ① 명령을 따로 보내고 앱에서 락 ② Redis 트랜잭션(MULTI/WATCH) ③ Lua 스크립트
- 선택과 이유: ③. Redis는 스크립트 하나를 끝까지 실행한 뒤 다음 것을 처리하므로 락이 필요 없고, 중간 상태가 보이지 않는다. 왕복도 한 번이다.
- 감수한 단점: 스크립트가 바뀌면 동작 전체가 바뀌므로 통합 테스트가 필수다. 클러스터로 바꾸면 스크립트가 쓰는 키를 같은 슬롯에 두도록 키 이름을 바꿔야 한다 (단일 노드 전제).
- 확인: 500명 동시 진입에서 번호표 중복 0, 같은 회원 50번 연타에서 줄에 1번, 같은 CI 20계정 동시 진입에서 1계정만 성공.
- 관련 코드·커밋: `enter.lua`, `QueueServiceTest` · `c70a1a1`

### 결정 3. 진입 시각을 앱이 아니라 Redis `TIME`으로 찍는다

- 상황: 앱 시계로 score를 찍으면, 시각을 읽은 뒤 잠깐 멈춘 요청이 번호표(seq)는 늦은데 시각은 이른 값을 받아 순번이 뒤집힐 수 있다. 앱이 여러 대면 서버 시계 차이도 섞인다.
- 고려한 대안: ① 앱 시계 + NTP에 의존 ② Redis `TIME`을 스크립트 안에서 읽기
- 선택과 이유: ②. 번호표 발급과 시각 읽기가 같은 스크립트 안이라 시각 순서와 번호표 순서가 항상 같다.
- 감수한 단점: Redis 한 대의 시계가 기준이다 (클러스터로 가면 샤드마다 달라 보장이 약해짐). Redis 5.0 이상 필요.
- 관련 코드·커밋: `enter.lua`, `admit.lua` · `6fe8bed`

### 결정 4. 입장 토큰은 (운행, 회원) 쌍마다 하나, 검증은 컨트롤러 앞단에서

- 상황: 목표는 "토큰 없이 좌석 API 호출 차단율 100%, 무효 토큰 재사용 차단 100%".
- 고려한 대안: ① JWT에 입장 정보를 넣고 서명으로 검증 ② Redis에 토큰 저장 후 조회
- 선택과 이유: ②. 키가 `queue:pass:{운행}:{회원}`이라 남의 토큰·다른 운행 토큰은 조회 단계에서 걸러지고, 이탈하면 키를 지우는 것만으로 즉시 무효가 된다. ①은 이미 발급한 토큰을 되돌릴 방법이 없다. 값은 256비트 `SecureRandom`, 비교는 시간 일정한 방식(`MessageDigest.isEqual`)으로 한다. 검증은 로그인(JWT) 검사 뒤에 실행되는 인터셉터(`QueueSeatTokenInterceptor`)라 컨트롤러에 닿기 전에 막힌다.
- 감수한 단점: 좌석 요청마다 Redis를 한 번 읽는다. POST `/reservations`는 운행 ID가 본문에 있어 필터로 못 막으므로 B가 `QueuePassService.verify`를 직접 불러야 한다.
- 관련 코드·커밋: `QueueTokenFilter`, `QueuePassService`, `admit.lua` · `c70a1a1`

### 결정 5. 식별정보는 SHA-256이 아니라 HMAC, 종류 이름을 함께 해시

- 상황: 전화번호·카드번호는 경우의 수가 작고, 같은 CI·카드를 쓰는 계정은 원문 없이 묶어야 한다.
- 고려한 대안: ① 키 없는 SHA-256 ② 암호화(AES) ③ HMAC-SHA256
- 선택과 이유: ③. ①은 가능한 번호를 전부 해시해 보면 원문이 나온다. ②는 복호화가 가능해 이 용도(묶음 키)에는 필요 이상으로 위험하다. 종류 이름(`CI`, `PHONE`…)을 메시지에 넣어, 같은 문자열이라도 테이블이 다르면 해시를 맞대어 사람을 잇지 못한다.
- 감수한 단점: 키를 바꾸면 이미 저장된 해시와 이어지지 않으므로 프로젝트 기간 동안 고정해야 한다. 정규화 규칙·`Purpose` 이름도 바꿀 수 없어, 깨지면 테스트가 실패하도록 고정값 테스트를 뒀다.
- 관련 코드·커밋: `common/hmac/Pseudonymizer` · `2471985`

### 결정 6. 진입 한 건당 Redis 왕복을 9번에서 2번으로 줄인다

- 상황: 부하 테스트에서 진입 처리량이 2,000~2,900건/초에서 정체하고 지연이 늘었다. 코드를 보니 진입 한 건이 정책 조회 서너 번, 진입 스크립트, 순번·토큰·입장 속도 재조회로 Redis를 약 9번 왕복했다.
- 고려한 대안: ① 서버 늘리기·스레드 늘리기 ② 왕복 줄이기
- 선택과 이유: ②. 병목이 CPU가 아니라 왕복 수에 있다고 봤다 (병목 위치를 직접 확인한 것은 아니고 코드 근거와 측정 결과의 일치로 판단). 정책값 1초 앱 캐시, 진입 스크립트가 순번·입장 속도를 함께 반환, 번호표 조회를 `status.lua` 하나로 통합했다. 조회가 한 스크립트라 입장 처리가 끼어들어도 결과가 어긋나지 않는 부수 효과도 있다.
- 감수한 단점: 정책을 바꾸면 최대 1초 뒤 반영된다 (실제로 k6 시나리오가 이 지연 때문에 한 번 실패했다).
- 결과: 같은 환경에서 목표 4,000건/초 구간의 p95가 568~625ms → 32~62ms, 정체 지점이 약 2,900 → 약 4,700~5,000건/초.
- 관련 코드·커밋: `PolicyProvider`, `status.lua` · `2dc0269`

### 결정 7. 위험 점수는 모르면 막는 쪽으로 읽는다

- 상황: 위험 점수 캐시가 비거나(Redis 재시작) 값이 오염되면(`NaN` 등) 위험 사용자가 패널티 없이 통과할 수 있었다.
- 고려한 대안: ① 잘못된 값은 무시(0점) ② 100점 + 경고 ③ 진입 거절
- 선택과 이유: ②. 패널티는 순번만 미루고 거절하지 않으므로 피해가 작고, 조작된 값이 "패널티 없음"이 되는 우회로가 없다. 캐시가 비었는지는 `risk:meta:synced_at`으로 구분하고, 비었으면 Oracle을 직접 본다.
- 감수한 단점: Redis 재시작 뒤 재동기화 전까지(최대 10분) 진입이 Oracle을 조회한다 (팀 협의 중, `팀-확인-요청.md` 17번).
- 관련 코드·커밋: `RiskPenaltyService`, `RiskScoreFallbackPort` · `aff413e`

## 5. 다른 파트와의 연결

모두 아직 팀과 합의하기 전이라 "제안"입니다. 합의되면 이 칸을 고칩니다.

| 상대 | 주고받는 것 | 약속한 내용 |
|---|---|---|
| B 강동균 | 좌석 API가 입장 토큰을 확인 / 판매 중 운행 목록 | 제안: `/runs/{id}/seats`는 필터가 막고, `POST /reservations`는 `QueuePassService.verify(runId, memberId, token)` 호출. 운행 상태는 `OnSaleRunProvider`로 받기 |
| B 강동균 (ERD 반영) | `queue:member` 값 형식 변경, 새 정책 키 | 제안: 값 `{runId}\|{queue member}\|{ciHash}`(ciHash는 입장·이탈 때 `queue:ci`를 찾기 위해 덧붙임), `queue.entry_ttl_sec`(3600) 시드 추가 |
| D 강다인 | 위험 점수 캐시 / 회원 정보 / HMAC 사용 | 제안: `risk:{CI\|PAYMENT\|DEVICE}:{해시}`에 `final_score`를 숫자 문자열(0~100)로. 대기열은 읽기만. 값이 오염되면 100점, `risk:meta:synced_at`이 없으면 Oracle 직접 조회(`RiskScoreFallbackPort`)를 다인 님이 구현. 회원 CI·결제 수단·기기 해시와 상태는 `MemberIdentityPort`로. CI·전화번호 등은 `hmac` 모듈로 해시해야 값이 같아짐 |
| C 길동현 | queue_log 적재 / 에러 코드 | 제안: `QueueLogSink`를 Kafka 발행으로 구현(토픽 합의 필요). 기능설계서 9장에 `QUEUE_NOT_FOUND`(404), `AUTH_REQUIRED`(401) 추가 |
| E 조영준 | 로그인 인증 / 비밀값 / k6 | JWT는 팀 구현(`AuthPrincipal`)을 그대로 씀 (해결). `JEJARI_HMAC_KEY`를 `.env`로 관리, 공통 영역에 `SERVICE_UNAVAILABLE`·Redis 즉시 실패 설정을 추가했으니 확인 부탁, 대기열 k6는 `k6/queue/`와 `loadtest/` |

## 7. 예상 질문

- Q. 위험 사용자는 어떻게 후순위로 보내나요?
  - A. 요청을 늦추지 않고, 대기열 정렬 점수(진입 시각 + 위험 점수 × 1초)를 뒤로 밉니다. 서버 자원을 더 쓰지 않고 순서만 바뀌고, 입장은 맨 앞부터 꺼내기만 하면 됩니다. 단, 줄이 비어 있으면 패널티가 있어도 바로 입장하므로 "붐빌 때 뒤로 밀린다"가 정확한 표현입니다.
- Q. 새로고침을 하거나 여러 번 눌러도 순번이 안 밀리나요?
  - A. 진입 스크립트가 이미 줄에 있는 회원이면 새 번호표 없이 기존 순번을 돌려줍니다. 같은 회원 50번 동시 요청에서 줄에는 1번만 섰고, 이 판단이 Lua 한 번 안에서 원자적으로 일어나서 그렇습니다.
- Q. 동시에 수백 명이 들어오면 번호표가 겹치지 않나요?
  - A. 번호표는 Redis `INCR`로 주고, Redis가 한 번에 한 명령만 처리해서 겹치지 않습니다. 500명 동시 진입에서 번호표 500개가 모두 달랐고, 초당 3,000건 규모 부하 한 번에서는 발급된 번호표 수와 카운터가 정확히 일치했습니다.
- Q. 다계정으로 여러 줄에 서는 것을 막았나요?
  - A. 같은 CI의 다른 계정이 대기·입장 중이면 거절합니다 (`queue:ci`). 20계정이 동시에 들어와도 1계정만 성공했습니다. 다만 CI는 모의 본인인증 값이라, 실제 서비스라면 인증 수준에 의존합니다.
- Q. 토큰을 어떻게 안전하게 검증하나요?
  - A. 256비트 무작위 값을 Redis에 (운행, 회원) 쌍으로 저장하고 좌석 API 앞 인터셉터에서 비교합니다. 남의 토큰, 다른 운행, 이탈 후, 만료 후 모두 403이고, k6로 차단해야 할 500건이 전부 막히는 것을 확인했습니다. JWT 대신 Redis를 쓴 이유는 이탈 시 즉시 무효화하기 위해서입니다.
- Q. 성능은 어떻게 개선했고 얼마나 좋아졌나요?
  - A. 코드를 보니 진입 한 건이 Redis를 9번 왕복해서, 정책 캐시·스크립트 통합으로 2번까지 줄였습니다. 같은 환경에서 4,000건/초 구간 p95가 568~625ms에서 32~62ms로, 처리량 정체 지점이 약 2,900에서 약 4,700~5,000건/초로 올랐습니다. 단, k6·앱·Redis가 한 대에서 돌아간 값이라 서버 한계 수치는 아닙니다.
- Q. 한계나 아쉬운 점은요?
  - A. ① 입장 스케줄러가 앱 한 대 기준이라 여러 대면 입장 인원이 대수만큼 늘어납니다 (리스 필요). ② 위험 점수는 진입 순간에만 반영됩니다. ③ 실제 회원 조회(DB)가 붙으면 처리량이 내려갑니다. ④ 취소표 대기는 위험 점수를 반영하지 않아 봇이 취소표를 먼저 가져갈 수 있는 구멍이 설계에 남아 있습니다 (미정 사항 7번).
