# 배포 승인 (BLOCKED 풀기를 관리자 화면에서)

작성자: 길동현 · 코드 위치: `src/main/java/com/jejari/admin/deploy/DeployApprovalService.java`, `frontend/src/admin/Deploy.jsx`, `deploy/auto-deploy.sh`

## 한 줄 요약

자동 배포가 DB·인프라 변경 때문에 멈추면(BLOCKED), 관리자 화면 A-08에서 막힌 이유를 보고 DB 패치를 넣은 뒤 승인해 배포합니다. 서버에 SSH로 들어가 `deploy.sh`를 칠 필요가 줄어듭니다.

## 어떻게 동작하나

```
auto-deploy.sh 가 BLOCKED → autodeploy.blocked 에 커밋·막힌 파일
  → A-08 화면: 파일마다 할 일 (DB 패치 [적용] / 할 일 없음 / 서버에서 직접 + 체크)
  → [승인] → autodeploy.approved 에 그 커밋 → 자동 배포 지금 한 번 실행
  → auto-deploy.sh: 승인된 커밋 = 고른 커밋이면 BLOCKED 건너뛰고 배포
```

- DB 패치는 앱 계정이 docker 그룹이라 `docker exec ... sqlplus`로 넣습니다. 비밀번호는 명령줄이 아니라 표준 입력의 `CONNECT` 줄로 넘깁니다.
- 실행하는 패치는 막힌 **그 커밋의** `db/patch/vNN.sql`뿐입니다. 막힌 목록에 없는 파일은 실행하지 않습니다.

## 왜 이렇게 했나

- CI는 매번 새 DB에 최신 DDL을 통째로 만들어 테스트하므로, "서버 DB에 패치가 들어갔는지"는 확인하지 못합니다. 그래서 BLOCKED는 남기고, 푸는 수고만 줄였습니다.
- 새 sudo 권한이 필요 없게 했습니다. 배포 시작은 기존 배포 버튼과 같은 줄(`systemctl start --no-block jejari-autodeploy.service`)을 씁니다.
- 승인은 커밋 하나에만 걸립니다. 그사이 새 커밋이 오면 그 커밋의 변경까지 다시 확인해야 하므로 다시 멈춥니다.

## 주의할 점

- systemd 유닛·sudoers·Caddy·compose 변경은 웹에서 실행하지 않습니다 (root 권한이 필요하거나 컨테이너를 다시 만듦). 화면에 명령만 보여 주고 사람이 서버에서 합니다.
- 패치 실패(ORA-/SP2- 출력)는 적용된 것으로 보지 않습니다. 결과 출력을 보고 고친 뒤 다시 적용하세요. 패치는 다시 실행해도 안전하게 쓰는 것이 저장소 규칙입니다.
- 배포 버튼과 같은 스위치(`JEJARI_OPS_DEPLOY_ENABLED`)와 관리자 목록(`JEJARI_OPS_DEPLOY_ADMIN_IDS`)을 씁니다. **프로젝트가 끝나면 지웁니다** (웹에서 서버 명령을 실행하는 기능).
