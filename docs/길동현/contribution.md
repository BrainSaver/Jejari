# 길동현 개인 기여 정리

> **열차 예매에서 어디?** 좌석을 고른 뒤 돈을 내는 **결제**와, 예매 상태가 바뀔 때 다른 기능에 알려 주는 **이벤트 연락망**을 맡았습니다. 한눈에 보기: [README.md](README.md)

> 면접에서 "본인이 한 일"을 바로 꺼내 쓸 수 있게, 작업할 때마다 조금씩 채웁니다.

## 3. 설계 결정

결정 하나당 한 칸. "왜 이렇게 했는가"를 면접에서 그대로 말할 수 있게 적습니다.

### 결정 1. Kafka 발행은 Transactional Outbox로

- 상황: 예약·결제 상태가 바뀌면 좌석 해제·알림·위험 신호 소비자에게 알려야 함
- 고려한 대안: 커밋 후 Kafka 직접 발행 / Kafka 트랜잭션 / Outbox
- 선택과 이유: Outbox. 직접 발행은 커밋과 발행 사이에 죽으면 이벤트가 사라지고, 반대 순서면 롤백된 일이 알려짐. Outbox는 이벤트를 업무와 같은 트랜잭션의 행으로 남겨 둘이 항상 같이 성공·실패
- 감수한 단점: 릴레이가 최소 한 번 발행이라 소비자에 Inbox(중복 제거)가 꼭 필요, 테이블 정리 배치 필요
- 관련 코드·커밋: `com.jejari.event.outbox`, `0f9f181`

### 결정 2. 릴레이는 잠긴 행을 건너뛰지 않고 기다림 (SKIP LOCKED 금지)

- 상황: 같은 예약의 이벤트는 순서(선점 → 결제 시작 → 확정)대로 도착해야 함
- 고려한 대안: `FOR UPDATE SKIP LOCKED`(처리량↑) / `FOR UPDATE WAIT n`
- 선택과 이유: WAIT. 건너뛰면 뒤 이벤트가 먼저 나감. 샤드(reservation_id 해시 16개) 안에서 seq 순서로 보내고, 실패하면 그 샤드의 이번 회차를 멈춤
- 감수한 단점: 한 샤드가 5회 실패로 FAILED가 되면 그 샤드의 다른 예약 이벤트도 멈춤 (다른 샤드는 계속)
- 관련 코드·커밋: `OutboxRelay`, `0f9f181`

### 결정 3. 결제 중복은 세 겹으로 막음 (EVT-04)

- 상황: 버튼 연타, 네트워크 재시도, 탭 두 개로 같은 예약을 동시에 결제할 수 있음
- 고려한 대안: Redis 멱등 키만 / DB UNIQUE만 / 둘 다 + 상태 조건부 UPDATE
- 선택과 이유: 세 겹. Redis 키는 빠르지만 TTL이 지나면 사라지고, 키가 다르면 못 막음. 예약 `HOLD → PAYMENT_PENDING` 조건부 UPDATE가 "예약당 결제 시작 한 번"을 DB에서 보장하고, UNIQUE가 마지막 안전망
- 감수한 단점: 결제 실패 후 재시도 불가 (다시 예매해야 함). 대신 마감이 계속 연장돼 좌석을 오래 붙잡는 문제가 없음
- 관련 코드·커밋: `PaymentService`, `PaymentStartTx`

### 결정 4. PG 결과를 모르면 예약을 만료시키지 않음 (EVT-05)

- 상황: PG 응답이 없으면 돈이 빠졌는지 알 수 없음
- 고려한 대안: 마감이 지나면 만료 / 결과를 알 때까지 미룸
- 선택과 이유: 미룸. 만료시키면 돈은 빠졌는데 좌석이 남에게 갈 수 있음. 스캐너가 PG에 다시 묻고, 승인·실패가 확인될 때만 Saga를 진행하거나 보상
- 감수한 단점: 그동안 좌석이 묶임. 오래 모르면 관리자 확인(ADM-09)
- 관련 코드·커밋: `PaymentRecheckScanner`, `PaymentSaga`

### 결정 5. 늦은 승인은 예약을 되살리지 않고 전액 자동 환불 (PAY-05)

- 상황: 결제를 실패로 정리해 좌석을 풀었는데, 나중에 PG가 "사실 승인됐다"고 알려 옴. 돈은 빠졌고 좌석은 이미 남에게 갔을 수 있음
- 고려한 대안: 예약을 되살림 / 관리자가 손으로 환불 / 자동 전액 환불
- 선택과 이유: 자동 전액 환불(수수료 0). 되살리면 같은 좌석이 두 명에게 팔릴 수 있음. 결제를 APPROVED로 바꾸는 트랜잭션에서 환불 기록(cancellation REQUESTED)을 같이 남겨, 커밋 직후 앱이 죽어도 "돌려줘야 할 돈"이 사라지지 않음. PG 환불은 커밋 뒤에 하고, 환불 키 `cancel:{cancel_id}`로 두 번 불러도 한 번만 환불
- 감수한 단점: 고객은 예매를 잃음. PG 환불이 실패하면 FAILED로 남아 재시도 배치(CNL-03)가 필요
- 관련 코드·커밋: `LateApprovalRefund`, `PaymentSaga`, `235ba83`

### 결정 6. 알림은 "만들기"와 "보내기"를 나눔 (EVT-06·WL-04)

- 상황: 만료·환불 완료·결제 기한 임박·취소표 제안을 알림함에 보여야 함. 이벤트는 중복으로 올 수 있음
- 고려한 대안: 이벤트를 받자마자 발송 / 알림 행을 남기고 발송기가 따로 보냄
- 선택과 이유: 나눔. 이벤트 소비자는 Inbox 도장과 알림 행을 한 트랜잭션에 남겨 중복을 막고, 발송기가 `sent_at`이 빈 행만 보내고 표시함. 다른 파트(취소표 제안)는 행만 남기면 되고, 나중에 푸시·메일로 바꿀 때 발송기만 고치면 됨
- 감수한 단점: 발송까지 최대 1초 지연. 지금 발송은 로그뿐
- 관련 코드·커밋: `com.jejari.notification`, `0cf4c45`

## 7. 예상 질문

- Q. Outbox를 쓰면 중복 발행은 안 생기나요?
  - A. 생깁니다. 릴레이가 Kafka에 보낸 뒤 PUBLISHED 표시 전에 죽으면 다시 보냅니다. 그래서 소비자가 `(컨슈머 그룹, event_id)`를 PK로 INSERT하고 업무 처리와 같은 트랜잭션에 묶어, 두 번째부터는 건너뜁니다. 테스트로 재발송 시 처리 1회를 확인했습니다.
- Q. 왜 SKIP LOCKED를 안 썼나요?
  - A. 처리량은 좋아지지만 잠긴 앞 행을 건너뛰고 뒤 행을 보내 같은 예약의 이벤트 순서가 깨집니다. 기다렸다가 시간이 넘으면 이번 회차를 포기하는 쪽을 골랐습니다.
- Q. 테스트를 어떻게 믿을 수 있나요?
  - A. 롤백되는 테스트는 커밋 경계를 검증하지 못해서 실제로 커밋하는 테스트를 따로 만들었고, 릴레이에 일부러 순서 버그를 넣어 테스트가 실패하는지 확인했습니다.
- Q. 결제 버튼을 두 번 누르면 어떻게 되나요?
  - A. 같은 멱등 키면 Redis가 처음 결과를 돌려주고, 키가 달라도 예약 상태를 `HOLD`일 때만 결제 중으로 바꾸므로 두 번째는 거절됩니다. 같은 예약에 20개를 동시에 보내도 결제는 1건, PG 승인도 1번인 것을 테스트로 확인했습니다.
- Q. PG가 응답을 안 주면요?
  - A. 예약을 만료시키지 않고 결제 중으로 둡니다. 마감이 지나면 스캐너가 PG에 결과를 물어서, 승인이면 확정하고 실패면 좌석을 돌려줍니다(Saga 보상). 계속 모르면 다음 조회로 미루고 오래되면 관리자에게 알립니다.
- Q. 결제를 실패로 처리했는데 나중에 승인되면요?
  - A. 예약은 되살리지 않고 전액을 수수료 없이 자동 환불합니다. 좌석이 이미 다른 사람에게 갔을 수 있기 때문입니다. 결제를 승인으로 바꾸는 트랜잭션에서 환불 기록을 같이 남기므로 중간에 서버가 죽어도 돌려줄 돈을 잃지 않고, 환불 키가 같아서 두 번 불러도 한 번만 환불됩니다.
- Q. 실제 카드 없이 어떻게 테스트했나요?
  - A. 가짜 PG(Mock PG)를 만들어 카드번호 끝자리로 승인·거절·응답 없음·늦은 승인을 정했습니다. PG 환불 실패는 테스트에서 PG를 Mockito로 바꿔 예외를 던지게 해서 확인했습니다.
