## 1. 한 줄로 내 역할

> **돈이 오가는 부분(결제)과, 그 결과를 다른 파트에 확실히 전달하는 부분(이벤트)을 맡는다.**

- 팀장, 역할 **C**, 브랜치 **`DongHyeon`**
- 지켜야 할 숫자 두 개
  - **중복 결제 0건**: 같은 예약에 돈이 두 번 빠지면 안 됨
  - **좌석 복구율 100%**: 결제가 실패하거나 시간이 지나면 좌석이 반드시 돌아와야 함

## 2. 전체 흐름에서 내 자리

```
 좌석 선점 ──▶ [결제 시작] ──▶ [PG 결과] ──┬─ 승인 ──▶ 예약 확정
  (강동균)       (나)            (나)       │
                                            └─ 실패·시간 초과 ──▶ 좌석 복구 (Saga, 나)
                                                                  └─ 실제 해제는 강동균 로직 호출

 위의 모든 상태 변화 ──▶ [Outbox] ──▶ Kafka ──▶ [Inbox] ──▶ 좌석 반환·알림·위험 점수
                         (나)                    (나)        (각 담당자)
```

내가 만드는 것은 대괄호 안 다섯 가지입니다.

| 부분 | 쉽게 말하면 |
|---|---|
| **결제 시작** | "결제할게요" 버튼을 누르면 예약을 결제 중 상태로 바꾸고 마감 시간을 한 번 늘려 줌 |
| **PG 결과 처리** | PG(결제 대행사)에서 승인·실패가 오면 예약을 확정하거나 풀어 줌 |
| **Saga** | 여러 단계(선점 → 결제 → 확정) 중 중간에 실패하면 앞 단계를 되돌리는 관리자 |
| **Outbox** | "이런 일이 있었다"를 DB에 먼저 적어 두고 나중에 Kafka로 보내는 우체통 |
| **Inbox** | 같은 편지가 두 번 와도 한 번만 처리하게 하는 수신 기록장 |

여기에 **알림**(취소표 제안 등)과 **결제 수단 등록**(가상 카드)도 맡습니다.

## 3. 꼭 기억할 규칙 7개

모든 코드가 이 7개를 지키면 중복 결제·순서 꼬임이 안 생깁니다.

1. **Redis는 빠른 1차 판정, Oracle이 최종 판정.** Redis가 통과시켜도 DB가 거절하면 거절이다.
2. **마감 시각의 원본은 `reservation.pay_deadline_at` 하나.** 다른 곳(좌석, Saga, 대기자, Redis)은 복사본이라 바꿀 때 같이 바꾼다. 시간은 앱 시계로 계산한다.
3. **상태를 바꿀 땐 "지금 상태가 X일 때만" 바꾸고, 바뀐 행 수를 확인한다.** 0행이면 누가 먼저 처리한 것이니 그 뒤 일을 하지 않는다. 이게 중복 방지의 핵심이다.
4. **예약(reservation) 행을 먼저 잠그고** 결제·좌석·Saga를 바꾼다. 순서가 같아야 데드락이 안 난다.
5. **PG 호출과 Kafka 발행은 DB 트랜잭션 밖에서.** 락을 쥔 채 외부 응답을 기다리지 않는다.
6. **이벤트는 DB에 먼저 적는다(Outbox).** 상태를 바꾼 같은 트랜잭션 안에서, 예약 행을 바꾼 **뒤에** INSERT한다.
7. **숫자 값(시간·횟수)은 코드에 박지 않고 `app_policy`에서 읽는다.**

## 4. 기능별 핵심 (구현할 때 해당 칸만)

### 4-1. 결제 시작 — PAY-01 · `concurrency.md §4`

- **무엇:** 예약을 `HOLD` → `PAYMENT_PENDING`으로 바꾸고 결제를 요청한다.
- **마감 연장:** 마감을 `지금 + 4분`(PG 3분 + 여유 1분)과 기존 마감 중 **늦은 쪽**으로 바꾼다. 줄어들지 않고 **딱 한 번만** 늘어난다.
- **좌석 확인:** 좌석 행 수가 예상과 다르면 좌석을 이미 잃은 것이므로 거절한다.
- **커밋 뒤:** Redis 좌석 키도 연장한 다음 PG에 승인 요청을 보낸다.
- **결제 실패 후 재시도는 없다** → 다시 예매한다.
  - 왜? 재시도마다 마감이 늘어나면 한 사람이 좌석을 오래 붙잡게 된다.

### 4-2. 결과 처리 — PAY-02·03 · `§5`

- PG 응답, 콜백, 스캐너 조회 **어느 경로로 와도, 몇 번 와도 결과가 같아야 한다.**
- 먼저 예약 행을 잠그고 `payment.status`를 본다.

| payment 상태 | 하는 일 |
|---|---|
| `REQUESTED` (처음) | 승인이면 확정, 실패면 예약 만료 |
| `APPROVED` + 예약 확정됨 | 이미 끝남, 성공 응답만 |
| `APPROVED` + 예약 안 됨 | "환불 진행 중" 응답 |
| `REFUNDED` | "환불 완료" 응답 |
| `FAILED`인데 승인이 옴 | **늦은 승인**: 돈은 빠졌는데 좌석은 이미 풀림 → 전액 환불, 예약은 되살리지 않음 |

- **확정:** 좌석 SOLD → 결제 APPROVED → 예약 CONFIRMED → Saga DONE → 이벤트 `RESERVATION_CONFIRMED`
- **실패:** 결제 FAILED → 예약 EXPIRED(사유 `PAY_FAILED`) → 좌석 반환. 따로 "결제 실패" 예약 상태는 두지 않는다.

### 4-3. PG 결과 확인 스캐너 — PAY-04 · `§6.2`

- **무엇:** 마감이 지났는데 결과를 모르는 결제를 PG에 다시 물어본다.
- **강동균의 HOLD 만료 스캐너와 쿼리를 분리한다.** 내 쪽이 밀려도 좌석 만료는 계속 돌아간다.

| PG 대답 | 처리 |
|---|---|
| 승인 | 4-2 확정 |
| 실패 | 4-2 실패 |
| 요청 기록 없음 | PG에 취소를 요청한 뒤 실패 처리 |
| **모름 (장애)** | **자동 만료하지 않는다.** 1분 뒤 다시 묻고, 좌석은 지킨다. 30분 넘으면 관리자 알림 |

- 왜 자동 만료하지 않나? 돈이 이미 빠졌을 수 있기 때문이다.
- 1차 구현은 승인·실패만 처리하고, "모름"은 다음 조회로 미루기만 한다.

### 4-4. Saga · 좌석 복구 — EVT-05 · `§7`

- **무엇:** 예약이 단계(선점 → 결제 중 → 확정)를 밟는 동안 Saga가 진행 상황을 들고 있다.
- **실패·만료 시:** 상태를 `COMPENSATED`로 바꾸고 좌석 반환·매수 카운터 감소·Redis 정리를 한다.
- **실제 좌석 해제는 강동균이 만든 로직을 `reservation_id`로 호출한다.** 두 번 불러도 결과가 같아야 한다.
- **늦은 승인 환불(§7.3, P2):** `cancellation`에 전액·수수료 0으로 기록 → PG 환불 → 완료 시 `REFUNDED`

### 4-5. Outbox — EVT-01·02 · `§11`

- **왜 필요하나?** DB 커밋과 Kafka 발행을 동시에 성공시키는 방법이 없다. 그래서 DB에 "보낼 이벤트"를 같이 적고, 릴레이가 나중에 보낸다.
- **순서 보장 장치**
  - Kafka 키는 항상 `reservation_id` → 같은 예약 이벤트는 같은 파티션에 들어간다.
  - 샤드 번호 = `ORA_HASH(TO_CHAR(키), 15)`. **키는 항상 문자열로 넘긴다.** 숫자로 넘기면 샤드가 달라져 순서가 깨진다.
  - 샤드 하나는 릴레이 인스턴스 하나만 맡는다(Redis 리스).
  - `seq` 순서로 하나씩 보내고, **실패하면 그 샤드는 거기서 멈춘다.** 뒤 이벤트가 앞을 추월하지 않게.
  - `SKIP LOCKED`는 쓰지 않는다. 건너뛰면 순서가 깨진다.
- **5번 실패하면** FAILED로 두고 그 샤드만 정지 + 알림. 관리자가 되돌리면 재개된다.
- **프로듀서 설정:** `enable.idempotence=true`, `acks=all`
- **1차 구현:** 샤드 1개, 인스턴스 1대

### 4-6. Inbox — EVT-03 · `§12`

- 한 트랜잭션 안에서 `processed_event` INSERT(이미 있으면 건너뜀) → 업무 처리 → 커밋 → **그 다음에** Kafka 오프셋 커밋.
- 기록은 **8일** 보관한다. Kafka 보관이 7일이라 그보다 길어야 재전달 중복을 막는다.

### 4-7. 결제 멱등 — EVT-04 · `§1`

- 버튼을 누를 때마다 클라이언트가 UUID를 만들어 `Idempotency-Key` 헤더로 보낸다. 재시도는 같은 키를 쓴다.
- **3중 방어**
  - Redis `idem:pay:{예약ID}:{키}`
  - DB `UNIQUE(reservation_id, idempotency_key)`
  - 예약당 승인 1건 인덱스 `ux_payment_approved`

### 4-8. 알림 — EVT-06·WL-04

- 실제 발송은 없다. `notification` 테이블에 쌓고 알림함으로 보여 준다.
- 종류: 취소표 제안, 결제 기한 임박, 예약 만료, 대기 건너뜀, 환불 완료
- **1차 구현:** INSERT만 하고, 알림함 화면(U-11)은 나중에 만든다.

## 5. 상태 그림

**예약**
```
HOLD ──결제 시작──▶ PAYMENT_PENDING ──승인──▶ CONFIRMED ──취소──▶ CANCELED
 │                        │
 ├─시간 초과·뺏김─▶ EXPIRED ◀─결제 실패─┘
 └─결제 전 취소──▶ CANCELED
```
`PAYMENT_PENDING`(결제 중)은 사용자가 취소할 수 없고, 다른 사람이 가져갈 수도 없습니다.

**결제**
```
REQUESTED ──▶ APPROVED ──▶ REFUNDED
    └──▶ FAILED ──(늦은 승인)──▶ APPROVED ──▶ 환불
```

## 8. 면접 예상 질문 (답은 한 줄로 말할 수 있게)

| 질문 | 답의 핵심 |
|---|---|
| 중복 결제를 어떻게 막았나? | 멱등 키 3중 방어 + 예약 락 + "상태가 X일 때만" UPDATE |
| 왜 결제 재시도를 막았나? | 재시도마다 마감이 늘어나 좌석을 오래 붙잡는 걸 막으려고 |
| 결과를 모르는 결제는 왜 자동 취소하지 않나? | 돈이 빠졌을 수 있어서. 좌석을 지키며 다시 묻는다 |
| 왜 Outbox인가? | DB 저장과 이벤트 발행이 따로 실패하는 걸 막으려고 |
| 이벤트 순서는 어떻게 보장하나? | 같은 키, 같은 샤드, 샤드당 릴레이 1대, 실패하면 멈춤 |
| 같은 메시지가 두 번 오면? | Inbox 기록과 업무 처리를 한 트랜잭션에. 보관 8일 > Kafka 7일 |
| 늦은 승인은? | 승인으로 기록하고 전액 환불. 좌석은 이미 남에게 갔을 수 있어 되살리지 않는다 |

## 부록. 용어

| 용어 | 뜻 |
|---|---|
| PG | 결제 대행사 (토스페이먼츠 등). 1차는 직접 만든 Mock |
| 멱등 | 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같음 |
| Saga | 여러 단계 작업이 중간에 실패하면 앞 단계를 되돌리는 방식 |
| Outbox / Inbox | 보낼 이벤트를 DB에 적어 두는 표 / 받은 이벤트를 기록해 중복을 거르는 표 |
| 샤드 | 이벤트를 16묶음으로 나눈 것. 묶음마다 담당 릴레이가 하나 |
| 리스 | "이 샤드는 내가 맡는다"는 Redis 임시 표시 (15초, 계속 연장) |
| HOLD | 좌석을 잡아 둔 상태 (결제 전) |
