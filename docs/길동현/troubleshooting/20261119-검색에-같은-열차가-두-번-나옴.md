# [data] 공용 서버 열차 검색에 같은 KTX가 두 번 나옴 (`00103`과 `103`)

> **열차 예매에서 어디?** 첫 화면 열차 검색 결과입니다. 사용자가 보는 목록 맨 위에 같은 열차가 두 줄로 나왔습니다.

> 파일 이름: `docs/길동현/troubleshooting/20261119-검색에-같은-열차가-두-번-나옴.md`

## 1. 문제

- 현상: https://jejari.duckdns.org 에서 11-19 서울→부산을 검색하면 첫 두 줄이 `00103`·`103`. 둘 다 09:28 → 12:35, 운임·남은 좌석도 같음
- 찾은 방법: chrome-devtools MCP로 사이트를 직접 돌려 보다가 발견. 같은 페이지에서 `/api/v1/runs` 응답을 확인함
  ```
  runId 703221  trainNo "00103"  09:28 → 12:35   ← 강동균 시드 (열차 1)
  runId 723103  trainNo "103"    09:28 → 12:35   ← 내 시간표 스크립트 (열차 10103)
  ```
- 영향: 같은 실제 열차가 좌석 재고가 따로 있는 두 열차가 됨. 한쪽에서 매진돼도 다른 쪽에는 빈자리가 보이고, 시연 화면 맨 위에서 바로 눈에 띔

## 2. 원인

- 가설: 화면이 같은 행을 두 번 그리나? → API 응답부터 run_id가 다른 두 행이라 화면 문제가 아님
- 확인: 두 run의 train_id를 따라가 보니 출처가 둘
  1. 11-18 강동균이 시드 열차 1·2를 실제 KTX `00103`·`00026`으로 바꿈 (DATA-01, 시드 04가 2개월 동안 매일 운행을 깔아 둠)
  2. 공용 서버는 조영준의 `deploy/tago-refresh.sh`가 매일 내 `tools/load-tago-schedule.js`를 실행해 실제 시간표 전체를 넣음. 이 스크립트는 103편을 `train_id 10103`, 번호 `103`으로 넣음
- 최종 원인: 내 스크립트는 "시드에 이미 같은 열차가 있는지"를 보지 않았음. 시드가 가짜 번호(101·102)를 쓸 때는 안 겹쳤는데, 시드가 실제 번호로 바뀐 순간부터 겹침. 번호 표기(5자리 / 3자리)도 달라 눈으로도 같은 열차인 줄 알기 어려웠음
- 같이 찾은 것: 내 운행 번호 규칙 `400000 + 연중일 × 1000 + 열차번호`와 시드 규칙 `700000 + (운행일 - 2026-01-01) × 10 + train_id`가 날짜에 따라 같은 번호를 낼 수 있음. 지금 날짜 범위에서는 안 겹치지만, 겹치면 내 MERGE가 시드 운행의 마감 시각을 덮어씀

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 시드에서 103·026편을 빼기 | 내 스크립트는 그대로 | 남의 기준 데이터(DATA-01)를 바꿈. 시드는 테스트·시연 기준이라 건드리면 영향이 큼 | |
| 서버에서 겹친 행만 손으로 지우기 | 바로 됨 | 다음 날 갱신 때 다시 생김 | |
| 내 스크립트가 시드와 같은 번호를 건너뛰고, 예전에 넣은 것도 스스로 정리 | 내 코드만 고침. 서버는 다음 갱신 때 자동으로 정리됨 | 생성 SQL이 조금 길어짐 | ✓ |

- 선택한 이유: 겹친 쪽은 내 스크립트이고 시드는 원래 있던 기준 데이터임. 매일 도는 작업이라 한 번 지워도 다시 생기므로 스크립트가 스스로 정리해야 함
- 바뀐 코드 위치: `tools/load-tago-schedule.js`
  - 시드 열차(`train_id < 10000`)에 같은 번호(`LPAD(train_no, 5, '0')`로 비교)가 있으면 열차·운행·정차 MERGE를 건너뜀
  - 예전에 넣은 같은 편 운행은 예약·대기·좌석 행이 없으면 DELETE. 남은 건수를 마지막 SELECT에 출력
  - 열차 번호를 시드와 같은 5자리(`00103`)로 통일
  - 운행 MERGE는 `train_id`가 같을 때만 UPDATE. 같은 run_id를 다른 열차가 쓰고 있으면 건드리지 않음

## 4. 수치

| 지표 | 전 | 후 |
|---|---|---|
| 같은 날 같은 번호 열차 쌍 | 2 | 0 |
| 시드와 겹친 운행 (열차 10103·10026) | 28건 | 0건 |
| 예약이 있어 못 지운 운행 | | 0 |
| 실제 시간표 열차 번호 자릿수 | 3 | 5 (시드와 같음) |

- 측정 환경: 로컬 Docker Compose Oracle, 11-12~11-26 시간표 (열차 143개, 운행 1,604건)
- 측정 방법: 로컬 시드 번호를 실제 값(00103·00026)으로 바꾸고 생성 SQL을 한 트랜잭션에서 돌려 위 지표를 센 뒤 ROLLBACK (로컬 DB는 그대로 둠)
- 공용 서버: `jejari-tago.timer`(매일 04:30) 다음 실행 때 정리됨. 바로 하려면 `sudo systemctl start jejari-tago`

## 5. 정리

- 한 줄 요약: "공용 서버 검색에 같은 KTX가 두 번 나와서 보니, 시드가 실제 열차 번호로 바뀐 뒤 내 시간표 스크립트가 같은 편을 다른 열차로 한 번 더 넣고 있었고, 시드와 같은 번호는 건너뛰고 예전 것은 스스로 지우게 고쳐 겹친 운행을 28건에서 0건으로 줄였다."
- 다음에 비슷한 상황이면:
  - 같은 테이블에 데이터를 넣는 경로가 둘이면, 남의 데이터가 바뀌어도 안 겹치는지(번호 규칙·기준 키)를 먼저 맞춘다
  - 매일 도는 적재 작업은 "넣기"뿐 아니라 "예전에 잘못 넣은 것 정리"까지 스스로 해야 한다
  - ID 대역을 나눌 때 계산식끼리 겹치는 구간이 없는지 범위로 확인한다
