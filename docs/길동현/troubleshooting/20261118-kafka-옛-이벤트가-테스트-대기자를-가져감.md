## 1. 문제

- 현상: 내 PC에서 `WaitlistPaymentInfraTest`가 가끔 실패함
  ```
  Expected size: 1 but was: 0   (offer() 안의 assertThat(offered).hasSize(1))
  ```
- 재현 조건: 앱을 띄우거나 다른 통합 테스트를 돌려서 Kafka `reservation-events` 토픽에 취소 이벤트가 쌓인 뒤, 이 테스트를 돌림
- 영향: 서비스 동작은 정상임. 테스트가 환경에 따라 실패해서 결과를 믿을 수 없었음

## 2. 원인

- 가설 1: 제안 트랜잭션(`WaitlistOfferTx.offer`)이 좌석을 못 찾나? → 좌석은 테스트가 직접 풀어 줘서 비어 있었음
- 가설 2: 다른 누가 그 대기자를 먼저 처리했나? → 제안할 WAITING 대기자가 없다는 건 테스트가 부르기 전에 누군가 제안을 했다는 뜻
- 확인: 테스트 컨텍스트에 강동균의 `SeatReleaseConsumer`(Kafka 그룹 `seat-release`)가 켜져 있었음. 이 소비자는 취소 이벤트를 받으면 같은 운행·구간의 WAITING 대기자에게 자동으로 제안함
- 최종 원인: 테스트가 뜨자마자 소비자가 **Kafka에 남아 있던 옛 취소 이벤트**(운행 9001, 서울→부산)를 읽고, 방금 테스트가 넣은 WAITING 대기자에게 먼저 제안함. 그래서 테스트가 직접 부른 `offer()`는 제안할 대기자가 없어 빈 목록을 돌려받음

```
테스트: 대기자 INSERT (WAITING) ──┐
                                  ├─ 소비자: 옛 RESERVATION_CANCELED 소비 → 대기자 OFFERED  ← 먼저 끝남
테스트: offerTx.offer(...)  ──────┘   → 대기자 없음 → offered = []  → 실패
```

- DB는 테스트마다 지우지만 Kafka 토픽은 안 지우기 때문에, 이전 실행의 이벤트가 남아 있음

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 테스트 전에 토픽 비우기 | 깨끗한 상태에서 시작 | 다른 테스트·앱과 토픽을 같이 써서 위험, 느림 | |
| 테스트마다 다른 운행 ID 쓰기 | 소비자는 그대로 | 시드 운행이 9001뿐이라 데이터를 더 만들어야 함, 옛 이벤트가 우연히 겹칠 수 있음 | |
| 이 테스트에서 seat-release 소비자 끄기 | 한 줄, 확실함. 제안은 테스트가 직접 부르므로 소비자가 필요 없음 | 소비자 경로는 이 테스트에서 안 봄 (강동균 테스트가 따로 봄) | ✓ |

- 선택한 이유: 이 테스트가 보는 것은 "제안된 예약을 결제했을 때"이고, 제안은 테스트가 `WaitlistOfferTx.offer`로 직접 만듦. 자동 제안 소비자는 테스트 대상이 아님
- 바뀐 코드 위치: `src/test/java/com/jejari/payment/WaitlistPaymentInfraTest.java` `@SpringBootTest` 속성
  ```java
  "jejari.notification.dispatcher-enabled=false",
  // seat-release 소비자가 Kafka에 남은 옛 이벤트로 이 테스트의 대기자에게 먼저 제안하지 않게 (제안은 테스트가 직접 부른다)
  "jejari.waitlist.offer-enabled=false"
  ```
  (`SeatReleaseConsumer`는 `@ConditionalOnProperty(name = "jejari.waitlist.offer-enabled", matchIfMissing = true)`)

## 5. 정리

- 한 줄 요약: "취소표 결제 테스트가 가끔 실패해서 보니, Kafka에 남은 옛 취소 이벤트를 자동 제안 소비자가 먼저 읽어 테스트의 대기자를 가져가고 있었고, 이 테스트에서 소비자를 꺼서 해결했다."
- 다음에 비슷한 상황이면:
  - DB는 테스트마다 지워도 **Kafka 토픽은 남는다**. Kafka 소비자가 테스트 데이터를 건드릴 수 있는지부터 본다
  - 테스트가 직접 부르는 기능의 자동 경로(소비자·스케줄러)는 그 테스트에서 끈다. `build.gradle`의 테스트 속성이나 `@SpringBootTest(properties=…)`로
  - "내가 부르기 전에 이미 상태가 바뀌어 있다"면 백그라운드 소비자·스케줄러를 의심한다
