# FairRail

명절 열차 공정 예매 시스템 팀 프로젝트 (5명 · 3주). Spring Boot · Kafka · Redis · MongoDB · Oracle · Python.

## 폴더 구조

```
FairRail/
├─ README.md                         기획서
├─ CONTRIBUTING.md                   깃 규칙 (커밋 메시지, 브랜치, 머지, 기능 문서)
├─ .github/pull_request_template.md  PR 틀
├─ CLAUDE.md                         Claude Code가 자동으로 읽는 작업 규칙
├─ .claude/settings.json             Claude Code 커밋·PR 서명 끄기 (지우지 말 것)
├─ .gitmessage                       커밋 메시지 틀
├─ docs/
│  ├─ 작업안내.md                     이 파일
│  ├─ FairRail_기획서.pdf             원 기획서
│  ├─ FairRail_ERD.md                 종합 ERD 문서 ← 팀원은 이것만 읽으면 됨 (자동 생성)
│  ├─ concurrency.md                  동시성 절차 ← 예매·결제·취소 구현은 이것 (트랜잭션 순서·SQL·Redis)
│  ├─ erd/
```

## 시작 순서

1. 규칙·ERD·문서가 main에 올라감 (완료)
2. 조영준: Docker Compose(Oracle·MongoDB·Redis·Kafka)와 Spring Boot 뼈대를 **main에 직접** 올림 (처음 한 번만 예외)
3. 팀장 공지 후 나머지 팀원이 main에서 자기 이름 브랜치를 만듦 → 뼈대가 이미 들어 있음
4. 이후 main이 바뀌면 각자 브랜치에서 `git pull origin main`

## 처음 한 번 할 일

```bash
git clone https://github.com/BrainSaver/FairRail.git
cd FairRail
git config commit.template .gitmessage   # 커밋 메시지 틀
git config core.quotepath false          # 한글 파일 이름이 깨져 보이지 않게
git switch DongHyeon                     # 본인 이름 브랜치로 이동 (이미 만들어져 있음)
```

## 백업과 Claude 사용

- **새 브랜치를 만들지 않습니다.** 작업 중 백업은 자기 이름 브랜치에 커밋하고 push하면 됩니다.
  ```bash
  git add -A && git commit -m "wip: 좌석 선점 작업 중" && git push
  ```
  자잘한 `wip` 커밋은 main에 합칠 때 Squash로 하나로 묶입니다.
- 잠깐 다른 일을 할 때: `git stash` → 돌아와서 `git stash pop`
- 실험이 망했을 때 마지막 push 상태로: `git reset --hard origin/본인브랜치`
- **웹·앱 Claude를 쓸 때**는 시작할 때 "`DongHyeon` 브랜치에서 작업하고 거기에 push해" 처럼 브랜치를 꼭 말해 줍니다. 말하지 않으면 `claude/...` 브랜치를 새로 만들 수 있습니다 (GitHub 규칙으로 막혀 있어 push가 실패함).
- PC의 Claude Code는 `.claude/settings.json`이 새 브랜치 만들기 명령을 막아 둡니다.

## 개인 설정 파일

아래 파일은 사람마다 다르므로 `.gitignore`로 막아 두었습니다. 레포에 올리지 않습니다.

| 파일 | 용도 |
|---|---|
| `CLAUDE.local.md` | 나만 쓰는 Claude 지시 (팀 공용 규칙은 `CLAUDE.md`) |
| `.claude/settings.local.json` | 나만 쓰는 Claude Code 설정 |
| `application-local.yml` | 내 DB 비밀번호·포트 |
| `.env` | 비밀값 (키 이름만 `.env.example`로 공유) |
| `docker-compose.override.yml` | 내 PC에서만 바꾸는 포트·볼륨 |

## 문서 쓰는 법

- **트러블슈팅**: 문제를 해결하면 바로 `docs/templates/troubleshooting.md`를 복사해 `docs/본인이름/troubleshooting/YYYYMMDD-제목.md`로 씁니다. 문제 → 원인 → 해결 → 수치 순서. 수치가 아직 없으면 "측정 예정"으로 두고 나중에 채웁니다. 3주차에 몰아 쓰지 않기 위한 규칙입니다.
- **기능 문서**: 기능을 main에 합칠 때 `docs/templates/feature-note.md`를 복사해 `docs/본인이름/features/기능이름.md`로 짧게 씁니다. 한 줄 요약, 어떻게 동작하나, 왜 이렇게 했나, 주의할 점. 다른 팀원이 1~2분 안에 이해할 수 있으면 충분합니다.
- **개인 기여**: `docs/본인이름/contribution.md`에 설계 결정(왜 이렇게 했는지, 대안, 감수한 단점)과 수치를 그때그때 추가합니다.

## 스키마를 바꾸는 방법

**편집기 화면에서 고친 경우**

1. `docs/erd/fairrail-erd.html`을 브라우저로 열고 고칩니다. 고친 내용은 그 브라우저에만 저장됩니다.
2. "내보내기 → JSON 내보내기 → 복사" 후 `docs/erd/exports/이름-날짜.json`으로 저장해 커밋합니다.
3. **ERD 반영 담당자(강동균)**가 Claude Code에 "docs/erd/exports/이름-날짜.json 반영해줘"라고 요청합니다. 다른 팀원은 HTML을 직접 고치지 않습니다 (패치 번호 충돌 방지). Claude가 아래 명령을 차례로 실행하고 HTML에 패치를 붙입니다.

```bash
node tools/erd-diff.js docs/erd/fairrail-erd.html docs/erd/exports/이름-날짜.json   # 차이 → 패치 코드
node tools/check-erd.js docs/erd/fairrail-erd.html                              # 검사 + DDL (FAIL 0이어야 커밋)
node tools/erd-md.js docs/erd/fairrail-erd.html > docs/FairRail_ERD.md           # 종합 문서 갱신
```

**Claude에게 말로 요청하는 경우** ("member에 컬럼 추가해줘" 등, ERD 반영 담당자만)

Claude가 HTML에 바로 패치를 쓰므로 `erd-diff`는 필요 없고 검사와 종합 문서 갱신만 합니다.

여러 명의 JSON은 한 번에 하나씩, 내보낸 순서대로 반영합니다. 새 HTML을 받으면 덮어쓰고 열면 되고, 각자 브라우저에 고쳐 둔 내용은 유지됩니다.

필요한 것: Node.js (설치할 패키지 없음).
