# 제자리

명절 열차 공정 예매 시스템 팀 프로젝트 (5명 · 3주). Spring Boot · Kafka · Redis · MongoDB · Oracle · Python.

## 시작 순서

1. 규칙·ERD·문서가 main에 올라감 (완료)
2. 조영준: Docker Compose(Oracle·MongoDB·Redis·Kafka)와 Spring Boot 뼈대를 **main에 직접** 올림 (처음 한 번만 예외)
3. 팀장 공지 후 나머지 팀원이 main에서 자기 이름 브랜치를 만듦 → 뼈대가 이미 들어 있음
4. 이후 main이 바뀌면 각자 브랜치에서 `git pull origin main`

## 처음 한 번 할 일

```bash
git clone https://github.com/BrainSaver/jejari.git
cd jejari
git config commit.template .gitmessage   # 커밋 메시지 틀
git config core.quotepath false          # 한글 파일 이름이 깨져 보이지 않게
git switch DongHyeon                     # 본인 이름 브랜치로 이동 (이미 만들어져 있음)
```

## 백업과 Claude 사용

- **새 브랜치를 만들지 않습니다.** 작업 중 백업은 자기 이름 브랜치에 커밋하고 push하면 됩니다.
  ```bash
  git add -A && git commit -m "wip: 좌석 선점 작업 중" && git push
  ```
  자잘한 `wip` 커밋은 main에 합칠 때 Squash로 하나로 묶입니다.
- 잠깐 다른 일을 할 때: `git stash` → 돌아와서 `git stash pop`
- 실험이 망했을 때 마지막 push 상태로: `git reset --hard origin/본인브랜치`
- **웹·앱 Claude를 쓸 때**는 시작할 때 "`DongHyeon` 브랜치에서 작업하고 거기에 push해" 처럼 브랜치를 꼭 말해 줍니다. 말하지 않으면 `claude/...` 브랜치를 새로 만들 수 있습니다 (GitHub 규칙으로 막혀 있어 push가 실패함).
- PC의 Claude Code는 `.claude/settings.json`이 새 브랜치 만들기 명령을 막아 둡니다.

## 문서 사이트 (jejari.pages.dev)

- 기능설계서, DB설계·ERD, 화면설계, 기획서, 동시성 문서를 웹에서 봅니다. 보기는 누구나 됩니다.
- 고치려면 오른쪽 위 로그인 → 내 이름 → 숫자 4자리 PIN. **처음 들어온 사람이 PIN을 정합니다.** 잊으면 팀장(길동현)이 초기화합니다.
- 섹션(##) 단위로 고치고 저장하면 **내 이름 브랜치에 커밋**됩니다. 커밋 메시지는 AI가 써 주고 고칠 수 있습니다.
- 다 고쳤으면 위쪽 "main에 합치기"를 누릅니다. 충돌이 없으면 바로 main에 들어갑니다.
- 사이트에서 저장하면 원격 브랜치가 앞서 나가므로, PC에서 작업하기 전에 `git pull` 합니다.
- ERD는 사이트 안 편집기에서 고친 뒤 "내 수정 저장"을 누르면 `docs/erd/exports/이름-날짜.json`으로 커밋됩니다. 스키마 반영은 지금처럼 강동균이 합니다.

## 개인 설정 파일

아래 파일은 사람마다 다르므로 `.gitignore`로 막아 두었습니다. 레포에 올리지 않습니다.

| 파일 | 용도 |

| `CLAUDE.local.md` | 나만 쓰는 Claude 지시 (팀 공용 규칙은 `CLAUDE.md`) |

## 문서 쓰는 법

- **트러블슈팅**: 문제를 해결하면 바로 `docs/templates/troubleshooting.md`를 복사해 `docs/본인이름/troubleshooting/YYYYMMDD-제목.md`로 씁니다. 문제 → 원인 → 해결 → 수치 순서. 수치가 아직 없으면 "측정 예정"으로 두고 나중에 채웁니다. 3주차에 몰아 쓰지 않기 위한 규칙입니다.
- **개발일지**: 작업한 날마다 `docs/templates/devlog.md` 틀로 `docs/본인이름/devlog/YYYYMMDD-제목.md`를 씁니다. 한 일, 어떻게 했나, 왜 그렇게 했나, 막힌 점, 다음 할 일. 문서 사이트(jejari.pages.dev) "팀원 문서"에서 바로 쓰고 볼 수 있습니다. 보고서·시연 페이지처럼 HTML로 만든 문서도 같은 폴더에 `.html`로 두면 사이트에서 그대로 보입니다 (사이트의 "+ HTML" 버튼으로 붙여 넣거나 파일을 올릴 수 있음).
- **기능 문서**: 기능을 main에 합칠 때 `docs/templates/feature-note.md`를 복사해 `docs/본인이름/features/기능이름.md`로 짧게 씁니다. 한 줄 요약, 어떻게 동작하나, 왜 이렇게 했나, 주의할 점. 다른 팀원이 1~2분 안에 이해할 수 있으면 충분합니다.
- **개인 기여**: `docs/본인이름/contribution.md`에 설계 결정(왜 이렇게 했는지, 대안, 감수한 단점)과 수치를 그때그때 추가합니다.

## 스키마를 바꾸는 방법

**편집기 화면에서 고친 경우**

1. `docs/erd/jejari-erd.html`을 브라우저로 열고 고칩니다. 고친 내용은 그 브라우저에만 저장됩니다.
2. "내보내기 → JSON 내보내기 → 복사" 후 `docs/erd/exports/이름-날짜.json`으로 저장해 커밋합니다.
3. **ERD 반영 담당자(강동균)**가 Claude Code에 "docs/erd/exports/이름-날짜.json 반영해줘"라고 요청합니다. 다른 팀원은 HTML을 직접 고치지 않습니다 (패치 번호 충돌 방지). Claude가 아래 명령을 차례로 실행하고 HTML에 패치를 붙입니다.

```bash
node tools/erd-diff.js docs/erd/jejari-erd.html docs/erd/exports/이름-날짜.json   # 차이 → 패치 코드
node tools/check-erd.js docs/erd/jejari-erd.html                              # 검사 + DDL (FAIL 0이어야 커밋)
node tools/erd-md.js docs/erd/jejari-erd.html > docs/Jejari_ERD.md           # 종합 문서 갱신
```

**Claude에게 말로 요청하는 경우** ("member에 컬럼 추가해줘" 등, ERD 반영 담당자만)

Claude가 HTML에 바로 패치를 쓰므로 `erd-diff`는 필요 없고 검사와 종합 문서 갱신만 합니다.

여러 명의 JSON은 한 번에 하나씩, 내보낸 순서대로 반영합니다. 새 HTML을 받으면 덮어쓰고 열면 되고, 각자 브라우저에 고쳐 둔 내용은 유지됩니다.

필요한 것: Node.js (설치할 패키지 없음).

## 테스트 돌리는 법

`.env`는 docker compose용이고 **Gradle은 읽지 않습니다.** 앱·테스트는 실제 환경변수로 읽으므로
통합 테스트 전에 내보내야 합니다. 안 하면 회원 인증 통합 테스트가 `PiiCipher` 빈이 없다며 실패합니다.

```bash
docker compose up -d
set -a && . <(grep -E "^JEJARI_(ENC|PEPPER|HMAC)" .env) && set +a
LC_ALL=C.UTF-8 TZ=Asia/Seoul ./gradlew test        # 단위 (인프라 없이도 됨)
LC_ALL=C.UTF-8 TZ=Asia/Seoul ./gradlew infraTest   # 통합 (@Tag("infra"), Docker 필요)
# 처음이면 천천히 따라 하는 안내: docs/강동균/통합테스트-돌리는-법.md
```

- `LC_ALL=C.UTF-8` — 없으면 한글 테스트 이름이 `bad filename …$회피.class`로 컴파일 실패
- `TZ=Asia/Seoul` — 없으면 기동 점검이 JVM 시간대를 UTC로 보고 거부해 통합 테스트가 전부 멈춤

> **앱(bootRun)을 끄고 돌리세요.** 통합 테스트와 앱이 같은 Oracle·Redis·Kafka를 보기 때문에,
> 앱이 떠 있으면 앱의 만료 스캐너가 테스트의 좌석 선점을 먼저 만료시키고 outbox 릴레이가
> 테스트 이벤트를 먼저 가져갑니다. **실행할 때마다 다른 테스트가 깨져서 원인을 짐작하기 어렵습니다.**
> 지금은 테스트가 시작하자마자 알려 주고 멈춥니다 (`NoRunningApp`).
> 일부러 띄운 채 돌려야 하면 `-Djejari.test.allow-running-app=true`.
> 자세한 내용: `docs/강동균/troubleshooting/20261117-앱이-떠-있으면-통합테스트가-조용히-깨짐.md`

**스키마를 바꾼 뒤에는** Oracle 볼륨을 다시 만들거나(`docker compose rm -sf oracle &&
docker volume rm jejari_oracle-data && docker compose up -d oracle`), 데이터를 지키고 싶으면
`db/patch/`의 델타를 실행합니다. 볼륨이 묵으면 테이블은 다 있는데 **시퀀스만 없어** 통합 테스트가
무더기로 깨집니다 (`SELECT COUNT(*) FROM user_sequences`로 확인).

## 락 방식 비교 돌려 보기 (측정 웹 러너)

좌석 선점을 **비관적 락 · 낙관적 락 · Redis 1차** 세 가지로 실제로 재는 도구입니다 (동시성 §17.1).
버튼을 누르면 그 자리에서 k6가 돕니다.

- **결과만 보려면** 설치가 필요 없습니다 → 문서 사이트의 `강동균 / 기능문서 / 락비교-결과`
- **직접 돌리려면** 아래 3단계. 추가 설치는 k6 하나입니다

```bash
winget install --id GrafanaLabs.k6 -e     # 한 번만. 패키지 ID가 Grafana.k6 가 아닙니다
                                          # mac: brew install k6

docker compose up -d                      # 1) 인프라

# 2) 앱 — 개발 모드여야 벤치 API가 생깁니다
set -a && . <(grep -E "^JEJARI_(ENC|PEPPER|HMAC)" .env) && set +a
LC_ALL=C.UTF-8 TZ=Asia/Seoul ./gradlew bootRun   --args="--jejari.dev-mode=true --jejari.queue.dev-on-sale-runs=9001"

# 3) 러너 — 다른 터미널에서 (의존성 없음, npm install 불필요)
node bench/web/server.js                  # → http://localhost:8099
```

사전 점검 4개(k6 · 앱 · 개발 모드 · 스크립트)가 전부 초록이면 `▶ 측정 시작`.
빨간 칩 옆에 원인이 한 줄로 뜹니다. 전체 3시나리오 × 3전략 × 3회차는 3~4분, 결과는
`bench/results/`에 쌓입니다(gitignore).

> **서버에 올리지 않습니다.** 벤치 API는 개발 모드에서만 열리고 인증이 없어, 공인 IP에 노출하면
> 누구나 실험 테이블을 건드릴 수 있습니다. 수치도 "앱·DB·k6가 한 PC"를 전제로 한 값이라
> 서버에 올리면 기존 측정과 비교가 깨집니다.

자세한 설명: `bench/README.md`, `docs/강동균/features/락비교-k6-재측정.md`
