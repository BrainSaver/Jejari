## 0. 30초 설명

**제자리**는 명절 열차 예매처럼 짧은 시간에 요청이 몰릴 때 **좌석을 중복 없이, 공정한 순서로** 파는 가상 철도 예매 시스템입니다.
5명이 3주 동안 Spring Boot 백엔드로 만들었고, 기능을 많이 늘리기보다 세 가지 기술 문제를 깊게 풀고 수치로 검증했습니다.

1. **몰림**: Redis 대기열로 입장 인원을 조절
2. **동시성**: 같은 좌석을 수백 명이 동시에 눌러도 1명만 성공 (Redis 1차 + Oracle 최종 판정)
3. **신뢰성**: 결제 실패·서버 장애가 나도 좌석·돈·이벤트가 어긋나지 않음 (Saga · Outbox · 멱등성)

여기에 **공정성**을 더했습니다. 행동 로그로 봇·암표 의심 사용자의 위험 점수를 매겨 대기열·취소표 순서를 뒤로 미루고, 관리자가 "왜 의심되는지"를 타임라인·화면 녹화로 되돌아볼 수 있게 했습니다. ← **이 부분이 내(D) 담당**

**배경 숫자** (기획서): 코레일 2026 추석 웹 서버 11 → 60대 증설 / 2026 설 매크로 비정상 접근 4만 2,695건 차단 / 2025 명절 재판매 못 한 표 66만 4천 장(2021년의 5.3배).

## 2. 기술 스택과 "왜 이걸 썼나"

|---|---|---|
| **Spring Boot + JPA** | REST API, 트랜잭션 | 팀 공통 역량. 경쟁이 심한 곳은 JPA 대신 네이티브 조건부 UPDATE |
| **Oracle** | 예약·결제·좌석·회원 (돈과 좌석의 **최종 판정**) | PK·UNIQUE·CHECK·조건부 UPDATE로 "절대 틀리면 안 되는 것"을 지킴 |
| **Redis** | 대기열, 좌석 선점 1차 판정(Lua), 매수 한도, 멱등 키, 위험 점수 캐시 | 빠름. 대부분의 패배자를 DB에 오기 전에 돌려보냄 |
| **Kafka** | 예약 이벤트(Outbox 발행), 행동 로그, 녹화 이벤트 | 후속 처리(좌석 반환·취소표·알림·위험 점수)를 비동기로, 순서 보장(같은 키 = 같은 파티션) |
| **MongoDB** | 행동 로그, 화면 녹화, 모델 점수 | 대량·스키마 유연, TTL로 자동 삭제(180일) |
| **Python** | 가상 데이터 생성, 이상 탐지 모델(Isolation Forest·부스팅) | 데이터 분석 생태계 |
| **k6 / Playwright** | 부하 테스트·봇 시뮬레이션 / 진짜 브라우저 봇 | 탐지율·오탐률의 "정답 라벨" |

## 3. 예매 한 건의 전체 흐름

```
가입·본인인증 → 로그인 → 열차 조회 → 대기열 진입(위험 점수만큼 뒤로)
 → 입장 토큰 → 좌석 선점(HOLD, 결제 기한 시작) → 결제 시작(기한 연장)
 → PG 승인 → CONFIRMED                                   ↘ 실패·기한 초과 → EXPIRED (좌석 복구)
 → (나중에) 확정 취소 → 수수료 계산·환불 → 좌석을 취소표 대기자에게 먼저 제안
```

**예약 상태** (`reservation.status`)

```
HOLD ─결제 시작→ PAYMENT_PENDING ─승인→ CONFIRMED ─취소→ CANCELED
  │                    └─실패→ EXPIRED
  ├─기한 초과·재선점→ EXPIRED
  └─결제 전 취소→ CANCELED
```

허용 안 된 전이(예: CANCELED → CONFIRMED)는 `WHERE status = '현재 상태'` 조건부 UPDATE가 **0행**이 되어 저절로 막힙니다. 모든 전이는 `reservation_history`에 남습니다.

## 4. 꼭 알아야 할 핵심 개념 10개

원천: `docs/concurrency.md` (§ 번호)

### 4.1 판정 계층: Redis는 1차, Oracle이 최종 (§0.1)
- Redis가 빠르게 거절(좌석 경쟁·매수 한도·중복 요청) → 패배자는 **DB 쓰기 0건**
- Redis가 통과시켜도 DB가 거절하면 거절. 반대로 "DB는 되는데 Redis가 막는" 일이 남지 않게 보상·자가 복구 장치를 둠
- 결과: 같은 좌석 100명 → 1명 성공, DB 왕복 **101 → 1회** (락 방식 C)

### 4.2 좌석 선점 (§2)
1. 멱등 키 확인 → 2. Redis 매수 한도 `limit_incr.lua` → 3. 마감 시각 `:d` 계산 → 4. `hold.lua`로 좌석 키 `seat:hold:{run}:{seat}:{seg}`를 `SET NX`(하나라도 남이 갖고 있으면 전부 실패)
5. 승자만 DB 트랜잭션: reservation · seat_inventory · reservation_seat · purchase_counter · history · saga · outbox를 **한 트랜잭션**에
- 롤백되면 Redis 키를 compare-and-delete(내 값일 때만 지움)로 되돌림

**락 방식 비교** (B): A 비관적 락 / B 낙관적 락 / C Redis + DB. 1석 100명에서 C가 DB 왕복 1회로 압도적. TPS는 측정 조건에 따라 B·C가 편차 안이라 "승부 없음" — **정직하게 말할 수 있는 결과**.

### 4.3 멱등성 (§1)
- 버튼을 누를 때마다 클라이언트가 UUID `idempotency_key` 생성, 재시도는 같은 키
- Redis `SET idem:{member}:{key} NX` + DB `UNIQUE(member_id, idempotency_key)` 이중 방어
- 결제도 같은 방식 + "예약당 승인 1건" 유니크 인덱스 → **중복 결제 0건**

### 4.4 마감 시각은 한 곳이 원천 (§0.2, §0.7)
- `reservation.pay_deadline_at`이 원천. `seat_inventory.hold_expires_at`, Redis 키 만료, `saga_instance.timeout_at`, `waitlist.offer_deadline_at`은 **같은 값 복사**
- 마감은 앱 시계로 한 번 계산. Oracle OS·JVM·DB 세션 시간대 모두 Asia/Seoul 고정(틀리면 기동 거부)
- **유예 10초**: 마감 때 Redis 키가 바로 사라지면 새로고침하는 봇이 대기자보다 먼저 좌석을 가져감(측정 0.37~5.15초 틈) → 키만 10초 늦게 지우고 그 사이 스캐너가 대기자에게 넘김. 결제 가능 시간은 DB 기준이라 늘지 않음

### 4.5 Saga (결제 실패 시 좌석 복구)
- 분산 트랜잭션을 하나로 묶을 수 없으니, 단계별로 진행하고 실패하면 **보상 작업**(좌석 해제·한도 반환)을 실행
- `saga_instance`가 현재 단계와 타임아웃을 기록. 만료 스캐너가 기한 지난 것을 정리
- PG 결과를 모르면(타임아웃) 바로 실패 처리하지 않고 조회 스캐너가 다시 확인 (`rehold.lua`로 좌석 유지)

### 4.6 Outbox (이벤트 유실 방지) (§11)
- 문제: DB 커밋은 됐는데 Kafka 발행 전에 서버가 죽으면 이벤트 유실. 반대로 발행 후 롤백되면 유령 이벤트
- 해결: 상태 변경과 **같은 트랜잭션**에 `outbox_event` 행을 INSERT → 릴레이가 읽어 Kafka로 발행
- 릴레이는 `shard_no`로 샤드를 나눠 맡고, 샤드 안에서 순서대로, 멱등 프로듀서로 발행

### 4.7 Inbox (중복 소비 방지) (§12)
- Kafka는 "최소 한 번" 전달 → 같은 메시지가 두 번 올 수 있음
- 소비자가 `processed_event(consumer_group, event_id)`에 INSERT, 중복이면 PK 위반 → 이미 처리한 것
- 처리 못 한 메시지는 버리지 않고 **격리 보관함(DLQ)** 에 두고 다시 넣을 수 있게

### 4.8 Kafka 키 = reservation_id
- 같은 예약의 이벤트(선점 → 결제 → 확정 → 취소)가 같은 파티션 → **순서 보장**
- run_id(운행)로 키를 잡으면 인기 열차 하나에 쏠림 → 비교 실험 대상
- 토픽: `jejari.reservation`(12), `jejari.waitlist`(6), `jejari.behavior`(12, 키 ci_hash), `jejari.replay`(6)

### 4.9 락 순서 = 데드락 방지 (§0.4)
- 예약에 딸린 행은 **reservation 행을 먼저** 잠근 뒤에만 바꿈
- 여러 예약은 `reservation_id` 오름차순으로 **한 건씩** (`IN (...) FOR UPDATE`는 순서를 보장 못 함)
- 외부 호출(PG, Kafka)은 **트랜잭션 밖에서** — 락을 쥔 채 남의 응답을 기다리지 않음

### 4.10 매수 제한 (§10)
- 1회 9매, 운행별·하루·명절 행사별 한도. 사람 단위 = **CI 해시**(계정을 여러 개 만들어도 같은 사람)
- Redis가 1차, `purchase_counter` 조건부 UPDATE가 최종. Redis가 틀어지면 DB와 대조해 자가 복구

## 5. 내 파트 (D) 자세히

### 5.1 회원가입·모의 본인인증·로그인 (AUTH-01~03)
- 같은 사람 = 같은 **CI**(이름+휴대폰 → HMAC-SHA256). CI가 매수 제한·위험 점수의 "사람" 단위
- 인증 결과는 암호화 토큰으로 2단계(인증 → 가입) 전달
- 비밀번호 Argon2id, 이메일 중복은 미리 SELECT하지 않고 **UNIQUE 위반으로 판정**(경쟁 조건 없음)
- 로그인 5회 실패 15분 잠금, 관리자·회원 세션 쿠키 분리

### 5.2 개인정보 암호화 (`common/pii`)
| 무엇 | 방법 | 이유 |
|---|---|---|
| 휴대폰 등 복호화 필요 | **AES-256-GCM** + 키 버전(`enc_key_id`), **행 ID를 AAD로 묶음** | 암호문을 다른 행에 복사해 붙여도 복호화 실패 |
| 식별(CI·카드·기기·IP) | **HMAC-SHA256** | 같은 값끼리 비교만 필요, 원문 복원 불가 |
| 비밀번호 | Argon2id | 느린 해시로 무차별 대입 방어 |
| 리프레시·재설정 토큰 | SHA-256만 저장 | DB가 털려도 토큰 재사용 불가 |
| 관리자 화면 | 마스킹, 해제는 권한 + 기록 | 최소 열람 |

키가 없으면 앱이 **기동 실패**(fail-closed). 목표 "평문 개인정보 0건".

### 5.3 행동 로그 (RISK-01)
- 각 API에 `behaviorLog.mark()` 한 줄 → Kafka `jejari.behavior` → `behavior-sink` → MongoDB `insertMany`
- 이벤트 종류: 조회, 대기열 진입, 좌석 선점, 결제, 취소 등. **실패 요청(409 등)도 기록** (봇은 실패를 많이 함)
- `event_id` 유니크 인덱스로 재전달 중복 저장 방지, `expire_at` + TTL로 180일 뒤 자동 삭제
- 처리 시간 `elapsed_ms`도 남김 → "응답 받은 뒤 다음 행동까지"를 재기 위해 (아래 5.4)
- Kafka가 멈춰도 디스크 버퍼·회로 차단으로 유실 0 (B가 보강)

### 5.4 규칙 기반 위험 점수 (RISK-02~04)
**한 줄**: CI·결제 수단·기기마다 신호를 모아 규칙 배점을 더하고(최대 100), 지난 점수는 반감기 30일로 줄여 **둘 중 큰 값**이 최종 점수. 80 이상이거나 핵심 규칙이 걸리면 의심 케이스를 엶.

| 규칙 | 보는 것 | 케이스 |
|---|---|---|
| FAST_CLICK | 200ms 미만 요청 간격 **개수** | ✅ |
| SAME_SEAT_RETRY | 같은 좌석 선점 실패 반복 | ✅ |
| CANCEL_AFTER_PAY | 구매 후 30분 안 취소 (암표 되팔기 신호) | ✅ |
| MULTI_ACCOUNT_SYNC | 60초 안에 여러 계정이 선점 (한 기기에서 계정 전환 15초 안) | ✅ |
| REGULAR_INTERVAL | 간격이 너무 일정함 (변동계수 ≤ 0.05) | ✅ |
| LINEAR_MOUSE | 마우스 순간이동·직선·등속 (녹화) | ✅ |
| HEADLESS_HOLD | 좌석 잡은 세션에 화면 녹화 없음 / 손 움직인 흔적 없음 | ✅ |
| INHUMAN_STEP | 좌석표 응답 → 선점, 선점 응답 → 결제가 1초 미만 | ✅ |
| NO_SEARCH_ENTRY | 열차 조회 없이 대기열로 직행 | 점수만 30 |
| 그 밖 (취소 비율, 출발 직전 취소, 대량 구매, 연결 계정, 신규 계정) | 보조 신호 | 점수만 |

**등급**: 정상 0~29 · 경고 30~79 · **위험 80~** (= 케이스 · 결제 차단 기준과 같게. 따로 두면 "위험인데 결제는 됨"처럼 어긋남)

**점수가 쓰이는 곳**
- 대기열: 1점 = 1초 뒤로 (A)
- 취소표 대기: 1점 = **3분** 뒤로 (대기가 몇 시간~며칠이라 1초 단위면 의미 없음)
- 80 이상: 의심 케이스 + 결제 차단, 70부터 화면 녹화를 자세히

**1분 배치**: 새 신호가 생긴 대상만 Redis `risk:dirty`에 넣고, 매분 `RENAMENX`로 작업 목록을 떼어 한 대만(락) 계산 → Oracle `risk_score` 저장 + Redis `risk:*` 캐시. 전체 회원을 매번 계산하지 않음.

**봇이 점수를 피하는 길 막기 (면접 포인트)**
- **평균이 아니라 개수**를 셈 → 빠른 클릭 사이에 느린 요청 10만 건을 섞어도 걸림
- 모든 규칙이 단조 증가 → "더 나쁘게 했더니 점수가 내려감"이 무작위 2만 번 시험에서 0번
- 쉬어도 반감기로만 줄어듦 (1시간 쉬면 90 → 89.9)
- NaN·음수·잘못된 설정은 예외 → 이전 정책 유지 (탐지가 조용히 꺼지지 않게)
- 근거 JSON엔 enum과 숫자만 (주입 방지)

**사람을 지키는 장치**: 보조 신호만으론 케이스 안 엶(정상 다구매 고객 보호), 터치·키보드는 마우스 규칙에서 제외, 녹화가 고장 나면 "녹화 없음"을 세지 않음, 한 번은 우연이라 2번부터, 선점 버튼 두 번 누름은 빠른 단계에서 제외, 가족이 한 컴퓨터를 쓰는 경우는 15초 기준.

### 5.5 의심 구간 타임라인·케이스 판정 (ADM-04~06) — 우리 차별점
- 위험 사용자 목록(마스킹) → 케이스 상세 → 이벤트 타임라인 + 의심 구간 하이라이트 + 발동 규칙 + 점수 변화
- 판정: OPEN → REVIEWING → **CONFIRMED**(위험 확정, RESTRICTED·BANNED 조치) 또는 **DISMISSED**(오탐 → ACTIVE 복구, 같은 증거로 다시 안 잡히게 clearedAt 이후만 봄)
- **화면 녹화 재생**(ADM-11): 녹화기 → Kafka → Mongo → 재생기. 마우스 궤적·클릭·"무엇을 했나". **입력값은 저장하지 않음**, 케이스 단위로만 열람
- "숫자만 보여주지 않고 CCTV처럼 근거를 보여준다" → 관리자가 오탐을 가려냄

### 5.6 확정 취소·환불 (CNL-01~04)
- 미리보기와 실제 취소가 **같은 수수료 계산기**. 서버가 취소 시점에 다시 계산 (클라이언트 값 안 믿음)
- 한 트랜잭션: reservation 잠금 → 수수료 계산 → CONFIRMED → CANCELED → 좌석 행 삭제·카운터 감소 → cancellation·outbox 기록. **환불 PG 호출은 커밋 뒤**
- 좌석 키는 `REOFFER:R`로 남겨 **대기자 먼저**
- 환불 실패는 재시도 배치(CNL-03), 재판매 여부 집계(CNL-04), 관리자 강제 취소(ADM-07, 수수료 면제 선택), 단체 위약금

### 5.7 취소표 대기 (WL-01~03)
- 신청: 같은 운행 1건, 전체 3건까지. 매진일 때만. RESTRICTED 회원은 신청 불가
- 순서 = `priority_at` = **신청 시각 + 위험 점수 × 3분** (신청 때 한 번 계산)
- 좌석이 풀리면 `seat-release` 소비자가 `FOR UPDATE SKIP LOCKED`로 다음 대기자를 잡아 **그 사람 명의로 선점**(제안) → 기한 안 결제하면 확정, 아니면 다음 대기자
- 한도에 걸린 대기자는 SKIPPED, 맞는 대기자가 없으면 일반 판매로

### 5.8 가상 데이터·외부 데이터
- DATA-02: 가상 회원 1,000명(정상 910 + 봇 90) 예매·행동 생성 → 탐지율 100%(90/90), 오탐 0%(0/910)
- DATA-04: Kaggle 호텔 예약 취소 11만 9천 건 분석 → "예약 시점·이력과 취소의 관계"를 반복 취소 규칙의 근거로

## 10. 예상 질문과 답

**Q. 왜 Redis만으로 좌석을 판정하지 않나요?**
A. Redis는 장애·보상 유실로 틀릴 수 있어서 빠른 1차 판정만 맡깁니다. 돈과 좌석은 Oracle의 PK·조건부 UPDATE가 최종입니다. 대부분의 패배자가 Redis에서 걸러져 DB 왕복이 101회에서 1회로 줄었습니다.

**Q. 비관적 락이 아니라 왜 조건부 UPDATE인가요?**
A. 상태 전이를 `WHERE status = '현재'`로 하면 영향 행 수로 "내가 먼저였나"를 알 수 있어 락을 오래 쥐지 않습니다. 0행이면 다른 트랜잭션이 먼저 처리한 것이므로 뒤의 부수 작업(카운터 감소, 이벤트)을 하지 않습니다.

**Q. Outbox 없이 커밋 뒤에 Kafka로 보내면 안 되나요?**
A. 커밋과 발행 사이에 서버가 죽으면 이벤트가 사라집니다. 그러면 좌석이 대기자에게 안 넘어가거나 환불이 안 됩니다. 같은 트랜잭션에 outbox 행을 남기면 커밋된 것만, 반드시 한 번 이상 발행됩니다. 중복은 소비자 Inbox가 거릅니다.

**Q. 위험 점수가 틀리면 정상 사용자가 피해를 보지 않나요?**
A. 점수로는 막지 않고 **순서만 뒤로** 미룹니다(1점 = 대기열 1초). 막는 건 관리자가 근거(타임라인·녹화)를 보고 판정한 경우뿐이고, 오탐이면 DISMISSED로 바로 복구됩니다. 보조 신호만으론 케이스를 열지 않고, 2차 대회 진짜 사람 27계정 오탐 0을 확인했습니다.

**Q. 왜 머신러닝이 아니라 규칙인가요?**
A. 규칙은 "왜 의심되는지" 설명할 수 있어 관리자 검토와 맞습니다. 모델도 만들었는데, 규칙이 못 잡는 봇(botc)을 잡지만 사람 오탐이 높아서 판정이 아닌 보조 의견으로만 씁니다. 둘은 서로 다른 봇을 잡습니다.

**Q. 봇이 점수를 알고 피하면요?**
A. 평균이 아니라 개수로 세서 정상 행동을 섞어도 점수가 안 내려가고, 쉬어도 반감기로만 줄어듭니다. 그리고 "봇이 사람과 다를 수밖에 없는 성질"(화면 없이 선점, 사람 손보다 빠른 단계)을 봅니다. 사람 속도로 하면 봇을 쓰는 이점이 사라집니다.

**Q. 취소표 대기에 위험 점수를 넣은 이유는?**
A. 대기열에서 뒤로 밀린 봇이 취소표 대기로 우회할 수 있었습니다. 대기는 몇 시간~며칠이라 대기열과 같은 1초 단위로는 의미가 없어서 1점 = 3분(80점 = 4시간)으로 잡았습니다. 오탐된 사람도 몇 시간 뒤면 차례가 옵니다.

**Q. 개인정보는 어떻게 지켰나요?**
A. 비교만 필요한 건 HMAC(원문 복원 불가), 복호화가 필요한 건 AES-256-GCM에 행 ID를 AAD로 묶어 복사·붙여넣기 공격을 막았고, 키가 없으면 앱이 아예 뜨지 않습니다. 관리자 화면은 마스킹, 녹화는 입력값을 저장하지 않습니다.

**Q. 가장 어려웠던 점은?**
A. 1차 봇 대회에서 케이스 0건이 나온 것. 원인을 보니 "우리가 만든 봇"에만 맞춘 규칙이었고, 단계 속도에 서버 처리 시간이 섞이는 측정 버그도 있었습니다. 봇이 피할 수 없는 성질로 규칙을 바꾸고 진짜 사람 데이터로 기준값을 다시 잡아 botb 6/6, 사람 오탐 0이 됐습니다.

**Q. 아직 못 한 것은?**
A. 진짜 사람 표본이 27계정으로 작고, 곡선 마우스를 흉내 내는 진짜 브라우저 봇은 규칙으로 못 잡습니다. 녹화 해상도를 올려 손 모양을 보는 것이 다음 과제입니다.

## 11. 용어 사전

| 용어 | 뜻 |
|---|---|
| CI | 본인인증으로 얻는 "같은 사람" 식별값. 여기선 HMAC 해시만 저장 |
| HOLD | 좌석을 잡았지만 결제 전 (결제 기한 있음) |

| Lua 스크립트 | Redis에서 여러 명령을 한 번에(원자적으로) 실행 |
| compare-and-delete | "값이 내 것일 때만 지운다" — 남의 선점을 지우지 않게 |
| SKIP LOCKED | 다른 트랜잭션이 잠근 행은 기다리지 않고 건너뜀 |
| 멱등 | 같은 요청을 여러 번 해도 결과가 한 번 한 것과 같음 |
| Saga | 여러 단계 작업에서 실패 시 앞 단계를 되돌리는 보상 흐름 |
| Outbox / Inbox | 이벤트를 DB에 같이 남겨 발행 보장 / 받은 이벤트 ID를 남겨 중복 처리 방지 |
| DLQ | 처리 못 한 메시지를 버리지 않고 모아 두는 곳 |
| app_policy | 임계값·TTL 같은 운영 설정 테이블. 코드에 하드코딩하지 않음 |
| fail-closed | 설정·키가 이상하면 "대충 동작"하지 말고 멈춤 |
| ERD v40 | 스키마 패치 버전. `docs/erd/jejari-erd.html`이 원본 |
