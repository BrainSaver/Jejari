## 어떻게 했나

- 위험 점수 흐름

  ```
  행동 로그 → SignalCollector(신호 집계) → RiskEngine(점수)
    → RiskScoreStore: Oracle MERGE ─커밋 뒤→ Redis risk:{CI|PAYMENT|DEVICE}:{hash}
    → 대기열이 읽어서 순번 뒤로 미룸 (캐시가 없으면 Oracle 직접 조회)
  ```

- 행동 로그 흐름

  ```
  컨트롤러에서 BehaviorLog.mark(type, runId, meta) 한 줄
    → 인터셉터가 요청 끝에 최종 응답 코드를 붙여 큐에 넣음 (요청은 기다리지 않음)
    → 전용 스레드가 Kafka 발행 (키 = 회원 ID)
    → 컨슈머가 형식 재검사·ci_hash 붙여 insertMany, event_id 중복은 무시
  ```

- 가입·로그인: 본인인증 토큰(1회용, Redis `GETDEL`) → 가입은 `member`·`member_credential`·`identity_verification` 한 트랜잭션 → 비밀번호는 pepper(HMAC) + Argon2id
- 검증은 실제 Oracle·Redis·MongoDB·Kafka 컨테이너로 통합 테스트

## 왜 이렇게 했나

- **캐시가 비면 안 된다(fail-closed)**: 대기열은 Redis에 점수 키가 없으면 0점으로 본다. 캐시를 날리면 봇이 깨끗한 사용자가 되므로 TTL을 두지 않고, 표시 키가 사라지면(Redis 재시작) 10분을 기다리지 않고 즉시 재동기화한다.
- **커밋 뒤에 Redis 기록**: 롤백된 점수가 캐시에 남지 않게.
- **암호문에 AAD로 위치를 묶음**: 테이블·컬럼·행 ID를 함께 묶어 남의 행 암호문을 내 행에 복사해 넣는 공격을 막는다. 16바이트 단위 패딩으로 길이도 숨김.
- **계정 존재를 드러내지 않음**: 없는 이메일도 같은 실패 횟수로 잠그고, 없는·탈퇴 계정은 더미 해시로 같은 시간이 걸리게 한다. 정지 안내는 비밀번호가 맞을 때만.
- **키가 하나라도 없으면 기능을 끔**: HMAC·암호화 키·pepper가 없을 때 약한 기본값으로 돌아가지 않는다.
- **회원 조회에 캐시 없음**: 정지·제한 조치가 다음 대기열 진입부터 바로 반영되게. 한 쿼리(UNION ALL)로 평균 2.4ms라 캐시가 필요 없었다.
- **취소표 패널티 1점 = 3분**: 봇은 매진 직후 신청하니 판매 첫날 오전 신청자 뒤로 보내고, 오탐된 정상 사용자도 몇 시간 뒤면 차례가 오도록 (80점 = 4시간).
- **행동 로그는 요청을 막지 않음**: 로그 때문에 예매가 느려지면 안 되므로 전용 스레드 + 5만 건 큐, 넘치면 버리고 개수만 센다.
- 감수한 단점: 큐가 넘치거나 앱이 갑자기 죽으면 행동 로그·로그인 시도 기록 일부가 사라질 수 있다 (분석용이라 허용).

## 막힌 점과 해결

- **동기화 표시 키 불일치**: 나는 `riskcache:synced_at`, 대기열은 `risk:meta:synced_at`을 읽고 있었다 → 대기열이 캐시를 안 믿고 Oracle로 빠지는데 그 구현이 없어 **모든 회원이 100점**이 됨 → 대기열의 `QueueKeys.RISK_SYNCED_AT` 상수를 그대로 쓰고 Oracle 조회 구현 추가. 옛 키로 되돌리면 통합 테스트 3개가 실패하는 것도 확인.
- **MongoDB가 끊기면 로그인 30초 멈춤**: 로그인 시도 기록을 요청 안에서 동기로 저장해 드라이버 기본 대기(30초)를 그대로 기다림 → 연결 대기 2초 + 비동기 저장. Mongo를 멈춘 상태에서 로그인 0.3초 확인.
- **전체 infraTest에서만 대기열 동시성 테스트 실패**: 통합 테스트 4개가 설정이 조금씩 달라 Spring 컨텍스트를 4개 띄워 메모리 부족 → 공통 애너테이션 `FullStackInfraTest`로 하나만 쓰게 함.
- **main 병합 뒤 대기열 E2E 3건 409**: 강동균 님의 실제 판매 중 운행 조회가 들어와 테스트용 가짜 운행보다 우선됨 → 시드의 상시 판매 운행(9001)을 쓰게 수정.
- **기존 Mongo 볼륨에 `event_id` 유니크 인덱스가 없어 중복 저장**: 컨슈머가 시작할 때 인덱스를 직접 보장.
- **재시도 때 정상 사용자가 FAST_CLICK에 걸림**: 클릭 간격을 저장 전에 기억해 재시도 시 간격 0이 됨 → 저장 성공 뒤에만 기억.
- 문서 충돌: 기능설계서(RESTRICTED 신청 불가)와 concurrency.md §9.3(신청 가능)이 병합 중 어긋나 있어 기능설계서 기준으로 통일.

## 배운 점

- 다른 파트와 키 이름을 맞출 땐 문자열을 따로 적지 말고 **상대 코드의 상수를 그대로 가져다 쓴다**. 오타 하나가 "전원 100점" 같은 조용한 장애가 된다.
- 요청 경로 안의 부가 기록(로그인 시도, 행동 로그)은 **그 저장소가 죽어도 본 기능이 멈추지 않게** 비동기로. 타임아웃 기본값(30초)을 믿으면 안 된다.
- 통합 테스트는 하나씩 돌리면 통과해도 전체로 돌리면 자원 문제로 깨질 수 있다. 합치기 전에 전체를 돌린다.
