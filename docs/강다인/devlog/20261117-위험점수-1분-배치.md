## 어떻게 했나

```
행동 로그 적재 ──────── CI·기기 ────┐
예약 확정·취소 이벤트 ─ CI·결제 수단 ─┼─SADD→ risk:dirty ─RENAMENX→ risk:dirty:work ─→ 1분 배치 (락 risk:batch:lock)
하루 넘게 다시 계산 안 한 점수 ─────┘
대상마다: 행동 로그(1일)·구매·취소(30일)·연결 계정 → 엔진 → 바뀌었으면 [점수·이력 저장 + 조건 넘으면 케이스·마커] 한 트랜잭션 → 커밋 뒤 캐시
```

| 대상 | 행동 신호 (Mongo) | 구매·취소 (Oracle) | 연결 계정 |
|---|---|---|---|
| CI | O | O (같은 CI 회원의 예약) | 같은 CI 회원 (탈퇴 포함) |
| 결제 수단 | - (행동 로그에 없음) | O (그 카드로 결제한 예약) | 그 카드를 등록한 회원 |
| 기기 | O | - (가족 공용 기기 오탐 방지) | 그 기기를 쓴 회원 |

| 케이스 조건 | 결과 |
|---|---|
| 이번 증거만으로 규칙 점수 ≥ 80 | `RISK_THRESHOLD` |
| 마커 규칙(FAST_CLICK·SAME_SEAT_RETRY·CANCEL_AFTER_PAY·MULTI_ACCOUNT_SYNC) 적중 | `RULE` |
| 감쇠한 이전 점수만 높음 / 같은 증거 재계산 / 이미 열린 케이스 있음 | 열지 않음 |

## 왜 이렇게 했나

- **바뀐 대상만 계산**: 매분 전체 회원을 계산하면 회원 수에 비례해 느려진다.
- **목록을 통째로 넘겨받기 (RENAMENX)**: 같은 집합에서 꺼내고 지우면 계산하는 사이 다시 들어온 표시가 지워져 새 신호를 놓친다. 계산 중에 앱이 죽어도 `work`가 남아 다음 배치가 이어서 한다.
- **이벤트 값을 믿지 않음**: 예약 이벤트에서는 예약 ID만 쓰고 해시는 Oracle에서 다시 읽는다 (남의 해시를 넣어 재계산 폭주시키는 것 방지).
- **inbox 생략**: 표시(SADD)는 몇 번 해도 결과가 같다.
- **표시 실패는 재시도**: 표시를 잃으면 점수가 안 바뀐다 (fail-closed).
- **CI 구매는 member_id로**: 쓰기 폭주 테이블 `reservation`에 인덱스를 새로 걸지 않고 `UNIQUE(member_id, idempotency_key)`를 탄다.
- **"취소 시 즉시 재계산"(미정 9)** = 다음 배치(최대 1분). 취소 응답이 느려지지 않는다.
- **케이스는 새 증거일 때만**: 엔진의 `openCase`는 감쇠한 이전 점수로도 켜진다. 그대로 쓰면 관리자가 닫은 케이스가 같은 증거로 매분 다시 열린다.
- **점수 저장과 케이스를 한 트랜잭션으로**: 따로 하면 케이스만 실패했을 때 다음 배치가 "바뀐 게 없다"며 영영 안 연다.
- **CLEARED는 PENDING으로 안 바꿈**: 풀면 엔진이 CLEAR 이전 증거까지 다시 센다.

## 막힌 점과 해결

- **매분 저장하면 감쇠가 멈춤** (설계 중 발견): `calculated_at`이 감쇠 기준인데, 매분 저장하면 1분 감쇠량(80점 기준 0.001점)이 소수 둘째 자리 반올림에 지워지고 기준 시각만 밀려 **점수가 영원히 안 줄어든다** (오탐된 정상 사용자가 계속 쓰면 영영 안 풀림).
  → 저장 조건 분리 (`shouldWrite`): 새 증거가 지배하면 값·근거가 바뀔 때만, 감쇠가 지배하면 1점 이상 내려갔거나 하루가 지났을 때만.
- **통합 테스트 기대값 2건이 틀림**: 같은 간격 30번은 REGULAR_INTERVAL(+15)까지 걸려 40점, 3계정 기기는 연결 계정 MID(10)라 50점. 엔진이 맞고 손계산이 틀림 → 기대값·근거 주석 수정.
- **ERD에 RISK-04용 시퀀스·제약이 없었음**: 요청 → 기다리는 동안 요청한 이름으로 코드 작성, 로컬 DB에만 임시 반영해 테스트. main에는 "케이스만 건너뛰기"로 안전하게 합침 → v19 반영 뒤 임시 코드 제거, 로컬 DB에 v19의 나머지 시퀀스 5개·인덱스 2개 추가.
- **trigger_detail은 200바이트**: VARCHAR2(200)은 바이트 단위(한글 약 66자) → UTF-8 바이트로, 4바이트 문자가 반쪽 나지 않게 자름.
- **직접 확인 스크립트가 처음엔 점수를 못 만듦**: ① Windows curl이 한글 이름을 깨뜨려 400 → 영문 이름 ② 좌석 배치도가 입장 토큰 없이 403이라 행동 로그가 안 남음 → 대기열 입장 단계 추가 ③ curl을 30번 따로 띄우면 한 번에 0.2초 넘게 걸려 빠른 클릭이 안 됨 → curl 하나로 `--next` 연속 요청 ④ 본인인증 IP 제한(시간당 10번) → 이유를 화면에 보여 주고 로컬 전용 `RESET_RATE=1`
- **PowerShell에서 안내 명령이 안 됨**: Git Bash 문법으로 적어서 → 안내 문서에 PowerShell 명령을 따로 적음 (`.\gradlew.bat bootRun`, `& "C:\Program Files\Git\bin\bash.exe" tools/risk-demo.sh bot`)
- **bootRun을 켠 채 전체 테스트를 돌려 10분 넘게 멈춤**: 앱이 테스트와 같은 Kafka 소비 그룹을 나눠 씀 → 앱을 끄고 실행. `bootRun`의 `80% EXECUTING`은 멈춘 게 아니라 앱이 떠 있는 상태.

## 배운 점

- 반올림해서 저장하는 값을 다음 계산의 기준으로 다시 쓰면 작은 변화가 계속 지워져 값이 멈출 수 있다. "언제 저장하나"도 설계 대상이다.
- 큐에서 꺼낸 뒤 지우는 방식은 "꺼낸 사이에 들어온 것"을 놓친다. 넘겨받기(RENAME)로 경계를 나눈다.
- 상태(감쇠 점수)에서 나온 신호는 매번 켜져 있다. 행동(케이스 생성)은 사건(새 증거)에 반응하게 해야 한다.
- 멱등한 작업이면 중복 처리 장치를 생략할 수 있다. 장치를 붙이기 전에 "두 번 해도 같은가"를 먼저 본다.
- 스키마가 아직 없을 때는 "기다리기"와 "깨진 채 합치기" 말고 **안전하게 기능 일부만 끄고 합치기**가 있다. 반영되면 임시 코드를 바로 지운다.
- 테스트가 통과해도 **사람이 직접 보고 확인할 방법**이 있어야 한다. 데모 스크립트가 오히려 실제 흐름의 함정(입장 토큰, IP 제한, OS 차이)을 드러냈다.
