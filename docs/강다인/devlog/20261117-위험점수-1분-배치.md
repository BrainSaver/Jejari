## 어떻게 했나

```
행동 로그 적재 ──SADD──┐
예약 확정·취소 이벤트 ─SADD─┼→ risk:dirty ──RENAMENX──→ risk:dirty:work ──→ 1분 배치 (락 risk:batch:lock)
하루 넘은 점수(감쇠) ──SADD─┘                                            대상마다 계산 → 저장 → SREM
```

| 대상 | 행동 신호 (Mongo) | 구매·취소 (Oracle) | 연결 계정 |
|---|---|---|---|
| CI | O | O (같은 CI 회원의 예약) | 같은 CI 회원 |
| 결제 수단 | - (행동 로그에 없음) | O (그 카드로 결제한 예약) | 그 카드를 등록한 회원 |
| 기기 | O | - (가족 공용 기기 오탐 방지) | 그 기기를 쓴 회원 |

## 왜 이렇게 했나

- **전체가 아니라 바뀐 대상만**: 매분 모든 회원을 다시 계산하면 회원 수에 비례해 느려진다. 신호가 생긴 대상만 표시해 두고 계산한다.
- **목록을 통째로 넘겨받기 (RENAMENX)**: 같은 집합에서 꺼내고 지우면, 계산하는 사이 다시 들어온 표시가 지워져 새 신호를 놓친다. 넘겨받은 뒤 들어온 표시는 새 `risk:dirty`에 쌓인다. 계산 중에 앱이 죽으면 `work`가 남아 다음 배치가 이어서 한다.
- **이벤트 값을 믿지 않음**: 예약 이벤트에서는 예약 ID만 쓰고, CI·결제 수단 해시는 Oracle에서 다시 읽는다 (토픽에 남의 해시를 넣어 재계산을 폭주시키는 것 방지).
- **inbox(processed_event)를 쓰지 않음**: 표시(SADD)는 몇 번 해도 결과가 같아서 중복 처리가 문제되지 않는다.
- **표시 실패 시 재시도**: 표시를 잃으면 그 대상 점수가 다음 활동 전까지 안 바뀐다. 로그만 남기고 넘어가지 않고 같은 묶음을 다시 처리한다 (fail-closed).
- **CI 구매는 member_id로 찾음**: `reservation.ci_hash`에는 인덱스가 없고, 쓰기 폭주 테이블이라 인덱스를 새로 걸지 않는다. `UNIQUE(member_id, idempotency_key)` 인덱스를 탄다.
- **탈퇴 계정도 연결 계정으로 셈**: 탈퇴 후 재가입으로 계정 수를 줄이는 회피 방지.
- **"취소 시 즉시 재계산"(미정 9)** = 다음 배치(최대 1분). 요청 경로에서 점수를 계산하지 않아 취소 응답이 느려지지 않는다.

## 막힌 점과 해결

- **매분 저장하면 감쇠가 멈춤** (설계 중 발견): `calculated_at`이 감쇠 기준인데, 활동 중인 대상을 매분 저장하면 1분 감쇠량(80점 기준 0.001점)이 소수 둘째 자리 반올림에 지워지고 기준 시각만 밀려 **점수가 영원히 안 줄어든다**. 오탐된 정상 사용자가 계속 쓰면 영영 풀리지 않는 문제.
  → 저장 조건을 나눔 (`RiskScoreBatch.shouldWrite`): 새 증거가 지배하면 값·근거가 바뀔 때만, 감쇠가 지배하면 1점 이상 내려갔거나 하루가 지났을 때만 저장.

- **통합 테스트 기대값 2건이 틀림**: 같은 간격 30번 클릭은 FAST_CLICK(25)에 REGULAR_INTERVAL(15)까지 걸려 40점, 3계정 기기는 연결 계정 MID(10)라 50점이었다. 엔진이 맞았고 테스트의 손계산이 틀렸다 → 기대값과 근거 주석을 고침.

## 배운 점

- 점수처럼 **반올림해서 저장하는 값을 다음 계산의 기준으로 다시 쓰면**, 작은 변화가 반올림에 계속 지워져 값이 멈출 수 있다. "언제 저장하나"도 설계 대상이다.
- 큐에서 꺼낸 뒤 지우는 방식은 "꺼낸 사이에 다시 들어온 것"을 놓친다. 넘겨받기(RENAME)로 경계를 나누면 간단히 해결된다.
- 멱등한 작업(SADD)이면 inbox 같은 중복 처리 장치를 생략해도 된다. 장치를 붙이기 전에 "두 번 해도 같은가"를 먼저 본다.
