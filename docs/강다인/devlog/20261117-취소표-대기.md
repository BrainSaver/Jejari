## 어떻게 했나

```
검사(등급·매수) → 판매 중·구간(B TrainRunReader) → 1회 한도(B PurchaseLimits) → ACTIVE만(D MemberIdentityPort)
 → 매진 확인(B SeatMapService.remainingByGrade) → 위험 점수(A RiskPenaltyService) × 180000ms
 → [트랜잭션] member 행 FOR UPDATE → 활성 대기 수 → INSERT waitlist (waitlist_seq, ERD v19)
```

- 다른 파트 코드 5개를 그대로 가져다 씀. 위험 점수를 따로 읽지 않고 A의 `RiskPenaltyService`를 써서 대기열과 취소표가 **같은 점수 규칙**(CI·결제 수단·기기 중 최댓값, 캐시 없으면 Oracle, 모르면 100)을 쓴다.

## 왜 이렇게 했나

- **회원 행 잠금으로 한도 확인**: "세고 → 넣기"를 그냥 하면 동시에 들어온 두 요청이 둘 다 0건을 보고 들어간다. 같은 회원의 신청만 줄 세우면 되므로 member 행 하나를 잠근다 (다른 회원끼리는 안 막힘).
- **점수·패널티는 응답에 안 보임**: 순서가 왜 밀렸는지 알려 주면 봇이 점수 기준을 역산할 수 있다. DB(`penalty_ms`)에는 근거로 남긴다.
- **남은 좌석이 매수보다 적으면 신청 가능**: 2매를 원하는데 1석만 남았으면 사실상 매진이다.
- **대기 취소는 WAITING만**: 제안받은 건(OFFERED)은 이미 시스템이 좌석을 잡은 예약이 있으니 그 예약을 취소해야 좌석이 다음 대기자에게 간다.
- **다시 눌러도 같은 결과**: 이미 취소된 대기를 또 취소하면 204 (네트워크 재시도에 안전).

## 막힌 점과 해결

- **매진 상태를 테스트로 만들기 어려움**: 좌석 495석을 실제로 다 팔 수 없다 → `SeatMapService`가 Redis 좌석 배치도 캐시(`seatmap:{runId}`)를 먼저 읽는 것을 이용해, 테스트용 Redis(15번 DB)에 GENERAL 좌석을 모두 판매됨으로 써서 매진을 만듦. FIRST는 그대로 둬서 "매진 아님" 경우도 같이 확인.
- **`AppPolicy` 기본값이 10개를 넘음**: `Map.of`는 10쌍까지라 컴파일 오류 → `Map.ofEntries`로 바꿈 (공용 파일이라 값은 그대로, 형식만).
- 테스트 컴파일 오류 2건: 메서드 반환형에 `var` 사용, `QueueKeys` 패키지 경로 → 수정.

## 배운 점

- 한도 검사("세고 넣기")는 동시 요청에 약하다. **무엇을 기준으로 줄 세울지**(여기선 회원 한 명)를 정하고 그 행만 잠그면 다른 사용자를 막지 않고 막을 수 있다.
- 다른 파트에 이미 있는 판단(매진, 한도, 위험 점수)은 **다시 만들지 말고 불러 쓴다**. 규칙이 바뀌어도 한 곳만 고치면 된다.
- 테스트하기 어려운 상태(매진)는 캐시 같은 "앞단"을 이용해 싸게 만들 수 있다. 단, 실제 데이터는 건드리지 않게 테스트 전용 저장소에서.
