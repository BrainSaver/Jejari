## 어떻게 했나

```
risk_score WHERE 점수·상태·유형 ORDER BY final_score DESC  (size+1개 읽어 다음 페이지 판단)
 → 행마다: reasons JSON에서 마커 규칙만 / 연결 회원 중 가장 오래된 계정 → 이름 가림, phone_enc 복호화 → 즉시 가림, 이메일 가림
          / (결제 수단) 카드 끝 4자리 / 최근 suspicious_case
```

- 대상의 연결 회원 찾기는 위험 점수 배치의 `RiskInputReader.membersOf`를 그대로 씀 (배치와 화면이 같은 "연결" 기준).

## 왜 이렇게 했나

- **원문이 나갈 길을 구조적으로 없앰**: 복호화 결과를 바로 마스킹 함수에 넣고 그 결과만 응답 객체에 담는다. 테스트는 응답 문자열 전체에서 원문 이름·번호·이메일 조각을 찾는다.
- **복호화 실패는 `***`**: 키 교체 중이거나 데이터가 깨진 행 하나 때문에 관리자가 목록 전체를 못 보면 안 된다. 실패 사실은 로그(회원 ID, 예외 종류만)에 남긴다.
- **마커는 4개 규칙만**: 관리자가 "왜 의심인가"를 한눈에 보게. 보조 신호까지 늘어놓으면 핵심이 묻힌다.
- **해제는 여기서 안 함**: 목록은 VIEWER도 보므로 가린 값만. 해제는 SUPERVISOR가 케이스 상세에서 사유를 남기고(ADM-06).

## 막힌 점과 해결

- **패키지 밖에서 쓰려던 메서드가 package-private**: `RiskInputReader.membersOf`를 관리자 화면에서도 쓰려다 컴파일 오류 → public으로 (같은 기준을 두 곳에서 따로 적지 않기 위해).
- 그 외 테스트 6개가 한 번에 통과. 다른 테스트가 남긴 `risk_score` 행이 섞여도 흔들리지 않게, 테스트마다 점수 값을 고유하게(55.10·55.20…) 넣고 그 구간으로만 걸러 확인함.

## 배운 점

- 개인정보 화면은 "가린다"보다 **"원문이 응답 객체에 들어갈 자리가 없다"**로 만드는 게 안전하다. 테스트도 필드 하나가 아니라 응답 전체에서 원문을 찾는다.
- 공유 DB를 쓰는 통합 테스트는 다른 데이터가 섞여도 깨지지 않게 **내 데이터만 골라낼 조건**을 처음부터 넣는다.
