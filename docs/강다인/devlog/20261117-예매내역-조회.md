## 어떻게 했나

```
GET /reservations         → reservation ⨝ train_run ⨝ train ⨝ station×2 ⨝ train_stop×2  WHERE member_id = 나  ORDER BY id DESC (n+1개 읽어 다음 커서)
GET /reservations/{id}    → 위 + reservation_seat⨝seat + 최근 payment + cancellation
                            → 상태별 취소 가능: HOLD 무료 / PAYMENT_PENDING 불가 / CONFIRMED 수수료 계산 / 나머지 불가
수수료: 운행 행사 정책 → 없으면 상시 정책 → 구간 [min,max) 하나 → 좌석마다 금액×비율 버림
```

- 컨트롤러는 강동균 님 `ReservationController`(같은 경로의 POST)를 건드리지 않고 내 패키지에 GET만 따로 둠

## 왜 이렇게 했나

- **남의 예약 = 없는 예약 (같은 404)**: 응답이 다르면 예약 ID를 넣어 보며 남의 예약이 있는지 알아낼 수 있다.
- **승차권 번호는 확정일 때만**: 선점 때 발급되지만 확정 전에는 효력이 없다. 보여 주면 결제 안 한 표를 쓸 수 있는 것처럼 보인다.
- **정책이 없으면 "취소 불가"로 (수수료 0원이 아니라)**: 0원으로 잘못 계산되면 사자마자 취소하는 되팔이의 비용이 사라진다 (fail-closed).
- **경계는 늘 불리한 쪽**: 남은 분은 내림, 출발 후는 더 지난 쪽으로. 1초 차이로 싼 구간에 들어가는 일을 막는다.
- **모르는 필터 값은 400**: 조용히 무시하면 "전체" 목록이 와서 화면이 필터가 된 것처럼 보인다.
- **`no-store`**: 승차권 번호·결제 상태가 캐시에 남지 않게.
- **새 인덱스 없음**: 회원별 조회는 `UNIQUE(member_id, idempotency_key)` 인덱스를 탄다. 쓰기 폭주 테이블 `reservation`에 인덱스를 늘리지 않음.

## 막힌 점과 해결

- **평시 운행에 쓸 상시 수수료 정책이 없음**: DDL 예시 5건이 모두 행사 1(지난 추석) 것이라 시드 운행 9001·9002는 계산할 정책이 없다 (`db/seed/README.md`에 D가 정해 달라는 항목). → 설계서 예시 비율을 상시 정책으로 쓰자고 강동균 님께 요청. 코드는 행사 → 상시 → 없으면 취소 불가 순서. 통합 테스트는 상시 정책이 없으면 잠깐 넣고 지움.
- **SQL 공백 누락으로 500**: 텍스트 블록 끝(`WHERE`) 뒤에 조건을 이어 붙이면서 공백이 사라져 `WHEREsale_event_id`가 됨 (ORA-03048). 통합 테스트에서 바로 잡힘 → `+ " " +`로 수정.
- 취소 담당이 김성원 님으로 정해짐: 같은 수수료 계산을 두 곳에서 만들면 상세의 예상 수수료와 실제 수수료가 어긋날 수 있어, 계산기를 공용으로 두고 재사용을 요청하기로 함.

## 배운 점

- "보여 주는 값"과 "실제로 처리하는 값"이 다른 사람 코드에 있으면 어긋나기 쉽다. **계산은 한 곳에 두고 양쪽이 부르게** 한다.
- 설정·정책 데이터가 비어 있을 때의 기본 동작을 정해 둬야 한다. 돈이 걸린 값은 "0으로 진행"이 아니라 "멈춤"이 기본이다.
- 텍스트 블록에 문자열을 이어 붙일 때 경계 공백을 조심한다. 통합 테스트가 없었으면 운영에서 500으로 처음 발견했을 것.
