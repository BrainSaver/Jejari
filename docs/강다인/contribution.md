## 1. 담당 범위

- 직책: 팀원 (D)
- 범위: 행동 로그 수집(MongoDB), 규칙 기반 위험 점수, 의심 구간 타임라인 API·화면, 취소·환불, 취소표 재배정 대기 관리, 회원·모의 본인인증, 개인정보 암호화(AES-256-GCM) 적용, 위험 사용자 관리자 화면(마스킹 표시)

## 3. 설계 결정

결정 하나당 한 칸. "왜 이렇게 했는가"를 면접에서 그대로 말할 수 있게 적습니다.

### 결정 1. RESTRICTED 회원은 취소표 대기 신청 불가

- 상황: 이용 제한 회원도 예매는 가능하고 대기열 패널티(최대 100초)만 받는 가정이었음. 그런데 취소표 대기는 대기열 입장 토큰 없이 신청하고, 순서도 위험 점수와 무관한 신청 순서라 패널티를 우회하는 길이 됨
- 고려한 대안: 취소표 대기 순서에 위험 점수 반영 / 제한 회원 예매 자체 차단
- 선택과 이유: 대기 신청만 막음. WL-01에서 상태 확인 한 줄이라 구현 비용이 작고, 대기 순서는 신청 순서 그대로라 설명이 단순함
- 감수한 단점: 오탐으로 제한된 정상 사용자는 취소표 기회를 잃음 → 케이스 판정(ADM-06)에서 DISMISSED 시 ACTIVE로 복구
- 관련 코드·커밋: 기능설계서 2장·WL-01·9장, U-10
- 이후 변경 (2026-11-16): 김성원 님 제안으로 취소표 대기 순서에도 위험 점수 패널티(1점 = 3분)를 넣었고, RESTRICTED 차단은 그대로 둠. 둘은 역할이 다름: 패널티는 추정 점수라 "뒤로 미루기", RESTRICTED는 관리자 판정이라 "막기" (concurrency.md §9.3 0번)

### 결정 2. 위험 등급의 "위험" 시작점 = 케이스·결제 차단 기준 (2026-11-23)

- 상황: 점수에 따라 하는 일(순번 조정, 녹화 FULL 70, 케이스 80, 결제 차단 80)이 여기저기 흩어져 있어 "몇 점이면 위험한가"를 한 번에 말할 수 없었음
- 고려한 대안: 등급마다 따로 문턱을 둠 (예: 위험 70)
- 선택과 이유: 정상 0~29 · 경고 30~79 · 위험 80~ 이고, **위험의 시작점은 `risk.rule.case_threshold`를 그대로** 씀. 따로 두면 "위험인데 결제는 됨"처럼 화면과 동작이 어긋남. 등급은 저장하지 않고 점수로 계산 (문턱을 바꾸면 바로 반영, ERD 칸 불필요)
- 감수한 단점: 마커 규칙은 점수와 상관없이 케이스를 열어서 "경고인데 케이스"가 생김 → 점수는 "얼마나 의심되나", 케이스는 "사람이 봐야 하나"로 설명
- 관련 코드·커밋: `RiskGrade`, `c84b6c7`, [봇-탐지-보강](features/봇-탐지-보강.md)

### 결정 3. ERD 패치보다 코드가 먼저 나가도 안전하게 (MarkerCodes, 2026-11-23)

- 상황: 새 마커 규칙은 `case_marker.rule_code` CHECK에 값이 있어야 함. 패치 전에 넣으면 ORA-02290으로 **점수 저장까지 롤백**되고 매 배치 같은 실패. 대회 전이라 배포·ERD 순서를 맞추기 어려움 (CI 잠금으로 수동 배포)
- 선택과 이유: 케이스를 열기 전에 DB CHECK를 읽어(5분 캐시) 받아 주는 코드만 마커로 넣음. 못 받는 마커는 빼고 점수는 저장. 패치가 들어오면 재배포 없이 켜짐 (예매 완료 알림 CONFIRMED 때와 같은 방식)
- 감수한 단점: CHECK 문장을 문자열로 읽어 파싱 (제약 이름 `CK_CASE_MARKER_RULE_CODE`에 의존). 못 읽으면 기존 마커만 허용

## 5. 다른 파트와의 연결

| 상대 | 주고받는 것 | 약속한 내용 |
|---|---|---|
| 전체 | `Pseudonymizer`(A)·`PiiCipher`·`PiiMasker` | 해시·암호화·마스킹은 공용 모듈로만 (정규화·키 통일). 암호화는 행 ID까지 AAD에 묶음 |
| A·B·C | 행동 로그 `mark()` | 담당 API마다 이벤트 1건, 실패 요청 포함 (합의 필요) |
| E | `PasswordHasher` (Argon2id) | 가입과 로그인이 같은 해셔·같은 파라미터 |

## 7. 예상 질문

- Q. 봇을 머신러닝이 아니라 규칙으로 잡은 이유는?
  - A. 대회 전까지 정답 라벨이 거의 없었고, 관리자가 "왜 막혔나"를 설명할 수 있어야 해서 규칙(점수 + 이유 코드)을 1차로 썼어요. 모델(Isolation Forest 등)은 점수를 바꾸지 않는 보조 의견으로만 붙였어요 ([모델-보조의견-설계](모델-보조의견-설계.md)).
- Q. 정상 사용자를 봇으로 잘못 잡으면?
  - A. 점수는 "뒤로 미루기"(대기열·취소표 순번 패널티)에만 쓰고, 막기(RESTRICTED)는 사람이 케이스를 보고 판정해요. 오탐으로 판정되면 DISMISSED로 바로 복구돼요. 실제로 선점 두 번 누른 사람 오탐을 찾아 0으로 고쳤어요.
- Q. 개인정보는 어떻게 지켰나요?
  - A. 복호화가 필요한 값(휴대폰)은 AES-256-GCM 암호문 + 키 버전, 찾기만 하면 되는 값은 HMAC 해시, 화면에는 마스킹. 암호화할 때 행 ID를 AAD로 묶어서 암호문을 다른 행에 옮겨 붙이면 복호화가 실패해요.
- Q. 같은 행동 로그가 두 번 오면?
  - A. 이벤트마다 `event_id`를 붙이고 Mongo에 유니크 인덱스를 걸어, Kafka가 같은 이벤트를 다시 보내도 1건만 저장해요. 처음엔 기존 볼륨에 인덱스가 빠져 재전달 때 2건이 저장된 걸 찾아, 컨슈머가 인덱스를 직접 보장하게 고쳤어요.
- Q. 취소 수수료 경계(출발 10분 59초 전 등)는?
  - A. 출발 전은 분을 내림, 출발 뒤는 음수로 올림해서 경계에서는 늘 "덜 남은 쪽"으로 계산해요. 그래서 같은 순간이 두 수수료 구간에 걸치지 않고, 화면 미리보기와 실제 취소가 같은 서버 계산을 써서 금액이 어긋나지 않아요.
- Q. 사이트 점검은 어떻게 했나요?
  - A. 공용 서버를 사람처럼 직접 써 보면서, 폰 폭에서 겹침·가로 넘침을 찾는 스크립트를 같이 돌렸어요. 화면 경로 허용 목록이 빠져 새로고침 때 401이 나던 걸 "API가 아닌 GET은 화면" 규칙으로 바꿔 목록 관리 자체를 없앴어요.
