# [behavior] 기존 Mongo 볼륨에 event_id 유니크 인덱스가 없어 같은 행동 로그가 중복 저장

| 항목 | 내용 |
|---|---|
| 작성자 | 강다인 |
| 날짜 | 2026-11-16 |
| 상태 | 해결 (RISK-01 개발 중 발견) |
| 관련 커밋·이슈 | `0f52bd2`, ERD v16(`ux_event_id`) |

## 1. 문제

- 현상: Kafka가 같은 메시지를 다시 전달하면 `behavior_log`에 같은 `event_id` 문서가 두 건 저장됐다.
- 재현 조건: ERD v16 이전에 만든 MongoDB 볼륨을 그대로 쓰는 PC에서 컨슈머가 같은 묶음을 재처리 (저장 실패 후 재시도, 리밸런스).
- 영향: 같은 클릭이 두 번 세어져 위험 점수 신호(반복 실패, 초고속 클릭)가 부풀려짐 → 정상 사용자 오탐 가능.

## 2. 원인

- 중복 방지는 `event_id` 유니크 인덱스(`ux_event_id`)에 맡기고, 컨슈머는 중복 키 오류(11000)를 성공으로 본다.
- 이 인덱스는 `docker/mongo/mongo-init.js`(v16에서 추가)가 만든다. 그런데 Mongo 공식 이미지의 init 스크립트는 **데이터 볼륨이 비어 있을 때 처음 한 번만** 실행된다.
- 최종 원인: 이전에 만들어 둔 볼륨에는 인덱스가 없어서 중복이 그대로 들어갔다.

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 팀원 모두 볼륨 지우고 다시 만들기 | 코드 변경 없음 | 사람마다 해야 하고, 다음 인덱스 추가 때 또 생김 | |
| 저장 전에 `event_id`로 조회 | 인덱스 없이도 동작 | 건마다 조회, 동시성에서 여전히 중복 가능 | |
| 컨슈머가 시작할 때 인덱스를 직접 보장(`createIndex`) | 볼륨 상태와 무관, 이미 있으면 아무 일 안 함 | 컨슈머가 인덱스 정의를 알아야 함 (init 스크립트와 같게 유지) | ✓ |

- `BehaviorSink.ensureIndexes()`: `ux_event_id`(유니크), `ttl_expire_at`(TTL) 생성. Mongo 장애로 실패하면 다음 묶음에서 다시 시도.
- 바뀐 코드: `behavior/sink/BehaviorSink.java`

## 4. 수치

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| 같은 `event_id` 재전달 시 저장 건수 | 2건 | 1건 |

- 측정 방법: Kafka·Mongo 통합 테스트 `BehaviorLogInfraTest` `같은_이벤트가_다시_와도_한_번만_저장`

## 5. 정리

- 면접용 한 줄 요약: "Kafka 재전달 중복을 Mongo 유니크 인덱스로 막는 구조였는데, init 스크립트는 빈 볼륨에서만 돌아 기존 환경에 인덱스가 없었다. 컨슈머가 시작할 때 인덱스를 직접 보장하게 해 환경과 상관없이 중복이 막히게 했다."
- 다음에 비슷한 상황이면: 정합성을 DB 제약에 기대는 코드는 그 제약이 **정말 있는지** 앱이 확인하거나 만든다. init 스크립트는 "새 환경"용일 뿐이다.
