# [behavior] 저장 재시도 때 클릭 간격이 0이 되어 정상 사용자가 FAST_CLICK에 걸림

| 항목 | 내용 |
|---|---|
| 작성자 | 강다인 |
| 날짜 | 2026-11-16 |
| 상태 | 해결 (RISK-01 개발 중 발견, main 병합 전) |
| 관련 커밋·이슈 | `0f52bd2` |

## 1. 문제

- 현상: MongoDB 저장이 실패해 컨슈머가 같은 묶음을 다시 처리하면, 그 묶음의 `interval_ms`(직전 클릭과의 간격)가 전부 0으로 저장됐다.
- 재현 조건: Mongo 장애 중 행동 로그 적재 → 복구 후 재시도.
- 영향: 위험 점수 FAST_CLICK 규칙(클릭 간격이 비정상적으로 짧음)에 **정상 사용자가 걸림**. Mongo 장애 한 번이 오탐 폭탄이 될 수 있었다.

## 2. 원인

- `IntervalTracker`가 세션별 직전 이벤트 시각을 메모리에 기억하고, 새 이벤트가 오면 그 차이를 간격으로 쓴다.
- 처음 구현은 **간격을 계산하는 순간 바로 기억을 갱신**했다. 저장이 실패해 같은 이벤트를 다시 계산하면 "직전 시각 = 자기 자신"이 되어 간격이 0.

```
1차: e1(10:00:00.0) → 간격 계산, 기억 = 10:00:00.0 → 저장 실패
2차: e1(10:00:00.0) → 직전 = 10:00:00.0 → interval_ms = 0  ← 오탐 재료
```

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 간격 0은 무시 | 간단 | 진짜 봇의 0ms 클릭도 놓침 | |
| 묶음 단위로 계산만 하고 **저장 성공 뒤에만 기억 반영**(`Batch.commit()`) | 재시도해도 같은 결과 | 코드가 조금 늘어남 | ✓ |

- 시각이 뒤바뀐 이벤트(리밸런스 직후 등)는 간격을 null로 두고 기억도 되돌리지 않음.
- 바뀐 코드: `behavior/sink/IntervalTracker.java`, `behavior/sink/BehaviorSink.java`

## 4. 수치

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| 재시도한 묶음의 `interval_ms` | 0 | 1차 계산과 같은 값 |

- 측정 방법: `./gradlew test --tests 'com.jejari.behavior.sink.IntervalTrackerTest'` (`저장_실패로_같은_묶음을_다시_처리해도_간격이_같다`, `순서가_뒤바뀐_이벤트는_null_기준_시각은_유지`)

## 5. 정리

- 면접용 한 줄 요약: "행동 로그 적재가 실패 후 재시도될 때 클릭 간격이 0으로 계산돼 정상 사용자가 봇 규칙에 걸릴 수 있었고, 간격 기억을 저장 성공 뒤에만 반영하도록 바꿔 재시도해도 결과가 같게(멱등하게) 했다."
- 다음에 비슷한 상황이면: 재시도되는 처리 안의 **메모리 상태 변경**도 DB 쓰기처럼 "성공 뒤에 확정"해야 한다.
