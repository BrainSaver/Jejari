# [member] MongoDB 연결이 안 되면 로그인이 30초 멈춤

| 항목 | 내용 |

## 1. 문제

- 현상: MongoDB 컨테이너를 멈춘 상태에서 로그인하면 응답이 약 30초 뒤에 왔다 (결과는 성공).
- 재현 조건: `docker compose stop mongo` → `POST /api/v1/auth/login`.
- 영향: 로그인 시도 기록용 부가 저장소 하나가 죽었는데 **본 기능인 로그인이 사실상 멈춤**. 몰리면 요청 스레드가 30초씩 묶여 다른 API까지 느려질 수 있음.

## 2. 원인

- 로그인마다 `login_attempt`(크리덴셜 스터핑 탐지용)를 MongoDB에 남기는데, 이 저장이 **요청 안에서 동기로** 실행됐다.
- 기록 실패는 try/catch로 삼켜 로그인을 막지는 않았지만, 실패하기까지 MongoDB 드라이버의 기본 서버 선택 대기 `serverSelectionTimeoutMS = 30000`을 그대로 기다렸다.
- 최종 원인: "실패해도 막지 않는다"만 챙기고 "실패하기까지 얼마나 걸리나"를 챙기지 않았다.

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 타임아웃만 2초로 줄이기 | 간단 | 장애 중엔 로그인마다 2초씩 느림 | 함께 적용 |
| 전용 스레드 + 큐로 비동기 저장 | 로그인 응답이 Mongo 상태와 무관 | 큐가 넘치거나 앱이 갑자기 죽으면 기록 일부 손실 | ✓ |
| Kafka로 보내기 | 유실 적음 | 로그인 기록 하나에 비해 과함 | |

- 적용한 내용
  - `application.yml`: Mongo URI에 `serverSelectionTimeoutMS=2000&connectTimeoutMS=2000` (Redis 2초와 같은 기준)
  - `LoginAttemptLog`: 스레드 1개 + 1만 건 큐. 로그인은 큐에 넣고 바로 돌아옴
  - 시각(`ts`)은 시도한 순간에 정함 (저장이 늦어도 시각은 안 밀리게)
  - 큐가 넘치면 버리고 버린 개수를 10초에 한 번 경고. 로그인 자체는 IP·이메일 제한이 따로 막으므로 기록이 빠져도 방어는 유지
  - 앱 종료 때 남은 기록을 최대 5초 기다려 저장
- 바뀐 코드: `member/login/LoginAttemptLog.java`, `application.yml`

## 4. 수치

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| Mongo 멈춘 상태의 로그인 응답 | 약 30초 | 0.3초 (200) |
| Mongo 멈춘 상태에서 기록 100건 요청 | 건마다 대기 | 즉시 반환 |

- 측정 환경: 로컬 Docker Compose
- 측정 방법: `docker compose stop mongo` 뒤 로그인 API 호출 시간 측정. 단위 테스트에 "Mongo가 멈춰도 100건이 즉시 반환", "저장 실패 시 예외 없음", "큐 초과 시 버린 개수" 포함

## 5. 정리

- 면접용 한 줄 요약: "로그인 시도 기록을 요청 안에서 동기로 저장해 MongoDB 장애 때 로그인이 드라이버 기본 대기 30초만큼 멈췄고, 타임아웃을 2초로 줄이고 전용 스레드 큐로 비동기화해 0.3초로 돌렸다."
- 다음에 비슷한 상황이면: 요청 경로에 부가 저장이 끼어 있으면 "그 저장소가 죽었을 때 몇 초 걸리나"를 먼저 재 본다. 드라이버 기본 타임아웃은 대부분 길다.
- 같은 설계를 행동 로그 발행(`BehaviorPublisher`, 5만 건 큐)에도 그대로 썼다.
