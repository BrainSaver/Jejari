# [notification] 트랜잭션 안에서 난 예외를 바깥에서 잡아도 전체가 롤백되는 문제

| 항목 | 내용 |
|---|---|
| 작성자 | 강다인 |
| 날짜 | 2026-11-19 |
| 상태 | 해결 |
| 관련 커밋·이슈 | `ea458b5` |

## 1. 문제

- 상황: 예매 완료 알림(`CONFIRMED`)을 추가했는데, DB의 `notification.type` CHECK에 CONFIRMED가 들어오는 ERD 패치가 아직 없었다
- 걱정: 패치 전에 코드가 main에 들어가면 알림 저장이 CHECK에 걸린다 → Inbox 트랜잭션 실패 → 알림 소비자가 그 이벤트를 **끝없이 재시도**하며 뒤의 알림(만료·환불)까지 멈춤
- 첫 시도: 저장 호출을 `try { writer.create(...) } catch (DataIntegrityViolationException e) { 건너뜀 }`으로 감쌈

## 2. 원인

- `NotificationWriter.create`는 `@Transactional(propagation = MANDATORY)`이다. 예외가 이 **프록시 경계를 빠져나오는 순간 Spring이 바깥(Inbox) 트랜잭션을 rollback-only로 표시**한다
- 그래서 바깥에서 잡아도 커밋할 때 `UnexpectedRollbackException` → 결국 실패하고 재시도 (잡는 방식은 동작하지 않음)

## 3. 해결

| 선택지 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 예외를 바깥에서 잡기 | 간단해 보임 | 위 이유로 동작 안 함 | |
| `REQUIRES_NEW`로 따로 저장 | 실패가 격리됨 | Inbox 도장과 알림이 따로 커밋 → 중복 알림 가능 | |
| **넣기 전에 DB 제약에 CONFIRMED가 있는지 확인, 없으면 그 한 건만 건너뜀** (5분마다 다시 확인) | 같은 트랜잭션 유지, 패치하면 재시작 없이 켜짐 | 제약 확인 쿼리 (5분에 한 번) | ✓ |

## 4. 수치

| 지표 | 결과 |
|---|---|
| 제약 없는 DB에서 CONFIRMED 이벤트 | 예외 없이 건너뜀, 같은 회원의 만료 알림은 정상 저장 (`NotificationInfraTest`) |

## 5. 정리

- 면접용 한 줄 요약: "@Transactional 메서드 안의 예외는 바깥에서 잡아도 트랜잭션이 rollback-only가 돼서, 실패할 조건을 미리 확인하는 방식으로 바꿔 메시지 소비자가 막히지 않게 했다."
- 다음에 비슷한 상황이면: 트랜잭션 프록시를 지나는 호출의 실패는 '잡기'가 아니라 '미리 확인'이나 '트랜잭션 분리'로.
