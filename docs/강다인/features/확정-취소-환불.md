# 확정 예약 취소·환불 (CNL-01·02)

작성자: 강다인 · 코드: `src/main/java/com/jejari/reservation/` (`ReservationCancelService`, `CancelFeeCalculator`) · 절차: concurrency.md §8 · 화면: U-08

## 한 줄 요약

확정 예약을 취소하면 서버가 수수료를 **다시 계산**해 `cancellation`에 남기고, 좌석을 대기자에게 먼저 돌려주고(REOFFER), 매수 카운터를 줄이고, 커밋 뒤 PG에 환불을 요청한다. 미리보기(CNL-01)와 실제 취소(CNL-02), 예매 내역 상세(RSV-04)가 같은 계산기를 쓴다.

## API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/v1/reservations/{id}/cancel-quote` | CNL-01 미리보기 `{paidAmount, departureAt, minutesBeforeDeparture, feeRate, fee, refund}`. 확정 예약만 (아니면 409 `RESERVATION_NOT_CONFIRMED`, 시간 지남 409 `CANCEL_NOT_ALLOWED`) |
| POST | `/api/v1/reservations/{id}/cancel` | 취소 (HOLD·CONFIRMED 공통). 응답 `{reservationId, status, kind: BEFORE_PAY/CONFIRMED, runId, seatCount, cancelFee, refundAmount, refundStatus}` |

`POST …/cancel`은 강동균 님 `seat.web.ReservationController`에 있고, 상태에 따라 나누는 일만 `ReservationCancelService.cancel`이 한다: HOLD·PAYMENT_PENDING → 좌석 쪽 결제 전 취소(RSV-05, 그대로), CONFIRMED → 아래 확정 취소.

## 확정 취소 순서 (§8)

```
[트랜잭션]
 0. reservation 행 FOR UPDATE (내 예약, CONFIRMED) ─ 아니면 RESERVATION_NOT_CONFIRMED
 1. 수수료 다시 계산 (CancelFeeCalculator) ─ 시간 지남·정책 없음이면 CANCEL_NOT_ALLOWED
 2. reservation CONFIRMED → CANCELED
 3. SeatReleaseService.returnSoldSeatsInCurrentTx (B): SOLD 행 삭제 + 카운터 감소, 커밋 뒤 좌석 키 REOFFER:R
 4. cancellation INSERT (USER, 수수료, 환불액, 정책 ID, 구매 후 분, 출발 전 분, REQUESTED, resold_yn N)
 5. outbox RESERVATION_CANCELED (reason USER, cancelFee, refundAmount, 분 값 + 좌석) → reservation_history (USER)
[커밋 뒤, 트랜잭션 밖]
 6. PgClient.refund(payment_id, pg_tx_id, 환불액, "cancel:<cancel_id>")
 7. 성공: cancellation DONE + refund_pg_tx_id, payment REFUNDED (한 트랜잭션) / 실패: cancellation FAILED (CNL-03 재시도 대상)
```

## 규칙

| 규칙 | 이유 |
|---|---|
| 수수료는 클라이언트 값을 받지 않고 잠근 뒤 서버가 다시 계산 | 미리보기 값을 그대로 믿으면 0원으로 바꿔 보낼 수 있음 |
| 예약 행을 먼저 잠금 (§0.4) | 동시에 두 번 눌러도 한 번만 취소 (3개 동시 요청 → 200 한 번, cancellation 1행, 카운터 한 번만 감소) |
| 환불은 커밋 뒤, 트랜잭션 밖 (§0.6) | PG 응답을 기다리는 동안 DB 락을 잡지 않음 |
| 환불 키 `cancel:<cancel_id>` | 재시도해도 PG에서 한 번만 환불 (멱등) |
| 환불 실패해도 취소는 유지, FAILED로 남김 | 돈은 나중에 재시도로 돌려줄 수 있지만, 취소를 되돌리면 좌석·카운터가 다시 꼬임 |
| 사용자 취소만 USER로 기록 | 위험 점수 신호(구매 직후 취소 CANCEL_AFTER_PAY 등)는 USER만. 이 취소 이벤트는 risk-signal이 받아 다음 1분 배치에 반영 |

## 다른 파트에 바꾼 것

| 대상 | 내용 |
|---|---|
| 강동균 (B) `ReservationController.cancel` | `SeatReleaseService.cancelBeforePay` 대신 `ReservationCancelService.cancel`을 부름 (결제 전 취소는 그 안에서 그대로 `cancelBeforePay`). 응답에 `kind`·`cancelFee`·`refundAmount`·`refundStatus`가 더해짐. 기존 `SeatHoldInfraTest` 통과 |

## 관리자 강제 취소 (ADM-07)

`POST /api/v1/admin/reservations/{id}/cancel` `{"memo":"사유 5자 이상"}` — **SUPERVISOR만**. 화면은 A-04(강동균 님이 칸을 붙임).

응답 `{"cancel": {위 취소 응답과 같은 모양}, "actionId": admin_action 행}`

**위 확정 취소와 같은 트랜잭션**을 actor `ADMIN`으로 쓴다 (§8.1). 다른 점만:

| | 사용자 취소 (USER) | 관리자 강제 취소 (ADMIN) |
|---|---|---|
| 누구 예약 | 내 예약만 | 아무 예약 (예약 주인으로 잠금) |
| 수수료 | 출발까지 남은 시간으로 계산, 시간 지나면 불가 | **0, 결제 금액 전액 환불**, 출발 뒤여도 됨 |
| 기록 | cancellation USER, 이력 USER | cancellation ADMIN, 이력 ADMIN, **`admin_action` CANCEL_RESERVATION**(관리자·예약 회원 CI·사유·예약 ID, 같은 트랜잭션) |
| 위험 점수 | 신호로 셈 (CANCEL_AFTER_PAY 등) | **세지 않음** (점수 쪽이 `cancel_type = 'USER'`만 셈) |

| 오류 | 언제 |
|---|---|
| 400 `ACTION_REASON_REQUIRED` | 사유가 없거나 5자 미만 (케이스 조치와 같은 규칙). 아무것도 바뀌지 않음 |
| 403 `ADMIN_FORBIDDEN` | VIEWER·REVIEWER |
| 404 `RESERVATION_NOT_FOUND` | 없는 예약 |
| 409 `RESERVATION_NOT_CONFIRMED` | 확정이 아님(결제 전 예약은 기한이 지나면 스스로 풀림) · 이미 취소됨(두 번 눌러도 한 번) |

테스트 2개 (`ReservationCancelInfraTest`): 강제 취소 전체(수수료 0·전액·환불 DONE·이력/이벤트 ADMIN·admin_action 값) / 권한·사유·상태·두 번 누르기·없는 예약

## 환불 재시도 배치 (CNL-03)

`RefundRetryBatch` — 5분마다 `refund_status`가 REQUESTED·FAILED인 취소를 다시 환불 요청한다 (사용자·관리자 취소 + 길동현 님 늦은 승인 환불).

```
대상: REQUESTED·FAILED  AND  updated_at < 지금 − 1분(유예)  AND  canceled_at > 지금 − 72시간(포기)
건마다: USER·ADMIN → ReservationCancelService.retryRefund (처음 환불과 같은 refund())
        PAY_FAILED → LateApprovalRefund.refund (길동현)
72시간 넘은 미환불 → 건드리지 않고 ERROR 로그 "사람이 처리해야 함"
```

| 규칙 | 이유 |
|---|---|
| 처음 환불과 **같은 코드·같은 환불 키** `cancel:<cancel_id>` | PG가 한 번만 환불한다. 서버 여러 대가 동시에 돌려도 같음 |
| DONE은 `refund_status <> 'DONE'` 조건부, 바꾼 쪽만 `REFUND_COMPLETED` (0원 제외) | 길동현 님 메모대로 알림이 한 번만 나간다 |
| 1분 유예 | 막 취소돼 커밋 뒤 환불이 진행 중인 건을 배치가 같이 잡지 않게 |
| 72시간 포기 | 계속 실패하는 건(승인 거래가 없는 등)을 매번 두드리지 않고 사람에게 넘김 |
| 한 건 실패해도 계속 | 실패 건은 FAILED로 남아 다음 주기에 |

설정 (`application.yml`, 기본값): `jejari.refund.retry-enabled`(true) · `retry-interval`(PT5M) · `retry-grace`(PT1M) · `retry-give-up`(PT72H) · `retry-batch-size`(100). 테스트에서는 `build.gradle`이 꺼 둔다(다른 테스트가 일부러 만든 FAILED를 도중에 바꾸지 않게). 테스트는 `run()`을 직접 부른다.

다른 파트에 바꾼 것: 길동현 님 `MockPgClient.refund`가 **성공만** 기억하도록 (전에는 실패도 기억해서 같은 환불 키로 재시도하면 영원히 같은 실패를 받았다. 실제 PG처럼).

테스트 2개 (`ReservationCancelInfraTest`): 실패 → 유예 안에서는 그대로 → 유예 뒤 DONE·payment REFUNDED·알림 한 번 / 늦은 승인 환불도 DONE, 72시간 넘은 건은 건드리지 않음
