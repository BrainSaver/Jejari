# 회원가입 + 모의 본인인증 (AUTH-01·02)

작성자: 강다인 · 코드 위치: `member/`, `auth/verify/` (예정) · 화면: U-02

> 상태: 설계 초안 (코드 전). 원천은 기능설계서 4.1, ERD `member`·`member_credential`·`identity_verification`.

## 한 줄 요약

이름 + 휴대폰 번호로 **항상 같은 가짜 CI**를 만들어 같은 사람의 여러 계정을 묶고, 그 결과로 회원을 만든다.

## 어떻게 동작하나

```
[1단계] POST /auth/verify  {name, phone, provider}
  → 정규화 → MockIdentityProvider가 CI 생성 → ci_hash 계산
  → 인증 결과를 암호화한 verificationToken 반환 (10분 유효)

[2단계] POST /auth/signup  {verificationToken, email, password}
  → 토큰 복호화·만료 확인
  → 한 트랜잭션: member INSERT → member_credential INSERT → identity_verification INSERT (SUCCESS)
  → 201
```

### 1단계: 모의 본인인증

- 정규화: 이름은 앞뒤 공백 제거 + 유니코드 NFC, 휴대폰은 숫자만 (`010-1234-5678` → `01012345678`).
- 가짜 CI: `CI = Base64(HMAC(mockCiKey, 이름 + "|" + 휴대폰))`. 같은 입력이면 항상 같은 CI가 나와서 다계정이 묶입니다.
- 저장하는 건 `ci_hash = PiiHasher.ci(CI)`뿐입니다. CI 원문은 저장하지 않습니다.
- `MockIdentityProvider`는 `IdentityProvider` 인터페이스 뒤에 둡니다. 실제 본인인증(PASS 등)으로 바꿀 때 이 구현체만 교체합니다.
- 실패 재현: 휴대폰 번호가 `0000`으로 끝나면 `AUTH_VERIFY_FAILED`를 돌려줍니다 (화면·테스트용). MOCK_PASS와 MOCK_PHONE은 동작이 같고 `provider` 값만 기록됩니다.

**verificationToken**: 인증 결과(`ciHash`, 이름, 휴대폰, provider, 만료 시각)를 `PiiCipher`로 암호화한 문자열입니다 (AAD `"auth.verification"`). 서버에 따로 저장하지 않아서 Redis 키나 테이블을 새로 만들 필요가 없습니다. 클라이언트는 내용을 읽을 수도, 고칠 수도 없습니다.

### 2단계: 가입

| 테이블 | 넣는 값 |
|---|---|
| `member` | email(소문자), ci_hash, name, `phone_enc` + `enc_key_id`(PiiCipher, AAD `"member.phone_enc"`), `phone_hash`, status = ACTIVE |
| `member_credential` | Argon2id PHC 문자열, `hash_algo = ARGON2ID`, `hash_params` = `app_policy auth.argon2_params`, `needs_rehash = N`, `failed_count = 0` |
| `identity_verification` | member_id, ci_hash, provider, result = SUCCESS, verified_at |

- 이메일 중복은 미리 조회하지 않고 `member.email` UNIQUE 위반을 잡아 `AUTH_EMAIL_DUPLICATED`로 바꿉니다. 미리 조회하면 동시에 두 번 가입할 때 둘 다 통과합니다.
- 비밀번호 규칙: 8~64자. 문자 종류 조합은 강제하지 않습니다 (NIST SP 800-63B). 이메일과 같으면 거절.
- **같은 CI로 여러 계정 가입은 허용**합니다 (다계정 실험 대상). 매수 제한·위험 점수가 CI 기준으로 합산하므로 막을 필요가 없습니다.
- 가입 성공 시 로그인 세션은 발급하지 않습니다. 화면은 U-01(로그인)로 이동합니다.

## 왜 이렇게 했나

- **CI를 HMAC으로 만듦**: 랜덤 CI면 같은 사람이 다시 인증할 때 다른 CI가 나와서 다계정 탐지가 안 됩니다. 실제 CI도 "같은 사람 = 같은 값"이라 성질이 같습니다.
- **토큰을 암호화해 들고 다님**: `identity_verification.member_id`가 NOT NULL이라 회원이 생기기 전에는 인증 결과를 저장할 곳이 없습니다. Redis에 두려면 `redis_keys`에 새 키를 추가해야 해서, 이미 만드는 암호화 모듈을 재사용했습니다.
- **2단계 분리**: 실제 서비스처럼 본인인증을 먼저 해야 가입 폼으로 넘어갑니다. 인증 없이 `/auth/signup`만 호출하는 경로가 없습니다.

## 다른 파트와의 약속

| 상대 | 약속 |
|---|---|
| E (로그인 AUTH-03) | Argon2id 해싱은 공용 `PasswordHasher` 하나로. 파라미터는 `app_policy auth.argon2_params`. 가입 시 만든 PHC 문자열을 로그인이 그대로 검증 |
| 전체 | `ci_hash`·`phone_hash`는 `PiiHasher`로만 계산 ([개인정보-암호화](개인정보-암호화.md)) |
| E (가상 데이터 DATA-02) | 봇·다계정 시드도 같은 정규화·같은 함수로 ci_hash를 만들어야 묶임 |

## 주의할 점

- verificationToken은 서버에 저장하지 않아서, 10분 안에는 같은 토큰으로 계정을 여러 개 만들 수 있습니다. 같은 CI 다계정은 원래 허용이라 문제는 없지만, 1회용으로 만들려면 Redis 키가 필요합니다.
- 응답·로그에 이름·휴대폰 원문을 넣지 않습니다. 응답은 `memberId`와 마스킹된 이메일만 돌려줍니다.

## 확인 필요 (팀)

1. **인증 실패 기록**: `identity_verification.member_id`가 NOT NULL이라 실패(FAIL)는 회원이 없어 저장할 수 없습니다. 1차는 앱 로그(값 없이 사유만)로 남기고, 실패 이력이 위험 신호로 필요하면 `member_id` NULL 허용을 ERD 담당(강동균)에게 요청합니다.
2. **이름 평문**: ERD의 `member.name`은 평문 `VARCHAR2(50)`입니다. "평문 개인정보 0건" 지표에서 이름을 빼는지(휴대폰·CI·카드만 대상), 아니면 `name_enc`로 바꾸는지 정해야 합니다. 제안: 이름은 예매자 확인·마스킹 표시에만 쓰므로 평문 유지, 지표 대상은 휴대폰·CI·카드·IP로 명시.

## 테스트

- 같은 이름·휴대폰(하이픈 유무만 다름)으로 두 번 인증 → ci_hash 같음
- 같은 이메일로 동시에 두 번 가입 → 하나만 성공, 다른 하나는 `AUTH_EMAIL_DUPLICATED`
- 만료된 토큰, 변조된 토큰 → `AUTH_VERIFY_FAILED`
- 가입 후 DB의 phone_enc 복호화 결과 = 입력 번호, 원문 컬럼 없음
- 휴대폰이 `0000`으로 끝나면 인증 실패
