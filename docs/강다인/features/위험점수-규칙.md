# 규칙 기반 위험 점수 엔진 (RISK-02)

작성자: 강다인 · 코드 위치: `src/main/java/com/jejari/risk/` (`com.jejari.risk.RiskEngine`, `SignalCollector`, `RiskPolicy`)

> 상태: 엔진 구현 완료 (단위 테스트 48개, 회피 시나리오·무작위 성질 검사 포함). 점수 저장(Oracle)·`risk:*` 캐시 쓰기·재동기화(RISK-03) 구현 완료. 입력 집계(Oracle·MongoDB 조회)와 1분 배치는 다음 작업입니다.

## 한 줄 요약

CI·결제 수단·기기마다 행동 신호를 모아 규칙별 배점을 더하고(최대 100), 지난 점수는 반감기 30일로 줄여 둘 중 큰 값을 최종 점수로 한다. 점수 80 이상이거나 핵심 규칙이 하나라도 걸리면 의심 케이스를 연다.

## 사용법

```java
RiskEngine engine = new RiskEngine(RiskPolicy.fromMap(appPolicyMap));   // 설정이 잘못되면 예외 → 이전 정책 유지

// 대상 하나마다 (예: CI 해시)
SignalCollector c = new SignalCollector(engine.policy(), SubjectType.CI, ciHash, windowFrom);
mongoCursor.forEach(e -> {                           // behavior_log, ts 오름차순
    if (e.intervalMs() != null) c.interval(e.intervalMs());
    if (e.type() == SEAT_HOLD) {
        c.seatHold(e.ts(), e.memberId());
        if (e.status() == 409) c.seatHoldFailure(e.seatId());
    }
});
purchases.forEach(p -> c.purchase(p.seatCount()));                 // 결제 확정
userCancels.forEach(x -> c.userCancel(x.minutesAfterPurchase(), x.minutesBeforeDeparture())); // USER만
c.linkedAccounts(accountCount).oldestAccountCreatedAt(oldestCreatedAt, now);

RiskResult r = engine.score(c.build(), previousOrNull, now);
// → risk_score UPSERT (final_score, rule_score, reasons = r.reasonsJson(), 신호 컬럼들)
// → r.openCase()면 suspicious_case(trigger_type = r.triggerType()) + r.markerReasons()로 case_marker
```

## 규칙과 기본 배점

| 코드 | 무엇을 보나 | MID | HIGH | 케이스 |
|---|---|---|---|---|
| `FAST_CLICK` | 200ms 미만 요청 간격 **개수** | 20회 → 25점 | 60회 → 35점 | ✅ |
| `SAME_SEAT_RETRY` | 한 좌석 선점 실패(409) 최대 횟수 | 5회 → 20 | 15회 → 30 | ✅ |
| `CANCEL_AFTER_PAY` | 구매 후 30분 안 취소 수 | 2건 → 15 | 5건 → 25 | ✅ |
| `MULTI_ACCOUNT_SYNC` | 60초 안에 선점한 서로 다른 계정 수 | 2개 → 30 | 3개 → 40 | ✅ |
| `REGULAR_INTERVAL` | 간격 변동계수 ≤ 0.05 (30건 이상) | 15 | | |
| `HIGH_CANCEL_RATIO` | 취소 비율 (구매 4건 이상일 때만) | 50% → 10 | 80% → 20 | |
| `LAST_MINUTE_CANCEL` | 출발 3시간 이내·출발 후 취소 수 | 3건 → 10 | 6건 → 15 | |
| `BULK_PURCHASE` | 누적 구매 매수 | 20매 → 10 | 40매 → 20 | |
| `LINKED_ACCOUNTS` | 연결 계정 수 (자기 포함) | 2개 → 10 | 4개 → 20 | |
| `NEW_ACCOUNT` | 가입 7일 미만 | 5 (LOW) | | |

- ✅ 4개는 ERD `case_marker.rule_code`에 있는 값입니다. 하나라도 걸리면 케이스를 엽니다(`RULE`). 나머지는 점수에만 더하는 보조 신호라 보조 신호만으로는 케이스를 열지 않습니다 (정상 다구매 고객 보호).
- 모든 값은 `app_policy`의 `risk.rule.*` 키로 바꿀 수 있습니다 (예: `risk.rule.fast_click.t1 = 20`, `.p1`, `.t2`, `.p2`). k6 봇 시나리오로 탐지율 90%·오탐률 5%를 맞추며 조정합니다.

## 보안 설계: 봇이 점수를 피하는 길 막기

| 회피 시도 | 막는 방법 | 테스트 |
|---|---|---|
| 빠른 클릭 사이에 느린 요청 수천 건을 섞어 평균을 사람처럼 만들기 | 평균이 아니라 **빠른 간격의 개수**를 셈. 목록을 자르지 않고 전부 셈(메모리는 평균·분산만) | 빠른 25회 + 느린 10만 회 → 여전히 FAST_CLICK |
| 고정 간격 매크로가 1시간 공백을 끼워 규칙성 흐리기 | 10분 넘는 간격은 규칙성 통계에서 제외 | 공백 섞어도 REGULAR_INTERVAL |
| 나쁜 행동을 더 해서 오히려 점수 낮추기 | 모든 규칙이 관측값에 단조 증가, 단계 역전 설정 금지 | 무작위 입력 2만 개 × 9가지 "더 나쁘게" → 점수가 내려간 적 0번 |
| 잠깐 조용히 있다가 다시 시작 | 이전 점수는 반감기(30일)로만 줄어듦. 1시간 쉬어도 90 → 89.9 | ✅ |
| 이전 점수 시각을 미래로 → 감쇠 계산이 커짐 | 경과 시간 음수면 0으로 | 10년 뒤 시각 → 점수 그대로 |
| 관리자가 오탐 해제(CLEAR)한 뒤 1분 배치가 같은 증거로 다시 잡음 | CLEARED면 `windowFrom ≥ clearedAt` 아니면 **예외** | ✅ |
| 서버 시계 차이로 생긴 음수 간격 | 버리지 않고 0ms(빠른 쪽)로 셈 | ✅ |
| 선점 시각 순서 뒤바뀜으로 동시 계정 놓치기 | 앞선 시각은 직전 시각으로 봄 | ✅ |
| 좌석 수·선점 수를 폭증시켜 배치 서버 메모리 고갈 | 좌석 5만 개·창 10만 건 상한. 상한에 닿아도 이미 센 최댓값은 유지 | ✅ |
| 집계 버그로 NaN이 들어가 규칙이 조용히 꺼짐 (NaN은 모든 비교가 false) | 입력에 NaN·무한대·음수·모순 값이 있으면 **예외** | ✅ |
| 운영 설정을 잘못 바꿔 탐지가 꺼짐 (`NaN`, 0, 단계 역전, 문턱 1계정) | 정책 생성 시 예외 → 이전 정책 유지 | 설정 19가지 거부 |
| 해시 자리에 원문 휴대폰 번호 등 개인정보가 들어감 | `subjectHash`는 소문자 16진수 64자만 | ✅ |
| 근거 JSON에 외부 문자열 주입 | 근거에는 enum 이름과 숫자만. 지수 표기도 없음 | ✅ |

## 한계 (솔직하게)

- **모의 CI는 이름+휴대폰으로 만듭니다.** 휴대폰 번호를 여러 개 가진 사람은 CI를 여러 개 만들 수 있습니다. 그래서 결제 수단·기기 점수를 같이 보고 회원 패널티는 셋 중 최댓값(`risk.member_penalty_rule = MAX`, A 담당)으로 합니다.
- **간격에 무작위 지터를 넣는 매크로**는 REGULAR_INTERVAL을 피할 수 있습니다. 대신 지터를 넣어도 200ms 미만으로 빠르면 FAST_CLICK에 걸리고, 사람 속도로 느리게 하면 봇의 이점이 없어집니다.
- **기기 지문은 클라이언트가 만듭니다.** 바꿔 가며 기기 점수를 피할 수 있지만 CI 점수는 그대로 쌓입니다.
- 감쇠된 이전 점수가 80 이상이면 배치마다 `openCase = true`가 나옵니다. **대상당 OPEN 케이스는 1건만** 두도록 저장 쪽에서 막아야 합니다 (케이스 생성 서비스에서 처리 예정).

## 점수 캐시 (RISK-03)

대기열(A)은 `risk:{CI|PAYMENT|DEVICE}:{hash}`만 읽고, **키가 없으면 0점**으로 봅니다. 그래서 캐시가 비는 것이 곧 보안 구멍입니다 (fail-open). 아래 규칙으로 캐시가 저절로 비지 않게 합니다.

| 규칙 | 코드 | 이유 |
|---|---|---|
| TTL 없음. 0점이 되면 그때 삭제 | `RiskScoreCache.put` | 시간이 지나 저절로 풀리면 "쉬었다 오면 통과"가 됨 |
| 값은 `"80.50"` 같은 숫자 문자열만 (0~100, 소수 둘째 자리) | `RiskScoreCache.format` | A가 `Double.parseDouble`로 읽음 |
| 키는 A의 `QueueKeys.risk()`로 만들고, 해시가 소문자 16진수 64자가 아니면 거부 | `RiskScoreCache.key` | 키 형식 어긋남, 원문 개인정보·SCAN 패턴(`*`) 주입 방지 |
| 저장 순서: Oracle `risk_score` 커밋 → Redis. 바깥 트랜잭션이 있으면 그 커밋 뒤 | `RiskScoreStore.save` | 롤백된 점수가 캐시에만 남지 않게. Oracle이 원본 |
| 관리자 판정(`review_status`)은 다시 계산해도 덮어쓰지 않음 | `RiskScoreStore` MERGE | CONFIRMED·CLEARED가 배치에 지워지지 않게 |
| 관리자가 점수를 바꾸면 `refreshCache` 호출 → 바로 반영 | `RiskScoreStore.refreshCache` | 오탐 해제가 재동기화(최대 10분)를 기다리지 않게 |
| 앱 시작 직후 + 10분마다 Oracle → Redis 재동기화. 빠진 키는 채우고, Redis에만 남은 키는 삭제 | `RiskCacheResync` | Redis 재시작·쓰기 실패 자동 복구 |
| 재동기화 완료 시각을 `riskcache:synced_at`에 기록 | `RiskScoreCache.markSynced` | 대기열이 "캐시가 준비됐는지" 알 수 있게 (아래 A 요청) |
| 위험 점수 작업은 전용 스레드 1개(`risk-1`)에서 | `RiskJobRunner` | 대기열 입장 스케줄러(1초)를 막지 않고, 배치와 재동기화가 서로 덮어쓰지 않음 |

설정: `jejari.risk.cache-resync-enabled`(기본 true), `jejari.risk.cache-resync-interval`(기본 10m). `model_version`은 `model_run`에서 켜진(`is_active='Y'`) RULE 모델 버전을 씁니다.

| 대상 | 내용 |
|---|---|
| 강동균 (ERD) | `app_policy`에 `risk.rule.*` 기본값 행 추가 (지금은 코드 기본값으로 동작, 없어도 됨) |
| 김성원 (A) | 대기열에서 `risk:{CI\|PAYMENT\|DEVICE}:{hash}` 셋 중 MAX, RESTRICTED면 100 (구현됨) |
| 김성원 (A) | **요청 1** `riskcache:synced_at` 키가 없으면(재동기화 전) 그 회원 점수를 Oracle `risk_score`에서 직접 읽기. 캐시가 빈 순간 0점 통과 방지 |
| 김성원 (A) | **요청 2** `risk:*` 값이 숫자가 아니거나 0~100 밖이면 지금은 예외 → 100점으로 보고 경고 로그 (오염된 값이 통과로 이어지지 않게) |
| 강동균 (ERD) | `redis_keys`: `risk:{subjectType}:{hash}` TTL 없음 명시, `riskcache:synced_at`(STRING, 재동기화 완료 시각) 추가 |
| 강동균 (ERD) | `risk_score_history.history_id`용 시퀀스 (`CREATE SEQUENCE risk_score_history_seq`). 생기면 저장 때 이력도 남김 |
| 조영준 (E) | k6 봇 시나리오: 빠른 클릭·같은 좌석 반복·다계정 동시 선점·구매 후 즉시 취소 4종 + 정상 사용자 → 정답 라벨(`synthetic_label`)로 탐지율·오탐률 측정 |

## 테스트

실행: 저장소 루트에서 `./gradlew test --tests 'com.jejari.risk.*'` (엔진 48개 + 캐시 형식 10개). 캐시 통합 테스트는 `docker compose up -d` 뒤 `./gradlew infraTest --tests 'com.jejari.risk.*'` (7개: 저장·0점 삭제·판정 유지·롤백 시 캐시 안 씀·커밋 뒤 씀·refreshCache·재동기화).

- 규칙마다 문턱 바로 아래·문턱·높은 단계 경계값
- 케이스: marker 규칙 → RULE, 80 이상 → RISK_THRESHOLD, 보조 신호만 → 케이스 없음
- 감쇠: 30일 → 절반, 60일 → 1/4, 미래 시각, CLEAR
- 무작위 입력 2만 개: 점수 0~100, JSON 형식 / 단조성 2만 × 9
- 회피 시나리오 7개, 봇 시나리오 → 100점, 정상 사용자 시나리오 → 0점
- 입력·설정 검증: NaN·무한대·음수·모순·해시 형식, 잘못된 설정 19가지
