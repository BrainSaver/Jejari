# 규칙 기반 위험 점수 엔진 (RISK-02)

작성자: 강다인 · 코드 위치: `src/main/java/com/jejari/risk/` (`com.jejari.risk.RiskEngine`, `SignalCollector`, `RiskPolicy`)

> 상태: 엔진 구현 완료 (단위 테스트 48개, 회피 시나리오·무작위 성질 검사 포함). 점수 저장(Oracle)·`risk:*` 캐시 쓰기·재동기화(RISK-03) 구현 완료. **1분 배치(입력 집계 → 엔진 → 저장) 구현 완료 (2026-11-17, 아래 "1분 배치")**. **의심 케이스 자동 생성(RISK-04) 구현 완료 (2026-11-17, ERD v19 반영)**.

## 한 줄 요약

CI·결제 수단·기기마다 행동 신호를 모아 규칙별 배점을 더하고(최대 100), 지난 점수는 반감기 30일로 줄여 둘 중 큰 값을 최종 점수로 한다. 점수 80 이상이거나 핵심 규칙이 하나라도 걸리면 의심 케이스를 연다.

## 사용법

```java
RiskEngine engine = new RiskEngine(RiskPolicy.fromMap(appPolicyMap));   // 설정이 잘못되면 예외 → 이전 정책 유지

// 대상 하나마다 (예: CI 해시)
SignalCollector c = new SignalCollector(engine.policy(), SubjectType.CI, ciHash, windowFrom);
mongoCursor.forEach(e -> {                           // behavior_log, ts 오름차순
    if (e.intervalMs() != null) c.interval(e.intervalMs());
    if (e.type() == SEAT_HOLD) {
        c.seatHold(e.ts(), e.memberId());
        if (e.status() == 409) c.seatHoldFailure(e.seatId());
    }
});
purchases.forEach(p -> c.purchase(p.seatCount()));                 // 결제 확정
userCancels.forEach(x -> c.userCancel(x.minutesAfterPurchase(), x.minutesBeforeDeparture())); // USER만
c.linkedAccounts(accountCount).oldestAccountCreatedAt(oldestCreatedAt, now);

RiskResult r = engine.score(c.build(), previousOrNull, now);
// → risk_score UPSERT (final_score, rule_score, reasons = r.reasonsJson(), 신호 컬럼들)
// → r.openCase()면 suspicious_case(trigger_type = r.triggerType()) + r.markerReasons()로 case_marker
```

## 규칙과 기본 배점

| 코드 | 무엇을 보나 | MID | HIGH | 케이스 |
|---|---|---|---|---|
| `FAST_CLICK` | 200ms 미만 요청 간격 **개수** | 20회 → 25점 | 60회 → 35점 | ✅ |
| `SAME_SEAT_RETRY` | 한 좌석 선점 실패(409) 최대 횟수 **또는** 여러 좌석의 재시도 실패 합(좌석마다 실패 수 − 1) 중 큰 값 | 5회 → 20 | 15회 → 30 | ✅ |
| `CANCEL_AFTER_PAY` | 구매 후 30분 안 취소 수 | 2건 → 15 | 5건 → 25 | ✅ |
| `MULTI_ACCOUNT_SYNC` | 60초 안에 선점한 서로 다른 계정 수 | 2개 → 30 | 3개 → 40 | ✅ |
| `REGULAR_INTERVAL` | 간격 변동계수 ≤ 0.05 (30건 이상) | 15 | | ✅ (v24부터) |
| `LINEAR_MOUSE` | 화면 녹화의 **기계적 마우스 이동 수** (클릭 자리로 순간이동 + 직선·등속 이동, 마우스 클릭만) | 8회 → 25 | 20회 → 40 | ✅ (11-23부터) |
| `HIGH_CANCEL_RATIO` | 취소 비율 (구매 4건 이상일 때만) | 50% → 10 | 80% → 20 | |
| `LAST_MINUTE_CANCEL` | 출발 3시간 이내·출발 후 취소 수 | 3건 → 10 | 6건 → 15 | |

| `LINKED_ACCOUNTS` | 연결 계정 수 (자기 포함) | 2개 → 10 | 4개 → 20 | |
| `NEW_ACCOUNT` | 가입 7일 미만 | 5 (LOW) | | |

- ✅ 6개는 ERD `case_marker.rule_code`에 있는 값입니다. 하나라도 걸리면 케이스를 엽니다(`RULE`). 나머지는 점수에만 더하는 보조 신호라 보조 신호만으로는 케이스를 열지 않습니다 (정상 다구매 고객 보호).
- 모든 값은 `app_policy`의 `risk.rule.*` 키로 바꿀 수 있습니다 (예: `risk.rule.fast_click.t1 = 20`, `.p1`, `.t2`, `.p2`). k6 봇 시나리오로 탐지율 90%·오탐률 5%를 맞추며 조정합니다.

## 한계 (솔직하게)

- **모의 CI는 이름+휴대폰으로 만듭니다.** 휴대폰 번호를 여러 개 가진 사람은 CI를 여러 개 만들 수 있습니다. 그래서 결제 수단·기기 점수를 같이 보고 회원 패널티는 셋 중 최댓값(`risk.member_penalty_rule = MAX`, A 담당)으로 합니다.
- **간격에 무작위 지터를 넣는 매크로**는 REGULAR_INTERVAL을 피할 수 있습니다. 대신 지터를 넣어도 200ms 미만으로 빠르면 FAST_CLICK에 걸리고, 사람 속도로 느리게 하면 봇의 이점이 없어집니다.
- **기기 지문은 클라이언트가 만듭니다.** 바꿔 가며 기기 점수를 피할 수 있지만 CI 점수는 그대로 쌓입니다.
- 감쇠된 이전 점수가 80 이상이면 엔진은 배치마다 `openCase = true`를 냅니다. 케이스 생성(`SuspiciousCaseOpener`)은 **새 증거일 때만** 열고 **대상당 열린 케이스 1건**만 둡니다 (아래 RISK-04).

## 1분 배치 (`risk/batch/`)

매분 **새 신호가 생긴 대상만** 다시 계산합니다. 전체 회원을 매번 계산하지 않습니다.

```
행동 로그 적재(BehaviorSink) ── CI·기기 ──┐
예약 확정·취소 이벤트(risk-signal) ─ CI·결제 수단 ─┼─SADD→ risk:dirty
하루 넘게 다시 계산 안 한 점수(감쇠 반영) ────┘
          │ RENAMENX → risk:dirty:work   (락 risk:batch:lock, 한 대만)
          ▼
대상마다: risk_score 현재 행 → 행동 로그(1일)·구매·취소(30일)·연결 계정 → 엔진 → 바뀌었으면 저장(+이력) → 캐시
```

| 대상 | 행동 신호 (Mongo) | 구매·취소 (Oracle) | 연결 계정 |
|---|---|---|---|
| CI | O | O (같은 CI 회원의 예약) | 같은 CI 회원 (탈퇴 포함) |
| 결제 수단 | - (행동 로그에 없음) | O (그 카드로 결제한 예약) | 그 카드를 등록한 회원 |
| 기기 | O | - (가족 공용 기기 오탐 방지) | 그 기기를 쓴 회원 |

| 규칙 | 이유 |
|---|---|
| 목록을 RENAMENX로 통째로 넘겨받고, 성공한 대상만 SREM | 계산 중 들어온 새 표시를 지우지 않음. 중간에 죽으면 work가 남아 이어서 함 |
| 표시(SADD) 실패는 예외 → 같은 묶음 재처리 | 표시를 잃으면 그 대상 점수가 안 바뀜 (fail-closed). SADD는 몇 번 해도 같아서 inbox 불필요 |
| 예약 이벤트는 예약 ID만 쓰고 해시는 Oracle에서 다시 읽음 | 토픽에 남의 해시를 넣어 재계산을 폭주시키는 것 방지 |
| 저장 조건 `shouldWrite`: 새 증거가 지배하면 값·근거가 바뀔 때만, 감쇠가 지배하면 1점 이상 내려갔거나 하루가 지났을 때만 | 매분 저장하면 1분 감쇠량이 반올림에 지워져 **점수가 영원히 줄지 않음** (테스트로 재현) |
| 처음 보는 대상이 0점이면 행을 만들지 않음 | 정상 회원 전원의 0점 행이 쌓이지 않게 |
| 규칙 값은 배치마다 app_policy `risk.rule.*`에서. 잘못된 값이면 **이전 정책 유지** | 기본값으로 돌아가 운영자가 강화한 문턱이 조용히 풀리는 것 방지 |
| 대상 하나 실패 → 다음 배치로 미루고 나머지 계속 | 한 대상 때문에 전체가 멈추지 않게 |

설정: `jejari.risk.batch-enabled`(주기 실행), `batch-interval`(1m), `batch-max-run`(40s), `behavior-window`(1d), `purchase-window`(30d), `decay-refresh-after`(1d), `signal-listener-enabled`.

## 의심 케이스 자동 생성 (RISK-04, `SuspiciousCaseOpener`)

배치가 점수를 저장할 때 **같은 트랜잭션에서** 케이스를 엽니다. 따로 하면 점수만 저장되고 케이스가 빠졌을 때, 다음 배치는 "바뀐 게 없다"며 둘 다 건너뜁니다.

| 조건 | 결과 |
|---|---|
| 규칙 점수 ≥ 80 (새 증거가 점수를 만듦) | `RISK_THRESHOLD` |
| 아니면 마커 규칙(FAST_CLICK·SAME_SEAT_RETRY·CANCEL_AFTER_PAY·MULTI_ACCOUNT_SYNC·REGULAR_INTERVAL·LINEAR_MOUSE)이 하나라도 걸림 | `RULE` |
| 감쇠한 이전 점수가 지배 (새 증거 아님) | 열지 않음. 관리자가 닫은 케이스가 같은 증거로 다시 열리지 않게 |
| 같은 증거로 다시 계산 (저장 안 함) | 열지 않음 |
| 이 대상에 OPEN·REVIEWING 케이스가 있음 | 열지 않음 (DB 유니크 인덱스로도 보장) |

- **마커**: 걸린 마커 규칙마다 `case_marker`(AUTO) 1개. 위치는 그 규칙의 마지막 근거 이벤트 시각, 세션은 그 이벤트 세션 (auth_session에 없으면 비움). 구매 직후 취소는 Oracle 기록이라 세션이 없습니다.
- **의심 구간**: 마커 근거 이벤트의 처음 ~ 끝, 앞뒤 1분. 마커 없이 점수만 넘으면 행동 로그를 센 기간 전체.
- **설명**(`trigger_detail`, `label`): "200ms 미만 간격 요청 30회", "구매 후 30분 안 취소 2건"처럼 숫자와 고정 문구만. 200바이트(한글 약 66자)를 넘으면 글자 단위로 자릅니다.
- **검토 상태**: `risk_score.review_status`가 NONE이면 PENDING으로. CLEARED·CONFIRMED는 그대로 둡니다 (CLEARED를 풀면 엔진이 CLEAR 이전 증거를 다시 셈).

## 점수 캐시 (RISK-03)

대기열(A)은 `risk:{CI|PAYMENT|DEVICE}:{hash}`만 읽고, **키가 없으면 0점**으로 봅니다. 그래서 캐시가 비는 것이 곧 보안 구멍입니다 (fail-open). 아래 규칙으로 캐시가 저절로 비지 않게 합니다.

| 규칙 | 코드 | 이유 |
|---|---|---|
| TTL 없음. 0점이 되면 그때 삭제 | `RiskScoreCache.put` | 시간이 지나 저절로 풀리면 "쉬었다 오면 통과"가 됨 |
| 값은 `"80.50"` 같은 숫자 문자열만 (0~100, 소수 둘째 자리) | `RiskScoreCache.format` | A가 `Double.parseDouble`로 읽음 |
| 키는 A의 `QueueKeys.risk()`로 만들고, 해시가 소문자 16진수 64자가 아니면 거부 | `RiskScoreCache.key` | 키 형식 어긋남, 원문 개인정보·SCAN 패턴(`*`) 주입 방지 |
| 저장 순서: Oracle `risk_score` 커밋 → Redis. 바깥 트랜잭션이 있으면 그 커밋 뒤 | `RiskScoreStore.save` | 롤백된 점수가 캐시에만 남지 않게. Oracle이 원본 |
| 관리자 판정(`review_status`)은 다시 계산해도 덮어쓰지 않음 | `RiskScoreStore` MERGE | CONFIRMED·CLEARED가 배치에 지워지지 않게 |
| 관리자가 점수를 바꾸면 `refreshCache` 호출 → 바로 반영 | `RiskScoreStore.refreshCache` | 오탐 해제가 재동기화(최대 10분)를 기다리지 않게 |
| 앱 시작 직후 + 10분마다 Oracle → Redis 재동기화. 빠진 키는 채우고, Redis에만 남은 키는 삭제 | `RiskCacheResync` | Redis 재시작·쓰기 실패 자동 복구 |
| 재동기화 완료 시각을 `risk:meta:synced_at`(A의 `QueueKeys.RISK_SYNCED_AT`)에 기록. 30초마다 확인해 없으면 즉시 재동기화 | `RiskCacheResync` | 이 키가 없으면 대기열은 캐시를 믿지 않고 요청마다 Oracle을 읽음. 그 시간을 짧게 |
| 위험 점수 작업은 전용 스레드 1개(`risk-1`)에서 | `RiskJobRunner` | 대기열 입장 스케줄러(1초)를 막지 않고, 배치와 재동기화가 서로 덮어쓰지 않음 |
| 캐시가 준비 안 됐을 때 대기열이 부르는 Oracle 조회 (`RiskScoreFallbackPort` 구현): 회원의 CI·결제·기기 점수 최댓값, 해시 형식이 틀리면 예외 → 대기열이 100점 | `OracleRiskScoreFallback` | 모르면 막는 쪽 (fail-closed) |
| 개발 모드(`jejari.dev-mode=true`)에서는 재동기화·Oracle 조회를 끄고 A의 개발용 대체품을 씀 | `@Conditional…` | 부하 테스트가 Redis에 직접 넣은 점수를 재동기화가 지우지 않게 |

설정: `jejari.risk.cache-resync-enabled`(기본 true), `jejari.risk.cache-resync-interval`(기본 10m), `jejari.risk.cache-marker-check-interval`(기본 30s). `model_version`은 `model_run`에서 켜진(`is_active='Y'`) RULE 모델 버전을 씁니다.

## 팀 확인 필요

| 대상 | 내용 |
|---|---|

## 바뀐 것 (2026-11-18)

- **SAME_SEAT_RETRY에 여러 좌석 합산**: 조영준 님 경계 측정에서 "좌석마다 4번씩"처럼 문턱(5) 아래로 나누면 0점이었다. 같은 좌석을 **다시** 눌러 또 실패한 횟수를 모든 좌석에 걸쳐 더해, 한 좌석 최댓값과 비교해 큰 쪽을 쓴다. 좌석마다 4번씩 2좌석이면 3+3 = 6 → 걸림
  - 첫 실패는 세지 않는다: 이미 잡힌 좌석을 한 번 만나고 다른 좌석으로 가는 건 사람도 흔하다 (정상 노이즈 "같은 좌석 409 1~2번"은 최대 1)
  - 문턱 바로 아래에 작은 점수를 주는 방법은 쓰지 않았다: 정상 회원 노이즈(연타 1~4번, 409 1~2번)까지 점수를 받게 된다
- **REGULAR_INTERVAL을 마커 규칙으로**: 일정 간격 매크로가 이 규칙(15점)에만 걸려 케이스가 안 열렸다. 강동균 님 ERD v24(`case_marker.rule_code` CHECK에 추가) 뒤 `RiskRule` marker를 true로. 마커 구간은 규칙성 통계에 들어간 요청(10분 넘는 공백 제외)의 처음~끝, 설명은 "요청 간격이 기계처럼 일정함 (변동계수 0.001)"
  - 기존 DB는 `db/patch/v24.sql`을 먼저 실행해야 한다 (안 하면 ORA-02290으로 케이스 열기 실패)

## 케이스에 묶인 세션과 이유 남기기 (case_session, 2026-11-19)

강동균 님 지적: 설계는 "케이스를 열 때 `case_session`에 연결 계정을 박아 둔다"인데, 구현은 화면을 열 때마다 `RiskInputReader.membersOf`로 **실시간 조회**만 했다. 그래서 **"왜 이 계정이 묶였는지"가 안 나오고**, 나중에 기기 연결이 바뀌면 **조사 당시 묶음이 사라졌다** (증거 보존 문제). → 설계대로 채운다 (1번 길). 실시간 조회의 장점은 남긴다.

- **열 때** (`SuspiciousCaseOpener`): 대상의 연결 계정이 **의심 구간 안에서 쓴 로그인 세션**을 `behavior_log`에서 찾아(최대 200개) 케이스와 같은 트랜잭션에 넣는다
  - 마커 근거가 된 세션 → `TRIGGER`, 나머지 → 대상 종류대로 `SAME_CI` / `SAME_DEVICE` / `SAME_PAYMENT` (`SAME_IP`는 IP로 묶지 않아서 안 씀)
  - `auth_session`에 없는 세션(가상 데이터·옛 로그)은 FK 때문에 넣지 않음
- **볼 때** (`CaseAdminService.accounts`): 열 때 묶은 계정 ∪ 지금 연결된 계정. 계정마다 이유 표시 — 탐지된 세션 · 같은 명의 · 같은 기기 · 같은 카드 · **연 뒤 연결**(열 때는 없었는데 지금 연결됨)
- 녹화 재생도 묶어 둔 세션을 포함 (그 뒤 연결이 바뀌어도 재생 가능)
- 점수 계산은 그대로 → 봇 대회 전 규칙 동결과 무관
- `sync_offset_ms`(여러 세션 동시 재생 보정)는 아직 비워 둠
- 테스트: `RiskScoreBatchInfraTest` — 봇 세션 TRIGGER, 같은 명의 다른 계정 SAME_CI, 남의 계정 제외, auth_session 없는 세션 제외

## 마우스 궤적 규칙 LINEAR_MOUSE (2026-11-23, 봇 대회 1차 뒤 보강)

**왜**: 1차 대회에서 두 봇(botb·botc) 모두 규칙 케이스 0건. 화면 녹화(ADM-11)는 마우스 궤적을 남기는데 그걸로 판정하는 코드가 없었다. ERD `case_marker.rule_code` CHECK에는 `LINEAR_MOUSE`가 처음부터 있었다 → ERD 패치 없이 케이스를 여는 규칙으로.

### 무엇을 세나 (`risk/MouseMotion`)

| 신호 | 판정 | 누가 이렇게 움직이나 |
|---|---|---|
| **클릭 자리로 순간이동** | 녹화된 **연속한 두 점이 모두 서로 다른 마우스 클릭 자리(±3)** 에 있고 150 이상(화면의 15%) 떨어짐 = 클릭에서 다음 클릭으로 중간 점 없이 | 브라우저 자동화 기본 클릭 (요소 가운데로 한 번에 이동) |
| **직선·등속 이동** | 한 묶음 안 연속 5점이 현/호 ≥ 0.98, 구간 속도 변동계수 ≤ 0.15, 100 이상 이동 | 자동화 도구의 "n단계로 나눠 이동" |

- 좌표는 화면 비율 0~1000. **시각 대신 점의 순서와 자리로** 판정한다: 녹화기는 클릭은 바로, 궤적은 몇 초마다 묶어 보내서 궤적 점의 절대 시각을 정확히 알 수 없다. 직선 판정의 속도는 같은 묶음 안의 상대 시각이라 정확하다
- 세션마다 따로 세고 더한다 (다른 세션의 점끼리 이어 붙이면 없는 순간이동이 생김). 대상(CI·기기)당 최근 녹화 세션 50개, 세션당 이벤트 5,000개까지 (`RiskInputReader.mouse`)
- **개수**로 센다 (비율 아님) → 정상 이동을 섞어도 줄지 않는다 (단조성 시험에 추가)
- 케이스 마커의 세션 = 그 기간 마지막 녹화 세션 → 관리자가 A-06에서 바로 재생. `auth_session`에 없으면(예전 녹화기) 비움 (FK)
- 설명: "마우스가 기계처럼 움직임 (클릭 자리로 순간이동·직선 등속 17회)"
- 문턱: `risk.rule.linear_mouse.t1/p1/t2/p2` (기본 8 → 25점, 20 → 40점)
