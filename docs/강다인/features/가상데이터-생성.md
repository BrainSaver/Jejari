## 한 줄 요약

정상 회원과 봇 4종을 수천 명 규모로 DB에 바로 만든다. 시나리오 12와 **같은 이메일 라벨 규칙**이라 `eval_risk.sh`로 그대로 탐지율·오탐률을 잰다. 시나리오 12는 "지금 들어오는 트래픽", 이건 "이미 쌓여 있는 데이터"를 맡는다.

## 실행 (PowerShell, 앱은 꺼 둔 상태에서)

```powershell

# 3) 지우기
cd C:\jjr

```

생성기가 끝날 때 위험 점수 배치를 그 자리에서 다 돌린다. 처음엔 "생성 → 앱 켜기 → 1분 기다리기 → 평가"였는데, 앱을 켜지 않고 평가해서 **탐지율 0%**(점수가 하나도 계산되지 않은 상태)가 나온 일이 있어 순서를 없앴다.

태그는 영문 소문자·숫자 8자 이내, 같은 태그로 두 번 만들 수 없음. `--jejari.synthetic.seed=…`로 같은 모양을 다시 만들 수 있음.

### 정상 회원의 사람다운 모습 (조영준 님 점검 반영, 2026-11-17)

이메일 라벨은 모두 `normal`(정답 NORMAL)이라 `eval_risk.sh`가 그대로 읽는다. 범위는 **규칙 문턱이 아니라 "그런 사람이 실제로 어떻게 하나"로 정한 [가정]**이다 (근거 통계를 찾으면 바꿈).

| 모습 | 비율 | 데이터 | 가까이 가는 규칙 |
|---|---|---|---|
| 더블클릭·새로고침 연타 | 정상의 30% | 200ms 미만 간격 1~4번 (60~190ms) | FAST_CLICK (문턱 20) |
| 인기 좌석 경합 | 정상의 15% | 같은 좌석 409 1~2번 → 다른 좌석 성공 | SAME_SEAT_RETRY (문턱 5) |
| family 가족 다구매 | 정상의 6% | 3~6건 × 3~4매 | BULK_PURCHASE (누적 20매) |
| replan 일정 변경 | 4% | 4~7건, 건마다 50%를 1시간~2일 뒤 취소 | HIGH_CANCEL_RATIO (4건 이상, 50%) |
| biz 출장자 | 4% | 4~8건 × 1매, 건마다 40%를 출발 10분~10시간 전 취소 | LAST_MINUTE_CANCEL (180분 안 3건) |

보조 규칙(BULK·HIGH_CANCEL·LAST_MINUTE·LINKED)은 10~20점이라 케이스 문턱 80을 혼자 넘지 못한다. 그래서 정상 회원이 이 규칙에 걸려도 **점수는 오르지만 케이스(=탐지)는 열리지 않는 것**이 설계대로의 동작이고, 이번 데이터로 그걸 처음 확인할 수 있게 됐다.

결제 번호는 앱과 같이 `payment_id = reservation_id`. 처음엔 `payment_seq`를 써서, 앱으로 결제한 적 있는 DB(각자 PC·공용 서버)에서 `ORA-00001 PK_PAYMENT`로 멈췄다 (조영준 님 발견).

- 회원·카드·기기·`member_device`·행동 로그(최근 3시간)·과거 예약·결제·취소(최근 20일)를 만들고 `risk:dirty`에 표시.
- CI(`mockCiHash`)·전화 암호화(`PiiCipher`)·카드·기기 해시(`Pseudonymizer`)가 **실제 가입과 같은 함수**라 대기열·위험 점수·관리자 화면이 똑같이 읽는다. 카드번호는 `9`로 시작하는 가짜 16자리.
- 과거 이력은 **태그 전용 "출발한 운행"**(run_id 880001~)에 쌓는다. 판매 중 운행·테스트용 9001·9002의 좌석 재고는 건드리지 않는다.
- 비밀번호는 만들지 않음 (로그인 안 함, Argon2 1,000번은 느림).
