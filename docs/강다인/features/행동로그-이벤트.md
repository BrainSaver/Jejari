# 행동 로그 수집 (RISK-01)

작성자: 강다인 · 코드 위치: `src/main/java/com/jejari/behavior/`

> 상태: 구현 완료 (단위 테스트 22개, Kafka·MongoDB 통합 테스트 3개). **A·B·C 파트가 자기 API에서 한 줄씩 남겨야 하는 팀 약속**이 있습니다. 원천은 ERD `behavior_log`, 기능설계서 8장, concurrency.md §13.

## 한 줄 요약

사용자의 주요 요청마다 이벤트 한 건을 Kafka `jejari.behavior`로 보내고, 적재 컨슈머가 MongoDB `behavior_log`에 묶어서 저장한다. 위험 점수와 의심 구간 타임라인의 재료다.

## 다른 파트가 할 일: 한 줄

```java
import com.jejari.behavior.BehaviorLog;
import com.jejari.behavior.BehaviorType;

// 컨트롤러 안에서, 예외를 던지기 전에. 회원·세션·IP·기기·UA·응답 코드·시각은 자동으로 채워진다
BehaviorLog.mark(BehaviorType.SEAT_HOLD, runId, Map.of("seatIds", seatIds, "seatCount", seatIds.size()));
```

- **static 메서드라 주입이 필요 없다.** `@WebMvcTest`처럼 행동 로그가 없는 테스트에서도 그냥 아무 일도 안 해서 테스트가 깨지지 않는다.
- 요청에 표시만 하고, 요청이 끝날 때 인터셉터가 **최종 응답 코드**(예외 처리 후 409 등)를 붙여 한 번 보낸다. 실패 요청도 꼭 남긴다 — 같은 좌석 반복 실패가 봇 신호다.
- `meta`에는 **ID·숫자·코드만**. 아래 모양이 아닌 값은 자동으로 빠지고 경고 로그가 남는다.

| 통과 | 빠짐 |
|---|---|
| 숫자, true/false, enum, 코드 문자열(영문·숫자·`_-:.` 64자), 그 목록(50개까지) | 한글·공백·`@`가 든 문자열(이름·이메일), 숫자만 9자리 이상인 문자열(휴대폰·카드), 중첩 객체, 이상한 키(`$where`, `a.b`), 키 21개째부터 |

## 이벤트 종류

| eventType | 남기는 곳 (담당) | runId | meta |
|---|---|---|---|
| `VIEW_TRAIN` | 운행 검색 TRN-02 (B) | 없음 | `fromStationId`, `toStationId`, `travelDate`, `resultCount` |
| `VIEW_SEAT` | 좌석 배치도 RSV-01 (B) | O | `carNo`, `grade` |
| `QUEUE_ENTER` | 대기열 진입 QUE-01 (A) | O | `ticketNo`, `rejected`(중복 진입 거절이면 true) |
| `SEAT_HOLD` | 좌석 선점 RSV-02 (B) | O | `reservationId`(성공 시), `seatIds`, `seatCount`, `errorCode`(실패 시) |
| `PAY` | 결제 시작 PAY-01 (C) | O | `reservationId`, `amount`, `errorCode` |
| `CANCEL` | 결제 전 취소 RSV-05 (B), 확정 취소 CNL-02 (D) | O | `reservationId`, `cancelKind`(`BEFORE_PAY` / `CONFIRMED`), `seatCount`, `minutesAfterPurchase`, `minutesBeforeDeparture` |

결제 승인·만료처럼 사용자 요청이 아닌 결과는 여기 남기지 않는다 (outbox `jejari.reservation`이 있음).

## 어떻게 동작하나

```
요청 → 인터셉터 preHandle(시각) → 컨트롤러 mark() → afterCompletion(응답 코드)
     → 전용 스레드 큐 → Kafka 전송 (요청 스레드는 안 기다림)
     → behavior-sink 컨슈머: poll(최대 behavior.batch_size건) → 형식 재검사 → ci_hash 붙이기
       → interval_ms 계산 → insertMany(ordered:false) → 성공하면 간격 기억·오프셋 커밋
```

## 설계 판단

| 판단 | 이유 |
|---|---|
| **요청은 절대 기다리지 않음**: 전용 스레드 + 5만 건 큐, 넘치면 버리고 개수 경고. 전용 프로듀서(메타데이터 대기 2초, acks=1, lz4) | Kafka가 죽어도 예매 응답은 그대로 (테스트: 1000건 보내기 0.5초 이내). 로그 몇 건 유실 < 예매 지연. 팀 공용 프로듀서(acks=all, 예약 이벤트용)와 설정을 섞지 않음 |
| **Kafka 키 = 회원 ID** (비로그인이면 기기 해시 → IP 해시). ci_hash는 **컨슈머가 member_id로 찾아 붙임**(캐시) | 초안은 키를 ci_hash로 했지만, 그러려면 요청마다 DB 조회가 필요. 같은 회원의 이벤트는 같은 파티션으로 가서 세션 간격 계산은 그대로 됨. CI는 바뀌지 않아 캐시 안전 |
| **클릭 간격은 저장에 성공한 뒤에만 기억** | Mongo 장애로 같은 묶음을 다시 처리할 때 이미 기억한 시각과 비교하면 간격이 전부 0이 되어, 정상 사용자가 초고속 클릭(FAST_CLICK)으로 잘못 찍힘. 테스트로 고정 |
| **중복은 event_id 유니크 인덱스**, 중복 키 오류(11000)만이면 성공으로 봄 | Kafka 재전달 시 같은 이벤트가 두 번 저장되면 반복 횟수가 부풀어 위험 점수가 틀어짐 |
| **인덱스를 컨슈머가 직접 보장** (`ux_event_id`, `ttl_expire_at`) | `mongo-init.js`는 볼륨을 처음 만들 때만 돈다. 실제로 기존 볼륨에 v16 유니크 인덱스가 없어 중복이 저장됐음. TTL이 없으면 개인 행동 기록이 보관 기간(180일) 뒤에도 남음. 만들 수 없는 상태(이미 중복 존재 등)면 적재는 계속하고 오류 로그 |
| **토픽 메시지를 다시 검사** | Kafka 토픽에는 인증이 없어 누구나 넣을 수 있다고 봄. UUID·해시(64자 hex)·채널·상태 코드·크기를 검사하고 meta도 다시 거름. 원문 IP가 든 메시지는 버림. 깨진 메시지는 건너뛰어 컨슈머가 멈추지 않음 |
| **Mongo 장애는 5초마다 무한 재시도** (커밋 안 함) | Kafka 7일 보관 동안 잃지 않음 |
| 기기 ID 헤더(`X-Device-Id`)는 8~128자 영문·숫자·`_-`만, 아니면 버림. UA는 제어 문자 제거·300자 | 클라이언트가 보내는 값이라 로그 위조·폭탄 방지 |

정책값: `behavior.retention_days`(180, 30~730), `behavior.batch_size`(1000, 100~5000). 범위 밖이면 기본값. 끄기: `jejari.behavior.enabled=false`, 컨슈머만 끄기: `jejari.behavior.sink-enabled=false`.

## 위험 점수 규칙과의 연결

| 규칙 | 쓰는 이벤트·필드 |
|---|---|
| FAST_CLICK | `interval_ms` (세션 안 간격이 기준 미만으로 반복) |
| SAME_SEAT_RETRY | `SEAT_HOLD` + `meta.seatIds` + `response_status = 409` |
| CANCEL_AFTER_PAY | `CANCEL` + `meta.minutesAfterPurchase` |
| MULTI_ACCOUNT_SYNC | 같은 `ci_hash`, 다른 `member_id`의 `SEAT_HOLD`가 짧은 시간 안에 |

타임라인(ADM-05)은 인덱스 `{member_id: 1, ts: 1}`로 회원의 이벤트를 시간순으로 읽는다.

## 팀 확인 필요

| 대상 | 내용 |
|---|---|
| 김성원 (A) | `QueueController.enter`에 `BehaviorLog.mark(QUEUE_ENTER, runId, Map.of("ticketNo", …))` (중복 진입 거절이면 `"rejected", true`) |
| 강동균 (B) | 좌석 선점 컨트롤러에 `mark(SEAT_HOLD, …)` — **실패(409)도 남기도록 예외 전에**. 좌석 배치도 `VIEW_SEAT`, 운행 검색 `VIEW_TRAIN` |
| C 담당 | 결제 시작에 `mark(PAY, …)` |
| 프런트 | `X-Device-Id` 헤더: 1차는 localStorage UUID (8~128자 영문·숫자·`_-`), `X-Channel: APP`(앱일 때만) |
