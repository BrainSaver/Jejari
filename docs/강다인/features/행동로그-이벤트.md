# 행동 로그 이벤트 스키마 (RISK-01)

작성자: 강다인 · 코드 위치: `behavior/` (예정)

> 상태: 설계 초안 (코드 전). **A·B·C 파트가 자기 API에서 이벤트를 남겨야 하는 팀 약속**이라 먼저 고정합니다. 원천은 ERD `behavior_log`, 기능설계서 8장, concurrency.md §13.

## 한 줄 요약

사용자의 주요 요청마다 이벤트 한 건을 Kafka `jejari.behavior`로 보내고, 적재 컨슈머가 MongoDB `behavior_log`에 1000건씩 저장한다. 위험 점수와 의심 구간 타임라인의 재료다.

## 다른 파트가 할 일: 한 줄

```java
// 컨트롤러 안에서. 공통 필드(회원·세션·IP·기기·UA·응답 코드·시각)는 자동으로 채워진다
behaviorLog.mark(BehaviorType.SEAT_HOLD, runId, Map.of(
    "reservationId", id, "seatIds", seatIds, "seatCount", seatIds.size()));
```

- `mark()`는 요청 속성에 기록만 하고, 요청이 끝날 때 `HandlerInterceptor.afterCompletion`이 응답 코드를 붙여 한 번 보냅니다. **실패한 요청(409 등)도 보내야 합니다.** 같은 좌석 반복 실패(SAME_SEAT_RETRY)가 위험 신호입니다.
- 예외로 컨트롤러가 끝나도 `afterCompletion`은 실행되므로, 예외를 던지기 전에 `mark()`를 먼저 부릅니다.

## 이벤트 종류

| eventType | 남기는 곳 (담당) | runId | meta |
|---|---|---|---|
| `VIEW_TRAIN` | 운행 검색 TRN-02 (B) | 없음 | `fromStationId`, `toStationId`, `travelDate`, `resultCount` |
| `VIEW_SEAT` | 좌석 배치도 RSV-01 (B) | O | `carNo`, `grade` |
| `QUEUE_ENTER` | 대기열 진입 QUE-01 (A) | O | `ticketNo`, `rejected`(중복 진입 거절이면 true) |
| `SEAT_HOLD` | 좌석 선점 RSV-02 (B) | O | `reservationId`(성공 시), `seatIds`, `seatCount`, `errorCode`(실패 시) |
| `PAY` | 결제 시작 PAY-01 (C) | O | `reservationId`, `amount`, `errorCode` |
| `CANCEL` | 결제 전 취소 RSV-05 (B), 확정 취소 CNL-02 (D) | O | `reservationId`, `cancelKind`(`BEFORE_PAY` / `CONFIRMED`), `seatCount`, `minutesAfterPurchase`, `minutesBeforeDeparture` |

- 결제 승인·만료처럼 사용자 요청이 아닌 결과는 여기 남기지 않습니다. 그건 outbox 이벤트(`jejari.reservation`)가 있고, 위험 점수는 둘 다 읽습니다.
- `meta`에는 ID·숫자·코드만 넣습니다. 이름·휴대폰·이메일·카드번호는 넣지 않습니다.

## 메시지 형식

토픽 `jejari.behavior`, 키 = `ciHash` (비로그인이면 `deviceHash`, 그것도 없으면 `ipHash`).

```json
{
  "eventId": "6f1c…(UUID)",
  "eventType": "SEAT_HOLD",
  "ts": "2026-11-20T10:00:00.123+09:00",
  "memberId": 1001,
  "ciHash": "a3f…(64)",
  "deviceHash": "9bc…(64)",
  "ipHash": "11d…(64)",
  "sessionId": "c2d…(UUID, auth_session.session_id)",
  "runId": 5001,
  "channel": "WEB",
  "userAgent": "Mozilla/5.0 …",
  "responseStatus": 409,
  "meta": { "seatIds": [12, 13], "seatCount": 2, "errorCode": "SEAT_ALREADY_TAKEN" }
}
```

| 필드 | 채우는 곳 | 비고 |
|---|---|---|
| `ts` | 인터셉터 `preHandle` 시각 (ms) | 응답 시각이 아니라 요청 시각. 클릭 간격 분석 기준 |
| `memberId`, `ciHash`, `sessionId` | 인증 정보 (JWT → 세션) | 비로그인이면 null |
| `deviceHash` | 헤더 `X-Device-Id` → `PiiHasher.device()` | 클라이언트가 만든 기기 지문 |
| `ipHash` | 요청 IP → `PiiHasher.ip()` | 프록시 뒤면 신뢰하는 프록시의 `X-Forwarded-For`만 |
| `channel` | 헤더 `X-Channel` (기본 WEB) | `WEB` / `APP` |
| `interval_ms` | **컨슈머가 계산** | 아래 참고 |

MongoDB에 저장할 때는 ERD 컬럼명(snake_case)으로 바꾸고 `expire_at = ts + behavior.retention_days`(180일)를 붙입니다.

## 어떻게 동작하나

```
요청 → 컨트롤러 mark() → afterCompletion에서 Kafka 비동기 send
     → behavior-sink 컨슈머: poll → interval_ms 계산 → insertMany(ordered:false, 1000건) → 오프셋 커밋
```

- **보내기는 요청을 막지 않습니다.** 비동기 send, 실패하면 버리고 실패 카운터(메트릭)만 올립니다. 로그 몇 건 유실보다 예매 응답 지연이 더 나쁩니다.
- **interval_ms는 컨슈머에서**: 키가 `ciHash`라 같은 사람의 이벤트는 항상 같은 파티션 → 같은 컨슈머 인스턴스로 순서대로 옵니다. 컨슈머가 메모리(LRU)에 `sessionId → 직전 ts`를 들고 차이를 계산합니다. 앱 서버 여러 대가 Redis로 직전 시각을 공유할 필요가 없습니다. 리밸런스 직후 첫 이벤트는 null이 될 수 있고, 위험 점수 배치는 null을 건너뜁니다.
- **오프셋은 insertMany 성공 뒤 커밋**합니다. 그래서 장애 시 같은 이벤트가 다시 들어올 수 있습니다 (아래 확인 필요 1).
- 형식이 깨진 메시지는 건너뛰고 로그만 남깁니다 (컨슈머가 멈추지 않게).

## 왜 이렇게 했나

- **앱이 Mongo에 직접 쓰지 않음**: 예매 오픈 순간 쓰기 폭주가 Mongo로 바로 가면 예매 API까지 느려집니다. Kafka가 완충하고 컨슈머가 묶어서 씁니다 (ERD 비고).
- **outbox를 쓰지 않음**: 행동 로그는 DB 트랜잭션과 묶일 필요가 없고 양이 많습니다. outbox에 넣으면 예약 이벤트 릴레이가 밀립니다.
- **실패 요청도 기록**: 봇은 실패를 빠르게 반복합니다. 성공만 남기면 가장 중요한 신호가 사라집니다.

## 위험 점수 규칙과의 연결

| 규칙 | 쓰는 이벤트·필드 |
|---|---|
| FAST_CLICK | `interval_ms` (세션 안 간격이 기준 미만으로 반복) |
| SAME_SEAT_RETRY | `SEAT_HOLD` + `meta.seatIds` + `responseStatus = 409` |
| CANCEL_AFTER_PAY | `CANCEL` + `meta.minutesAfterPurchase` |
| MULTI_ACCOUNT_SYNC | 같은 `ciHash`, 다른 `memberId`의 `SEAT_HOLD`가 짧은 시간 안에 |

타임라인(ADM-05)은 인덱스 `{member_id: 1, ts: 1}`로 회원의 이벤트를 시간순으로 읽습니다.

## 확인 필요 (팀)

1. **중복 저장**: `behavior_log`에 이벤트 ID 컬럼이 없어 재전달되면 같은 이벤트가 두 번 저장됩니다. 클릭 간격·반복 횟수가 부풀 수 있습니다. 제안: ERD에 `event_id`(String) + 유니크 인덱스 추가를 강동균에게 요청하고, 컨슈머는 중복 키 오류를 무시 (`replay_event`와 같은 방식). 그 전까지는 `meta.eventId`에 넣어 둡니다.
2. **이벤트 남기기 담당**: 위 표의 A·B·C 담당 API에 `mark()` 한 줄씩. 각자 기능을 만들 때 넣는 걸로 합의가 필요합니다.
3. **헤더 `X-Device-Id`, `X-Channel`**: 프런트에서 기기 지문을 만드는 방식(라이브러리 또는 localStorage UUID)을 정해야 합니다. 제안: 1차는 localStorage UUID.

## 테스트

- 409로 끝난 선점 요청도 이벤트 1건 발행
- Kafka가 내려가 있어도 예매 API 응답 시간·결과 변화 없음
- 같은 세션 이벤트 3건 → interval_ms 두 번째부터 채워짐
- 저장된 문서에 원문 IP·이메일·휴대폰 없음, `expire_at` = ts + 180일
