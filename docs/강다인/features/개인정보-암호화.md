# 개인정보 암호화·해시 모듈 (AES-256-GCM · HMAC-SHA256)

작성자: 강다인 · 코드 위치: `pii/` 모듈 (`com.jejari.pii.PiiCipher`, `PiiField`, `PiiMasker`) · 해시는 A의 `hmac/` 모듈 (`com.jejari.hmac.Pseudonymizer`)

> 상태: 암호화·마스킹 구현 완료 (단위 테스트 51개, 공격 시나리오 포함). 해시(HMAC)는 A(김성원)가 만든 `Pseudonymizer`를 그대로 씁니다 (README 9장 조정 기준).

## 한 줄 요약

원문이 다시 필요한 개인정보는 **AES-256-GCM으로 암호화**하되 암호문을 **그 행·그 컬럼에 묶어** 옮겨 붙일 수 없게 하고, 같은 값끼리 묶기만 하면 되는 값은 **HMAC-SHA256 해시**로 바꿔 저장한다.

## 무엇을 어디에 쓰나

| 값 | 방식 | 저장 위치 | 이유 |
|---|---|---|---|
| 휴대폰 번호 | 암호화 + 해시 | `member.phone_enc` + `enc_key_id`, `member.phone_hash` | 알림에 원문 필요, 중복 가입 탐지는 해시로 |
| CI | 해시만 | `member.ci_hash`, `identity_verification.ci_hash` 등 | 묶음 단위. 원문 불필요 |
| 이메일(로그인 실패 기록) | 해시만 | `login_attempt.email_hash` | 없는 계정 시도 추적 |
| IP, 기기 지문 | 해시만 | `*.ip_hash`, `*.device_hash` | 집중도·다계정 탐지 |
| 카드 번호 | 해시만 | `payment_method.method_hash` | 같은 카드 묶음 |
| 관리자 TOTP 비밀키 (P3) | 암호화 | `admin_user.mfa_secret_enc` | 검증에 원문 필요 |

비밀번호는 이 모듈이 아니라 Argon2id(`member_credential`)입니다. 리프레시 토큰은 SHA-256입니다.

## 사용법

```java
// 앱 시작 시 한 번 (키가 없거나 약하면 여기서 예외 → 앱이 뜨지 않음)
PiiCipher cipher = PiiCipher.fromEnv();

// 회원가입: member_id를 시퀀스로 먼저 받은 뒤 암호화한다 (행 ID가 AAD에 들어가므로)
long memberId = memberIdSequence.next();
Encrypted e = cipher.encrypt(phone, PiiField.MEMBER_PHONE, memberId);  // long PK 그대로
member.setPhoneEnc(e.cipherText());   // "v1.k1.…"
member.setEncKeyId(e.keyId());        // "k1"

// 알림 발송
String phone = cipher.decrypt(new Encrypted(m.getPhoneEnc(), m.getEncKeyId()),
                              PiiField.MEMBER_PHONE, m.getMemberId());

// enc_key_id 컬럼이 없는 곳 (admin_user.mfa_secret_enc): 암호문 안의 키 ID를 쓴다
String secret = cipher.decrypt(a.getMfaSecretEnc(), PiiField.ADMIN_MFA_SECRET, a.getAdminId());

// 해시: 묶기만 하는 값 → A의 com.jejari.hmac.Pseudonymizer (정규화까지 이 안에서 한다)
pseudonymizer.ci(ci);  pseudonymizer.phone(phone);  pseudonymizer.email(email);
pseudonymizer.ip(ip);  pseudonymizer.device(fp);    pseudonymizer.paymentMethod(cardNo);

// 화면 표시용 마스킹
PiiMasker.name("홍길동");          // 홍*동
PiiMasker.phone("010-1234-5678"); // 010-****-5678
PiiMasker.email("abcdef@x.com");  // ab***@x.com
```

- 다른 파트는 **해시를 직접 만들지 말고 반드시 `Pseudonymizer`를 씁니다.** 정규화나 키가 하나라도 다르면 같은 사람이 다른 해시가 되어 다계정 묶음과 매수 제한이 깨집니다.
- 새 암호화 컬럼이 생기면 `PiiField`에 상수를 추가합니다. 기존 상수의 이름은 바꾸지 않습니다 (바꾸면 저장된 암호문이 모두 복호화되지 않음).
- JPA `@GeneratedValue(strategy = SEQUENCE)`면 `persist()` 직후 ID가 채워지므로, `persist` → `encrypt` → 같은 트랜잭션 안에서 `setPhoneEnc` 순서로 해도 됩니다.

## 어떻게 동작하나

```
encrypt(plain, MEMBER_PHONE, "1001")
 → 평문을 16바이트 단위로 채움 (0x80 + 0x00…)     ← 길이 숨김
 → IV 12바이트 SecureRandom (매번 새로)
 → AES/GCM/NoPadding, 태그 128비트
     AAD = "jejari-pii|v1|k1|member.phone_enc|1001" ← 형식·키·컬럼·행에 묶음
 → "v1.k1." + base64url( IV ‖ 암호문 ‖ 태그 )
```

- 휴대폰 번호 암호문 = 65자, 최대 길이(64바이트) 평문도 200자 안. `VARCHAR2(200)`에 들어갑니다.
- 복호화 때 AAD를 똑같이 다시 만들어 넣습니다. 한 글자라도 다르면 태그가 맞지 않아 `PiiDecryptException`이 납니다. 메시지에는 값을 넣지 않고, 실패 원인(변조·키·컬럼·행)도 구분하지 않습니다 (공격자에게 힌트를 주지 않음).

## 막는 공격 (모두 테스트로 확인)

| 공격 | 방법 | 막는 장치 |
|---|---|---|
| 암호문 변조 | 암호문 아무 비트나 바꿈 | GCM 인증 태그 (모든 비트 하나씩 바꿔 보는 테스트) |
| **행 바꿔치기** | DB 쓰기 권한을 얻은 공격자가 자기 `phone_enc`를 피해자 행에 복사 → 피해자 알림·인증번호가 공격자에게 감 | AAD에 행 ID |
| 컬럼 바꿔치기 | 다른 컬럼 암호문을 옮겨 붙임 | AAD에 테이블.컬럼 |
| 키 ID 바꿔치기 | `v1.k1.` → `v1.k2.` 또는 `enc_key_id`만 수정 | AAD에 키 ID + 컬럼 값과 암호문 안 값 일치 확인 |
| 형식 버전 바꿔치기 | `v1` → `v2` | AAD에 형식 버전 |
| 길이로 추측 | 암호문 길이로 평문 길이 짐작 | 16바이트 단위 패딩 (10·11자리 번호가 같은 길이) |
| IV 재사용 | 같은 IV 두 번 → GCM 키스트림 노출 | 매번 SecureRandom, 키 하나당 2^32건까지 안전 |
| 약한 키 | `0000…` 같은 테스트 키, 버전끼리 같은 키, HMAC 키 재사용 | 생성 시 거부 → 앱 기동 실패 |
| 키 노출 | 예외 메시지·`toString()`·로그 | 메시지에 키·평문·암호문 없음 (테스트) |
| 구분자 주입 | 행 ID에 `\|` 넣어 AAD 경계 흐리기 | 행 ID·테이블·컬럼 글자 제한 |

## 키 관리

| 키 | 설정 | 형식 | 교체 |
|---|---|---|---|
| 암호화 키 (여러 버전) | `JEJARI_ENC_KEYS_FILE`(파일 경로, 권장) 또는 `JEJARI_ENC_KEYS` | `k1:<base64 32바이트>,k2:<…>` | 새 버전을 추가하고 `JEJARI_ENC_ACTIVE`를 바꿈. 옛 키는 복호화용으로 남김 |
| 활성 암호화 키 | `JEJARI_ENC_ACTIVE` | `k1` | |
| 해시 키 (A 모듈) | `JEJARI_HMAC_KEY` | base64 32바이트 이상 | **프로젝트 기간 고정** (바꾸면 모든 `*_hash` 재계산 필요) |

- 생성: `openssl rand -base64 32` (키마다 따로. 암호화 키와 HMAC 키를 같은 값으로 쓰면 기동 실패)
- 키 ID는 소문자·숫자 1~20자입니다 (`k1`, `k2`, `k20261201`).
- **시연 서버는 파일 방식**: 환경변수는 `docker inspect`, `/proc/<pid>/environ`으로 누구나 볼 수 있습니다. Docker secret(`/run/secrets/enc_keys`)이나 권한 600 파일로 두고 경로만 `JEJARI_ENC_KEYS_FILE`에 넣습니다.
- 키는 저장소·`application.yml`·로그·메신저에 넣지 않습니다. 로컬은 `.env`(gitignore)에 각자 만듭니다.

## 왜 이렇게 했나

- **GCM**: 암호화와 변조 검출(인증 태그)을 한 번에 합니다. CBC는 별도 MAC이 필요하고, 패딩 오라클 같은 실수 여지가 있습니다.
- **AAD에 행 ID까지**: 처음 설계(테이블.컬럼만)로는 같은 컬럼의 다른 행끼리 암호문을 바꿔 넣는 공격을 못 막았습니다. 암호화는 "읽지 못하게"만 하고 "제자리에 있는지"는 AAD가 보장합니다.
- **키 ID를 암호문 안에도**: `admin_user`에는 `enc_key_id` 컬럼이 없어, 키를 교체하면 어느 키로 풀지 알 수 없었습니다. 스키마를 고치지 않고 해결합니다.
- **JPA `AttributeConverter`를 쓰지 않음**: 컨버터는 행 ID를 모르고 `enc_key_id`도 같이 채울 수 없습니다. 서비스에서 `encrypt()`를 명시적으로 부릅니다.
- **해시에 HMAC**: 그냥 SHA-256이면 휴대폰 번호(경우의 수 약 1억)는 전수 대입으로 바로 되돌릴 수 있습니다. 비밀 키가 있어야 계산할 수 있게 합니다.

## 이 모듈이 막지 못하는 것 → 팀 체크리스트

암호화는 **DB만 털린 경우**를 막습니다. 아래는 모듈 밖에서 막아야 합니다.

| # | 위험 | 대책 | 담당 |
|---|---|---|---|
| 1 | 키가 저장소에 커밋됨 | CI에 gitleaks 비밀값 검사 추가, `.env`는 gitignore (되어 있음) | E (CI) |
| 2 | 복호화한 평문이 로그에 찍힘 | DTO `toString()` 마스킹, 요청 본문 로깅 금지, 로그 출력 전 휴대폰·이메일 패턴 마스킹 필터 | 전원 / E |
| 3 | 앱 서버 자체가 털림 (키+메모리) | 이 범위는 못 막음. 복호화 지점을 알림 발송·관리자 해제 두 곳으로 제한해 피해 범위를 줄임 | D |
| 4 | 관리자가 마스킹 해제를 남용 | SUPERVISOR만 해제, 사유 필수, `admin_action`에 이력 (ADM-04, `/admin/cases/{id}/unmask`) | D |
| 5 | 관리자 계정 탈취 | 관리자 MFA(P3), 로그인 실패 잠금, 세션 만료 | E |
| 6 | JWT에 개인정보 | payload는 `memberId`만 | E |
| 7 | API 응답에 개인정보 원문 | 응답 DTO는 마스킹 값만. 본인 조회도 마스킹 | 전원 |
| 8 | 전송 구간 도청 | 시연 서버 HTTPS 강제, DB·Redis·Kafka는 외부 포트 닫기 | E |
| 9 | DB 계정 권한 과다 | 앱 계정은 DML만, DDL 권한 분리 | E |
| 10 | 의존성 취약점 | Dependabot 또는 OWASP dependency-check | E |
| 11 | 백업·덤프 유출 | 덤프 파일은 저장소·공유 드라이브에 올리지 않음 (`*.hprof`는 gitignore 되어 있음) | 전원 |

## 테스트

실행: `cd pii && ./gradlew test` (JDK 21이 없으면 Gradle이 자동으로 내려받음). 51개 통과.

- 기본: 암호화 → 복호화 원문 일치 (한글·이모지·최대 길이), 1000번 암호화 모두 다른 값, 길이 200자 이내, 길이 숨김
- 공격: 위 "막는 공격" 표의 항목마다 테스트 1개 이상
- 키: 누락·길이 오류·모두 같은 바이트·버전 간 중복·HMAC 키 재사용·잘못된 ID → 생성 실패, 메시지에 키 없음
- 키 교체: `k1` 암호문을 `k2` 활성 상태에서 복호화
- 16스레드 2000건 동시 처리
- 마스킹: 이름·휴대폰·이메일 경계값, null·빈 값
- 해시 정규화(`phone("010-1234-5678") == phone("01012345678")`)는 A의 `PseudonymizerTest`에서 확인
