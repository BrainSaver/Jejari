# 개인정보 암호화·해시 모듈 (AES-256-GCM · HMAC-SHA256)

작성자: 강다인 · 코드 위치: `common/crypto/PiiCipher.java`, `common/crypto/PiiHasher.java` (예정)

> 상태: 설계 초안 (코드 전). 모든 파트가 쓰는 공용 모듈이라 인터페이스를 먼저 고정합니다.

## 한 줄 요약

원문이 다시 필요한 개인정보는 **AES-256-GCM으로 암호화**하고, 같은 값끼리 묶기만 하면 되는 값은 **HMAC-SHA256 해시**로 바꿔 저장한다.

## 무엇을 어디에 쓰나

| 값 | 방식 | 저장 위치 | 이유 |
|---|---|---|---|
| 휴대폰 번호 | 암호화 + 해시 | `member.phone_enc` + `enc_key_id`, `member.phone_hash` | 알림에 원문 필요, 중복 가입 탐지는 해시로 |
| CI | 해시만 | `member.ci_hash`, `identity_verification.ci_hash` 등 | 묶음 단위. 원문 불필요 |
| 이메일(로그인 실패 기록) | 해시만 | `login_attempt.email_hash` | 없는 계정 시도 추적 |
| IP, 기기 지문 | 해시만 | `*.ip_hash`, `*.device_hash` | 집중도·다계정 탐지 |
| 카드 번호 | 해시만 | `payment_method.method_hash` | 같은 카드 묶음 |
| 관리자 TOTP 비밀키 (P3) | 암호화 | `admin_user.mfa_secret_enc` | 검증에 원문 필요 |

비밀번호는 이 모듈이 아니라 Argon2id(`member_credential`)입니다. 리프레시 토큰은 SHA-256입니다.

## 인터페이스

```java
// 암호화: 원문이 다시 필요한 값
public record Encrypted(String cipherText, String keyId) {}   // → phone_enc, enc_key_id

public interface PiiCipher {
    Encrypted encrypt(String plain, String aad);              // aad 예: "member.phone_enc"
    String decrypt(String cipherText, String keyId, String aad);
}

// 해시: 묶기만 하는 값. 정규화까지 이 안에서 한다
public interface PiiHasher {
    String ci(String ci);
    String phone(String phone);      // 숫자만 남김: 010-1234-5678 → 01012345678
    String email(String email);      // trim + 소문자
    String ip(String ip);
    String device(String fingerprint);
    String card(String cardNo);      // 숫자만
}
```

다른 파트는 **해시를 직접 만들지 말고 반드시 `PiiHasher`를 씁니다.** 정규화나 키가 하나라도 다르면 같은 사람이 다른 해시가 되어 다계정 묶음과 매수 제한이 깨집니다.

## 어떻게 동작하나

**암호화 (AES-256-GCM)**

```
encrypt(plain, aad)
 → 활성 키(keyId) 선택
 → IV 12바이트 SecureRandom (매번 새로)
 → Cipher "AES/GCM/NoPadding", 태그 128비트, AAD = aad
 → Base64( IV ‖ 암호문 ‖ 태그 ), keyId 반환
```

- 휴대폰 11바이트 → 12 + 11 + 16 = 39바이트 → Base64 52자. `VARCHAR2(200)`에 충분합니다.
- 복호화는 저장된 `enc_key_id`로 키를 찾고, 태그가 안 맞으면(변조·키 오류·AAD 불일치) `PiiDecryptException`을 던집니다. 예외 메시지에 값을 넣지 않습니다.

**해시 (HMAC-SHA256)**

```
phone("010-1234-5678") → 정규화 "01012345678" → HMAC(hashKey, "phone:" + 값) → 16진수 64자
```

- `"phone:"` 같은 종류 접두어를 붙여, 우연히 같은 문자열인 서로 다른 종류의 값이 같은 해시가 되지 않게 합니다.
- 결과는 16진수 소문자 64자라서 `VARCHAR2(64)`와 맞습니다.

## 키 관리

| 키 | 환경변수 | 형식 | 교체 |
|---|---|---|---|
| 암호화 키 (여러 버전) | `JEJARI_ENC_KEYS` | `k1:<base64 32바이트>,k2:<…>` | 새 버전을 추가하고 `JEJARI_ENC_ACTIVE`를 바꿈. 옛 키는 복호화용으로 남김 |
| 활성 암호화 키 | `JEJARI_ENC_ACTIVE` | `k1` | |
| 해시 키 | `JEJARI_HASH_KEY` | base64 32바이트 | **프로젝트 기간 고정** (바꾸면 모든 `*_hash` 재계산 필요) |

- 키는 저장소·`application.yml`·로그에 넣지 않습니다. 로컬은 `.env`(gitignore), 팀 공용 값은 메신저가 아니라 각자 생성 후 시연 서버에만 등록합니다.
- 생성: `openssl rand -base64 32`
- 키가 없거나 32바이트가 아니면 **앱 기동을 실패**시킵니다 (조용히 평문으로 저장되는 사고 방지).

## 왜 이렇게 했나

- **GCM**: 암호화와 변조 검출(인증 태그)을 한 번에 합니다. CBC는 별도 MAC이 필요하고, 패딩 오라클 같은 실수 여지가 있습니다.
- **IV를 매번 랜덤**: GCM은 같은 키로 IV가 한 번이라도 겹치면 안전성이 무너집니다. 96비트 랜덤 IV는 키 하나당 수십억 건까지 안전해서 이 프로젝트 규모에 충분합니다.
- **AAD에 "테이블.컬럼"**: 다른 컬럼의 암호문을 복사해 붙여 넣으면 복호화가 실패합니다.
- **JPA `AttributeConverter`를 쓰지 않음**: 컨버터는 컬럼 하나만 다룰 수 있어 `enc_key_id`를 같이 채울 수 없습니다. 서비스에서 `encrypt()`를 명시적으로 부르고 두 컬럼을 함께 설정합니다.
- **해시에 HMAC**: 그냥 SHA-256이면 휴대폰 번호(경우의 수 약 1억)는 전수 대입으로 바로 되돌릴 수 있습니다. 비밀 키가 있어야 계산할 수 있게 합니다.

## 주의할 점

- `Cipher` 객체는 스레드 안전하지 않습니다. 호출마다 `Cipher.getInstance()`로 새로 만듭니다.
- 평문이 로그에 찍히지 않게 DTO의 `toString()`을 마스킹합니다. 화면 표시용 마스킹은 `PiiMasker`로 제공합니다: 이름 `홍*동`, 휴대폰 `010-****-5678`, 이메일 `ab***@example.com`.
- 성과 지표 "평문 개인정보 0건"(기능설계서 10장)은 DB·MongoDB·로그·JWT payload를 검사합니다. JWT에는 `memberId`만 넣습니다.
- 키 교체 후 옛 암호문을 새 키로 다시 암호화하는 배치는 확장 계획입니다 (ERD "확장 계획 → 해시 키 교체").

## 테스트

- 암호화 → 복호화 결과가 원문과 같음
- 같은 값을 두 번 암호화하면 암호문이 다름 (IV가 매번 다름)
- 암호문 1바이트 변조, 다른 AAD, 다른 키 → 모두 `PiiDecryptException`
- `k1`로 암호화 → 활성 키를 `k2`로 바꿈 → `k1` 암호문 복호화 성공
- `phone("010-1234-5678") == phone("01012345678")`
- 키 누락 시 컨텍스트 로딩 실패
