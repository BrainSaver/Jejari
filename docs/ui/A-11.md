# A-11 봇 대회 결과

- 기능: DATA-03 (봇 탐지 평가) — 봇 대회 결과를 관리자 화면에서 읽기
- 담당: 강동균
- 시안: 없음 (운영 도구)
- 구현: `frontend/src/admin/Contests.jsx` (+ 서버 `admin/contest/` `ContestAdminController`·`ContestResultService`·`ContestTally`) (2026-11-25)

## 목적

봇 대회(블라인드 봇 + 진짜 사람이 같은 운행을 사는 시험)의 결과를 발표·회의 때 **관리자 로그인만으로** 보여 줍니다.
지금까지는 진행자 PC의 `loadtest/contest/results/{태그}/eval.txt`(평가 스크립트 출력)를 열어야 했습니다.

**읽기 전용입니다.** 대회 진행(봇 실행·평가 스크립트)은 진행자 PC의 진행 화면(`loadtest/contest/web`)이 하고,
이 화면은 DB를 다시 읽기만 합니다. 웹에서 서버 명령·봇을 실행하는 기능은 일부러 두지 않았습니다
(관리자 페이지에서 임의 코드를 돌리는 구멍이 되고, 봇이 앱과 같은 CPU를 써서 결과가 흐려짐).

## 화면 구성

| 영역 | 내용 |
|---|---|
| 대회 고르기 | 참가자 이메일 태그별 목록 (최근 30개, 봇·사람 계정 수·첫 가입일). 참가자가 여러 운행을 예약했으면 운행도 고름 (기본: 예약이 가장 많은 운행) |
| KPI 4칸 | 봇 탐지(계정) · **봇이 결제한 좌석**(실제 피해) · **사람 오탐**(목표 5% 이하, 있으면 빨강) · 사람이 결제한 좌석 |
| 종류별 결과 | 종류(botb·botc·human…)마다 계정·명의·결제/잡고 안 낸 좌석·선점 시도·제한 거절·탐지·최고 점수·순번 -초·**막힌 층**(매수제한·규칙·순번조정·관리자판정, 없으면 "뚫림") 또는 오탐 |
| 걸린 규칙 | 종류 × 대상(CI·결제수단·기기) × 규칙별로 그 규칙의 케이스가 연결된 계정 수. 사람 줄의 규칙 = 오탐을 낸 규칙 |

## 숫자를 내는 규칙 (eval_contest.sh와 같음)

- 참가자: 이메일 `lt{태그}.{종류}.g{묶음}.{번호}@loadtest.example.com`, 종류가 `bot…` 또는 `human…`. 진행 화면의 점검 계정(`lt{태그}p.probe…`)·부하 시험 계정은 빠짐
- 탐지: 그 계정의 CI·결제수단 해시, 행동 로그의 기기 해시 중 하나라도 의심 케이스(`suspicious_case`)가 있으면
- 순번 -초: 연결 대상의 최고 위험 점수 × `risk.penalty_ms_per_point`
- 행동 로그(MongoDB)를 못 읽으면 선점 시도·제한 거절·기기 연결만 빼고 나머지를 보여 줌
