## 목적

명절 예매가 열리는 순간 **지금 얼마나 몰리고, 어디가 느리거나 깨지는지**를 관리자 로그인만으로 한 화면에서 봅니다.
Grafana "제자리 · 앱 개요"와 같은 지표(127.0.0.1에만 열려 있어 서버 접속이 필요)를 관리자 화면 안으로 가져온 것입니다.
큰 회사 관제 화면의 흔한 순서를 따릅니다: ① 지금 괜찮은가 → ② 얼마나 몰리나 → ③ 어디가 병목인가.

"크게 보기"는 화면 전체(관제실 TV)로 띄운다. 앱 서버가 떠 있지 않던 시각은 그래프에서 0이 아니라 빈칸이다.

### 흐름도 읽는 법

- **파란 점** = 정상 요청, **빨간 큰 점** = 5xx (영역 노드에서 터짐), **노란 빈 점** = 429 요청 제한 (노드 앞에서 되돌아감), **회색 점** = 그 밖의 4xx (409 포함)
- 점 수는 꾸민 움직임이 아니라 **실제 비율** 그대로: 가장 바쁜 선이 초당 점 25개를 넘지 않게 "점 1개 = N건"을 1·2·5 단위로 고르고 범례에 적는다. 요청과 저장소 작업은 단위를 따로 쓴다 (요청 1건이 Redis 명령 여러 개라)
- 선 굵기·노드 크기 = 초당 값 (로그). 노드 테두리 초록 정상 · 노랑 주의(5xx 1%↑, 4xx 25%↑, 평균 1초↑) · 빨강 위험(5xx 5%↑, 고리가 번짐)
- 6초 넘게 새 값이 안 오면 점을 멈추고 "연결 끊김"을 덮는다 (옛 값으로 움직이는 화면을 믿지 않게)
- 노드에 마우스를 올리면 자세한 값, "표로 보기"는 같은 값을 표로 (색을 못 쓰는 경우)
- 움직임 줄이기 설정(prefers-reduced-motion)이면 점 없이 선 굵기·숫자만

### 업무 영역 (URI 템플릿으로 나눔, `TrafficService.group`)

대기열 `/api/v1/runs/*/queue*` · 좌석 조회 `/api/v1/runs/*/seats*` · 예약·결제 `/api/v1/reservations*`·`/api/v1/waitlists*` · 로그인·내 정보 `/api/v1/auth*`·`/api/v1/me*` · 관리자 `/api/v1/admin*` · 기타 (actuator 제외)

### 데이터 놓침·밀림 문턱 (`TrafficService.pipelineReasons`)

| 지표 | 주의 | 위험 | 왜 |
|---|---|---|---|
| 행동 로그 버림 (보내기 큐 넘침, 5분) | 1건 | 1,000건 | 몰리는 순간의 봇 탐지 재료가 빠짐 |
| 행동 로그 Kafka 전송 실패 (5분) | 1건 | 1,000건 | 〃 |
| 행동 로그 형식 오류 (5분) | 1건 | 저장한 것보다 많음 | 커밋되어 다시 오지 않고 **밀림에도 안 잡힘**. 형식이 통째로 깨지면(화면 배포 실수) 전부 여기로 |
| 행동 로그 적재 멈춤 (30초) | 받음 1/초↑인데 저장이 받음의 10% 미만 | — | MongoDB가 멈추면 밀림은 천천히 쌓여 문턱까지 몇 분 |
| 보내기 큐 | 50% | 90% | 다 차면 버리기 시작 |
| Kafka 소비 밀림: 예약 흐름 (좌석 정리·알림·위험 신호·환불) | 100건 | 1,000건 | 바로바로 따라가야 함 |
| Kafka 소비 밀림: 대량 적재 (행동 로그·재생 기록) | 1만 건 | 10만 건 | 몰릴 때 잠깐 밀리는 것은 정상 |
| Kafka 소비 밀림을 잴 수 없음 | 측정 실패 | — | Kafka가 죽으면 밀림이 "0"이 아니라 "모름" |
| outbox 가장 오래 기다린 이벤트 | 30초 | 2분 | 릴레이는 1초 안팎. 2분이면 예약 이벤트가 멈춘 것 |
| outbox 발행 실패 | 1건 | — | 재시도 대기 |

흐름도의 Kafka 노드는 밀림·버림, MongoDB 노드는 적재 멈춤을 테두리 색과 이름표로 보여 준다.

**알림**(장애 아님): 트래픽 급증(최근 24시간 중앙값의 3배↑, 초당 5건↑), 429 요청 제한 5%↑.

상태와 KPI "지금" 값은 **최근 30초**로 잰다 (흐름도와 같음). 그래프는 기간별 간격(15초~10분)으로 잰 평균이라 그래프 끝 값과 KPI가 조금 다를 수 있다. 명절 예매 시작에는 당연히 몰리므로 급증 자체는 빨간색이 아니다 — 그때 함께 볼 것은 응답 시간과 오류율.

## API

| 메서드 | 경로 | 권한 | 설명 |
|---|---|---|---|
| GET | `/api/v1/admin/traffic?range=30m\|1h\|6h\|24h` | VIEWER | 상태·KPI·그래프(공통 시각 `t` + 선별 값)·API 표. 4초 캐시 |
| GET | `/api/v1/admin/traffic/flow` | VIEWER | 흐름도 값 (최근 30초 초당). 1.5초 캐시 |

- 서버가 Prometheus(`jejari.ops.prometheus-url`, 기본 `http://127.0.0.1:9090`, 환경변수 `JEJARI_PROMETHEUS_URL`)에 **고정 쿼리**만 보낸다. 화면은 기간만 고르므로 관리자 화면을 통해 아무 PromQL이나 보내는 통로가 없다
- Prometheus가 꺼져 있으면 `available: false` + 이유 → 화면은 "확인 불가" 띠. 앱 나머지는 영향 없음 (3초 시간 초과)
- 대기열 인원 지표 `jejari_queue_waiting`·`jejari_queue_active`는 이번에 새로 내보낸다 (`QueueMetrics`, 대기열 Redis 키를 읽기만). 배포 직후에는 그래프 앞부분이 비어 있다
- 개인정보 없음 (요청 수·응답 시간·자원)

## 무엇을 세나 · 얼마나 늦나

| 항목 | 출처 | 비고 |
|---|---|---|
| 요청 | `http_server_requests_seconds_*` (Spring, URI 템플릿·상태별) | actuator(수집)와 이 화면 자신의 폴링(`/api/v1/admin/traffic*`)은 뺀다. 2초 폴링이 관리자 한 명당 초당 0.5건이라 빼지 않으면 조용한 서버에서 "관리자"가 가장 바빠 보인다 |
| 평소 | 최근 24시간 초당 요청의 중앙값 (지금 10분 제외) | 1시간 평균은 몰림이 길어지면 몰림 자체가 "평소"가 되어 버려 바꿈. 앱을 처음 띄운 직후 10분은 "평소 값 쌓는 중" |
| 어제 같은 시각 | 같은 쿼리 `offset 1d` | Prometheus 보관 15일 |
| 재시작 | `process_start_time_seconds`가 기간 안인 시각 | 배포마다 앱이 다시 뜨므로 배포 표시로 씀. 36px 안에 붙은 것은 하나로 |
| Redis / Oracle / MongoDB / Kafka | Lettuce 명령 · Hikari 커넥션 사용 · Mongo 드라이버 명령 · KafkaTemplate 발행 (초당) | Oracle은 쿼리 수가 아니라 커넥션 대여 수 (트랜잭션 하나 ≈ 1) |
| 힙 | 힙 사용 합 ÷ 최대가 0보다 큰 풀의 최대 | G1은 Old Gen만 최대(= 힙 전체)를 내고 Eden·Survivor는 -1 |
| 행동 로그 | `jejari_behavior_{sent,dropped,failed,stored,skipped}_total`, `jejari_behavior_queue_size` | `BehaviorPublisher`·`BehaviorSink`가 세던 값을 `admin/traffic/PipelineMetrics`가 내보냄. Kafka 발행 수(흐름도)에도 더함 — 행동 로그 전용 프로듀서는 KafkaTemplate 관측에 안 잡힘 |
| Kafka 소비 밀림 | `jejari_kafka_consumer_lag{group}` | 15초마다 AdminClient로 (끝 오프셋 − 커밋 오프셋). Kafka 자체 도구(kafka-consumer-groups.sh)와 같은 값인 것 확인 |
| outbox 미발행 | `jejari_outbox_{pending,failed,oldest_seconds}` | 15초마다. `ix_outbox_pending`(PENDING·FAILED 행만 담는 함수 기반 인덱스)으로 그 행만 읽음 |

**늦음**: 앱 → Prometheus 5초 + rate 창 30초 + 화면 폴링(흐름도 2초·나머지 10초) + 서버 캐시(1.5초·4초). 장애가 나면 흐름도는 5~10초, 상태 띠는 10~20초 안에 바뀌고, 끝나면 30~45초 안에 정상으로 돌아온다 (아래 실측).

## 실측 검증 (2026-11-20, 로컬 docker compose + 앱 1대 + k6)

1. **정해 둔 양과 같은가**: k6로 대기열 100/초 · 좌석 50/초 · 없는 주소 10/초를 3분 보냄 → 흐름도 100.00 · 50.00 · 10.00, 전체 159.98/초, API 표 비중 62.5% · 31.2% · 6.2% (정확히 맞음)
2. **장애를 잡는가**: 섞인 부하(대기열 줄 서기 20/초, 상태 조회 150/초, 좌석 60/초, 틀린 로그인 5/초) 중 Redis를 40초 멈춤 → 28초 안에 상태 "위험 · 5xx 70%", 대기열 노드 빨강·빨간 점, Redis 명령 211 → 1.9/초, 탭 제목 "● 위험"
3. **회복을 바로 보이는가**: Redis를 다시 켠 뒤 30초에 5xx 12%로 내려가는 중 (고치기 전에는 그래프 마지막 점을 써서 1분 창이라 30초 뒤에도 43%로 오히려 올라가 보였음 → "지금" 값을 30초 창으로 바꿈)
4. 이 검증에서 고친 것: 흐름도 노드 이름표·색이 첫 값에 멈춰 있던 버그 (그리기 루프가 처음 받은 값을 계속 씀), 4xx 폭증(모든 요청 403·404)을 "정상"으로 보이던 것, 이 화면 자신의 폴링이 섞이던 것

### 데이터 놓침·밀림 실측 (2026-11-20, 같은 환경, 행동 로그 약 20건/초)

| 상황 | 화면 |
|---|---|
| dev 모드 그대로 (세션 ID가 "dev-session"이라 적재기가 형식 오류로 전부 건너뜀) | **위험** "행동 로그 1,402건 형식 오류로 적재 안 됨 — 저장 0건보다 많음". 고치기 전에는 밀림 0·오류 없음이라 **정상으로 보였음** |
| MongoDB 60초 정지 | 적재 20 → 0/초, 행동 로그 적재 밀림 896건 → 다시 켜자 1건으로 따라잡음 (유실 없음). 이때 상태 띠가 조용해서 "적재 멈춤" 규칙 추가 |
