돈이 오가는 부분(결제)과, 그 결과를 다른 파트에 확실히 전달하는 부분(이벤트)을 맡는다.

3꼭 기억할 규칙 7개

모든 코드가 이 7개를 지키면 중복 결제·순서 꼬임이 안 생깁니다.

  1. Redis는 빠른 1차 판정, Oracle이 최종 판정. Redis가 통과시켜도 DB가 거절하면 거절이다.
  2. 마감 시각의 원본은 reservation.pay_deadline_at 하나. 다른 곳(좌석, Saga, 대기자, Redis)은 복사본이라 바꿀 때 같이 바꾼다. 시간은 앱 시계로 계산한다.
  3. 상태를 바꿀 땐 "지금 상태가 X일 때만" 바꾸고, 바뀐 행 수를 확인한다. 0행이면 누가 먼저 처리한 것이니 그 뒤 일을 하지 않는다. 이게 중복 방지의 핵심이다.
  4. 예약 행을 먼저 잠그고 결제·좌석·Saga를 바꾼다. 순서가 같아야 데드락이 안 난다.
  5. PG 호출과 Kafka 발행은 DB 트랜잭션 밖에서. 락을 쥔 채 외부 응답을 기다리지 않는다.
  6. 이벤트는 DB에 먼저 적는다(Outbox). 상태를 바꾼 같은 트랜잭션 안에서, 예약 행을 바꾼 뒤에 INSERT한다.
  7. 숫자 값(시간·횟수)은 코드에 박지 않고 app_policy에서 읽는다.

4기능별 핵심 (구현할 때 해당 칸만)

4-1. 결제 시작 PAY-01 · concurrency.md §4

  • 무엇: 예약을 HOLD → PAYMENT_PENDING으로 바꾸고 결제를 요청한다.
  • 마감 연장: 마감을 지금 + 4분(PG 3분 + 여유 1분)과 기존 마감 중 늦은 쪽으로. 줄어들지 않고 딱 한 번만 늘어난다.
  • 좌석 확인: 좌석 행 수가 예상과 다르면 좌석을 이미 잃은 것 → 거절.
  • 커밋 뒤: Redis 좌석 키도 연장 → PG에 승인 요청.
  • 결제 실패 후 재시도는 없다 → 다시 예매.
    재시도마다 마감이 늘어나면 한 사람이 좌석을 오래 붙잡게 된다.

4-2. 결과 처리 PAY-02·03 · §5

PG 응답, 콜백, 스캐너 조회 어느 경로로 와도, 몇 번 와도 결과가 같아야 한다. 먼저 예약 행을 잠그고 payment.status를 본다.

payment 상태하는 일
REQUESTED (처음)승인이면 확정, 실패면 예약 만료
APPROVED + 예약 확정됨이미 끝남, 성공 응답만
APPROVED + 예약 안 됨"환불 진행 중" 응답
REFUNDED"환불 완료" 응답
FAILED인데 승인이 옴늦은 승인: 돈은 빠졌는데 좌석은 이미 풀림 → 전액 환불, 예약은 되살리지 않음
  • 확정: 좌석 SOLD → 결제 APPROVED → 예약 CONFIRMED → Saga DONE → 이벤트 RESERVATION_CONFIRMED
  • 실패: 결제 FAILED → 예약 EXPIRED(사유 PAY_FAILED) → 좌석 반환. 따로 "결제 실패" 예약 상태는 없다.

4-3. PG 결과 확인 스캐너 PAY-04 · §6.2

  • 무엇: 마감이 지났는데 결과를 모르는 결제를 PG에 다시 물어본다.
  • 강동균의 HOLD 만료 스캐너와 쿼리를 분리 → 내 쪽이 밀려도 좌석 만료는 계속 돈다.

4-4. Saga · 좌석 복구 EVT-05 · §7

  • 예약이 단계(선점 → 결제 중 → 확정)를 밟는 동안 Saga가 진행 상황을 들고 있다.
  • 실패·만료 시: COMPENSATED로 바꾸고 좌석 반환·매수 카운터 감소·Redis 정리.
  • 실제 좌석 해제는 강동균 로직을 reservation_id로 호출. 두 번 불러도 결과가 같아야 한다.
  • 늦은 승인 환불(§7.3, P2): cancellation에 전액·수수료 0 기록 → PG 환불 → 완료 시 REFUNDED

4-5. Outbox EVT-01·02 · §11

DB 커밋과 Kafka 발행을 동시에 성공시키는 방법이 없다. 그래서 DB에 "보낼 이벤트"를 같이 적고, 릴레이가 나중에 보낸다.

순서 보장 장치

  • Kafka 키는 항상 reservation_id → 같은 예약 이벤트는 같은 파티션.
  • 샤드 번호 = ORA_HASH(TO_CHAR(키), 15). 키는 항상 문자열로. 숫자로 넘기면 샤드가 달라져 순서가 깨진다.
  • 샤드 하나는 릴레이 인스턴스 하나만 맡는다 (Redis 리스).
  • seq 순서로 하나씩 보내고, 실패하면 그 샤드는 거기서 멈춘다. 뒤 이벤트가 앞을 추월하지 않게.
  • SKIP LOCKED는 쓰지 않는다. 건너뛰면 순서가 깨진다.
  • 5번 실패하면 FAILED, 그 샤드만 정지 + 알림. 관리자가 되돌리면 재개.
  • 프로듀서 설정: enable.idempotence=true, acks=all
  • 1차 구현: 샤드 1개, 인스턴스 1대

4-6. Inbox EVT-03 · §12

  • 한 트랜잭션: processed_event INSERT(이미 있으면 건너뜀) → 업무 처리 → 커밋 → 그 다음에 Kafka 오프셋 커밋.
  • 8일 보관. Kafka 보관이 7일이라 그보다 길어야 재전달 중복을 막는다.

4-7. 결제 멱등 EVT-04 · §1

  • 버튼 누를 때마다 클라이언트가 UUID를 만들어 Idempotency-Key 헤더로 보낸다. 재시도는 같은 키.
  • 3중 방어
    1. Redis idem:pay:{예약ID}:{키}
    2. DB UNIQUE(reservation_id, idempotency_key)
    3. 예약당 승인 1건 인덱스 ux_payment_approved

4-8. 알림 EVT-06·WL-04

  • 실제 발송 없음. notification 테이블에 쌓고 알림함으로 보여 준다.
  • 종류: 취소표 제안, 결제 기한 임박, 예약 만료, 대기 건너뜀, 환불 완료
  • 1차 구현: INSERT만. 알림함 화면(U-11)은 나중에.
